# embarch: feature roadmap

**Status:** active, 2026-07-20. Restructured 2026-08-17 — see Changelog.

## Shipped foundation

The suite's original numbered milestones (Flash, Token, Study Designer scoping + implementation, Dev Bench scoping, Onboarding) are done and shipped as real `v0.1.0` releases across all three code-bearing repos (see Release, below) — they're recorded here as a foundation rather than as active numbered milestones, since none of them are still open work:

- **Flash** — EmbArch flashes a chip without USB-forwarding WSL2↔Windows, validated against a generic test board (`project-a-board`). Steps: [embarch-api/milestone-1.md](embarch-api/milestone-1.md), [embarch-core/milestone-1.md](embarch-core/milestone-1.md).
- **Token** — the insecure `dev-token-change-me` fallback replaced by an auto-generated, machine-wide token file Core persists and embarch-api discovers on its own. Full design: [embarch-token.md](embarch-token.md). Steps: [embarch-api/milestone-2.md](embarch-api/milestone-2.md), [embarch-core/milestone-2.md](embarch-core/milestone-2.md).
- **Study Designer, scoping + implementation** — `embarch-study-designer`, the shared `no_std` Rust library defining hardware-in-the-loop study types (BLE advertise/connect/data-exchange plus power profiling), designed and implemented with its full type model, wire-format tooling, and schema versioning. *(This entry originally also named validation actions and a `SignalCheck` evaluator; post-hoc validation was removed outright 2026-08-25 — `embarch-study-designer/design.md` §3 decision 48 — having never once run.)* Full design: [embarch-study-designer/design.md](embarch-study-designer/design.md). Steps: [embarch-study-designer/milestone-3.md](embarch-study-designer/milestone-3.md).
- **Dev Bench scoping** — `embarch-dev-bench`'s architecture scoped: Zephyr-based, cross-vendor (one shared application across per-vendor west workspaces), BLE + power sampling v1 scope. Full design: [embarch-dev-bench/design.md](embarch-dev-bench/design.md).
- **Onboarding** — `embarch-umbrella` (the `embarch` binary): `setup`/`init`/`doctor`/`status`/`up`/`down`, `base_url = "auto"` in API, `start`/`stop` in Core, and the suite's first real release binaries. Full design: [embarch-umbrella/design.md](embarch-umbrella/design.md); user-facing guide: [embarch-user-guide.md](embarch-user-guide.md). Steps: [embarch-umbrella/milestone-6.md](embarch-umbrella/milestone-6.md).

Two real gaps this foundation left behind, which is exactly what the new milestones below close: no shipped milestone ever flashed real hardware through a real client repo (`project-a-board` was a placeholder; the real `reference-dut-fw` repo was only ever used to validate config/discovery, never an actual physical flash — see `embarch-umbrella/milestone-6.md`'s 2026-08-13/14 entries), and `embarch-dev-bench` firmware has never been run on physical hardware at all (`embarch-dev-bench/design.md` §4).

## Milestones

Each milestone below uses a real umbrella-suite release plus the real `reference-dut-fw` client repo as its test target, rather than a placeholder project or a synthetic fixture. Numbered starting fresh at 1 — the shipped foundation above is intentionally not renumbered into this sequence. *(Filename note: when an execution doc is created for one of these, it's filed as `milestone-N.md` using N = 7/8/9/10 — continuing the on-disk numbering past the shipped foundation's 1–6 — specifically so it can't collide with those still-live historical files; only this doc's own prose uses the fresh 1–4 numbering.)*

### 1 - Flash & Build (real hardware)

Projects : API - Core
Use the real `reference-dut-fw` repo — not a placeholder project — to validate the full build→flash chain for real, with EmbArch API run from WSL2 and EmbArch Core run on Windows: the suite's actual daily-use topology. The shipped foundation's Flash milestone proved this chain against a generic test board; Onboarding validated `init`/`list_targets`/`doctor` against reference-dut's real config but never drove an actual physical flash through it. This milestone closes that gap: check out a real reference-dut board/variant, `embarch init`, `list_targets`, `build_and_flash` through the WSL2⟷Windows split, onto physical hardware.
Steps : **done, 2026-08-18** — [embarch-api/milestone-7.md](embarch-api/milestone-7.md) / [embarch-core/milestone-7.md](embarch-core/milestone-7.md), both docs' Definition of Done fully closed. Target board/variant/revision was deliberately not pre-selected in either doc — resolved via live `list_targets` discovery against the real repo (`dut_dev@7`/`reference-dut`/`ble-shell`), per decision 12.

### 2 - Dev Bench Self-Test

Projects : Core - Dev Bench - API *(expanded 2026-08-18 from the original Core+Dev-Bench-only scoping — see below)*
No client/DUT repo involved. Establish the dev-bench self-test as a standing precondition every study runs before touching a DUT: dev-bench firmware exercises its own peripherals and the Core⟷dev-bench transport — serial link, `Hello`/`HelloAck` handshake, real per-`Study` dispatch of a multi-step `Study` with `StepResult`/`StudyDone` round-tripping (`embarch-dev-bench/design.md` §3 decision 21) — end-to-end on physical hardware for the first time. Confirms dev-bench is ready for a task before Milestone 3 points it at a real DUT. Power sampling is explicitly out of scope here (Milestone 4). **Target board retargeted 2026-08-19 from the nRF54L15DK to the ESP32-C5-WROOM-1 DK** (`embarch-decision-reversals.md` row 13) — the nRF54L15DK's RMA replacement never arrived and closed this milestone; the ESP32-C5, originally only an interim substitute, already validated the entire dispatch/handshake/study mechanism end to end, so this milestone's own scope moved to it rather than staying blocked on the nRF54L15DK.
Steps : **done, 2026-08-20** — [embarch-core/milestone-8.md](embarch-core/milestone-8.md) / [embarch-dev-bench/milestone-8.md](embarch-dev-bench/milestone-8.md) / [embarch-api/milestone-8.md](embarch-api/milestone-8.md), all three docs' Definition of Done closed except one item: the host-side watchdog's lapse-produces-`"failed"` behavior stayed code-reviewed/unit-tested only, not live-confirmed — two live attempts (a human-timed physical USB unplug, and a software JTAG-reset race) both lost the same timing race against the self-test fixture's `BleAdvertise` step resolving in well under a second, faster than either could land inside the window. Everything else closed for real against the ESP32-C5 in this final pass: the stale-firmware `doctor` check (surfacing and fixing a real CMake staleness bug along the way), Core-crash-mid-study, dev-bench port auto-detection extended to cover this board's own VID directly, and the MCP-path repeat (surfacing and fixing a real MCP-specific schema bug the CLI path can't hit, plus confirming a previously-flagged stack-overflow risk is debug-build-specific). Scope decisions made in the original drafting pass, ahead of execution: Core implements the full four-endpoint `/study*` surface now rather than deferring `power-data`/`waveform-data` to Milestone 4; dev-bench closes `design.md` decision 8 (Rust cross-compile/west-module wiring) in this milestone rather than leaving `study_ffi.c` stubbed; the self-test `Study` is `BleAdvertise`-only steps (no DUT, no power hardware needed); and `embarch-api`'s already-locked-in `run_study`/`study_status` surface (`embarch-study-designer/design.md` §6) was pulled into this milestone's scope as the way the self-test actually gets submitted, rather than a raw HTTP call — the reason this milestone's Projects line grew a third repo.

### 3 - Study Designer: Feature-Branch Iteration

Projects : Study Designer - Core - API - Dev Bench
Use the full EmbArch chain to iterate a test of a feature branch on the real reference-dut repo: build and flash a feature branch via EmbArch, dev-bench BLE-connects to the running reference-dut DUT, exchanges GATT data per the branch's feature, and forwards the acquisition data over the Core⟷dev-bench serial link into `embarch-core`. One successful end-to-end run is the Definition of Done — not a repeated edit→rebuild→reflash loop.
**Design-questions pass, 2026-08-19:** the GATT interaction is generic, not tied to one known characteristic — new `embarch-study-designer` types `Action::GattDiscover` (live wildcard GATT-table discovery) and `Action::GattMonitorAll` (self-sufficient discover+subscribe-all+capture-everything) replace an original plan to target one specific characteristic (a reference-dut dock-bounce debounce fix, `fix/bouncing_dock`, whose actual fix is explicitly out of scope for this milestone — it has no commits past `main` as of this pass). A second new piece, answering "autodetect a DUT's GATT config" from source rather than live: a generic `GattConfigExtractor` trait plus one concrete implementation scoped to this one firmware's real macro conventions. Full detail: `embarch-study-designer/design.md` §3 decisions 31/32/33.
Steps : **done, 2026-08-24** — [embarch-study-designer/milestone-9.md](embarch-study-designer/milestone-9.md) / [embarch-core/milestone-9.md](embarch-core/milestone-9.md) / [embarch-api/milestone-9.md](embarch-api/milestone-9.md) / [embarch-dev-bench/milestone-9.md](embarch-dev-bench/milestone-9.md), all four docs' Definition of Done fully closed. Target board: the ESP32-C5-WROOM-1 DK (already validated in Milestone 2), not the still-unreplaced nRF54L15DK. A real `BleConnect`->`GattDiscover`->`GattMonitorAll` study against the real reference-dut DUT (`bugfix/gpio-debounce-ppg-work-queue`) completed clean via both CLI and MCP — the first physical BLE connection between two independent boards this suite has ever made, and the first real GATT discovery/monitoring against real hardware. Getting there needed a real production fix along the way: a debug-build stack-overflow risk `embarch-study-designer/design.md` §7 had only ever tracked against a tiny fixture crashed `embarch-api`'s `study_status` for real against this milestone's GATT-sized result, fixed by spawning its runtime on a dedicated big-stack thread (`embarch-api/design.md` decision 36) — which incidentally also fixed a separate, previously-unrelated-looking `--release`-build crash. Closed with one real gap left open rather than blocking: a ~50% flake rate connecting to and discovering the DUT's GATT table (one outright connection failure, one mid-discovery disconnect, inconsistent service counts across successful runs), not yet root-caused (`embarch-dev-bench/milestone-9.md` §6).

The milestone keeps its number and its scope so the sequencing history stays readable — it is deferred, not cancelled or renumbered.

All four are now deferrals with one shared trigger — power profiling resuming — instead of four separate questions waiting on an answer nobody could give.

### 5 - Study Designer UI

Projects : Study Designer
Opened by a real gap Milestone 3's own closing session hit directly: a real `GattMonitorAll` run against the reference-dut DUT came back empty, because nothing in that `Study` ever wrote anything to make the DUT stream, and there was no way for whoever authored it to know what to write — that's DUT-specific knowledge no generic discovery can produce, and an attempt to answer it by reading the DUT firmware's own source and asserting a conclusion from it was flagged directly as destructive to the dev process — an inference from source isn't the same as knowing. This milestone builds the actual fix: an interactive, table-based `Study` builder (own local web UI, shipping inside `embarch-study-designer`) whose action list merges built-in `Action`s, live `GattDiscover`, and static `GattConfigExtractor` output, plus a user-authored custom-action registry — name and clickable enumerated parameter values only, never a semantic description this crate invents on its own. Full design: `embarch-study-designer/design.md` §3 decisions 34/35.
Steps : **done, 2026-08-24, except real-hardware validation** — [embarch-study-designer/milestone-11.md](embarch-study-designer/milestone-11.md). The UI (interactive table builder, live+static discovery, the custom-action registry, run-and-watch) is built and live-smoke-tested against the real `reference-dut-fw` repo; closing the loop for real — a real engineer-supplied action producing real captured GATT activity — needs a connected DUT/dev-bench and someone who actually knows that DUT's protocol, deliberately not invented by this milestone.

### 6 - Stimulate-and-Capture (NUS shell + exhaustive GATT logging)

Projects : Study Designer - Dev Bench - Core - API - UI
Opened 2026-08-25 by a concrete user goal — "send an NUS shell message to the DUT mid-study, stimulate it over BLE, and get exhaustive logs of everything that happened on the GATTs, from a study I can save and re-run, authored in the UI" — and by the gap that goal immediately exposed: **it wasn't expressible.** Steps run strictly in sequence and `GattMonitorAll` unsubscribes when its own step ends, so a stimulus write and a capture could never overlap; every ordering produced an empty capture and a `Pass`. Five pieces, all built: `Action::GattMonitorStart`/`GattMonitorStop` (a capture window that outlives its step), a streamed uncapped GATT transcript landing in `gatt.csv` and served by `GET /study/{id}/gatt-data` / `study_gatt_data`, a free-text payload path alongside the registry, a saved-study library under the firmware repo that doubles as a `run-study --study-file` input, and the Study Designer tab's frontend (which, it turned out, had never actually been built — only its backend). Full design: [embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decisions 36/37/38, [embarch-dev-bench/design.md](embarch-dev-bench/design.md) §3 decision 28.
Second pass, 2026-08-25, once hardware was connected: three more pieces, two of them fixes to defects that made the original five unusable on real hardware. `vendor.rs`, a built-in table of vendor-defined GATT service identities so Nordic's UART Service UUIDs aren't every engineer's to transcribe; `Step.delay_before_ms`, making *when* a stimulus fires authorable rather than implicit; and `Action::BleConnect.target_name`, because "connect to whichever DUT shows up first" reached a different peripheral on consecutive runs of the same study. Design: [embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decisions 41/42/43, [embarch-dev-bench/design.md](embarch-dev-bench/design.md) §3 decisions 30/31/32. Schema 5 → 7.
Steps : **the pipeline is built, deployed and exercised on real hardware; the end-to-end NUS run is not yet done.** Both boards are flashed and enrolled (DUT `dut_dev@7` + `-S ble-shell`, dev-bench ESP32-C5), Core is rebuilt and live on the Windows service, and the `Hello`/`HelloAck` handshake reports `schema_version: 7, compatible: true`. A study authored in the Study Designer UI, saved to the firmware repo, and re-run from the CLI now reaches the DUT's GATT table for real, and `gatt.csv` returns an exhaustive both-directions transcript. Tests: study-designer 80, Core 56, api 39, dev-bench ztest 24/24.

  **Running it is what found the real bugs**, none of which any test suite would have caught: (1) dev-bench's inbound link was *polled*, so every frame larger than the UART's 128-byte hardware FIFO was silently truncated and dropped — and this milestone's own four-step study, at 132 bytes, is the first one this suite ever authored large enough to cross that line, which is why the feature could never have worked; (2) 16-bit UUIDs were reported two bytes out of place, so a study authored against any 16-bit UUID could never match its own discovery output; (3) `BleConnect` with no target connected to arbitrary nearby peripherals and then reported `"service not found on DUT"` about devices that were never under test. All three fixed and verified against hardware. The ztest suite now also decodes the *real* bytes Core sends, not only what its own encoder produces — the blind spot that let (1) survive.

  **Still open, and reframed 2026-08-25 — the previous version of this paragraph was wrong about why.** It read that the DUT "advertises slowly (minutes, not seconds) and under a name that is *not* its configured `CONFIG_BT_DEVICE_NAME`", and treated that as the obstacle. The board was **bricked by EmbArch's own `--erase` flash** ([embarch-core/design.md](embarch-core/design.md) §3 decision 32, [embarch-decision-reversals.md](embarch-decision-reversals.md) row 19); the scan diagnostics built to explain its absence were explaining damage the suite had done. Once it was recovered with `west flash --erase` and advertising again as `the client S11 B9C3`, the real blocker showed itself: `connect` passes and `open-capture` then fails with `"disconnected during service discovery"`, deterministically, 4 of 4 — while the same discovery walks an Apple device, a `0x1910` device and two `7dfc*` devices without trouble. **The DUT requires an MITM-authenticated `BT_SECURITY_L4` link before it will tolerate discovery** (asked and answered by the engineer, not inferred), and dev-bench registers no pairing callbacks at all, which makes L4 unreachable from this bench no matter what a study asks for. Four design decisions came out of that: [embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decisions 44 (`Action::BleSecurity`) and 45 (`Study.gatt`), [embarch-dev-bench/design.md](embarch-dev-bench/design.md) §3 decision 34 (central-side pairing), and [embarch-ui/design.md](embarch-ui/design.md) §3 decision 12. **None of them are code yet, and the attribution of the disconnect to the pairing gap is itself unvalidated** — the hardware was detached before it could be tested. The DUT also advertises a rotating resolvable private address (two addresses inside one 60-second scan), so `target_address` is not a usable handle for it and decision 43's name filter is the one that works. The shell command and terminator to send remain engineer-supplied and unconfirmed — deliberately, per decision 41's identity-only rule; the author will write them in the Study Designer UI. Also noted for follow-up, deliberately *not* concluded: one run whose `Read` step reported `Pass` yielded a `read_request` row in `gatt.csv` with no matching `read_response` row and a null `captured_data`. Both the schema variant (`GattEventKind::ReadResponse`) and the firmware emit call exist, so this is an unexplained observation needing diagnosis, not a missing feature — recorded here so it isn't rediscovered from scratch.

### 7 - MCU Load Tracing (embarch-outpost)

Projects : Outpost - Topology - Core - Study Designer - Dev Bench - API - UI
Opened 2026-08-25 by a goal nothing in this suite can currently serve: **"a study told me the DUT responded in 40 ms; I need to know whether that was one busy thread, forty context switches, or an ISR storm."** Every existing component observes the DUT from outside it, and none of them can see inside the MCU. This milestone builds the one that ships *inside*: a Zephyr module ([embarch-outpost/design.md](embarch-outpost/design.md)) compiled into the DUT's own debug firmware, implementing `CONFIG_TRACING_USER`'s kernel hooks plus engineer-placed markers, emitting compact ID-based records out a **TX-only** UART into a lock-free ring drained asynchronously, decoded host-side against a CRC-matched build-time manifest.

Three pieces land alongside it, none of them optional: **"dev-bench bypass"** becomes a real modelled route rather than a description of how things happen to be wired ([embarch-topology/design.md](embarch-topology/design.md) §3 decision 18) — the bench has neither the spare pins nor the pass-through firmware, so the outpost's UART goes to a USB-UART bridge on the Core machine, declared as `Route::Direct` and drawn in the diagram as a signal going *around* the bench; the **stream-pipeline proposal's inbound half is accepted** ([embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decision 39), which is what keeps this from becoming the suite's fourth near-identical capture pipeline; and [embarch-ui](embarch-ui/design.md) gains route declaration in the Topology tab plus a post-hoc Trace view.

**Sequence this before Milestone 4 (Power-Sampling Study).** Same argument the proposal made for itself, now sharper: Milestone 4 is exactly what makes the current stream wire shape load-bearing on real hardware, and Milestone 6's dev-bench firmware has not been flashed yet either. Nothing about the shapes being reshaped here has ever carried a real byte. That stops being true the moment either runs.

A fourth piece joined the same design pass, wider than the outpost that prompted it: **a `Study` now declares the dev-bench and DUT firmware versions it is meant to run against, with reflash as the operator's per-run choice** ([embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decision 40). It was raised to give the outpost's trace manifest something to bind to, and closed a gap nobody had named — a `StudyResult` could not say what firmware it ran against, making two runs of one study against two builds indistinguishable afterwards.

Capture is **study-scoped and rendered post-hoc — there is no live feed**, reversing this milestone's own opening framing, deliberately ([embarch-outpost/design.md](embarch-outpost/design.md) §3 decision 10).
Steps : **Phases A and B closed 2026-08-25; Phase C and Phase D both closed 2026-08-26 — closing C shipped the two host halves its own trigger had parked, and D landed across five repos with one item deliberately scoped out; E not started, and it needs hardware that does not exist** — [embarch-outpost/milestone-1.md](embarch-outpost/milestone-1.md), phased A–E across seven repos. Phase A is the shared types both other host phases build against: `Study.streams`/`StreamTap` and the `StreamOpen`/`StreamChunkBatch`/`StreamClose` wire triple, `Study.requires`/`StudyResult.provenance`, `embarch-topology`'s `SignalLink`, and `STUDY_DESIGNER_SCHEMA_VERSION` **7 → 8** (one bump for decisions 39 and 40 together; the 5 → 6 both were written against went stale when decisions 42/43 shipped first). Every new wire record is pinned in both languages. **Nothing has captured a real byte yet** — `streams/`, the version gate, reflash and now dev-bench's own tap handling are all built as of Phase B, but none of it has run against hardware and the dev-bench half has never been flashed; the UI and the outpost module itself are still ahead. First consumer: `reference-dut-fw` (nRF54L15, already enrolled as `dut`).

**The five questions Phase A left open were settled 2026-08-25 as decisions, and shipped the same day as Phase B item 0** ([embarch-outpost/milestone-1.md](embarch-outpost/milestone-1.md) §3 item 0): a sibling `streams_crc` rather than a widened `steps_crc`; `Step.power_sample` retired so a `PowerFrontEnd` tap is the only way to author a power capture; a stream-fed `ValidationSource` naming the tap rather than a `DataChannel`; `POST /signals` + `GET /signals` on Core with no `embarch-topology` CLI mirror; and the durable `alerts.jsonl` record for a `SignalMismatch` closed as not-needed-yet with a named trigger rather than carried as owed work. Settling them surfaced a sixth thing none of them predicted: `STUDY_DESIGNER_SCHEMA_VERSION` was guarding two hops with different exposure and **split into `DEV_BENCH_WIRE_SCHEMA_VERSION` and `HOST_TYPE_SCHEMA_VERSION`, both 9**. Four of the six are recorded as reversals (rows 21–24) — all found by reading the real repos rather than the docs' summaries of them.

**Phase B items 1 and 2 shipped 2026-08-25, and item 2 was not the api-only item this milestone scoped it as.** Item 1 is Core's whole half with no schema change: `streams/` replacing the three fixed CSV paths (raw bytes always written before any decode), both retention knobs, the parameterised stream route with the three old ones as aliases, `provenance`/`streams` in `events.json`, the `409` version gate that runs no step, and Core's own `Route::Direct` signal port. Item 2 is `study_stream_data`/`list_study_streams`, `run_study --reflash`/`--allow-version-mismatch`, and **the two signals decision 40 created without giving either a place to land** — an override that had to be recorded in a `StudyResult` with no field for one, and a `VersionSource::FlashedThisRun` nothing could produce. Both cross `POST /study` as **query parameters**, which is "a run parameter, not a study field" written as a request; `Provenance` gained `overrides` at host schema **9 → 10**, the first bump that moves that constant alone. Two things nobody had anticipated came out of it: supplying the flashed version is also what makes `requires.firmware_version` checkable, so the DUT half of Core's gate is live for the first time; and `embarch-core/design.md` §3 decision 32's `erase` turns out to describe a vendor-tool delegation **that is not in the tree** (reversal row 28). **Only the manifest half of Phase B remains deferred**, under one trigger shared by Core's receiving half and api's sending half: Phase C emitting a real `outpost-manifest.json`. **Item 3 closed 2026-08-25, and closed Phase B — with both of its scoped premises wrong.** Taps are decoded and stored, opened and closed from their declared `StreamScope`, and the GATT transcript rides `StreamChunkBatch` on its declared tap; the retired tag 10 is gone from the encoder and from `main.c`, its value left burned rather than reused, because the "no such firmware was ever flashed" argument that licensed reusing tags 2/3/4 expires the moment this firmware is. But **the payload-interpretation deletion this item was named for had already happened in Phase A** — grep found none of the four things the decision said were still there — so the item was purely additive and the phase ends net *bigger*, +128 bytes here on top of item 0's +654, against a net-negative expectation (reversal row 35). And **the reserved `dev-bench` log tap was Core's, not dev-bench's**: `tap_for` resolved ids against the submitted `Study`, so a tap the bench invented would have been dropped as undeclared; it ships as Core rendering the `LogLine` frames it already receives, with no firmware at all (row 36). **Two of Phase B's four items were not the single repo their scope named** — item 2 moved three, item 3 moved two — which is a lesson about one-word item scoping rather than two accidents.

**Implementing item 0 produced two more reversals (rows 25, 26), and one of them inverts a stated bar.** The pass was expected to make dev-bench firmware *smaller*; it made it **+654 bytes bigger**, because the C decoder never walked the `streams` span the new seal covers — Phase A had appended `streams` after `steps_crc` precisely so it would not have to. The decision stands; the walker is item 3's cost arriving early. The second: `StepResult` had been silently writing two bytes for fields retired a schema version earlier, invisible because the both-languages pinning rule had been scoped to *new* records and `StepResult` is the oldest one. The schema bump was re-derived rather than copied, taking **8 → 9** and pushing decisions 44/45's own reserved 8 → 9 back to be re-derived — row 18's protocol working as intended for once. **Items 1–3 (Core's `streams/`, the api surface, dev-bench's payload-interpretation deletion) are not started, and nothing is deployed.**

**Phase B item 1 — Core's whole half — closed 2026-08-25, and the two open questions it carried were settled rather than guessed at** ([embarch-outpost/milestone-1.md](embarch-outpost/milestone-1.md) §3 item 1). `streams/` replaced the three fixed CSV paths with one file per declared tap, raw bytes always written before any decode is attempted; both retention knobs landed (`EMBARCH_STREAM_MAX_BYTES`, `EMBARCH_STUDY_RESULTS_KEEP` — the first EmbArch settings a plain operator may need to turn, so both got [embarch-user-guide.md](embarch-user-guide.md) rows); `GET /study/{id}/stream/{name}` shipped with the three old routes as aliases for one release; `StudyResult.streams` and `provenance` reached `events.json`, which had never carried either; and the version gate went live, rejecting a stale bench with a `409` **before `StudyStart` is sent**, so no step runs. A `Route::Direct` signal tap now opens Core's own third serial port — `resolve_signal_port`'s first caller anywhere, which is what [embarch-topology](embarch-topology/design.md) §5 had recorded as unwired infrastructure. No schema change, and no source change in `embarch-api`/`embarch-ui`/`embarch-umbrella`, which is what the aliases exist for.

**Phase C closed 2026-08-26 — the outpost module exists, and closing it fired the manifest trigger** ([embarch-outpost/milestone-1.md](embarch-outpost/milestone-1.md) §4). The Zephyr module builds for `native_sim` and for the real nRF54L15 reference-dut target; a `native_sim` run produces a stream that decodes cleanly (41 frames, 848 records, every record kind including gaps, no CRC, framing or sequence failures); the post-link manifest generator resolves **13 real ISRs and 5 real threads out of the reference-dut's own ELF**. Because that is exactly the precondition Core's and api's manifest halves were parked on, **both shipped in the same pass** rather than becoming recorded debt — Core stores what a flash bound (per chip, cleared by a flash of the same chip carrying none) and decodes a trace against it post-hoc, `embarch-api` sends it by finding it *beside the artifact* rather than taking it as a parameter, and a build-ID mismatch costs the **names** and never the capture.

**Eight reversals came out of Phase C (rows 37–44), and five of them are the same shape**: this suite's docs asserting how a *build system or toolchain* behaves, where the mechanism named was the one that looked right rather than the one that works — `select` on a Kconfig choice member, `zephyr_iterable_section` on the template-`.ld` path, `_sw_isr_table` naming a shared trampoline instead of a handler, a Cargo feature that only ever built via unification from another dependency, a hand-mirrored constant guarded by a comment rather than a mechanism. **Row 37 is the one to carry forward and is a different lesson**: `embarch-study-designer` had *shipped* a `StreamEncoding::OutpostTrace { manifest_crc }` encoding a mechanism `embarch-outpost` decision 9 had **already reversed in prose**, and only producing a real manifest made that visible. A decision reversed in a doc does not reverse the code that shipped against its earlier form. It is now a unit variant at schema **v11 wire / v13 host**.

**What Phase C did not do, and must not be read as having done**: no outpost byte has crossed a real UART on any board; every Kconfig wire constant is an unmeasured default (a host process writing to a pty sustains a rate no UART will, so the `native_sim` run proves correctness and nothing about cost); and the instrumentation's own overhead is deliberately uncharacterised, which was the user's call on 2026-08-25 — the milestone doc's own definition of done still listed "overhead measured" and that contradiction is struck rather than quietly satisfied.

**Phase D closed 2026-08-26 — routing is declarable by a human and a trace renders, across five repos rather than the one its scope named** ([embarch-outpost/milestone-1.md](embarch-outpost/milestone-1.md) §5). `embarch-ui` gains a sixth tab: signal-route rows in Topology with the diagram drawing a `direct` signal *around* the dev-bench node, and a post-hoc Trace view with lanes per thread/ISR/CPU-idle. The four things its one-word scope missed were all upstream of the UI — `embarch-core-client` had no `/signals` wrapper at all, and Core needed `GET /serial-ports` (which needed `embarch-topology` too), `GET /study/{id}/streams`, and `DELETE /signals/{name}`. The third is the one that matters: Phase C made Core record *why* a trace has no names and put it in a file with no HTTP caller, so over HTTP a refused trace and a named one were indistinguishable — exactly the confusion that refusal exists to prevent.

**Two things Phase D deliberately did not do.** Decision 11's reflash selector is `embarch-api` orchestration (`check → build → flash → submit`, over project config and build machinery `embarch-ui` does not have), so it is scoped out with the dependency-direction question recorded rather than answered under time pressure. And **nothing was deployed**: validation ran against a dev Core built from `main` inside a private mount namespace with a scratch `/var/lib`, which is also how Phase D discovered that the live Windows service predates all of Phase B and answers `404` on `/signals` — the plan's own "exercise this against the live Core" step was impossible (rows 45–48).

**What Phase D must not be read as having done**: no outpost byte has crossed a real UART, so the Trace view has rendered the committed `native_sim` capture and never a DUT's, and every wire constant in §5.3 is still an unmeasured default. A working timeline is not validation of the numbers underneath it.

**Record layout 2, 2026-08-26 — the DUT stopped keeping time, and it is a scope change to this milestone rather than a detail** ([embarch-outpost/design.md](embarch-outpost/design.md) §3 decisions 4, 17, 18). At the repo owner's call, on emit-path cost: the per-record `k_cycle_get_32()` read sat inside the context switch and inside `_isr_wrapper()`, so the instrument was charging its cost to the path it measures. Every timestamp comes off the wire; `embarch-core` stamps each *frame* with its own receipt time instead, persisted beside the capture and joined on at render time with a verified alignment. Five repos touched, all green.

What this milestone can now claim is narrower and worth stating in the same breath as the win. **It buys:** ~32% fewer bytes per record (9.25 → 6.32 measured on the same workload), a ring that is finally the size its Kconfig says, and — the part nobody had written down as a gap — a trace on the *same clock* as every other stream in a study, where DUT cycles had no sync point to host wall time at all. **It costs:** a frame is now the resolution of the instrument, so **ISR duration is no longer measurable** — this wire counts interrupt entries and refuses to time them — and per-thread load excludes a fourth class of span for the same reason. Milestone 7's opening goal ("was it one busy thread, forty context switches, or an ISR storm?") is still answered; "how long did that one ISR take" is not, and is now out of scope for this instrument rather than pending a measurement.

**Still true, and now the headline measurement this milestone owes:** no outpost byte has crossed a real UART, so nobody knows how many milliseconds a frame actually takes to arrive or how much that jitters — and that number is the resolution of everything the trace says.

**The manifest half was settled and deliberately not built** — until Phase C fired its trigger a day later; the record of *why* it waited is kept because the trigger mechanism is the part worth preserving: its transport is an optional `manifest` part on `POST /flash` (not a route of its own, so the flash that binds a manifest is the request that carries it), and building storage/selection/verification/refuse-to-render now would be four mechanisms with nothing able to exercise any of them until Phase C emits a real manifest — which is the named trigger. That is the third time this milestone has closed something with a trigger instead of leaving it as owed work. **One more reversal (row 27) came out of building it**: decision 30(a) said a signal tap's port opens "at `StreamStart`", a trigger that cannot exist for the one stream source dev-bench does not mediate — the decision had borrowed a lifetime signal from precisely the sources it was defining itself against.
