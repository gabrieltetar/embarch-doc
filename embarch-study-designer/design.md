# embarch-study-designer: design

**Status:** draft, 2026-08-11. Implemented at [gabrieltetar/embarch-study-designer](https://github.com/gabrieltetar/embarch-study-designer): the full §4 type model, `steps_crc`, `STUDY_DESIGNER_SCHEMA_VERSION` (now v3), the `limits` module, `core-validation`'s `SignalCheck` evaluation logic, decisions 24/25/27's `StudyStart`/`StepResult`/`StudyDone`/`StreamChunkBatch` wire messages and `Sample.unit`/`channel_id`, and an expanded `ffi` module (§7) covering both the original `Study`-decode-and-CRC-check surface and a new `BleAdvertise`-scoped decode-to-C-struct surface for dev-bench's real dispatch — all real, `#![no_std]`, and tested across every feature combination. As of 2026-08-18, **also actually consumed** as a Cargo dependency by both `embarch-core` and `embarch-api` (path dependency, not the git reference decision 8 originally named — see that decision's own amendment) for the first time, as part of Milestone 2 (Dev Bench Self-Test, `embarch-roadmap.md`). Written as Milestone 3's deliverable; see [milestone-3.md](milestone-3.md) for that execution plan and §8 below for the implementation passes that followed it.

## 1. Purpose and scope

`embarch-study-designer` is a shared Rust library that lets an EmbArch API user — human or agent, symmetrically (§6) — define and run **studies** of a DUT through a future `embarch-dev-bench` companion device. A study is a scripted sequence of stimulus/interaction steps plus measurement/validation, used for three overlapping purposes: fuzz testing, power profiling, and automated unit/integration testing during firmware development.

Unlike `embarch-api` or `embarch-core`, this is **not a service** — it's a data-types-and-tools library. It defines the shared vocabulary (a `Study`, its steps, the stimulus/sensing/validation shapes) *and* the narrow set of helper functions needed to work with that vocabulary identically everywhere (§3 decision 2) — e.g. CRC sealing (§3 decision 17) and canonical CSV-row rendering (§4.7, §5.2) — that every component along the full path a study crosses (`embarch-api` → `embarch-core` → `embarch-dev-bench` firmware → DUT, §2) compiles in directly, so neither the wire format nor the artifacts derived from it can drift into independently-maintained, slowly-diverging definitions.

`embarch-study-designer` is **not**:
- A service or binary of its own — no `main.rs`, no HTTP surface, no MCP tools live in this crate itself. Those belong to whichever component compiles it in (`embarch-core`, `embarch-api`, dev-bench firmware).
- A transport-layer implementation. It defines *what* gets sent (the types), not the socket/serial-port plumbing that sends it — that lives in each compiling component.
- Tied to one physical bench design. The type model is meant to outlive whatever `embarch-dev-bench`'s first physical revision turns out to be.

## 2. Architecture overview

```
                          embarch-study-designer (shared crate, #![no_std])
                          compiled in by all three:
                                    |
        +---------------------------+---------------------------+
        |                           |                           |
  embarch-api                 embarch-core                embarch-dev-bench
  (MCP + CLI,                 (bridges HTTP/JSON           firmware (C; BLE central/
   future §6)                  <-> serial/binary,           peripheral + power sampling;
                                future §5)                   links embarch-study-designer
                                                              via FFI staticlib, §3 decision 7)
        |                           |                           |
        +----- HTTP + JSON  ------->+----- Serial (UART/USB CDC, COBS-framed postcard) ----->+
                                                                                            |
                                                                                       DUT (BLE)
```

`embarch-api` and `embarch-core` already speak HTTP+JSON (`embarch-core/design.md` §4) — that hop is unchanged. The new hop this project introduces is `embarch-core` → `embarch-dev-bench`, over a serial link (§3), carrying the same logical `embarch-study-designer` types in a different wire format (§3). `embarch-dev-bench` is the component that actually talks BLE to the DUT and samples power — `embarch-core` never talks BLE or samples power itself, matching the suite's existing pattern of "hardware access stays in the layer closest to the hardware" (`embarch-core/design.md` §1).

That serial link now carries more than discrete `Study` submission and `StudyResult` reporting: a continuous streaming sub-protocol for power/sensor-waveform data captured during a step (§3 decision 20), and a CRC-sealed integrity check on `Study.steps` performed independently at both this hop and the API↔Core HTTP hop (§3 decision 17), on top of the schema-version handshake §3 decision 12 already establishes.

1. **Separable crate, not embedded in `embarch-api`.** All three of `embarch-core`, `embarch-api`, and dev-bench firmware compile it in independently — as a literal Cargo dependency for the first two, and via a cross-compiled FFI staticlib for dev-bench firmware (decision 7). This was chosen explicitly over embedding study logic inside `embarch-api` — the whole point is that dev-bench firmware (a different binary, a different language even) needs the identical types, which isn't possible if they only exist inside `embarch-api`'s crate.
2. **Data types plus the narrow set of tools needed to work with them identically everywhere — not a protocol or transport implementation.** The crate's job is defining `serde`-derived types (§4) *and* the small number of type-adjacent helper functions every consumer needs the identical implementation of, so `embarch-core`/`embarch-api`/dev-bench firmware never each reimplement the same logic and risk it drifting apart: CRC sealing (`steps_crc`, §3 decision 17) and, since §5.2's CSV rework, `Sample`'s canonical row-rendering (§4.7). It still intentionally does not hardcode a wire format or a transport — different hops in the architecture (§2) need different formats (decision 3), and baking one in would force a lossy re-encoding step at whichever hop didn't match. The line: anything every consumer must agree on byte-for-byte or column-for-column belongs in the crate; anything hop-specific (the socket, the HTTP client) stays out of it.
3. **Serialization is format-agnostic at the type level; two formats chosen per hop.** `embarch-api` ↔ `embarch-core` stays JSON, matching every existing Core endpoint (`embarch-core/design.md` §4) — no reason to break that convention for a hop that isn't resource-constrained. `embarch-core` ↔ `embarch-dev-bench` uses a compact binary format instead — **`postcard` is locked in** (pairs naturally with `serde` + `no_std`, no allocator required). Locked without real dev-bench hardware to spike against (none exists yet, milestone-3.md §5) — a stand-in `no_std`/no-alloc round-trip check is treated as sufficient for now, flagged for re-confirmation once real nRF54 hardware exists, the same way §3.2/decision 7's firmware-language call was. See decision 9 for the framing layered on top of it.
4. **Transport for the new hop is serial (UART or USB CDC).** Chosen over HTTP for `embarch-core` ↔ `embarch-dev-bench` specifically because dev-bench is expected to be a resource-constrained MCU wired directly to whatever machine runs `embarch-core` — mirrors Core's existing DUT serial-log pattern (`serialport`, `embarch-core/design.md` §5) rather than requiring dev-bench to carry a network stack.
5. **`#![no_std]`, not std-everywhere.** Locked in because dev-bench firmware may be bare-metal/resource-constrained and its own runtime is still undecided (§7) — a `no_std` crate keeps every downstream option open (bare-metal Rust, an RTOS, or a hosted environment via a `std`-compatible shim), whereas a `std`-only crate would foreclose the bare-metal case outright. `embarch-core` and `embarch-api` run on hosted `std` environments and are unaffected by this constraint — they simply use the `no_std`-compatible types over `std`.
6. **Symmetric human/agent access, once code work starts.** Follows the suite-wide principle already established for Core/API (`embarch.md` §5: "every hardware-facing capability is reachable both by an agent and directly by a human, converging on the same underlying modules"). Concretely, once `embarch-api` grows study-running code, expect new MCP tools *and* CLI subcommands (§6) — not one without the other, matching `build`/`flash`/etc.'s existing pattern (`embarch-api/design.md` §5, §5a).
7. **Dev-bench firmware is C, bridged via an FFI staticlib — not native Rust or a Zephyr+Rust module.** Resolved over native embedded Rust and `zephyr-lang-rust` (Zephyr's official Rust support) because the nRF54 family splits sharply by variant: nRF54L15 (single Cortex-M33) has a workable Rust path via existing `zephyr-lang-rust` samples on comparable Nordic parts, but nRF54H20's mandatory multi-core `sysbuild` build isn't a proven fit for that project's west-module/CMake integration — and either way, Zephyr's BLE host stays a C API reached through generated bindings, not idiomatic Rust, so the BLE-heavy parts of dev-bench firmware wouldn't be native Rust regardless. Going C-firmware sidesteps that split entirely. `embarch-study-designer` compiles as a `#![no_std]` staticlib cross-compiled for the target ABI, exposing `extern "C"` functions to build/serialize/deserialize `Study`/`Step`; `cbindgen` generates the matching C header directly from the Rust source, so it can't drift out of sync by hand. The `postcard` encode/decode logic (decision 3) stays inside the compiled Rust code — C firmware calls into it rather than re-implementing the wire format, which is what keeps this from becoming the three-independently-maintained-definitions problem decision 1 exists to avoid.
8. **Distributed as a sibling-repo dependency, not published to a registry — amended 2026-08-18 to a Cargo path dependency, not the git reference originally planned.** `embarch-core` and `embarch-api` consume `embarch-study-designer` directly rather than as a published crates.io/private-registry package — avoids registry version-bump-and-republish overhead while the type model (§4) is still actively changing across all three consumers, all of whom need to track it at head rather than a pinned release. Originally specified as a git dependency; actually implemented as `embarch-study-designer = { path = "../embarch-study-designer" }` in both consumers' `Cargo.toml`s instead, once Milestone 2 (`embarch-roadmap.md`) needed the dependency wired for real — a plain path is simpler for local co-development (edits to this crate are picked up by the next `cargo build` in either consumer with no commit/push/re-vendor step) and is exactly what `DOC-PROTOCOL.md` §2's sibling-repo layout already assumes every cross-repo reference can rely on. A git dependency remains an option to revisit if a consumer's checkout ever isn't a true sibling of this repo (a CI runner, a machine without all four repos cloned side by side) — not needed for any real workflow yet. The repo itself: [gabrieltetar/embarch-study-designer](https://github.com/gabrieltetar/embarch-study-designer), a standalone sibling repo alongside `embarch-core`/`embarch-api`/`embarch-doc` per `DOC-PROTOCOL.md` §2 — not folded into an existing repo as a workspace member, since three independently-versioned consumers (two Cargo dependents, one FFI/C consumer) is exactly the case a shared standalone crate is for. How dev-bench firmware's own build pulls in the compiled staticlib from this repo is resolved too — see §7's update to the nRF54 cross-compilation item.
9. **Async, job-based execution for the new Core↔dev-bench-bridging HTTP surface, not a single blocking call like `/flash`.** A `Study`'s BLE steps (advertise, wait for a connection) can legitimately take an unbounded time, unlike Core's existing bounded operations — a synchronous call would either need an unreasonably long client-side timeout or risk truncating a study mid-run. Core instead accepts a `Study`, returns a `study_id` immediately, and reports progress/result via polling. Full endpoint shapes in §5.1; this decision covers the *shape* of the interaction, which is a property of the whole study-execution flow this crate's types serve, not just Core's implementation.
10. **Serial framing: COBS-encoded postcard messages, versioned by an append-only top-level enum, not a manual length prefix or version byte.** postcard itself has no message framing or self-describing schema. COBS (Consistent Overhead Byte Stuffing) wraps each postcard-encoded message with a self-terminating frame that can resync after a dropped/corrupted byte — chosen over a fixed length-prefix header, which desyncs the reader on any single corrupted length field until a resync heuristic kicks in, a real risk on a physical UART link. The `cobs` crate is `no_std`-compatible with no allocator required, matching decision 5. Versioning is handled by making every message dev-bench sends/receives a variant of one top-level `serde`-derived enum (e.g. `DevBenchMessage`) — postcard's varint-encoded enum discriminant gives wire compatibility across additions for free, provided variants are only ever appended, never reordered or removed, which is the discipline this decision commits to rather than a separate hand-rolled version byte. New variants added later for the dev-bench→Core streaming mechanism (§3 decision 20) follow the same append-only discipline.
11. **Result storage splits by data shape: a JSON events file plus a CSV data file, not one combined file or a database.** Per-step pass/fail and captured BLE data go in a small, human-readable `events.json`; power time-series samples — potentially large, high-sample-rate — go in a separate `data.csv`, referenced from `events.json` rather than embedded. Chosen so the common case (check whether a study passed) never requires parsing a large series, while still following the suite's "no database" principle (`embarch-api/design.md` §3.6) for the small side of the split. Full layout in §5.2.
12. **A manually-bumped schema-version constant, checked at both connection points, rather than silent trust in "everyone tracks head."** Per decision 8, `embarch-core` and `embarch-api` consume this crate as a git dependency at head, but the two are deployed and redeployed independently (e.g. Core native on Windows, API elsewhere) — nothing stops one side from running a build a change or two ahead of the other, and a drifted `Study`/`StudyResult` shape would fail in whatever way `serde` happens to fail, not with a clear error. The crate exposes `STUDY_DESIGNER_SCHEMA_VERSION: u32`, bumped by hand only when a wire-relevant type changes (independent of Cargo.toml's own semver, which bumps for reasons that don't affect the wire shape at all). It's checked at both hops, in the way each hop's own connection-establishment step already works:
    - **`embarch-core` ↔ `embarch-dev-bench` (serial, §3/§10)** — the hop most exposed to drift, since dev-bench firmware is flashed once and can silently lag behind a rebuilt Core. The first messages exchanged when Core opens the serial port are a `Hello { schema_version: u32 }` / `HelloAck { schema_version: u32, compatible: bool }` pair (both variants of the same `DevBenchMessage` enum decision 10 already establishes), before any `Study` traffic. A mismatch fails the connection outright rather than proceeding and failing mid-study on a decode error.
    - **`embarch-api` ↔ `embarch-core` (HTTP, §5.1)** — no separate handshake call; `GET /status` (`embarch-core/design.md` §4) already serves as the connection-establishment check, so it gains a `study_designer_schema_version: u32` field for `embarch-api` to compare against its own compiled-in constant before submitting a `Study`.
    
    This is a version *mismatch detector*, not a compatibility *negotiator* — there's no fallback to an older wire format on a mismatch, matching the suite's existing minimal-viable posture (no config hot-reload, single shared token) rather than building version-negotiation machinery nothing yet needs.

    **`Hello` also now doubles as a hard reset.** Independent of the version check above, receiving a `Hello` unconditionally tells dev-bench to abort whatever it's currently running (any in-progress `Study`) and clear its execution state before replying with `HelloAck`. This is what lets Core recover to a usable connection after its own crash/restart (§3 decision 16) without a separate abort message or waiting out dev-bench's own step timeouts first.

    **`Hello` also now carries `host_utc_ms: u64`.** Dev-bench has no other clock source, so this is its only way to learn wall-clock time at all: it seeds/resyncs its own UTC offset (correcting its free-running tick counter against this value) every time it receives a `Hello` — i.e. on every connection and reconnection (§3 decision 16's amendment below). This is what makes `Sample.rx_utc_ms` (§4.7) a real UTC timestamp rather than dev-bench-uptime-relative. Best-effort periodic resync, not continuous NTP-style discipline — the acceptable drift between resyncs is an open item (§7), same posture as this doc's other hardware-unvalidated constants.
13. **Per-step, not per-study, fail-continuation policy: `Step.continue_on_fail: bool` (§4.2), not a single study-wide abort-on-fail switch.** A `Study`'s steps often mix "must pass or the rest is meaningless" checks (e.g. a `BleConnect` step — nothing downstream works without a connection) with "record and move on" checks (e.g. a `DataExchange` step that's informational for a fuzzing run rather than fatal to it). A single study-wide switch can't express that mix; a per-`Step` bool can. Defaults to `false` (abort the `Study` immediately on this step's `Fail`/`TimedOut` outcome), matching typical test-runner semantics for §1's automated-testing use case — an author opts a specific step into `true` only where continuing past its failure is actually useful. This governs only the device-observed `Outcome` (§4.5) — the real-time signal dev-bench itself can act on. It has no bearing on the separate, Core-side post-hoc content-validity check (§3 decision 19): dev-bench can't know that result in time to decide whether to continue, so `continue_on_fail` simply doesn't apply to it.
14. **Correlation by array position (`step_index: u32`), not by `Step.name`, for `StudyResult`/`StepResult`, and for the new `ValidationSource` (§3 decision 19).** `Step.name` (§4.2) stays purely a human-readable label — useful when a person reads `events.json` directly (§5.2) — but nothing in the wire types uses it to locate a step. `Study.steps` is already order-significant (§4.1: "run in order"), so a step's position in that `Vec` is already a unique, stable-within-that-`Study` identifier; reusing it costs no new field and sidesteps the ambiguity a name-based lookup would have if a `Study` author (or a fuzzer generating `Step`s, §4.5) gave two steps the same `name`. Encoded as `u32`, not `usize` — `usize`'s width isn't fixed across the architectures this wire format actually crosses (a 64-bit host running `embarch-core`/`embarch-api` vs. a 32-bit nRF54 MCU running dev-bench firmware, decision 7), and postcard would encode a mismatched-width `usize` inconsistently between them. `ValidationSource.step_index` originally had to reference a strictly earlier index, back when `Validate` was itself an ordered `Step` (now removed, §3 decision 22) — that constraint no longer applies now that post-hoc validation lives in `Study.validations`, a separate list Core evaluates only once the whole `Study` has finished running: by then every step (if the study completed) has already executed, so `step_index` just needs to be in-bounds for `Study.steps`, in either direction, which Core checks up front (§3 decision 18).
15. **Fixed-capacity `heapless` collections, not `alloc`-based `Vec`/`String`, for every sequence/string field in §4 — with concrete max-size constants.** Decision 5 commits the crate to `#![no_std]`, and decision 3 already treats postcard's own encoding as allocator-free — but neither decision actually constrained the crate's *own* data types: as originally drafted, `Study.steps: Vec<Step>`, `Step.name: String`, `GattOperation::Write { payload: Vec<u8> }`, and similar fields all require a global heap allocator (`extern crate alloc`) somewhere in whatever links this crate — not something dev-bench firmware (bare-metal C, decision 7) is guaranteed to provide. Resolved by switching every such field to `heapless::Vec<T, N>` / `heapless::String<N>` — `heapless`'s `serde` feature implements `Serialize`/`Deserialize` for both, and pairs with postcard with no allocator anywhere in the chain, closing the loop decision 3 started: the crate is now allocator-free end to end, not just at the encoding layer. This forces a concrete max-size constant onto every such field rather than leaving it unbounded, which also directly serves §1's fuzz-testing use case: a fuzzer generating `Step`s (§4.5's fuzzing note) now has an explicit ceiling to generate within, rather than being able to construct a `Study` no real dev-bench MCU could ever hold in memory. Constants (module `limits`, all `pub const _: usize`):
    - `MAX_STEPS_PER_STUDY = 64` — `Study.steps`, `StudyResult.steps`.
    - `MAX_STUDY_NAME_LEN = 64` — `Study.name`, `StudyResult.study_name`.
    - `MAX_NAME_LEN = 32` — `Step.name`, `StepResult.step_name`.
    - `MAX_SERVICE_UUIDS = 4` — `BleAdvertise.service_uuids`.
    - `MAX_LOCAL_NAME_LEN = 26` — `BleAdvertise.local_name`; sized to fit inside a legacy 31-byte BLE advertising PDU alongside AD-structure/flags overhead, not an arbitrary round number.
    - `MAX_PAYLOAD_LEN = 512` — `GattOperation::Write.payload`, `StepResult.captured_data`, `ExpectedValue::Equals`/`Contains`; sized above BLE 5's practical extended-MTU ceiling (247-byte ATT_MTU / 251-byte L2CAP payload), not the legacy 23-byte default, so a single-PDU-worth exchange never truncates.
    - `MAX_FAIL_REASON_LEN = 64` — `Outcome::Fail.reason` (also reused by `ContentValidity::Invalid.reason`, §3 decision 19).
    - `MAX_RESULT_REF_LEN = 64` — `StepResult.power_samples_ref`, `StepResult.waveform_ref` (§3 decision 21).
    - `MAX_VALIDATIONS_PER_STUDY = 64` — `Study.validations`, `StudyResult.validations` (§3 decision 19); matches `MAX_STEPS_PER_STUDY` since a validation entry costs no more than a step and there's no reason to allow more validations than there are steps to validate.
    - `MAX_CSV_ROW_LEN = 96` — `Sample::to_csv_row`'s returned buffer (§4.7); sized to comfortably fit `rx_utc_ms` (up to 20 ASCII digits for a `u64`), a `MAX_NAME_LEN`-bounded step name, a formatted `value`, and separators — now also `unit`/`channel_id` (§3 decision 27), still comfortably within budget since both are short (a `Unit` variant name, one or two digits). (`MAX_STREAM_CHUNK_LEN` from an earlier revision of this list is retired — since `DevBenchMessage::StreamChunk` now carries a `Sample` directly, a small fixed-size struct, rather than an arbitrary-length raw byte buffer, there's nothing left for a byte-length capacity constant to bound; see §3 decision 20's implementation note.)
    - `MAX_BATCH_SAMPLES = 32` — `StreamChunkBatch.values` (§3 decision 25); placeholder-but-concrete, same posture as every other constant here, sized to keep one batched frame comfortably within a UART receive buffer at 1 Mbaud without real hardware to size against yet.

    These are placeholder-but-concrete, the same posture decision 3 already accepted for postcard itself: chosen without real dev-bench hardware to size against, flagged for re-confirmation once real nRF54 memory constraints are known. A value proving too small in practice is a version-bumped (decision 12) breaking wire-format change, same as any other field change.

16. **A Core crash/restart mid-study is an unrecoverable, catastrophic failure for that specific study — not a scenario the design tries to gracefully resume.** Each `Step.timeout_ms` (§4.2) already self-bounds any single hung action, so dev-bench is never stuck waiting past a step's own budget regardless of whether Core is still there to talk to — but that says nothing about what happens to the *study* itself if Core disappears entirely (process crash, unplugged, restarted) partway through. Resolved: that study is written off. Core's in-memory job registry (§5.1's retention policy) doesn't survive a restart, and Core — not dev-bench — is what persists `events.json`/`data.csv` (§5.2), so a study in flight when Core dies never gets a `StudyResult` written for it; a caller polling that `study_id` afterward just gets `404` (the registry entry is gone, indistinguishable from a `study_id` that never existed). Recovering the *connection* itself (as opposed to that specific study) is decision 12's `Hello`-as-hard-reset amendment: when Core comes back and reconnects, dev-bench aborts whatever it was still running and both sides start clean. Raw data already streamed to disk before the crash (§3 decision 20) may still be sitting in `data.csv`/`waveform.csv` on Core's disk — a partial diagnostic artifact, not a completed result — since decision 20 writes incrementally rather than buffering until the end.

    **A dev-bench crash/hang mid-study is symmetrically catastrophic — and needs a Core-side watchdog to even detect it.** The treatment above is written one-directionally: what happens when *Core* dies. A dev-bench firmware crash or hang partway through a study is written off exactly the same way — no attempt to detect-and-resume that specific study — but it can't rely on the same detection mechanism, because each `Step.timeout_ms` is enforced by dev-bench itself; if dev-bench is the thing that's hung or crashed, nothing on the device side is left to report `TimedOut`. Core therefore also enforces its own host-side watchdog: it expects a `StepResult` for the in-flight step within `timeout_ms` plus a small fixed grace margin of sending it (exact value open, same placeholder posture as §7's other timing constants), and treats that margin lapsing — or the serial connection dropping outright — as an immediate `"failed"` outcome for the study, the same terminal state a device-reported `Fail`/`TimedOut` already produces, just detected by Core instead of by dev-bench. Recovering the *connection* for whichever study comes next still goes through the same `Hello`-as-hard-reset path already established above.

17. **A CRC-sealed integrity check on `Study.steps`, checked independently at both the API↔Core and Core↔dev-bench hops.** Neither existing safeguard covers payload corruption: COBS (decision 10) only provides frame resync after a dropped/corrupted byte, not corruption *detection*, and postcard itself has no checksum; the API↔Core hop is plain JSON over HTTP with no equivalent check at all. `Study` gains a `steps_crc: u32` field, computed by whoever authors/submits the `Study` (`embarch-api`, or a human via the CLI) via a crate-exported `steps_crc(steps: &heapless::Vec<Step, N>) -> u32` function (CRC-32; exact `no_std`-compatible crate TBD, e.g. `crc` — §7) over `steps` specifically — not `name`, and not the new `validations` list (decision 19), which never leaves Core's own process and so has no second party to disagree with. Checked twice: Core recomputes the same function over the `steps` it deserialized from the HTTP body and rejects with `400` on mismatch before generating a `study_id` (alongside decision 18's structural checks); then again at the serial hop, where Core includes its own `steps_crc` in the same handshake exchange decision 12 already establishes, and dev-bench recomputes over what it decoded before running any step, rejecting the study outright on mismatch rather than running with possibly-corrupted step data.

18. **Core validates a submitted `Study` before generating a `study_id` or touching the serial link — structurally, not just for CRC integrity.** Two checks, both producing a `400` with a message naming the offending field/limit rather than a raw `serde` deserialize error (important since §6's `--study-file` path means a human is often hand-writing the JSON): every `limits`-module capacity (§3 decision 15) is within bounds, and every `step_index` referenced anywhere in the new `Study.validations` list (§3 decision 19) is in-bounds for `Study.steps` (decision 14's revised, no-ordering-constraint rule).

19. **Two-tier validation: a real-time, device-observed `Outcome` per step, and a separate, Core-side, post-hoc content-validity check — not one mechanism doing both.** The original design conflated "did this step's action mechanically succeed" with "was the data it captured actually correct" into one `Validate` `Action` (now removed, §3 decision 22). They're different questions, answered by different actors at different times:
    - **Firmware-side, real-time:** a `DataExchange` step's existing `Outcome` (Pass/Fail/TimedOut, §4.5) already *is* this — did the GATT operation complete without a protocol-level error or timeout. Nothing new here; this is what `continue_on_fail` (§3 decision 13) gates, exactly as it already did.
    - **Core-side, post-hoc:** a new `Study.validations: heapless::Vec<PostHocValidation, {limits::MAX_VALIDATIONS_PER_STUDY}>` list, sibling to `steps`, never transmitted to dev-bench (it has nothing to do with it — dev-bench only ever receives `Study.steps`, §3 decision 17). Each entry is `PostHocValidation { source: ValidationSource, check: PostHocCheck }`, where `ValidationSource { step_index: u32, channel: DataChannel }` names which step and which of its data channels to read (`DataChannel::CapturedData | PowerSamples | SensorWaveform`, §4.6), and `PostHocCheck` is either `Simple(ExpectedValue)` (the original Equals/Contains/InRange, §4.3) or `Signal(SignalCheck)` — a new, richer enum of check kinds (mean-in-range, glitch/threshold detection, frequency-domain checks, etc.; illustrative placeholder set, §4.6) needed for power time-series and sensor-waveform data (PPG and similar), which a byte-equality check can't meaningfully express. Evaluated by Core **only if and when the study reaches `"completed"` status** — skipped entirely on any early abort/failure, even for steps that did capture data before the abort; results land in a parallel `StudyResult.validations: heapless::Vec<ValidationResult, {limits::MAX_VALIDATIONS_PER_STUDY}>`, empty exactly when validation didn't run. `ContentValidity` (`Valid` | `Invalid { reason: heapless::String<{limits::MAX_FAIL_REASON_LEN}> }`) is its own type, not a reuse of `Outcome` — `TimedOut` has no meaning for a desktop-side comparison. The actual `SignalCheck` evaluation logic — the number-crunching, not the wire shape — lives behind a `core-validation` Cargo feature on `embarch-study-designer` that only Core's build enables (needing `std`/`alloc`, floating point, possibly an FFT library); `embarch-api` and dev-bench firmware link the crate without that feature, so they see and can serialize/display every `SignalCheck` variant but never compile the code that evaluates one.

20. **A streaming sub-protocol from dev-bench to Core for continuous power/sensor-waveform capture, replacing discrete end-of-window sampling.** A step's `power_sample` window (§4.2/§4.4) or a new streamed sensor capture (§3 decision 21) can run for the length of the step, producing far more data than fits in one bounded message. New `DevBenchMessage` variants (append-only, same discipline as decision 10): `StreamStart { step_index: u32, channel: StreamChannel }`, `StreamChunk { sample: Sample }` (§4.7), `StreamEnd { step_index: u32, channel: StreamChannel }` (`StreamChannel::Power | SensorWaveform`, §4.6) — chunks in between carry no `step_index`/`channel` of their own, since Core tracks which channel is "open" from the last matching `StreamStart` it saw, keeping per-chunk overhead minimal on a UART link. `StreamChunk` carries a `Sample` directly, not arbitrary raw sensor bytes — so a chunk is self-contained and hardware-agnostic at the wire level; translating a raw ADC/sensor reading into a `Sample` (and stamping its `rx_utc_ms`) is dev-bench's own job before the value ever reaches the wire, which is what keeps Core's CSV-writing logic (§5.2) free of any hardware-specific decoding. Since `Sample` is a small fixed-size struct, no separate byte-length capacity constant is needed for it, unlike this decision's original raw-bytes framing. More than one channel can be open on the same step concurrently (e.g. a power window overlapping a sensor-waveform capture), so both `Start` and `End` carry the channel tag to disambiguate. Core writes each incoming chunk to disk **incrementally** — appending to `data.csv` or the new `waveform.csv` (§5.2) as it arrives, rather than buffering the whole capture in memory until the study finishes — so raw capture data can survive even a Core crash that writes off the study itself as failed (§3 decision 16), even though post-hoc validation (decision 19) still never runs over an incomplete study.

21. **Sensor-waveform capture is a new `GattOperation` variant, not a step-level field like `PowerSampleWindow`.** `GattOperation::StreamCapture` joins `Read`/`Write`/`Notify`/`Indicate`/`Subscribe` (§4.3) — a continuous capture of whatever the characteristic streams (e.g. a PPG waveform), landing in the new `SensorWaveform` data channel rather than `StepResult.captured_data`. No separate duration field, matching `PowerSampleWindow`'s existing reasoning (§4.2): it runs for exactly as long as the step's own `timeout_ms`/completion allows, so a capture can't silently outlive or fall short of the step characterizing it.

22. **`Action::Validate` (original §4.3) is removed.** Its job — checking a prior step's captured data against an expected value — is now done entirely by the new, Core-side, post-hoc `Study.validations` mechanism (decision 19). Keeping both would mean two overlapping validation systems; dev-bench firmware now has no validation-related code path at all, only the three remaining `Action` variants plus the new `StreamCapture` `GattOperation`.

23. **The FFI boundary (decision 7) is panic-safe by construction: `panic = "abort"`, plus explicit error codes on every `extern "C"` function — not `catch_unwind`.** A Rust panic unwinding across an `extern "C"` boundary into C firmware is undefined behavior; decision 7 established the staticlib but left this unaddressed. Resolved in favor of the simpler of the two standard fixes: `panic = "abort"` in the crate's `[profile.release]` (already the natural fit for a `no_std` bare-metal target with no unwinding runtime to begin with, decision 5) rather than wrapping every exported function body in `std::panic::catch_unwind` (which itself needs `std`, unavailable here). Every exported `extern "C"` function (build/serialize/deserialize `Study`/`Step`, decision 7) returns an explicit, C-friendly result — an integer status code (`0` = success, negative = a specific documented failure reason: buffer-too-small, capacity-exceeded, malformed input) plus out-parameters for any produced value — rather than a Rust `Result`/panic ever reaching the C caller. Mirrors decision 18's Core-side validation philosophy (name the specific failure, don't let a raw internal error surface) at the FFI boundary instead of the HTTP boundary.

24. **`Study` submission and per-step results get their own `DevBenchMessage` variants — the whole `steps` vector transferred in one message, not one step at a time.** Closes the single largest gap the 2026-08-15 design-improvement review found (its item 1): `embarch-core/design.md` §4 said Core "begins relaying `Study.steps`" to dev-bench, but no wire message actually carried a `Study` before this decision, and it was unspecified whether steps crossed the serial link one at a time or as a whole vector — a real gap, since decision 17's `steps_crc` is computed over the whole vector at once. Two new variants, append-only per decision 10: **`StudyStart { steps: heapless::Vec<Step, {limits::MAX_STEPS_PER_STUDY}>, steps_crc: u32 }`** (Core→dev-bench, sent once immediately after the `Hello`/`HelloAck` handshake — the whole vector in one postcard-encoded message, not streamed step-by-step) and **`StudyDone { completed: bool }`** (dev-bench→Core, sent once after the last step dev-bench actually ran, whether that's every submitted step or an early stop via `continue_on_fail`). Whole-vector transfer, not per-step streaming, because it's the shape that keeps decision 17's CRC check atomic: a per-step transfer would need either a running CRC accumulated message-by-message or per-message CRCs plus a final reconciliation, for a payload that's already small and bounded (`MAX_STEPS_PER_STUDY = 64`, each `Step` itself capacity-bounded by decision 15) and therefore cheap to send in one frame. Per-step *results* stream back incrementally instead, mirroring `StreamChunk`'s reasoning (decision 20): a new **`DevBenchMessage::StepResult { step_index: u32, result: StepResult }`** (§4.5) variant is sent as each step completes, so Core can write `events.json`'s per-step entries progressively and the host-side watchdog (decision 16) can key off individual `StepResult` arrivals rather than one final blob at the end of the study.

25. **UART link budget stated explicitly, and `StreamChunk` batches samples instead of one frame per sample.** Closes item 3 of the review: a COBS+postcard-framed single-`Sample` `StreamChunk` (decision 20) is roughly 10–14 bytes on the wire, and the power-profiling rate this crate is meant to serve (10–100 kHz, per §1's motivating use case) needs far more throughput than one frame per sample can deliver at any baud a UART link can reasonably run. Two changes: (1) **the Core↔dev-bench UART link runs at 1 Mbaud** — the practical ceiling for both the nRF54L15's UART peripheral and the on-board J-Link VCOM bridge it crosses (`embarch-dev-bench/design.md` §3 decision 6) without exotic clocking, stated here since nothing in either doc previously named a rate. (2) **`StreamChunk` gains a batched sibling, `StreamChunkBatch { base_utc_ms: u64, sample_interval_ms: u32, unit: Unit, channel_id: u8, values: heapless::Vec<f32, {limits::MAX_BATCH_SAMPLES}> }`**, append-only alongside the existing `StreamChunk` (kept, not removed, for wire-compatibility with anything still speaking an earlier schema version) — one base timestamp plus a fixed sample interval (both already known at `StreamStart` time, from `PowerSampleWindow.sample_rate_hz`) means every sample after the first needs no per-sample timestamp, only its `f32` value, turning per-sample framing overhead into a per-batch cost. `unit`/`channel_id` (decision 27) are carried once per batch, not once per sample, since a single capture window doesn't change units or channel mid-stream. `limits::MAX_BATCH_SAMPLES` (placeholder `32`, same posture as every other `limits` constant, decision 15) governs how many samples one batch carries. Core reconstructs each sample's `rx_utc_ms` as `base_utc_ms + i * sample_interval_ms` when writing `data.csv`/`waveform.csv` rows (§5.2) — placeholder-but-concrete, to be re-confirmed once real dev-bench sampling hardware exists and the actually-achievable rate is known, same posture as decision 3/15's other hardware-unvalidated constants.

26. **`steps_crc` is filled in by whoever *submits* a `Study`, not required of whoever *authors* one — closing the gap between decision 17's integrity check and the symmetric human/agent principle (decision 6).** Item 4 of the review: decision 17 requires a correct CRC-32 on submission, which makes a hand-authored `Study` JSON file (`embarch-api/design.md` §5a's `run-study --study-file`) unusable without a human computing a CRC by hand. Resolved without touching the check itself — Core still recomputes and validates `steps_crc` exactly as decisions 17/18 already specify — by moving *who fills the field* before it crosses the wire: `embarch-api`'s `run_study` tool / `run-study` CLI subcommand (§6) computes `steps_crc` via this crate's own exported `steps_crc()` function and overwrites whatever value (including a missing/zero one) was present in the submitted JSON, immediately before the `POST /study` call. A caller that already computed a correct value (a fuzzing driver generating `Study`s programmatically) is unaffected — the recomputation is idempotent. **Also new:** the crate ships a generated JSON Schema for `Study` (via the `schemars` dependency already present for `core-validation`'s use, decision 19) as a build artifact, `study.schema.json`, so a human hand-authoring a `--study-file` gets editor/CI validation before ever submitting, independent of the CRC question entirely.

27. **`Sample` gains `unit` and `channel_id` fields — resolving an ambiguity `StreamChannel`'s two variants (`Power`, `SensorWaveform`, §4.6) already implied but never settled.** Item 38: today's `Sample { rx_utc_ms: u64, value: f32 }` (§4.7) is one shape shared by both power and arbitrary sensor-waveform data, with nothing on the wire saying what `value` means or which of possibly-several concurrent channels on the same step it came from — a real gap the moment a capture needs more than one bare scalar (e.g. current *and* voltage sampled together, or a multi-lead sensor). Adding these fields now, rather than after real dev-bench hardware forces the question, avoids stacking a second version-bumped breaking wire change on top of the one hardware validation will likely already require. New fields: **`unit: Unit`** — a small, append-only enum (`Milliamps`, `Volts`, `Milliwatts`, `Raw`), extended as real hardware needs more — and **`channel_id: u8`**, disambiguating more than one concurrent stream on the same `StreamChannel` (`0` for the common single-channel case). Both are threaded through `Sample::to_csv_row`/`csv_header` (§4.7) as two new trailing CSV columns, and are carried once per batch (not once per sample) in `StreamChunkBatch` (decision 25).

28. **Post-hoc validation can now optionally run over an aborted study's completed steps, gated by a new opt-in `Study.validate_on_abort: bool` field defaulting to `false`.** Item 39: decision 19 skips post-hoc validation entirely on any non-`"completed"` study status — defensible for the automated-testing use case, but working against §1's *first-listed* purpose, fuzz testing, where a fuzzer often wants to know whether data a step *did* capture before a later step aborted the study was itself valid. Default `false` preserves every existing behavior and every already-shipped assumption (`StudyResult.validations` stays empty unless this is set explicitly); when `true`, Core runs `Study.validations` (§4.6) against whichever prefix of `Study.steps` actually executed before the abort — a `ValidationSource.step_index` referencing a step beyond that prefix is skipped, not an error, and reported as `ContentValidity::Invalid { reason: "step not reached" }` so a caller can distinguish "not reached" from "checked and failed."

29. **The fuzz-testing loop against `MAX_STEPS_PER_STUDY = 64` and one-study-at-a-time is documented, not changed.** Item 40 flagged the combination of a 64-step ceiling, no queue, and a `409 Conflict` on a concurrent submission as making a fuzzing driver look like an awkward N-round-trip loop against a rejection. Examined and left as-is deliberately: raising the ceiling doesn't help a fuzzer exploring many *distinct* short studies rather than one very long one (§4.1's "fuzzing, explicitly not modeled here" note already frames a `Study` as fuzzing's *output*, one concrete value per run), and a queue is real new machinery — persistence, ordering, partial-failure semantics — this suite has avoided everywhere else (`embarch-api/design.md` §3.6's no-database stance). The intended shape, stated explicitly here for the first time: a fuzzing driver runs entirely client-side (`embarch-api`, or a human/agent script driving it), generating one `Study` at a time, submitting it, polling `GET /study/{id}` (§5.1) to a terminal status, then generating and submitting the next — the poll loop *is* the intended backpressure mechanism, not a workaround for a missing one.

30. **Core records its own arrival time alongside every incoming message, independent of `Hello`'s resync — closing item 42 without changing when dev-bench's clock actually resyncs.** `Sample.rx_utc_ms` (§4.7) is stamped by dev-bench's own free-running clock, corrected only when a `Hello` arrives (decision 12) — for a long-running study with no reconnect, that clock free-runs between resyncs with no way to correct for it after the fact. Resolved without adding a second resync trigger (decision 12 deliberately keeps that tied to connection establishment, not a periodic timer): Core timestamps its own receipt of every `DevBenchMessage` that matters for timing — `StepResult`, `StreamChunkBatch`/`StreamChunk` — using its own wall clock, and records that alongside the message's own `rx_utc_ms` in `events.json`/the CSV files as a new, additive `core_rx_utc_ms` column that doesn't change `Sample`'s own wire shape. This doesn't correct drift in real time, but gives post-hoc analysis (a `SignalCheck`, or a human reviewing `data.csv`) the raw material to detect and account for it after the fact — which a resync-on-`Hello`-only design otherwise has no way to surface.

## 4. Concrete data model

Field-level, resolving milestone-3.md §3.1: concrete enough that a `#[derive(Serialize, Deserialize)]` Rust translation is mechanical — exact byte/UUID representations (`[u8; 16]` vs. a `uuid`-crate newtype, `no_std`-compatible either way) are implementation detail, not a design choice left open here. Every `Vec<T>`/`String` below is `heapless::Vec<T, N>`/`heapless::String<N>`, not `alloc`-based — §3 decision 15's `limits` module defines each `N`.

### 4.1 `Study`

- `name: heapless::String<{limits::MAX_STUDY_NAME_LEN}>` — human-readable identifier; not required to be unique (uniqueness, if ever needed, is an `embarch-api`-level concern per §6, not enforced by the type itself).
- `steps: heapless::Vec<Step, {limits::MAX_STEPS_PER_STUDY}>` — run in order. A `Study` is entirely static once submitted for v1: no parameter-range/generator construct (see the fuzzing note below).

### 4.2 `Step`

- `name: heapless::String<{limits::MAX_NAME_LEN}>` — label surfaced in results (`StepResult.step_name`, §4.5), so a `Study` author and whoever reads results can correlate them without relying on array index.
- `action: Action` (§4.3) — the one thing this step does.
- `timeout_ms: u32` — max wall-clock time dev-bench allows this step before reporting `Outcome::TimedOut` rather than letting a stalled BLE connect/advertise hang the whole `Study`.
- `power_sample: Option<PowerSampleWindow>` (§4.4) — optional, overlapping power measurement bounded by this step's own start/end (or its `timeout_ms`, whichever comes first) — no separate duration field, so a window can't silently outlive or fall short of the step it's meant to characterize.
- `continue_on_fail: bool` — when this step's `Outcome` (§4.5) is `Fail` or `TimedOut`: `false` (the default) aborts the `Study` immediately, running no further steps; `true` continues to the next step regardless. Defaults to `false` since most steps in the automated-testing use case (§1) are prerequisites for what follows — a failed `BleConnect` makes every later `DataExchange` step moot. An author sets it `true` only on a step where continuing past that step's own failure is actually useful (e.g. a `DataExchange` step in a fuzzing run whose response content doesn't itself gate the rest of the sequence, or a purely diagnostic step). Governs only the device-observed `Outcome`, not the separate Core-side post-hoc content-validity check, which dev-bench can't act on in real time regardless of this flag. §3 decision 13.

### 4.3 `Action`

Three variants, matching §1's motivating categories (stimulus/interaction plus measurement — content validation is now handled entirely post-hoc by Core, §3 decision 19, not as a fourth on-device `Action`):

- **`BleAdvertise { local_name: Option<heapless::String<{limits::MAX_LOCAL_NAME_LEN}>>, service_uuids: heapless::Vec<Uuid, {limits::MAX_SERVICE_UUIDS}>, adv_interval_ms: u16 }`** — dev-bench advertises as a BLE peripheral for the DUT to discover.
- **`BleConnect { role: BleRole, target_address: Option<BleAddress> }`** — `BleRole` is `Central` or `Peripheral` (which side dev-bench plays for this step); `target_address` is `None` for "accept/connect to whichever DUT shows up first" (the common case — a `Study` author usually doesn't hardcode the DUT's BLE address) or `Some(addr)` to require a specific one. **`BleAddress`'s 6 raw bytes are display order, most-significant byte first** (`AA:BB:CC:DD:EE:FF`) — stated explicitly here as of 2026-08-15 (closing item 47 of that day's design-improvement review), matching `Uuid`'s already-documented big-endian convention and `embarch-dev-bench`'s `ble_bridge_real.c`, which has always assumed this order and reverses on the way into Zephyr's little-endian `bt_addr_le_t` (`embarch-dev-bench/design.md` §4). Previously this crate said only "6 raw address bytes" with no order specified — a real risk, since a wrong guess means a `BleConnect` with an explicit `target_address` silently never matches.
- **`DataExchange { service_uuid: Uuid, characteristic_uuid: Uuid, operation: GattOperation }`** — UUIDs are raw, not symbolic (per your call — no separate name-resolution table to maintain). `GattOperation` is `Read`, `Write { payload: heapless::Vec<u8, {limits::MAX_PAYLOAD_LEN}> }`, `Notify { timeout_ms: u32 }` (wait for a notification, bounded independently of the step's own `timeout_ms` since a notify-wait is often shorter than the step's overall budget), `Indicate { timeout_ms: u32 }` (same wait-for-a-pushed-value shape as `Notify`, but over BLE's acknowledged indication mechanism rather than best-effort notification — the ATT-level confirmation round-trip is the GATT stack's job, not something this type models), `Subscribe` (enable notifications/indications without waiting for one, e.g. to arm a later step's `Notify`/`Indicate`), or `StreamCapture` (a continuous capture of whatever the characteristic streams for the duration of the step — e.g. a PPG waveform — landing in the new `SensorWaveform` data channel rather than `StepResult.captured_data`; no separate duration field, bound by the step's own `timeout_ms` like `PowerSampleWindow`; §3 decisions 20/21).

A step's own `Outcome` (§4.5) is the only on-device validation signal — did the action (including a `DataExchange`'s `GattOperation`) complete without a protocol-level error or timeout. Whether the *content* it produced was actually correct is a separate question, answered later and only by Core (§3 decision 19, §4.6) — the original `Validate` `Action` that used to ask that question on-device has been removed (§3 decision 22).

### 4.4 `PowerSampleWindow`

- `sample_rate_hz: u32` — dev-bench's power-sampling rate for this window. Delivered to Core via the streaming sub-protocol (§3 decision 20, `StreamChannel::Power`) rather than a single bulk transfer once the window closes.

### 4.5 `StudyResult` / `StepResult`

- **`StudyResult { study_name: heapless::String<{limits::MAX_STUDY_NAME_LEN}>, steps: heapless::Vec<StepResult, {limits::MAX_STEPS_PER_STUDY}>, validations: heapless::Vec<ValidationResult, {limits::MAX_VALIDATIONS_PER_STUDY}> }`** — the aggregate outcome, same shape whether read by `embarch-core`, `embarch-api`, or a human reading the result file directly (§5.2). `steps` is not guaranteed to be the same length as the submitted `Study.steps`: if some step's `continue_on_fail` is `false` (the default, §4.2) and that step's `Outcome` is `Fail`/`TimedOut`, execution aborts and `steps` is a proper prefix ending at that step, rather than always covering every submitted step. `validations` (§3 decision 19, §4.6) is populated only once the study reaches `"completed"` status — it stays empty on any `"failed"` outcome, even for steps that did capture data before the abort.
- **`StepResult { step_name: heapless::String<{limits::MAX_NAME_LEN}>, outcome: Outcome, captured_data: Option<heapless::Vec<u8, {limits::MAX_PAYLOAD_LEN}>>, power_samples_ref: Option<heapless::String<{limits::MAX_RESULT_REF_LEN}>>, waveform_ref: Option<heapless::String<{limits::MAX_RESULT_REF_LEN}>> }`** — `Outcome` is `Pass`, `Fail { reason: heapless::String<{limits::MAX_FAIL_REASON_LEN}> }`, or `TimedOut`. `step_name` is a denormalized copy of the corresponding `Step.name`, carried purely for human readability when reading `events.json` directly (§5.2) — it is not used for machine correlation (§3 decision 14 uses `Study.steps` array position for that, via `ValidationSource.step_index`, and `StudyResult.steps`' own position tracks the same index since steps run and are appended in order). `captured_data` holds whatever bytes a `DataExchange` read/notify step pulled off the DUT (unused for other action kinds). `power_samples_ref` is a reference (§5.2 — the CSV file it lives in) rather than raw samples inline, keeping `StudyResult` itself small and JSON-friendly even when a study captured a lot of power data. `waveform_ref` is the same kind of reference, pointing at `waveform.csv` (§5.2) instead — populated only for a step whose `DataExchange` action used `GattOperation::StreamCapture` (§3 decision 21).

**Fuzzing, explicitly not modeled here (resolved):** §1's fuzz-testing use case is served by treating a `Study` as the *output* of fuzzing, not by adding a parameter-range/generator type to these types themselves — "generate many concrete `Study` values externally (with varied `Step` parameters), submit each one" is a caller-side (`embarch-api`, or a human/agent driving it) concern. This keeps `Study`/`Step` themselves simple and keeps the fuzzing strategy free to evolve independently of the wire types.

### 4.6 Post-hoc validation types (`Study.validations` / `StudyResult.validations`, §3 decision 19)

`Study` gains a new top-level field, sibling to `steps`: `validations: heapless::Vec<PostHocValidation, {limits::MAX_VALIDATIONS_PER_STUDY}>`. Never transmitted to dev-bench (§3 decision 17) — Core is the only consumer, and only once a study reaches `"completed"` status.

- **`PostHocValidation { source: ValidationSource, check: PostHocCheck }`** — one entry per post-hoc check an author wants run.
- **`ValidationSource { step_index: u32, channel: DataChannel }`** — which step's data to check, and which of that step's data channels. No ordering constraint on `step_index` (§3 decision 14) — evaluation only ever happens after the whole study has finished.
- **`DataChannel`** — `CapturedData` (a `DataExchange` step's `StepResult.captured_data`), `PowerSamples` (a step's `PowerSampleWindow` output, streamed into `data.csv`), or `SensorWaveform` (a `GattOperation::StreamCapture` step's output, streamed into `waveform.csv`, §3 decision 21).
- **`PostHocCheck`** — `Simple(ExpectedValue)` (the original `Equals`/`Contains`/`InRange` byte-level check, unchanged in shape from the removed `Validate` `Action`) or `Signal(SignalCheck)`.
- **`SignalCheck`** — a growing, `serde`-derived enum of richer check kinds needed for time-series/waveform data, which byte equality can't express. Illustrative placeholder set, extensible over time (append-only, same discipline as `DevBenchMessage`, §3 decision 10): `MeanInRange { min: f32, max: f32 }`, `NoGlitchAbove { threshold: f32 }`, `FftPeakNear { hz: f32, tolerance_hz: f32 }`. Every consumer can serialize/deserialize/display any `SignalCheck` variant; only Core's `core-validation` Cargo feature (§3 decision 19) contains code that actually evaluates one against real sample data — `embarch-api` and dev-bench firmware link the crate without that feature.
- **`ContentValidity`** — `Valid` or `Invalid { reason: heapless::String<{limits::MAX_FAIL_REASON_LEN}> }`. Deliberately not a reuse of `Outcome` — `TimedOut` has no meaning for a desktop-side comparison run well after the study finished.
- **`ValidationResult { step_index: u32, channel: DataChannel, result: ContentValidity }`** — one per `Study.validations` entry, landing in `StudyResult.validations` (§4.5).

A related but distinct enum, used only in the wire *protocol* rather than in validation authoring: **`StreamChannel`** (§3 decision 20) — `Power` or `SensorWaveform` only, since a discrete `CapturedData` read is never delivered via the streaming sub-protocol.

### 4.7 `Sample` (streamed power/waveform data, §3 decisions 2/11/20)

- **`Sample { rx_utc_ms: u64, value: f32, unit: Unit, channel_id: u8 }`** — the one wire-level record type carried by both `StreamChannel::Power` and `StreamChannel::SensorWaveform` (§4.6); `data.csv` and `waveform.csv` (§5.2) share this identical row shape rather than each inventing their own columns. `rx_utc_ms` is stamped by dev-bench itself, at the moment it captures/receives the sample from its own sampling hardware — its own local clock, seeded and periodically resynced from Core's `host_utc_ms` on every `Hello` (§3 decision 12) — not assigned by Core on arrival, so the timestamp reflects when the sample was actually taken rather than when it happened to reach Core over a variable-latency serial link. `unit`/`channel_id` (§3 decision 27) name what `value` actually measures and, for a capture with more than one concurrent stream, which one — both are placeholder-but-concrete pending real dev-bench sampling hardware (§7); appending further fields later is a version-bumped wire change like any other (§3 decision 12). In the batched wire form (`StreamChunkBatch`, §3 decision 25), `unit`/`channel_id` are carried once per batch rather than once per `Sample`, since neither changes mid-capture.
- **`Sample::to_csv_row(&self, step_name: &str) -> Option<heapless::String<{limits::MAX_CSV_ROW_LEN}>>`** and **`Sample::csv_header() -> &'static str`** — the crate's own CSV-rendering tools (§1, §3 decision 2). Core's job writing `data.csv`/`waveform.csv` reduces to: decode a `StreamChunkBatch` (§3 decision 25) into its constituent `Sample`s, call `to_csv_row` for each with the step name of whichever step is currently open on that channel (already known from the last `StreamStart`, §3 decision 20), and append the returned row plus Core's own `core_rx_utc_ms` (§3 decision 30) — column knowledge lives only in this crate, never duplicated in Core. Row shape: `rx_utc_ms,step_name,value,unit,channel_id`, with `core_rx_utc_ms` appended by Core itself rather than by this helper (§3 decision 30 — it's Core's own receipt time, not part of the wire type). Returns `None` if `step_name` doesn't fit alongside the rest of the row within `MAX_CSV_ROW_LEN` — Core is expected to log and skip that one row rather than truncate it silently, since a truncated CSV row is a worse failure mode than a dropped one.

## 5. Relationship to embarch-core

This is a real scope expansion for Core, not a small addition. Today, Core's stated purpose is deliberately narrow: it "owns the debug probe (flash/reset) and the serial console log" for the DUT and "has no idea the EmbArch API or Claude Code exist" beyond its bearer-token-authed endpoints (`embarch-core/design.md` §1). Bridging study commands to `embarch-dev-bench` over a second serial link is a new hardware relationship for Core — a second physical connection, a second wire format (binary, not Core's existing JSON-only endpoint bodies), and new endpoints beyond the DUT-facing `/status`, `/flash`, `/reset`, `/serial-log`. The first piece of that relationship now exists: `GET /dev-bench/port` (`embarch-core/design.md` §4, §5) identifies which serial port dev-bench is on. It opens nothing and speaks no `DevBenchMessage` — every part of the hop described below is still unimplemented.

§5.1/§5.2 below now specify those endpoints and the result storage they populate — resolving what was milestone-3 follow-up work. `embarch-core/design.md` itself has been updated to match (new endpoint rows, §2 architecture diagram, module layout) per `DOC-PROTOCOL.md` §5, ahead of any actual implementation — the same "recorded ahead of code" pattern `embarch-api/design.md` §3.10 used for its CLI decision.

### 5.1 New endpoints (async job model, §3 decision 9)

| Method | Path | Body / Query | Response |
|---|---|---|---|
| `POST` | `/study` | `Study` (JSON, §4.1, including the new `validations`/`steps_crc` fields — §3 decisions 17/19) | `{ study_id: Uuid, status: "accepted" }` — Core generates `study_id`, sends a single `StudyStart { steps, steps_crc }` message (§3 decision 24) over the serial link (§3 decisions 3/10/17 — `validations` never crosses this hop, only `steps`), and returns immediately without waiting for any step to run. Before any of that, Core validates the submission (§3 decision 18: capacity limits, in-bounds `step_index` references in `validations`) and checks `steps_crc` (§3 decision 17, auto-filled by the submitter per §3 decision 26 if it was absent) — either failing rejects with `400` and no `study_id` at all, distinct from the async job's own `"failed"` status. Per-step progress arrives back as `DevBenchMessage::StepResult` (§3 decision 24), and the study's end as `StudyDone` — both drive `GET /study/{study_id}`'s `current_step` below. |
| `GET` | `/study/{study_id}` | — | `{ status: "pending" \| "running" \| "completed" \| "failed", current_step: u32?, total_steps: u32?, result: StudyResult?, reason: String? }` — `result` (§4.5, now including `validations` once they've run — §3 decision 19) is present only once `status` is `"completed"`; `"failed"` carries `reason` instead (e.g. dev-bench disconnected mid-study, or the crash/reconnect scenario §3 decision 16 covers). Unknown `study_id` → `404`. |
| `GET` | `/study/{study_id}/power-data` | — | Raw CSV bytes (`Content-Type: text/csv`, §5.2), concatenated across every step's `PowerSampleWindow` in the study; `404` if the study captured no power data or isn't `"completed"` yet. Served as bytes, not a local file path — deliberately sidesteps the class of problem `/flash`'s `firmware_path` has (`embarch-core/design.md` §7's artifact-transfer gap): Core and `embarch-api` aren't guaranteed to share a filesystem. |
| `GET` | `/study/{study_id}/waveform-data` | — | Raw CSV bytes (`Content-Type: text/csv`, §5.2), the sensor-waveform capture (`waveform.csv`, §3 decision 21) — same shape/rationale as `/power-data` above; `404` if the study captured no waveform data. |

- **One study in flight at a time**, enforced by a dedicated lock separate from Core's existing `hw_lock` (`embarch-core/design.md` §3 decision 4) — dev-bench is a second, independent physical connection, so a running study doesn't need to block a concurrent `/flash`/`/reset` against the debug probe, but two overlapping studies would both be trying to drive the one dev-bench. A `POST /study` received while another is still running is rejected outright with `409 Conflict` (body includes the in-flight `study_id`), not queued — matching the suite's minimal-viable posture (no queueing machinery exists anywhere else in Core); the caller re-submits after polling the in-flight study's `GET /study/{id}` to completion.
- **No cancel endpoint for v1** — deferred deliberately, matching the suite's existing "don't build a capability nothing yet needs" pattern (`embarch-api/design.md` §12's CLI-exit-code-granularity precedent). A stuck study still bounds itself via each `Step`'s own `timeout_ms` (§4.2).
- **Job retention**: completed/failed job status and results stay in Core's in-memory registry until Core restarts — no expiry, matching the suite's existing no-cleanup-until-restart posture (single shared token, no config hot-reload, `embarch-api/design.md` §12). The on-disk result files (§5.2) outlive the in-memory registry entry regardless. A Core restart while a study is in flight loses that study's registry entry entirely — a subsequent poll 404s, per §3 decision 16.
- **Incremental result writes.** Unlike the in-memory job registry above, `data.csv`/`waveform.csv` (§5.2) are appended to as streamed chunks arrive during the study (§3 decision 20), not written once at the end — so raw capture data can outlive a Core crash that writes off the study itself as `"failed"` (§3 decision 16), even though `events.json` and any post-hoc `validations` (§3 decision 19) never get written for that study at all.

### 5.2 Result storage (§3 decision 11)

Per completed (or failed) study, Core writes to a results directory under its own local data directory — same machine-wide-local-data convention `token_store.rs` already establishes for `EMBARCH_TOKEN` (`embarch-core/design.md` §8) — at `study_results/<study_id>/`:

- **`events.json`** — the `StudyResult` (§4.5) verbatim: per-step pass/fail, captured BLE data, everything except raw power/waveform samples — now including `validations` (§3 decision 19) once they've run. Small and human-readable; this is what `GET /study/{id}` (§5.1) returns inline once `status` is `"completed"`. Written only once, after the study reaches a terminal status *and*, for a `"completed"` study, after Core's post-hoc validation pass has finished — unlike `data.csv`/`waveform.csv` below, which are written incrementally throughout.
- **`data.csv`** — power samples across every `PowerSampleWindow` in the study, one row per `Sample` (§4.7) received over `StreamChannel::Power`. Core's job here is purely mechanical: for each `StreamChunkBatch` (§3 decision 25) it decodes into its constituent `Sample`s, it calls that type's own `to_csv_row` helper (§4.7) with the step name of whichever step is currently open on this channel (tracked from the last `StreamStart`, §3 decision 20) and appends the result plus its own `core_rx_utc_ms` (§3 decision 30) — Core holds no independent knowledge of what the columns mean or how many there are beyond that one addition, only this crate does. Row shape: `rx_utc_ms,step_name,value,unit,channel_id,core_rx_utc_ms` (header row written once, from `Sample::csv_header()` plus the `core_rx_utc_ms` column Core itself appends); `rx_utc_ms` is dev-bench's own capture-time timestamp (§4.7), not a Core-assigned arrival time — `core_rx_utc_ms` is that Core-assigned arrival time, recorded alongside for post-hoc drift correction (§3 decision 30) rather than in place of it. `value`'s real-world meaning is named by `unit` (§3 decision 27) but its exact hardware mapping is still open (§7) — the column *shape* is locked, its *content* isn't. Kept separate from `events.json` so checking a study's pass/fail never requires parsing a large, high-rate capture. `GET /study/{id}/power-data` (§5.1) streams this file's bytes.
- **`waveform.csv`** — the sensor-waveform equivalent (§3 decision 21), same `Sample` row shape as `data.csv` above, populated from `StreamChannel::SensorWaveform` batches instead. `GET /study/{id}/waveform-data` (§5.1) streams this file's bytes. Both `data.csv` and `waveform.csv` are written incrementally as `StreamChunkBatch` messages (§3 decision 25) arrive during the study, not assembled once at the end — each arriving batch is decoded into its `Sample`s and appended as that many rows, nothing buffered.

## 6. Relationship to embarch-api

Once `embarch-study-designer` has code behind it and Core exposes the study-bridging endpoints (§5.1), `embarch-api` is expected to grow a matching MCP tool surface and CLI subcommand surface, mirroring the existing `build`/`flash`/`build_and_flash`/`reset`/`serial_log` pattern (`embarch-api/design.md` §5, §5a). Because study execution is async (§3 decision 9), the shape is two calls rather than one, mirroring Core's own two-endpoint split rather than trying to fake synchronicity by blocking `embarch-api` itself until the study finishes (which would just move the "how long do we wait" problem up one layer without resolving it). This keeps faith with §3 decision 6: any hardware-facing capability reachable by an agent must be equally reachable by a human with no agent in front of them, converging on the same `embarch-study-designer` types and the same orchestration code — not two independent implementations.

**Locked-in tool/subcommand surface** — implemented 2026-08-18 (Milestone 2, Dev Bench Self-Test); naming/param shapes below match exactly what shipped, see `embarch-api/design.md` §5/§5a for the real implementation detail:

| Name (MCP tool = CLI subcommand) | Params | Behavior |
|---|---|---|
| `run_study` | MCP: `study` (`serde_json::Value`, not a typed `Study` schema — this crate doesn't derive `schemars::JsonSchema` on `Study`, so `rmcp`'s `#[tool]` param struct can't use it directly; deserialized into `Study` inside the handler, with a clear schema-mismatch error on failure, same practical effect as a typed param). CLI: `--study-file <path>` (a JSON file matching the same schema — `Study`'s nesting makes per-field CLI flags impractical, unlike `build`/`flash`'s scalar args). | Calls Core `POST /study` (§5.1) and returns `{ study_id }` immediately. No `project` param — unlike `build`/`flash`, a study isn't tied to one of `embarch-api`'s configured projects; it targets whatever DUT is connected through Core's one dev-bench serial link. Recomputes/overwrites `steps_crc` via this crate's own `steps_crc()` before ever calling Core (decision 26). A `400` from Core (failed pre-flight validation or CRC check, §3 decisions 17/18) surfaces as an immediate MCP/CLI error with no `study_id` at all — distinct from `study_status` later reporting `"failed"` for a study that was accepted but failed during or after execution. |
| `study_status` | `study_id` (both MCP and CLI). | Calls Core `GET /study/{study_id}` (§5.1) and returns its status/`current_step`/`total_steps`/`result`/`reason` shape verbatim. |
| `study_power_data` | `study_id` (both MCP and CLI). | Calls Core `GET /study/{study_id}/power-data` (§5.1) and returns the raw CSV bytes (as MCP tool content, or written to stdout/a `--out <path>` file for the CLI). Named 2026-08-15, closing item 44 of the design-improvement review — previously left as "a small remaining item" with no name at all. |
| `study_waveform_data` | `study_id` (both MCP and CLI). | Same shape as `study_power_data`, calling `GET /study/{study_id}/waveform-data` instead. Named alongside `study_power_data` for the same reason — no rationale to name one and not the other. |

No convenience "block until done" wrapper (a `run_study`-side analogue of `build_and_flash`'s bundling) for v1 — deferred deliberately, matching the suite's existing minimal-viable posture (`embarch-api/design.md` §12's CLI-exit-code-granularity precedent, `design.md` §5.1's "no cancel endpoint for v1"): a study's total runtime is far less predictable than a build's, so a blocking wrapper would need its own timeout policy layered on top of Core's per-`Step` `timeout_ms` (§4.2) for no clear benefit yet. Revisit if a real caller finds the two-call poll loop genuinely burdensome.

## 7. Open questions / future work

- **The physical `embarch-dev-bench` design itself** (what BLE radio hardware, what power-sampling hardware, connector/form factor) stays entirely out of scope here — `embarch-dev-bench/design.md` remains a placeholder by deliberate choice (this milestone's scoping decision), not an oversight. `data.csv`'s (§5.2) exact power-sample columns depend on this and stay unresolved until it isn't.
- ~~**nRF54 cross-compilation toolchain and build-system wiring for the FFI staticlib.**~~ — **resolved 2026-08-18** (`embarch-dev-bench/design.md` §3 decision 8, Milestone 2): the crate cross-compiles cleanly for the nRF54L15's Cortex-M33 core via `cargo rustc --release --target thumbv8m.main-none-eabi --features ffi --lib --crate-type staticlib`, invoked automatically from `embarch-dev-bench/app/CMakeLists.txt` as part of a plain `west build` — one build command, as decision 8 there always intended, just via a direct path-based `cargo` invocation rather than formal west-manifest module plumbing (see that decision's own text for why). The panic-handler gap this bullet used to track is closed: a `#[panic_handler]` now exists in `src/ffi.rs`, gated to `target_os = "none"` specifically so it doesn't fire (and conflict with libstd's own) on `cargo test --features ffi`'s host-target build. **One real gotcha found closing this, worth keeping on record:** the target triple must be the *soft*-float variant, `thumbv8m.main-none-eabi`, not `-eabihf` — this firmware's Zephyr build has no hardware-FPU ABI enabled, and a hard-float-ABI staticlib fails to link against it ("uses VFP register arguments") the moment any code path touches an `f32` (not just this crate's actual FFI-exposed function signatures, none of which pass a float — `Sample`'s own field is enough to trigger it internally). Confirmed producing a real, flashable `zephyr.hex` for the nRF54L15DK. **Narrower gap still open, not this one:** the FFI decode surface (`essd_study_decode_full`, `src/ffi.rs`) that hands a decoded `Study` back to C as a fixed-layout struct is scoped to `Action::BleAdvertise` steps only (dev-bench's own decision 21, same milestone) — extending it to `BleConnect`/`DataExchange` is real, separate future work once a study actually needs to dispatch those action kinds against real dev-bench hardware, not attempted yet.
- **A real stack-overflow risk in `Study`/`Step` deserialization, found 2026-08-18 while implementing `embarch-api`'s `run_study` — reproduced live 2026-08-19/20, and confirmed release-build-safe.** `Step`'s `Action` variants are large (`GattOperation::Write`'s 512-byte payload dominates `size_of::<Step>()`), and `Study.steps` is a fixed-capacity `heapless::Vec<Step, MAX_STEPS_PER_STUDY=64>` — a 64-slot inline array regardless of how many steps are actually populated. Originally only reproduced under `libtest`'s own stack; **now reproduced for real in production code**, running `embarch-api/milestone-8.md` §3.8's MCP-path repeat: a debug (`cargo build`, no `--release`) `embarch-api` genuinely crashed (`thread 'tokio-rt-worker' has overflowed its stack, fatal runtime error: stack overflow, aborting`) serving a live `study_status` call over MCP, for a real, tiny 2-step self-test `Study` — not a large or adversarial one. The identical sequence (`run_study` then `study_status`, same real Core, same real ESP32-C5) against a `--release` build of the exact same commit completed cleanly, both steps `Pass`, no crash — release's larger effective stack margin (smaller per-frame stack usage from optimization, not a larger stack size) is enough headroom for this specific case, but that's a property of today's code size and optimization level, not a guarantee. Still not sized, measured, or fixed at the root — options remain shrinking `MAX_STEPS_PER_STUDY`, boxing/pointer-indirecting the largest `Action` variants (would need `alloc`, ruled out by decision 5), or having callers that parse untrusted `Study` JSON do so on a deliberately larger stack. Narrowed by this finding: the practical exposure today is debug builds specifically (`embarch-api/design.md` §5's changelog), not every build — but nothing here should be read as "safe in release," only as "not yet observed to fail in release."
- **`Sample.value`'s real-world shape, narrowed but not closed** (§4.7, §5.2) — the CSV row *shape* (`rx_utc_ms,step_name,value,unit,channel_id,core_rx_utc_ms`, §3 decisions 27/30) is now locked, and `unit`/`channel_id` name what a value means and which stream it belongs to — but whether one `Sample` per real capture instant is still the right grain (vs. dev-bench needing to emit more than one `Sample` per instant for a genuinely multi-lead sensor) depends on dev-bench's eventual power-sampling and sensor hardware (previous bullet).
- **Dev-bench's UTC clock-resync accuracy** (§3 decision 12's `host_utc_ms` amendment, §4.7) — resync happens only on `Hello` (connection/reconnection), so `Sample.rx_utc_ms`'s drift between resyncs, and whether that's acceptable for post-hoc `SignalCheck` analysis (§4.6), isn't validated against real dev-bench hardware yet. §3 decision 30's `core_rx_utc_ms` gives post-hoc analysis the raw material to detect that drift after the fact, but doesn't correct it in real time or say how much drift is actually acceptable — that judgment still needs real hardware.
- **Core's host-side watchdog grace margin** (§3 decision 16's dev-bench-crash amendment) — the fixed margin added on top of a step's own `timeout_ms` before Core gives up on a hung/crashed dev-bench is a placeholder, not yet sized against real serial-link latency.
- ~~**Exact CRC crate/algorithm**~~ — resolved during implementation: the `crc` crate (CRC-32/ISO-HDLC), computed by streaming each `Step`'s postcard encoding through a `Digest` one at a time rather than buffering all of `steps` at once, so a constrained dev-bench MCU only needs stack space for one `Step`, not `MAX_STEPS_PER_STUDY` of them.
- **`SignalCheck`'s real variant set, and the DSP/statistics implementations' rigor, behind Core's `core-validation` feature** (§3 decision 19, §4.6) — the illustrative placeholder set (mean-in-range, glitch detection, frequency-domain) now has working evaluation logic (implemented and tested against synthetic signals), including a naive O(n²) DFT for `FftPeakNear` rather than a real FFT-crate dependency. Both the variant set itself and that DFT's adequacy remain provisional pending what dev-bench's eventual sensors/power hardware actually produce and how much data a real capture generates — swap in a proper FFT crate if profiling ever shows the naive approach doesn't scale.

    - **Core as pre-flight validator** (new §3 decision 18): `POST /study` now checks every `limits`-module capacity and every `Study.validations` `step_index` bound before generating a `study_id` or touching the serial link, rejecting with a `400` that names the offending field rather than a raw deserialize error — material since `--study-file` (§6) means a human is often hand-writing the JSON.
    - **Two-tier validation model** (new §3 decision 19, rewritten §3 decision 14, new §4.6, `Action::Validate` removed per new §3 decision 22): split "did the step's action mechanically succeed" (the existing device-observed `Outcome`, real-time, gates `continue_on_fail` per §3 decision 13, now with its scope made explicit) from "was the captured data actually correct" (a new, Core-only, post-hoc mechanism — `Study.validations`/`StudyResult.validations`, `PostHocValidation`/`ValidationSource`/`PostHocCheck`/`SignalCheck`/`ContentValidity`/`ValidationResult`). Runs only if/when a study reaches `"completed"` status; `SignalCheck`'s actual evaluation logic (signal/statistics functions for power and sensor-waveform data, beyond simple `ExpectedValue` equality/range checks) lives behind a new `core-validation` Cargo feature that only Core's build enables, keeping dev-bench/`embarch-api` free of `std`/`alloc`/floating-point/FFT dependencies they don't need.
    - **Dev-bench→Core streaming sub-protocol** (new §3 decision 20) and **sensor-waveform capture as a new `GattOperation::StreamCapture` variant** (new §3 decision 21, §4.3): replaces discrete end-of-window sampling for power/sensor data with `StreamStart`/`StreamChunk`/`StreamEnd` `DevBenchMessage` variants, channel-tagged to allow concurrent streams per step (`StreamChannel::Power`/`SensorWaveform`). Core now writes `data.csv`/new `waveform.csv` (§5.2, new `GET /study/{id}/waveform-data` endpoint, §5.1) incrementally as chunks arrive rather than buffering until the study ends, so raw capture data can survive even the catastrophic-failure crash scenario above.
    - New `limits` constants: `MAX_VALIDATIONS_PER_STUDY`, `MAX_STREAM_CHUNK_LEN` (§3 decision 15). New §7 open items: exact CRC crate, `SignalCheck`'s real variant set/DSP implementation, `MAX_STREAM_CHUNK_LEN`'s value, `waveform.csv`'s column schema — all placeholder-but-concrete in the same posture as the doc's existing hardware-blocked items. `milestone-3.md` updated to match.
- 2026-07-29 — Fifth design review pass, closing four gaps a pre-implementation review surfaced (none blocking, none requiring new hardware):
