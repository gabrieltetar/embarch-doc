## 1. Purpose and scope

`embarch-study-designer` is a shared Rust library that lets an EmbArch API user — human or agent, symmetrically (§6) — define and run **studies** of a DUT through a future `embarch-dev-bench` companion device. A study is a scripted sequence of stimulus/interaction steps plus measurement/validation, used for three overlapping purposes: fuzz testing, power profiling, and automated unit/integration testing during firmware development.

Unlike `embarch-api` or `embarch-core`, this is **not a service** — it's a data-types-and-tools library. It defines the shared vocabulary (a `Study`, its steps, the stimulus/sensing/validation shapes) *and* the narrow set of helper functions needed to work with that vocabulary identically everywhere (§3 decision 2) — e.g. CRC sealing (§3 decision 17) and canonical CSV-row rendering (§4.7, §5.2) — that every component along the full path a study crosses (`embarch-api` → `embarch-core` → `embarch-dev-bench` firmware → DUT, §2) compiles in directly, so neither the wire format nor the artifacts derived from it can drift into independently-maintained, slowly-diverging definitions.

`embarch-study-designer` is **not**:
- ~~A service or binary of its own — no `main.rs`, no HTTP surface, no MCP tools live in this crate itself.~~ **Reversed 2026-08-24 (decision 34), then re-reversed the same day the retirement landed (2026-08-24, ui milestone 1 §4.9):** the interim state held through decision 33's own `gatt-extract` CLI tool (an offline, one-shot binary, never a service) and, briefly, decision 34's own `study-designer-ui` binary (a genuine local HTTP surface, `main.rs` and all). That binary is now deleted — `embarch-ui`'s Study Designer tab covers the same authoring/build/run ground, calling this crate's `registry`/`merged_actions`/`study_builder` **in-process as a library**, not through a binary of its own. The original "not a service" stance holds again: this crate carries no `main.rs`/HTTP surface of its own, only `extract-gatt-config` (still a one-shot offline binary, unaffected) alongside the library code itself.
- A transport-layer implementation. It defines *what* gets sent (the types), not the socket/serial-port plumbing that sends it — that lives in each compiling component.
- Tied to one physical bench design. The type model is meant to outlive whatever `embarch-dev-bench`'s first physical revision turns out to be.

## 2. Architecture overview

```
                          embarch-study-designer (shared crate, #![no_std])
                          compiled in by all three:
                                    |
        +---------------------------+---------------------------+
        |                           |                           |
  embarch-api                 embarch-core                embarch-dev-bench
  (MCP + CLI,                 (bridges HTTP/JSON           firmware (C; BLE central/
   future §6)                  <-> serial/binary,           peripheral + power sampling;
                                future §5)                   links embarch-study-designer
                                                              via FFI staticlib, §3 decision 7)
        |                           |                           |
        +----- HTTP + JSON  ------->+----- Serial (UART/USB CDC, COBS-framed postcard) ----->+
                                                                                            |
                                                                                       DUT (BLE)
```

`embarch-api` and `embarch-core` already speak HTTP+JSON (`embarch-core/design.md` §4) — that hop is unchanged. The new hop this project introduces is `embarch-core` → `embarch-dev-bench`, over a serial link (§3), carrying the same logical `embarch-study-designer` types in a different wire format (§3). `embarch-dev-bench` is the component that actually talks BLE to the DUT and samples power — `embarch-core` never talks BLE or samples power itself, matching the suite's existing pattern of "hardware access stays in the layer closest to the hardware" (`embarch-core/design.md` §1).

That serial link now carries more than discrete `Study` submission and `StudyResult` reporting: a continuous streaming sub-protocol for power/sensor-waveform data captured during a step (§3 decision 20), and a CRC-sealed integrity check on `Study.steps` performed independently at both this hop and the API↔Core HTTP hop (§3 decision 17), on top of the schema-version handshake §3 decision 12 already establishes.

## 4. Concrete data model

Field-level, resolving milestone-3.md §3.1: concrete enough that a `#[derive(Serialize, Deserialize)]` Rust translation is mechanical — exact byte/UUID representations (`[u8; 16]` vs. a `uuid`-crate newtype, `no_std`-compatible either way) are implementation detail, not a design choice left open here. Every `Vec<T>`/`String` below is `heapless::Vec<T, N>`/`heapless::String<N>`, not `alloc`-based — §3 decision 15's `limits` module defines each `N`.

### 4.1 `Study`

- `name: heapless::String<{limits::MAX_STUDY_NAME_LEN}>` — human-readable identifier; not required to be unique (uniqueness, if ever needed, is an `embarch-api`-level concern per §6, not enforced by the type itself).
- `requires: Requirements { dev_bench_version, firmware_version }` (§3 decision 40) — the builds this study is meant to run against, both mandatory, `any` a legal explicit value. Host-side only; never sent to dev-bench, like `validations`. No `#[serde(default)]`, deliberately: an omitted `requires` fails to deserialize rather than defaulting to `any`, which is what makes "it has to be *said*" true rather than aspirational.
- `streams: heapless::Vec<StreamTap, {limits::MAX_STREAMS_PER_STUDY}>` (§3 decision 39, §4.8) — the study's declared capture channels. `#[serde(default)]`, unlike `requires`: a saved study (§3 decision 38) authored before taps existed captured nothing, and still does. **Does** cross the wire to dev-bench, unlike `validations`/`requires` — and, since §3 decision 39's 2026-08-25 amendment (implemented 2026-08-25, schema v9), is sealed by its own `streams_crc`, a sibling of `steps_crc` rather than a widening of it.
- `gatt: Option<DeclaredGatt>` (§3 decision 45) — the GATT table this study was authored against, and where it came from (`GattSource::Vendor`/`Extracted`/`Authored`). `#[serde(default)]` — a study authored before this existed declares nothing, which is what those studies did. Host-side only, like `validations`/`requires`: never sent to dev-bench. Reconciled by Core against a `GattDiscover`/`GattMonitorStart` step's live result, with the live table winning and the difference reported.
- `steps: heapless::Vec<Step, {limits::MAX_STEPS_PER_STUDY}>` — run in order. A `Study` is entirely static once submitted for v1: no parameter-range/generator construct (see the fuzzing note below).
- `steps_crc: u32` / `streams_crc: u32` (§3 decision 17, and decision 39's 2026-08-25 amendment) — two sibling integrity seals, each over the one contiguous span it names, each checked independently at both hops so a mismatch says **which half** is corrupt. Both are recomputed and overwritten by whoever submits (`embarch-api/design.md` §3 decision 26), so neither stored value is ever trusted. `streams_crc` is `#[serde(default)]` where `steps_crc` isn't: a saved study (§3 decision 38) authored before taps existed has no taps, and `0` is the genuine CRC of zero bytes rather than a sentinel — so the defaulted value is the *right* value, which is not something `requires`' own missing-field case could ever have said.

### 4.2 `Step`

- `name: heapless::String<{limits::MAX_NAME_LEN}>` — label surfaced in results (`StepResult.step_name`, §4.5), so a `Study` author and whoever reads results can correlate them without relying on array index.
- `action: Action` (§4.3) — the one thing this step does.
- `timeout_ms: u32` — max wall-clock time dev-bench allows this step before reporting `Outcome::TimedOut` rather than letting a stalled BLE connect/advertise hang the whole `Study`.
- ~~`power_sample: Option<PowerSampleWindow>` (§4.4)~~ — **retired by §3 decision 39's 2026-08-25 amendment; removed the same day** (Milestone 7 Phase B item 0, schema v9). It described an optional overlapping power measurement bounded by the step's own start/end; a `StreamSource::PowerFrontEnd { sample_hz }` tap scoped to that step range (§4.8) says the same thing, and was already the only one of the two anything read. See §4.4.
- `delay_before_ms: u32` — how long dev-bench waits *before* starting this step's action (§3 decision 40). `#[serde(default)]`, so a `Step` authored before it existed loads as 0 — start immediately, which is exactly what those studies did. Not deducted from `timeout_ms`, which still bounds only the action itself.
- `continue_on_fail: bool` — when this step's `Outcome` (§4.5) is `Fail` or `TimedOut`: `false` (the default) aborts the `Study` immediately, running no further steps; `true` continues to the next step regardless. Defaults to `false` since most steps in the automated-testing use case (§1) are prerequisites for what follows — a failed `BleConnect` makes every later `DataExchange` step moot. An author sets it `true` only on a step where continuing past that step's own failure is actually useful (e.g. a `DataExchange` step in a fuzzing run whose response content doesn't itself gate the rest of the sequence, or a purely diagnostic step). Governs only the device-observed `Outcome`, not the separate Core-side post-hoc content-validity check, which dev-bench can't act on in real time regardless of this flag. §3 decision 13.

### 4.3 `Action`

Three variants, matching §1's motivating categories (stimulus/interaction plus measurement — content validation is now handled entirely post-hoc by Core, §3 decision 19, not as a fourth on-device `Action`):

- **`BleAdvertise { local_name: Option<heapless::String<{limits::MAX_LOCAL_NAME_LEN}>>, service_uuids: heapless::Vec<Uuid, {limits::MAX_SERVICE_UUIDS}>, adv_interval_ms: u16 }`** — dev-bench advertises as a BLE peripheral for the DUT to discover.
- **`BleConnect { role: BleRole, target_address: Option<BleAddress>, target_name: Option<heapless::String<{limits::MAX_LOCAL_NAME_LEN}>> }`** — `target_name` (§3 decision 41) connects only to an advertiser whose advertised Local Name equals it exactly; `None`/blank means no name filter. Set alongside `target_address` and both must match. **`target_address: None` *and* `target_name: None` together mean "whichever connectable peripheral advertises first", which on any bench with another BLE device in range is a coin toss** — decision 41 has the live evidence. `BleRole` is `Central` or `Peripheral` (which side dev-bench plays for this step); `target_address` is `None` for "accept/connect to whichever DUT shows up first" (the common case — a `Study` author usually doesn't hardcode the DUT's BLE address) or `Some(addr)` to require a specific one. **`BleAddress`'s 6 raw bytes are display order, most-significant byte first** (`AA:BB:CC:DD:EE:FF`) — stated explicitly here as of 2026-08-15 (closing item 47 of that day's design-improvement review), matching `Uuid`'s already-documented big-endian convention and `embarch-dev-bench`'s `ble_bridge_real.c`, which has always assumed this order and reverses on the way into Zephyr's little-endian `bt_addr_le_t` (`embarch-dev-bench/design.md` §4). Previously this crate said only "6 raw address bytes" with no order specified — a real risk, since a wrong guess means a `BleConnect` with an explicit `target_address` silently never matches.
- **`DataExchange { service_uuid: Uuid, characteristic_uuid: Uuid, operation: GattOperation }`** — UUIDs are raw, not symbolic (per your call — no separate name-resolution table to maintain). `GattOperation` is `Read`, `Write { payload: heapless::Vec<u8, {limits::MAX_PAYLOAD_LEN}> }`, `Notify { timeout_ms: u32 }` (wait for a notification, bounded independently of the step's own `timeout_ms` since a notify-wait is often shorter than the step's overall budget), `Indicate { timeout_ms: u32 }` (same wait-for-a-pushed-value shape as `Notify`, but over BLE's acknowledged indication mechanism rather than best-effort notification — the ATT-level confirmation round-trip is the GATT stack's job, not something this type models), or `Subscribe` (enable notifications/indications without waiting for one, e.g. to arm a later step's `Notify`/`Indicate`). **`StreamCapture` was a sixth variant and is retired by §3 decision 39**: a continuous capture of what a characteristic streams is now a declared `StreamSource::GattNotify` tap (§4.8), not a per-step action kind. It was removed outright rather than kept as a dead trailing variant — the schema break is already paid for, and an authorable action nothing dispatches is the silently-captures-nothing failure decision 36 was opened by.
- **`GattDiscover {}`** (§3 decision 31, Milestone 3) — no fields: walks the connected DUT's entire GATT table (every primary service, every characteristic, each characteristic's raw ATT properties byte) rather than requiring a caller to already know a `service_uuid`/`characteristic_uuid` pair. Reports its result in `StepResult.gatt_services` (§4.3a, §4.5); doesn't subscribe or capture anything itself.
- **`GattMonitorStart {}`** (§3 decision 36) — no fields: runs the same discovery-and-subscribe-to-everything walk as `GattMonitorAll`, then returns immediately, **leaving every subscription armed so the capture window outlives this step**. Every step that runs afterwards — a `DataExchange` write stimulating the DUT above all — has its GATT traffic recorded into the streamed transcript (§4.3b) until a `GattMonitorStop` closes the window. This is the one action that makes "stimulate the DUT and capture what comes back" expressible at all: steps run strictly in sequence, and `GattMonitorAll` tears its own subscriptions down when its step ends, so a write step and a `GattMonitorAll` step can never overlap. Reports `gatt_services` in its own `StepResult`; `gatt_activity` is necessarily empty this early.
- **`GattMonitorStop {}`** (§3 decision 36) — no fields: closes the window a preceding `GattMonitorStart` opened, unsubscribing everything it armed and reporting the window's `gatt_services` plus its capped inline `gatt_activity`. A `GattMonitorStop` with no open window is a no-op `Pass`, not a `Fail`, and a study that ends without one has its window closed implicitly by dev-bench's own dispatch loop — so neither a forgotten `Stop` nor a mid-study abort can leave subscriptions armed into the next study.
- **`BleSecurity { level: BleSecurityLevel }`** (§3 decision 44, implemented 2026-08-26 at wire v12) — requests elevation of the current connection to at least `level` and waits for the link's security to actually change, or for the connection to drop, within this step's `timeout_ms`. `BleSecurityLevel` is `L1`/`L2`/`L3`/`L4`, one-to-one with Zephyr's `BT_SECURITY_L1..L4`. **`L1` is authorable and means "this DUT needs no security", said out loud** — the same distinction `REQUIREMENT_ANY` draws for `requires`, and not a value the builder refuses. A link already at or above `level` is a `Pass` — a peripheral that initiates its own elevation on connect can win the race, and this DUT does — and so is a procedure that was *already in flight* when the step started, which is the case real hardware actually produced ([embarch-dev-bench/design.md](../embarch-dev-bench/design.md) §3 decision 37). The **achieved** level is reported in `StepResult.security_level` (§4.5), so asking for L4 and getting L2 fails at the step that asked rather than at the discovery that follows; `Step.continue_on_fail` is how a study asks for the attempt without the abort. Carries no passkey, no IO capability, and nothing about bonding: those are dev-bench's (§3 decisions 11/34/37 there), not the study's.
- **`BleUnbond {}`** (§3 decision 50) — no fields: clears dev-bench's bonding table *inside* the study, so "pair, do work, drop the bond, pair again" is authorable. **Disconnects**, because Zephyr's `bt_unpair` disconnects a peer whose keys it clears — a study that unbonds mid-run needs its own `BleConnect` afterwards. Its own `StepResult.security_level` is `None`: by the time it returns there is no link to report a level for.
- **`GattMonitorSelected { targets }`** / **`GattMonitorSelectedStart { targets }`** (§3 decision 53) — the same discovery-and-subscribe walk as `GattMonitorAll`/`GattMonitorStart`, narrowed to the `GattTarget`s the study names. `targets` is `Bounded<GattTarget, {limits::MAX_MONITOR_TARGETS}>` and **may not be empty**: "monitor these" with nothing named is refused rather than promoted to "everything". A target that isn't on the DUT, or that can neither notify nor indicate, **fails the step naming it** — the unfiltered walk's log-and-skip rule is right only because nothing there was named. Closed by the same `GattMonitorStop`.

- **`GattMonitorAll {}`** (§3 decision 32, Milestone 3) — no fields: runs the same discovery as `GattDiscover` internally, subscribes to every characteristic whose properties include Notify or Indicate, and captures everything that arrives until the step's `timeout_ms` expires. Reports both `gatt_services` and `gatt_activity` (§4.3a, §4.5) — self-sufficient, doesn't depend on a preceding `GattDiscover` step's result.

A step's own `Outcome` (§4.5) is the only on-device validation signal — did the action (including a `DataExchange`'s `GattOperation`, or `GattDiscover`/`GattMonitorAll` themselves) complete without a protocol-level error or timeout. Whether the *content* it produced was actually correct is a separate question, answered later and only by Core (§3 decision 19, §4.6) — the original `Validate` `Action` that used to ask that question on-device has been removed (§3 decision 22).

### 4.3a GATT discovery types (§3 decisions 31/32/33)

- **`GattCharacteristicInfo { uuid: Uuid, properties: u8 }`** — `properties` is the raw ATT characteristic-properties byte (bit 0 = broadcast, 1 = read, 2 = write-without-response, 3 = write, 4 = notify, 5 = indicate, 6 = authenticated-signed-writes, 7 = extended-properties, per the Bluetooth Core Spec's own characteristic-declaration encoding) — passed through unchanged from what the ATT discovery response returned, not re-encoded into a crate-invented bitflag enum, matching this crate's existing "raw, not symbolic" stance on UUIDs (§4.3).
- **`GattServiceInfo { uuid: Uuid, characteristics: heapless::Vec<GattCharacteristicInfo, {limits::MAX_CHARS_PER_SERVICE}> }`** — one primary service and its characteristics, in discovery order.
- **`GattTarget { service_uuid: Uuid, characteristic_uuid: Uuid }`** (§3 decision 53) — one characteristic a study names explicitly. Both UUIDs, because subscribing needs the service to discover within, exactly as `DataExchange` always has; it is also the pair a `StreamSource::GattNotify` tap carries, so a characteristic named as a monitor target and one given its own decoded file are addressed identically.

- **`GattActivityRecord` was here and is retired** by §3 decision 54, along with `StepResult.gatt_activity` and `limits::MAX_GATT_ACTIVITY_RECORDS`. What a monitor step captured is read out of the study's `streams/` files, which hold all of it rather than its first 32 records.
- Both a live `GattDiscover`/`GattMonitorAll` result and a static extraction (§3 decision 33) produce `heapless::Vec<GattServiceInfo, {limits::MAX_DISCOVERED_SERVICES}>` — the same shape, so the two are directly comparable rather than needing separate diffing logic.
- **`ExtractedGatt { services, symbols: Vec<GattSymbol>, scan: ScanReport }`** and **`GattSymbol { uuid, identifier, kind: GattSymbolKind }`** (§3 decisions 56/57) — what `GattConfigExtractor::extract_labeled` returns: the table above, plus the C identifier each **service and** characteristic was declared under, plus the walk's own account of itself. Host-only and uncapped (a plain `Vec`, unlike the `heapless` table beside it): names never cross the wire, so there is no buffer on the far end for them to fit. One `symbols` list rather than two — a name lookup is keyed by UUID and a service UUID never collides with a characteristic's — with `ExtractedGatt::characteristic_symbols()`/`service_symbols()` as the filtered views `GattNameBook` takes. `extract` is a provided method returning `services` alone, so a caller with no use for names — and every caller written before decision 56 — is unaffected. `services` is in sorted-repo-relative-path-then-source order: **stable, and not a claim about ATT handle order** (§3 decision 57 — compare a static extraction and a live discovery as sets).
- **`ScanReport { root, files_read, sources: Vec<ScannedSource>, blocked_dirs, unreadable }`** and **`ScannedSource { path, uuid_macros, uuid_vars, services }`** (§3 decision 57) — what the walk read, which files actually contributed and what each contributed, what `SCAN_BLOCKED_DIR_NAMES` pruned, and what wasn't valid UTF-8. Counts rather than a second copy of the parsed values: this is the report an engineer reads to answer "did it open the file I expected", which a two-file read could never answer at all. `path` is repo-relative so the report compares between machines.
- **`GattName { label, source, origin }`** / **`GattNameBook`** (§3 decision 56, `src/gatt_names.rs`, `std`-only) — one characteristic's display name, resolved from the vendor table (`GattNameSource::Vendor`, winning where both apply) or from an extraction's symbols (`FirmwareSymbol`). `origin` is the untrimmed identifier or the vendor's full name; `label` is what a picker shows. `GattNameBook::get` returns `Option`, and `None` — nothing names this characteristic — is an ordinary answer, not an error. Since decision 56's 2026-08-26 amendment the same book also names **services**: `with_service_symbols`/`service()` against a second map, `vendor::find_service_by_uuid` for the vendor half, and `label_from_service_symbol` trimming `_uuid` while keeping `_service`. Two maps because a service UUID resolves against the vendor table's services — one map would have to guess which lookup a UUID wanted.

### 4.3b GATT transcript types (§3 decision 36)

The **exhaustive**, streamed record — as opposed to §4.3a's `GattActivityRecord`, which is the capped, per-step, inbound-only summary that lives inline in `events.json`. Both survive deliberately; see decision 36 for why, and for why a reader comparing their counts will correctly see different numbers.

- **`GattDirection`** — `Out` (dev-bench → DUT), `In` (DUT → dev-bench), or `Local` (a dev-bench-side event that isn't an ATT PDU in either direction — discovery starting, a subscription being armed).
- **`GattEventKind`** — `Connected`, `Disconnected`, `DiscoveryStarted`, `ServiceDiscovered`, `CharacteristicDiscovered`, `Subscribed`, `Unsubscribed`, `WriteRequest`, `WriteResponse`, `ReadRequest`, `ReadResponse`, `Notification`, `Indication`, `Error`. Append-only, same discipline as `DevBenchMessage` (§3 decision 10).
- **`GattTranscriptEntry { rx_utc_ms: u64, direction: GattDirection, kind: GattEventKind, service_uuid: Option<Uuid>, characteristic_uuid: Option<Uuid>, att_status: u8, payload: heapless::Vec<u8, {limits::MAX_PAYLOAD_LEN}> }`** — one line of the transcript. UUIDs are carried in full rather than as a `characteristic_index` into a step's `gatt_services` (the compression `GattActivityRecord` uses), because a transcript spans steps — including steps that ran no discovery at all — so there is no single flattened table an index could mean anything against. `att_status` is the raw ATT error code, `0` when there was none; for a `CharacteristicDiscovered` entry it carries the raw ATT properties byte instead, documented here rather than adding a field used by one event kind. `rx_utc_ms` is dev-bench's own capture-time clock, inheriting the same unresolved clock-resync gap §7 already tracks for `Sample.rx_utc_ms` — Core's own `core_rx_utc_ms` column (§5.2) is the wall-clock anchor until that closes.
- **`GattTranscriptEntry::csv_header()`/`to_csv_row(step_index, step_name)`** — this crate's own transcript-CSV renderer (§5.2), so column knowledge lives here and nowhere else, same split `Sample::to_csv_row` established. The payload appears **twice by design**: `payload_hex` is the exact bytes, and `payload_ascii` renders printable bytes as themselves and everything else as `.`, so a shell/NUS transcript is directly readable without decoding hex by hand while nothing is lost for a binary protocol. Returns `None` — dropped and logged, never truncated — if a row wouldn't fit `MAX_GATT_CSV_ROW_LEN`, or if a step name contains a character that would break the CSV shape.

### 4.3c Table-authoring types (§3 decisions 34/37)

Authoring-side only (`study-ui` feature, `std`), never on the wire: `TableRow { name, action: RowAction, timeout_ms, continue_on_fail }`, where `RowAction` is `BuiltIn { which: BuiltInActionKind, role }`, `Registered { name, field_choices }`, or — added by decision 37 — **`Raw { service_uuid: String, characteristic_uuid: String, operation: RegisteredOperation, payload: Vec<u8> }`**, a one-off `DataExchange` against a UUID pair typed directly with a payload supplied as literal bytes. `build_study` resolves all three into real `Action`s; `Uuid::parse` (decision 37) accepts the hyphenated form, 32 bare hex digits, or a 16-bit shorthand expanded against the Bluetooth SIG Base UUID.

### 4.4 `PowerSampleWindow` — retired

**Retired by §3 decision 39's 2026-08-25 amendment; removed 2026-08-25** (Milestone 7 Phase B item 0, schema v9). It carried one field, `sample_rate_hz: u32`, naming dev-bench's power-sampling rate for a step-bounded window. A `StreamSource::PowerFrontEnd { sample_hz }` tap with a `StreamScope::Steps { from, to }` covering the same step (§4.8) expresses exactly that, and is the only one of the two anything ever read.

**Retired on evidence, not on symmetry.** Nothing consumed this field: `embarch-core` takes a power capture's rate from the tap; dev-bench's C encoder wrote its `Option` byte as `None` unconditionally and its decoder read-and-discarded it; `study_builder::build_study` always emitted `None`. Removal was one field off `Step` in the same bump as `streams_crc`, priced while Milestone 6's firmware was still unflashed — re-verified before the work rather than assumed. Milestone 4 (which has never run) is the first study that would author a power capture, and finds one way to do it rather than two.

### 4.5 `StudyResult` / `StepResult`

- **`StudyResult.provenance: Provenance { dev_bench_version, firmware_version, dev_bench_source, firmware_source, overrides }`** (§3 decision 40) — what the study actually ran against, **how each version was established**, and **which requirements, if any, it was allowed past rather than satisfying**. The source is `ReportedByDevBench` / `ReportedByOutpost` / `FlashedThisRun` / `Declared`, and it is not bookkeeping — a `Declared` DUT version is an assertion nobody checked, and a result that rendered it identically to a verified one would reintroduce exactly the mislabelling this decision exists to close. **Written by Core since 2026-08-25.** The bench is always `ReportedByDevBench`: Core reads it off the live `HelloAck`. `ReportedByOutpost` still waits on outpost firmware existing.

  **`FlashedThisRun` became reachable 2026-08-25 (Milestone 7 Phase B item 2), and not by Core learning to do anything new.** It remains structurally impossible for Core to produce on its own — `POST /flash` and `POST /study` are separate calls with nothing linking them, by design — so the process that sequenced both is the one that says so: `embarch-api` passes `?flashed_firmware_version=<string>` on `POST /study`, out of band of the `Study` body because §3 decision 40 settles that reflash is a run parameter and not a study field. Absent it, the DUT's version stays `Declared` and is compared against nothing, exactly as before. Present, it is *also* what makes `requires.firmware_version` checkable for the first time — the DUT half of Core's gate has no other way to fire.

  **The string it carries describes the tree that was built, not the image that is running**, and that limit is stated rather than papered over: `embarch-api` derives it by running a project-declared `version_command` (defaulting to the suite's own `git describe --always --dirty --abbrev=8`) in the project's checkout, and nothing in this suite can read a version back off a DUT to confirm the build embedded it. `FlashedThisRun` therefore means "this run put the build of this tree on the board" — strictly stronger than `Declared`, which nobody checked at all, and strictly weaker than `ReportedByDevBench`, which is a measurement.

- **`Provenance.overrides: heapless::Vec<VersionOverride, {limits::MAX_VERSION_OVERRIDES}>`** (§3 decision 40, added 2026-08-25 at host schema v10) — one entry per version requirement this run was allowed to proceed past, empty in the normal case. `VersionOverride { subject: VersionSubject, required, actual }`, where `VersionSubject` is `DevBench` or `Firmware` — the two fields `Requirements` has, so the capacity is the arity of the thing rather than a capacity guess.

  **A record, not a flag, because neither string is recoverable from the rest of a `StudyResult`.** `Study.requires` never travels into the result, and the *actual* version is only in the sibling field when the override is the reason that field is there at all. A bare `overridden: bool` would say a rule was bent without saying which one or by how far — the same half-answer `VersionSource::Declared` exists to stop this type giving. `#[serde(default)]`, so an `events.json` written before the field existed still reads back, truthfully, as not overridden: those runs predate any way to override anything.


- **`StudyResult { study_name, steps, validations, provenance, streams }`** — `streams: heapless::Vec<StreamRef, {limits::MAX_STREAMS_PER_STUDY}>` (§3 decision 39, §4.8) is one entry per declared tap: its name, the bytes written, and whether it was truncated. `provenance` is the §4.5 entry above. — the aggregate outcome, same shape whether read by `embarch-core`, `embarch-api`, or a human reading the result file directly (§5.2). `steps` is not guaranteed to be the same length as the submitted `Study.steps`: if some step's `continue_on_fail` is `false` (the default, §4.2) and that step's `Outcome` is `Fail`/`TimedOut`, execution aborts and `steps` is a proper prefix ending at that step, rather than always covering every submitted step. `validations` (§3 decision 19, §4.6) is populated only once the study reaches `"completed"` status — it stays empty on any `"failed"` outcome, even for steps that did capture data before the abort.
- **`StepResult { step_name: heapless::String<{limits::MAX_NAME_LEN}>, outcome: Outcome, captured_data: Option<heapless::Vec<u8, {limits::MAX_PAYLOAD_LEN}>>, gatt_services: Option<Bounded<GattServiceInfo, {limits::MAX_DISCOVERED_SERVICES}>>, security_level: Option<BleSecurityLevel> }`** — `Outcome` is `Pass`, `Fail { reason: heapless::String<{limits::MAX_FAIL_REASON_LEN}> }`, or `TimedOut`. `step_name` is a denormalized copy of the corresponding `Step.name`, carried purely for human readability when reading `events.json` directly (§5.2) — it is not used for machine correlation (§3 decision 14 uses `Study.steps` array position for that, via `ValidationSource.step_index`, and `StudyResult.steps`' own position tracks the same index since steps run and are appended in order). `captured_data` holds whatever bytes a `DataExchange` read/notify step pulled off the DUT (unused for other action kinds). **`power_samples_ref` and `waveform_ref` were here and are retired by §3 decision 39**: a capture belongs to the study's declared taps, not to one step, so what a run captured is reported once as `StudyResult.streams` — which is the thing neither per-step field could ever have filled in correctly for a tap whose scope outlives a single step. `gatt_services` (§3 decisions 31/32, §4.3a) is populated by every discovering action — `GattDiscover`, both monitor pairs — landing inline in `events.json` like `captured_data` rather than as a CSV-file reference, since it is bounded and small enough to stay JSON-friendly. **`gatt_activity` was here and is retired by §3 decision 54**: it was a 32-record cap on something unbounded and streamed, and a study holding 32 of several thousand records looked exactly like one that had captured everything. What a monitor step captured is a file under `streams/` now, uncapped. `security_level` (§3 decision 44, added 2026-08-26 at wire v12) is the BLE security level the link was sitting at when the step finished — **populated for every step, not only a `BleSecurity` one**, which is a deliberately larger claim than decision 44 made and the one that pays for itself: a `"disconnected during service discovery"` at L1 and the same failure at L4 are different findings, and nothing in a result could distinguish them before this existed. `None` means there was no connection to ask about, never that nobody looked; `#[serde(default)]`, so a `StudyResult` written before the field existed reads back truthfully as having recorded no level.

**Fuzzing, explicitly not modeled here (resolved):** §1's fuzz-testing use case is served by treating a `Study` as the *output* of fuzzing, not by adding a parameter-range/generator type to these types themselves — "generate many concrete `Study` values externally (with varied `Step` parameters), submit each one" is a caller-side (`embarch-api`, or a human/agent driving it) concern. This keeps `Study`/`Step` themselves simple and keeps the fuzzing strategy free to evolve independently of the wire types.

### 4.6 Post-hoc validation types — retired

**Retired and removed 2026-08-25** (§3 decision 48, host schema v11). `Study.validations`, `StudyResult.validations`, `PostHocValidation`, `ValidationSource`, `DataChannel`, `PostHocCheck`, `ExpectedValue`, `SignalCheck`, `ContentValidity` and `ValidationResult` are all gone, along with `signal.rs`'s evaluation logic and the `core-validation` Cargo feature. See decision 48 for the reasoning and for what the removal actually cost.

**The measurement that made this section worth removing rather than fixing:** `PostHocValidation` was 576 bytes (two `MAX_PAYLOAD_LEN` byte buffers inside `ExpectedValue`), and `MAX_VALIDATIONS_PER_STUDY` was 64, so `Study.validations` alone was a **36,872-byte inline array** — 97% of `Study` even after §3 decision 46 fixed `steps`. `Study` is now **1,088 bytes**, down from 77,368 before this pass began.

### 4.7 `Sample` (streamed power/waveform data, §3 decisions 2/11/20)

- **`Sample { rx_utc_ms: u64, value: f32, unit: Unit, channel_id: u8 }`** — **no longer a wire type as of §3 decision 39.** The wire carries arrival-stamped bytes (`StreamRecord`, §4.8); a `Sample` is what `streams::samples_in` produces from those bytes against a tap's declared `StreamEncoding::Samples { layout, unit, channel_id }`. Every `Samples`-encoded tap's rendered CSV (§5.2) shares this identical row shape rather than each inventing its own columns, and **that row shape is untouched by the reshape** — only the path the numbers take to reach it changed. (It was `data.csv` and `waveform.csv`, two fixed files chosen per channel; since 2026-08-25 it is `streams/<tap name>.csv`, one per declared tap — `embarch-core/design.md` §3 decision 30(b).) `rx_utc_ms` is stamped by dev-bench itself, at the moment it captures/receives the sample from its own sampling hardware — its own local clock, seeded and periodically resynced from Core's `host_utc_ms` on every `Hello` (§3 decision 12) — not assigned by Core on arrival, so the timestamp reflects when the sample was actually taken rather than when it happened to reach Core over a variable-latency serial link. `unit`/`channel_id` (§3 decision 27) name what `value` actually measures and, for a capture with more than one concurrent stream, which one — both are placeholder-but-concrete pending real dev-bench sampling hardware (§7); appending further fields later is a version-bumped wire change like any other (§3 decision 12). `unit`/`channel_id` are declared once per tap now, on `StreamEncoding::Samples`, rather than repeated per wire message — the same "neither changes mid-capture" reasoning the retired per-batch fields used, moved to where the rest of a capture's declared meaning already lives.
- **`Sample::to_csv_row(&self, step_name: &str) -> Option<heapless::String<{limits::MAX_CSV_ROW_LEN}>>`** and **`Sample::csv_header() -> &'static str`** — the crate's own CSV-rendering tools (§1, §3 decision 2). Core's job writing a `Samples` tap's rendered CSV reduces to: run each `StreamRecord` through `streams::samples_in` (which owns the element width/byte-order decode), call `to_csv_row` for each `Sample` with the name of whichever step is open, and append the returned row plus Core's own `core_rx_utc_ms` (§3 decision 30) — column knowledge lives only in this crate, never duplicated in Core. Row shape: `rx_utc_ms,step_name,value,unit,channel_id`, with `core_rx_utc_ms` appended by Core itself rather than by this helper (§3 decision 30 — it's Core's own receipt time, not part of the wire type). Returns `None` if `step_name` doesn't fit alongside the rest of the row within `MAX_CSV_ROW_LEN` — Core is expected to log and skip that one row rather than truncate it silently, since a truncated CSV row is a worse failure mode than a dropped one.

### 4.8 Stream taps (§3 decision 39)

**Implemented 2026-08-25** (`src/streams.rs`, Milestone 7 Phase A). Field-level below; anything the decision left open and implementation had to settle is marked as such.

- **`StreamTap { id: u8, name, source: StreamSource, encoding: StreamEncoding, scope: StreamScope }`** — `id` is the wire handle (its own index in `Study.streams`); `name` names the output file under `streams/`, the post-hoc validation source (literally, as of §3 decision 19's 2026-08-25 amendment — a stream-fed `ValidationSource` carries this name), and nothing else. `dev-bench` is a **reserved** name, rejected by `POST /study`'s pre-flight validation (§3 decision 18), since it belongs to the reserved `DevBenchLog` tap.
- **`StreamSource`** — `GattNotify { service_uuid, characteristic_uuid }`, `PowerFrontEnd { sample_hz }`, `GattTranscript`, `DevBenchLog`, `Signal { name }`. The first four are dev-bench-mediated (`StreamSource::is_dev_bench_mediated`); `Signal` is read by Core itself, with the carrier resolved live by [embarch-topology](../embarch-topology/design.md) §3 decision 18 — Core opens a local serial port for a `Route::Direct` signal, or receives relayed bytes for a `Route::ViaDevBench` one, and the tap is identical either way.
- **`StreamEncoding`** — `Raw`, `Text`, `Samples { layout, unit, channel_id }`, `GattTranscript`, `OutpostTrace`, `Struct { decoder }`. This is the **only** place a byte payload acquires a meaning, it is always engineer-declared, and no component ever guesses one — §3 decision 35's rule, applied to the read direction.

### 4.8a Declared struct decoding (§3 decision 52)

`StreamEncoding::Struct { decoder: u8 }` indexes `Study.decoders`, a **host-only** `Bounded<StructLayout, {limits::MAX_DECODERS_PER_STUDY}>` that never crosses the dev-bench hop — the same posture as `Study.requires`, and for a stronger reason: what a payload means is exactly the knowledge §3 decision 39 took away from dev-bench. Only the index rides on the tap, because a tap's encoding *does* cross on `StudyStart` and dev-bench has to walk past it.

- **`ScalarType`** — `u8`/`i8` and the 16/32/64-bit integer and IEEE-754 float widths in both byte orders, 18 in all. **Width, signedness and byte order only** — no scale, no offset, no unit, the same line [`SampleLayout`] draws.
- **`StructField { name: heapless::String<{limits::MAX_STRUCT_FIELD_NAME_LEN}>, ty: ScalarType }`** — one named scalar. Fields are packed in declaration order with no padding; a layout needing padding declares a field for it rather than having an alignment rule guessed on the DUT compiler's behalf.
- **`StructLayout { name, header, repeat }`** — `header` is read once at offset 0; `repeat`, when non-empty, is read as many times as fits in what remains, producing **one row per repetition** with the header's values denormalized onto each.

Authored in the firmware repo's `embarch/study-structs.toml` (`StructRegistry`, sibling to `study-actions.toml`) and resolved into `Study.decoders` at build time, so the submitted study is self-contained — Core cannot read that repo.

**Row shape**, rendered by Core (§5.2): `rx_utc_ms,step_index,step_name,rep_index,<header fields…>,<repeat fields…>,payload_hex,decode_note,core_rx_utc_ms`. The last two are always present, not only on a failed row, so a reader can tell a payload that fitted the layout from one that didn't without the columns shifting mid-file.

**A payload that doesn't fit still gets a row**, with the decoded columns empty and `payload_hex`/`decode_note` filled. The raw `.bin` is written before any decode is attempted, so a wrong layout costs a rendering rather than a capture. An **empty repetition list is zero rows and no error** — a DUT sending a header with nothing after it is real, and a row invented for it would be invented data. `DecodeError`'s rendered text carries no comma and no quote, asserted in its own tests, because this crate refuses to produce a CSV value that would break the column shape rather than quoting it (`csv_escape_ok`'s rule).
- **`SampleLayout`** (settled during implementation; the decision named `layout` without defining it) — `F32Le`/`F32Be`/`I16Le`/`I16Be`/`U16Le`/`U16Be`. **Element width, type, and byte order only: no scaling, no offset, no unit conversion.** Those would be a claim about what a particular DUT's bytes *mean*, which is its engineers' knowledge and not this crate's; `unit` names the quantity, nothing here transforms the number. Append-only.
- **`StreamScope`** — `WholeStudy` or `Steps { from, to }`, both indices **inclusive** (a single-step window is `from == to`). The outpost uses `WholeStudy`; a power window uses the step range it belongs to. `StreamScope::covers(step_index)` is the crate-side predicate.
- **Wire records: `StreamOpen { id }`, `StreamChunkBatch { id, records }`, `StreamClose { id, dropped }`**, where a record is `StreamRecord { rx_utc_ms: u64, bytes }` — arrival-stamped bytes, never decoded values. `dropped` is carried on close, so a stream that lost data says so rather than presenting a shorter, plausible capture as complete. Neither open nor close carries a `step_index`: when a tap opens is a property of its declared `scope`, not of the wire.

  **That guarantee is only as good as the close, and for `WholeStudy` taps there wasn't one until 2026-08-27.** dev-bench ended a run by syncing scopes against one step past the last, which closes a `Steps` window and leaves every `WholeStudy` tap open — `StreamScope::covers` returns `true` for `WholeStudy` at every index, correctly. No close meant no `StreamClose`, meant no `dropped`, meant `StreamRef.truncated: false` however much had been lost. Nothing in this crate was wrong; the sentence above was simply unreachable for one of the two scopes it applies to. Fixed in firmware ([embarch-dev-bench/design.md](../embarch-dev-bench/design.md) §3 decision 42, [embarch-decision-reversals.md](../embarch-decision-reversals.md) row 98). Worth keeping here because it is this type's contract that was quietly not being met, and a reader of `truncated` has no way to tell a scope-dependent hole from a clean capture.
- **`StudyStart` carries the study's `streams`** (settled during implementation, appended after `steps_crc` — see §3 decision 39's implementation note for why), **followed by `streams_crc`**. The seal gap that appending left is closed by a second CRC rather than a widened one (§3 decision 39's 2026-08-25 amendment, implemented 2026-08-25 at schema v9): a sibling `streams_crc` over `streams`, carried after it so each seal immediately follows the one contiguous span it covers, checked independently at both hops. `steps_crc`'s own definition did not move. dev-bench walks the taps to locate that span (`pc_skip_stream_tap`) without storing them — opening them for real is Phase B item 3 — and aborts the study on a mismatch, naming which seal failed.
- **`StudyResult.streams: heapless::Vec<StreamRef, ..>`** — per tap: `StreamRef { name, bytes_written, truncated }`. Replaces `StepResult`'s `power_samples_ref`/`waveform_ref`. **Actually written by Core since 2026-08-25** (`embarch-core/design.md` §3 decision 30's implementation note), with three things settled there rather than here: an entry exists for **every** declared tap, including one that produced nothing (`bytes_written: 0`) — a missing entry and an empty one are different facts; `bytes_written` counts every raw byte the run wrote, including bytes a retention rotation later deleted, with `truncated` saying the file no longer holds all of them; and `truncated` covers both losses a reader cares about equally — a rotation that dropped a segment, and a `StreamClose` reporting a non-zero `dropped`.

  **`StreamRef` deliberately did *not* grow a `note` field on 2026-08-26, and the reasoning is worth keeping.** Milestone 7 Phase D needed to distinguish an outpost trace that had a manifest applied from one that did not, and this type was the obvious place to put the reason — it is already per-tap and already in the result. It was rejected: `StreamRef` rides inside `StudyResult`, which crosses the dev-bench wire, so growing it is a **host schema bump** for a fact that is produced by Core *after* dev-bench has finished and is meaningless to it. Core exposes its own `streams/index.json` over a new route instead ([embarch-core/design.md](../embarch-core/design.md) §3 decision 30(c)'s amendment). `truncated` stays the one thing this type says about incompleteness, and it says it about the *capture*, which is dev-bench's business.
- **`dev_bench_log_tap(&declared)`** (added 2026-08-25, Milestone 7 Phase B item 3) — builds the reserved `DevBenchLog` tap, the one tap a `Study` may not author. **Its `id` is `declared.len()`**, which is free by construction: a declared tap's `id` is its own index, so the first index past the end can never collide with one — and that single rule is what lets both ends agree on the handle without either sending it. Encoding `Text`, scope `WholeStudy`. **Where its bytes come from changed in implementation, and the change is recorded rather than absorbed:** this section originally had *dev-bench* opening the tap and sending `StreamOpen`/`StreamChunkBatch`/`StreamClose` for its own log. What shipped is Core synthesizing the tap and rendering into it the `LogLine` frames it already receives — strictly less firmware, less link traffic and less SRAM on a board at 98.5% of `sram0_0_seg`, to move bytes that were crossing the link anyway. The asymmetry the tap exists to close is closed either way. See [embarch-decision-reversals.md](../embarch-decision-reversals.md) row 36.
- **`validate_taps(&streams, step_count)`** — `POST /study`'s pre-flight rules, computed here rather than in Core so there is no second copy to drift: `id` must equal its own index; no blank, reserved, or duplicated name; no step range that is inverted or out of bounds. That last one exists because both failures produce a capture that is **silently empty**, which is the failure decisions 34 and 36 were each opened by.
- **`samples_in(record, layout, unit, channel_id, sample_hz)`** — the crate-side decode for a `Samples` tap, so Core holds no column or layout knowledge of its own. With a declared rate (a `PowerFrontEnd` tap has one), element *i* is stamped `rx_utc_ms + i * 1000 / sample_hz`; **with no declared rate, every sample carries the record's own arrival stamp unchanged**, rather than an interpolation nobody stated the basis for. A trailing partial element is dropped, never zero-padded into a plausible wrong value.

**What a `GattTranscript`-encoded record actually contains** (settled during implementation): one postcard-encoded `GattTranscriptEntry` (§4.3b), unchanged. The entry keeps its own `rx_utc_ms` alongside the record's — the same value from the same clock — rather than having it removed, so the row shape decision 36 pinned stays byte-for-byte what it was. The `step_index` column comes from whichever step the host has open when the record arrives, which is exactly what decision 36 defined that field to mean; the generic record carries no step of its own.

### 4.9 Protocol manifests (§3 decisions 58–62)

`Study.protocols: Bounded<ProtocolDef, {limits::MAX_PROTOCOLS_PER_STUDY}>`, resolved out of the firmware repo's `embarch/protocols/*.eap` at build time and sealed by `protocols_crc` — the study's **third** seal, because unlike `Study.decoders` this is a value dev-bench *executes* rather than one the host renders with. `Action::RunProtocol { protocol: u8, entry_state: u8 }` indexes it; both are indices, not names, so no firmware compares strings and every cross-reference is range-checked once, host-side, by `validate_protocol`.

**Where each half lives.** The `no_std` wire types are `eap.rs` and cross to dev-bench on `DevBenchMessage::StudyStart`, whose last two fields are `protocols` and `protocols_crc` (appended there 2026-08-26 — decision 58's amendment). The parser and a host-side **reference** interpreter are `eap_parse.rs`/`eap_interp.rs`, behind an `eap-parse` feature that implies `std` — the same posture `gatt-extract` has (§3 decision 33), so dev-bench firmware carries the definitions and no parser at all. **The real-time interpreter is `embarch-dev-bench`'s own scope**, exactly as §3 decisions 31/32 shipped `GattDiscover`/`GattMonitorAll`'s wire types here and left live BLE dispatch there — and as of 2026-08-26 it exists (`eap_interp.c`, that doc's §3 decision 41), pinned against this module by a literal `StudyStart` frame carrying the worked BDS protocol plus eight semantics cases mirroring the ones below. What the host-side one is for: pinning the semantics the C must match, proving the primitive set against the worked protocols below, and replaying a capture offline.

#### Types

- **`ProtocolDef { name, sources, frames, session, states }`** — one `protocol { … }` block. Self-contained: it declares its own characteristic aliases (`ProtocolSource { name, service_uuid, characteristic_uuid }`) rather than referencing the study's taps, so one protocol is portable across studies wired up differently.
- **`FrameDef { name, source, select_if, fields, spans }`** — a frame shape the machine can dispatch on. `fields` are the **guard-reachable** integer reads only (§3 decision 59's split), not the whole packet; `spans` are byte runs whose *length* an expression can reach and whose contents it cannot. Two frames may share a source and the first matching `select_if` wins; an unguarded frame must be the last declared for its source, so it cannot shadow a more specific sibling into unreachability.
- **`FrameMatch { offset, eq }`** — `select_if`. `len` is not stored: it is `eq.len()` by construction, and carrying both would admit a manifest where they disagree. A payload too short to contain the match **does not match** — a truncated notification and a different format are different facts.
- **`ScalarRead { name, offset, ty }`** reuses §3 decision 52's own `ScalarType`, so a frame lowered into a `StructLayout` for rendering reads its bytes through the identical code path a guard does. Float widths are refused where they are declared, not at runtime, because the expression set is integer-only.
- **`SessionVarDef { name, initial }`** — integers only (§3 decision 60).
- **`StateDef { name, kind }`**, `StateKind::{Active, Terminal}`. An `ActiveState` has an optional `on_enter` write, a list of `on_event` arms, and an optional `on_timeout`. `TerminalOutcome::{Pass, Fail}` is what a manifest can *declare*; `Outcome` is what a run *reports*, and `Outcome::TimedOut` is reachable only by running out of time — no manifest can name it.
- **`Operand::{Literal, Field, Session, SpanLen}`**, **`Expr::{Term, Add}`**, **`Condition { lhs, op, rhs }`** — the whole expression set, enumerated in §3 decision 60 along with what is deliberately absent.
- **`ProtocolOutcome { final_state, outcome }`** on `StepResult`, appended last so the wire change is a pure suffix dev-bench's C decoder adopts by reading one more `Option` rather than re-walking the message.

#### Grammar

The full EBNF lives in `eap_parse.rs`'s module docs, next to the parser that implements it, so the two cannot drift. In outline:

```text
protocol   = "protocol" ident "{" { source | frame | struct | session | state } "}" ;
source     = "source" ident "=" "characteristic" "(" "service" ":" string "," "char" ":" string ")" ;
frame      = "frame" ident "on" ident [ select_if ] "{" { field } "}" ;
field      = scalar | span | repeat | bitpack | crc ;
state      = "state" ident ( "outcome" ":" ("pass"|"fail") | "{" { clause } "}" ) ;
clause     = "on_enter" ":" write
           | "on_event" ident ":" { remember } { when } [ otherwise ]
           | "on_timeout" int ["ms"] [ "retry" int ] ":" "goto" ident ;
operand    = int | "session" "." ident | ident "." ident | "len" "(" ident "." ident ")" ;
```

Whitespace and `#` comments are insignificant; a 16-/32-bit UUID shorthand expands through the Bluetooth Base UUID via `Uuid::parse`, so a manifest names a characteristic the way its firmware's own header does. Offsets accumulate in declaration order with no padding when `@` is omitted — and a field following a variable-length one **must** state its offset rather than have one guessed on its behalf. Every error carries its source line.

#### The two worked protocols are tests, not illustrations

`tests/fixtures/*.eap` and `tests/eap_worked_protocols.rs`. They were chosen because they are structurally representative of a real DUT's BLE stack, so they exist to **prove the primitive set is sufficient** rather than to show what it looks like. If the grammar ever stops expressing one of them, that is a real finding about the primitive set and those tests are where it surfaces. **`bds_batch_download` is now also dev-bench's own fixture**: its resolved bytes are the literal frame that firmware's ztest suite decodes and its sequences are what that firmware's C interpreter is driven through, so the two interpreters are exercised against one protocol rather than each against its own.

- **`bds_batch_download.eap`** — request → chunked pump loop with flow control → consume, shaped like the Batch Data Service §3 decision 57 found. Driven through the reference interpreter over a real 700-byte/200-byte-chunk sequence to `Pass`; separately stalled to prove the watchdog reaches `aborting` and then `failed`, and timed out three times to prove `retry` **re-sends the `on_enter` write** rather than waiting longer. Also pins that an unrelated notification is ignored rather than failing the run, and that a truncated frame does not advance the machine.
**What the first real manifest changed about the worked ones (2026-08-27).** `bds_batch_download.eap` was chosen as structurally representative of a real DUT's BLE stack, and it is — but the real `bds_ppg_drain.eap` written against the same firmware differs from it in one load-bearing way, and the difference is a finding about the primitive set's *use*, not its sufficiency. The fixture's pump loop counts received bytes (`remember received = received + len(chunk.payload)`) and leaves the state on `received >= expect_total`. Against a firmware that bursts several notifications per control write into dev-bench's four-slot notification queue, a single dropped chunk makes that count short **forever**: the state stalls to its watchdog and aborts a transfer the device fully intended to finish. It happened three times in five minutes, each ending in the device's own `BDS_ERR_TIMEOUT`.

The real firmware publishes what the count was reconstructing — `bds.c`'s "offset == total is the transfer-complete sentinel" — on the low-rate status characteristic, and reading completion off the device rather than inferring it took the same study from 0 completed transfers to 34 of 34. The primitive set expressed both versions fine; what the fixture could not tell anyone is *which* to write. So: **a manifest should branch on a state the DUT reports, not on a quantity the manifest accumulates, wherever the DUT reports one** — accumulation is only correct when no input can be lost, and `RunProtocol`'s queue can lose input by construction ([embarch-dev-bench/design.md](../embarch-dev-bench/design.md) §4, [embarch-decision-reversals.md](../embarch-decision-reversals.md) rows 72–73). The fixture is not wrong and is not being changed — it proves the primitives, which is what §4.9 chose it for — but it is a *fixture*, and this paragraph exists so nobody reads it as a recommended shape.

The second finding is about what a protocol should declare at all: `bds_ppg_drain.eap` deliberately does **not** name the bulk `batch_data` characteristic as a source, even though the download is the thing it exists to drive. A tap on a protocol source is fed from the interpreter's own dequeue, so the queue's drops are the tap's drops; the bulk characteristic belongs on a `GattMonitorSelectedStart` window and the protocol keeps the control/status pair. Same 5 minutes, 28,548 bytes → 714,927.

- **`gwf1_batch.eap`** — a self-describing batch record: fixed header, a full compile-time-capacity channel descriptor table (`repeat channel[30]` — literal, because the flash erase happens before the geometry is known), a runtime-counted chunk list (`count_from: n_chunks`), delta+zigzag bit-packed columns, and a trailing CRC-32 at `policy: skip`. Its tests assert the split directly: five header scalars are guard-reachable at offsets `[0, 4, 12, 13, 15]`, and the descriptor table, the bit-packed columns and the CRC are **not** on the wire. A flat `PPG1` sibling on the same source lowers into a `StructLayout` and really renders (`rep_index,magic,seq,green,red`); `GWF1` gets no layout at all, which is the refusal §3 decision 62 describes.

## 5. Relationship to embarch-core

This is a real scope expansion for Core, not a small addition. Today, Core's stated purpose is deliberately narrow: it "owns the debug probe (flash/reset) and the serial console log" for the DUT and "has no idea the EmbArch API or Claude Code exist" beyond its bearer-token-authed endpoints (`embarch-core/design.md` §1). Bridging study commands to `embarch-dev-bench` over a second serial link is a new hardware relationship for Core — a second physical connection, a second wire format (binary, not Core's existing JSON-only endpoint bodies), and new endpoints beyond the DUT-facing `/status`, `/flash`, `/reset`, `/serial-log`. The first piece of that relationship now exists: `GET /dev-bench/port` (`embarch-core/design.md` §4, §5) identifies which serial port dev-bench is on. It opens nothing and speaks no `DevBenchMessage` — every part of the hop described below is still unimplemented.

§5.1/§5.2 below now specify those endpoints and the result storage they populate — resolving what was milestone-3 follow-up work. `embarch-core/design.md` itself has been updated to match (new endpoint rows, §2 architecture diagram, module layout) per `DOC-PROTOCOL.md` §5, ahead of any actual implementation — the same "recorded ahead of code" pattern `embarch-api/design.md` §3.10 used for its CLI decision.

### 5.1 New endpoints (async job model, §3 decision 9)

| Method | Path | Body / Query | Response |
|---|---|---|---|
| `POST` | `/study` | `Study` (JSON, §4.1, including the new `validations`/`steps_crc` fields — §3 decisions 17/19) | `{ study_id: Uuid, status: "accepted" }` — Core generates `study_id`, sends a single `StudyStart { steps, steps_crc, streams }` message (§3 decisions 24/39) over the serial link (§3 decisions 3/10/17/40 — `validations` and `requires` never cross this hop; `streams` does, because four of the five sources are dev-bench-mediated), and returns immediately without waiting for any step to run. Before any of that, Core validates the submission (§3 decision 18: capacity limits, in-bounds `step_index` references in `validations`, `validate_taps` over `streams` per §4.8, and a non-blank `requires` per §3 decision 40) and checks `steps_crc` (§3 decision 17, auto-filled by the submitter per §3 decision 26 if it was absent) — either failing rejects with `400` and no `study_id` at all, distinct from the async job's own `"failed"` status. Per-step progress arrives back as `DevBenchMessage::StepResult` (§3 decision 24), and the study's end as `StudyDone` — both drive `GET /study/{study_id}`'s `current_step` below. |
| `GET` | `/study/{study_id}` | — | `{ status: "pending" \| "running" \| "completed" \| "failed", current_step: u32?, total_steps: u32?, result: StudyResult?, reason: String? }` — `result` (§4.5, now including `validations` once they've run — §3 decision 19) is present only once `status` is `"completed"`; `"failed"` carries `reason` instead (e.g. dev-bench disconnected mid-study, or the crash/reconnect scenario §3 decision 16 covers). Unknown `study_id` → `404`. |
| `GET` | `/study/{study_id}/stream/{name}` | `?raw=1` | **The route the three below collapse into**, added 2026-08-25 (`embarch-core/design.md` §3 decision 30, §4): one declared tap's capture, by the name the `Study` gave it (§4.8). Its rendered file by default (`text/csv` for a `Samples` or `GattTranscript` tap); `?raw=1` for the byte-for-byte capture. Served as bytes, not a local file path — deliberately sidesteps the class of problem `/flash`'s `firmware_path` has (`embarch-core/design.md` §7's artifact-transfer gap): Core and `embarch-api` aren't guaranteed to share a filesystem. |

Retired by `embarch-api`'s own `study_stream_data` (Milestone 7 Phase B item 2). |
| `GET` | `/study/{study_id}/gatt-data` — **an alias since 2026-08-25** | — | Raw CSV bytes (`Content-Type: text/csv`, §5.2) — the study's whole GATT transcript (§3 decision 36), every entry across every step, uncapped and in both directions. Distinct from what `GET /study/{study_id}` returns inline: that carries each step's `gatt_activity`, the bounded inbound-only summary. `404` if the study captured no GATT traffic. Same served-as-bytes rationale as the two rows below. |
| `GET` | `/study/{study_id}/waveform-data` — **an alias since 2026-08-25** | — | Raw CSV bytes (`Content-Type: text/csv`, §5.2), the sensor-waveform capture (§3 decision 21) — same shape/rationale as `/power-data` above; `404` if the study captured no waveform data. |

- **One study in flight at a time**, enforced by a dedicated lock separate from Core's existing `hw_lock` (`embarch-core/design.md` §3 decision 4) — dev-bench is a second, independent physical connection, so a running study doesn't need to block a concurrent `/flash`/`/reset` against the debug probe, but two overlapping studies would both be trying to drive the one dev-bench. A `POST /study` received while another is still running is rejected outright with `409 Conflict` (body includes the in-flight `study_id`), not queued — matching the suite's minimal-viable posture (no queueing machinery exists anywhere else in Core); the caller re-submits after polling the in-flight study's `GET /study/{id}` to completion.
- **No cancel endpoint for v1** — deferred deliberately, matching the suite's existing "don't build a capability nothing yet needs" pattern (`embarch-api/design.md` §12's CLI-exit-code-granularity precedent). A stuck study still bounds itself via each `Step`'s own `timeout_ms` (§4.2).
- **Job retention**: completed/failed job status and results stay in Core's in-memory registry until Core restarts — no expiry, matching the suite's existing no-cleanup-until-restart posture (single shared token, no config hot-reload, `embarch-api/design.md` §12). The on-disk result files (§5.2) outlive the in-memory registry entry regardless. A Core restart while a study is in flight loses that study's registry entry entirely — a subsequent poll 404s, per §3 decision 16.
- **Incremental result writes.** Unlike the in-memory job registry above, everything under `streams/` (§5.2) is appended to as records arrive during the study (§3 decision 20, §4.8), not written once at the end — so raw capture data can outlive a Core crash that writes off the study itself as `"failed"` (§3 decision 16), even though `events.json` and any post-hoc `validations` (§3 decision 19) never get written for that study at all.

### 5.2 Result storage (§3 decision 11)

Per completed (or failed) study, Core writes to a results directory under its own local data directory — same machine-wide-local-data convention `token_store.rs` already establishes for `EMBARCH_TOKEN` (`embarch-core/design.md` §8) — at `study_results/<study_id>/`:

- **`events.json`** — the `StudyResult` (§4.5) verbatim: per-step pass/fail, captured BLE data, `validations` (§3 decision 19) once they've run, and — since 2026-08-25, when they were first actually written rather than merely present in the type — `provenance` (§4.5, §3 decision 40) and `streams` (§4.8). Small and human-readable; this is what `GET /study/{id}` (§5.1) returns inline once `status` is `"completed"`. Written only once, after the study reaches a terminal status *and*, for a `"completed"` study, after Core's post-hoc validation pass has finished — unlike everything under `streams/` below, which is written incrementally throughout. Core streams it to disk one `StepResult` at a time and never materializes a whole `StudyResult` host-side (§7's ~1.3 MB finding, `embarch-core/design.md` §3 decision 24); `provenance` and `streams` are both small and bounded, so both are serialized directly at the end without breaking that discipline.

- **`streams/`** — one file per declared tap, named by the tap (`embarch-core/design.md` §3 decision 30(b), implemented 2026-08-25). **This replaces the fixed `data.csv`/`waveform.csv`/`gatt.csv` paths as *paths* while keeping every one of their row shapes** — only the path the numbers take to reach a row changed. Everything here is written incrementally as bytes arrive, so a study that failed part-way still has the capture that led up to the failure, which is exactly what is wanted when something went wrong.

  **A tap always writes its raw bytes before any decode is attempted.** A decode that fails then costs a rendering, not a capture. Files, by the tap's *declared* `StreamEncoding` (§4.8) and never by anything inferred from the bytes:

  | Declared encoding | Raw file | Rendered file | Row shape |
  |---|---|---|---|
  | `Raw` | `<tap>.bin` | *(none — nobody declared a meaning)* | — |
  | `Text` | `<tap>.txt` | *(none — the decode is the identity, so the raw file already is the rendering)* | — |
  | `Samples { .. }` | `<tap>.bin` | `<tap>.csv` | `rx_utc_ms,step_name,value,unit,channel_id,core_rx_utc_ms` — `Sample::csv_header()` (§4.7) plus the one column Core appends |
  | `GattTranscript` | `<tap>.bin` | `<tap>.csv` | `rx_utc_ms,step_index,step_name,direction,kind,service_uuid,characteristic_uuid,att_status,payload_len,payload_hex,payload_ascii,core_rx_utc_ms` — `GattTranscriptEntry::csv_header()` (§4.3b) plus the same one |
  | `Struct { decoder }` | `<tap>.bin` | `<tap>.csv` | `rx_utc_ms,step_index,step_name,rep_index,<the layout's own columns>,payload_hex,decode_note,core_rx_utc_ms` — §4.8a. The decoded columns come from `Study.decoders[decoder]`, which the engineer declared; Core supplies the fixed columns around them and nothing else |
  | `OutpostTrace` | `<tap>.bin`, plus `<tap>.arrival.csv` | `<tap>.trace.csv` | `frame_index,frame_seq,rx_utc_ms,kind,a,b,name` — [`outpost`]'s own row shape, rendered post-hoc from the complete raw file once the capture closes. **`rx_utc_ms` here is Core's own receipt time for the *frame* that carried the record**, joined on from `<tap>.arrival.csv`, because an outpost record carries no timestamp of its own at all ([embarch-outpost/design.md](../embarch-outpost/design.md) §3 decisions 4, 17, 18) — so consecutive rows repeating one value is the normal case. Written **even when no manifest applies** (with `name` empty) and **even when no arrival stamps apply** (with `rx_utc_ms` empty); `streams/index.json` carries `named`, `timed` and a note saying which. What is refused is applying the *wrong* manifest, or the *wrong* stamps (`embarch-core/design.md` §3 decision 30(c)) |

  Core's job for a rendered row stays purely mechanical and unchanged by the move: run each `StreamRecord` through `streams::samples_in` (§4.8) or `postcard`-decode it as a `GattTranscriptEntry`, call the crate's own `to_csv_row` with the name of whichever step is open, and append its own `core_rx_utc_ms` (§3 decision 30 there) — Core holds no independent knowledge of what the columns mean or how many there are beyond that one addition. `rx_utc_ms` is the capturing node's own timestamp (§4.7), not a Core-assigned arrival time; `core_rx_utc_ms` is that Core-assigned arrival time, recorded alongside for post-hoc drift correction rather than in place of it. `value`'s real-world meaning is named by `unit` (§3 decision 27) but its exact hardware mapping is still open (§7) — the column *shape* is locked, its *content* isn't. A `Sample` or entry whose `step_index` is out of range is still written, with an empty `step_name`, rather than dropped: it is real data that happened, and losing it because Core couldn't label it would be the worse trade.

  Two more files live here, both Core's own rather than this crate's: **`index.json`**, one entry per declared tap mapping its name to its files, its encoding, and which of the three retired fixed routes it answers — the thing that lets `GET /study/{id}/stream/{name}` and those three aliases resolve from a handler holding no `Study`; and **`<tap>.1.<ext>`**, the previous segment of a file that has rotated under `EMBARCH_STREAM_MAX_BYTES`. See `embarch-core/design.md` §3 decision 30 for both, and for why a rotation that *deletes* a segment is what sets `StreamRef.truncated` (§4.8).

**`data.csv`, `waveform.csv` and `gatt.csv` were here**, at fixed paths, chosen per-channel. All three are retired by the above; results captured before 2026-08-25 still hold them, and Core's three alias routes still read them for exactly those (`embarch-core/design.md` §4).

## 6. Relationship to embarch-api

Once `embarch-study-designer` has code behind it and Core exposes the study-bridging endpoints (§5.1), `embarch-api` is expected to grow a matching MCP tool surface and CLI subcommand surface, mirroring the existing `build`/`flash`/`build_and_flash`/`reset`/`serial_log` pattern (`embarch-api/design.md` §5, §5a). Because study execution is async (§3 decision 9), the shape is two calls rather than one, mirroring Core's own two-endpoint split rather than trying to fake synchronicity by blocking `embarch-api` itself until the study finishes (which would just move the "how long do we wait" problem up one layer without resolving it). This keeps faith with §3 decision 6: any hardware-facing capability reachable by an agent must be equally reachable by a human with no agent in front of them, converging on the same `embarch-study-designer` types and the same orchestration code — not two independent implementations.

**Locked-in tool/subcommand surface** — implemented 2026-08-18 (Milestone 2, Dev Bench Self-Test); naming/param shapes below match exactly what shipped, see `embarch-api/design.md` §5/§5a for the real implementation detail:

| Name (MCP tool = CLI subcommand) | Params | Behavior |
|---|---|---|
| `run_study` | MCP: `study` (`serde_json::Value`, not a typed `Study` schema — this crate doesn't derive `schemars::JsonSchema` on `Study`, so `rmcp`'s `#[tool]` param struct can't use it directly; deserialized into `Study` inside the handler, with a clear schema-mismatch error on failure, same practical effect as a typed param). CLI: `--study-file <path>` (a JSON file matching the same schema — `Study`'s nesting makes per-field CLI flags impractical, unlike `build`/`flash`'s scalar args). | Calls Core `POST /study` (§5.1) and returns `{ study_id }` immediately. No `project` param — unlike `build`/`flash`, a study isn't tied to one of `embarch-api`'s configured projects; it targets whatever DUT is connected through Core's one dev-bench serial link. Recomputes/overwrites `steps_crc` via this crate's own `steps_crc()` before ever calling Core (decision 26). A `400` from Core (failed pre-flight validation or CRC check, §3 decisions 17/18) surfaces as an immediate MCP/CLI error with no `study_id` at all — distinct from `study_status` later reporting `"failed"` for a study that was accepted but failed during or after execution. |
| `study_status` | `study_id` (both MCP and CLI). | Calls Core `GET /study/{study_id}` (§5.1) and returns its status/`current_step`/`total_steps`/`result`/`reason` shape verbatim. |
| `study_power_data` | `study_id` (both MCP and CLI). | Calls Core `GET /study/{study_id}/power-data` (§5.1) and returns the raw CSV bytes (as MCP tool content, or written to stdout/a `--out <path>` file for the CLI). Named 2026-08-15, closing item 44 of the design-improvement review — previously left as "a small remaining item" with no name at all. |
| `study_gatt_data` | `study_id` (both MCP and CLI). | Calls Core `GET /study/{study_id}/gatt-data` (§5.1) and returns the raw CSV bytes, same shape as `study_power_data`. Added 2026-08-25 alongside §3 decision 36 — the exhaustive transcript, as opposed to `study_status`'s capped per-step `gatt_activity`. |
| `study_waveform_data` | `study_id` (both MCP and CLI). | Same shape as `study_power_data`, calling `GET /study/{study_id}/waveform-data` instead. Named alongside `study_power_data` for the same reason — no rationale to name one and not the other. |

No convenience "block until done" wrapper (a `run_study`-side analogue of `build_and_flash`'s bundling) for v1 — deferred deliberately, matching the suite's existing minimal-viable posture (`embarch-api/design.md` §12's CLI-exit-code-granularity precedent, `design.md` §5.1's "no cancel endpoint for v1"): a study's total runtime is far less predictable than a build's, so a blocking wrapper would need its own timeout policy layered on top of Core's per-`Step` `timeout_ms` (§4.2) for no clear benefit yet. Revisit if a real caller finds the two-call poll loop genuinely burdensome.

## 7. Open questions / future work

- ~~**`steps_crc` seals `steps`, but a study's `streams` now also cross the wire outside that seal**~~ — **resolved and implemented 2026-08-25** (§3 decision 39's amendment, schema v9, Milestone 7 Phase B item 0). A sibling `streams_crc`, not a widening of `steps_crc`. One correction worth keeping on record, since it is what decided it: this bullet used to argue a widening would "silently invalidate every saved study's sealed value." It would not — `embarch-api` recomputes and overwrites `steps_crc` on every submit (§3 decision 26), so no stored value is ever trusted. The real objection to widening is structural: `steps_crc` sits *between* `steps` and `streams` on the wire, so the C side would have to digest two non-contiguous spans or `StudyStart`'s fields would have to be reshuffled. A second correction, this one found by implementing it: the C decoder did **not** already walk the `streams` span, so the dev-bench half cost a full `StreamTap` walker (+654 bytes of `native_sim` text) rather than the varint-and-a-CRC-call it was priced at — see decision 39's amendment for the full account.
- ~~**`Step.power_sample` and a `StreamSource::PowerFrontEnd { sample_hz }` tap now overlap**~~ — **resolved and implemented 2026-08-25** (§3 decision 39's amendment, §4.4, schema v9). `power_sample` is retired and the tap is the only authoring path. Settled on evidence rather than on preference: `power_sample` was already fully vestigial — `embarch-core` never read it, dev-bench's C encoder always wrote `None` and its decoder read-and-discarded it, and `study_builder::build_study` always emitted `None`. Milestone 4 therefore arrives to one way to author a power capture, not two.
- ~~**Whether a `ValidationSource` should name a tap rather than a `DataChannel`**~~ — **resolved and implemented 2026-08-25** (§3 decision 19's amendment, §4.6). It should, for stream-fed data, with no `step_index`; `DataChannel` narrows to the two genuinely per-step channels, and `ValidationResult` carries the whole source rather than a flattened `step_index`/`channel` pair. More live than this bullet realised when it was written: Phase B replaces the three fixed CSV files those variants named, so leaving them would have left three variants pointing at files nothing writes. Settling it surfaced a second thing, now its own decision — the schema constant that would have charged this to dev-bench guards two hops with different exposure, and **split in two** (§3 decision 12's amendment, implemented the same day as `DEV_BENCH_WIRE_SCHEMA_VERSION`/`HOST_TYPE_SCHEMA_VERSION`, both at 9). This reshape moved only the host one, which is the split's first concrete payoff.

- **The physical `embarch-dev-bench` design itself** (what BLE radio hardware, what power-sampling hardware, connector/form factor) stays entirely out of scope here, and **as of 2026-08-25 is deferred with power profiling as a whole** — the user's call in that day's suite-wide design pass: Milestone 4 (Power-Sampling Study) moves out of the near sequence into the Later bucket and no front-end hardware gets ordered ([embarch-roadmap.md](../embarch-roadmap.md)). `data.csv`'s (§5.2) exact power-sample columns depend on this and stay unresolved with it. This is now a deferral with a named trigger — power profiling resuming — rather than an open question waiting on someone to answer it.
- ~~**nRF54 cross-compilation toolchain and build-system wiring for the FFI staticlib.**~~ — **resolved 2026-08-18** (`embarch-dev-bench/design.md` §3 decision 8, Milestone 2): the crate cross-compiles cleanly for the nRF54L15's Cortex-M33 core via `cargo rustc --release --target thumbv8m.main-none-eabi --features ffi --lib --crate-type staticlib`, invoked automatically from `embarch-dev-bench/app/CMakeLists.txt` as part of a plain `west build` — one build command, as decision 8 there always intended, just via a direct path-based `cargo` invocation rather than formal west-manifest module plumbing (see that decision's own text for why). The panic-handler gap this bullet used to track is closed: a `#[panic_handler]` now exists in `src/ffi.rs`, gated to `target_os = "none"` specifically so it doesn't fire (and conflict with libstd's own) on `cargo test --features ffi`'s host-target build. **One real gotcha found closing this, worth keeping on record:** the target triple must be the *soft*-float variant, `thumbv8m.main-none-eabi`, not `-eabihf` — this firmware's Zephyr build has no hardware-FPU ABI enabled, and a hard-float-ABI staticlib fails to link against it ("uses VFP register arguments") the moment any code path touches an `f32` (not just this crate's actual FFI-exposed function signatures, none of which pass a float — `Sample`'s own field is enough to trigger it internally). Confirmed producing a real, flashable `zephyr.hex` for the nRF54L15DK. **Narrower item, resolved 2026-08-20 as "correctly left as-is," not extended:** the FFI decode surface (`essd_study_decode_full`, `src/ffi.rs`) that hands a decoded `Study` back to C as a fixed-layout struct is still scoped to `Action::BleAdvertise` steps only (dev-bench's own decision 21) — dev-bench milestone 9 §3.1 had named extending it to the other four action kinds as Milestone 3's own scope, but implementing that milestone found the premise wrong: this surface decodes a postcard-encoded `Study` (name + steps + validations + steps_crc), not the `DevBenchMessage::StudyStart` (steps + steps_crc only) dev-bench actually receives over the wire — `study_ffi.h`'s own doc comment already said so, and `main.c`'s real dispatch has never called it (it decodes `StudyStart` directly via `serial_protocol.c`'s own hand-written decoder instead). Extending this surface would have been real, tested work with no caller to exercise it. Left exactly as it was — `Action::BleAdvertise`-scoped, validated-but-unused infrastructure for a future caller that does have a real `Study` blob to decode — per `embarch-dev-bench/design.md` decision 27's own correction; the actual wire-decode extension needed (and got) is `embarch-dev-bench`'s own `serial_protocol.h`/`.c`.
- ~~**A real stack-overflow risk in `Study`/`Step` deserialization.**~~ — **resolved 2026-08-25 (§3 decision 46): the type is fixed, not just the stack.** `Study.steps` becomes a heap `Vec<Step>` on the host behind an `alloc` feature and stays `heapless::Vec<Step, MAX_STEPS_PER_STUDY>` for the no_std dev-bench build, so the ~38 KB inline value that actually crashed a debug `embarch-api` collapses to a pointer. Decision 36's 512 MiB runtime thread stops being the thing standing between the suite and a crash and goes back to being ordinary headroom. **What is still owed and worth naming**: nobody has ever measured `size_of::<Step>()` or `size_of::<StepResult>()`, including the newer, larger `gatt_activity` variant — a `size_of` assertion test so the next growth fails CI rather than a stack is the cheap follow-on, and is not done.
- **`Sample.value`'s real-world shape — deferred with power profiling, 2026-08-25** (§4.7, §5.2). The CSV row *shape* (`rx_utc_ms,step_name,value,unit,channel_id,core_rx_utc_ms`, §3 decisions 27/30) is locked and unaffected. The open half — whether one `Sample` per capture instant is the right grain, or a genuinely multi-lead sensor needs several — was always downstream of what dev-bench's power and sensor hardware turns out to be, and that is now deferred as a whole (bullet above). Answering it speculatively would be designing against imagined data.
- **Dev-bench's UTC clock-resync accuracy** (§3 decision 12's `host_utc_ms` amendment, §4.7) — resync happens only on `Hello` (connection/reconnection), so `Sample.rx_utc_ms`'s drift between resyncs, and whether that's acceptable for post-hoc `SignalCheck` analysis (§4.6), isn't validated against real dev-bench hardware yet. §3 decision 30's `core_rx_utc_ms` gives post-hoc analysis the raw material to detect that drift after the fact, but doesn't correct it in real time or say how much drift is actually acceptable — that judgment still needs real hardware.
- ~~**Core's host-side watchdog grace margin**~~ (§3 decision 16's dev-bench-crash amendment) — **sized 2026-08-27, and the premise of this bullet was wrong.** It asked for "a distribution of real round-trip times on a healthy link", and the margin turns out not to be a link-latency quantity: it has to cover the teardown, transcript drain and `StepResult` encode that dev-bench does *after* its own clock expires, all queued behind whatever stream data is still in flight. It scales with how much the step captured, so an idle-link distribution would have measured the wrong thing however carefully. 2_000 was too small and cost a completed 715KB capture its result; now 10_000 ([embarch-core/design.md](../embarch-core/design.md) §3 decision 33, [embarch-decision-reversals.md](../embarch-decision-reversals.md) row 74).
- ~~**Exact CRC crate/algorithm**~~ — resolved during implementation: the `crc` crate (CRC-32/ISO-HDLC), computed by streaming each `Step`'s postcard encoding through a `Digest` one at a time rather than buffering all of `steps` at once, so a constrained dev-bench MCU only needs stack space for one `Step`, not `MAX_STEPS_PER_STUDY` of them. `streams_crc` (schema v9) reuses all three choices unchanged, one `StreamTap` at a time.
- ~~**`SignalCheck`'s real variant set, and the DSP/statistics implementations' rigor.**~~ — **closed 2026-08-25 by removal, not by answer (§3 decision 48).** The variant set was illustrative, the DFT was naive and O(n²), and both were provisional pending real captured data — which the same day's deferral of power profiling put out of reach indefinitely. Rather than carry a placeholder set behind a feature nothing called, the whole post-hoc validation notion was deleted. If checks over real capture data are wanted later, they get designed against that data, which is what this bullet always said should happen.
- **`GattDiscover`/`GattMonitorAll` (§3 decisions 31/32) and the extraction tool (§3 decision 33) — this crate's own half implemented 2026-08-20; `embarch-dev-bench`'s live BLE dispatch of the two new `Action`s is still separate, tracked work.** study-designer milestone 9 §3.1–3.7 landed: `GattCharacteristicInfo`/`GattServiceInfo`/`GattActivityRecord` (§4.3a), the two new `Action` variants and `StepResult` fields, `DataChannel::GattActivity`, `STUDY_DESIGNER_SCHEMA_VERSION` 3→4, the `GattConfigExtractor` trait, and `ZephyrBleDefExtractor` — all with round-trip tests (postcard + serde_json) and confirmed clean across every feature combination including `--all-features`. `MAX_DISCOVERED_SERVICES`/`MAX_CHARS_PER_SERVICE`/`MAX_GATT_ACTIVITY_RECORDS` (§3 decision 15's update): the first two are now validated against `ZephyrBleDefExtractor`'s real output (**3 services with 3, 7 and 8 characteristics — corrected 2026-08-26 by §3 decision 57, which found the extractor had never been reading the file the third one is declared in**) rather than approximated by hand; `MAX_GATT_ACTIVITY_RECORDS` still isn't, since that requires dev-bench actually running `GattMonitorAll` against live notification traffic — dev-bench milestone 9's own scope, unstarted as of this update.
- **`gatt_activity`'s worst-case `StepResult` size still has not been computed** (§3 decision 32's own text) — unchanged as a gap, but §3 decision 46 changes what the fix looks like. The host side no longer needs static-allocation treatment for it (the heap `Vec` fix applies to `Study`, and `StepResult` is assembled host-side), so what remains is the dev-bench half plus the `size_of` assertion decision 46's bullet above names. Still a real risk to check early in dev-bench milestone 9's implementation rather than after a stack overflow surfaces it, exactly as decision 21's did.
- **`ZephyrBleDefExtractor` (§3 decision 33) is scoped to exactly one firmware's macro conventions** — generic at the trait boundary, deliberately narrow at the implementation, per the user's explicit call during Milestone 3's design pass. A second firmware project's own extractor is new, separate future work, not a generalization of this one. **Narrowed 2026-08-26 by §3 decision 57**: the two *hardcoded filenames* are gone (the scan is repo-wide, scoped by the firmware repo's own ignore files), so what remains project-specific is only the convention that a 128-bit UUID reaches a `bt_uuid_128` through a `#define <NAME>_UUID_VAL`. The name is kept as-is because `static_extractor = "zephyr-ble-def"` is a value in real configs, and because that remaining assumption is real.

- ~~**The `.eap` state machine has no real-time interpreter yet**~~ — **resolved and implemented 2026-08-26** ([embarch-dev-bench/design.md](../embarch-dev-bench/design.md) §3 decision 41, wire schema v15). `eap_interp.c` is the executor and this crate's `eap_interp.rs` stays the specification; the cross-language pin is a literal `StudyStart` frame carrying the **real worked BDS protocol**, decoded on the C side and asserted field by field, plus eight interpreter-semantics cases mirroring `tests/eap_worked_protocols.rs`'s own. **One thing this crate was one field short of**, found closing it: `DevBenchMessage::StudyStart` had no `protocols` at all — decisions 58-62 shipped `Study.protocols` and stopped at the wire, so a `RunProtocol` step indexed something dev-bench had never been sent ([embarch-decision-reversals.md](../embarch-decision-reversals.md) row 68). Both fields are appended after `dev_bench_log_level`. What is still owed is a real run: nothing has executed a `.eap` file against a real DUT, only against a host.
- **`Study.protocols` has no authoring path in the Study Designer UI** (§3 decision 58). `parse`/`resolve` are public and `Study.protocols` is a plain field, so a study can be built with a protocol programmatically or from a hand-authored JSON; `study_builder::build_study` emits an empty list, because `RowAction` has no protocol row and inventing one ahead of the first real manifest would be designing against imagined authoring. The trigger is the same one §3.8 has been waiting on: a real engineer with a real DUT writing a real `.eap`. **That happened on 2026-08-27** — `bds_ppg_drain.eap`, in the reference-dut firmware repo's own `embarch/protocols/`, driving that DUT's Batch Data Service through 34 request/pump/consume cycles against a live link. It was authored by hand and resolved programmatically through `parse`/`resolve`, exactly as this bullet said was possible, and the study was built by a throwaway Rust program calling this crate rather than by anything in the suite — which is the gap this bullet describes, now with a worked example of what the missing authoring path would have to produce. Two things that first real manifest showed, both recorded in §4.9.
- ~~**Every new `MAX_*` bound in `limits.rs` for protocols is unmeasured against real firmware**~~ — **measured 2026-08-26** ([embarch-dev-bench/design.md](../embarch-dev-bench/design.md) §3 decision 41). From-scratch ESP32-C5 build: `sram0_0_seg` **81.12% → 87.04%**, +22,400 B, 49 KB free. **Both halves of the estimate this bullet carried were wrong, and in opposite directions.** The `no_std` `ProtocolDef` really is 17,496 bytes, but that is not what a firmware holds: dropping every name but `StateDef.name` and packing `Operand` — whose `i64` literal wastes six bytes of alignment padding in a type multiplied by arms, states, protocols and two `dev_bench_message` statics — takes the real C structure to **4,376 bytes**, a quarter of the number this bullet sized against. And the dominant term turned out not to be the storage at all but the **wire bound**: three staging buffers grow with `DBM_MAX_STUDY_START_LEN`, which is why dev-bench added a disclosed 3 KB byte cap over the whole span rather than deriving a bound from eleven count ceilings that multiply to ~7.4 KB *per protocol* of mostly-discarded names. Of the two levers this bullet named, both were pulled; a third nobody had named — a TX staging buffer sized for a message dev-bench cannot send — paid for 6.2 KB of it. Every count cap on the bench is this crate's own value except `MAX_EVENT_ARMS_PER_STATE`, which is 2 there against 4 here.
- **`repeat`, `bitpack`, `crc32` and `fixed` are parsed and pinned but nothing consumes them yet** (§3 decision 59). They lower into `FrameRender`, which today only produces a `StructLayout` for the flat cases; the bit-unpacker, the `count_from` walker and the CRC check are the render half and are not written. Deliberately so — a rendering written before any real capture exists would be tested against synthetic bytes, which is exactly what §3 decision 48 removed `SignalCheck` for. The tests pin that each primitive *parses into the right shape*, so the gap is a missing consumer rather than a silent misparse waiting to surface.
