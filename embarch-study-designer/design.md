## 1. Purpose and scope

`embarch-study-designer` is a shared Rust library that lets an EmbArch API user — human or agent, symmetrically (§6) — define and run **studies** of a DUT through a future `embarch-dev-bench` companion device. A study is a scripted sequence of stimulus/interaction steps plus measurement/validation, used for three overlapping purposes: fuzz testing, power profiling, and automated unit/integration testing during firmware development.

Unlike `embarch-api` or `embarch-core`, this is **not a service** — it's a data-types-and-tools library. It defines the shared vocabulary (a `Study`, its steps, the stimulus/sensing/validation shapes) *and* the narrow set of helper functions needed to work with that vocabulary identically everywhere (§3 decision 2) — e.g. CRC sealing (§3 decision 17) and canonical CSV-row rendering (§4.7, §5.2) — that every component along the full path a study crosses (`embarch-api` → `embarch-core` → `embarch-dev-bench` firmware → DUT, §2) compiles in directly, so neither the wire format nor the artifacts derived from it can drift into independently-maintained, slowly-diverging definitions.

`embarch-study-designer` is **not**:
- ~~A service or binary of its own — no `main.rs`, no HTTP surface, no MCP tools live in this crate itself.~~ **Reversed 2026-08-24 (decision 34), then re-reversed the same day the retirement landed (2026-08-24, `embarch-ui/milestone-1.md` §4.9):** the interim state held through decision 33's own `gatt-extract` CLI tool (an offline, one-shot binary, never a service) and, briefly, decision 34's own `study-designer-ui` binary (a genuine local HTTP surface, `main.rs` and all). That binary is now deleted — `embarch-ui`'s Study Designer tab covers the same authoring/build/run ground, calling this crate's `registry`/`merged_actions`/`study_builder` **in-process as a library**, not through a binary of its own. The original "not a service" stance holds again: this crate carries no `main.rs`/HTTP surface of its own, only `extract-gatt-config` (still a one-shot offline binary, unaffected) alongside the library code itself.
- A transport-layer implementation. It defines *what* gets sent (the types), not the socket/serial-port plumbing that sends it — that lives in each compiling component.
- Tied to one physical bench design. The type model is meant to outlive whatever `embarch-dev-bench`'s first physical revision turns out to be.

## 2. Architecture overview

```
                          embarch-study-designer (shared crate, #![no_std])
                          compiled in by all three:
                                    |
        +---------------------------+---------------------------+
        |                           |                           |
  embarch-api                 embarch-core                embarch-dev-bench
  (MCP + CLI,                 (bridges HTTP/JSON           firmware (C; BLE central/
   future §6)                  <-> serial/binary,           peripheral + power sampling;
                                future §5)                   links embarch-study-designer
                                                              via FFI staticlib, §3 decision 7)
        |                           |                           |
        +----- HTTP + JSON  ------->+----- Serial (UART/USB CDC, COBS-framed postcard) ----->+
                                                                                            |
                                                                                       DUT (BLE)
```

`embarch-api` and `embarch-core` already speak HTTP+JSON (`embarch-core/design.md` §4) — that hop is unchanged. The new hop this project introduces is `embarch-core` → `embarch-dev-bench`, over a serial link (§3), carrying the same logical `embarch-study-designer` types in a different wire format (§3). `embarch-dev-bench` is the component that actually talks BLE to the DUT and samples power — `embarch-core` never talks BLE or samples power itself, matching the suite's existing pattern of "hardware access stays in the layer closest to the hardware" (`embarch-core/design.md` §1).

That serial link now carries more than discrete `Study` submission and `StudyResult` reporting: a continuous streaming sub-protocol for power/sensor-waveform data captured during a step (§3 decision 20), and a CRC-sealed integrity check on `Study.steps` performed independently at both this hop and the API↔Core HTTP hop (§3 decision 17), on top of the schema-version handshake §3 decision 12 already establishes.

1. **Separable crate, not embedded in `embarch-api`.** All three of `embarch-core`, `embarch-api`, and dev-bench firmware compile it in independently — as a literal Cargo dependency for the first two, and via a cross-compiled FFI staticlib for dev-bench firmware (decision 7). This was chosen explicitly over embedding study logic inside `embarch-api` — the whole point is that dev-bench firmware (a different binary, a different language even) needs the identical types, which isn't possible if they only exist inside `embarch-api`'s crate.
2. **Data types plus the narrow set of tools needed to work with them identically everywhere — not a protocol or transport implementation.** The crate's job is defining `serde`-derived types (§4) *and* the small number of type-adjacent helper functions every consumer needs the identical implementation of, so `embarch-core`/`embarch-api`/dev-bench firmware never each reimplement the same logic and risk it drifting apart: CRC sealing (`steps_crc`, §3 decision 17) and, since §5.2's CSV rework, `Sample`'s canonical row-rendering (§4.7). It still intentionally does not hardcode a wire format or a transport — different hops in the architecture (§2) need different formats (decision 3), and baking one in would force a lossy re-encoding step at whichever hop didn't match. The line: anything every consumer must agree on byte-for-byte or column-for-column belongs in the crate; anything hop-specific (the socket, the HTTP client) stays out of it.
3. **Serialization is format-agnostic at the type level; two formats chosen per hop.** `embarch-api` ↔ `embarch-core` stays JSON, matching every existing Core endpoint (`embarch-core/design.md` §4) — no reason to break that convention for a hop that isn't resource-constrained. `embarch-core` ↔ `embarch-dev-bench` uses a compact binary format instead — **`postcard` is locked in** (pairs naturally with `serde` + `no_std`, no allocator required). Locked without real dev-bench hardware to spike against (none exists yet, milestone-3.md §5) — a stand-in `no_std`/no-alloc round-trip check is treated as sufficient for now, flagged for re-confirmation once real nRF54 hardware exists, the same way §3.2/decision 7's firmware-language call was. See decision 9 for the framing layered on top of it.
4. **Transport for the new hop is serial (UART or USB CDC).** Chosen over HTTP for `embarch-core` ↔ `embarch-dev-bench` specifically because dev-bench is expected to be a resource-constrained MCU wired directly to whatever machine runs `embarch-core` — mirrors Core's existing DUT serial-log pattern (`serialport`, `embarch-core/design.md` §5) rather than requiring dev-bench to carry a network stack.
5. **`#![no_std]`, not std-everywhere.** Locked in because dev-bench firmware may be bare-metal/resource-constrained and its own runtime is still undecided (§7) — a `no_std` crate keeps every downstream option open (bare-metal Rust, an RTOS, or a hosted environment via a `std`-compatible shim), whereas a `std`-only crate would foreclose the bare-metal case outright. `embarch-core` and `embarch-api` run on hosted `std` environments and are unaffected by this constraint — they simply use the `no_std`-compatible types over `std`.
6. **Symmetric human/agent access, once code work starts.** Follows the suite-wide principle already established for Core/API (`embarch.md` §5: "every hardware-facing capability is reachable both by an agent and directly by a human, converging on the same underlying modules"). Concretely, once `embarch-api` grows study-running code, expect new MCP tools *and* CLI subcommands (§6) — not one without the other, matching `build`/`flash`/etc.'s existing pattern (`embarch-api/design.md` §5, §5a).
7. **Dev-bench firmware is C, bridged via an FFI staticlib — not native Rust or a Zephyr+Rust module.** Resolved over native embedded Rust and `zephyr-lang-rust` (Zephyr's official Rust support) because the nRF54 family splits sharply by variant: nRF54L15 (single Cortex-M33) has a workable Rust path via existing `zephyr-lang-rust` samples on comparable Nordic parts, but nRF54H20's mandatory multi-core `sysbuild` build isn't a proven fit for that project's west-module/CMake integration — and either way, Zephyr's BLE host stays a C API reached through generated bindings, not idiomatic Rust, so the BLE-heavy parts of dev-bench firmware wouldn't be native Rust regardless. Going C-firmware sidesteps that split entirely. `embarch-study-designer` compiles as a `#![no_std]` staticlib cross-compiled for the target ABI, exposing `extern "C"` functions to build/serialize/deserialize `Study`/`Step`; `cbindgen` generates the matching C header directly from the Rust source, so it can't drift out of sync by hand. The `postcard` encode/decode logic (decision 3) stays inside the compiled Rust code — C firmware calls into it rather than re-implementing the wire format, which is what keeps this from becoming the three-independently-maintained-definitions problem decision 1 exists to avoid.
8. **Distributed as a sibling-repo dependency, not published to a registry — amended 2026-08-18 to a Cargo path dependency, not the git reference originally planned.** `embarch-core` and `embarch-api` consume `embarch-study-designer` directly rather than as a published crates.io/private-registry package — avoids registry version-bump-and-republish overhead while the type model (§4) is still actively changing across all three consumers, all of whom need to track it at head rather than a pinned release. Originally specified as a git dependency; actually implemented as `embarch-study-designer = { path = "../embarch-study-designer" }` in both consumers' `Cargo.toml`s instead, once Milestone 2 (`embarch-roadmap.md`) needed the dependency wired for real — a plain path is simpler for local co-development (edits to this crate are picked up by the next `cargo build` in either consumer with no commit/push/re-vendor step) and is exactly what `DOC-PROTOCOL.md` §2's sibling-repo layout already assumes every cross-repo reference can rely on. A git dependency remains an option to revisit if a consumer's checkout ever isn't a true sibling of this repo (a CI runner, a machine without all four repos cloned side by side) — not needed for any real workflow yet. The repo itself: [gabrieltetar/embarch-study-designer](https://github.com/gabrieltetar/embarch-study-designer), a standalone sibling repo alongside `embarch-core`/`embarch-api`/`embarch-doc` per `DOC-PROTOCOL.md` §2 — not folded into an existing repo as a workspace member, since three independently-versioned consumers (two Cargo dependents, one FFI/C consumer) is exactly the case a shared standalone crate is for. How dev-bench firmware's own build pulls in the compiled staticlib from this repo is resolved too — see §7's update to the nRF54 cross-compilation item.
9. **Async, job-based execution for the new Core↔dev-bench-bridging HTTP surface, not a single blocking call like `/flash`.** A `Study`'s BLE steps (advertise, wait for a connection) can legitimately take an unbounded time, unlike Core's existing bounded operations — a synchronous call would either need an unreasonably long client-side timeout or risk truncating a study mid-run. Core instead accepts a `Study`, returns a `study_id` immediately, and reports progress/result via polling. Full endpoint shapes in §5.1; this decision covers the *shape* of the interaction, which is a property of the whole study-execution flow this crate's types serve, not just Core's implementation.
10. **Serial framing: COBS-encoded postcard messages, versioned by an append-only top-level enum, not a manual length prefix or version byte.** postcard itself has no message framing or self-describing schema. COBS (Consistent Overhead Byte Stuffing) wraps each postcard-encoded message with a self-terminating frame that can resync after a dropped/corrupted byte — chosen over a fixed length-prefix header, which desyncs the reader on any single corrupted length field until a resync heuristic kicks in, a real risk on a physical UART link. The `cobs` crate is `no_std`-compatible with no allocator required, matching decision 5. Versioning is handled by making every message dev-bench sends/receives a variant of one top-level `serde`-derived enum (e.g. `DevBenchMessage`) — postcard's varint-encoded enum discriminant gives wire compatibility across additions for free, provided variants are only ever appended, never reordered or removed, which is the discipline this decision commits to rather than a separate hand-rolled version byte. New variants added later for the dev-bench→Core streaming mechanism (§3 decision 20) follow the same append-only discipline.
11. **Result storage splits by data shape: a JSON events file plus a CSV data file, not one combined file or a database.** Per-step pass/fail and captured BLE data go in a small, human-readable `events.json`; power time-series samples — potentially large, high-sample-rate — go in a separate `data.csv`, referenced from `events.json` rather than embedded. Chosen so the common case (check whether a study passed) never requires parsing a large series, while still following the suite's "no database" principle (`embarch-api/design.md` §3.6) for the small side of the split. Full layout in §5.2.
12. **A manually-bumped schema-version constant, checked at both connection points, rather than silent trust in "everyone tracks head."** Per decision 8, `embarch-core` and `embarch-api` consume this crate as a git dependency at head, but the two are deployed and redeployed independently (e.g. Core native on Windows, API elsewhere) — nothing stops one side from running a build a change or two ahead of the other, and a drifted `Study`/`StudyResult` shape would fail in whatever way `serde` happens to fail, not with a clear error. The crate exposes a hand-bumped `u32` constant per hop — one until this decision's 2026-08-25 amendment split it into `DEV_BENCH_WIRE_SCHEMA_VERSION` and `HOST_TYPE_SCHEMA_VERSION` — bumped only when a wire-relevant type changes (independent of Cargo.toml's own semver, which bumps for reasons that don't affect the wire shape at all). It's checked at both hops, in the way each hop's own connection-establishment step already works:
    - **`embarch-core` ↔ `embarch-dev-bench` (serial, §3/§10)** — the hop most exposed to drift, since dev-bench firmware is flashed once and can silently lag behind a rebuilt Core. The first messages exchanged when Core opens the serial port are a `Hello { schema_version: u32 }` / `HelloAck { schema_version: u32, compatible: bool }` pair (both variants of the same `DevBenchMessage` enum decision 10 already establishes), before any `Study` traffic. A mismatch fails the connection outright rather than proceeding and failing mid-study on a decode error.
    - **`embarch-api` ↔ `embarch-core` (HTTP, §5.1)** — no separate handshake call; `GET /status` (`embarch-core/design.md` §4) already serves as the connection-establishment check, so it gains a `study_designer_schema_version: u32` field for `embarch-api` to compare against its own compiled-in constant before submitting a `Study`.
    
    This is a version *mismatch detector*, not a compatibility *negotiator* — there's no fallback to an older wire format on a mismatch, matching the suite's existing minimal-viable posture (no config hot-reload, single shared token) rather than building version-negotiation machinery nothing yet needs.

    **`Hello` also now doubles as a hard reset.** Independent of the version check above, receiving a `Hello` unconditionally tells dev-bench to abort whatever it's currently running (any in-progress `Study`) and clear its execution state before replying with `HelloAck`. This is what lets Core recover to a usable connection after its own crash/restart (§3 decision 16) without a separate abort message or waiting out dev-bench's own step timeouts first.

    **`Hello` also now carries `host_utc_ms: u64`.** Dev-bench has no other clock source, so this is its only way to learn wall-clock time at all: it seeds/resyncs its own UTC offset (correcting its free-running tick counter against this value) every time it receives a `Hello` — i.e. on every connection and reconnection (§3 decision 16's amendment below). This is what makes `Sample.rx_utc_ms` (§4.7) a real UTC timestamp rather than dev-bench-uptime-relative. Best-effort periodic resync, not continuous NTP-style discipline — the acceptable drift between resyncs is an open item (§7), same posture as this doc's other hardware-unvalidated constants.

    **Amendment 2026-08-25, settling a gap Milestone 7 Phase A left in §7: one constant becomes two, because it was guarding two hops with different exposure.** `schema_version.rs` listed `crate::validation` among the modules whose changes bump this constant, and settling §7's `ValidationSource` question forced the question of whether that is right. It is half right, and the wrong half matters: `validations` is never transmitted to dev-bench at all (decisions 17, 19), so no change to it can drift a dev-bench decoder — but `Study` **including `validations`** does cross the `embarch-api` -> `embarch-core` HTTP hop as JSON, and that hop's only drift check is this same constant. Dropping validation from the trigger list outright would therefore have created a real, undetected failure between two processes this suite genuinely builds and deploys separately (`embarch-dev-workflow.md`). So the constant splits instead:

    - **A dev-bench wire version**, checked at `Hello`/`HelloAck` as today, bumped only by a change to something dev-bench itself parses or emits. This is the number whose movement costs a firmware reflash and a both-languages re-pinning pass (decision 36's pairing).
    - **A host type version**, checked at `GET /status` as today, bumped by any change to a type crossing the `embarch-api`<->`embarch-core` hop — a superset, covering every dev-bench wire change *and* host-side-only ones like `Study.validations` and `Study.requires`.

    Both stay mismatch *detectors*, not negotiators; the two bullets above are unchanged in that respect. What changes is that a host-side-only reshape no longer moves a number dev-bench compares itself against, so it no longer implies firmware work that cannot exist — while the api<->Core hop still refuses to talk across the drift. The precedent this contradicts is stated rather than hidden: `Study.requires` (decision 40) is host-side-only and did move the single constant at the last pass; under this rule it would have moved only the host one. Recorded in [embarch-decision-reversals.md](../embarch-decision-reversals.md), since a versioning rule that fires on changes the version cannot express is how a bump number stops meaning anything. **The concrete number each constant starts at is implementation's to fill in** — see decision 39's own bump note for why a version written into a doc ahead of the work that derives it is a fact with a shelf life.

    **Implemented 2026-08-25** (Milestone 7 Phase B item 0). `STUDY_DESIGNER_SCHEMA_VERSION` is gone; `DEV_BENCH_WIRE_SCHEMA_VERSION` and `HOST_TYPE_SCHEMA_VERSION` replace it, **both at 9**. The old name was removed outright rather than kept as an alias, so every call site had to choose which hop it meant — which is the whole content of the split, and an alias would have let the ambiguity survive.

    **Amendment 2026-08-25 (Milestone 7 Phase B item 2): the split's prediction held, and this is the evidence that it works.** `Provenance` gained `overrides` — a `StudyResult` field, and `StudyResult` is assembled *by the host* out of the `StepResult` messages dev-bench sends; dev-bench has never encoded or decoded one. So the change moved `HOST_TYPE_SCHEMA_VERSION` 9 → 10 and left `DEV_BENCH_WIRE_SCHEMA_VERSION` at 9, checked rather than assumed: a grep of `embarch-dev-bench`'s C for `Provenance`/`StudyResult` finds one comment and no code, and decision 36's both-languages pinning rule does not apply because nothing new crosses that wire. **This is the first bump that moves one constant alone**, which is the whole content of the split — the second host-only change it spares dev-bench, after decision 19's amendment, and the first that actually separates the two numbers. Under the pre-split single constant it would have charged a firmware reflash for a type firmware cannot observe.

    The consequence this doc predicted has now happened: **the two numbers are no longer equal**, so "they match" has stopped being available as a (worthless) check. What replaced it is a compile-time assertion in `schema_version.rs` that `HOST_TYPE_SCHEMA_VERSION >= DEV_BENCH_WIRE_SCHEMA_VERSION` — the host constant's triggers are a strict superset, so it can never trail, and a wire bump that forgot to move the host one would otherwise leave the api<->Core hop talking across a difference it exists to refuse. Compile-time rather than a test, because the build that would carry the bug is not necessarily one anybody ran the test suite against.

    **Neither constant was renumbered, and that was a decision, not an omission.** Both continue the single constant's own sequence from v8; `schema_version.rs`'s rewritten history says which side each past bump would have belonged to under today's rule instead of recounting them. Renumbering would make every version string already logged, pinned in a C test, or written into a doc ambiguous about which scheme it was counted in — the same class of harm as [embarch-decision-reversals.md](../embarch-decision-reversals.md) row 18's stale bump number, with a wider blast radius. The consequence, stated rather than discovered later: the two numbers are **equal today and will diverge on the first host-only pass**, so "they match" proves nothing about whether the split works.

    **Three things implementation settled that this amendment did not spell out:**

    - **The api<->Core half had never actually been built.** This decision has described `GET /status` carrying `study_designer_schema_version` since 2026-07-28, and `embarch-core/design.md` §4's endpoint table already recorded (2026-08-23) that `status_handler` returns `{status, probes}` and nothing else. So "update Core's `/status` field and `embarch-api`'s comparison" was in fact *adding* both for the first time. `embarch-api`'s comparison lives in `embarch-core-client`'s `post_study`, not at each caller: the CLI and the MCP tool both submit through that one method, and a drift detector only one of them runs is not a detector.
    - **A Core that serves no version at all is a mismatch, not a pass.** `StatusResponse.study_designer_schema_version` is `Option<u32>` purely so such a response still *parses* and the drift can be named (`SchemaVersionMismatch`, downcastable like `StudyConflictError`); `None` is refused. The operational consequence is real and is not hidden: **the currently-deployed live Core serves no such field, so `embarch-api` will refuse to submit a study to it until Core is redeployed.** That is the detector working, not a regression — but it means this pass's deployment order is Core first.
    - **The FFI's `essd_schema_version` returns the wire constant**, and there is deliberately no FFI surface for the host one. dev-bench is not a party to that hop at all. Separately, `study_ffi_stub.c` — the by-hand mirror `native_sim` uses in place of the real staticlib — was found **stale at v4, four bumps behind**, because nothing compares it against the crate by construction. Corrected to 9; the gap in what `native_sim` can prove is unchanged by fixing the number and is recorded in `embarch-dev-bench/design.md`.
13. **Per-step, not per-study, fail-continuation policy: `Step.continue_on_fail: bool` (§4.2), not a single study-wide abort-on-fail switch.** A `Study`'s steps often mix "must pass or the rest is meaningless" checks (e.g. a `BleConnect` step — nothing downstream works without a connection) with "record and move on" checks (e.g. a `DataExchange` step that's informational for a fuzzing run rather than fatal to it). A single study-wide switch can't express that mix; a per-`Step` bool can. Defaults to `false` (abort the `Study` immediately on this step's `Fail`/`TimedOut` outcome), matching typical test-runner semantics for §1's automated-testing use case — an author opts a specific step into `true` only where continuing past its failure is actually useful. This governs only the device-observed `Outcome` (§4.5) — the real-time signal dev-bench itself can act on. It has no bearing on the separate, Core-side post-hoc content-validity check (§3 decision 19): dev-bench can't know that result in time to decide whether to continue, so `continue_on_fail` simply doesn't apply to it.
14. **Correlation by array position (`step_index: u32`), not by `Step.name`, for `StudyResult`/`StepResult`, and for the new `ValidationSource` (§3 decision 19).** `Step.name` (§4.2) stays purely a human-readable label — useful when a person reads `events.json` directly (§5.2) — but nothing in the wire types uses it to locate a step. `Study.steps` is already order-significant (§4.1: "run in order"), so a step's position in that `Vec` is already a unique, stable-within-that-`Study` identifier; reusing it costs no new field and sidesteps the ambiguity a name-based lookup would have if a `Study` author (or a fuzzer generating `Step`s, §4.5) gave two steps the same `name`. Encoded as `u32`, not `usize` — `usize`'s width isn't fixed across the architectures this wire format actually crosses (a 64-bit host running `embarch-core`/`embarch-api` vs. a 32-bit nRF54 MCU running dev-bench firmware, decision 7), and postcard would encode a mismatched-width `usize` inconsistently between them. `ValidationSource.step_index` originally had to reference a strictly earlier index, back when `Validate` was itself an ordered `Step` (now removed, §3 decision 22) — that constraint no longer applies now that post-hoc validation lives in `Study.validations`, a separate list Core evaluates only once the whole `Study` has finished running: by then every step (if the study completed) has already executed, so `step_index` just needs to be in-bounds for `Study.steps`, in either direction, which Core checks up front (§3 decision 18).
15. **Fixed-capacity `heapless` collections, not `alloc`-based `Vec`/`String`, for every sequence/string field in §4 — with concrete max-size constants.** Decision 5 commits the crate to `#![no_std]`, and decision 3 already treats postcard's own encoding as allocator-free — but neither decision actually constrained the crate's *own* data types: as originally drafted, `Study.steps: Vec<Step>`, `Step.name: String`, `GattOperation::Write { payload: Vec<u8> }`, and similar fields all require a global heap allocator (`extern crate alloc`) somewhere in whatever links this crate — not something dev-bench firmware (bare-metal C, decision 7) is guaranteed to provide. Resolved by switching every such field to `heapless::Vec<T, N>` / `heapless::String<N>` — `heapless`'s `serde` feature implements `Serialize`/`Deserialize` for both, and pairs with postcard with no allocator anywhere in the chain, closing the loop decision 3 started: the crate is now allocator-free end to end, not just at the encoding layer. This forces a concrete max-size constant onto every such field rather than leaving it unbounded, which also directly serves §1's fuzz-testing use case: a fuzzer generating `Step`s (§4.5's fuzzing note) now has an explicit ceiling to generate within, rather than being able to construct a `Study` no real dev-bench MCU could ever hold in memory. Constants (module `limits`, all `pub const _: usize`):
    - `MAX_STEPS_PER_STUDY = 64` — `Study.steps`, `StudyResult.steps`.
    - `MAX_STUDY_NAME_LEN = 64` — `Study.name`, `StudyResult.study_name`.
    - `MAX_NAME_LEN = 32` — `Step.name`, `StepResult.step_name`.
    - `MAX_SERVICE_UUIDS = 4` — `BleAdvertise.service_uuids`.
    - `MAX_LOCAL_NAME_LEN = 26` — `BleAdvertise.local_name`; sized to fit inside a legacy 31-byte BLE advertising PDU alongside AD-structure/flags overhead, not an arbitrary round number.
    - `MAX_PAYLOAD_LEN = 512` — `GattOperation::Write.payload`, `StepResult.captured_data`, `ExpectedValue::Equals`/`Contains`; sized above BLE 5's practical extended-MTU ceiling (247-byte ATT_MTU / 251-byte L2CAP payload), not the legacy 23-byte default, so a single-PDU-worth exchange never truncates.
    - `MAX_FAIL_REASON_LEN = 64` — `Outcome::Fail.reason` (also reused by `ContentValidity::Invalid.reason`, §3 decision 19).
    - ~~`MAX_RESULT_REF_LEN = 64`~~ — was `StepResult.power_samples_ref`/`waveform_ref` (§3 decision 21); **retired 2026-08-25 with the two fields**, §3 decision 39. `MAX_BATCH_SAMPLES` went the same way and for the same reason. What replaced them: `MAX_STREAMS_PER_STUDY = 8`, `MAX_STREAM_NAME_LEN = 32`, `MAX_SIGNAL_NAME_LEN = 32`, `MAX_STREAM_CHUNK_BYTES = 512`, `MAX_STREAM_RECORDS_PER_BATCH = 4` (§4.8) — all placeholder-but-concrete, none sized against a real capture, same posture as the rest of this list.
    - `MAX_VALIDATIONS_PER_STUDY = 64` — `Study.validations`, `StudyResult.validations` (§3 decision 19); matches `MAX_STEPS_PER_STUDY` since a validation entry costs no more than a step and there's no reason to allow more validations than there are steps to validate.
    - `MAX_DISCOVERED_SERVICES = 8` — `GattServiceInfo` entries per `StepResult.gatt_services` (§3 decisions 31/32, §4.3a); sized against real DUT firmware observed so far (`reference-dut-fw`'s `lib/ble/ble_def.h` declares 2 services today), with headroom for a DUT this crate hasn't seen yet.
    - `MAX_CHARS_PER_SERVICE = 16` — `GattServiceInfo.characteristics` (§4.3a); the same DUT's larger service is actually the Device Management Service at 8 characteristics, not the Sensor Data Service (7) as an earlier draft of this bullet said — corrected 2026-08-20 once `ZephyrBleDefExtractor` (§3 decision 33) ran for real against the checked-out repo and the two counts could be read off its output rather than approximated by hand.
    - `MAX_GATT_ACTIVITY_RECORDS = 32` — `StepResult.gatt_activity` (§3 decision 32); provisional, same posture as every other hardware-unvalidated constant in this doc — §7 carries the stack-safety risk this size implies.
    - `MAX_CSV_ROW_LEN = 96` — `Sample::to_csv_row`'s returned buffer (§4.7); sized to comfortably fit `rx_utc_ms` (up to 20 ASCII digits for a `u64`), a `MAX_NAME_LEN`-bounded step name, a formatted `value`, and separators — now also `unit`/`channel_id` (§3 decision 27), still comfortably within budget since both are short (a `Unit` variant name, one or two digits). (`MAX_STREAM_CHUNK_LEN` from an earlier revision of this list is retired — since `DevBenchMessage::StreamChunk` now carries a `Sample` directly, a small fixed-size struct, rather than an arbitrary-length raw byte buffer, there's nothing left for a byte-length capacity constant to bound; see §3 decision 20's implementation note.)
    - `MAX_BATCH_SAMPLES = 32` — `StreamChunkBatch.values` (§3 decision 25); placeholder-but-concrete, same posture as every other constant here, sized to keep one batched frame comfortably within a UART receive buffer at 1 Mbaud without real hardware to size against yet.

    These are placeholder-but-concrete, the same posture decision 3 already accepted for postcard itself: chosen without real dev-bench hardware to size against, flagged for re-confirmation once real nRF54 memory constraints are known. A value proving too small in practice is a version-bumped (decision 12) breaking wire-format change, same as any other field change.

16. **A Core crash/restart mid-study is an unrecoverable, catastrophic failure for that specific study — not a scenario the design tries to gracefully resume.** Each `Step.timeout_ms` (§4.2) already self-bounds any single hung action, so dev-bench is never stuck waiting past a step's own budget regardless of whether Core is still there to talk to — but that says nothing about what happens to the *study* itself if Core disappears entirely (process crash, unplugged, restarted) partway through. Resolved: that study is written off. Core's in-memory job registry (§5.1's retention policy) doesn't survive a restart, and Core — not dev-bench — is what persists `events.json`/`data.csv` (§5.2), so a study in flight when Core dies never gets a `StudyResult` written for it; a caller polling that `study_id` afterward just gets `404` (the registry entry is gone, indistinguishable from a `study_id` that never existed). Recovering the *connection* itself (as opposed to that specific study) is decision 12's `Hello`-as-hard-reset amendment: when Core comes back and reconnects, dev-bench aborts whatever it was still running and both sides start clean. Raw data already streamed to disk before the crash (§3 decision 20) may still be sitting in `data.csv`/`waveform.csv` on Core's disk — a partial diagnostic artifact, not a completed result — since decision 20 writes incrementally rather than buffering until the end.

    **A dev-bench crash/hang mid-study is symmetrically catastrophic — and needs a Core-side watchdog to even detect it.** The treatment above is written one-directionally: what happens when *Core* dies. A dev-bench firmware crash or hang partway through a study is written off exactly the same way — no attempt to detect-and-resume that specific study — but it can't rely on the same detection mechanism, because each `Step.timeout_ms` is enforced by dev-bench itself; if dev-bench is the thing that's hung or crashed, nothing on the device side is left to report `TimedOut`. Core therefore also enforces its own host-side watchdog: it expects a `StepResult` for the in-flight step within `timeout_ms` plus a small fixed grace margin of sending it (exact value open, same placeholder posture as §7's other timing constants), and treats that margin lapsing — or the serial connection dropping outright — as an immediate `"failed"` outcome for the study, the same terminal state a device-reported `Fail`/`TimedOut` already produces, just detected by Core instead of by dev-bench. Recovering the *connection* for whichever study comes next still goes through the same `Hello`-as-hard-reset path already established above.

17. **A CRC-sealed integrity check on `Study.steps`, checked independently at both the API↔Core and Core↔dev-bench hops.** Neither existing safeguard covers payload corruption: COBS (decision 10) only provides frame resync after a dropped/corrupted byte, not corruption *detection*, and postcard itself has no checksum; the API↔Core hop is plain JSON over HTTP with no equivalent check at all. `Study` gains a `steps_crc: u32` field, computed by whoever authors/submits the `Study` (`embarch-api`, or a human via the CLI) via a crate-exported `steps_crc(steps: &heapless::Vec<Step, N>) -> u32` function (CRC-32; exact `no_std`-compatible crate TBD, e.g. `crc` — §7) over `steps` specifically — not `name`, and not the new `validations` list (decision 19), which never leaves Core's own process and so has no second party to disagree with. Checked twice: Core recomputes the same function over the `steps` it deserialized from the HTTP body and rejects with `400` on mismatch before generating a `study_id` (alongside decision 18's structural checks); then again at the serial hop, where Core includes its own `steps_crc` in the same handshake exchange decision 12 already establishes, and dev-bench recomputes over what it decoded before running any step, rejecting the study outright on mismatch rather than running with possibly-corrupted step data.

18. **Core validates a submitted `Study` before generating a `study_id` or touching the serial link — structurally, not just for CRC integrity.** Two checks, both producing a `400` with a message naming the offending field/limit rather than a raw `serde` deserialize error (important since §6's `--study-file` path means a human is often hand-writing the JSON): every `limits`-module capacity (§3 decision 15) is within bounds, and every `step_index` referenced anywhere in the new `Study.validations` list (§3 decision 19) is in-bounds for `Study.steps` (decision 14's revised, no-ordering-constraint rule).

19. ~~**Two-tier validation: a real-time, device-observed `Outcome` per step, and a separate, Core-side, post-hoc content-validity check — not one mechanism doing both.**~~ **The post-hoc half is retired and removed, 2026-08-25 (§3 decision 48).** The real-time `Outcome` half stands and is unaffected — it is what dev-bench reports per step and what every study has always actually used. Everything below about `Study.validations` and its type family is history; kept for the record of what was built and why, not as a description of the crate.

    **Original text follows.**

     The original design conflated "did this step's action mechanically succeed" with "was the data it captured actually correct" into one `Validate` `Action` (now removed, §3 decision 22). They're different questions, answered by different actors at different times:
    - **Firmware-side, real-time:** a `DataExchange` step's existing `Outcome` (Pass/Fail/TimedOut, §4.5) already *is* this — did the GATT operation complete without a protocol-level error or timeout. Nothing new here; this is what `continue_on_fail` (§3 decision 13) gates, exactly as it already did.
    - **Core-side, post-hoc:** a new `Study.validations: heapless::Vec<PostHocValidation, {limits::MAX_VALIDATIONS_PER_STUDY}>` list, sibling to `steps`, never transmitted to dev-bench (it has nothing to do with it — dev-bench only ever receives `Study.steps`, §3 decision 17). Each entry is `PostHocValidation { source: ValidationSource, check: PostHocCheck }`, where `ValidationSource { step_index: u32, channel: DataChannel }` names which step and which of its data channels to read (`DataChannel::CapturedData | PowerSamples | SensorWaveform`, §4.6), and `PostHocCheck` is either `Simple(ExpectedValue)` (the original Equals/Contains/InRange, §4.3) or `Signal(SignalCheck)` — a new, richer enum of check kinds (mean-in-range, glitch/threshold detection, frequency-domain checks, etc.; illustrative placeholder set, §4.6) needed for power time-series and sensor-waveform data (PPG and similar), which a byte-equality check can't meaningfully express. Evaluated by Core **only if and when the study reaches `"completed"` status** — skipped entirely on any early abort/failure, even for steps that did capture data before the abort; results land in a parallel `StudyResult.validations: heapless::Vec<ValidationResult, {limits::MAX_VALIDATIONS_PER_STUDY}>`, empty exactly when validation didn't run. `ContentValidity` (`Valid` | `Invalid { reason: heapless::String<{limits::MAX_FAIL_REASON_LEN}> }`) is its own type, not a reuse of `Outcome` — `TimedOut` has no meaning for a desktop-side comparison. The actual `SignalCheck` evaluation logic — the number-crunching, not the wire shape — lives behind a `core-validation` Cargo feature on `embarch-study-designer` that only Core's build enables (needing `std`/`alloc`, floating point, possibly an FFT library); `embarch-api` and dev-bench firmware link the crate without that feature, so they see and can serialize/display every `SignalCheck` variant but never compile the code that evaluates one.

    **Amendment 2026-08-25: a stream-fed validation names the tap, not a `DataChannel` (settling §7).** `ValidationSource { step_index, channel: DataChannel }` was written when every capture belonged to a step and landed in one of three fixed files. Decision 39 ended both halves of that: a capture belongs to a declared tap whose `scope` may outlive any step, and Phase B (`embarch-core/design.md` §3 decision 30) replaces `data.csv`/`waveform.csv`/`gatt.csv` with `streams/<tap name>` — so `DataChannel`'s `PowerSamples`/`SensorWaveform`/`GattTranscript` variants would be naming files nothing writes any more. The source therefore splits by what it actually addresses:

    - **A per-step target** — `CapturedData` and `GattActivity`, both landing inline in `events.json`, both genuinely per-step, so `step_index` keeps its meaning (decision 14's array-position correlation, unchanged).
    - **A tap target** — named by `StreamTap.name`, exactly as §4.8 already said a tap's name is "the post-hoc validation source." **`step_index` does not apply to it and is not carried**: when a tap is open is a property of its declared `scope`, not of a step — the same thing the wire already says by carrying no `step_index` on `StreamOpen`/`StreamClose`.

    Naming the tap also gives `Raw`/`Text`/`OutpostTrace` taps a validation target, which no `DataChannel` variant ever had. **What this deliberately does not change: validation stays Core-side, static, and post-hoc** — evaluated once, after the study reaches `"completed"`, exactly as this decision's second bullet already specifies. Nothing here makes validation live, incremental, or anything dev-bench participates in. The cost is host-side only — no dev-bench work and nothing re-pinned, since `validations` never crosses that wire — but it does move the host type version decision 12's amendment splits out, because `Study` crosses the api<->Core hop whole. Free of consumers to break, too: `embarch-core` writes `"validations":[]` unconditionally and has never evaluated one, so there is no authored check to migrate. Settled before the first one is authored, which is what §7 said the point was.

    **Implemented 2026-08-25** (Milestone 7 Phase B item 0), as `ValidationSource::Step { step_index, channel }` / `ValidationSource::Tap { name }`, with `DataChannel` narrowed to `CapturedData`/`GattActivity`. It moved `HOST_TYPE_SCHEMA_VERSION` to 9 and left `DEV_BENCH_WIRE_SCHEMA_VERSION` alone — **the first change the decision 12 split actually spares dev-bench**, and the concrete argument for having made it.

    **Two things implementation settled that this amendment did not spell out:**

    - **`ValidationResult` had to move too, and this amendment only mentioned the source.** §4.6 defined it as `{ step_index, channel, result }` — a flattened copy of the old source. A tap-sourced check has no `step_index`, so reporting one would have reintroduced on the result side exactly the mislabelling removed from the source side. It now carries the whole `ValidationSource`: `ValidationResult { source, result }`, one per `Study.validations` entry, unchanged in that correspondence.
    - **Naming a tap the study doesn't declare is a `POST /study` pre-flight failure**, alongside the existing out-of-range `step_index` check (`embarch-core`'s `validate_study`). Nothing in the type system stops an author naming a tap that isn't there, and the failure it would otherwise produce is a check that silently never runs — which is the same silently-empty-capture class `validate_taps`' own step-range rule exists for (§4.8).

20. **A streaming sub-protocol from dev-bench to Core for continuous power/sensor-waveform capture, replacing discrete end-of-window sampling.** A step's `power_sample` window (§4.2/§4.4) or a new streamed sensor capture (§3 decision 21) can run for the length of the step, producing far more data than fits in one bounded message. New `DevBenchMessage` variants (append-only, same discipline as decision 10): `StreamStart { step_index: u32, channel: StreamChannel }`, `StreamChunk { sample: Sample }` (§4.7), `StreamEnd { step_index: u32, channel: StreamChannel }` (`StreamChannel::Power | SensorWaveform`, §4.6) — chunks in between carry no `step_index`/`channel` of their own, since Core tracks which channel is "open" from the last matching `StreamStart` it saw, keeping per-chunk overhead minimal on a UART link. `StreamChunk` carries a `Sample` directly, not arbitrary raw sensor bytes — so a chunk is self-contained and hardware-agnostic at the wire level; translating a raw ADC/sensor reading into a `Sample` (and stamping its `rx_utc_ms`) is dev-bench's own job before the value ever reaches the wire, which is what keeps Core's CSV-writing logic (§5.2) free of any hardware-specific decoding. Since `Sample` is a small fixed-size struct, no separate byte-length capacity constant is needed for it, unlike this decision's original raw-bytes framing. More than one channel can be open on the same step concurrently (e.g. a power window overlapping a sensor-waveform capture), so both `Start` and `End` carry the channel tag to disambiguate. Core writes each incoming chunk to disk **incrementally** — appending to `data.csv` or the new `waveform.csv` (§5.2) as it arrives, rather than buffering the whole capture in memory until the study finishes — so raw capture data can survive even a Core crash that writes off the study itself as failed (§3 decision 16), even though post-hoc validation (decision 19) still never runs over an incomplete study.

21. **Sensor-waveform capture is a new `GattOperation` variant, not a step-level field like `PowerSampleWindow`.** `GattOperation::StreamCapture` joins `Read`/`Write`/`Notify`/`Indicate`/`Subscribe` (§4.3) — a continuous capture of whatever the characteristic streams (e.g. a PPG waveform), landing in the new `SensorWaveform` data channel rather than `StepResult.captured_data`. No separate duration field, matching `PowerSampleWindow`'s existing reasoning (§4.2): it runs for exactly as long as the step's own `timeout_ms`/completion allows, so a capture can't silently outlive or fall short of the step characterizing it.

22. **`Action::Validate` (original §4.3) is removed.** Its job — checking a prior step's captured data against an expected value — is now done entirely by the new, Core-side, post-hoc `Study.validations` mechanism (decision 19). Keeping both would mean two overlapping validation systems; dev-bench firmware now has no validation-related code path at all, only the three remaining `Action` variants plus the new `StreamCapture` `GattOperation`.

23. **The FFI boundary (decision 7) is panic-safe by construction: `panic = "abort"`, plus explicit error codes on every `extern "C"` function — not `catch_unwind`.** A Rust panic unwinding across an `extern "C"` boundary into C firmware is undefined behavior; decision 7 established the staticlib but left this unaddressed. Resolved in favor of the simpler of the two standard fixes: `panic = "abort"` in the crate's `[profile.release]` (already the natural fit for a `no_std` bare-metal target with no unwinding runtime to begin with, decision 5) rather than wrapping every exported function body in `std::panic::catch_unwind` (which itself needs `std`, unavailable here). Every exported `extern "C"` function (build/serialize/deserialize `Study`/`Step`, decision 7) returns an explicit, C-friendly result — an integer status code (`0` = success, negative = a specific documented failure reason: buffer-too-small, capacity-exceeded, malformed input) plus out-parameters for any produced value — rather than a Rust `Result`/panic ever reaching the C caller. Mirrors decision 18's Core-side validation philosophy (name the specific failure, don't let a raw internal error surface) at the FFI boundary instead of the HTTP boundary.

24. **`Study` submission and per-step results get their own `DevBenchMessage` variants — the whole `steps` vector transferred in one message, not one step at a time.** Closes the single largest gap the 2026-08-15 design-improvement review found (its item 1): `embarch-core/design.md` §4 said Core "begins relaying `Study.steps`" to dev-bench, but no wire message actually carried a `Study` before this decision, and it was unspecified whether steps crossed the serial link one at a time or as a whole vector — a real gap, since decision 17's `steps_crc` is computed over the whole vector at once. Two new variants, append-only per decision 10: **`StudyStart { steps: heapless::Vec<Step, {limits::MAX_STEPS_PER_STUDY}>, steps_crc: u32 }`** (Core→dev-bench, sent once immediately after the `Hello`/`HelloAck` handshake — the whole vector in one postcard-encoded message, not streamed step-by-step) and **`StudyDone { completed: bool }`** (dev-bench→Core, sent once after the last step dev-bench actually ran, whether that's every submitted step or an early stop via `continue_on_fail`). Whole-vector transfer, not per-step streaming, because it's the shape that keeps decision 17's CRC check atomic: a per-step transfer would need either a running CRC accumulated message-by-message or per-message CRCs plus a final reconciliation, for a payload that's already small and bounded (`MAX_STEPS_PER_STUDY = 64`, each `Step` itself capacity-bounded by decision 15) and therefore cheap to send in one frame. Per-step *results* stream back incrementally instead, mirroring `StreamChunk`'s reasoning (decision 20): a new **`DevBenchMessage::StepResult { step_index: u32, result: StepResult }`** (§4.5) variant is sent as each step completes, so Core can write `events.json`'s per-step entries progressively and the host-side watchdog (decision 16) can key off individual `StepResult` arrivals rather than one final blob at the end of the study.

25. **UART link budget stated explicitly, and `StreamChunk` batches samples instead of one frame per sample.** Closes item 3 of the review: a COBS+postcard-framed single-`Sample` `StreamChunk` (decision 20) is roughly 10–14 bytes on the wire, and the power-profiling rate this crate is meant to serve (10–100 kHz, per §1's motivating use case) needs far more throughput than one frame per sample can deliver at any baud a UART link can reasonably run. Two changes: (1) **the Core↔dev-bench UART link runs at 1 Mbaud** — the practical ceiling for both the nRF54L15's UART peripheral and the on-board J-Link VCOM bridge it crosses (`embarch-dev-bench/design.md` §3 decision 6) without exotic clocking, stated here since nothing in either doc previously named a rate. (2) **`StreamChunk` gains a batched sibling, `StreamChunkBatch { base_utc_ms: u64, sample_interval_ms: u32, unit: Unit, channel_id: u8, values: heapless::Vec<f32, {limits::MAX_BATCH_SAMPLES}> }`**, append-only alongside the existing `StreamChunk` (kept, not removed, for wire-compatibility with anything still speaking an earlier schema version) — one base timestamp plus a fixed sample interval (both already known at `StreamStart` time, from `PowerSampleWindow.sample_rate_hz`) means every sample after the first needs no per-sample timestamp, only its `f32` value, turning per-sample framing overhead into a per-batch cost. `unit`/`channel_id` (decision 27) are carried once per batch, not once per sample, since a single capture window doesn't change units or channel mid-stream. `limits::MAX_BATCH_SAMPLES` (placeholder `32`, same posture as every other `limits` constant, decision 15) governs how many samples one batch carries. Core reconstructs each sample's `rx_utc_ms` as `base_utc_ms + i * sample_interval_ms` when writing `data.csv`/`waveform.csv` rows (§5.2) — placeholder-but-concrete, to be re-confirmed once real dev-bench sampling hardware exists and the actually-achievable rate is known, same posture as decision 3/15's other hardware-unvalidated constants.

26. **`steps_crc` is filled in by whoever *submits* a `Study`, not required of whoever *authors* one — closing the gap between decision 17's integrity check and the symmetric human/agent principle (decision 6).** Item 4 of the review: decision 17 requires a correct CRC-32 on submission, which makes a hand-authored `Study` JSON file (`embarch-api/design.md` §5a's `run-study --study-file`) unusable without a human computing a CRC by hand. Resolved without touching the check itself — Core still recomputes and validates `steps_crc` exactly as decisions 17/18 already specify — by moving *who fills the field* before it crosses the wire: `embarch-api`'s `run_study` tool / `run-study` CLI subcommand (§6) computes `steps_crc` via this crate's own exported `steps_crc()` function and overwrites whatever value (including a missing/zero one) was present in the submitted JSON, immediately before the `POST /study` call. A caller that already computed a correct value (a fuzzing driver generating `Study`s programmatically) is unaffected — the recomputation is idempotent. **Also new:** the crate ships a generated JSON Schema for `Study` (via the `schemars` dependency already present for `core-validation`'s use, decision 19) as a build artifact, `study.schema.json`, so a human hand-authoring a `--study-file` gets editor/CI validation before ever submitting, independent of the CRC question entirely.

27. **`Sample` gains `unit` and `channel_id` fields — resolving an ambiguity `StreamChannel`'s two variants (`Power`, `SensorWaveform`, §4.6) already implied but never settled.** Item 38: today's `Sample { rx_utc_ms: u64, value: f32 }` (§4.7) is one shape shared by both power and arbitrary sensor-waveform data, with nothing on the wire saying what `value` means or which of possibly-several concurrent channels on the same step it came from — a real gap the moment a capture needs more than one bare scalar (e.g. current *and* voltage sampled together, or a multi-lead sensor). Adding these fields now, rather than after real dev-bench hardware forces the question, avoids stacking a second version-bumped breaking wire change on top of the one hardware validation will likely already require. New fields: **`unit: Unit`** — a small, append-only enum (`Milliamps`, `Volts`, `Milliwatts`, `Raw`), extended as real hardware needs more — and **`channel_id: u8`**, disambiguating more than one concurrent stream on the same `StreamChannel` (`0` for the common single-channel case). Both are threaded through `Sample::to_csv_row`/`csv_header` (§4.7) as two new trailing CSV columns, and are carried once per batch (not once per sample) in `StreamChunkBatch` (decision 25).

Original text follows.

     Item 39: decision 19 skips post-hoc validation entirely on any non-`"completed"` study status — defensible for the automated-testing use case, but working against §1's *first-listed* purpose, fuzz testing, where a fuzzer often wants to know whether data a step *did* capture before a later step aborted the study was itself valid. Default `false` preserves every existing behavior and every already-shipped assumption (`StudyResult.validations` stays empty unless this is set explicitly); when `true`, Core runs `Study.validations` (§4.6) against whichever prefix of `Study.steps` actually executed before the abort — a `ValidationSource.step_index` referencing a step beyond that prefix is skipped, not an error, and reported as `ContentValidity::Invalid { reason: "step not reached" }` so a caller can distinguish "not reached" from "checked and failed."

29. **The fuzz-testing loop against `MAX_STEPS_PER_STUDY = 64` and one-study-at-a-time is documented, not changed.** Item 40 flagged the combination of a 64-step ceiling, no queue, and a `409 Conflict` on a concurrent submission as making a fuzzing driver look like an awkward N-round-trip loop against a rejection. Examined and left as-is deliberately: raising the ceiling doesn't help a fuzzer exploring many *distinct* short studies rather than one very long one (§4.1's "fuzzing, explicitly not modeled here" note already frames a `Study` as fuzzing's *output*, one concrete value per run), and a queue is real new machinery — persistence, ordering, partial-failure semantics — this suite has avoided everywhere else (`embarch-api/design.md` §3.6's no-database stance). The intended shape, stated explicitly here for the first time: a fuzzing driver runs entirely client-side (`embarch-api`, or a human/agent script driving it), generating one `Study` at a time, submitting it, polling `GET /study/{id}` (§5.1) to a terminal status, then generating and submitting the next — the poll loop *is* the intended backpressure mechanism, not a workaround for a missing one.

30. **Core records its own arrival time alongside every incoming message, independent of `Hello`'s resync — closing item 42 without changing when dev-bench's clock actually resyncs.** `Sample.rx_utc_ms` (§4.7) is stamped by dev-bench's own free-running clock, corrected only when a `Hello` arrives (decision 12) — for a long-running study with no reconnect, that clock free-runs between resyncs with no way to correct for it after the fact. Resolved without adding a second resync trigger (decision 12 deliberately keeps that tied to connection establishment, not a periodic timer): Core timestamps its own receipt of every `DevBenchMessage` that matters for timing — `StepResult`, `StreamChunkBatch`/`StreamChunk` — using its own wall clock, and records that alongside the message's own `rx_utc_ms` in `events.json`/the CSV files as a new, additive `core_rx_utc_ms` column that doesn't change `Sample`'s own wire shape. This doesn't correct drift in real time, but gives post-hoc analysis (a `SignalCheck`, or a human reviewing `data.csv`) the raw material to detect and account for it after the fact — which a resync-on-`Hello`-only design otherwise has no way to surface.
31. **`Action::GattDiscover` — a new Action that walks a connected DUT's entire GATT table via wildcard discovery, rather than requiring a `DataExchange` step's author to already know a `service_uuid`/`characteristic_uuid` pair.** Motivated by `embarch-roadmap.md` Milestone 3 (Study Designer: Feature-Branch Iteration): a Study author (human or agent) pointed at an unfamiliar DUT — or one whose exact characteristic layout isn't already known — has no way to ask "what's actually on this device" before authoring a `DataExchange` step against it. `GattDiscover` closes that gap: after a preceding `BleConnect` step establishes a connection, this step walks every primary service and, per service, every characteristic (Zephyr's ordinary wildcard `bt_gatt_discover`, no target UUID given — a superset of the single-service/single-characteristic discovery `ble_bridge_real.c` already does per `DataExchange` call, `embarch-dev-bench/design.md` §3's `BleConnect`/`DataExchange` implementation note), reporting the discovered table in the new `StepResult.gatt_services` field (§4.3a, §4.5) rather than acting on it further — no subscribe, no capture. Bound by the step's own `timeout_ms`, no separate duration field, matching every other Action's precedent (`PowerSampleWindow`, `GattOperation::StreamCapture`, decision 21). Properties are carried as the raw ATT characteristic-properties byte (bit 0 = broadcast … bit 5 = indicate, per the Bluetooth Core Spec's own characteristic-declaration encoding), not a crate-invented bitflag enum — consistent with this crate's existing "UUIDs are raw, not symbolic" stance on `DataExchange` (§4.3).
32. **`Action::GattMonitorAll` — a second, self-sufficient new Action: discovers, subscribes to every notify/indicate-capable characteristic, and captures whatever arrives for the rest of the step — deliberately not built on top of `GattDiscover`'s result.** Considered and rejected: a design where `GattMonitorAll` consumes a *prior* step's `GattDiscover` output, so discovery only ever happens once per connection. Rejected because every other `Action` in this crate is self-contained within its own step — `DataExchange` re-resolves its own service/characteristic on every call rather than assuming a previous step already did (`embarch-dev-bench/design.md` §3's per-call discovery) — and threading one step's discovered table into a later step's input would be new wire-level state-passing this crate has never needed before, for a capability (an unfamiliar-firmware smoke test, not a steady-state high-frequency operation) where re-running discovery once more per step is cheap. So: `GattMonitorAll` runs its own internal discovery first (identical walk to `GattDiscover`), then subscribes to every characteristic whose discovered properties include Notify or Indicate, then captures every notification/indication that arrives until the step's `timeout_ms` expires. Reports both `gatt_services` (§4.3a, so a consumer can decode which characteristic each captured record came from) and the new `gatt_activity: Option<heapless::Vec<GattActivityRecord, {limits::MAX_GATT_ACTIVITY_RECORDS}>>` in `StepResult` (§4.5) — each record `{ rx_utc_ms: u64, characteristic_index: u16, payload: heapless::Vec<u8, {limits::MAX_PAYLOAD_LEN}> }`, `characteristic_index` indexing into `gatt_services` flattened in service-then-characteristic order (service 0's characteristics first, then service 1's, and so on — stated here since it's the one place both dev-bench's encoder and any consumer need to agree on that flattening). `STUDY_DESIGNER_SCHEMA_VERSION` bumps 3 → 4 for this pair of decisions together (one bump covering both new `Action` variants and both new `StepResult` fields, same one-bump-per-pass discipline decision 18's `LogLine`+`firmware_version` pairing already established). **A real risk carried over from decision 21's own finding, not yet resolved:** `gatt_activity`'s worst case (`MAX_GATT_ACTIVITY_RECORDS` records at up to `MAX_PAYLOAD_LEN` bytes each) makes this `StepResult` variant substantially larger than `StudyStart`'s own worst case already was when it first triggered the stack-safety fix in `embarch-dev-bench/design.md` decision 21 (static, not stack-allocated, scratch buffers) — dev-bench's implementation of this decision needs the same treatment from the outset, not as a fix found the hard way a second time; tracked as an implementation risk in `embarch-dev-bench/milestone-9.md`, not re-litigated as a new design question here. **Overflow behavior, stated here since Milestone 3's own Definition of Done depends on it:** if real notification traffic fills `gatt_activity` to `MAX_GATT_ACTIVITY_RECORDS` before the step's `timeout_ms` elapses, dev-bench stops capturing further records for that step and reports what it already has — not a `Fail`/`TimedOut` outcome — matching `Sample::to_csv_row`'s existing "log and skip rather than corrupt" precedent (§4.7) rather than silently wrapping or truncating a record's own payload.
33. **A GATT-config extraction tool ships in this crate — a generic `GattConfigExtractor` trait plus exactly one concrete implementation for now — answering "what UUIDs does this DUT firmware actually expose" from source, ahead of ever connecting to real hardware.** Distinct from decisions 31/32 (which answer the same question live, over BLE, against whatever's actually running): a Study author working against a specific client firmware repo (e.g. `reference-dut-fw`) usually has that repo checked out locally already, and its GATT table is source, not a runtime mystery — extracting it statically means a `DataExchange` step can be authored with real UUIDs before dev-bench ever connects to anything, and gives a second, independent source to diff against `GattDiscover`'s live result (catching e.g. a service compiled out of a specific build). Shape: a `GattConfigExtractor` trait (one method, `extract(&self, repo_root: &Path) -> Result<heapless::Vec<GattServiceInfo, {limits::MAX_DISCOVERED_SERVICES}>, ExtractError>` — reusing §4.3a's own `GattServiceInfo`/`GattCharacteristicInfo` types, so a static extraction and a live `GattDiscover` result are byte-for-byte comparable, not two shapes needing their own diffing logic) plus exactly one implementation shipped now, `ZephyrBleDefExtractor`, scoped narrowly to this one firmware's actual conventions — confirmed against the real source (`lib/ble/ble_def.h`'s `..._UUID_VAL` macros, `lib/ble/ble.c`'s `BT_GATT_SERVICE_DEFINE`/`BT_GATT_PRIMARY_SERVICE`/`BT_GATT_CHARACTERISTIC(&uuid, PROPS, ...)` calls) rather than guessed against a generic Zephyr BLE peripheral layout other projects might use differently. Lives in this crate (`embarch-study-designer/tools/`, a new `std`-only Cargo binary target behind a new `gatt-extract` feature, not the `no_std` core — an authoring-time tool a human or agent runs before submitting a `Study`, never something dev-bench firmware or Core links) rather than `embarch-api`, since it's used *when creating* a Study, not while one runs (`embarch-api`'s tool surface is for driving hardware, §6) — matching where `GattServiceInfo`/`GattCharacteristicInfo` themselves already live. Deliberately generic at the trait boundary and narrow at the implementation, per the user's explicit call: adding a second firmware project's own extractor later is a new `impl GattConfigExtractor`, not a redesign of the trait or the output shape.

34. **A Study Designer UI: an interactive, table-based `Study` builder, shipping inside this crate — 2026-08-24, opening `embarch-roadmap.md` Milestone 3's design-questions follow-up.** **Implemented 2026-08-24** (`embarch-study-designer/milestone-11.md`): `src/study_builder.rs` (table rows → `Study`) and `tools/study_designer_ui.rs` (the `axum` server itself), live-smoke-tested against the real `reference-dut-fw` repo. Not yet validated against real GATT traffic — that needs a real DUT/dev-bench connected and, per decision 35, a real engineer-supplied action (§3.8 there). Motivated by a real gap Milestone 3's own closing session hit directly: a real `GattMonitorAll` run against the reference-dut DUT came back with an empty `gatt_activity` — nothing was captured because nothing in that `Study` ever *wrote* anything, and there was no way for whoever authored it to know what to write, since that's DUT-specific knowledge no generic discovery can produce (decision 35 names the principle this surfaces). Closing that gap needs two things: a real authoring UI (this decision) and a place for that DUT-specific knowledge to actually live (decision 35) — this decision is the UI half.

    **Shape:** a local web UI (own `main.rs`, reversing §1's "not a service" stance — see that section's own update) whose main surface is a table: each row is a `Step` — an `Action` picked from a dropdown, its parameters filled in (a dropdown of engineer-registered named values for a custom action, decision 35; the natural typed fields for a built-in `Action` like `BleConnect`), `timeout_ms`, `continue_on_fail`. Rows can be added, removed, and reordered — sequencing ("run this before that") is expressed purely by row order, not a separate precondition field, matching how a `Study.steps` array already works (§4.1, no state passed between steps per decision 32's own "every `Action` is self-contained" stance).

    **The action list a row can pick from is merged from three sources, not one:** this crate's own built-in `Action` variants (`BleConnect`/`GattDiscover`/`GattMonitorAll`/`DataExchange`); live `GattDiscover` results, when a DUT happens to be connected already; and `GattConfigExtractor`'s static output (decision 33) — the same dual-source cross-check decision 33 already established, both now feeding one UI instead of being two things a human diffs by hand.

    **Scope: author, run, and watch — but read-only outside the authoring table itself.** The UI can submit the `Study` it just built (or a small ad hoc discovery `Study`) and poll/display each step's live result as it completes — a human shouldn't need a second tool just to try what they built. It does **not** build or flash anything — provisioning the DUT/dev-bench (`build_and_flash`/`build_and_flash_dev_bench`) stays exactly where it is today, a separate step via `embarch-api`, done before this UI's "run" button means anything. Exactly how the UI reaches Core to submit/poll (shelling out to `embarch-api`'s existing CLI subcommands, a new thin client, or an extracted shared client crate) is left to implementation — the narrowed submit-and-poll-only surface makes this a small enough surface that it doesn't need deciding here.

    **This crate's own `tools/study_designer_ui.rs` binary — everything described above — is retired, 2026-08-24 (`embarch-ui/milestone-1.md` §4.9).** `embarch-ui`'s Study Designer tab is the successor: the same merged action list, the same table-based authoring model, the same registry (decision 35, unaffected), but calling `registry`/`merged_actions`/`study_builder` in-process from `embarch-ui`'s own binary rather than running a second local web server, and submitting/watching a `Study` via `embarch-core-client` over HTTP+Bearer rather than shelling out to `embarch-api`'s CLI (the "left to implementation" question this decision's last sentence deliberately deferred — resolved by `embarch-ui`, not here). `src/study_builder.rs`, `src/registry.rs`, and `src/merged_actions.rs` are entirely unaffected; only the binary that wrapped them in a server is gone.

35. **A user-authored custom-action registry — name and enumerated parameter choices only, never a semantic description, and never anything this crate infers on its own.** **Implemented 2026-08-24** (`src/registry.rs`): `ActionRegistry`/`RegisteredAction`/`ActionField`/`ActionFieldValue`, exactly this shape — a value's bytes are the engineer's own literal bytes, never a numeric type this crate encodes itself (that correction, and why, is `milestone-11.md` §3.1's own account). Persists at `<firmware-repo>/embarch/study-actions.toml`, confirmed round-tripping correctly against the real `reference-dut-fw` repo. This is the actual fix for what motivated decision 34: closing Milestone 3, an attempt to figure out what a custom GATT write "does" by reading the DUT firmware's own source and asserting a conclusion from it was flagged directly as destructive to the dev process — reading code and inferring behavior from it isn't the same as knowing it, and presenting that inference as fact is worse than not answering at all. The fix isn't a smarter inference — it's removing inference from the loop entirely: this knowledge only ever comes from the engineer, explicit and unambiguous, through a registry this UI reads and writes.

    **What the engineer actually provides, per the user's own explicit call — mechanical, not documentary:** for a detected characteristic (from either half of decision 34's merged action list) they want to use, a freely-chosen `name` (shown in the UI's action dropdown), which characteristic it targets, its `operation` (read/write/subscribe/notify/indicate), and — for a write — its payload described as one or more named fields, each with a small enumerated set of engineer-supplied `{label, value}` pairs. Building a `Study` step against a registered action means clicking a name and clicking a value; nothing is typed as raw hex, and nothing describes *why* a value does what it does — there is deliberately no "what this does" field at all, since that would just be this crate inventing a place to write down another guess.

    **Persisted in the firmware repo's own `embarch/` folder, sibling to `embarch.toml`** — travels with the firmware, versioned in that repo's own git history, shared across engineers the same way `embarch.toml` already is; not a catalog this tool owns separately, and not re-entered per `Study`. Exact filename/format (a `study-actions.toml`, matching `embarch.toml`'s own format, is the working assumption) is an implementation detail, not re-litigated here.

    **The durable principle, stated plainly since it generalizes past this one crate:** no EmbArch component should ever present an inference about what a specific piece of hardware or firmware does — derived from reading its source, its comments, or any other heuristic — as established fact. Where that knowledge is needed, the answer is a pipeline for the engineer who actually knows to supply it explicitly, built once, generically, for any project — this registry is that pipeline for "what does this GATT action do," not a one-off for `reference-dut-fw`.

36. **`Action::GattMonitorStart`/`GattMonitorStop` — a capture window that outlives its own step — plus a streamed, uncapped GATT transcript, 2026-08-25.** Opened by a gap found trying to author the first real stimulate-and-capture study: **it was not expressible.** Steps run strictly in sequence, one at a time, and `GattMonitorAll` (decision 32) unsubscribes everything it armed when its own step ends (`ble_bridge_real.c`'s teardown loop) — so a `DataExchange` write that stimulates the DUT and a `GattMonitorAll` step that captures the response can never overlap. Write first and the response arrives after the capture step is over; capture first and the write never happens during it. Every ordering loses, silently, producing an empty capture and a `Pass` — the same "nothing captured, no error" failure decision 34 was opened by, from a different direction.

    Two new field-less `Action` variants, appended after `GattMonitorAll` (postcard discriminants 5 and 6; decision 10's append-only rule): **`GattMonitorStart {}`** runs the same wildcard discovery and subscribe-to-everything walk `GattMonitorAll` does, then **returns immediately, leaving every subscription armed**, so every step that follows runs inside a live capture window; **`GattMonitorStop {}`** unsubscribes and reports the window's `gatt_services` plus its (capped) inline `gatt_activity`. A `Stop` with no open window is a no-op `Pass`, not a `Fail` — and a study that ends without one gets its window closed implicitly by dev-bench's own dispatch loop, so an abort mid-study can't leave subscriptions armed into the next one. `GattMonitorAll` is kept unchanged: a single-step "just watch for N seconds" capture is still the common case and still the simpler thing to author.

    **The second half — and the reason this is one decision, not two:** a window that spans steps immediately outgrows `StepResult.gatt_activity`, which is per-step, capped at `MAX_GATT_ACTIVITY_RECORDS` (32), and records *inbound notifications only* — nothing about what dev-bench itself sent, which is precisely the half a stimulate-and-capture transcript needs to be readable. So this decision also adds a **streamed GATT transcript**: a new `DevBenchMessage::GattTranscriptRecord { step_index: u32, entry: GattTranscriptEntry }` (§4.3b), emitted as each GATT event happens, and appended by Core to a new `gatt.csv` (§5.2) incrementally, exactly as `data.csv`/`waveform.csv` already are (decision 20). Because one entry is streamed per message, only a single entry ever has to fit in dev-bench's message buffer — which is what lifts the cap: the transcript is bounded by the study's own duration, nothing else.

    Deliberately **its own `DevBenchMessage` variant rather than a third `StreamChannel`** carried by `StreamChunk`/`StreamChunkBatch` (decision 20/25): those carry `Sample`, one `f32` plus a unit, with no room for a raw byte payload, a direction, or a pair of UUIDs. And deliberately **not a replacement for `gatt_activity`** — that inline summary stays, so checking a study's outcome never requires opening a large capture file, the same split that keeps `data.csv` out of `events.json` (§5.2).

    **Where the two disagree, and why that's intended:** `gatt_activity` counts only what a single step received, capped; `gatt.csv` records everything, both directions, across every step. A reader comparing them will see different numbers. `DataChannel::GattTranscript` (§4.6) names the new channel for future `PostHocCheck` use, alongside `GattActivity`, for the same forward-looking reason that one was added.

    **Partially superseded 2026-08-25, one day later, by decision 39 — knowingly, and with the collision flagged before the call was made.** `GattTranscriptRecord`'s *dedicated `DevBenchMessage` variant* is folded into the generic inbound stream pipeline decision 39 accepts; `gatt.csv`, its columns, `GattTranscriptEntry`/`GattDirection`/`GattEventKind`, and the entire "streamed, uncapped, both directions, incrementally appended" behavior above survive unchanged as a declared *encoding* over a generic tap rather than as their own message class. **The reasoning in this decision was not wrong** — `Sample`'s single `f32` genuinely has no room for a byte payload, a direction, or a UUID pair, and that is exactly why a third parallel pipeline looked like the only option. It was an argument against the shape `StreamChunk`/`StreamChunkBatch` had, not against a generic pipeline as such, and decision 39's tap model was designed around that specific objection. What made the reversal affordable rather than expensive: **this decision's dev-bench firmware, though code-complete and deployed, has never been flashed or run against hardware**, so nothing about its wire shape is load-bearing on a real bench yet. `Action::GattMonitorStart`/`GattMonitorStop` and the capture-window semantics — the half of this decision that opened it — are untouched.

    `STUDY_DESIGNER_SCHEMA_VERSION` bumps 4 → 5 for this decision: two `Action` variants, one `DevBenchMessage` variant, the `GattTranscriptEntry`/`GattDirection`/`GattEventKind` types, and one `DataChannel` variant — one bump per pass, same discipline as v4.

    **Cross-language wire contract, pinned in both languages.** dev-bench hand-writes its postcard encoding in C (`serial_protocol.c`), and nothing in either side's own test suite would notice the two drifting — a reordered field or a `u8` written as a varint decodes into plausible-looking garbage, not an error. So the exact bytes for one `GattTranscriptRecord` are pinned twice: as a literal COBS frame in dev-bench's ztest suite, and as the identical pre-COBS body in this crate's own `gatt_transcript_record_decodes_dev_bench_firmwares_own_hand_written_encoding`, which asserts postcard decodes them into the matching value *and* re-encodes to the same bytes. Changing the shape must break both. This pairing found a real discrepancy the first time it ran, which is the argument for it.

37. **A free-text payload path alongside the registry — `RowAction::Raw`, 2026-08-25.** Decision 35's registry is the right home for a *named, reusable* action, but it is the only way to send a payload at all, which makes a one-off — an ad-hoc shell command, a value being tried once to see what happens — require editing `study-actions.toml` first. `RowAction::Raw { service_uuid, characteristic_uuid, operation, payload }` (§4.3c) takes a UUID pair typed directly and a payload supplied as literal bytes.

    **This does not weaken decision 35.** That rule forbids two specific things: this crate inventing a *semantic description* of what an action does, and this crate *encoding a number into bytes* on an engineer's behalf (which requires assuming a width and endianness nobody here is in a position to know). `Raw`'s `payload` is already bytes when it reaches this crate — parsed client-side by the same parser the registration form uses, from either UTF-8 text with explicit escapes or hex tokens — so nothing here interprets or encodes anything. The registry remains how an action gets *named and re-used*; this is how one gets *sent before it has a name*.

    `Uuid::parse` is added alongside it, accepting the hyphenated 128-bit form, 32 bare hex digits, or the 16-bit shorthand expanded against the Bluetooth SIG Base UUID. That expansion is a Core Spec fact — a 16-bit UUID *means* that 128-bit value by definition — not an inference about any particular DUT, so it doesn't cross decision 35's line either.

38. **A saved-study library at `<firmware-repo>/embarch/studies/*.json`, 2026-08-25.** Until now a `Study` authored in the UI existed only for as long as the browser tab did; re-running one meant rebuilding the table by hand. Saved studies live beside `study-actions.toml`, same per-repo convention, so a study travels with the firmware it was written against and is versionable with it.

    **The file *is* a `Study`** — `embarch-api run-study --study-file <path>` re-runs it directly, with no conversion step and nothing else installed. The authoring rows ride along in one extra key, `_embarch_ui_rows`, which `Study`'s own deserializer ignores (no `deny_unknown_fields` anywhere in this crate). That single-file choice is what makes a saved study both re-runnable from the CLI *and* re-loadable into an editable table; a sidecar file would have made one of the two lossy or the pair separable. A `Study` JSON dropped into that directory by hand or by an agent is still listed and still runnable — it just has no rows to load back, and the UI says so rather than offering a Load that would silently produce an empty table.


39. **One generic inbound stream pipeline — [embarch-stream-pipeline-proposal.md](../embarch-stream-pipeline-proposal.md)'s read direction accepted, its write direction still proposed, 2026-08-25.** Opened by [embarch-outpost](../embarch-outpost/design.md), a new sub-project whose DUT-side debug UART needs its bytes captured for a study's duration — and which would otherwise have become **the fourth** near-identical capture pipeline in this crate, after power, sensor waveform, and (as of yesterday) the GATT transcript. Four pipelines that differ only in what the bytes mean is the point at which the pattern has to be named rather than repeated again.

    **`Study` gains one top-level field, sibling to `steps`/`validations`: `streams: heapless::Vec<StreamTap, {limits::MAX_STREAMS_PER_STUDY}>`** (§4.8). A tap declares four things — **where the bytes come from, how long the tap lives, how to render what arrives, and what to call the output** — and nothing else. Everything that used to be a bespoke channel becomes a declared `StreamSource`, and everything that used to be a bespoke row shape becomes a declared `StreamEncoding`.

    **What folds in, and what each one used to be:**

    | Was | Becomes |
    |---|---|
    | `StreamChannel::Power` + `StreamChunk`/`StreamChunkBatch` (decisions 20/25) | `StreamSource::PowerFrontEnd { sample_hz }` + `StreamEncoding::Samples { .. }` |
    | `GattOperation::StreamCapture` → `StreamChannel::SensorWaveform` (decision 21) | `StreamSource::GattNotify { service_uuid, characteristic_uuid }` + `StreamEncoding::Samples { .. }` |
    | `DevBenchMessage::GattTranscriptRecord` → `gatt.csv` (decision 36) | `StreamSource::GattTranscript` + `StreamEncoding::GattTranscript` |
    | `DevBenchMessage::LogLine`, which reached only Core's rolling log and never a study's results at all | `StreamSource::DevBenchLog`, a reserved tap — closing a real asymmetry rather than inventing a feature |
    | *(nothing — did not exist)* | **`StreamSource::Signal { name }`** — a signal Core reads itself, resolved to a carrier by [embarch-topology](../embarch-topology/design.md) §3 decision 18. The outpost's tap. |
    | *(nothing — did not exist)* | **`StreamEncoding::OutpostTrace`** — decoded against a build-time manifest ([embarch-outpost/design.md](../embarch-outpost/design.md) §3 decision 9). Shipped as `OutpostTrace { manifest_crc }` and corrected to a unit variant at schema v11/v13 — see the 2026-08-26 amendment below |

    **`StreamSource::Signal { name }` is the one genuinely new idea, and it is what makes the outpost expressible at all.** Every other source above is dev-bench-mediated: dev-bench receives the bytes and forwards them. The outpost's bytes reach Core over a wire that **bypasses dev-bench entirely** today, and are intended to go through it later — so the tap names the *signal*, and topology's declared route decides the carrier. The identical saved study (decision 38) runs unchanged across that migration, across a differently-enumerating USB bridge, and against a Core on another machine. A source variant naming the concrete port or pin would have re-authored every saved study the day the bench was rewired.

    **The write direction is explicitly not accepted.** `Action::StreamSend`, `StreamExpect`, and the shell-interaction case stay in the proposal, unadopted. The outpost is TX-only and needs nothing from them, and adopting a step type nothing yet sends would be building a capability nothing needs — the same posture §5.1's no-cancel-endpoint note already takes. The proposal file survives, its status narrowed rather than deleted.

    **`STUDY_DESIGNER_SCHEMA_VERSION` bumps once for this pass**, covering this decision and decision 40 together, same discipline as v4 and v5. Wire changes are real and are not being minimised: `DevBenchMessage`'s stream variants collapse to one `StreamOpen`/`StreamChunkBatch`/`StreamClose` triple carrying `{ rx_utc_ms, bytes }` records rather than `Sample`s, `GattTranscriptRecord` is retired as a variant, `StreamChunk` and `StreamChunkBatch` — **both still live, and both still handled by Core in separate match arms**, a duplication decision 25 was believed to have removed — finally collapse into one. Every new record shape gets the same both-languages wire pinning decision 36 introduced (a literal COBS frame in dev-bench's ztest suite and the identical pre-COBS body asserted here), because that pairing found a real discrepancy the first time it ran.

    **The bump is 7 → 8, not the 5 → 6 written here when this decision was made, 2026-08-25.** Both this decision and decision 40 were recorded against a v5 crate; decisions 42 and 43 were then implemented first and took v6 and v7 before either of these was code. Nothing about the substance moved — still one bump, still covering both decisions — only the arithmetic. Recorded rather than silently corrected, since "one bump per pass" is exactly the kind of rule a stale number quietly turns into two.

    **Three things this decision did not spell out, settled during implementation:**

    - **`StudyStart` gains `streams`, appended after `steps_crc`.** Four of the five sources are dev-bench-mediated, so dev-bench has to know which taps to open, which characteristic a `GattNotify` tap means, and which `id` each answers to. `validations` and `requires` still never cross this hop. Appended rather than inserted, the same discipline decision 42 used, so dev-bench's hand-written C decoder — which does not read taps yet — sees one unconsumed trailing byte instead of a re-shuffled sequence.
    - **`steps_crc` still seals `steps` alone**, so a study's taps ride outside the integrity seal. Widening the CRC would break its C-side implementation and both pinned test vectors for a property nothing has asked for yet; left as an open question (§7) rather than paid for on speculation. **Closed 2026-08-25 as a second seal rather than a widened one — see this decision's amendment below.**
    - **The retired triple's discriminants (2, 3, 4) are reused by the new one.** postcard encodes a serde enum by declaration index, so leaving holes would need placeholder variants existing only to be un-constructible. The `Hello`/`HelloAck` handshake refusing a version mismatch outright is what makes reuse safe — and no dev-bench firmware carrying the old shapes has ever been flashed, which is the same fact that made the whole reshape affordable.

    **The cost of doing this now, stated plainly.** It reverses a decision that is one day old (decision 36's own amendment above), re-bumps a schema that was just bumped, and edits dev-bench firmware that is code-complete and deployed to a live Core. The offsetting fact is the same one the proposal argued for itself: **no real byte has ever crossed the streaming path** — Milestone 4 (power) has never run, and Milestone 6's dev-bench firmware has not been flashed. Nothing here is load-bearing on a real bench yet, and that stops being true the moment either of those runs. This was the last cheap moment, and it was taken deliberately.

    **Amendment 2026-08-25, settling the two §7 gaps this implementation opened. Both land in Milestone 7 Phase B, in one schema bump.**

    **(a) `streams` gets its own seal: a second CRC, not a widened one.** A sibling `streams_crc` over `Study.streams`, computed by the same host-side path that already computes `steps_crc` and carried on `StudyStart` after `streams`, checked independently at both hops exactly as `steps_crc` is (decision 17). `steps_crc`'s own definition does not move, so nothing about the existing seal's meaning changes and dev-bench's hand-written C CRC keeps digesting the one contiguous span it already walks — the new seal is a second span it already walks too, plus one varint. **The widening alternative was rejected on a corrected fact, not on the one §7 recorded.** §7 said widening would "silently invalidate every saved study's sealed value." It would not: `embarch-api` recomputes and overwrites `steps_crc` on every submit (decision 26), so no stored value is ever trusted. The real cost of widening is structural — `steps_crc` sits *between* `steps` and `streams` on the wire, so the C side would have to digest two non-contiguous spans, or `StudyStart`'s field order would have to be reshuffled, which is a reshape where an append will do. Two seals also fail more usefully than one: a mismatch says which half is corrupt.

    **(b) `Step.power_sample` is retired; a `PowerFrontEnd` tap becomes the only way to author power capture.** This decision's own retire list omitted `PowerSampleWindow`, so Phase A left it alone rather than deciding by implementation order (§4.4). Settled against what the code does rather than what the types allow: **`power_sample` is already fully vestigial.** `embarch-core` never reads it — a power capture's rate comes from the tap's own `PowerFrontEnd { sample_hz }`; dev-bench's C encoder writes that `Option` byte as `None` unconditionally and its decoder reads-and-discards the field; and `study_builder::build_study`, the one authoring path there is, always emits `None`. Nothing consumes it anywhere, so retiring it deletes a second way of saying something only one way has ever said. Cost, in the same bump as (a): one field off `Step`, the C decoder loses an `Option`-byte read and the encoder a write (net-negative firmware, matching Phase B's own bar), both pinned `StudyStart` vectors regenerate, and two `embarch-api` CLI/MCP description strings that say "power_sample steps" get corrected to name the tap. Milestone 4, which has never run, then arrives to exactly one way to author a power capture instead of two.

    **Both ride the same still-open window, re-checked rather than assumed when they were settled.** Milestone 6's dev-bench firmware is still code-complete, deployed, and never flashed: `embarch-dev-bench`'s Phase A changes are uncommitted working-tree edits over commit `9515e0e`, and its newest build artifact predates them. That is the same fact that made the whole reshape affordable, and it is why both of these price at one bump rather than at a migration. Being dev-bench wire changes, they move **both** of the constants decision 12's amendment splits out. **The number is implementation's to fill in**, per this decision's own bump note above and [embarch-decision-reversals.md](../embarch-decision-reversals.md) row 18.

    **Implemented 2026-08-25** (Milestone 7 Phase B item 0). **The bump is 8 → 9**, one bump covering both halves, re-derived rather than copied — decisions 44/45's own reserved bump is still unshipped, so this pass took the number and 44/45 re-derive theirs, which is exactly the protocol row 18 asks for. `crc.rs` gained `streams_crc` beside `steps_crc` (same algorithm, same one-tap-at-a-time digest, its own `StreamTapTooLargeError`); `Study` gained `streams_crc` next to `steps_crc`; `StudyStart` gained it after `streams`; `Step.power_sample` and `PowerSampleWindow` are gone. The window was re-verified before any code was written: `embarch-dev-bench`'s Phase A edits are now committed (`d5dc6d8`) rather than uncommitted, but the newest `build-artifacts/` binary is still `zephyr-dc4cc07-current.bin` from six days earlier — **still never flashed**, so the price held.

    **Five things implementation settled that this amendment did not spell out. The first is a corrected cost, and it is the important one:**

    - **dev-bench's decoder did *not* already walk the `streams` span, and this pass is therefore net-positive firmware, not net-negative.** The expectation going in was that dev-bench gained "one varint read and one CRC call over a span its decoder already walks." It walks no such span: Phase A appended `streams` *after* `steps_crc` precisely so the C decoder could stop at `steps_crc` and see one unconsumed trailing byte, which is what it did. Checking the seal at the dev-bench hop therefore required teaching C to walk a `StreamTap` — a ~120-line `pc_skip_stream_tap` covering every `StreamSource`/`StreamEncoding`/`StreamScope` variant, since postcard carries no per-variant length. Measured on `native_sim`: **25,660 → 26,314 bytes of text, +654**, against the roughly two dozen bytes recovered from `power_sample` and the retired refs. **The decision stands as written** — a seal computed at one hop and taken on trust at the other is not "checked independently at both hops" — and the walker is not spent work either: Phase B item 3 has to decode taps anyway to open them, so this is that cost pulled forward, not added. What is wrong is only the estimate.
    - **`Study.streams_crc` is `#[serde(default)]`, and that default is *correct* rather than merely permissive.** Saved studies (decision 38) are JSON files deserialized straight back into `Study`, so a mandatory field would have made every one of them unloadable. It doesn't need to be mandatory the way `requires` does: a study authored before taps existed has no taps, and `0` is the genuine CRC-32/ISO-HDLC of zero bytes (init and xorout are both `0xFFFF_FFFF`, which cancel), not a sentinel. The same fact has a sharp edge on the test side — an empty tap list validates against a decoder that never computed the CRC at all — so the both-languages pin below deliberately carries three real taps.
    - **A Phase A leftover on the same wire, found while walking the C encoder against the Rust type: dev-bench was still writing two `Option` bytes for `StepResult`'s retired `power_samples_ref`/`waveform_ref`.** Decision 39 retired both fields at v8; the C encoder and decoder kept writing and skipping them, so every `StepResult` dev-bench sends carried two bytes Rust does not expect — on the message it sends most. Both suites stayed green because each agreed with itself: `StepResult` predates decision 36's both-languages rule, which applied to *new* records, so it was never pinned. Fixed here, and **`StepResult` is now pinned in both languages** so the gap cannot reopen. This is the second time that pairing has found a real discrepancy the first time it ran for a given record.
    - **The `BleAdvertise`-scoped FFI decode surface still checks `steps_crc` only.** `essd_study_decode_and_verify`'s single `out_crc_matches` bool, and `essd_study_decode_full`'s single `CrcMismatch` status, cannot say which of two seals failed — folding both in would quietly destroy the property the second seal exists to provide, and widening the C ABI would extend a surface §7 records as having no caller anywhere. Left as it is, with the reason written at the call site. The real Core<->dev-bench check is dev-bench's own C decoder, which computes both.
    - **dev-bench aborts the study on a `streams_crc` mismatch**, with its own log line naming which seal failed, even though this firmware does not open taps yet. Computing the seal and ignoring it would leave a study whose tap declarations arrived corrupt running to completion and reporting captures that are silently missing or wrong.

40. **A `Study` declares the dev-bench and DUT firmware versions it is meant to run against; whether to reflash before running is the operator's per-run choice, not a property of the study, 2026-08-25.** Prompted directly, and it closes a gap wider than the one it was raised for: **a `StudyResult` today cannot say what it ran against.** Two runs of the same study against two different firmware builds produce results that are indistinguishable after the fact — the same silent-mislabelling class that decision 39's manifest handling and decision 35's no-inference rule both exist to prevent, sitting unnoticed in the middle of the thing the whole suite produces.

    **`Study.requires: Requirements { dev_bench_version, firmware_version }`** — two free-form strings, matching the shape `HelloAck.firmware_version` already uses ([embarch-dev-bench/design.md](../embarch-dev-bench/design.md) §3 decision 18: whatever the build embeds, typically `git describe --always --dirty --abbrev=8`). **Host-side only — it never crosses the wire to dev-bench**, exactly as `validations` doesn't (§5.1): dev-bench has no use for a requirement it cannot check about itself, and `steps_crc` seals what dev-bench actually executes, which is unchanged.

    **Both fields are mandatory, and `any` is an explicit legal value.** "I don't care which build" is a real, legitimate answer — a dev-bench self-test involves no DUT at all — but it has to be *said*, not achieved by leaving a field out. Omitting either is a `POST /study` pre-flight validation failure (decision 18's existing shape), because the failure this decision exists to prevent is precisely the one where nobody thought about it.

    **Reflash is a run parameter, not a study field, and the split is the same one decision 39 already draws for signal routes.** A `Study` describes *what the experiment is*; how a particular run is set up to satisfy it is the operator's call at run time (`embarch-api/design.md` §3 decision 40). Baking it in would mean a saved study (decision 38) that reflashes a board every time you re-read its results.

    **On a mismatch with no reflash requested, the study is rejected before any step runs**, naming both strings — the same shape `doctor` check 13 already fails in. Not a warning that proceeds: a result attributed to the wrong firmware is worse than no result, which is the whole premise of this decision. An explicit override is available and is **recorded in the result** rather than silently honoured.

    **The verification asymmetry, which is the load-bearing limitation and cannot be designed away.** dev-bench *self-reports* its version over `HelloAck` — Core reads it, so a dev-bench requirement is genuinely **checked**. The DUT reports nothing at all: Core flashes it through a debug probe with no readback path. So a `firmware_version` requirement is only verifiable when either the outpost is compiled in (its header record carries a build ID, [embarch-outpost/design.md](../embarch-outpost/design.md) §3 decision 9) or **the run just flashed it**, which is what makes reflash the only way to actually *know* rather than assert. `StudyResult` therefore records not just the versions but **how each was established** — `ReportedByDevBench`, `ReportedByOutpost`, `FlashedThisRun`, or `Declared` (asserted, unverified). A result that quietly presented a declared string as a verified one would be the same defect in a new place.

    Folded into decision 39's single schema bump rather than taking its own: neither decision had shipped, and one bump per pass is the standing discipline. That bump landed as **7 → 8**, not the 5 → 6 written here — see decision 39 for why.

    **Implementation note 2 (2026-08-25, Milestone 7 Phase B item 2) — where the override and `FlashedThisRun` actually landed, since this decision created both without giving either a place to live.** `StudyResult` had no field for an override and `Provenance` had four; `VersionSource::FlashedThisRun` was a variant nothing could produce. Both are settled now, and the shape follows from this decision's own "run parameter, not a study field": **they cross `POST /study` as query parameters** — `?allow_version_mismatch=1` and `?flashed_firmware_version=<string>` — because a parameter of the *request* is literally a run parameter, and because that leaves the `Study` body byte-identical, so `steps_crc`/`streams_crc` and every fixture on disk are untouched. Query rather than a header, for the same reason the override is recorded rather than honoured silently: a query parameter shows up in Core's request log and in a `curl` an engineer types by hand.

    `Provenance` grew `overrides` (§4.5) to receive the first, at host schema v10. The second needed no new field: `firmware_version` carries what was flashed and `firmware_source` becomes `FlashedThisRun`. **A consequence this decision did not anticipate, and the most useful thing item 2 produced:** supplying the flashed version is also what makes `requires.firmware_version` *checkable*. The verification asymmetry below said a DUT requirement is verifiable "when the run just flashed it" — that sentence had no implementation anywhere, and now it is Core's gate rejecting a `409` on the DUT half, not only on the bench's.

    **What the flashed string is, stated because the asymmetry does not go away:** `embarch-api` derives it from the *tree it built*, via a project-declared `version_command` defaulting to `git describe --always --dirty --abbrev=8` — not from the board. Nothing reads a version back off a DUT. `FlashedThisRun` is therefore stronger than `Declared` (nobody checked that at all) and weaker than `ReportedByDevBench` (a measurement), which is exactly the ordering `VersionSource` exists to express.

    **Implementation note (2026-08-25):** `Requirements` is mandatory with no `serde` default, so an omitted `requires` fails to deserialize rather than quietly becoming `any`; a *blank* one is a separate, explicit `POST /study` pre-flight failure (`Requirements::validate`). `requirement_satisfied(required, actual)` lives in this crate so Core's version gate holds no second copy of the comparison rule. A test asserts the two halves of "host-side only" structurally rather than by inspection: two studies differing only in `requires` must encode byte-identical `StudyStart` messages and the same `steps_crc`.

    **The human surface landed 2026-08-26** ([embarch-ui/design.md](../embarch-ui/design.md) §3 decision 11, Milestone 7 Phase D), and it is the first thing that ever stated a real requirement: `embarch-ui`'s Study Designer had been submitting `Requirements::any()` unconditionally — honestly, since it had no fields to say anything else in. Both fields are now prefilled from live bench state, `any` is a visible checkbox rather than an empty field that happens to validate, and a blank field is **refused rather than quietly promoted to `any`**, which is the distinction this decision rests on. `requirement_satisfied` is what that tab calls to show a mismatch before the run, so no second copy of the comparison rule exists; `VersionSource::is_verified` is what decides whether a version renders as verified, so no UI re-derives which variants count. The reflash half of that decision is deliberately not built there — it is `embarch-api` orchestration — and is recorded as an open question rather than as a gap.

41. **A built-in table of vendor-defined GATT service identities — `vendor.rs`, 2026-08-25.** Decision 35's registry is per-firmware-repo and engineer-authored, because what a *custom* characteristic's bytes mean is knowledge only that repo's engineers have. A vendor-defined service is the opposite kind of fact: Nordic's UART Service has the same UUIDs on every device that implements it, published in Zephyr's own `nus.h`/`nus/inst.h`. Requiring every engineer to transcribe `6e400002-b5a3-f393-e0a9-e50e24dcca9e` into their own `study-actions.toml` to write to a service the stack itself defines is pure error surface, so those identities ship in this crate as constants: `VendorService`/`VendorCharacteristic`, `NORDIC_UART_SERVICE`, `vendor::ALL`, `vendor::find_characteristic`. Surfaced as `MergedAction::Vendor` (§4.3c) and authored as `RowAction::Vendor { service, characteristic, operation, payload }` — picked by **id** (`"nordic-uart"`, `"rx"`), never by typing a UUID.

    **Identity only. No semantics, ever.** This is decision 35's rule applied to a table that would be far more tempting to over-fill. The table records *where* to write (which service, which characteristic, and which operations the vendor declares there) and records nothing whatsoever about *what to write*: no command vocabulary, no line terminator, no "send `help` to list commands". Whatever sits behind a given DUT's NUS endpoint — a Zephyr shell, an application protocol, a bootloader, nothing at all — is that DUT's business and its engineers' knowledge, supplied per study as literal bytes exactly as `RowAction::Raw` already does. An entry is also **a conditional, not a claim**: *if* a device exposes this vendor service, these are its UUIDs. `Action::GattDiscover` against real hardware remains the only thing that answers "does this DUT actually have it?" — and this milestone's own run is why that distinction is written down rather than assumed, since the first DUT it was pointed at turned out not to expose NUS at all.

    `VendorCharacteristic::properties` is included because it is part of the vendor's own declaration and it decides whether a chosen operation is even legal — `build_study` refuses a `Write` against NUS TX (Notify-only) rather than letting it fail mid-study as an opaque ATT error. It remains the vendor's claim, not a measurement: `MergedAction::Vendor` carries a separate `discovered_properties`, and where the two disagree live discovery wins and the disagreement is itself the finding.

    **No schema bump.** A vendor row resolves into an ordinary `Action::DataExchange` carrying plain UUIDs before anything is encoded, so dev-bench firmware never learns the table exists — pinned by a test asserting a `Vendor` row and the equivalent `Raw` row build the byte-identical `Action`.

42. **`Step.delay_before_ms` — the "when" half of authoring a stimulus, 2026-08-25.** Steps run strictly in sequence, so until now the only expressible timing was "immediately after the previous step finished". That isn't enough to author a stimulus: letting a DUT settle after a connect, or waiting inside an open `GattMonitorStart` window before writing so the transcript visibly separates unsolicited traffic from the response to the write, both need a delay that isn't a side effect of some other step's `timeout_ms`. Requested directly — the Study Designer UI had no way for an engineer to say *when* a write happens, only what it contained.

    Deliberately **not folded into `timeout_ms`**: this is time spent before the action starts, so it doesn't consume the action's own budget, and `Outcome::TimedOut` keeps meaning "the action took too long" rather than "the delay was too long". It also **replaced a workaround** — the UI's prefilled capture template previously held the run open with a `GattMonitorAll` step, which re-subscribes inside an already-open window; a delay on the `GattMonitorStop` step does that job without a second action.

    Declared and encoded **last**, on purpose: postcard is field-order-sensitive with no field names on the wire and dev-bench hand-decodes `Step` in C, so appending gave that decoder one extra trailing varint read instead of a reshuffled sequence. `STUDY_DESIGNER_SCHEMA_VERSION` bumps 5 → 6 — appending is still a wire break in both directions, and the `Hello`/`HelloAck` handshake refusing the mismatch outright is the point. Covered by `steps_crc`, so the timing an engineer authored is inside the integrity seal.

43. **`Action::BleConnect.target_name` — naming the DUT instead of taking whichever advertises first, 2026-08-25.** `target_address: None` was documented as "the common case", on the assumption that a bench has one advertiser. It does not. Found live on the first real stimulate-and-capture run: consecutive runs of the *same* study connected to visibly different peripherals — one saw a GATT table with a `0x1910` service, the next an entirely different table carrying two Apple 128-bit services, neither of them the DUT — and every study then failed with `"service not found on DUT"`, which is true and completely misleading. The service wasn't on the device dev-bench happened to reach.

    `target_address` remains the precise filter but can't be authored ahead of time for a DUT advertising a resolvable private address, and nobody knows their DUT's MAC by heart. A name is what an engineer actually knows (`CONFIG_BT_DEVICE_NAME`). Both may be set; both must then match. Matched **exactly**, and against the advertised Local Name only — never the GAP Device Name characteristic (`0x2A00`), which would require connecting first, i.e. the very thing this exists to avoid. A blank/whitespace name means "no filter", not "match the empty name", so an untouched UI field can't become a filter nothing satisfies.

    A **failed** name match reports what *was* on the air (`"no name match; on air: 'GABRIEL', ..."`) rather than a bare `TimedOut`, because "nothing called X appeared, but these did" is the answer to the only question anyone asks at that point — and it immediately proved its worth: the DUT's real advertised name turned out not to be its configured `CONFIG_BT_DEVICE_NAME` at all. `STUDY_DESIGNER_SCHEMA_VERSION` bumps 6 → 7, same append-don't-insert discipline as v6.

44. **`Action::BleSecurity { level }` — elevating the link is a step an engineer authors, not something the stack is left to trigger by accident, 2026-08-25.** The DUT this milestone was built for **requires an encrypted, MITM-authenticated link (Zephyr `BT_SECURITY_L4`) before it will tolerate GATT service discovery**. That is the engineer's answer to a direct question, per decision 35's no-inference rule — not something read off behavior. And the level has to be *authorable*, not pinned to what one DUT happens to need: the same requirement stated as "L4 always" would be wrong for the next DUT.

    `BleSecurityLevel` is `L1`/`L2`/`L3`/`L4`, mapping one-to-one onto Zephyr's `BT_SECURITY_L1..L4` — no security, encrypted-unauthenticated, encrypted-authenticated, LE Secure Connections authenticated with a 128-bit key. A study says which one it needs; nothing in the suite defaults it, and `L1` is the honest way to say "this DUT needs none" rather than omitting the step and hoping.

    **Why its own `Action` rather than a `require_security` field on `BleConnect`** — considered, and rejected on the ambiguity it would preserve. A `BleSecurity` step gets its own `StepResult` row with its own `Outcome` and its own error text, so *"connected, then failed to pair"* is distinguishable from *"couldn't connect"* and from *"discovery failed"*. That distinction is not hypothetical: this milestone lost a session to a deterministic `"disconnected during service discovery"` (4 of 4 attempts) which is what a failed elevation looks like when nothing in the pipeline can name elevation as a thing that happens. A separate step also composes with `delay_before_ms` (decision 42), and lets a study elevate at a point of its own choosing, or not at all.

    Semantics: request at least `level` and wait for the link's security to actually change — or for the connection to drop — within the step's own `timeout_ms`. A link **already** at or above `level` is a `Pass`, not an error, since a peripheral that initiates its own elevation on connect (this DUT does, after a 200 ms delay of its own) can win the race. The **achieved** level is reported back, so a study that asked for L4 and got L2 fails loudly at the step that asked, instead of proceeding into a discovery the DUT will refuse.

    **What it deliberately does not carry:** a pairing method, a passkey, an IO capability, or anything about bonding. Same identity-only discipline decision 41 states for the vendor table — how dev-bench answers a pairing exchange is dev-bench's design ([embarch-dev-bench/design.md](../embarch-dev-bench/design.md) §3 decision 34), and whether a bond survives the run is decision 11 there. A study says *what security the link must reach*, and nothing about how.

    Appended after `GattMonitorStop` — postcard discriminant 7, decision 10's append-only rule, so an older `Step` decoder reads every preceding variant unchanged. The schema bumps once, covering this decision and decision 45 together, same discipline as v4/v5/v8 — **still prospective, and to be re-derived at implementation time**, per [embarch-decision-reversals.md](../embarch-decision-reversals.md) row 18: a bump number written into a design doc ahead of the work that performs it is a fact with a shelf life.

    **The 8 → 9 this decision originally reserved is now taken, and this is row 18's shape playing out as anticipated rather than as a surprise.** Decision 39's amendment shipped first, on 2026-08-25 (Milestone 7 Phase B item 0), and took v9. Whichever number this pass derives, it derives from what is implemented *then* — no number is written here. Note also that decision 12's amendment **split this constant in two** (a dev-bench wire version and a host type version), so "one bump" here means moving both, since `Action::BleSecurity` and `Study.gatt` are each dev-bench-visible: the first is a new `Action` dev-bench dispatches, and the second, though host-side only in its own right, arrives alongside it.

    **Implemented 2026-08-26, at wire v12 / host v14, and validated against the real DUT.** Discriminant 7 is what it got, as reserved. The bump was re-derived at implementation time exactly as this decision said to (v11 → v12), which is row 18's protocol working rather than a number being corrected. Three things the implementation had to settle that this decision did not name:

    - **Where the achieved level is reported.** This decision said "the achieved level is reported back" without saying where, and there was nowhere: `StepResult` had no field for it. It gets one — `security_level: Option<BleSecurityLevel>`, appended (§4.5) — and it is populated on **every** step, not only a security step. That is a strictly larger claim than this decision made, and it is the one that pays: `"disconnected during service discovery"` at L1 and the same failure at L4 are different findings, and until this field existed a result could not tell them apart. `None` means there was no connection to ask about, never that nobody looked.
    - **What "fails loudly" is, mechanically.** The step `Fail`s when the reached level is lower than asked. No separate "request it but don't insist" flag was added: `Step.continue_on_fail` (decision 13) is already exactly that knob, so a study that wants the attempt without the abort sets it. Adding a second one would have been two ways to say one thing.
    - **`L1` really is authorable, and the first implementation of this decision got that wrong.** It refused `L1` as "a level to report, not one to elevate to" — which reads sensibly and contradicts this decision's own text, where `L1` is *"the honest way to say 'this DUT needs none' rather than omitting the step and hoping"*. Corrected before commit; the refusal is gone from the builder, from the firmware, and from the UI's own dropdown, and an `L1` step is a `Pass` under the same already-at-or-above rule as every other level rather than by a special case. Recorded because the failure is instructive rather than because the fix was hard: **the design was already written and the implementation invented a stricter rule than the design asked for**, which is the same shape as ignoring it.

    **Hardware, 2026-08-26 — and it is this decision's own central claim that got confirmed.** Against `the client S11 B9C3`: `connect` `Pass` at L1, `BleSecurity { level: L4 }` `Pass` reporting **L4**, then `GattDiscover` `Pass` returning **7 services**. Discovery of that table had never once succeeded before this pass. Three runs of the same study, identical results. An `L1` step in the same study `Pass`es at L1, as above. dev-bench's own log names the pairing method that actually ran — `LE SC Numeric Comparison (authenticated)` — rather than leaving it inferred; see [embarch-dev-bench/design.md](../embarch-dev-bench/design.md) §3 decisions 34/37.

45. **A `Study` declares the GATT table it was authored against, and live discovery is what checks it — 2026-08-25.** Three sources of GATT knowledge exist in this crate, built at three different times, and **nothing ever joined them**: `vendor.rs`'s built-in vendor identities (decision 41), `gatt_extract.rs`'s static extraction from a firmware repo's own source (decision 33's `GattConfigExtractor`/`ZephyrBleDefExtractor`), and the engineer-authored registry (decision 35). A `Study` could reference any of them and declared none of them, so nothing could ever answer the question this milestone actually got stuck on — *is the service this study writes to even present on the build under test?* A whole session ran without that being answerable, because the DUT's GATT table had never once been seen.

    `Study.gatt: Option<DeclaredGatt>` — `{ source: GattSource, services: heapless::Vec<GattServiceInfo, {limits::MAX_DECLARED_SERVICES}> }`, reusing §4.3a's existing `GattServiceInfo`/`GattCharacteristicInfo` rather than a parallel shape, so a declaration and a live discovery result are literally the same type and comparing them is a comparison, not a translation. `GattSource` is `Vendor { ids }` (resolved from `vendor::ALL`), `Extracted { repo, revision }` (produced by `extract-gatt-config` against a real checkout, and recording *which* checkout), or `Authored` (typed in). Host-side only, like `validations` and `requires` — it never crosses the wire to dev-bench, which continues to interpret nothing (decision 39).

    **Live discovery wins, and the difference is reported rather than tolerated.** `vendor.rs`'s own module doc already states this rule for the vendor half — a build that modifies a service disagrees with the vendor's declaration, and the measurement is the truth. Generalised here: when a `GattDiscover`/`GattMonitorStart` step runs in a study that declared a table, Core reconciles the two and records what was declared-but-absent, present-but-undeclared, or present with different properties. A declared service missing from the DUT is not a study failure by default — it is the single most useful line in the result, and it is exactly the fact ("`CONFIG_BT_ZEPHYR_NUS=y` was set, but was the service actually registered?") that nobody could produce for a whole session.

    This is the durable form of decision 35's rule. That decision said engineer-supplied knowledge must come from the engineer; this one says **where in the study it goes**, so an agent authoring a study has a field to put it in rather than a temptation to infer it.

46. **`Study.steps` is a heap `Vec` on the host and stays `heapless::Vec<Step, MAX_STEPS_PER_STUDY>` on the no_std dev-bench build, 2026-08-25 — the actual fix for the stack overflow this doc has tracked since 2026-08-18.** `Step`'s largest `Action` variant carries a 512-byte payload, and a `heapless::Vec<Step, 64>` is a 64-slot inline array *regardless of how many steps are populated* — roughly 38 KB of value moved on the stack every time a `Study` is passed around, for a real 2-step self-test study. That is what genuinely crashed a debug `embarch-api` serving a live `study_status` call over MCP.

    The mitigation shipped for it — decision 36's dedicated 512 MiB-stack runtime thread — works, and is why a release build survives. But it is a workaround standing between the suite and a crash, sized against today's code and optimization level rather than against the type. Behind a `std`/`alloc` feature the field becomes `alloc::vec::Vec<Step>` and the 38 KB value collapses to a pointer; the `no_std` FFI build for dev-bench keeps the fixed-capacity form it needs. The crate already feature-gates for `ffi`, so this is an established pattern here, not a new one.

    **No schema bump.** `Vec` and `heapless::Vec` serialize identically under both postcard and serde_json — a length prefix followed by elements — so nothing observable crosses either hop differently, and neither constant moves. Worth stating explicitly because "the type changed" reads like a wire change and is not one.

    Two alternatives declined. `heapless::Vec<Box<Step>, 64>` shrinks the container but adds an allocation per step and still needs the same feature gate to be shareable with `no_std`, so it pays the gate's cost without the simplification. And shrinking `MAX_STEPS_PER_STUDY` from 64 to 16 — the cheapest possible change — was declined because it reduces a real authoring limit to serve an implementation detail, at exactly the moment studies are getting longer: Milestone 6's are already four steps and growing, and dev-bench's own unilateral shrink to 16 is a cautionary tale in this same pass ([embarch-dev-bench/design.md](../embarch-dev-bench/design.md) §3 decision 35).

    **`MAX_STEPS_PER_STUDY` becomes a single authority again** once dev-bench's own span decode lands: today `DBM_MAX_STEPS_PER_STUDY` is 16 here and this constant is 64, so a 20-step study is accepted by every host-side check and rejected on the wire. That divergence is dev-bench decision 35's to close; this decision is why the host side no longer has a reason to shrink to meet it.

47. **`HelloAck` gains dev-bench's own `hardware_id`; `DEV_BENCH_WIRE_SCHEMA_VERSION` 9 → 10 and `HOST_TYPE_SCHEMA_VERSION` 11 → 12, 2026-08-25.** *(Written as 10 → 11; decision 48 landed first and took the host constant to 11, so this one re-derives to 12 — [embarch-decision-reversals.md](../embarch-decision-reversals.md) row 18's protocol working as intended, the same way decisions 44/45's reserved 8 → 9 had to be re-derived earlier.)* The wire half of [embarch-core/design.md](../embarch-core/design.md) §3 decision 35 and the answer to [embarch-topology/design.md](../embarch-topology/design.md) §5's UART-and-JTAG-are-different-USB-devices gap, which that doc has correctly described as needing a firmware protocol change it could not make unilaterally.

    One field on the handshake frame that already carries `schema_version` and `firmware_version`, both of which Core already checks at exactly this moment — so the comparison lands in an existing gate rather than adding one. Dev-bench reads its own chip ID and reports it; Core compares against the identity `hardware::validate_role` just verified over JTAG and refuses the link on a mismatch.

    Both constants move, per decision 12's own rule: the wire constant because a message dev-bench encodes changed shape, and the host constant because its triggers are a strict superset of the wire constant's and `schema_version.rs`'s compile-time assertion refuses to let it trail. Decision 36's both-languages pinning applies in full — this is a new field on a record that crosses that wire, which is precisely the case the rule exists for.

    **Implemented 2026-08-25.** `MAX_HARDWARE_ID_LEN = 32` (double the 16 chars both of this suite's JTAG reads produce — `hwinfo`'s length is a per-SoC driver decision, not something this crate gets to fix), the field appended to `HelloAck` after `firmware_version`, and both constants moved. Decision 36's pinning was applied as promised, and the interesting part is that **`HelloAck` had never been pinned at all** — like `StepResult`, it predates that rule. So `WIRE_HELLO_ACK` here and `test_hello_ack_encodes_to_the_pinned_wire_bytes` in dev-bench's ztest suite now hold the same 30 bytes from both sides. They agreed on the first run.

    **An empty `hardware_id` is a real value, not an absent field**, and both sides test it: a board whose Zephyr build has no `hwinfo` driver reports `""`, which still writes its length prefix and leaves the frame walkable. Core's own comparison is where "no ID" acquires meaning — the encoder's job is only to carry it faithfully.

48. **Post-hoc validation is removed outright, 2026-08-25 — the whole notion, not a field.** `Study.validations`, `StudyResult.validations`, `PostHocValidation`, `PostHocCheck`, `ExpectedValue`, `SignalCheck`, `ValidationSource`, `DataChannel`, `ContentValidity`, `ValidationResult`, `signal.rs`'s evaluation logic and the `core-validation` Cargo feature are all gone. Decision 19's post-hoc half and decision 28 are retired with it; decision 19's real-time `Outcome` half is untouched and is what every study has always actually used.

    **It was never once used.** That is the decision, and everything else is detail. `embarch-core`'s `events.json` writer wrote a hardcoded `"validations":[]` — not "empty because this run had none", but a literal string in the source, because Core never evaluated a validation in its life. Decision 28's `validate_on_abort` field was designed and never added to `Study` at all. The `SignalCheck` variant set was described in its own §7 bullet as an "illustrative placeholder", and its `FftPeakNear` was implemented as a naive O(n²) DFT against synthetic signals, because no real signal has ever reached it. The one thing that would have made any of it real — power and sensor hardware producing data worth checking — was deferred to the Later bucket earlier the same day ([embarch-roadmap.md](../embarch-roadmap.md), Milestone 4).

    **What it cost to keep, measured.** `ExpectedValue` inlines two `MAX_PAYLOAD_LEN` buffers, so `PostHocValidation` is 576 bytes; times `MAX_VALIDATIONS_PER_STUDY = 64` gives a **36,872-byte inline array** in `Study`. After §3 decision 46 fixed `steps` — the field that actually crashed a debug `embarch-api` — `validations` was **97% of what remained**. `Study` was 77,368 bytes at the start of this pass, 37,960 after decision 46, and is **1,088 bytes** now. Decision 46 got a 2× reduction; removing this got a further 35×.

    **Host-type schema 10 → 11, and `DEV_BENCH_WIRE_SCHEMA_VERSION` untouched at 9.** None of this ever crossed the dev-bench wire (§3 decision 17 said so from the start, and it held), so dev-bench needs no reflash and its C decoder needed no change — only three stale comments. This is the second bump to move the host constant alone, and the cleanest evidence yet for decision 12's split: under the old single constant, deleting a type dev-bench cannot observe would have charged a firmware reflash. A removal is exactly as breaking as an addition on the api⟷Core hop, which is why it bumps at all.

    **Not "deferred", and not left as a stub.** The alternative on the table was to keep the types and stop growing them. Declined: a subsystem that is fully typed, partly implemented, wired into two repos' call sites, and has never run is worse than no subsystem — it reads as a feature to everyone who meets it, and it was already misleading readers. `embarch-api`'s own MCP tool description advertised `validations` in the study schema to every agent that ever called `run_study`. If post-hoc checks are wanted when real captured data exists to check, they should be designed against that data — which is exactly what §7 said about the `SignalCheck` variant set all along.

    **Done on a branch**, unlike the rest of this pass, at the repo owner's explicit direction — [embarch-dev-workflow.md](../embarch-dev-workflow.md) §6's standing carve-out for "real, risky, or exploratory work", not an exception to the no-branches rule.

49. **Decision 46's newtype is generalised to `Bounded<T, N>` and applied to the result types — because `steps` was neither the worst instance nor the one that crashed the release build, 2026-08-25.** Decision 46 fixed `Study.steps` and stopped there, on the reasoning that it was the field that had actually crashed something. Measuring the rest immediately afterwards showed how narrow that was:

    | Type | Before | After |
    |---|---:|---:|
    | `StudyResult` | 1,293,608 | 9,024 |
    | `StepResult` | 20,200 | 696 |
    | `DevBenchMessage` | 20,208 | 2,128 |

    `StudyResult.steps` was a 64-slot inline array of 20 KB `StepResult`s — **1.29 MB**, in a type Core assembles and `embarch-api` deserializes. And `StepResult` was 20 KB because `gatt_activity` inlined 32 × 536-byte records and `gatt_services` 8 × 296, whether or not the step captured any. Three fields, the same defect as `steps`, none of them touched by decision 46.

    **This is the one that matters most, and decision 46 did not address it at all.** `embarch-core`'s `build_runtime` sets a 64 MiB thread stack, and its own comment records why: the first real `run_study` POST crashed the **release** Windows service with `STATUS_STACK_OVERFLOW` on `spawn_blocking(run_study_to_completion)` — a `StudyResult` path, not a `Study` one. Decision 46's fix could not have prevented that crash. This one addresses its actual cause.

    `StepList` becomes `pub type StepList = Bounded<Step, MAX_STEPS_PER_STUDY>`, so decision 46's call sites are unchanged. `captured_data` is deliberately **left alone**: at 528 bytes it is 0.5% of the old `StepResult` and would have touched dozens of byte-level `from_slice`/`extend_from_slice` call sites for no meaningful gain — the cut is where the inline arrays are big, not everywhere they exist.

    **Still no schema bump, and now asserted for more than one element type.** Decision 46 pinned this with a test comparing postcard bytes against the `heapless` shape for `Step`; decision 49 applies the newtype to three fields with different element types, so the property is re-asserted generically. Better still, `gatt_services`' existing round-trip test now encodes from a `Bounded` and decodes into a plain `heapless::Vec` — which is precisely the host-encodes/dev-bench-decodes case in miniature, and the first test in this crate to prove the two shapes agree rather than assert it in prose.

    **The `no_std` shape is asserted too, in the opposite direction.** A test requires `size_of::<StepResult>() > 4096` without `alloc`, so that "make it smaller" can never be applied to the one build that has no allocator to make it smaller with.

50. **`Action::BleUnbond {}` — dropping the bond is a step, because "pair, do work, drop the bond, pair again" is a real test — 2026-08-26.** Decision 44 gave a study a way to *reach* a security level. It gave it no way to get back, and [embarch-dev-bench/design.md](../embarch-dev-bench/design.md) §3 decision 11 clears bonds only between studies. So the only way to author a second pairing exchange was to end the study, which is not the same experiment: a bond re-established inside one run exercises the reconnect path, and a bond re-established across two runs exercises the bench's reset.

    Field-less, appended at postcard discriminant 8 alongside decision 44's variant, one wire bump for the pair — `BleUnbond` is only reachable once something can establish a bond, so shipping decision 44 alone would have shipped half a feature at two reflashes' cost.

    **It drops the link, and that is stated rather than mitigated.** Zephyr's `bt_unpair` disconnects a peer whose keys it clears. dev-bench does not choose that and does not work around it: a link whose keys just went away is not a link. So a study that unbonds mid-run needs its own `BleConnect` afterwards — which is what "pair again" meant. `StepResult.security_level` is `None` for the step, correctly: by the time it returns there is no connection to ask about.

    **Why an action rather than a lifecycle setting**, having considered the alternative: the same argument decision 44 makes for its own variant. A step gets its own `Outcome` row, composes with `delay_before_ms`, and lets the author choose the moment. A `clear_bonds_between_steps` flag on `Study` could not express "here, and not there".

    The companion half — bonds cleared at *study end* rather than only on the next `Hello` — is dev-bench's, not this crate's: [embarch-dev-bench/design.md](../embarch-dev-bench/design.md) §3 decision 37.

## 4. Concrete data model

Field-level, resolving milestone-3.md §3.1: concrete enough that a `#[derive(Serialize, Deserialize)]` Rust translation is mechanical — exact byte/UUID representations (`[u8; 16]` vs. a `uuid`-crate newtype, `no_std`-compatible either way) are implementation detail, not a design choice left open here. Every `Vec<T>`/`String` below is `heapless::Vec<T, N>`/`heapless::String<N>`, not `alloc`-based — §3 decision 15's `limits` module defines each `N`.

### 4.1 `Study`

- `name: heapless::String<{limits::MAX_STUDY_NAME_LEN}>` — human-readable identifier; not required to be unique (uniqueness, if ever needed, is an `embarch-api`-level concern per §6, not enforced by the type itself).
- `requires: Requirements { dev_bench_version, firmware_version }` (§3 decision 40) — the builds this study is meant to run against, both mandatory, `any` a legal explicit value. Host-side only; never sent to dev-bench, like `validations`. No `#[serde(default)]`, deliberately: an omitted `requires` fails to deserialize rather than defaulting to `any`, which is what makes "it has to be *said*" true rather than aspirational.
- `streams: heapless::Vec<StreamTap, {limits::MAX_STREAMS_PER_STUDY}>` (§3 decision 39, §4.8) — the study's declared capture channels. `#[serde(default)]`, unlike `requires`: a saved study (§3 decision 38) authored before taps existed captured nothing, and still does. **Does** cross the wire to dev-bench, unlike `validations`/`requires` — and, since §3 decision 39's 2026-08-25 amendment (implemented 2026-08-25, schema v9), is sealed by its own `streams_crc`, a sibling of `steps_crc` rather than a widening of it.
- `gatt: Option<DeclaredGatt>` (§3 decision 45) — the GATT table this study was authored against, and where it came from (`GattSource::Vendor`/`Extracted`/`Authored`). `#[serde(default)]` — a study authored before this existed declares nothing, which is what those studies did. Host-side only, like `validations`/`requires`: never sent to dev-bench. Reconciled by Core against a `GattDiscover`/`GattMonitorStart` step's live result, with the live table winning and the difference reported.
- `steps: heapless::Vec<Step, {limits::MAX_STEPS_PER_STUDY}>` — run in order. A `Study` is entirely static once submitted for v1: no parameter-range/generator construct (see the fuzzing note below).
- `steps_crc: u32` / `streams_crc: u32` (§3 decision 17, and decision 39's 2026-08-25 amendment) — two sibling integrity seals, each over the one contiguous span it names, each checked independently at both hops so a mismatch says **which half** is corrupt. Both are recomputed and overwritten by whoever submits (`embarch-api/design.md` §3 decision 26), so neither stored value is ever trusted. `streams_crc` is `#[serde(default)]` where `steps_crc` isn't: a saved study (§3 decision 38) authored before taps existed has no taps, and `0` is the genuine CRC of zero bytes rather than a sentinel — so the defaulted value is the *right* value, which is not something `requires`' own missing-field case could ever have said.

### 4.2 `Step`

- `name: heapless::String<{limits::MAX_NAME_LEN}>` — label surfaced in results (`StepResult.step_name`, §4.5), so a `Study` author and whoever reads results can correlate them without relying on array index.
- `action: Action` (§4.3) — the one thing this step does.
- `timeout_ms: u32` — max wall-clock time dev-bench allows this step before reporting `Outcome::TimedOut` rather than letting a stalled BLE connect/advertise hang the whole `Study`.
- ~~`power_sample: Option<PowerSampleWindow>` (§4.4)~~ — **retired by §3 decision 39's 2026-08-25 amendment; removed the same day** (Milestone 7 Phase B item 0, schema v9). It described an optional overlapping power measurement bounded by the step's own start/end; a `StreamSource::PowerFrontEnd { sample_hz }` tap scoped to that step range (§4.8) says the same thing, and was already the only one of the two anything read. See §4.4.
- `delay_before_ms: u32` — how long dev-bench waits *before* starting this step's action (§3 decision 40). `#[serde(default)]`, so a `Step` authored before it existed loads as 0 — start immediately, which is exactly what those studies did. Not deducted from `timeout_ms`, which still bounds only the action itself.
- `continue_on_fail: bool` — when this step's `Outcome` (§4.5) is `Fail` or `TimedOut`: `false` (the default) aborts the `Study` immediately, running no further steps; `true` continues to the next step regardless. Defaults to `false` since most steps in the automated-testing use case (§1) are prerequisites for what follows — a failed `BleConnect` makes every later `DataExchange` step moot. An author sets it `true` only on a step where continuing past that step's own failure is actually useful (e.g. a `DataExchange` step in a fuzzing run whose response content doesn't itself gate the rest of the sequence, or a purely diagnostic step). Governs only the device-observed `Outcome`, not the separate Core-side post-hoc content-validity check, which dev-bench can't act on in real time regardless of this flag. §3 decision 13.

### 4.3 `Action`

Three variants, matching §1's motivating categories (stimulus/interaction plus measurement — content validation is now handled entirely post-hoc by Core, §3 decision 19, not as a fourth on-device `Action`):

- **`BleAdvertise { local_name: Option<heapless::String<{limits::MAX_LOCAL_NAME_LEN}>>, service_uuids: heapless::Vec<Uuid, {limits::MAX_SERVICE_UUIDS}>, adv_interval_ms: u16 }`** — dev-bench advertises as a BLE peripheral for the DUT to discover.
- **`BleConnect { role: BleRole, target_address: Option<BleAddress>, target_name: Option<heapless::String<{limits::MAX_LOCAL_NAME_LEN}>> }`** — `target_name` (§3 decision 41) connects only to an advertiser whose advertised Local Name equals it exactly; `None`/blank means no name filter. Set alongside `target_address` and both must match. **`target_address: None` *and* `target_name: None` together mean "whichever connectable peripheral advertises first", which on any bench with another BLE device in range is a coin toss** — decision 41 has the live evidence. `BleRole` is `Central` or `Peripheral` (which side dev-bench plays for this step); `target_address` is `None` for "accept/connect to whichever DUT shows up first" (the common case — a `Study` author usually doesn't hardcode the DUT's BLE address) or `Some(addr)` to require a specific one. **`BleAddress`'s 6 raw bytes are display order, most-significant byte first** (`AA:BB:CC:DD:EE:FF`) — stated explicitly here as of 2026-08-15 (closing item 47 of that day's design-improvement review), matching `Uuid`'s already-documented big-endian convention and `embarch-dev-bench`'s `ble_bridge_real.c`, which has always assumed this order and reverses on the way into Zephyr's little-endian `bt_addr_le_t` (`embarch-dev-bench/design.md` §4). Previously this crate said only "6 raw address bytes" with no order specified — a real risk, since a wrong guess means a `BleConnect` with an explicit `target_address` silently never matches.
- **`DataExchange { service_uuid: Uuid, characteristic_uuid: Uuid, operation: GattOperation }`** — UUIDs are raw, not symbolic (per your call — no separate name-resolution table to maintain). `GattOperation` is `Read`, `Write { payload: heapless::Vec<u8, {limits::MAX_PAYLOAD_LEN}> }`, `Notify { timeout_ms: u32 }` (wait for a notification, bounded independently of the step's own `timeout_ms` since a notify-wait is often shorter than the step's overall budget), `Indicate { timeout_ms: u32 }` (same wait-for-a-pushed-value shape as `Notify`, but over BLE's acknowledged indication mechanism rather than best-effort notification — the ATT-level confirmation round-trip is the GATT stack's job, not something this type models), or `Subscribe` (enable notifications/indications without waiting for one, e.g. to arm a later step's `Notify`/`Indicate`). **`StreamCapture` was a sixth variant and is retired by §3 decision 39**: a continuous capture of what a characteristic streams is now a declared `StreamSource::GattNotify` tap (§4.8), not a per-step action kind. It was removed outright rather than kept as a dead trailing variant — the schema break is already paid for, and an authorable action nothing dispatches is the silently-captures-nothing failure decision 36 was opened by.
- **`GattDiscover {}`** (§3 decision 31, Milestone 3) — no fields: walks the connected DUT's entire GATT table (every primary service, every characteristic, each characteristic's raw ATT properties byte) rather than requiring a caller to already know a `service_uuid`/`characteristic_uuid` pair. Reports its result in `StepResult.gatt_services` (§4.3a, §4.5); doesn't subscribe or capture anything itself.
- **`GattMonitorStart {}`** (§3 decision 36) — no fields: runs the same discovery-and-subscribe-to-everything walk as `GattMonitorAll`, then returns immediately, **leaving every subscription armed so the capture window outlives this step**. Every step that runs afterwards — a `DataExchange` write stimulating the DUT above all — has its GATT traffic recorded into the streamed transcript (§4.3b) until a `GattMonitorStop` closes the window. This is the one action that makes "stimulate the DUT and capture what comes back" expressible at all: steps run strictly in sequence, and `GattMonitorAll` tears its own subscriptions down when its step ends, so a write step and a `GattMonitorAll` step can never overlap. Reports `gatt_services` in its own `StepResult`; `gatt_activity` is necessarily empty this early.
- **`GattMonitorStop {}`** (§3 decision 36) — no fields: closes the window a preceding `GattMonitorStart` opened, unsubscribing everything it armed and reporting the window's `gatt_services` plus its capped inline `gatt_activity`. A `GattMonitorStop` with no open window is a no-op `Pass`, not a `Fail`, and a study that ends without one has its window closed implicitly by dev-bench's own dispatch loop — so neither a forgotten `Stop` nor a mid-study abort can leave subscriptions armed into the next study.
- **`BleSecurity { level: BleSecurityLevel }`** (§3 decision 44, implemented 2026-08-26 at wire v12) — requests elevation of the current connection to at least `level` and waits for the link's security to actually change, or for the connection to drop, within this step's `timeout_ms`. `BleSecurityLevel` is `L1`/`L2`/`L3`/`L4`, one-to-one with Zephyr's `BT_SECURITY_L1..L4`. **`L1` is authorable and means "this DUT needs no security", said out loud** — the same distinction `REQUIREMENT_ANY` draws for `requires`, and not a value the builder refuses. A link already at or above `level` is a `Pass` — a peripheral that initiates its own elevation on connect can win the race, and this DUT does — and so is a procedure that was *already in flight* when the step started, which is the case real hardware actually produced ([embarch-dev-bench/design.md](../embarch-dev-bench/design.md) §3 decision 37). The **achieved** level is reported in `StepResult.security_level` (§4.5), so asking for L4 and getting L2 fails at the step that asked rather than at the discovery that follows; `Step.continue_on_fail` is how a study asks for the attempt without the abort. Carries no passkey, no IO capability, and nothing about bonding: those are dev-bench's (§3 decisions 11/34/37 there), not the study's.
- **`BleUnbond {}`** (§3 decision 50) — no fields: clears dev-bench's bonding table *inside* the study, so "pair, do work, drop the bond, pair again" is authorable. **Disconnects**, because Zephyr's `bt_unpair` disconnects a peer whose keys it clears — a study that unbonds mid-run needs its own `BleConnect` afterwards. Its own `StepResult.security_level` is `None`: by the time it returns there is no link to report a level for.
- **`GattMonitorAll {}`** (§3 decision 32, Milestone 3) — no fields: runs the same discovery as `GattDiscover` internally, subscribes to every characteristic whose properties include Notify or Indicate, and captures everything that arrives until the step's `timeout_ms` expires. Reports both `gatt_services` and `gatt_activity` (§4.3a, §4.5) — self-sufficient, doesn't depend on a preceding `GattDiscover` step's result.

A step's own `Outcome` (§4.5) is the only on-device validation signal — did the action (including a `DataExchange`'s `GattOperation`, or `GattDiscover`/`GattMonitorAll` themselves) complete without a protocol-level error or timeout. Whether the *content* it produced was actually correct is a separate question, answered later and only by Core (§3 decision 19, §4.6) — the original `Validate` `Action` that used to ask that question on-device has been removed (§3 decision 22).

### 4.3a GATT discovery types (§3 decisions 31/32/33)

- **`GattCharacteristicInfo { uuid: Uuid, properties: u8 }`** — `properties` is the raw ATT characteristic-properties byte (bit 0 = broadcast, 1 = read, 2 = write-without-response, 3 = write, 4 = notify, 5 = indicate, 6 = authenticated-signed-writes, 7 = extended-properties, per the Bluetooth Core Spec's own characteristic-declaration encoding) — passed through unchanged from what the ATT discovery response returned, not re-encoded into a crate-invented bitflag enum, matching this crate's existing "raw, not symbolic" stance on UUIDs (§4.3).
- **`GattServiceInfo { uuid: Uuid, characteristics: heapless::Vec<GattCharacteristicInfo, {limits::MAX_CHARS_PER_SERVICE}> }`** — one primary service and its characteristics, in discovery order.
- **`GattActivityRecord { rx_utc_ms: u64, characteristic_index: u16, payload: heapless::Vec<u8, {limits::MAX_PAYLOAD_LEN}> }`** — one captured notification/indication from `GattMonitorAll`. `characteristic_index` indexes into that same step's `gatt_services`, flattened in service-then-characteristic order (service 0's characteristics first, then service 1's, and so on) — not a repeated 16-byte UUID per record. `rx_utc_ms` is dev-bench's own capture-time timestamp, same convention as `Sample.rx_utc_ms` (§4.7).
- Both a live `GattDiscover`/`GattMonitorAll` result and a static extraction (§3 decision 33) produce `heapless::Vec<GattServiceInfo, {limits::MAX_DISCOVERED_SERVICES}>` — the same shape, so the two are directly comparable rather than needing separate diffing logic.

### 4.3b GATT transcript types (§3 decision 36)

The **exhaustive**, streamed record — as opposed to §4.3a's `GattActivityRecord`, which is the capped, per-step, inbound-only summary that lives inline in `events.json`. Both survive deliberately; see decision 36 for why, and for why a reader comparing their counts will correctly see different numbers.

- **`GattDirection`** — `Out` (dev-bench → DUT), `In` (DUT → dev-bench), or `Local` (a dev-bench-side event that isn't an ATT PDU in either direction — discovery starting, a subscription being armed).
- **`GattEventKind`** — `Connected`, `Disconnected`, `DiscoveryStarted`, `ServiceDiscovered`, `CharacteristicDiscovered`, `Subscribed`, `Unsubscribed`, `WriteRequest`, `WriteResponse`, `ReadRequest`, `ReadResponse`, `Notification`, `Indication`, `Error`. Append-only, same discipline as `DevBenchMessage` (§3 decision 10).
- **`GattTranscriptEntry { rx_utc_ms: u64, direction: GattDirection, kind: GattEventKind, service_uuid: Option<Uuid>, characteristic_uuid: Option<Uuid>, att_status: u8, payload: heapless::Vec<u8, {limits::MAX_PAYLOAD_LEN}> }`** — one line of the transcript. UUIDs are carried in full rather than as a `characteristic_index` into a step's `gatt_services` (the compression `GattActivityRecord` uses), because a transcript spans steps — including steps that ran no discovery at all — so there is no single flattened table an index could mean anything against. `att_status` is the raw ATT error code, `0` when there was none; for a `CharacteristicDiscovered` entry it carries the raw ATT properties byte instead, documented here rather than adding a field used by one event kind. `rx_utc_ms` is dev-bench's own capture-time clock, inheriting the same unresolved clock-resync gap §7 already tracks for `Sample.rx_utc_ms` — Core's own `core_rx_utc_ms` column (§5.2) is the wall-clock anchor until that closes.
- **`GattTranscriptEntry::csv_header()`/`to_csv_row(step_index, step_name)`** — this crate's own transcript-CSV renderer (§5.2), so column knowledge lives here and nowhere else, same split `Sample::to_csv_row` established. The payload appears **twice by design**: `payload_hex` is the exact bytes, and `payload_ascii` renders printable bytes as themselves and everything else as `.`, so a shell/NUS transcript is directly readable without decoding hex by hand while nothing is lost for a binary protocol. Returns `None` — dropped and logged, never truncated — if a row wouldn't fit `MAX_GATT_CSV_ROW_LEN`, or if a step name contains a character that would break the CSV shape.

### 4.3c Table-authoring types (§3 decisions 34/37)

Authoring-side only (`study-ui` feature, `std`), never on the wire: `TableRow { name, action: RowAction, timeout_ms, continue_on_fail }`, where `RowAction` is `BuiltIn { which: BuiltInActionKind, role }`, `Registered { name, field_choices }`, or — added by decision 37 — **`Raw { service_uuid: String, characteristic_uuid: String, operation: RegisteredOperation, payload: Vec<u8> }`**, a one-off `DataExchange` against a UUID pair typed directly with a payload supplied as literal bytes. `build_study` resolves all three into real `Action`s; `Uuid::parse` (decision 37) accepts the hyphenated form, 32 bare hex digits, or a 16-bit shorthand expanded against the Bluetooth SIG Base UUID.

### 4.4 `PowerSampleWindow` — retired

**Retired by §3 decision 39's 2026-08-25 amendment; removed 2026-08-25** (Milestone 7 Phase B item 0, schema v9). It carried one field, `sample_rate_hz: u32`, naming dev-bench's power-sampling rate for a step-bounded window. A `StreamSource::PowerFrontEnd { sample_hz }` tap with a `StreamScope::Steps { from, to }` covering the same step (§4.8) expresses exactly that, and is the only one of the two anything ever read.

**Retired on evidence, not on symmetry.** Nothing consumed this field: `embarch-core` takes a power capture's rate from the tap; dev-bench's C encoder wrote its `Option` byte as `None` unconditionally and its decoder read-and-discarded it; `study_builder::build_study` always emitted `None`. Removal was one field off `Step` in the same bump as `streams_crc`, priced while Milestone 6's firmware was still unflashed — re-verified before the work rather than assumed. Milestone 4 (which has never run) is the first study that would author a power capture, and finds one way to do it rather than two.

### 4.5 `StudyResult` / `StepResult`

- **`StudyResult.provenance: Provenance { dev_bench_version, firmware_version, dev_bench_source, firmware_source, overrides }`** (§3 decision 40) — what the study actually ran against, **how each version was established**, and **which requirements, if any, it was allowed past rather than satisfying**. The source is `ReportedByDevBench` / `ReportedByOutpost` / `FlashedThisRun` / `Declared`, and it is not bookkeeping — a `Declared` DUT version is an assertion nobody checked, and a result that rendered it identically to a verified one would reintroduce exactly the mislabelling this decision exists to close. **Written by Core since 2026-08-25.** The bench is always `ReportedByDevBench`: Core reads it off the live `HelloAck`. `ReportedByOutpost` still waits on outpost firmware existing.

  **`FlashedThisRun` became reachable 2026-08-25 (Milestone 7 Phase B item 2), and not by Core learning to do anything new.** It remains structurally impossible for Core to produce on its own — `POST /flash` and `POST /study` are separate calls with nothing linking them, by design — so the process that sequenced both is the one that says so: `embarch-api` passes `?flashed_firmware_version=<string>` on `POST /study`, out of band of the `Study` body because §3 decision 40 settles that reflash is a run parameter and not a study field. Absent it, the DUT's version stays `Declared` and is compared against nothing, exactly as before. Present, it is *also* what makes `requires.firmware_version` checkable for the first time — the DUT half of Core's gate has no other way to fire.

  **The string it carries describes the tree that was built, not the image that is running**, and that limit is stated rather than papered over: `embarch-api` derives it by running a project-declared `version_command` (defaulting to the suite's own `git describe --always --dirty --abbrev=8`) in the project's checkout, and nothing in this suite can read a version back off a DUT to confirm the build embedded it. `FlashedThisRun` therefore means "this run put the build of this tree on the board" — strictly stronger than `Declared`, which nobody checked at all, and strictly weaker than `ReportedByDevBench`, which is a measurement.

- **`Provenance.overrides: heapless::Vec<VersionOverride, {limits::MAX_VERSION_OVERRIDES}>`** (§3 decision 40, added 2026-08-25 at host schema v10) — one entry per version requirement this run was allowed to proceed past, empty in the normal case. `VersionOverride { subject: VersionSubject, required, actual }`, where `VersionSubject` is `DevBench` or `Firmware` — the two fields `Requirements` has, so the capacity is the arity of the thing rather than a capacity guess.

  **A record, not a flag, because neither string is recoverable from the rest of a `StudyResult`.** `Study.requires` never travels into the result, and the *actual* version is only in the sibling field when the override is the reason that field is there at all. A bare `overridden: bool` would say a rule was bent without saying which one or by how far — the same half-answer `VersionSource::Declared` exists to stop this type giving. `#[serde(default)]`, so an `events.json` written before the field existed still reads back, truthfully, as not overridden: those runs predate any way to override anything.


- **`StudyResult { study_name, steps, validations, provenance, streams }`** — `streams: heapless::Vec<StreamRef, {limits::MAX_STREAMS_PER_STUDY}>` (§3 decision 39, §4.8) is one entry per declared tap: its name, the bytes written, and whether it was truncated. `provenance` is the §4.5 entry above. — the aggregate outcome, same shape whether read by `embarch-core`, `embarch-api`, or a human reading the result file directly (§5.2). `steps` is not guaranteed to be the same length as the submitted `Study.steps`: if some step's `continue_on_fail` is `false` (the default, §4.2) and that step's `Outcome` is `Fail`/`TimedOut`, execution aborts and `steps` is a proper prefix ending at that step, rather than always covering every submitted step. `validations` (§3 decision 19, §4.6) is populated only once the study reaches `"completed"` status — it stays empty on any `"failed"` outcome, even for steps that did capture data before the abort.
- **`StepResult { step_name: heapless::String<{limits::MAX_NAME_LEN}>, outcome: Outcome, captured_data: Option<heapless::Vec<u8, {limits::MAX_PAYLOAD_LEN}>>, gatt_services: Option<heapless::Vec<GattServiceInfo, {limits::MAX_DISCOVERED_SERVICES}>>, gatt_activity: Option<heapless::Vec<GattActivityRecord, {limits::MAX_GATT_ACTIVITY_RECORDS}>>, security_level: Option<BleSecurityLevel> }`** — `Outcome` is `Pass`, `Fail { reason: heapless::String<{limits::MAX_FAIL_REASON_LEN}> }`, or `TimedOut`. `step_name` is a denormalized copy of the corresponding `Step.name`, carried purely for human readability when reading `events.json` directly (§5.2) — it is not used for machine correlation (§3 decision 14 uses `Study.steps` array position for that, via `ValidationSource.step_index`, and `StudyResult.steps`' own position tracks the same index since steps run and are appended in order). `captured_data` holds whatever bytes a `DataExchange` read/notify step pulled off the DUT (unused for other action kinds). **`power_samples_ref` and `waveform_ref` were here and are retired by §3 decision 39**: a capture belongs to the study's declared taps, not to one step, so what a run captured is reported once as `StudyResult.streams` — which is the thing neither per-step field could ever have filled in correctly for a tap whose scope outlives a single step. `gatt_services`/`gatt_activity` (§3 decisions 31/32, §4.3a) are populated by `GattDiscover` (`gatt_services` only) and `GattMonitorAll` (both) — landing inline in `events.json` like `captured_data` rather than as a CSV-file reference, since both are bounded and small enough to stay JSON-friendly (unlike the high-rate power/waveform channels). `security_level` (§3 decision 44, added 2026-08-26 at wire v12) is the BLE security level the link was sitting at when the step finished — **populated for every step, not only a `BleSecurity` one**, which is a deliberately larger claim than decision 44 made and the one that pays for itself: a `"disconnected during service discovery"` at L1 and the same failure at L4 are different findings, and nothing in a result could distinguish them before this existed. `None` means there was no connection to ask about, never that nobody looked; `#[serde(default)]`, so a `StudyResult` written before the field existed reads back truthfully as having recorded no level.

**Fuzzing, explicitly not modeled here (resolved):** §1's fuzz-testing use case is served by treating a `Study` as the *output* of fuzzing, not by adding a parameter-range/generator type to these types themselves — "generate many concrete `Study` values externally (with varied `Step` parameters), submit each one" is a caller-side (`embarch-api`, or a human/agent driving it) concern. This keeps `Study`/`Step` themselves simple and keeps the fuzzing strategy free to evolve independently of the wire types.

### 4.6 Post-hoc validation types — retired

**Retired and removed 2026-08-25** (§3 decision 48, host schema v11). `Study.validations`, `StudyResult.validations`, `PostHocValidation`, `ValidationSource`, `DataChannel`, `PostHocCheck`, `ExpectedValue`, `SignalCheck`, `ContentValidity` and `ValidationResult` are all gone, along with `signal.rs`'s evaluation logic and the `core-validation` Cargo feature. See decision 48 for the reasoning and for what the removal actually cost.

**The measurement that made this section worth removing rather than fixing:** `PostHocValidation` was 576 bytes (two `MAX_PAYLOAD_LEN` byte buffers inside `ExpectedValue`), and `MAX_VALIDATIONS_PER_STUDY` was 64, so `Study.validations` alone was a **36,872-byte inline array** — 97% of `Study` even after §3 decision 46 fixed `steps`. `Study` is now **1,088 bytes**, down from 77,368 before this pass began.

### 4.7 `Sample` (streamed power/waveform data, §3 decisions 2/11/20)

- **`Sample { rx_utc_ms: u64, value: f32, unit: Unit, channel_id: u8 }`** — **no longer a wire type as of §3 decision 39.** The wire carries arrival-stamped bytes (`StreamRecord`, §4.8); a `Sample` is what `streams::samples_in` produces from those bytes against a tap's declared `StreamEncoding::Samples { layout, unit, channel_id }`. Every `Samples`-encoded tap's rendered CSV (§5.2) shares this identical row shape rather than each inventing its own columns, and **that row shape is untouched by the reshape** — only the path the numbers take to reach it changed. (It was `data.csv` and `waveform.csv`, two fixed files chosen per channel; since 2026-08-25 it is `streams/<tap name>.csv`, one per declared tap — `embarch-core/design.md` §3 decision 30(b).) `rx_utc_ms` is stamped by dev-bench itself, at the moment it captures/receives the sample from its own sampling hardware — its own local clock, seeded and periodically resynced from Core's `host_utc_ms` on every `Hello` (§3 decision 12) — not assigned by Core on arrival, so the timestamp reflects when the sample was actually taken rather than when it happened to reach Core over a variable-latency serial link. `unit`/`channel_id` (§3 decision 27) name what `value` actually measures and, for a capture with more than one concurrent stream, which one — both are placeholder-but-concrete pending real dev-bench sampling hardware (§7); appending further fields later is a version-bumped wire change like any other (§3 decision 12). `unit`/`channel_id` are declared once per tap now, on `StreamEncoding::Samples`, rather than repeated per wire message — the same "neither changes mid-capture" reasoning the retired per-batch fields used, moved to where the rest of a capture's declared meaning already lives.
- **`Sample::to_csv_row(&self, step_name: &str) -> Option<heapless::String<{limits::MAX_CSV_ROW_LEN}>>`** and **`Sample::csv_header() -> &'static str`** — the crate's own CSV-rendering tools (§1, §3 decision 2). Core's job writing a `Samples` tap's rendered CSV reduces to: run each `StreamRecord` through `streams::samples_in` (which owns the element width/byte-order decode), call `to_csv_row` for each `Sample` with the name of whichever step is open, and append the returned row plus Core's own `core_rx_utc_ms` (§3 decision 30) — column knowledge lives only in this crate, never duplicated in Core. Row shape: `rx_utc_ms,step_name,value,unit,channel_id`, with `core_rx_utc_ms` appended by Core itself rather than by this helper (§3 decision 30 — it's Core's own receipt time, not part of the wire type). Returns `None` if `step_name` doesn't fit alongside the rest of the row within `MAX_CSV_ROW_LEN` — Core is expected to log and skip that one row rather than truncate it silently, since a truncated CSV row is a worse failure mode than a dropped one.

### 4.8 Stream taps (§3 decision 39)

**Implemented 2026-08-25** (`src/streams.rs`, Milestone 7 Phase A). Field-level below; anything the decision left open and implementation had to settle is marked as such.

- **`StreamTap { id: u8, name, source: StreamSource, encoding: StreamEncoding, scope: StreamScope }`** — `id` is the wire handle (its own index in `Study.streams`); `name` names the output file under `streams/`, the post-hoc validation source (literally, as of §3 decision 19's 2026-08-25 amendment — a stream-fed `ValidationSource` carries this name), and nothing else. `dev-bench` is a **reserved** name, rejected by `POST /study`'s pre-flight validation (§3 decision 18), since it belongs to the reserved `DevBenchLog` tap.
- **`StreamSource`** — `GattNotify { service_uuid, characteristic_uuid }`, `PowerFrontEnd { sample_hz }`, `GattTranscript`, `DevBenchLog`, `Signal { name }`. The first four are dev-bench-mediated (`StreamSource::is_dev_bench_mediated`); `Signal` is read by Core itself, with the carrier resolved live by [embarch-topology](../embarch-topology/design.md) §3 decision 18 — Core opens a local serial port for a `Route::Direct` signal, or receives relayed bytes for a `Route::ViaDevBench` one, and the tap is identical either way.
- **`StreamEncoding`** — `Raw`, `Text`, `Samples { layout, unit, channel_id }`, `GattTranscript`, `OutpostTrace`. This is the **only** place a byte payload acquires a meaning, it is always engineer-declared, and no component ever guesses one — §3 decision 35's rule, applied to the read direction.
- **`SampleLayout`** (settled during implementation; the decision named `layout` without defining it) — `F32Le`/`F32Be`/`I16Le`/`I16Be`/`U16Le`/`U16Be`. **Element width, type, and byte order only: no scaling, no offset, no unit conversion.** Those would be a claim about what a particular DUT's bytes *mean*, which is its engineers' knowledge and not this crate's; `unit` names the quantity, nothing here transforms the number. Append-only.
- **`StreamScope`** — `WholeStudy` or `Steps { from, to }`, both indices **inclusive** (a single-step window is `from == to`). The outpost uses `WholeStudy`; a power window uses the step range it belongs to. `StreamScope::covers(step_index)` is the crate-side predicate.
- **Wire records: `StreamOpen { id }`, `StreamChunkBatch { id, records }`, `StreamClose { id, dropped }`**, where a record is `StreamRecord { rx_utc_ms: u64, bytes }` — arrival-stamped bytes, never decoded values. `dropped` is carried on close, so a stream that lost data says so rather than presenting a shorter, plausible capture as complete. Neither open nor close carries a `step_index`: when a tap opens is a property of its declared `scope`, not of the wire.
- **`StudyStart` carries the study's `streams`** (settled during implementation, appended after `steps_crc` — see §3 decision 39's implementation note for why), **followed by `streams_crc`**. The seal gap that appending left is closed by a second CRC rather than a widened one (§3 decision 39's 2026-08-25 amendment, implemented 2026-08-25 at schema v9): a sibling `streams_crc` over `streams`, carried after it so each seal immediately follows the one contiguous span it covers, checked independently at both hops. `steps_crc`'s own definition did not move. dev-bench walks the taps to locate that span (`pc_skip_stream_tap`) without storing them — opening them for real is Phase B item 3 — and aborts the study on a mismatch, naming which seal failed.
- **`StudyResult.streams: heapless::Vec<StreamRef, ..>`** — per tap: `StreamRef { name, bytes_written, truncated }`. Replaces `StepResult`'s `power_samples_ref`/`waveform_ref`. **Actually written by Core since 2026-08-25** (`embarch-core/design.md` §3 decision 30's implementation note), with three things settled there rather than here: an entry exists for **every** declared tap, including one that produced nothing (`bytes_written: 0`) — a missing entry and an empty one are different facts; `bytes_written` counts every raw byte the run wrote, including bytes a retention rotation later deleted, with `truncated` saying the file no longer holds all of them; and `truncated` covers both losses a reader cares about equally — a rotation that dropped a segment, and a `StreamClose` reporting a non-zero `dropped`.

  **`StreamRef` deliberately did *not* grow a `note` field on 2026-08-26, and the reasoning is worth keeping.** Milestone 7 Phase D needed to distinguish an outpost trace that had a manifest applied from one that did not, and this type was the obvious place to put the reason — it is already per-tap and already in the result. It was rejected: `StreamRef` rides inside `StudyResult`, which crosses the dev-bench wire, so growing it is a **host schema bump** for a fact that is produced by Core *after* dev-bench has finished and is meaningless to it. Core exposes its own `streams/index.json` over a new route instead ([embarch-core/design.md](../embarch-core/design.md) §3 decision 30(c)'s amendment). `truncated` stays the one thing this type says about incompleteness, and it says it about the *capture*, which is dev-bench's business.
- **`dev_bench_log_tap(&declared)`** (added 2026-08-25, Milestone 7 Phase B item 3) — builds the reserved `DevBenchLog` tap, the one tap a `Study` may not author. **Its `id` is `declared.len()`**, which is free by construction: a declared tap's `id` is its own index, so the first index past the end can never collide with one — and that single rule is what lets both ends agree on the handle without either sending it. Encoding `Text`, scope `WholeStudy`. **Where its bytes come from changed in implementation, and the change is recorded rather than absorbed:** this section originally had *dev-bench* opening the tap and sending `StreamOpen`/`StreamChunkBatch`/`StreamClose` for its own log. What shipped is Core synthesizing the tap and rendering into it the `LogLine` frames it already receives — strictly less firmware, less link traffic and less SRAM on a board at 98.5% of `sram0_0_seg`, to move bytes that were crossing the link anyway. The asymmetry the tap exists to close is closed either way. See [embarch-decision-reversals.md](../embarch-decision-reversals.md) row 36.
- **`validate_taps(&streams, step_count)`** — `POST /study`'s pre-flight rules, computed here rather than in Core so there is no second copy to drift: `id` must equal its own index; no blank, reserved, or duplicated name; no step range that is inverted or out of bounds. That last one exists because both failures produce a capture that is **silently empty**, which is the failure decisions 34 and 36 were each opened by.
- **`samples_in(record, layout, unit, channel_id, sample_hz)`** — the crate-side decode for a `Samples` tap, so Core holds no column or layout knowledge of its own. With a declared rate (a `PowerFrontEnd` tap has one), element *i* is stamped `rx_utc_ms + i * 1000 / sample_hz`; **with no declared rate, every sample carries the record's own arrival stamp unchanged**, rather than an interpolation nobody stated the basis for. A trailing partial element is dropped, never zero-padded into a plausible wrong value.

**What a `GattTranscript`-encoded record actually contains** (settled during implementation): one postcard-encoded `GattTranscriptEntry` (§4.3b), unchanged. The entry keeps its own `rx_utc_ms` alongside the record's — the same value from the same clock — rather than having it removed, so the row shape decision 36 pinned stays byte-for-byte what it was. The `step_index` column comes from whichever step the host has open when the record arrives, which is exactly what decision 36 defined that field to mean; the generic record carries no step of its own.

## 5. Relationship to embarch-core

This is a real scope expansion for Core, not a small addition. Today, Core's stated purpose is deliberately narrow: it "owns the debug probe (flash/reset) and the serial console log" for the DUT and "has no idea the EmbArch API or Claude Code exist" beyond its bearer-token-authed endpoints (`embarch-core/design.md` §1). Bridging study commands to `embarch-dev-bench` over a second serial link is a new hardware relationship for Core — a second physical connection, a second wire format (binary, not Core's existing JSON-only endpoint bodies), and new endpoints beyond the DUT-facing `/status`, `/flash`, `/reset`, `/serial-log`. The first piece of that relationship now exists: `GET /dev-bench/port` (`embarch-core/design.md` §4, §5) identifies which serial port dev-bench is on. It opens nothing and speaks no `DevBenchMessage` — every part of the hop described below is still unimplemented.

§5.1/§5.2 below now specify those endpoints and the result storage they populate — resolving what was milestone-3 follow-up work. `embarch-core/design.md` itself has been updated to match (new endpoint rows, §2 architecture diagram, module layout) per `DOC-PROTOCOL.md` §5, ahead of any actual implementation — the same "recorded ahead of code" pattern `embarch-api/design.md` §3.10 used for its CLI decision.

| `GET` | `/study/{study_id}/waveform-data` — **an alias since 2026-08-25** | — | Raw CSV bytes (`Content-Type: text/csv`, §5.2), the sensor-waveform capture (§3 decision 21) — same shape/rationale as `/power-data` above; `404` if the study captured no waveform data. |

- **One study in flight at a time**, enforced by a dedicated lock separate from Core's existing `hw_lock` (`embarch-core/design.md` §3 decision 4) — dev-bench is a second, independent physical connection, so a running study doesn't need to block a concurrent `/flash`/`/reset` against the debug probe, but two overlapping studies would both be trying to drive the one dev-bench. A `POST /study` received while another is still running is rejected outright with `409 Conflict` (body includes the in-flight `study_id`), not queued — matching the suite's minimal-viable posture (no queueing machinery exists anywhere else in Core); the caller re-submits after polling the in-flight study's `GET /study/{id}` to completion.
- **No cancel endpoint for v1** — deferred deliberately, matching the suite's existing "don't build a capability nothing yet needs" pattern (`embarch-api/design.md` §12's CLI-exit-code-granularity precedent). A stuck study still bounds itself via each `Step`'s own `timeout_ms` (§4.2).
- **Job retention**: completed/failed job status and results stay in Core's in-memory registry until Core restarts — no expiry, matching the suite's existing no-cleanup-until-restart posture (single shared token, no config hot-reload, `embarch-api/design.md` §12). The on-disk result files (§5.2) outlive the in-memory registry entry regardless. A Core restart while a study is in flight loses that study's registry entry entirely — a subsequent poll 404s, per §3 decision 16.
- **Incremental result writes.** Unlike the in-memory job registry above, everything under `streams/` (§5.2) is appended to as records arrive during the study (§3 decision 20, §4.8), not written once at the end — so raw capture data can outlive a Core crash that writes off the study itself as `"failed"` (§3 decision 16), even though `events.json` and any post-hoc `validations` (§3 decision 19) never get written for that study at all.

### 5.2 Result storage (§3 decision 11)

Per completed (or failed) study, Core writes to a results directory under its own local data directory — same machine-wide-local-data convention `token_store.rs` already establishes for `EMBARCH_TOKEN` (`embarch-core/design.md` §8) — at `study_results/<study_id>/`:

- **`events.json`** — the `StudyResult` (§4.5) verbatim: per-step pass/fail, captured BLE data, `validations` (§3 decision 19) once they've run, and — since 2026-08-25, when they were first actually written rather than merely present in the type — `provenance` (§4.5, §3 decision 40) and `streams` (§4.8). Small and human-readable; this is what `GET /study/{id}` (§5.1) returns inline once `status` is `"completed"`. Written only once, after the study reaches a terminal status *and*, for a `"completed"` study, after Core's post-hoc validation pass has finished — unlike everything under `streams/` below, which is written incrementally throughout. Core streams it to disk one `StepResult` at a time and never materializes a whole `StudyResult` host-side (§7's ~1.3 MB finding, `embarch-core/design.md` §3 decision 24); `provenance` and `streams` are both small and bounded, so both are serialized directly at the end without breaking that discipline.

- **`streams/`** — one file per declared tap, named by the tap (`embarch-core/design.md` §3 decision 30(b), implemented 2026-08-25). **This replaces the fixed `data.csv`/`waveform.csv`/`gatt.csv` paths as *paths* while keeping every one of their row shapes** — only the path the numbers take to reach a row changed. Everything here is written incrementally as bytes arrive, so a study that failed part-way still has the capture that led up to the failure, which is exactly what is wanted when something went wrong.

  **A tap always writes its raw bytes before any decode is attempted.** A decode that fails then costs a rendering, not a capture. Files, by the tap's *declared* `StreamEncoding` (§4.8) and never by anything inferred from the bytes:

  | Declared encoding | Raw file | Rendered file | Row shape |
  |---|---|---|---|
  | `Raw` | `<tap>.bin` | *(none — nobody declared a meaning)* | — |
  | `Text` | `<tap>.txt` | *(none — the decode is the identity, so the raw file already is the rendering)* | — |
  | `Samples { .. }` | `<tap>.bin` | `<tap>.csv` | `rx_utc_ms,step_name,value,unit,channel_id,core_rx_utc_ms` — `Sample::csv_header()` (§4.7) plus the one column Core appends |
  | `GattTranscript` | `<tap>.bin` | `<tap>.csv` | `rx_utc_ms,step_index,step_name,direction,kind,service_uuid,characteristic_uuid,att_status,payload_len,payload_hex,payload_ascii,core_rx_utc_ms` — `GattTranscriptEntry::csv_header()` (§4.3b) plus the same one |
  | `OutpostTrace` | `<tap>.bin`, plus `<tap>.arrival.csv` | `<tap>.trace.csv` | `frame_index,frame_seq,rx_utc_ms,kind,a,b,name` — [`outpost`]'s own row shape, rendered post-hoc from the complete raw file once the capture closes. **`rx_utc_ms` here is Core's own receipt time for the *frame* that carried the record**, joined on from `<tap>.arrival.csv`, because an outpost record carries no timestamp of its own at all ([embarch-outpost/design.md](../embarch-outpost/design.md) §3 decisions 4, 17, 18) — so consecutive rows repeating one value is the normal case. Written **even when no manifest applies** (with `name` empty) and **even when no arrival stamps apply** (with `rx_utc_ms` empty); `streams/index.json` carries `named`, `timed` and a note saying which. What is refused is applying the *wrong* manifest, or the *wrong* stamps (`embarch-core/design.md` §3 decision 30(c)) |

  Core's job for a rendered row stays purely mechanical and unchanged by the move: run each `StreamRecord` through `streams::samples_in` (§4.8) or `postcard`-decode it as a `GattTranscriptEntry`, call the crate's own `to_csv_row` with the name of whichever step is open, and append its own `core_rx_utc_ms` (§3 decision 30 there) — Core holds no independent knowledge of what the columns mean or how many there are beyond that one addition. `rx_utc_ms` is the capturing node's own timestamp (§4.7), not a Core-assigned arrival time; `core_rx_utc_ms` is that Core-assigned arrival time, recorded alongside for post-hoc drift correction rather than in place of it. `value`'s real-world meaning is named by `unit` (§3 decision 27) but its exact hardware mapping is still open (§7) — the column *shape* is locked, its *content* isn't. A `Sample` or entry whose `step_index` is out of range is still written, with an empty `step_name`, rather than dropped: it is real data that happened, and losing it because Core couldn't label it would be the worse trade.

  Two more files live here, both Core's own rather than this crate's: **`index.json`**, one entry per declared tap mapping its name to its files, its encoding, and which of the three retired fixed routes it answers — the thing that lets `GET /study/{id}/stream/{name}` and those three aliases resolve from a handler holding no `Study`; and **`<tap>.1.<ext>`**, the previous segment of a file that has rotated under `EMBARCH_STREAM_MAX_BYTES`. See `embarch-core/design.md` §3 decision 30 for both, and for why a rotation that *deletes* a segment is what sets `StreamRef.truncated` (§4.8).

**`data.csv`, `waveform.csv` and `gatt.csv` were here**, at fixed paths, chosen per-channel. All three are retired by the above; results captured before 2026-08-25 still hold them, and Core's three alias routes still read them for exactly those (`embarch-core/design.md` §4).

## 6. Relationship to embarch-api

Once `embarch-study-designer` has code behind it and Core exposes the study-bridging endpoints (§5.1), `embarch-api` is expected to grow a matching MCP tool surface and CLI subcommand surface, mirroring the existing `build`/`flash`/`build_and_flash`/`reset`/`serial_log` pattern (`embarch-api/design.md` §5, §5a). Because study execution is async (§3 decision 9), the shape is two calls rather than one, mirroring Core's own two-endpoint split rather than trying to fake synchronicity by blocking `embarch-api` itself until the study finishes (which would just move the "how long do we wait" problem up one layer without resolving it). This keeps faith with §3 decision 6: any hardware-facing capability reachable by an agent must be equally reachable by a human with no agent in front of them, converging on the same `embarch-study-designer` types and the same orchestration code — not two independent implementations.

**Locked-in tool/subcommand surface** — implemented 2026-08-18 (Milestone 2, Dev Bench Self-Test); naming/param shapes below match exactly what shipped, see `embarch-api/design.md` §5/§5a for the real implementation detail:

| Name (MCP tool = CLI subcommand) | Params | Behavior |
|---|---|---|
| `run_study` | MCP: `study` (`serde_json::Value`, not a typed `Study` schema — this crate doesn't derive `schemars::JsonSchema` on `Study`, so `rmcp`'s `#[tool]` param struct can't use it directly; deserialized into `Study` inside the handler, with a clear schema-mismatch error on failure, same practical effect as a typed param). CLI: `--study-file <path>` (a JSON file matching the same schema — `Study`'s nesting makes per-field CLI flags impractical, unlike `build`/`flash`'s scalar args). | Calls Core `POST /study` (§5.1) and returns `{ study_id }` immediately. No `project` param — unlike `build`/`flash`, a study isn't tied to one of `embarch-api`'s configured projects; it targets whatever DUT is connected through Core's one dev-bench serial link. Recomputes/overwrites `steps_crc` via this crate's own `steps_crc()` before ever calling Core (decision 26). A `400` from Core (failed pre-flight validation or CRC check, §3 decisions 17/18) surfaces as an immediate MCP/CLI error with no `study_id` at all — distinct from `study_status` later reporting `"failed"` for a study that was accepted but failed during or after execution. |
| `study_status` | `study_id` (both MCP and CLI). | Calls Core `GET /study/{study_id}` (§5.1) and returns its status/`current_step`/`total_steps`/`result`/`reason` shape verbatim. |
| `study_power_data` | `study_id` (both MCP and CLI). | Calls Core `GET /study/{study_id}/power-data` (§5.1) and returns the raw CSV bytes (as MCP tool content, or written to stdout/a `--out <path>` file for the CLI). Named 2026-08-15, closing item 44 of the design-improvement review — previously left as "a small remaining item" with no name at all. |
| `study_gatt_data` | `study_id` (both MCP and CLI). | Calls Core `GET /study/{study_id}/gatt-data` (§5.1) and returns the raw CSV bytes, same shape as `study_power_data`. Added 2026-08-25 alongside §3 decision 36 — the exhaustive transcript, as opposed to `study_status`'s capped per-step `gatt_activity`. |
| `study_waveform_data` | `study_id` (both MCP and CLI). | Same shape as `study_power_data`, calling `GET /study/{study_id}/waveform-data` instead. Named alongside `study_power_data` for the same reason — no rationale to name one and not the other. |

No convenience "block until done" wrapper (a `run_study`-side analogue of `build_and_flash`'s bundling) for v1 — deferred deliberately, matching the suite's existing minimal-viable posture (`embarch-api/design.md` §12's CLI-exit-code-granularity precedent, `design.md` §5.1's "no cancel endpoint for v1"): a study's total runtime is far less predictable than a build's, so a blocking wrapper would need its own timeout policy layered on top of Core's per-`Step` `timeout_ms` (§4.2) for no clear benefit yet. Revisit if a real caller finds the two-call poll loop genuinely burdensome.

## 7. Open questions / future work

- ~~**`steps_crc` seals `steps`, but a study's `streams` now also cross the wire outside that seal**~~ — **resolved and implemented 2026-08-25** (§3 decision 39's amendment, schema v9, Milestone 7 Phase B item 0). A sibling `streams_crc`, not a widening of `steps_crc`. One correction worth keeping on record, since it is what decided it: this bullet used to argue a widening would "silently invalidate every saved study's sealed value." It would not — `embarch-api` recomputes and overwrites `steps_crc` on every submit (§3 decision 26), so no stored value is ever trusted. The real objection to widening is structural: `steps_crc` sits *between* `steps` and `streams` on the wire, so the C side would have to digest two non-contiguous spans or `StudyStart`'s fields would have to be reshuffled. A second correction, this one found by implementing it: the C decoder did **not** already walk the `streams` span, so the dev-bench half cost a full `StreamTap` walker (+654 bytes of `native_sim` text) rather than the varint-and-a-CRC-call it was priced at — see decision 39's amendment for the full account.
- ~~**`Step.power_sample` and a `StreamSource::PowerFrontEnd { sample_hz }` tap now overlap**~~ — **resolved and implemented 2026-08-25** (§3 decision 39's amendment, §4.4, schema v9). `power_sample` is retired and the tap is the only authoring path. Settled on evidence rather than on preference: `power_sample` was already fully vestigial — `embarch-core` never read it, dev-bench's C encoder always wrote `None` and its decoder read-and-discarded it, and `study_builder::build_study` always emitted `None`. Milestone 4 therefore arrives to one way to author a power capture, not two.
- ~~**Whether a `ValidationSource` should name a tap rather than a `DataChannel`**~~ — **resolved and implemented 2026-08-25** (§3 decision 19's amendment, §4.6). It should, for stream-fed data, with no `step_index`; `DataChannel` narrows to the two genuinely per-step channels, and `ValidationResult` carries the whole source rather than a flattened `step_index`/`channel` pair. More live than this bullet realised when it was written: Phase B replaces the three fixed CSV files those variants named, so leaving them would have left three variants pointing at files nothing writes. Settling it surfaced a second thing, now its own decision — the schema constant that would have charged this to dev-bench guards two hops with different exposure, and **split in two** (§3 decision 12's amendment, implemented the same day as `DEV_BENCH_WIRE_SCHEMA_VERSION`/`HOST_TYPE_SCHEMA_VERSION`, both at 9). This reshape moved only the host one, which is the split's first concrete payoff.

- **The physical `embarch-dev-bench` design itself** (what BLE radio hardware, what power-sampling hardware, connector/form factor) stays entirely out of scope here, and **as of 2026-08-25 is deferred with power profiling as a whole** — the user's call in that day's suite-wide design pass: Milestone 4 (Power-Sampling Study) moves out of the near sequence into the Later bucket and no front-end hardware gets ordered ([embarch-roadmap.md](../embarch-roadmap.md)). `data.csv`'s (§5.2) exact power-sample columns depend on this and stay unresolved with it. This is now a deferral with a named trigger — power profiling resuming — rather than an open question waiting on someone to answer it.
- ~~**nRF54 cross-compilation toolchain and build-system wiring for the FFI staticlib.**~~ — **resolved 2026-08-18** (`embarch-dev-bench/design.md` §3 decision 8, Milestone 2): the crate cross-compiles cleanly for the nRF54L15's Cortex-M33 core via `cargo rustc --release --target thumbv8m.main-none-eabi --features ffi --lib --crate-type staticlib`, invoked automatically from `embarch-dev-bench/app/CMakeLists.txt` as part of a plain `west build` — one build command, as decision 8 there always intended, just via a direct path-based `cargo` invocation rather than formal west-manifest module plumbing (see that decision's own text for why). The panic-handler gap this bullet used to track is closed: a `#[panic_handler]` now exists in `src/ffi.rs`, gated to `target_os = "none"` specifically so it doesn't fire (and conflict with libstd's own) on `cargo test --features ffi`'s host-target build. **One real gotcha found closing this, worth keeping on record:** the target triple must be the *soft*-float variant, `thumbv8m.main-none-eabi`, not `-eabihf` — this firmware's Zephyr build has no hardware-FPU ABI enabled, and a hard-float-ABI staticlib fails to link against it ("uses VFP register arguments") the moment any code path touches an `f32` (not just this crate's actual FFI-exposed function signatures, none of which pass a float — `Sample`'s own field is enough to trigger it internally). Confirmed producing a real, flashable `zephyr.hex` for the nRF54L15DK. **Narrower item, resolved 2026-08-20 as "correctly left as-is," not extended:** the FFI decode surface (`essd_study_decode_full`, `src/ffi.rs`) that hands a decoded `Study` back to C as a fixed-layout struct is still scoped to `Action::BleAdvertise` steps only (dev-bench's own decision 21) — `embarch-dev-bench/milestone-9.md` §3.1 had named extending it to the other four action kinds as Milestone 3's own scope, but implementing that milestone found the premise wrong: this surface decodes a postcard-encoded `Study` (name + steps + validations + steps_crc), not the `DevBenchMessage::StudyStart` (steps + steps_crc only) dev-bench actually receives over the wire — `study_ffi.h`'s own doc comment already said so, and `main.c`'s real dispatch has never called it (it decodes `StudyStart` directly via `serial_protocol.c`'s own hand-written decoder instead). Extending this surface would have been real, tested work with no caller to exercise it. Left exactly as it was — `Action::BleAdvertise`-scoped, validated-but-unused infrastructure for a future caller that does have a real `Study` blob to decode — per `embarch-dev-bench/design.md` decision 27's own correction; the actual wire-decode extension needed (and got) is `embarch-dev-bench`'s own `serial_protocol.h`/`.c`.
- ~~**A real stack-overflow risk in `Study`/`Step` deserialization.**~~ — **resolved 2026-08-25 (§3 decision 46): the type is fixed, not just the stack.** `Study.steps` becomes a heap `Vec<Step>` on the host behind an `alloc` feature and stays `heapless::Vec<Step, MAX_STEPS_PER_STUDY>` for the no_std dev-bench build, so the ~38 KB inline value that actually crashed a debug `embarch-api` collapses to a pointer. Decision 36's 512 MiB runtime thread stops being the thing standing between the suite and a crash and goes back to being ordinary headroom. **What is still owed and worth naming**: nobody has ever measured `size_of::<Step>()` or `size_of::<StepResult>()`, including the newer, larger `gatt_activity` variant — a `size_of` assertion test so the next growth fails CI rather than a stack is the cheap follow-on, and is not done.
- **`Sample.value`'s real-world shape — deferred with power profiling, 2026-08-25** (§4.7, §5.2). The CSV row *shape* (`rx_utc_ms,step_name,value,unit,channel_id,core_rx_utc_ms`, §3 decisions 27/30) is locked and unaffected. The open half — whether one `Sample` per capture instant is the right grain, or a genuinely multi-lead sensor needs several — was always downstream of what dev-bench's power and sensor hardware turns out to be, and that is now deferred as a whole (bullet above). Answering it speculatively would be designing against imagined data.
- **Dev-bench's UTC clock-resync accuracy** (§3 decision 12's `host_utc_ms` amendment, §4.7) — resync happens only on `Hello` (connection/reconnection), so `Sample.rx_utc_ms`'s drift between resyncs, and whether that's acceptable for post-hoc `SignalCheck` analysis (§4.6), isn't validated against real dev-bench hardware yet. §3 decision 30's `core_rx_utc_ms` gives post-hoc analysis the raw material to detect that drift after the fact, but doesn't correct it in real time or say how much drift is actually acceptable — that judgment still needs real hardware.
- **Core's host-side watchdog grace margin** (§3 decision 16's dev-bench-crash amendment) — still a placeholder, never sized against real serial-link latency. Narrowed 2026-08-25: [embarch-core/design.md](../embarch-core/design.md) §3 decision 33 fixed a genuine defect adjacent to it (the deadline ignored `Step.delay_before_ms` entirely, failing healthy studies that authored a long delay) and, as a side effect, made the timeout path deterministically reachable for the first time. That closes the *testability* half. Sizing the margin is a different question and remains open — it needs a distribution of real round-trip times on a healthy link, which exercising the failure path does not produce.
- ~~**Exact CRC crate/algorithm**~~ — resolved during implementation: the `crc` crate (CRC-32/ISO-HDLC), computed by streaming each `Step`'s postcard encoding through a `Digest` one at a time rather than buffering all of `steps` at once, so a constrained dev-bench MCU only needs stack space for one `Step`, not `MAX_STEPS_PER_STUDY` of them. `streams_crc` (schema v9) reuses all three choices unchanged, one `StreamTap` at a time.
- ~~**`SignalCheck`'s real variant set, and the DSP/statistics implementations' rigor.**~~ — **closed 2026-08-25 by removal, not by answer (§3 decision 48).** The variant set was illustrative, the DFT was naive and O(n²), and both were provisional pending real captured data — which the same day's deferral of power profiling put out of reach indefinitely. Rather than carry a placeholder set behind a feature nothing called, the whole post-hoc validation notion was deleted. If checks over real capture data are wanted later, they get designed against that data, which is what this bullet always said should happen.
- **`GattDiscover`/`GattMonitorAll` (§3 decisions 31/32) and the extraction tool (§3 decision 33) — this crate's own half implemented 2026-08-20; `embarch-dev-bench`'s live BLE dispatch of the two new `Action`s is still separate, tracked work.** `embarch-study-designer/milestone-9.md` §3.1–3.7 landed: `GattCharacteristicInfo`/`GattServiceInfo`/`GattActivityRecord` (§4.3a), the two new `Action` variants and `StepResult` fields, `DataChannel::GattActivity`, `STUDY_DESIGNER_SCHEMA_VERSION` 3→4, the `GattConfigExtractor` trait, and `ZephyrBleDefExtractor` — all with round-trip tests (postcard + serde_json) and confirmed clean across every feature combination including `--all-features`. `MAX_DISCOVERED_SERVICES`/`MAX_CHARS_PER_SERVICE`/`MAX_GATT_ACTIVITY_RECORDS` (§3 decision 15's update): the first two are now validated against `ZephyrBleDefExtractor`'s real output (2 services, 7 and 8 characteristics respectively — see that decision's own correction) rather than approximated by hand; `MAX_GATT_ACTIVITY_RECORDS` still isn't, since that requires dev-bench actually running `GattMonitorAll` against live notification traffic — `embarch-dev-bench/milestone-9.md`'s own scope, unstarted as of this update.
- **`gatt_activity`'s worst-case `StepResult` size still has not been computed** (§3 decision 32's own text) — unchanged as a gap, but §3 decision 46 changes what the fix looks like. The host side no longer needs static-allocation treatment for it (the heap `Vec` fix applies to `Study`, and `StepResult` is assembled host-side), so what remains is the dev-bench half plus the `size_of` assertion decision 46's bullet above names. Still a real risk to check early in `embarch-dev-bench/milestone-9.md`'s implementation rather than after a stack overflow surfaces it, exactly as decision 21's did.
- **`ZephyrBleDefExtractor` (§3 decision 33) is scoped to exactly one firmware's macro conventions** — generic at the trait boundary, deliberately narrow at the implementation, per the user's explicit call during Milestone 3's design pass. A second firmware project's own extractor is new, separate future work, not a generalization of this one.
