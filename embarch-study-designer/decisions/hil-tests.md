# embarch-study-designer decisions: the HIL test, suite and plan

**Status:** active, 2026-11-25.

What `tasks/study-designer/094` (EMB-353, the root of the HIL Test chain), `095` (EMB-354, the checks, decision 110) and `096` (EMB-355, the expansion, decision 111) decided building the types `notes/hil/03-test.md` and `04-premade-suites.md` describe. Index: [../decisions.md](../decisions.md). Current truth: [../interfaces/hil-tests.md](../interfaces/hil-tests.md). Shapes' conventions: [hil-shapes.md](hil-shapes.md), decisions 90 and 91.

### 109 — The test, suite and plan are JSON types behind `hil-test`, hashed over RFC 8785, diffed per measurement

**`hil-test = ["verdicts", "dep:sha2", "dep:serde_json"]`**, one module (`hil_test`), host-only and additive: no existing type, wire format or schema version changes and no consumer turns it on. It reuses the verdict rules' `Limit`, `DecisionRule` and `Source` by conversion rather than by embedding, because `DecisionRule` does not refuse unknown keys and the HIL files must (decision 90); the test's own `DecisionRuleSpec` and `LimitSpec` do, with `expect` added to the limit kinds.

**Three choices are the plan's recommendations, which the owner may strike** (`notes/hil/14`): **JSON rather than TOML** (plan choice 2); **a suite's bench carrying its boards' command lines** (`idle`, `hello`, read-only lines, preconditions) **rather than a command-set file shipped with the board's firmware** (plan choice 4); **the suite's own requirement slugs rather than the atlas's `rid`** (plan choice 3). **A limit with `expect` for an observation's choice is plan choice 27**, also strikable. Striking one changes a field or a file, not the hash rule or the diff.

Where the notes were silent, each *(shape)*: `tags` sit on the test, since 03 selects by tag and names no home; `revision_range` is `{from, to}` with `null` open; `bench.config` is required; a `precondition` is required, never defaulted, so the file says it; a suite bench's saved-bench `description` is an opaque JSON object, since embarch-ui owns that shape (its decision 73); a plan's selection is `all` or `some {tests, tags}` and a test is selected by id **or** tag; `setup_terms` are `{name, unit, u, k}` uncertainty terms and never values (02: a person's act); `sources` carry `range_min`, `range_max`, `resolution`, `u` and `k`, what the acceptance-width rule reads.

**The definition hash is SHA-256 over the canonical JSON of the value as this crate serialises it**, not over the file's bytes: a test's file need not be canonical, and key order and a defaulted field's spelling must not change what a confirmation binds. The canonical form is written here (UTF-16 key order, ES6 numbers) because no JCS crate is a dependency of this one; it is checked against RFC 8785's number samples, not against a second implementation.

**`derived_diff` compares limits and sources per measurement**, so "limit widened" names the one measurement; and it leaves out `test_id`, `title`, `tags`, `schema` and `derived_from`, which decide no verdict. Measured: fixtures only; no real premade suite exists yet.

### 110 — A test is checked when it is defined: one function, every refusal returned, and an energising rule that fails safe

**`hil_check::check_test(test, study, bench, measured) -> Result<(), Vec<Refusal>>`**, in `src/hil_check.rs` under `hil-test`, returns **every** refusal (test, field, reason and a `Rule` to match on), so embarch-api and Core refuse the same test for the same reason and an author sees all of it at once. Its inputs are the plan's, not a topology type, because instrument metrology is not in `embarch-topology` yet (EMB-358): `study` is `Host(&HostStudy)` or `DevBench`; `measured` maps each limited measurement to who measured it (`bench`, `dut`, `person`) and the source's range, resolution and `U`, which the caller fills from an instrument's declaration or a bench board's characterisation. A `dut` measurement's numbers are read from the test's `sources` instead. A declared value must be finite and above zero, as the reducers require.

**Energising fails safe.** `energises(step, bench)` is true for an instrument set, for every DUT line, and for a bench-board line the bench does not list as read-only; a `Repeat` energises if an inner step does. **A signal is a bench board's only when it is named by the board's `part`; any other signal is the DUT's**, so a signal the check cannot place counts as energising, never as safe *(shape: the suite format has no signal-to-board map; the saved-bench description is opaque, decision 109)*. A `Repeat` is walked twice when it can run twice, so a handling prompt at the end of a pass reaches the first step of the next. Teardown steps are not walked: they switch outputs off. A bench holds a DUT when a `parts` entry has role `dut`, or, in the legacy shape with no `parts`, a non-null `dut` *(embarch-ui decision 73; the spelling is assumed, not read from a Core type)*.

**Three plan choices are the recommendations, which the owner may strike** (`notes/hil/14`): **the energising rule as 12 states it, with every DUT line energising** rather than listing energising lines per board and treating the rest as read-only (choice 5; striking it changes `energises` and `BenchBoard`); **a dev-bench study refused** rather than both kinds run (choice 18; striking it drops one refusal and `StudyKind::DevBench`); **`power_cycle` and `detach` needing the bench to say how** (choice 21). Not checkable yet, said so: an action prompt's confirming measurement feeding an `until`, since a host step's `until` is a text pattern and names no measurement; only a limit counts. Measured: fixtures only.

### 111 — A selection expands in one pure function into `run.json`, a selection record and the expanded studies

**`hil_expand::expand(suite, plan, dut, ctx) -> Result<Expansion, ExpandError>`**, under `hil-test`, is the one function embarch-api calls to write `run.json` and Core calls to re-expand it. It returns the `RunJson`, a `SelectionRecord` and the studies it expanded, with their bytes and hashes. Nothing in it reads a clock or a random source, and every walk is over a sorted map, so the same inputs give the same bytes and hash whatever order the suite lists its tests in. `RunJson::hash()` is SHA-256 over the RFC 8785 form (`definition_hash`); `duration_bound(run)` is the sum over tests of `run_count` times the test's `step_budget_ms`, which `run.json` carries so the bound needs no study.

**The record is named `SelectionRecord`**, because `hil_test::Selection` is a plan's picks and renaming a shipped enum would be a public change. **Statuses, in order:** `not_applicable` (the first unmet condition, or a template's capability absent or empty), then the plan's picks, then `hook_unmapped` and `bench_missing` for a picked test, and `not_selected`. A selected test's `requires` pull in the tests they name that apply and are not blocked (reason "required by X"); a `requires` on a blocked or inapplicable test stays in `run.json` and is Core's run-time skip (03: "a `requires` not met").

**Three fields are added to `TestDef` and one to `Plan`, all optional and skipped when empty, so no existing file or hash changes** *(shape: the notes name the concepts and no home)*: `applies_when` (conditions `present`, `equals`, `contains` over a capability, all of which must hold), `hooks` (the hooks it needs mapped), `checks` (the capability a test checks against the measured value), and `Plan.bench_order`. `derived_diff` reads the first three. **A template expands once per element of its capability's array** (a scalar is one value), ids `<id>#<n>` from 1 in array order, `{capability.<field>}` filled in every string of the study and of the test (a numeric limit cannot hold a placeholder, so a template's measurement names and `expect` values carry it); the expanded study is canonical JSON and its hash is of those bytes. **A capability's check** is the test whose `checks` names it: every template of that capability `requires` it, it is pulled in, and it sorts first on its bench. Bench order is the plan's, else the suite's; within a bench, `requires` order with checks first; a `requires` cycle, or one that runs later, is an `ExpandError`.

**`run_id` is the caller's** and `expand` refuses an empty one; Core refuses one it holds. **This is plan choice 9, a recommendation the owner may strike:** Core assigning the id is the alternative, and striking it removes the argument and the refusal. Not done here: `SuiteTest.hash` against the definition (Core's, since it is the file's hash and not the definition's), `revision_range` against the standard's revision, and the `dev_bench` study kind (plan choice 18). Measured: fixtures only.


### 113 — A study's hash is one function, `study_hash`

**`hil_test::study_hash(&HostStudy) -> String` is `definition_hash` of the study: SHA-256 over its RFC 8785 canonical JSON as this crate serialises it**, the convention `hil_expand::expand` already used for an expanded template (canonical JSON, hashed), so a template's expansion is hashed by the same rule and `expand` is unchanged. **The hash is of the study's content, not of the file's bytes as written** (109 had said bytes): a premade file's whitespace and key order then change nothing, and Core and `check_test` call this one function rather than each re-deriving it from bytes they would have to agree on. `StudyRef.hash` is therefore `study_hash` of the study its `file` holds. **`check_test` does not refuse a mismatch yet:** both consumers still hash a premade study's file bytes, so the refusal lands after they move to `study_hash` (`api/204`, `core/166`), as `study-designer/100`. Core's use of the function at the `POST /test-runs` prepare (core 134, `bytes_checked_against_hash`) is a separate core unit. Measured: the worked-example fixture pinned in `tests/hil_checks.rs`; the template path's own tests unchanged.
