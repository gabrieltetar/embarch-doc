# embarch: decision reversals

**Status:** draft, 2026-08-15. Added closing item 65 of that day's design-improvement review (`.claude/design-improvements-2026-08-15.md`, local working notes — not committed): every entry below is handled correctly in place, in its own owning doc — this page exists because there was no single place listing "assumptions reality has already overturned," which the review's own closing observation calls "the highest-signal document in the repo for anyone new, and the best predictor of which remaining assumptions to distrust." Per `DOC-PROTOCOL.md` §5, this doesn't restate any correction's full rationale — it links to the decision that recorded it.

## Reality-driven reversals — found by actually building or running something, not by review

These are the suite's real defect-finding mechanism at work (see this doc's closing note): every one of them was caught by a real build, a real hardware install, or reading a real repo's actual files — never by inspection alone.

| # | What was assumed | What reality showed | Found | Owning decision |
|---|---|---|---|---|
| 1 | Dev-bench's Core link would be USB CDC ACM | The nRF54L15 SoC has no USB device peripheral at all — only the newer nRF54LM20 family has one. The link is a plain UART over the DK's on-board J-Link VCOM instead | 2026-07-30, researching implementation | [embarch-dev-bench/design.md](embarch-dev-bench/design.md) §3 decision 6 |
| 2 | Dev-bench auto-detection would use a custom VID/PID (`0xEBAC`/`0xDB01`) | Follows directly from #1 — dev-bench firmware owns no USB descriptor to put a custom VID/PID in. Detection moved to `embarch-core` matching the J-Link's own SEGGER VID plus a heuristic | 2026-07-30, same investigation as #1 | [embarch-dev-bench/design.md](embarch-dev-bench/design.md) §3 decision 12 |
| 3 | The nRF54L15DK build would be a standard, non-`sysbuild` Zephyr build | NCS 3.4's `west build` wraps every application in `sysbuild` regardless — output lands in `build/app/zephyr/`, not `build/zephyr/` | 2026-08-04, first real `workspaces/nordic` build | [embarch-dev-bench/design.md](embarch-dev-bench/design.md) §3 decision 4 |
| 4 | `CONFIG_BT_MAX_CONN` would stay at its default single-connection value | The default is **2**, not 1 — and forcing it to 1 silently zeroes the central role's connection slots (`BT_CTLR_SDC_PERIPHERAL_COUNT` claims one), breaking every central-role `BleConnect` with no build error or warning | 2026-08-04, same build session as #3 | [embarch-dev-bench/design.md](embarch-dev-bench/design.md) §3 decision 15 |
| 5 | `service-manager`'s cross-platform install gave Core "one code path" for becoming a real OS service | True only for *registering* the service — Windows additionally requires a prompt `StartServiceCtrlDispatcherW` handshake or SCM kills the start after 30 seconds (Win32 1053). Core had never actually been installed as a real boot service before this was found — every prior test used a throwaway foreground instance | 2026-08-12, first real Windows service install | [embarch-core/design.md](embarch-core/design.md) §3 decision 3 |
| 6 | Elevation for service install/start was a Windows-only tax | A systemd *system* unit needs root/polkit too — confirmed on Linux, where an unprivileged `embarch-core start` fails with "Interactive authentication required" | 2026-08-05, smoke-testing on Linux | [embarch-core/design.md](embarch-core/design.md) §3 decision 3; [embarch-umbrella/design.md](embarch-umbrella/design.md) §3 decision 7 |
| 7 | A Zephyr board's `board.yml`-declared boards/variants/revisions describe what's actually buildable | Three separate real-repo bugs, one investigation: a declared (soc, variant) combination can have no real `.dts` file at all (`dts_exists`); a SoC with named product variants can still have a real *variant-less* build for the same cpucluster, which `board.yml` alone doesn't surface; and a "default revision is always backed" shortcut is wrong for a variant with its own custom `revision.cmake` coupling it to one specific revision | 2026-08-13, checking whether the real healthband repo's actual build was representable at all | [embarch-api/design.md](embarch-api/design.md) §3 decision 12 |
| 8 | `Cargo.toml`'s version tracks the release tag by construction | It had silently drifted from the `v0.1.1` tag — caught only because `doctor` check 1 happened to compare `--version` against the tag by hand that day | 2026-08-12 | [embarch-core/design.md](embarch-core/design.md) §11; now guarded by a release-CI assertion, [embarch-umbrella/design.md](embarch-umbrella/design.md) §3 decision 27 |

## Review-driven reversals — found by a documentation pass, not a real build

A different, faster-turnaround category: corrections made by re-reading the suite's own design docs for internal consistency, before code caught up. Lower-signal than the table above (no hardware or build forced the question), but worth distinguishing from a fresh decision rather than letting them read as one.

- **Core's default bind address flipped from `0.0.0.0` to `127.0.0.1`** (2026-08-15) — not wrong when written (§6's original reasoning — reachability from WSL2/a future LAN — was sound), but never assessed *together* with no-TLS-plus-a-static-token-plus-an-arbitrary-local-path, which composed into a real gap once looked at as a whole. [embarch-core/design.md](embarch-core/design.md) §3 decision 6.
- **`embarch-umbrella`'s `doctor` check 8 stopped maintaining its own mirrored Zephyr-target scanner one day after building it** (2026-08-14 → 2026-08-15) — the liftable-copy pattern (written for topology detection and token/config parsing, where a real dependency genuinely doesn't exist yet at call time) was applied a third time to a check that, on reflection, could have just shelled out to `embarch-api` like every other `doctor` check already does. [embarch-umbrella/design.md](embarch-umbrella/design.md) §3 decision 17's 2026-08-15 amendment.
