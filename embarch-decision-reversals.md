## Reality-driven reversals — found by actually building or running something, not by review

These are the suite's real defect-finding mechanism at work (see this doc's closing note): every one of them was caught by a real build, a real hardware install, or reading a real repo's actual files — never by inspection alone.

| # | What was assumed | What reality showed | Found | Owning decision |
|---|---|---|---|---|
| 1 | Dev-bench's Core link would be USB CDC ACM | The nRF54L15 SoC has no USB device peripheral at all — only the newer nRF54LM20 family has one. | 2 | Dev-bench auto-detection would use a custom VID/PID (`0xEBAC`/`0xDB01`) | Follows directly from #1 — dev-bench firmware owns no USB descriptor to put a custom VID/PID in. | 10 | `artifact_path_for_core`'s `\\wsl.localhost\...` UNC mechanism, once confirmed working against real hardware, would work the same way regardless of how Core is running | It only works with Core in an interactive-session foreground `run` — the installed Windows service runs as `LocalSystem` in Session 0, which has no access to the per-session `\\wsl.localhost` network provider at all (`os error 67`, confirmed by direct A/B test against identical config). | 12 | `embarch-core`'s probe-rs access "has no business flashing" dev-bench firmware — a deliberate, permanent separation of concerns | It stopped holding the moment a dev-bench board showed up whose on-chip debug probe `probe-rs` already speaks natively (the ESP32-C5 interim substitute's real `espusbjtag` driver) — Core flashed it directly, with zero WSL2↔Windows USB forwarding, no `usbipd`, no admin elevation | 2026-08-19/20, standing up the ESP32-C5 interim board while the real nRF54L15DK was RMA'd | [embarch-dev-bench/design.md](embarch-dev-bench/design.md) §3 decision 13, reversed; mechanism in [embarch-core/design.md](embarch-core/design.md) §3 decision 18 |

| 14 | The SEGGER-VID-plus-`"jlink"`-product-string heuristic would only ever need to disambiguate dev-bench's *own* eventual J-Link-based board from unrelated noise | It stopped holding the moment a genuinely different J-Link — the reference-dut DUT's own — was attached alongside dev-bench at the same time: its VCOM matches the identical heuristic just as validly, and Core correctly refused to guess between two different real boards rather than picking wrong. Fixed by having `dev_bench::detect()` fall back to `known_boards`'s `"dev-bench"`-role entry's `probe_serial` (recorded once, verified live at enrollment) when `EMBARCH_DEV_BENCH_SERIAL` isn't set, instead of requiring a second, separately-typed env var for a fact decision 22's enrollment already captured | 2026-08-20, first real session with the DUT's J-Link and dev-bench's own probe both attached | [embarch-core/design.md](embarch-core/design.md) §5 |
| 15 | `embarch-core`'s daily-rolling log file plus its `logs` CLI subcommand (decision 16) shipped in the 2026-08-15 design-only pass, same as the prose describing them read | `main.rs` never gained a `Logs` subcommand or a file-writing `tracing` setup at all — `tracing_subscriber::fmt::init()` (stderr only, unchanged since before decision 16 was written) was the entire story until this was actually built. The same "documented as implemented, wasn't" pattern hit decision 9's `probe_serial` gap earlier this same session (row 14's neighbor, [embarch-core/design.md](embarch-core/design.md) §3 decision 9's own text) — decision 11's `core.toml` config file (§3 decision 11) shows the identical symptom (no `core_config.rs`/`core.toml` reference anywhere in `src/`) but hasn't been independently investigated or fixed, so isn't given its own row here yet | 2026-08-20/21, blocked live on diagnosing decision 21's `target_reset()` reset behavior with no readable log output from the installed Windows service | [embarch-core/design.md](embarch-core/design.md) §3 decision 16 |
| 16 | The ESP32-C5's native USB-Serial/JTAG peripheral, once confirmed to work at all for flashing and a first self-test `Study` (decision 18), was a viable *permanent* link for dev-bench's own `Hello`/`HelloAck`/`Study` traffic, not just for that first successful run | It's a genuinely bad fit for the runtime link, confirmed by Espressif's own troubleshooting docs, not a coincidence: its core-only reset never re-samples the chip's boot-strapping pins, a genuine hardware reset pulse wedges its host-side USB CDC driver outright (needing a physical replug to clear), and a DTR/RTS-on-open gotcha reproduces that same wedge on demand. The board actually has a *second*, dedicated UART USB-C port built for exactly this reason — Espressif ships it precisely because the native peripheral has these known rough edges for embedded development use. The fix that actually closed the loop was moving the link off the native port entirely, not root-causing any of the above further | 2026-08-21, chasing a `HelloAck` timeout that survived a genuine hardware reset pulse and a physical USB replug alike | [embarch-core/design.md](embarch-core/design.md) §3 decision 21, §5; [embarch-dev-bench/design.md](embarch-dev-bench/design.md) decision 26 |
| 17 | Each kind of captured data gets its own channel, and dev-bench decodes payloads into `Sample`s — reaffirmed as recently as 2026-08-25, when a streamed GATT transcript got its own dedicated `DevBenchMessage` variant rather than being generalised | One pipeline; **dev-bench never interprets a payload**; what bytes mean is a declared, engineer-supplied encoding resolved host-side. The load-bearing finding, and the reason this is a reality-driven row rather than a review-driven one: dev-bench's stream handler had been decoding every notification as little-endian `f32`s — **an assumption about what a specific DUT's bytes mean, living in firmware, that no engineer ever declared** — which is wrong for a log, a packed 16-bit ADC stream, or anything framed. Affordable to reverse only because no real byte has ever crossed the streaming path | 2026-08-25, scoping [embarch-outpost](embarch-outpost/design.md), whose DUT trace UART would have become the fourth near-identical capture pipeline | [embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decision 39 (partially superseding decision 36, one day old); [embarch-dev-bench/design.md](embarch-dev-bench/design.md) §3 decision 22, **superseded** |
| 18 | A schema-version bump number written into a design doc ahead of implementation stays valid until it is implemented — `embarch-study-designer` decisions 39 and 40 both said "schema 5 → 6", and both were closed as settled on that basis | Decisions 42 and 43 were written the same day and implemented **first**, taking v6 and v7. By the time 39/40 became code the honest bump was **7 → 8**. Nothing about either decision's substance moved — one bump, covering both — but "one bump per pass" is exactly the discipline a stale number quietly turns into two, and the number appeared in four docs by then (the two decisions, `embarch-features.md`'s pipeline row, and the proposal). The general shape: a *derived* value recorded ahead of the work that derives it is a fact with a shelf life, unlike the decision it sits inside | 2026-08-25, implementing Milestone 7 Phase A ([embarch-outpost/milestone-1.md](embarch-outpost/milestone-1.md) §2) | [embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decision 39's own bump note |
| 19 | An `--erase` flash is a stronger, safer version of a normal flash — worth adding on request, with nothing about it needing validation of its own | It **bricks** the nRF54L15. Two runs each way, same artifact/probe/reset: without it the DUT comes up and advertises, with it the board goes silent. A plain non-erase EmbArch flash does not recover it — only Nordic's own `nrfutil` ERASEALL on the identical hex does. probe-rs's `do_chip_erase` and `flashing::erase_all` both route to the flash algorithm's `pc_erase_all`, and what that clears beyond the declared NVM region was never established, so the correlation is four-for-four and the mechanism is still a guess. The sector-erase fix written in response was **rejected** for being one more EmbArch-authored guess about Nordic flash, in favour of delegating to the tool that demonstrably works | 2026-08-25, diagnosing a DUT that had stopped advertising — an entire session of BLE scan diagnostics spent explaining a board EmbArch's own flash had killed | [embarch-core/design.md](embarch-core/design.md) §3 decision 32; [embarch-api/design.md](embarch-api/design.md) §3 decision 41 |
| 20 | dev-bench needs no BLE pairing callbacks: "decision 11's Just Works pairing needs no auth callbacks, so an explicit `bt_conn_set_security()` call would only duplicate" what Zephyr's ATT layer already does on an authentication error — written into `ble_bridge_real.c`'s own header as settled design | Both halves fail against a DUT that requires an authenticated link, and this one does (engineer-confirmed: `BT_SECURITY_L4` before it will tolerate service discovery). With no `bt_conn_auth_cb` registered anywhere, `get_io_capa()` returns `NO_INPUT_OUTPUT` and `sec_level_reachable()` refuses L4 outright — **unreachable from this bench regardless of what a study asks**, and ATT-error retry cannot exceed what pairing can achieve. The DUT also self-elevates 200 ms after connect, so no ATT request ever gets the chance to fail first. What it looked like from the bench: connect `Pass`, then a deterministic `"disconnected during service discovery"`, 4 of 4, while the same discovery walked four other devices fine — a failed elevation is invisible to a bench with no concept of elevation. **The attribution of that specific failure to this specific gap is unvalidated on hardware**; that L4 is unreachable as the firmware stands is not | 2026-08-25, asking the engineer why discovery was being refused rather than continuing to infer it from behavior | [embarch-dev-bench/design.md](embarch-dev-bench/design.md) §3 decision 34; [embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decision 44 |
| 21 | Widening `steps_crc` to also seal `Study.streams` "would silently invalidate every saved study's sealed value" — recorded as settled reasoning in [embarch-study-designer/design.md](embarch-study-designer/design.md) §7 and used there to pre-select a second CRC as "the cheap version" | No saved study's sealed value is ever trusted: `embarch-api` recomputes and overwrites `steps_crc` on **every** submit (§3 decision 26, `embarch-api/src/study.rs:19`, reached from both the CLI and MCP paths). The stated objection to widening did not exist. The decision still landed on a second `streams_crc`, but on the real objection instead — `steps_crc` sits *between* `steps` and `streams` on the wire, so widening means digesting two non-contiguous spans in dev-bench's hand-written C or reshuffling `StudyStart`'s fields | 2026-08-25, settling Milestone 7 Phase A's leftover open questions — found reading `embarch-api`'s real submit path rather than trusting the doc's own summary of it | [embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decision 39's 2026-08-25 amendment |
| 22 | `STUDY_DESIGNER_SCHEMA_VERSION` guards one thing, so one trigger list serves it — `schema_version.rs` listed `crate::validation` among the modules whose changes bump it, alongside `study`/`result`/`sample`/`protocol` | It guards **two hops with different exposure**, and the list is wrong at both ends. `validations` never reaches dev-bench at all (decisions 17/19), so a change there can never drift a dev-bench decoder — yet `Study` *including* `validations` crosses `embarch-api`→`embarch-core` as JSON, whose only drift check is the same constant, and those two are genuinely built and deployed separately on this bench. Dropping validation from the list (the first answer reached) would have created a real undetected failure; keeping it charges a firmware handshake number for something firmware cannot observe. The constant splits in two. `Study.requires` had already moved the single constant at v8 under the old rule, which is the precedent this contradicts | 2026-08-25, settling §7's `ValidationSource` question — the two-hop exposure surfaced only when pricing that change against the real `POST /study` path | [embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decision 12's 2026-08-25 amendment |

## Review-driven reversals — found by a documentation pass, not a real build

A different, faster-turnaround category: corrections made by re-reading the suite's own design docs for internal consistency, before code caught up. Lower-signal than the table above (no hardware or build forced the question), but worth distinguishing from a fresh decision rather than letting them read as one.

- **Core's default bind address flipped from `0.0.0.0` to `127.0.0.1`** (2026-08-15) — not wrong when written (§6's original reasoning — reachability from WSL2/a future LAN — was sound), but never assessed *together* with no-TLS-plus-a-static-token-plus-an-arbitrary-local-path, which composed into a real gap once looked at as a whole. [embarch-core/design.md](embarch-core/design.md) §3 decision 6.
- **`embarch-umbrella`'s `doctor` check 8 stopped maintaining its own mirrored Zephyr-target scanner one day after building it** (2026-08-14 → 2026-08-15) — the liftable-copy pattern (written for topology detection and token/config parsing, where a real dependency genuinely doesn't exist yet at call time) was applied a third time to a check that, on reflection, could have just shelled out to `embarch-api` like every other `doctor` check already does. [embarch-umbrella/design.md](embarch-umbrella/design.md) §3 decision 17's 2026-08-15 amendment.

## Changelog

- 2026-08-25 — **Rows 21–24 added**, all four from one pass settling the open questions Milestone 7 Phase A left behind ([embarch-outpost/milestone-1.md](embarch-outpost/milestone-1.md) §2), and all four found the way this table's own closing note predicts — by reading the real repos' actual files rather than the docs' summaries of them. 21 and 23 are cases where a doc's stated reason for an open choice did not survive contact with the code (`steps_crc` is recomputed on every submit, so nothing widening it could invalidate; `Step.power_sample` was already dead in all four consumers, so there was no live competitor to adjudicate). 22 is a versioning rule that fired on changes the version could not express, *and* would have broken a hop nobody was thinking about — the first answer reached was wrong in the opposite direction, which is why the constant splits rather than narrows. 24 is owed work queued ahead of anything that could trigger it.

- 2026-08-25 — **Rows 19 and 20 added**, both from the same session and both about the same failure mode: EmbArch acting on an assumption about a board rather than on something established. 19 is a capability the suite added on request and never validated, which bricked the DUT and then cost a session of diagnostics aimed at the wrong thing. 20 is a comment in dev-bench's own firmware asserting that pairing callbacks weren't needed — false against any DUT requiring an authenticated link, and the reason the bench could not even name what was failing.
