# embarch-umbrella: design

**Status:** draft, 2026-08-11. Implemented at [gabrieltetar/embarch-umbrella](https://github.com/gabrieltetar/embarch-umbrella): every command in §8's surface has real behavior behind it — `setup`, `init`, `doctor`, `up`/`down`, and `status` all ship. Release CI (decision 14) is verified end-to-end, all three repos: real `v0.1.0` tags, real GitHub Releases, and a real `suite-v0.1.0` assembled from them with `doctor` check 1 passing against its manifest. §5 check 11 (`embarch-study-designer` schema-version agreement) is the one remaining stub, for the reason recorded there: `embarch-study-designer` isn't a Cargo dependency of `embarch-core`/`embarch-api` yet, so neither side has a version to compare. Append changes to the Changelog (§12) rather than silently editing history above it.

## 1. Purpose and scope

`embarch-umbrella` is the sub-project that gets a firmware engineer from *nothing installed* to *`embarch-api build_and_flash my-project` works, from a terminal or from Claude Code* — on whatever topology their machine happens to be (Core native on Windows with the API in WSL2, both native on a Mac, both native on Linux, or Core on a separate box). It ships one binary, named `embarch` (§3 decision 2), with three jobs: **set up**, **verify**, and **start Core when it isn't already running**.

The reason it exists as its own sub-project rather than as more subcommands on an existing binary: it is the only component that knows about *both* `embarch-core` and `embarch-api`, and it is the binary a person downloads when they have neither. `embarch-api` can't hold this — it would have to install Core's OS service and register MCP servers, neither of which a thin build-orchestration layer has any business doing, and it can't be the answer to "what do I download first" when it's one of the two things being set up.

`embarch-umbrella` is **not**:
- **A process supervisor or daemon.** It has no restart loop, no health polling, no resident process. Core's own cross-platform service install (`embarch-core/design.md` §3.3) is what keeps Core running; umbrella's `up` exists only for when that isn't in place or has died (§3 decision 4).
- **In the runtime data path.** Nothing routes through umbrella after setup. It is not an MCP server, not a proxy, and deliberately not the process an MCP client spawns (§3 decision 5). If umbrella is deleted from a working machine, the stack keeps working.
- **A hardware or build layer.** It never links `probe-rs` or `serialport`, never runs a build command. Every capability it appears to have is a shell-out to `embarch-core` or `embarch-api`, or an HTTP call to Core's existing endpoints.
- **Multi-machine orchestration.** No SSH, no remote agent, no remote install. A Core on a separate box (a Pi over wifi) is started by a human on that box; umbrella only detects and verifies it (§3 decision 8).
- **A GUI.** A small EmbArch UI — a human glancing at whether Core is up, rather than asking an agent — is real anticipated scope but explicitly out of this document's v1 (§10). What v1 owes it is a stable machine-readable status contract (§3 decision 11).

## 2. Architecture overview

```
                    setup / init / doctor / status / up / down
                                    |
                                 embarch                    <- this sub-project
                          /         |          \
        shells out to     |         |           |  HTTP+Bearer (GET /status,
        embarch-core CLI  |         |           |  /dev-bench/port)
        (install/start)   |         |           v
                          |         |      embarch-core
                          |         |
                          |         +-- shells out to embarch-api CLI
                          |             (list_projects, status) and reads/writes
                          |             its config
                          |
                          +-- writes <firmware-repo>/embarch/embarch.toml
                              and registers the MCP server (local scope)

after setup, the runtime path has no umbrella in it:

Claude Code --stdio--> embarch-api --HTTP+Bearer--> embarch-core --> hardware
human ------CLI------> embarch-api ----------------^
```

Both of `embarch-api`'s front-ends stay first-class after setup: an MCP client spawning it over stdio, **and** a human running `embarch-api <subcommand>` directly (`embarch-api/design.md` §5a). Umbrella's job is to make the second one ergonomic too — a resolved config path in the environment, and the binary on `PATH` — not just to wire up the agent path.

## 3. Locked-in design decisions and rationale

1. **Language: Rust**, one static binary with no runtime dependencies, matching the rest of the suite. It must run on a machine where nothing else from EmbArch is installed yet, so a runtime (Python, Node) or a system library dependency would be self-defeating.

2. **Repo `embarch-umbrella`, binary `embarch`.** The repo name says what it is in the suite; the binary name is what a new engineer types on their first day (`embarch setup`, `embarch doctor`). `embarch-umbrella setup` was rejected purely on ergonomics — this is the most-typed command in the suite for someone who has never used it before.

3. **Core is always an installed, autostarting OS service — that, not a launcher, is the actual answer to "one button starts everything."** On the four same-machine topologies (§4), if Core autostarts at boot there is nothing for a human to start, ever: `embarch-api` is invoked per-use (spawned by an MCP client, or run directly by a human), and it finds a Core that is already up. So the problem is a *one-time setup* problem plus an *ongoing verification* problem, not a process-management problem. `embarch-core install` already exists and already handles all three OSes via the `service-manager` crate (`embarch-core/design.md` §3.3) — umbrella's contribution is making sure it actually got run, with the right environment, on the right machine.

    *Refinement from implementing this (2026-08-05): `setup` does **not** edit `PATH`, despite this decision originally listing that as one of its jobs.* Decision 14's single release archive puts all three binaries in one directory, so umbrella finds `embarch-core` as a sibling of itself with no environment surgery at all. Editing a shell rc (which shell? which of the four startup files?) or the Windows registry is invasive, easy to get subtly wrong, and awkward to undo — for a benefit the sibling lookup already delivers. `setup` prints the one `export PATH=...` line and leaves the choice to the operator.

    **Reversed 2026-08-17 (decision 28) — this refinement is bad design and is being undone.** Sibling-lookup ties correct operation to wherever the archive happened to be unpacked staying put forever, and a real `wsl-host` run the same day already surfaced the confusion this causes (§10/changelog, 2026-08-17: the printed `embarch-core: <path>` line reported the local sibling instead of the Windows-side binary a `wsl-host` topology actually needs). See decision 28 for the replacement: a real install step plus real, safe `PATH` mutation.

4. **`up`/`down` exist, but as a fallback, not the main path.** They cover: the service isn't installed (someone wants to try the stack before committing to a service install), the service died, or a foreground Core is wanted for debugging. `up` prefers starting the installed service and only spawns a foreground `embarch-core run` if there is no service to start (§3 decision 7) — a directly-spawned Core dies with the shell that started it, which is a confusing failure mode to hand someone as the default.

    *Refinement from implementing this (2026-08-05): the foreground fallback is **opt-in**, not automatic.* Distinguishing "no service installed" from "start failed for some other reason" means pattern-matching each backend's error text, which is exactly the per-OS fragility decision 4 exists to avoid. So a failed `up` prints the three real options — install it, elevate, or `embarch up --foreground` — and does nothing else. `--foreground` then runs Core in the caller's terminal (blocking, Ctrl-C to stop) rather than detaching, so nobody ends up with a Core that vanished when they closed a window. A `remote` topology refuses `up`/`down` outright rather than falling back to a local binary, which would start a second, wrong Core.

5. **Umbrella is deliberately *not* the process the MCP client spawns.** The tempting alternative — register `embarch mcp` as the MCP server so that starting Claude Code brings the whole stack up — was considered and rejected for v1. It puts umbrella permanently in the stdio hot path, makes every MCP-transport problem a two-binary debugging exercise, and buys little once decision 3 means Core is already running. `.mcp.json`/local MCP registration points straight at `embarch-api`, exactly as it does today.

6. **Topology is auto-detected by probing, not declared — and only the *class* is ever persisted, never an address.** Detection builds an ordered candidate list and races a short-timeout `GET /status` at each:
   - `http://127.0.0.1:4884` — covers Core-local (Mac, Linux, Windows-native) *and* WSL2 in mirrored-networking mode, where localhost already reaches the Windows host.
   - if running under WSL2 (`/proc/version` contains `microsoft`, or `WSL_DISTRO_NAME` is set) — `http://<default-gateway>:4884`, from `ip route show default`. This is the NAT-mode WSL2 path.
   - a user-supplied host, if one was given at `setup` or is recorded in config.

   First responder wins. **A `401` counts as a hit, not a miss**, and is reported distinctly: it means Core is there and the token doesn't match, which is a completely different fix from "Core isn't running." Connection-refused/timeout is a miss.

   *Two refinements from implementing this (2026-08-05).* **"Race" means ordered-sequential, not concurrent** — ordering is the whole point, and the common miss (nothing listening) is a connection refusal that returns immediately rather than burning the per-candidate budget, so a concurrent fan-out would buy nothing and lose the preference order. The 500ms budget is only ever paid where packets are silently dropped. And a **third outcome** turned out to be worth distinguishing: something that answers HTTP with neither `200` nor `401` isn't Core at all — most likely another service squatting the port — which is not a hit, but reporting it as "nothing there" would send someone to start a Core that can't bind anyway.

   *A subtlety this leaves open:* under WSL2 with mirrored networking, a Windows-hosted Core answers at loopback and is therefore classified `local`, indistinguishable by address from a Core running inside the WSL2 guest. Harmless for addressing — both are reachable the same way — but `up` must not infer "I can start Core here" from a `local` classification without also checking whether it's under WSL2 (decision 7's elevation path). Noted in §10. What gets written down is the resolved *class* — `local`, `wsl-host`, or `remote` (plus the host, for `remote` only) — never the WSL2 gateway IP, which is dynamic and has already gone stale once in this suite's own records (`embarch-core/design.md` §7 recorded `172.29.64.1`; `embarch-api`'s real `config.toml` had `172.22.128.1`). Per §3 decision 9 the address is re-resolved at every use instead.

7. **Starting Core across the WSL2⟷Windows boundary is supported, because it's the same physical machine — but umbrella never tries to elevate itself. Elevation is required on every OS, not just Windows.** WSL2 can invoke a Windows binary directly (`/mnt/c/.../embarch-core.exe`), so `up` from the WSL2 side is mechanically possible. Controlling a *system* service, however, needs elevation — and not only on Windows: a systemd system unit wants root or a polkit prompt too, confirmed on Linux where an unprivileged `embarch-core start` fails with "Interactive authentication required" (`embarch-core/design.md` §3.3, corrected 2026-08-05 — this decision originally treated elevation as a Windows-only tax). Umbrella does not attempt self-elevation, UAC prompting, `sudo`, or an elevated helper on any platform: when the operation needs privileges, it prints the exact command to run in an elevated shell and exits nonzero. This is acceptable precisely because decision 3 makes it rare — a one-time elevated `embarch setup`, then autostart forever. Locating the Windows-side binary: `EMBARCH_CORE_EXE` env var, else the path recorded at setup, else a bounded search of the conventional install location — **becomes an exact known path once decision 28 ships** (`%LOCALAPPDATA%\embarch\bin\embarch-core.exe`), rather than a search.

8. **A Core on a genuinely separate machine is detect-and-verify only.** No SSH, no remote install, no remote start. `doctor` reports it as reachable-or-not and tells the human to go start it there. This topology previously also **could not flash**: `/flash` reads `firmware_path` from Core's own local disk and there was no shared filesystem to put an artifact on (`embarch-api/design.md` §9). **Resolved 2026-08-15**: `embarch-api`'s multipart upload for a `remote` topology (`embarch-api/design.md` §3 decision 15, `embarch-core/design.md` §3 decision 10) closes this — flashing now works for this topology, just via uploaded bytes rather than a shared path. `doctor` and §4's matrix are updated to match.

9. **`base_url = "auto"` is implemented in `embarch-api`, not in umbrella.** Umbrella could write a resolved URL into the config at setup time, but that just relocates the staleness problem — the WSL2 gateway IP changes on WSL restart, long after setup ran. So the config gets the literal string `auto` and `embarch-api` re-runs decision 6's candidate race itself, per process, at the point it first needs Core. Umbrella and the API therefore share one resolution algorithm; it belongs to the API because the API is the thing that has to be correct at 3pm on a Tuesday, not at install time. Full schema/behavior: `embarch-api/design.md` §4, §7.

10. **Per-firmware-repo project config lives in an `embarch/` subfolder of that repo, scaffolded by `embarch init`.** Running `embarch init` inside a firmware repo produces:

    ```
    <firmware-repo>/embarch/
    ├── embarch.toml     <- a complete embarch-api config: [core] + the [[projects]] for this repo only
    └── build/           <- the build directory this project's build_command targets, kept separate
                            from whatever the engineer's own interactive `west build` uses
    ```

    Three things follow from this shape:
    - **Scoped by construction.** An `embarch-api` started with this config sees only this repo's projects, so `list_projects` in a firmware repo can't offer up an unrelated board to flash.
    - **A separate build directory is the default, not an option.** Sharing one `build/` with the engineer's interactive builds means EmbArch and the human clobber each other's build tree (different board revisions, different pristine-vs-incremental state). `init` writes `--build-dir embarch/build` into the scaffolded `build_command` and points `artifact_path` at it.
    - **It is a complete config, not a fragment.** `[core]` gets duplicated into every repo, which is real duplication — accepted for v1 because `[core]` is now three lines (`base_url = "auto"` and timeouts) and because an include/fragment mechanism is new code in `embarch-api`'s config loader. Recorded as the deliberate v1 trade-off; the fragment version is §10's open item.

11. **`doctor` and `status` are split by cost, and both carry `--json`.** `status` is one Core `/status` call — cheap enough for a future UI (§10) or a shell prompt to poll. `doctor` is the full chain (§5), including filesystem checks and a build-command resolution, which is far too heavy to poll. The `--json` shape on both is the contract a future UI consumes; it exists in v1 specifically so the UI doesn't arrive and find only human-formatted text to scrape. Human-readable output is the default on both, matching `embarch-api`'s own CLI convention (`embarch-api/design.md` §5a).

12. **Local-only integration into a firmware repo touches nothing that is committed.** For a repo owned by someone else (a client's firmware repo), `init` must not dirty tracked files. Concretely: the `embarch/` folder is excluded via `.git/info/exclude`, **not** by editing the repo's committed `.gitignore`; and the MCP server is registered at Claude Code's local (per-project, per-user) scope rather than by writing a `.mcp.json` at the repo root. Both are reversible by `embarch init --uninstall` and invisible to anyone else cloning the repo. Committing the integration later is a deliberate follow-on step, not the default — see §7 for the options and their trade-offs.

13. **`init` derives what it can from the repo, *by looking rather than assuming*, and refuses to guess the rest.** For a Zephyr/west repo it reads `build/build_info.yml`'s recorded `west.command` when one exists, because that is the only reliable answer to the `build_cwd`-vs-positional-app-path question that has already silently broken this suite once (`embarch-api/design.md` §6, §12). What it will not guess is the probe-rs `chip` name — Zephyr's board identifier and probe-rs's target name are different namespaces with no mechanical mapping — so `init` writes a placeholder plus the exact `probe-rs chip list` invocation to resolve it, and `doctor` fails loudly while the placeholder is still there. Guessing a chip name would produce a config that flashes the wrong target rather than an error.

    *Extended while implementing (2026-08-05), same principle applied twice more:* `artifact_path` is resolved by **searching `build/` for a real `zephyr.hex`** (shortest match wins) rather than assuming a layout — sysbuild nests it under `build/<app>/zephyr/` and a plain build doesn't, and which applies depends on the SDK (`embarch-dev-bench/design.md` §3 decision 4's correction). And `artifact_path_for_core` is computed from `WSL_DISTRO_NAME` when under WSL2, since the UNC form is mechanically derivable from a path that is already known. A `-p always` found in the recorded command is *reported, not removed* — with a separate build directory the user may well still want it, so that's their call to make.

14. **Distribution: one suite release archive containing all three binaries, published from this repo.** `embarch-<version>-<target>.{tar.gz,zip}` contains `embarch`, `embarch-core`, and `embarch-api`, so the getting-started path is one download rather than three, and the three binaries in a user's hands are a version-tested set rather than an arbitrary combination. Targets: `x86_64-pc-windows-msvc`, `x86_64-unknown-linux-gnu`, `aarch64-apple-darwin`, and `aarch64-unknown-linux-gnu` (for a future Pi Core). Per-repo releases still exist for developers working on one component; the suite release is what the user guide points at. `doctor` warns when the installed component versions don't match the suite manifest. This is what [embarch-roadmap.md](../embarch-roadmap.md)'s existing "Release" concept becomes concretely.

    **Implemented, 2026-08-10, verified 2026-08-11 for two of three components ([milestone-6.md](milestone-6.md) §3.7).** Each repo gets its own `release.yml` (tag-triggered, four targets); `embarch-umbrella` additionally gets `assemble-suite.yml` (manual, pulls one tagged release of each component and repackages all three binaries plus a manifest per target). Both open questions this decision's plan had flagged turned out to have the same answer — "GitHub already provides this, no extra CI work needed": `aarch64-apple-darwin` builds natively because GitHub's `macos-14` runner is itself Apple Silicon (still unsigned — Gatekeeper is the guide's problem, not CI's), and `x86_64-pc-windows-msvc` needs nothing extra because `windows-latest` already ships the VS Build Tools workload `embarch-core/design.md` §7 found necessary locally. The one target that's a genuine cross-compile is `aarch64-unknown-linux-gnu` (no free aarch64-linux runner exists), and only `embarch-core` needs more than a bare cross-linker for it, since `probe-rs`/`serialport` pull in `libudev-sys` — that leg uses `cross` (Docker-based) with a `Cross.toml` installing `libudev-dev:arm64` into the container, while `embarch-api`/`embarch-umbrella` (no C dependency) just add `gcc-aarch64-linux-gnu` to the host runner. The manifest is a small JSON file (`suite_version`, `target`, each component's release tag) written by `assemble-suite.yml` and read by `doctor` check 1 (`crate::manifest`) when one happens to sit next to the running binary — absent for a per-repo release or a debug build, which reports as "skipped" rather than a failure. **Verified against real `v0.1.0` tags on all three repos, 2026-08-11.** `embarch-api` and `embarch-umbrella` each released clean across all four targets on the first push. `embarch-core`'s first push failed exactly where predicted as the risk: the native `x86_64-unknown-linux-gnu` leg, because `libudev-dev` had only been arranged for the cross-compiled `aarch64-unknown-linux-gnu` leg (`Cross.toml`) — `ubuntu-latest` doesn't ship it the way a real Linux dev machine does. One added `apt-get install libudev-dev` step, gated to that leg, and moving the tag to the fixed commit produced a clean release across all four targets. `assemble-suite.yml` itself then caught a second real bug on its first-ever run: its `ls a.tar.gz b.zip 2>/dev/null | head -n1` line to find whichever archive extension a target used exits 2 whenever only one of the two globs matches — which is every target, since none ever has both. `ls` still finds and prints the real file, but also complains on stderr about the glob that missed, and the script's `pipefail` turns that into a fatal error regardless. Fixed with `shopt -s nullglob` and a plain array instead of `ls`/`head` (`embarch-umbrella` commit `4e6cb16`); re-run clean across all four targets, and `doctor` check 1 passed against the resulting real `suite-v0.1.0` manifest — the first time that check ran against anything other than a hand-crafted manifest.

15. **Topology detection is written once here, in a deliberately liftable shape — not extracted into a shared crate.** `embarch-api` needs the identical candidate-ordering and probe logic for `base_url = "auto"` (`embarch-api/design.md` §3.11, §7), so there are exactly two consumers and one algorithm. A fourth Rust crate in the suite, versioned and released, to hold one function that takes a candidate list and returns which one answered, is more machinery than the problem justifies at this scale. The alternative accepted instead: it lives in one self-contained module here, written under a constraint — **no umbrella-specific types cross its boundary**. No CLI structs, no umbrella config types, no `anyhow` context strings that only make sense in a `doctor` run; just pure functions over plain inputs (an "am I under WSL2" bool, a gateway-IP string, a port, an optional host) returning plain outputs. That constraint is what makes it copyable into `embarch-api` verbatim, and what makes extracting it into a real crate later a move rather than a rewrite, if a third consumer ever appears.

    The honest cost is drift: two copies that must agree, with nothing mechanical enforcing it. Three things keep that visible rather than silent — the module carries a comment naming its mirror and this decision, its unit tests are copied alongside it (they're pure-function tests, so they port with no adaptation), and `doctor`'s check 3 reports *which candidate won* rather than just pass/fail, so a divergence between what umbrella resolves and what `embarch-api` resolves surfaces as two different answers on the same machine instead of as a mystery.

16. **`doctor`'s token check (§5 check 4) needed the same liftable-copy treatment decision 15 gave topology detection — applied to `embarch-api/src/token_discovery.rs` this time, as `token.rs`.** A `doctor` that resolved the token differently than the `embarch-api` it's diagnosing would produce checks that pass or fail for reasons unrelated to the real thing, which is worse than no check. Checks 6-9 needed the same treatment applied to config shape rather than token logic: `config.rs` mirrors `embarch-api/src/config.rs`'s `[core]`/`[[projects]]` fields (minus `flash_format` and `env`, which nothing here reads — TOML tolerates the extra keys since neither struct denies unknown fields) but skips `embarch-api`'s own validation, since `doctor`'s entire job is reporting what's wrong rather than failing fast on the first bad field. Same accepted drift risk and mitigation as decision 15: a header comment naming the mirror, and (for `token.rs`) tests copied unchanged.

    Two implementation details worth recording because they weren't obvious going in. First, check 9's "comparable under WSL2 by stat-ing both paths" (§5) turned out to mean *reverse*-translating `artifact_path_for_core`'s UNC form back to a `/`-rooted path (undoing `init.rs`'s `wsl_unc_path`) and comparing canonicalized paths — not literally stat-ing a `\\wsl.localhost\...` string, which isn't a path WSL2's own filesystem namespace resolves. It only verifies anything when the UNC's embedded distro name matches `$WSL_DISTRO_NAME`; a different distro or non-WSL2 host reports "can't verify from here" rather than guessing. Second, a config that still declares an explicit (non-`"auto"`) `[core].base_url` — decision 9's default is `"auto"` but the field doesn't forbid the older form — makes `doctor` probe exactly that address rather than running decision 6's auto-detection candidate race, or `doctor` could end up diagnosing a *different* Core than the one `embarch-api` would actually talk to.

17. **`init` stops guessing a single board for a Zephyr/west repo; it scaffolds a `discovery = "zephyr-west"` project and defers board/chip selection to call time.** *(Decided 2026-08-13, shipped 2026-08-14. Full detail and rationale: [embarch-api/design.md](../embarch-api/design.md) §3 decision 12.)* Prompted directly by running `init` for real against the healthband repo (`milestone-6.md`, 2026-08-13): the repo has four real boards, and `init`'s old behavior — read whichever `build/build_info.yml` happens to exist, write one `[[projects]]` entry from it — silently picked a dev board's build over the production one, with no signal that a choice had even been made.

    For a repo shaped like a Zephyr/west project (`boards/*/*.yml` plus at least one `app/*/CMakeLists.txt`), `init` now writes the minimal `discovery = "zephyr-west"` schema ([embarch-api/design.md](../embarch-api/design.md) §3 decision 12: `source_path`, `west_binary`, `build_dir_root`, `flash_format`, `build_timeout_secs` — no `build_command`, `chip`, `artifact_path`, or `artifact_path_for_core`) instead of guessing a board. Decision 13's chip-placeholder behavior (write `CHANGE-ME`, let `doctor` block on it) no longer applies to this case at all — chip has nowhere to be written down for a `zephyr-west` project, since it's resolved per call from the selected SoC. Decision 13's `build_command`-derivation-from-`build_info.yml` logic, and its `artifact_path_for_core` UNC computation, both get lifted out of `init.rs` and become `embarch-api`'s call-time logic instead (same computation, different call site: once at scaffold time → every time a target is resolved).

    For a repo that isn't Zephyr/west-shaped, `init` is unchanged: one guessed `discovery = "static"` project from whatever generic signal exists, chip left as `CHANGE-ME`, exactly as decision 13 already describes.

    **Implemented 2026-08-14.** New `zephyr.rs`: `looks_zephyr_west_shaped` (the detection `init` branches on) and `count_valid_targets` (what `doctor` check 8 needs) — a **trimmed** liftable copy of `embarch-api/src/zephyr.rs`'s scanning half (`design.md` §3 decision 15's pattern, applied a third time: topology detection first, then `token.rs`/`config.rs`, now this), scoped to detection and counting only since `init`/`doctor` never assemble a build command or select one target the way `embarch-api` does. `init.rs` gained `render_zephyr_west_config`, branching before any of the old static-guessing logic runs; `west_binary` is still derived from `build/build_info.yml`'s recorded command when one exists (same file `init` already read, just taking argv\[0\] instead of the whole command), falling back to bare `west` (on `PATH`) with a warning otherwise. `config.rs` (the read-only mirror `doctor` uses) gained the same `Discovery` enum and optional `build_command`/`artifact_path`/`chip`/`west_binary` fields as `embarch-api`'s, so `doctor` sees exactly what `embarch-api` would.

    `doctor`'s checks 7-9 branch as designed (§5 table). Check 8's `zephyr-west` count is a **coarser approximation** than `embarch-api`'s real `list_targets` scan, by design: it counts a hardware revision as backed if *any* revision-suffixed file in the board directory names it, rather than checking the exact (board, soc, cpucluster, variant) tuple `embarch-api` checks — cheap enough for a doctor pass/fail signal, not precise enough to replace `list-targets` as the source of truth for what's actually buildable, which the check's own fix line points at.

    Verified end-to-end against a synthetic fixture (one board, two variants, one hardware-revision overlay backing only one variant at one non-default revision — the same shape `embarch-api`'s own decision-12 verification used) and a real running `embarch-core`: `init` detected the Zephyr/west shape, wrote the minimal config with no `chip`/`build_command` to edit, excluded `embarch/` cleanly (`git status` clean), and printed `list-targets`/`build --board ...` as the next step instead of "set chip." The generated config loaded directly into a real `embarch-api` binary and `list-targets` returned the correct file-backing-validated set — real cross-repo interop, not just parsing the same schema in isolation. `doctor` against that same repo: check 7 correctly failed (`west` genuinely not on this sandbox's `PATH`), check 8 correctly passed (3 real valid targets counted), check 9 correctly passed with the new "computed per call, nothing to compare ahead of time" message. 67 unit tests (10 new in `zephyr.rs`/`config.rs`); `cargo build`/`cargo clippy --all-targets -- -D warnings`/`cargo test` clean.

18. **`doctor` check 5 distinguishes "no probe attached" from "a probe is attached but this user can't open it" — closing item 7 of the 2026-08-15 design-improvement review.** Check 5 previously reported zero probes in `/status`'s list as "warn — a probe can legitimately be unplugged," which is true but actively misleading for the most common Linux first-run failure: a probe that *is* physically attached but inaccessible because no udev rule grants the current user permission to open it, which `probe-rs`'s enumeration on Linux can silently under-report or fail to open depending on the failure mode. New sub-check, Linux-only (macOS/Windows don't have this permission model): after `/status?probes=1` returns zero probes, `doctor` additionally checks `/sys/bus/usb/devices/*/idVendor`+`idProduct` (or equivalent) for a device matching a known debug-probe VID (ST-Link, J-Link, CMSIS-DAP, FTDI, ESP USB-JTAG — the same vendor list `embarch-core/design.md` §4 already names) that the enumeration missed — a hit means "attached but not permitted," reported as a distinct fail (not warn) with the fix line pointing at the standard udev-rules install (`probe-rs`'s own documented udev rules, or the vendor's); a genuine miss on both checks stays the existing "warn — legitimately unplugged."

A mismatch fails with a fix line naming the exact `west flash` command dev-bench's own `embarch-dev-bench/design.md` §3 decision 13 already established as the human step. See §5's table for the check's placement.
20. **The liftable-copy pattern (§3 decisions 15/16) gets a CI job diffing the mirrored files against their source, instead of extracting a fourth crate — closing item 14.** Three modules now live in this pattern (topology detection, `token.rs`, `config.rs`), and the original one-function/two-consumers rationale is stretched thinner with each addition — but `embarch-study-designer/design.md` §3 decision 8 already established unpublished-git-dependency distribution as cheap in this suite, which weakens the "a fourth crate is too much machinery" argument that justified the copy approach in the first place. Resolved without reversing course: rather than extract `embarch-common` now (a real migration, for modules that are still small), a new CI job (`.github/workflows/mirror-drift.yml` or equivalent, run in whichever repo is easier to trigger from — likely `embarch-umbrella`'s, since it holds the copies) fetches the corresponding file from `embarch-api`'s repo at the commit `embarch-umbrella`'s own header comment names as its mirror source, diffs it against the local copy, and fails the build on any difference — replacing "a comment and hope" (§3 decision 15's own phrase) with an actual mechanical check. If a fourth module gets added to this pattern before a real cross-repo CI diff proves painful to maintain, that's the trigger to reconsider `embarch-common` instead, not before.
21. **`embarch setup --dry-run` prints the plan before an elevated run actually executes it — closing item 53.** `setup` today runs directly, including its elevated leg (§3 decision 7) — the elevation friction that decision already flags is partly a "what is this about to do to my machine" problem, worse when the answer requires trusting a binary you just downloaded. `--dry-run` runs every detection step (topology, service-install-needed-or-not, token-file-exists-or-not) exactly as `setup` already does, then prints the concrete actions it would take (which service-manager calls, which files it would write, whether elevation is needed) without executing any of them — reusing `setup`'s own detection code path, not a second parallel implementation.
22. **`doctor` gains three more first-day checks: bind-address-vs-topology reachability, firewall state, and disk space — closing item 54's remaining bullets (probe permissions is item 7/decision 18 above).** (a) A topology iii (`local` bind under WSL2 mirrored networking, or `wsl-host`) Core that bound `127.0.0.1` under the new default (`embarch-core/design.md` §3 decision 6's 2026-08-15 amendment) without `setup` having widened it is exactly the "reachable from *this* interface but not the one WSL2 can actually use" failure that default now makes possible for the first time — check reports the bind address `/status` was reached at vs. what the detected topology needs, failing when they don't match rather than reporting bare unreachability. (b) A Windows Firewall / Linux firewall (`ufw`/`firewalld`) check: attempts the same connectivity probe topology detection (§3 decision 6) already performs, and when it fails, checks (best-effort, OS-specific) whether an active firewall profile is the likely cause versus Core simply not running — informational, since firewall state can't always be introspected without elevation itself. (c) A disk-space check on the filesystem backing `embarch/build` and `study_results/` (once studies exist) — warn below a threshold (a few GB, generous given firmware artifacts are small but Zephyr's `zephyr/` toolchain checkout and repeated pristine rebuilds are not), since a build failing from `ENOSPC` reads as a mystifying compiler error otherwise.
23. **`doctor` check 10 (MCP registration) now actually spawns `embarch-api` and confirms the MCP handshake completes, not just that a registration entry exists — closing item 55.** The failure mode check 10 exists to catch — registered but broken — was exactly the one it couldn't detect: `claude mcp add` succeeding says nothing about whether the registered command actually starts and speaks MCP. New behavior: after confirming the registration entry (unchanged), `doctor` spawns the exact registered command with a short timeout and sends a minimal MCP initialize handshake, reporting success/failure/timeout distinctly — reusing whatever `rmcp`-compatible client capability is simplest to invoke one-shot from a Rust process (a thin hand-rolled JSON-RPC init exchange over stdio is sufficient; a full `rmcp` client isn't needed for one round-trip).
24. **Version skew between `embarch-core`/`embarch-api` stays a warning, not a refusal — decided, not left open (closing item 56).** §3 decision 14's warn-only posture is kept deliberately rather than escalated to a hard refuse: refusing to run a mismatched pair would obstruct the exact in-development, fast-iterating state this suite is still in (independent per-repo releases, `embarch-core/design.md` §3 decision 13's own `contract_version` warn-not-refuse precedent, `embarch-api/design.md` §3 decision 17). Revisit only once the suite has shipped enough stable releases that a mismatch is more likely an operator mistake than an expected in-progress state.
25. **`embarch setup --uninstall` reverses a machine setup, matching `embarch init --uninstall`'s existing reversibility promise — closing item 51.** `init --uninstall` already reverses a repo integration (§3 decision 12); nothing symmetric existed for `setup` itself. `--uninstall` reverses, in order: stops and unregisters the Core OS service (`embarch-core uninstall`, already exists), removes the machine-wide token file (§6; a fresh `setup` afterward regenerates one, matching normal first-run behavior), and — **superseded by decision 28**: originally printed (did not execute) the `PATH` line to remove, matching decision 3's refinement that `setup` never edits `PATH` itself; now that decision 3's refinement is reversed, `--uninstall` actually removes the canonical install directory and the real `PATH` additions decision 28 makes, per that decision's own uninstall bullet. Does not touch a firmware repo's own `embarch/` integration — that stays `init --uninstall`'s job, unchanged.
26. **`study_results/` retention and per-target `embarch/build` directory pruning both get an explicit policy instead of "grows forever" — closing item 21's remaining bullets (own `setup --uninstall` is item 51/decision 25 above).** `study_results/<study_id>/` (`embarch-core`, once `study.rs` exists) and `embarch/build/<target-hash>/` (`embarch-api`, one per distinct board×variant×revision×app×snippets×extra_args combination, decision 12) both currently have no cleanup mechanism at all. New `embarch doctor --prune` flag (opt-in, never automatic — deleting build artifacts or study results is not something `doctor`'s normal read-only pass should ever do silently): reports (always) how many `study_results` entries exist and their total size, and how many distinct build-dir combinations exist per project; with `--prune`, offers to delete `study_results` entries older than a configurable age (default 30 days) and build directories for a target combination no longer among the project's currently-valid `list_targets` output (e.g. a variant that no longer exists in the repo) — never a currently-valid target's build dir, regardless of age, since rebuilding it is the expensive part `embarch-api`'s caching-nothing design (decision 12) already avoids elsewhere.
28. **`setup` performs a real install — copies all three binaries to a canonical per-user location and persists `PATH` for real — reversing decision 3's sibling-lookup-plus-printed-hint refinement, which turned out to be bad design.** *(Decided 2026-08-17, prompted directly by a real `wsl-host` onboarding run the same day: the sibling-lookup mechanism reported the wrong `embarch-core` path for that topology — §10 — and the user directly requested this reversal rather than accepting it as a one-off cosmetic bug.)*

    **Implemented 2026-08-17.** New `install.rs`: `canonical_bin_dir` (per-user, no elevation — `%LOCALAPPDATA%\embarch\bin` on Windows, `$XDG_DATA_HOME` or `~/.local/share/embarch/bin` on Unix), `install_binaries` (copies from wherever the running `embarch` sits, skipping a binary that isn't present and no-op-ing when source already equals destination), and `install`/`uninstall` top-level entry points `setup.rs` calls. `PATH` mutation is real on both platforms: on Windows, `winreg` reads/writes `HKCU\Environment\Path` directly (never `setx`, which silently truncates a long `PATH`), preserving whether the existing value was `REG_SZ` or `REG_EXPAND_SZ` — downgrading a `%VAR%`-expanding value to a plain string on write would have been exactly the corruption this decision exists to avoid, so the raw registry value (not the high-level string-only API) is read and written back with its original type intact; on Unix, a dedicated sourced env file (`~/.local/share/embarch/env`) plus one idempotent line added to whichever of `.bashrc`/`.zshrc` already exist — resolving decision 3's original "which shell, which of several startup files?" objection, since only one line, sourcing one file, ever needs adding anywhere. Both directions (`ensure_*`/`ensure_not_*`, `ensure_path`/`remove_path`) are implemented and tested for idempotency. `locate.rs`'s sibling-lookup (`next_to_me`) is deleted outright, not merely deprioritized: `locate_core`/`locate_api` now resolve via env var → saved state → `PATH` → (WSL2 only) the real canonical Windows location — resolved from WSL2 by shelling out for the real per-user `%LOCALAPPDATA%` value, same technique `token.rs` already uses for the machine-wide `%ProgramData%` case, since WSL2 has no direct view of the Windows username needed to derive a per-user path by hand — falling back to the older fixed conventional directories only if that fails. `setup --uninstall` (decision 25) is implemented for real for the first time: stops/uninstalls the Core service if locatable, removes the token file, and calls `install::uninstall()`.

    **Not verified**: no linker for `x86_64-pc-windows-msvc` exists in this sandbox (the same `aws-lc-sys`/C-toolchain gap `embarch-core/design.md` §7 already documents for this repo), so the Windows-specific `winreg` code was verified by extracting it into a standalone throwaway crate and running `cargo check --target x86_64-pc-windows-msvc` against just that logic (clean) — real end-to-end behavior on Windows (registry write actually taking effect, a new shell actually picking up the `PATH` change) still needs a real Windows machine. The Unix path (env file + rc-file editing) and the rest of `install.rs`/`locate.rs`/`setup.rs` are fully built, tested (11 new unit tests, 79 total passing), and clippy-clean on the host (Linux) target. Not yet released — ships in whatever version comes after `v0.1.0`.

    **Canonical location**: `~/.local/share/embarch/bin/` (Linux, macOS, and — since it's the same filesystem — the directory `setup`'s WSL2 leg writes into too), `%LOCALAPPDATA%\embarch\bin\` (Windows). Chosen specifically because it needs no elevation to write to, unlike a system-wide location (`/usr/local/bin`, `C:\Program Files\...`) — keeping decision 7's "elevation is rare, only for the Core service" property intact for this new step too.

    **The copy step**: on every `setup` run, copy (overwriting) `embarch`, `embarch-core`, and `embarch-api` from the currently-running `embarch` binary's own directory (`current_exe()`'s parent — wherever the release archive was unpacked) into the canonical location. This is the *only* place "look at my own directory" logic remains — a one-time install source at `setup` time, not an ongoing resolution mechanism the way decision 3's sibling lookup was. After `setup` runs once, the unpacked archive directory can be deleted; nothing depends on it continuing to exist.

    **`PATH` mutation, done for real, idempotently — not just printed:**
    - *Windows*: edit `HKCU\Environment\Path` (user-scope registry — no elevation needed, distinct from the Core-service install's elevation requirement) directly via the registry API, **not** `setx`, which silently truncates a `PATH` value over roughly 1024 characters — a real corruption risk, not a hypothetical one. Check for the canonical directory's presence (case-insensitive) before appending, so repeated `setup` runs stay idempotent. Broadcast `WM_SETTINGCHANGE` (`SendMessageTimeout` to `HWND_BROADCAST`) so already-open Explorer windows notice; an already-open shell still needs to be restarted to see the new `PATH`, which is an OS constraint no installer can work around.
    - *Unix* (Linux, macOS, and WSL2's own shell): write a small dedicated env file, `~/.local/share/embarch/env` (one line: `export PATH="$HOME/.local/share/embarch/bin:$PATH"`), rather than editing a shell rc directly. This is what resolves decision 3's original "which shell, which of the four startup files?" objection — only *one* idempotent sourcing line (`. "$HOME/.local/share/embarch/env"`) needs adding to whichever rc files actually exist (`~/.bashrc`, `~/.zshrc` — skip one that doesn't exist, never create a new one), each checked for the line's presence before appending so re-running `setup` never duplicates it.

    **Fixes the `wsl-host` binary-path misreport as a side effect.** Decision 7's "Locating the Windows-side binary" (bounded search of the conventional install location) becomes exact rather than a search, once the canonical location is a known constant: `%LOCALAPPDATA%\embarch\bin\embarch-core.exe`, reachable from WSL2 at `/mnt/c/Users/<user>/AppData/Local/embarch/bin/embarch-core.exe`. The `embarch-core: <path>` line a `wsl-host` `setup` run prints can now report this real Windows-side path directly, instead of falling back to the local Linux sibling the way it did in the run that found this bug (§10).

    **`setup --uninstall` (decision 25) gains a matching real reversal**: delete the canonical directory's copied binaries, remove the `HKCU\Environment\Path` addition on Windows, and remove both the dedicated env file and the sourcing line(s) added to rc files on Unix — replacing decision 25's "prints, does not execute" removal with an actual one, symmetric with this decision's real install.

    **Trade-off accepted explicitly**: `setup` now writes outside the locations it already owned (token file, `umbrella.toml`) — a registry key and two dotfiles. Accepted because every one of these writes is per-user, needs no elevation, and is idempotent/reversible, which is materially less risk than the system-service install decision 7 already requires elevation for.

29. **A release-CI job asserts each repo's `Cargo.toml` version matches its pushed tag — closing item 25, recorded here since it's release engineering and this is where §3 decision 14's release CI already lives.** Prompted by a real, already-corrected drift (`embarch-core/design.md` §11's 2026-08-12 entry: Cargo.toml had drifted from the `v0.1.1` tag, caught only because `doctor` check 1 happened to compare `--version` against the tag by hand that day). New step in each repo's `release.yml` (`embarch-core`, `embarch-api`, `embarch-umbrella`): before building any target, assert `Cargo.toml`'s `version` field equals the tag that triggered the workflow (stripped of a leading `v`), failing the release outright on mismatch rather than shipping a binary whose `--version` output disagrees with the tag that produced it — exactly the class of bug `doctor` check 1's manifest comparison depends on nobody forgetting to avoid.

## 6. Token handling

Umbrella does not invent any token mechanism — [embarch-token.md](../embarch-token.md) remains the source of truth. What it adds is making the existing mechanism actually happen at setup time:

- **Same-machine topologies (i–iv):** ensure Core has started at least once, so `token_store` has generated and persisted the machine-wide token file, then confirm `embarch-api` can discover it (including the WSL2⟷Windows `/mnt/c` translation `token_discovery.rs` already does). No token value is ever written into a config file.
- **Separate-machine (v):** there is no shared filesystem, and per [embarch-token.md](../embarch-token.md) §8 this is an unsolved gap. Umbrella's contribution is not to solve it but to make it a 10-second manual step: `doctor` prints the exact `export EMBARCH_TOKEN=...` / `setx` line to run on the API machine, with the value read from the Core machine by the human.

## 7. MCP registration options

`init` uses the local-scope registration of the first row (§3 decision 12). The rest are recorded because the question "how does this get committed for the whole team" is the obvious next one, and the answer isn't the same as the local one.

| Option | Shape | Pro | Con |
|---|---|---|---|
| **Local scope** (v1) | `claude mcp add` at per-project/per-user scope, pointing at `embarch-api --config <repo>/embarch/embarch.toml` | Touches nothing tracked; per-repo scoped; trivially reversible | Every engineer runs `embarch init` themselves |
| Committed `.mcp.json`, PATH + relative config | `{"command": "embarch-api", "args": ["--config", "embarch/embarch.toml"]}` | No absolute paths, portable, works for everyone who ran `embarch setup` | Requires `embarch-api` on `PATH`; every engineer still needs their own `embarch/` folder |
| Committed `.mcp.json`, env expansion | `{"command": "${EMBARCH_API_BIN}", "args": ["--config", "${EMBARCH_API_CONFIG}"]}` | Fully machine-independent | Two env vars to get wrong, with an opaque failure when unset |
| Committed wrapper script | `{"command": "./embarch/mcp.sh"}` | One indirection point; can preflight | A shell script doesn't work on native Windows; needs a `.cmd` twin |
| Umbrella as the MCP server | `{"command": "embarch", "args": ["mcp", ...]}` | Starting the agent starts the stack | Rejected — §3 decision 5 |
| Absolute paths | `{"command": "/home/me/.../embarch-api", ...}` | Works immediately | Broken for every other engineer; non-starter if committed |

If the integration is ever committed, row 2 is the recommendation, since `embarch setup` is already the thing that puts `embarch-api` on `PATH`.

## 8. Command surface

| Command | Scope | Behavior |
|---|---|---|
| `embarch setup` | once per machine | Detect topology (§3 decision 6), install Core as a service where possible, ensure the token file exists, put both binaries on `PATH`, record the class + Windows-side Core path, then run `doctor`. `--dry-run` (§3 decision 21) prints the plan without executing it; `--uninstall` (§3 decision 25) reverses a prior `setup` |
| `embarch init` | once per firmware repo | Scaffold `embarch/embarch.toml` + `embarch/build/` (§3 decision 10, 13), exclude locally, register the MCP server (§3 decision 12), then run `doctor`. `--uninstall` reverses all of it |
| `embarch doctor` | anytime | §5's full chain. `--json`. `--prune` (§3 decision 26) reports/cleans stale `study_results/`/build-dir entries, opt-in only |
| `embarch status` | anytime, cheap | One `/status` call: is Core up, which class, how many probes. `--json` |
| `embarch up` / `embarch down` | fallback | Start/stop Core — installed service first, foreground `embarch-core run` only if no service exists (§3 decision 4, 7) |

Exit codes follow `embarch-api`'s CLI convention (`embarch-api/design.md` §5a): `0` on success, `1` on any failure with the message on stderr (or folded into the `--json` object on stdout when `--json` is set), `2` from `clap` for a malformed invocation.

## 9. Relationship to the rest of the suite

- **`embarch-core`:** umbrella shells out to its CLI (`install`, `uninstall`, and the `start`/`stop` pair proposed in `embarch-core/design.md` §10) and calls two of its HTTP endpoints (`/status`, `/dev-bench/port`). It adds no Core capability and holds no hardware knowledge.
- **`embarch-api`:** umbrella writes its config and shells out to its CLI for verification. The `base_url = "auto"` resolution lives there, not here (§3 decision 9). Umbrella never re-implements build orchestration.
- **`embarch-study-designer` / `embarch-dev-bench`:** umbrella's only involvement is two `doctor` checks (schema-version agreement, dev-bench port presence). It does not build, flash, or configure dev-bench firmware — that stays a human `west flash` (`embarch-dev-bench/design.md` §3 decision 13).
- **`embarch-promptu`:** out of scope. Umbrella registers the MCP server; it does not install skills or prompt patterns.

## 10. Open questions / future work

- **The EmbArch UI.** Explicitly out of v1 scope, and explicitly anticipated: a small local UI where an engineer can see whether Core is connected and drive `embarch-api`'s operations by hand, without asking an agent and without typing CLI subcommands. §3 decision 11's `--json` contract on `status`/`doctor` exists to be its data source. Unresolved: whether it's a native app, a local web page served by a new process, or a tray/menubar item; and whether it drives `embarch-api` by shelling out to the CLI or by embedding it.
- **A `local` classification under WSL2 is ambiguous about *where* Core is** (§3 decision 6's refinement note): with mirrored networking, a Windows-hosted Core and a WSL2-guest-hosted Core both answer at loopback. Addressing is unaffected, but `up` needs to disambiguate before deciding whether it can start Core itself or must print an elevated Windows command (decision 7). Detection already knows whether it's under WSL2; the open part is what `up` does with that. Not yet designed, and it can't be resolved from this machine — only NAT-mode WSL2 has ever been observed here.
- **Finding the probe-rs `chip` name currently requires installing a separate tool** — still true for a `discovery = "static"` project (§3 decision 13 unchanged there). For a `discovery = "zephyr-west"` project, §3 decision 17 / `embarch-api/design.md` §3 decision 12 covers the common case automatically via a maintained SoC→chip table, but an *unmapped* SoC hits this exact same wart: `cargo install probe-rs-tools && probe-rs chip list`, a Rust toolchain install in the middle of a download-a-binary onboarding. The Core-side fix recorded here — `embarch-core chip-list [filter]` as a CLI subcommand, `embarch-core/design.md` §10 — is still the right complementary fix for that fallback path, not superseded by the table. Not yet scoped into a milestone.
- ~~**`embarch-api/design.md` §3 decision 12's open sub-questions**~~ — resolved 2026-08-13 (folded into that decision); also resolved a new `embarch-core` endpoint, `/resolve-chip` (`embarch-core/design.md` §3 decision 8), which `init`/`doctor` don't call directly but which `embarch-api`'s call-time chip resolution now depends on.
- **Config fragments / includes**, so `[core]` isn't duplicated into every firmware repo's `embarch/embarch.toml` (§3 decision 10). Needs an `include` mechanism in `embarch-api`'s config loader; deferred rather than rejected.
- **Elevation is a hard edge on every platform** (§3 decision 7). `setup` needs an elevated shell once — Administrator on Windows, root/polkit for a systemd system unit — and umbrella deliberately won't self-elevate anywhere. Whether that's acceptable onboarding friction is a real question that only a second engineer walking the guide can answer. A user-level service (systemd `--user`, launchd LaunchAgent) would avoid it on Linux/macOS but wouldn't start before login, which defeats decision 3's whole point; not yet weighed properly.
- **Nothing here is validated.** No repo, no code — and every claim about topology detection (WSL2 mirrored-vs-NAT networking, the `401`-counts-as-a-hit probe, locating a Windows-side binary from WSL2) is reasoned rather than observed. Topology iii gets validated first because it's in daily use; i/ii/iv/v are reasoned only, and macOS specifically has no machine to test on yet.
- ~~**Version-skew policy is a warning, not an enforcement**~~ (§3 decision 14) — decided, not left open, 2026-08-15 (§3 decision 24): stays warn-only deliberately, revisit only once the suite has enough stable releases that a mismatch is more likely operator error than expected in-progress state.
- ~~**Uninstall is only specified for `init`, not for `setup`.**~~ — resolved 2026-08-15 (§3 decision 25): `embarch setup --uninstall` now reverses the service install, token file, and prints the `PATH` line to remove.
- ~~**Found (2026-08-17), live on a real Windows machine during Milestone 1 onboarding**: `setup`'s printed `PATH` hint was always POSIX `export PATH="<dir>:$PATH"` syntax, unconditionally — invalid on native Windows `cmd.exe`.~~ — folded into **decision 28** (2026-08-17): `setup` now mutates `PATH` for real, per-platform, rather than printing a hint at all; this bug is moot once that ships. `embarch-user-guide.md` §3.1 documents the manual translation as a stopgap until decision 28 is implemented.
- ~~**Found (2026-08-17), on the same real `wsl-host` run**: `setup`'s printed `embarch-core: <path>` line reported the local WSL2-side Linux sibling instead of the Windows-side `embarch-core.exe` a `wsl-host` topology actually needs.~~ — folded into **decision 28**: the canonical install location makes the Windows-side path an exact known constant instead of a search, so this line can report it directly once that decision ships. §10's older note below ("locating a Windows-side binary from WSL2... is reasoned rather than observed") is what anticipated this class of bug in the first place — now confirmed live rather than just reasoned-about.

## 11. Relationship to the user guide

[embarch-user-guide.md](../embarch-user-guide.md) was originally written against this design ahead of implementation — i.e. against tooling that didn't exist yet — with a clearly-marked appendix carrying the manual steps that worked in the meantime. That was deliberate: the guide doubled as this milestone's acceptance criteria. As of `v0.1.0` shipping (this milestone's DoD, §3.8 in [milestone-6.md](milestone-6.md)), the guide now describes the real, released tool; the old appendix is kept only as historical/reference material, not as "what you actually have to do" (2026-08-17 — corrected here after the guide itself was found still saying the opposite, live, during a real Windows onboarding attempt).
