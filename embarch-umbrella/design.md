## 1. Purpose and scope

`embarch-umbrella` is the sub-project that gets a firmware engineer from *nothing installed* to *`embarch-api build_and_flash my-project` works, from a terminal or from Claude Code* — on whatever topology their machine happens to be (Core native on Windows with the API in WSL2, both native on a Mac, both native on Linux, or Core on a separate box). It ships one binary, named `embarch` (§3 decision 2), with three jobs: **set up**, **verify**, and **start Core when it isn't already running**.

The reason it exists as its own sub-project rather than as more subcommands on an existing binary: it is the only component that knows about *both* `embarch-core` and `embarch-api`, and it is the binary a person downloads when they have neither. `embarch-api` can't hold this — it would have to install Core's OS service and register MCP servers, neither of which a thin build-orchestration layer has any business doing, and it can't be the answer to "what do I download first" when it's one of the two things being set up.

`embarch-umbrella` is **not**:
- **A process supervisor or daemon.** It has no restart loop, no health polling, no resident process. Core's own cross-platform service install (`embarch-core/decisions.md` §3.3) is what keeps Core running; umbrella's `up` exists only for when that isn't in place or has died (§3 decision 4).
- **In the runtime data path.** Nothing routes through umbrella after setup. It is not an MCP server, not a proxy, and deliberately not the process an MCP client spawns (§3 decision 5). If umbrella is deleted from a working machine, the stack keeps working.
- **A hardware or build layer.** It never links `probe-rs` or `serialport`, never runs a build command. Every capability it appears to have is a shell-out to `embarch-core` or `embarch-api`, or an HTTP call to Core's existing endpoints.
- **Multi-machine orchestration.** No SSH, no remote agent, no remote install. A Core on a separate box (a Pi over wifi) is started by a human on that box; umbrella only detects and verifies it (§3 decision 8).
- **A GUI.** A small EmbArch UI — a human glancing at whether Core is up, rather than asking an agent — is real anticipated scope but explicitly out of this document's v1 (§10). What v1 owes it is a stable machine-readable status contract (§3 decision 11).

## 2. Architecture overview

```
                    setup / init / doctor / status / up / down
                                    |
                                 embarch                    <- this sub-project
                          /         |          \
        shells out to     |         |           |  HTTP+Bearer (GET /status,
        embarch-core CLI  |         |           |  /dev-bench/port)
        (install/start)   |         |           v
                          |         |      embarch-core
                          |         |
                          |         +-- shells out to embarch-api CLI
                          |             (list_projects, status) and reads/writes
                          |             its config
                          |
                          +-- writes <firmware-repo>/embarch/embarch.toml
                              and registers the MCP server (local scope)

after setup, the runtime path has no umbrella in it:

Claude Code --stdio--> embarch-api --HTTP+Bearer--> embarch-core --> hardware
human ------CLI------> embarch-api ----------------^
```

Both of `embarch-api`'s front-ends stay first-class after setup: an MCP client spawning it over stdio, **and** a human running `embarch-api <subcommand>` directly (`embarch-api/design.md` §5a). Umbrella's job is to make the second one ergonomic too — a resolved config path in the environment, and the binary on `PATH` — not just to wire up the agent path.

## 3. Locked-in design decisions and rationale

1. **Language: Rust**, one static binary with no runtime dependencies, matching the rest of the suite. It must run on a machine where nothing else from EmbArch is installed yet, so a runtime (Python, Node) or a system library dependency would be self-defeating.

2. **Repo `embarch-umbrella`, binary `embarch`.** The repo name says what it is in the suite; the binary name is what a new engineer types on their first day (`embarch setup`, `embarch doctor`). `embarch-umbrella setup` was rejected purely on ergonomics — this is the most-typed command in the suite for someone who has never used it before.

3. **Core is always an installed, autostarting OS service — that, not a launcher, is the actual answer to "one button starts everything."** On the four same-machine topologies (§4), if Core autostarts at boot there is nothing for a human to start, ever: `embarch-api` is invoked per-use (spawned by an MCP client, or run directly by a human), and it finds a Core that is already up. So the problem is a *one-time setup* problem plus an *ongoing verification* problem, not a process-management problem. `embarch-core install` already exists and already handles all three OSes via the `service-manager` crate (`embarch-core/decisions.md` §3.3) — umbrella's contribution is making sure it actually got run, with the right environment, on the right machine.

    *Refinement from implementing this (2026-08-05): `setup` does **not** edit `PATH`, despite this decision originally listing that as one of its jobs.* Decision 14's single release archive puts all three binaries in one directory, so umbrella finds `embarch-core` as a sibling of itself with no environment surgery at all. Editing a shell rc (which shell? which of the four startup files?) or the Windows registry is invasive, easy to get subtly wrong, and awkward to undo — for a benefit the sibling lookup already delivers. `setup` prints the one `export PATH=...` line and leaves the choice to the operator.

    **Reversed 2026-08-17 (decision 28) — this refinement is bad design and is being undone.** Sibling-lookup ties correct operation to wherever the archive happened to be unpacked staying put forever, and a real `wsl-host` run the same day already surfaced the confusion this causes (§10/changelog, 2026-08-17: the printed `embarch-core: <path>` line reported the local sibling instead of the Windows-side binary a `wsl-host` topology actually needs). See decision 28 for the replacement: a real install step plus real, safe `PATH` mutation.

4. **`up`/`down` exist, but as a fallback, not the main path.** They cover: the service isn't installed (someone wants to try the stack before committing to a service install), the service died, or a foreground Core is wanted for debugging. `up` prefers starting the installed service and only spawns a foreground `embarch-core run` if there is no service to start (§3 decision 7) — a directly-spawned Core dies with the shell that started it, which is a confusing failure mode to hand someone as the default.

    *Refinement from implementing this (2026-08-05): the foreground fallback is **opt-in**, not automatic.* Distinguishing "no service installed" from "start failed for some other reason" means pattern-matching each backend's error text, which is exactly the per-OS fragility decision 4 exists to avoid. So a failed `up` prints the three real options — install it, elevate, or `embarch up --foreground` — and does nothing else. `--foreground` then runs Core in the caller's terminal (blocking, Ctrl-C to stop) rather than detaching, so nobody ends up with a Core that vanished when they closed a window. A `remote` topology refuses `up`/`down` outright rather than falling back to a local binary, which would start a second, wrong Core.

5. **Umbrella is deliberately *not* the process the MCP client spawns.** The tempting alternative — register `embarch mcp` as the MCP server so that starting Claude Code brings the whole stack up — was considered and rejected for v1. It puts umbrella permanently in the stdio hot path, makes every MCP-transport problem a two-binary debugging exercise, and buys little once decision 3 means Core is already running. `.mcp.json`/local MCP registration points straight at `embarch-api`, exactly as it does today.

6. **Topology is auto-detected by probing, not declared — and only the *class* is ever persisted, never an address.** Detection builds an ordered candidate list and races a short-timeout `GET /status` at each:
   - `http://127.0.0.1:4884` — covers Core-local (Mac, Linux, Windows-native) *and* WSL2 in mirrored-networking mode, where localhost already reaches the Windows host.
   - if running under WSL2 (`/proc/version` contains `microsoft`, or `WSL_DISTRO_NAME` is set) — `http://<default-gateway>:4884`, from `ip route show default`. This is the NAT-mode WSL2 path.
   - a user-supplied host, if one was given at `setup` or is recorded in config.

   First responder wins. **A `401` counts as a hit, not a miss**, and is reported distinctly: it means Core is there and the token doesn't match, which is a completely different fix from "Core isn't running." Connection-refused/timeout is a miss.

   *Two refinements from implementing this (2026-08-05).* **"Race" means ordered-sequential, not concurrent** — ordering is the whole point, and the common miss (nothing listening) is a connection refusal that returns immediately rather than burning the per-candidate budget, so a concurrent fan-out would buy nothing and lose the preference order. The 500ms budget is only ever paid where packets are silently dropped. And a **third outcome** turned out to be worth distinguishing: something that answers HTTP with neither `200` nor `401` isn't Core at all — most likely another service squatting the port — which is not a hit, but reporting it as "nothing there" would send someone to start a Core that can't bind anyway.

   *A subtlety this leaves open:* under WSL2 with mirrored networking, a Windows-hosted Core answers at loopback and is therefore classified `local`, indistinguishable by address from a Core running inside the WSL2 guest. Harmless for addressing — both are reachable the same way — but `up` must not infer "I can start Core here" from a `local` classification without also checking whether it's under WSL2 (decision 7's elevation path). Noted in §10. What gets written down is the resolved *class* — `local`, `wsl-host`, or `remote` (plus the host, for `remote` only) — never the WSL2 gateway IP, which is dynamic and has already gone stale once in this suite's own records (`embarch-core/decisions.md` §7 recorded `172.29.64.1`; `embarch-api`'s real `config.toml` had `172.22.128.1`). Per §3 decision 9 the address is re-resolved at every use instead.

   **Moved into `embarch-topology`, 2026-08-21 (decision 15's own update carries the full story) — the algorithm above is unchanged, just no longer implemented twice.** This module (and `env.rs`/`probe.rs` alongside it) are deleted from this repo; `status`/`setup`/`doctor` all call `embarch_topology::software::resolve_software_topology()` directly.

7. **Starting Core across the WSL2⟷Windows boundary is supported, because it's the same physical machine — and, as of 2026-08-18, elevation is umbrella's problem to *trigger*, not just to report. Elevation is required on every OS, not just Windows.** WSL2 can invoke a Windows binary directly (`/mnt/c/.../embarch-core.exe`), so `up` from the WSL2 side is mechanically possible. Controlling a *system* service, however, needs elevation — and not only on Windows: a systemd system unit wants root or a polkit prompt too, confirmed on Linux where an unprivileged `embarch-core start` fails with "Interactive authentication required" (`embarch-core/decisions.md` §3.3, corrected 2026-08-05 — this decision originally treated elevation as a Windows-only tax). Locating the Windows-side binary: `EMBARCH_CORE_EXE` env var, else the path recorded at setup, else a bounded search of the conventional install location — **becomes an exact known path once decision 28 ships** (`%LOCALAPPDATA%\embarch\bin\embarch-core.exe`), rather than a search.

    **Reversed, 2026-08-18 (`embarch-core/decisions.md` §3 decision 3 carries the full mechanism and rationale).** This decision originally had umbrella (and `embarch-core`) never self-elevate anywhere — print the exact command, exit nonzero, let a human paste it into a shell they open themselves — reasoned as acceptable *because* decision 3 makes elevation rare (one `setup`, then autostart forever). That reasoning covered first-time install but not a case that surfaced for real the same day: updating an *already-installed* Core's binary, which has no reason to be rare once the suite is under active development, and which had no supported path at all — only manual service-stop/binary-copy/service-start surgery in a hand-opened elevated shell (found live, deploying a `/resolve-chip` fix ahead of api milestone 7). Self-elevation now happens in `embarch-core` itself — not a second copy of the logic here in umbrella — since umbrella already reaches every privileged operation by shelling out to that same CLI rather than re-deriving per-OS service control (this decision's own original point). `up`/`down`/`setup` inherit self-elevation for free the moment `embarch-core`'s `install`/`uninstall`/`start`/`stop`/`update` do it; nothing in umbrella's own code changes. The one case this doesn't cover — no GUI and no TTY (CI, a script, a headless remote session) — falls back to exactly this decision's original behavior, since there's no one there to click through a prompt anyway.

8. **A Core on a genuinely separate machine is detect-and-verify only.** No SSH, no remote install, no remote start. `doctor` reports it as reachable-or-not and tells the human to go start it there. This topology previously also **could not flash**: `/flash` reads `firmware_path` from Core's own local disk and there was no shared filesystem to put an artifact on (`embarch-api/design.md` §9). **Resolved 2026-08-15**: `embarch-api`'s multipart upload for a `remote` topology (`embarch-api/design.md` §3 decision 15, `embarch-core/decisions.md` §3 decision 10) closes this — flashing now works for this topology, just via uploaded bytes rather than a shared path. `doctor` and §4's matrix are updated to match.

9. **`base_url = "auto"` is implemented in `embarch-api`, not in umbrella.** Umbrella could write a resolved URL into the config at setup time, but that just relocates the staleness problem — the WSL2 gateway IP changes on WSL restart, long after setup ran. So the config gets the literal string `auto` and `embarch-api` re-runs decision 6's candidate race itself, per process, at the point it first needs Core. Umbrella and the API therefore share one resolution algorithm; it belongs to the API because the API is the thing that has to be correct at 3pm on a Tuesday, not at install time. Full schema/behavior: `embarch-api/design.md` §4, §7.

10. **Per-firmware-repo project config lives in an `embarch/` subfolder of that repo, scaffolded by `embarch init`.** Running `embarch init` inside a firmware repo produces:

    ```
    <firmware-repo>/embarch/
    ├── embarch.toml     <- a complete embarch-api config: [core] + the [[projects]] for this repo only
    └── build/           <- the build directory this project's build_command targets, kept separate
                            from whatever the engineer's own interactive `west build` uses
    ```

    Three things follow from this shape:
    - **Scoped by construction.** An `embarch-api` started with this config sees only this repo's projects, so `list_projects` in a firmware repo can't offer up an unrelated board to flash.
    - **A separate build directory is the default, not an option.** Sharing one `build/` with the engineer's interactive builds means EmbArch and the human clobber each other's build tree (different board revisions, different pristine-vs-incremental state). `init` writes `--build-dir embarch/build` into the scaffolded `build_command` and points `artifact_path` at it.
    - **It is a complete config, not a fragment.** `[core]` gets duplicated into every repo, which is real duplication — accepted for v1 because `[core]` is now three lines (`base_url = "auto"` and timeouts) and because an include/fragment mechanism is new code in `embarch-api`'s config loader. Recorded as the deliberate v1 trade-off; the fragment version is §10's open item.

11. **`doctor` and `status` are split by cost, and both carry `--json`.** `status` is one Core `/status` call — cheap enough for a future UI (§10) or a shell prompt to poll. `doctor` is the full chain (§5), including filesystem checks and a build-command resolution, which is far too heavy to poll. The `--json` shape on both is the contract a future UI consumes; it exists in v1 specifically so the UI doesn't arrive and find only human-formatted text to scrape. Human-readable output is the default on both, matching `embarch-api`'s own CLI convention (`embarch-api/design.md` §5a).

12. **Local-only integration into a firmware repo touches nothing that is committed.** For a repo owned by someone else (a client's firmware repo), `init` must not dirty tracked files. Concretely: the `embarch/` folder is excluded via `.git/info/exclude`, **not** by editing the repo's committed `.gitignore`; and the MCP server is registered at Claude Code's local (per-project, per-user) scope rather than by writing a `.mcp.json` at the repo root. Both are reversible by `embarch init --uninstall` and invisible to anyone else cloning the repo. Committing the integration later is a deliberate follow-on step, not the default — see §7 for the options and their trade-offs.

13. **`init` derives what it can from the repo, *by looking rather than assuming*, and refuses to guess the rest.** For a Zephyr/west repo it reads `build/build_info.yml`'s recorded `west.command` when one exists, because that is the only reliable answer to the `build_cwd`-vs-positional-app-path question that has already silently broken this suite once (`embarch-api/design.md` §6, §12). What it will not guess is the probe-rs `chip` name — Zephyr's board identifier and probe-rs's target name are different namespaces with no mechanical mapping — so `init` writes a placeholder plus the exact `probe-rs chip list` invocation to resolve it, and `doctor` fails loudly while the placeholder is still there. Guessing a chip name would produce a config that flashes the wrong target rather than an error.

    *Extended while implementing (2026-08-05), same principle applied twice more:* `artifact_path` is resolved by **searching `build/` for a real `zephyr.hex`** (shortest match wins) rather than assuming a layout — sysbuild nests it under `build/<app>/zephyr/` and a plain build doesn't, and which applies depends on the SDK (`embarch-dev-bench/decisions.md` §3 decision 4's correction). And `artifact_path_for_core` is computed from `WSL_DISTRO_NAME` when under WSL2, since the UNC form is mechanically derivable from a path that is already known. A `-p always` found in the recorded command is *reported, not removed* — with a separate build directory the user may well still want it, so that's their call to make.

14. **Distribution: one suite release archive containing all three binaries, published from this repo.** `embarch-<version>-<target>.{tar.gz,zip}` contains `embarch`, `embarch-core`, and `embarch-api`, so the getting-started path is one download rather than three, and the three binaries in a user's hands are a version-tested set rather than an arbitrary combination. Targets: `x86_64-pc-windows-msvc`, `x86_64-unknown-linux-gnu`, `aarch64-apple-darwin`, and `aarch64-unknown-linux-gnu` (for a future Pi Core). Per-repo releases still exist for developers working on one component; the suite release is what the user guide points at. `doctor` warns when the installed component versions don't match the suite manifest. This is what [embarch-roadmap.md](../embarch-roadmap.md)'s existing "Release" concept becomes concretely.

    **Implemented, 2026-08-10, verified 2026-08-11 for two of three components ([milestone-6.md](milestone-6.md) §3.7).** Each repo gets its own `release.yml` (tag-triggered, four targets); `embarch-umbrella` additionally gets `assemble-suite.yml` (manual, pulls one tagged release of each component and repackages all three binaries plus a manifest per target). Both open questions this decision's plan had flagged turned out to have the same answer — "GitHub already provides this, no extra CI work needed": `aarch64-apple-darwin` builds natively because GitHub's `macos-14` runner is itself Apple Silicon (still unsigned — Gatekeeper is the guide's problem, not CI's), and `x86_64-pc-windows-msvc` needs nothing extra because `windows-latest` already ships the VS Build Tools workload `embarch-core/decisions.md` §7 found necessary locally. The one target that's a genuine cross-compile is `aarch64-unknown-linux-gnu` (no free aarch64-linux runner exists), and only `embarch-core` needs more than a bare cross-linker for it, since `probe-rs`/`serialport` pull in `libudev-sys` — that leg uses `cross` (Docker-based) with a `Cross.toml` installing `libudev-dev:arm64` into the container, while `embarch-api`/`embarch-umbrella` (no C dependency) just add `gcc-aarch64-linux-gnu` to the host runner. The manifest is a small JSON file (`suite_version`, `target`, each component's release tag) written by `assemble-suite.yml` and read by `doctor` check 1 (`crate::manifest`) when one happens to sit next to the running binary — absent for a per-repo release or a debug build, which reports as "skipped" rather than a failure. **Verified against real `v0.1.0` tags on all three repos, 2026-08-11.** `embarch-api` and `embarch-umbrella` each released clean across all four targets on the first push. `embarch-core`'s first push failed exactly where predicted as the risk: the native `x86_64-unknown-linux-gnu` leg, because `libudev-dev` had only been arranged for the cross-compiled `aarch64-unknown-linux-gnu` leg (`Cross.toml`) — `ubuntu-latest` doesn't ship it the way a real Linux dev machine does. One added `apt-get install libudev-dev` step, gated to that leg, and moving the tag to the fixed commit produced a clean release across all four targets. `assemble-suite.yml` itself then caught a second real bug on its first-ever run: its `ls a.tar.gz b.zip 2>/dev/null | head -n1` line to find whichever archive extension a target used exits 2 whenever only one of the two globs matches — which is every target, since none ever has both. `ls` still finds and prints the real file, but also complains on stderr about the glob that missed, and the script's `pipefail` turns that into a fatal error regardless. Fixed with `shopt -s nullglob` and a plain array instead of `ls`/`head` (`embarch-umbrella` commit `4e6cb16`); re-run clean across all four targets, and `doctor` check 1 passed against the resulting real `suite-v0.1.0` manifest — the first time that check ran against anything other than a hand-crafted manifest.

15. **Topology detection is written once here, in a deliberately liftable shape — not extracted into a shared crate.** `embarch-api` needs the identical candidate-ordering and probe logic for `base_url = "auto"` (`embarch-api/design.md` §3.11, §7), so there are exactly two consumers and one algorithm. A fourth Rust crate in the suite, versioned and released, to hold one function that takes a candidate list and returns which one answered, is more machinery than the problem justifies at this scale. The alternative accepted instead: it lives in one self-contained module here, written under a constraint — **no umbrella-specific types cross its boundary**. No CLI structs, no umbrella config types, no `anyhow` context strings that only make sense in a `doctor` run; just pure functions over plain inputs (an "am I under WSL2" bool, a gateway-IP string, a port, an optional host) returning plain outputs. That constraint is what makes it copyable into `embarch-api` verbatim, and what makes extracting it into a real crate later a move rather than a rewrite, if a third consumer ever appears.

    **Reversed 2026-08-21 — the "more machinery than the problem justifies" reasoning held for exactly this one function with two consumers; it stopped holding once `embarch-topology` needed to exist anyway for an unrelated reason (hardware topology, `embarch-topology/design.md` §1's motivating incident) and software topology turned out to fit the same crate.** `embarch-core` becoming a *third* consumer (§2's architecture, decision 6's "not the process the MCP client spawns" framing doesn't change, but Core itself never actually called this module before and still doesn't call `software.rs` today — only `embarch-api`/`embarch-umbrella` do) wasn't the trigger; the trigger was that a shared crate already had to exist, at which point copying this logic a second time inside it had no remaining justification. This decision's own "no umbrella-specific types cross its boundary" constraint is exactly what made the actual move trivial — the pure functions moved into `embarch_topology::software` completely unchanged, tests included. `topology.rs`/`env.rs`/`probe.rs` are deleted from this repo; `embarch-topology/design.md` §3 decisions 2, 3 carry the fuller reasoning. Decision 16's separate liftable copies (`token.rs`, `config.rs`, mirroring `embarch-api`'s own token/config logic — nothing to do with topology) are **unaffected** by this — still two hand-copied files, still decision 20's open "extract or CI-diff" question below.

    The honest cost is drift: two copies that must agree, with nothing mechanical enforcing it. Three things keep that visible rather than silent — the module carries a comment naming its mirror and this decision, its unit tests are copied alongside it (they're pure-function tests, so they port with no adaptation), and `doctor`'s check 3 reports *which candidate won* rather than just pass/fail, so a divergence between what umbrella resolves and what `embarch-api` resolves surfaces as two different answers on the same machine instead of as a mystery.

16. **`doctor`'s token check (§5 check 4) needed the same liftable-copy treatment decision 15 gave topology detection — applied to `embarch-api/src/token_discovery.rs` this time, as `token.rs`.** A `doctor` that resolved the token differently than the `embarch-api` it's diagnosing would produce checks that pass or fail for reasons unrelated to the real thing, which is worse than no check. Checks 6-9 needed the same treatment applied to config shape rather than token logic: `config.rs` mirrors `embarch-api/src/config.rs`'s `[core]`/`[[projects]]` fields (minus `flash_format` and `env`, which nothing here reads — TOML tolerates the extra keys since neither struct denies unknown fields) but skips `embarch-api`'s own validation, since `doctor`'s entire job is reporting what's wrong rather than failing fast on the first bad field. Same accepted drift risk and mitigation as decision 15: a header comment naming the mirror, and (for `token.rs`) tests copied unchanged.

    Two implementation details worth recording because they weren't obvious going in. First, check 9's "comparable under WSL2 by stat-ing both paths" (§5) turned out to mean *reverse*-translating `artifact_path_for_core`'s UNC form back to a `/`-rooted path (undoing `init.rs`'s `wsl_unc_path`) and comparing canonicalized paths — not literally stat-ing a `\\wsl.localhost\...` string, which isn't a path WSL2's own filesystem namespace resolves. It only verifies anything when the UNC's embedded distro name matches `$WSL_DISTRO_NAME`; a different distro or non-WSL2 host reports "can't verify from here" rather than guessing. Second, a config that still declares an explicit (non-`"auto"`) `[core].base_url` — decision 9's default is `"auto"` but the field doesn't forbid the older form — makes `doctor` probe exactly that address rather than running decision 6's auto-detection candidate race, or `doctor` could end up diagnosing a *different* Core than the one `embarch-api` would actually talk to.

17. **`init` stops guessing a single board for a Zephyr/west repo; it scaffolds a `discovery = "zephyr-west"` project and defers board/chip selection to call time.** *(Decided 2026-08-13, shipped 2026-08-14. Full detail and rationale: [embarch-api/design.md](../embarch-api/design.md) §3 decision 12.)* Prompted directly by running `init` for real against the reference-dut repo (milestone 6, 2026-08-13): the repo has four real boards, and `init`'s old behavior — read whichever `build/build_info.yml` happens to exist, write one `[[projects]]` entry from it — silently picked a dev board's build over the production one, with no signal that a choice had even been made.

    For a repo shaped like a Zephyr/west project (`boards/*/*.yml` plus at least one `app/*/CMakeLists.txt`), `init` now writes the minimal `discovery = "zephyr-west"` schema ([embarch-api/design.md](../embarch-api/design.md) §3 decision 12: `source_path`, `west_binary`, `build_dir_root`, `flash_format`, `build_timeout_secs` — no `build_command`, `chip`, `artifact_path`, or `artifact_path_for_core`) instead of guessing a board. Decision 13's chip-placeholder behavior (write `CHANGE-ME`, let `doctor` block on it) no longer applies to this case at all — chip has nowhere to be written down for a `zephyr-west` project, since it's resolved per call from the selected SoC. Decision 13's `build_command`-derivation-from-`build_info.yml` logic, and its `artifact_path_for_core` UNC computation, both get lifted out of `init.rs` and become `embarch-api`'s call-time logic instead (same computation, different call site: once at scaffold time → every time a target is resolved).

    For a repo that isn't Zephyr/west-shaped, `init` is unchanged: one guessed `discovery = "static"` project from whatever generic signal exists, chip left as `CHANGE-ME`, exactly as decision 13 already describes.

30. **Under WSL2, `up` probes for the installed Windows service before considering a guest-local Core, 2026-08-25.** Decision 6's refinement note recorded the ambiguity and stopped there: with mirrored networking a Windows-hosted Core and a WSL2-guest-hosted Core both answer at loopback, so a `local` classification does not say *where* Core is — and `up` has to know before deciding whether it can start Core itself (via `embarch-core start`, decision 7) or needs the Linux-side elevation path. Detection already knows it is under WSL2; what `up` does with that was never designed.

    It checks for the installed Windows service first. If one is there, that is the Core it drives, and the Linux elevation path is never attempted. This is not a coin flip dressed as a heuristic — the Windows service *is* the suite's actual deployment on the only machine this has ever run on, so the probe resolves the ambiguity in favour of the thing that is really there, and degrades to the existing behaviour when no service is found. It also fails safe: probing for a service is read-only, so a wrong guess costs a check, not a botched start.

    Two alternatives declined. Prompting once and recording the answer in `state.rs` (where `--host` already lives) is unambiguous by construction, but adds an interactive prompt to a command meant to run unattended. Refusing without an explicit `--core-side=windows|guest` never guesses wrong, at the price of making the single most common command on the suite's primary topology fail by default until a flag is typed.

    **Still not resolvable from this machine**, and this decision does not pretend otherwise: only NAT-mode WSL2 has ever been observed here, so the mirrored-networking case the ambiguity actually requires remains untested.     An older Core with no `flash-backend` subcommand is a **Warn** naming what it predates, not a Fail — it is a real and recoverable state during a staged rollout, and the deployment procedure ([embarch-dev-workflow.md](../embarch-dev-workflow.md) §4a) already assumes Core and the tooling around it move separately.

32. **`embarch deploy-core` — the WSL2-to-Windows-service deploy becomes a command, and its silent failure mode becomes a check, 2026-08-26.**

    **Amended 2026-08-27 — the check does not catch the failure it was written for, and the command reported success through it.** Deploying [embarch-core/decisions.md](../embarch-core/decisions.md) §3 decision 33's watchdog fix, the elevated child was cancelled (`Start-Process : The operation was canceled by the user`), `deploy-core` printed its own correct diagnosis — *"the elevated child never started, which is what a UAC prompt that never rendered looks like"* — and then printed **`deploy-core: landed, and com.embarch.core is running`** immediately after it. Twice, on two consecutive invocations. The installed binary never changed: `d3c2a0fe…` built versus `796d5e16…` installed, confirmed by hand.

    Two separate defects, and the changelog entry below already names the second one without recognising it as fatal to the first:

    - **The verification compares a byte count, and the two builds were the same size.** The command said so — `note: the installed binary is already 16263168 bytes — this deploy may be a no-op, and the verification below cannot tell the difference` — and then reported landing anyway. A length check cannot discriminate a Rust release rebuild of one constant, which is the *most common* thing a development deploy carries. It has to hash. That the entry below records dogfooding "one of them a rename-only change where the length check correctly reported that it could not discriminate" shows this was known and read as a corner case rather than as the normal case.
    - **The success line does not depend on the elevated half having run.** Whatever it keys off — the service being `RUNNING`, which it was, because it was never stopped — is true of a deploy that did nothing at all. An explicit cancellation is a hard failure and must exit non-zero.

    **What is *not* wrong with it, corrected the same day:** self-elevation from WSL works fine. Both cancellations were the repo owner simply not being at the machine when the dialog rendered, and a third invocation with them watching elevated, installed and restarted the service cleanly — verified by hash, `d3c2a0fe…` on both sides. The reading that the prompt "never rendered" came from the command's own diagnostic line, which cannot distinguish a dialog nobody answered from a dialog that never appeared; it is worth narrowing that message, because the two have completely different fixes and the wrong one was believed for an hour. [embarch-decision-reversals.md](../embarch-decision-reversals.md) row 77. [embarch-dev-workflow.md](../embarch-dev-workflow.md) §4a calls its own subject *"the single most-repeated undocumented step in the suite"* and records two consecutive handoffs pointing at a section that did not exist yet. Writing it down fixed the forgetting. It did not fix the re-typing: every deploy since has been a hand-assembled `rsync` loop, a hand-typed absolute `cargo.exe` path, and a from-scratch PowerShell script — re-derived, un-reviewed, and different each time. **A documented five-step manual procedure with a silent failure mode in the middle is a command waiting to be written**, and this session wrote the script from scratch one more time before that got said out loud.

    What it does unelevated: sync the three crates (shared first, `embarch-core` last — same ordering §6 of that doc requires for commits, and for the same reason: Core has `path` dependencies on both, so a run that copied it first and died leaves a tree that builds cleanly and is wrong), then build with the Windows `cargo.exe`. Then one elevation around stop → copy → start. Then **verify the binary on disk actually changed.**

    **That verification is the point of the whole command.** `embarch-core.exe update` self-elevates, and when the consent dialog never renders it **exits `0`, prints nothing, and does nothing** — §4a records that leaving the live Core down for several minutes, and it happened again in the session that wrote this. A deploy that cannot distinguish success from that is not a deploy. So the installed binary's length is compared against the freshly built one, and a mismatch fails loudly, names the likely cause, and points at `--print-script`. When the two happen to be *equal* before the copy (a rename-only change, say), it says so rather than reporting a confident success the check cannot actually support.

    **Nothing is guessed.** The install target comes from the service's own `BINARY_PATH_NAME` via `sc.exe qc` — read-only, and the authoritative answer, where `locate_core`'s conventional-location list is a guess by design and on this bench would miss entirely (the live service runs out of a release-archive directory on no such list). `cargo.exe` is probed at `%USERPROFILE%\.cargo\bin`. The Windows source root is **never** probed: nothing distinguishes a directory holding this suite's source copies from any other directory, and building the wrong tree and deploying it is worse than refusing — so an unset value is an error naming `--windows-root`, remembered afterwards. It and the source root are saved only **after a deploy that landed**, so a wrong path is not inherited by the next run.

    **Decision 7 is narrowed here, not abandoned, and the distinction is that umbrella still never elevates silently.** `--print-script` is decision 7's posture verbatim — do everything unelevated, write the script, print the one command — and is what runs when this is not under WSL2 at all. The default merely saves the human a copy-paste, through one UAC prompt they see and can decline. The script logs each step from *inside* the elevated context, because `ShellExecuteExW`'s relaunch gives the child its own console and a redirect around the unelevated launcher captures nothing (§4a again); it waits for `STOPPED` rather than trusting `sc.exe stop`'s own return, which reports the request and not its completion; and it rolls the old binary back on failure rather than leaving the service pointed at a half-copied file.

    It also prints `DEV_BENCH_WIRE_SCHEMA_VERSION`, read out of `embarch-study-designer`'s own source at deploy time — the same trick that crate's dev-bench `CMakeLists.txt` uses, and for the same reason: umbrella links none of the binaries it orchestrates (§1), so reading the source is the only honest way to state the number. §4a's coupling 1 (a wire bump means reflashing the bench in the same sitting) is a reminder the command gives rather than one a human has to remember.

## 4. Topology matrix

| # | Topology | Detected class | Core startable by umbrella? | Flash works? |
|---|---|---|---|---|
| i | macOS: Core + API both native | `local` | Yes (`launchd` service) | Yes |
| ii | Linux: Core + API both native | `local` | Yes (`systemd` service) | Yes |
| iii | Windows Core + WSL2 API (**today's primary**) | `wsl-host` (or `local` under mirrored networking) | Yes, but service start needs an elevated Windows shell (§3 decision 7) | Yes, via `artifact_path_for_core`'s UNC path (`embarch-api/design.md` §9) |
| iv | Windows: Core + API both native | `local` | Yes, elevation as above | Yes |
| v | Core on a separate box (Pi over wifi), API elsewhere | `remote` | **No** — human starts it there (§3 decision 8) | **Yes, as of 2026-08-15** — via `embarch-api`'s multipart upload for a `remote` topology (`embarch-api/design.md` §3 decision 15, `embarch-core/decisions.md` §3 decision 10); previously blocked entirely on the artifact-transfer gap |

i/ii are mechanically the simplest and are expected to work first-try; iii is the one actually in daily use and therefore the one that gets validated for real; iv is supported by construction but untested; v is partial by design and says so.

## 5. What `doctor` checks

Ordered, each check emitting a pass/warn/fail plus a concrete fix line. Several of these are not new capabilities — they are existing open questions that finally have a natural home.

| # | Check | On failure |
|---|---|---|
| 1 | `embarch-core` and `embarch-api` binaries found; versions match the suite manifest (§3 decision 14) | Where to download / which is mismatched |
| 2 | Core service installed, and running | The exact `embarch-core install` / elevated start command |
| 3 | Core reachable — reports which candidate won and the resolved class (§3 decision 6) | Distinguishes "nothing answered" from "answered 401" |
| 4 | Token resolves and matches (a `200`, not a `401`) | Points at [embarch-token.md](../embarch-token.md); for `remote`, prints the copy-paste `EMBARCH_TOKEN` line (§6) |
| 5 | At least one debug probe visible in `/status`'s probe list; on Linux, distinguishes "not permitted" from "unplugged" (§3 decision 18, 2026-08-15) | Warn if genuinely absent; **fail**, with the udev-rules fix line, if a known-vendor USB device is present but not enumerated |
| 6 | `embarch-api` config loads; every project's `source_path` exists | The config-load error verbatim |
| 7 | Each `discovery = "static"` project's `build_command[0]` resolves to an executable; each `discovery = "zephyr-west"` project's `west_binary` resolves instead (§3 decision 17, `embarch-api/design.md` §3 decision 12) | This is `embarch-api/design.md` §12's deferred PATH/toolchain preflight, landing here rather than in the build path |
| 8 | For a `discovery = "static"` project: `chip` is not still `init`'s placeholder (§3 decision 13). For a `discovery = "zephyr-west"` project: at least one live-discovered target is file-backing-valid — i.e. `boards/`/`app/` aren't empty or broken (§3 decision 17) | The `probe-rs chip list` invocation (static); a listing of what `list_targets` actually found, or didn't (zephyr-west) |
| 9 | For a `discovery = "static"` project: `artifact_path` is resolvable, and if `artifact_path_for_core` is set, that it names *the same file* — comparable under WSL2 by stat-ing both paths. For a `discovery = "zephyr-west"` project: nothing to compare (both are computed together at call time, §3 decision 17) — this check instead confirms the WSL2 UNC translation itself succeeds when applicable | Catches exactly the mismatch that already cost this suite a debugging session (`embarch-api/design.md` §12) |
| 10 | MCP server registered for this repo, **and the registered command actually completes an MCP handshake** (§3 decision 23, 2026-08-15) | The `claude mcp add` line; if registered but the handshake fails/times out, reports that distinctly rather than as "not registered" |
| 11 | `study_designer_schema_version` from `/status` agrees with `embarch-api`'s compiled constant | Version-drift warning (`embarch-study-designer/design.md` §3 decision 12) |
| 12 | Dev-bench port detected (`GET /dev-bench/port`) | Informational only — a `404` is "bench not plugged in," an expected state (`embarch-core/decisions.md` §4) |
| 13 | Dev-bench `HelloAck.firmware_version` matches the local `embarch-dev-bench` checkout's `git describe` (§3 decision 19 — **implemented and live-validated 2026-08-19/20**, not just designed 2026-08-15) | A rebuild-and-reflash line naming the checkout (`west build && west flash`, or `embarch-api flash` for a board using `embarch-core/decisions.md` §3 decision 18's native flashing support — `embarch-dev-bench/decisions.md` §3 decisions 13/25) |
| 14 | Core's reachable bind address matches what the detected topology actually needs (§3 decision 22, 2026-08-15) | Which interface `/status` answered on vs. which one the topology needs — catches the gap `embarch-core/decisions.md` §3 decision 6's 2026-08-15 loopback-default change makes possible |
| 15 | Firewall state, best-effort (§3 decision 22) | Informational — names the likely-active firewall profile when a connectivity probe fails and Core can't be ruled out as simply-not-running |
| 16 | Disk space on the filesystem backing `embarch/build`/`study_results/` (§3 decision 22) | Warn below a threshold; names the path |
| 17 | Tail of Core's log file (`embarch-core/decisions.md` §3 decision 16, 2026-08-15) | Informational — prints the last few lines so a human doesn't need to know the log path |

Check 9 is only meaningful where both paths are visible to the same process, i.e. topology iii. Checks 5, 11, 12, 15, and 16 are informational/warn-only and never fail the run outright — except check 5's new not-permitted branch, which does fail.

## 6. Token handling

Umbrella does not invent any token mechanism — [embarch-token.md](../embarch-token.md) remains the source of truth. What it adds is making the existing mechanism actually happen at setup time:

- **Same-machine topologies (i–iv):** ensure Core has started at least once, so `token_store` has generated and persisted the machine-wide token file, then confirm `embarch-api` can discover it (including the WSL2⟷Windows `/mnt/c` translation `token_discovery.rs` already does). No token value is ever written into a config file.
- **Separate-machine (v):** there is no shared filesystem, and per [embarch-token.md](../embarch-token.md) §8 this is an unsolved gap. Umbrella's contribution is not to solve it but to make it a 10-second manual step: `doctor` prints the exact `export EMBARCH_TOKEN=...` / `setx` line to run on the API machine, with the value read from the Core machine by the human.

## 7. MCP registration options

`init` uses the local-scope registration of the first row (§3 decision 12). The rest are recorded because the question "how does this get committed for the whole team" is the obvious next one, and the answer isn't the same as the local one.

| Option | Shape | Pro | Con |
|---|---|---|---|
| **Local scope** (v1) | `claude mcp add` at per-project/per-user scope, pointing at `embarch-api --config <repo>/embarch/embarch.toml` | Touches nothing tracked; per-repo scoped; trivially reversible | Every engineer runs `embarch init` themselves |
| Committed `.mcp.json`, PATH + relative config | `{"command": "embarch-api", "args": ["--config", "embarch/embarch.toml"]}` | No absolute paths, portable, works for everyone who ran `embarch setup` | Requires `embarch-api` on `PATH`; every engineer still needs their own `embarch/` folder |
| Committed `.mcp.json`, env expansion | `{"command": "${EMBARCH_API_BIN}", "args": ["--config", "${EMBARCH_API_CONFIG}"]}` | Fully machine-independent | Two env vars to get wrong, with an opaque failure when unset |
| Committed wrapper script | `{"command": "./embarch/mcp.sh"}` | One indirection point; can preflight | A shell script doesn't work on native Windows; needs a `.cmd` twin |
| Umbrella as the MCP server | `{"command": "embarch", "args": ["mcp", ...]}` | Starting the agent starts the stack | Rejected — §3 decision 5 |
| Absolute paths | `{"command": "/home/me/.../embarch-api", ...}` | Works immediately | Broken for every other engineer; non-starter if committed |

If the integration is ever committed, row 2 is the recommendation, since `embarch setup` is already the thing that puts `embarch-api` on `PATH`.

## 8. Command surface

| Command | Scope | Behavior |
|---|---|---|
| `embarch setup` | once per machine | Detect topology (§3 decision 6), install Core as a service where possible, ensure the token file exists, put both binaries on `PATH`, record the class + Windows-side Core path, then run `doctor`. `--dry-run` (§3 decision 21) prints the plan without executing it; `--uninstall` (§3 decision 25) reverses a prior `setup`; `--dev-bench-repo <path>` (§3 decision 19, 2026-08-19/20) records the local `embarch-dev-bench` checkout doctor check 13 compares against, overridable per-call via `EMBARCH_DEV_BENCH_REPO_PATH` |
| `embarch init` | once per firmware repo | Scaffold `embarch/embarch.toml` + `embarch/build/` (§3 decision 10, 13), exclude locally, register the MCP server (§3 decision 12), then run `doctor`. `--uninstall` reverses all of it |
| `embarch doctor` | anytime | §5's full chain. `--json`. `--prune` (§3 decision 26) reports/cleans stale `study_results/`/build-dir entries, opt-in only |
| `embarch status` | anytime, cheap | One `/status` call: is Core up, which class, how many probes. `--json` |
| `embarch up` / `embarch down` | fallback | Start/stop Core — installed service first, foreground `embarch-core run` only if no service exists (§3 decision 4, 7) |
| `embarch deploy-core` | WSL2 → Windows service, during development | Sync the three crates, build natively, stop/copy/start under one elevation, **verify the binary changed** (§3 decision 32). `--dry-run` prints the resolved plan and touches nothing; `--print-script` does the unelevated half and hands the privileged step to a human; `--source-root`/`--windows-root`/`--cargo`/`--install-target`/`--service` override what is otherwise saved state or probed |

Exit codes follow `embarch-api`'s CLI convention (`embarch-api/design.md` §5a): `0` on success, `1` on any failure with the message on stderr (or folded into the `--json` object on stdout when `--json` is set), `2` from `clap` for a malformed invocation.

## 9. Relationship to the rest of the suite

- **`embarch-core`:** umbrella shells out to its CLI (`install`, `uninstall`, and the `start`/`stop` pair proposed in `embarch-core/decisions.md` §10) and calls three of its HTTP endpoints (`/status`, `/dev-bench/port`, `/dev-bench/hello`). It adds no Core capability and holds no hardware knowledge.
- **`embarch-api`:** umbrella writes its config and shells out to its CLI for verification. The `base_url = "auto"` resolution lives there, not here (§3 decision 9). Umbrella never re-implements build orchestration.
- **`embarch-study-designer` / `embarch-dev-bench`:** umbrella's only involvement is two `doctor` checks (schema-version agreement, dev-bench port presence). It does not build, flash, or configure dev-bench firmware — that stays a human `west flash` (`embarch-dev-bench/decisions.md` §3 decision 13).
- **`embarch-promptu`:** out of scope. Umbrella registers the MCP server; it does not install skills or prompt patterns.

## 10. Open questions / future work

- **`doctor` check 11 never checks anything, and its stated reason is false — found 2026-08-26.** `check_schema_version` (`src/doctor.rs`) returns a hardcoded `Warn` reading *"not available yet — `embarch-study-designer` isn't wired into `embarch-core`/`embarch-api` as a dependency yet"*. It is a direct dependency of both; Core has served `study_designer_schema_version` on `/status` since 2026-08-25 ([embarch-core/decisions.md](../embarch-core/decisions.md) §3 decision 30's implementation note) and `embarch-api` compares its own compiled-in copy before every submit.

  **This is not cosmetic.** On 2026-08-26 the live pair was found sitting at Core wire **v13** against a dev-bench flashed to **v14** — a state the `Hello`/`HelloAck` handshake refuses correctly and loudly, but only to whoever calls `GET /dev-bench/hello` by hand. `doctor` is the surface whose whole job is to say that without being asked, and it reported `WARN … not available yet` the entire time. The three numbers worth comparing are Core's served host version, the version the located `embarch-api` was built against, and the wire version the bench reports over `/dev-bench/hello` — all three already reachable from checks 3, 1 and 12 respectively. Recorded rather than built in the pass that found it: that pass had already moved the wire, and a check that gates deploys is worth its own. See [embarch-decision-reversals.md](../embarch-decision-reversals.md) row 71.

- ~~**The EmbArch UI.**~~ — **stale; closed 2026-08-25.** Every part of this bullet has an answer and has had one since 2026-08-24. It is [embarch-ui](../embarch-ui/design.md): a local web page served by its own process (not a native app, not a tray item), reaching Core through the shared `embarch-core-client` crate rather than shelling out to or embedding `embarch-api`'s CLI. milestone 1 there is closed — all five tabs live-validated against the real deployed Core, plus a VS Code launcher extension. Decision 11's `--json` contract on `status`/`doctor` still stands as a data source and is unaffected. Found by a suite-wide design pass, not by anyone noticing: the doc had gone on asking a question the suite answered and shipped a day earlier.
- ~~**A `local` classification under WSL2 is ambiguous about *where* Core is**~~ — **designed and built 2026-08-25 (§3 decision 30).** The ambiguity is real and unchanged: with mirrored networking a Windows-hosted Core and a WSL2-guest-hosted Core both answer at loopback. What is no longer open is what `up` does about it — it probes for the installed Windows service first (read-only, `sc.exe query`), and defers to it when one is there. `down` too, as an extension the decision didn't name. **The evidence gap stays exactly where this bullet put it**: only NAT-mode WSL2 has ever run here, so what got live-validated is NAT mode, and the mirrored-networking case has defined behaviour and no evidence.
- ~~**Finding the probe-rs `chip` name currently requires installing a separate tool.**~~ — **resolved 2026-08-25: `embarch-core chip-list [filter]` is scheduled and built** ([embarch-core/decisions.md](../embarch-core/decisions.md) §3 decision 34). The wart this bullet describes — `cargo install probe-rs-tools`, a Rust toolchain install dropped into the middle of a download-a-binary onboarding, hit only on an *unmapped* SoC that the §3 decision 17 table does not cover — is gone. `init` can offer real candidates instead of writing a placeholder. Scoped 2026-08-15 and unscheduled for four months; the scheduling was the only thing still open about it.
- ~~**`embarch-api/design.md` §3 decision 12's open sub-questions**~~ — resolved 2026-08-13 (folded into that decision); also resolved a new `embarch-core` endpoint, `/resolve-chip` (`embarch-core/decisions.md` §3 decision 8), which `init`/`doctor` don't call directly but which `embarch-api`'s call-time chip resolution now depends on.
- **Config fragments / includes**, so `[core]` isn't duplicated into every firmware repo's `embarch/embarch.toml` (§3 decision 10). Needs an `include` mechanism in `embarch-api`'s config loader; deferred rather than rejected.
- ~~**Elevation is a hard edge on every platform**~~ (§3 decision 7) — reversed 2026-08-18: `embarch-core` now self-elevates (`embarch-core/decisions.md` §3 decision 3) instead of umbrella printing a command for a human to run in a shell they open themselves, closing the "is this acceptable onboarding friction" question below by removing the friction rather than answering it. Still genuinely open: a user-level service (systemd `--user`, launchd LaunchAgent) would avoid needing *any* elevation at all on Linux/macOS, but wouldn't start before login, which defeats decision 3's whole point; not yet weighed properly. Self-elevation also doesn't help the no-GUI/no-TTY case (CI, headless remote) — that still needs decision 3's original "print the command" fallback, since there's no one there to click a prompt.

- ~~**Found (2026-08-17), live on a real Windows machine during Milestone 1 onboarding**: `setup`'s printed `PATH` hint was always POSIX `export PATH="<dir>:$PATH"` syntax, unconditionally — invalid on native Windows `cmd.exe`.~~ — folded into **decision 28** (2026-08-17): `setup` now mutates `PATH` for real, per-platform, rather than printing a hint at all; this bug is moot once that ships. `embarch-user-guide.md` §3.1 documents the manual translation as a stopgap until decision 28 is implemented.

## 11. Relationship to the user guide

[embarch-user-guide.md](../embarch-user-guide.md) was originally written against this design ahead of implementation — i.e. against tooling that didn't exist yet — with a clearly-marked appendix carrying the manual steps that worked in the meantime. That was deliberate: the guide doubled as this milestone's acceptance criteria. As of `v0.1.0` shipping (this milestone's DoD, §3.8 in [milestone-6.md](milestone-6.md)), the guide now describes the real, released tool; the old appendix is kept only as historical/reference material, not as "what you actually have to do" (2026-08-17 — corrected here after the guide itself was found still saying the opposite, live, during a real Windows onboarding attempt).
