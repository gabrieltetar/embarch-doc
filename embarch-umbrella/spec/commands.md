# embarch-umbrella: spec — the command surface

**Status:** active, 2026-11-25.

Split verbatim out of [../spec.md](../spec.md) on 2026-11-25 under [DOC-COMPACTION.md](../../DOC-COMPACTION.md) §2 (`tasks/umbrella/107`); only relative link prefixes changed. Current truth: [../spec.md](../spec.md). Why: [../decisions.md](../decisions.md).

| Command | Scope | Behaviour |
|---|---|---|
| `embarch setup` | once per machine | Detect topology, install Core as a service, ensure the token file exists, copy all three binaries to the canonical per-user location and put it on `PATH`, **run `embarch-desk service install` and `claude plugin install embarch-desk@embarch` when the desk is located, each skipped by name when not (decision 58)**, record the class and the Windows-side Core path, then point at `embarch status` and `embarch init` as next steps — it does not run `doctor` itself. `--uninstall` reverses it (the desk's two steps included) and exits `1` if any step failed; **`--dry-run` prints the whole plan and changes nothing** (decision 21); `--dev-bench-repo` records the checkout check 13 compares against |
| `embarch init` | once per firmware repo | Scaffold the repo's `embarch/` config, install the `embarch-hil` skill at `.claude/skills/embarch-hil/` (decision 59), exclude both locally, register the MCP server, then point at `embarch status` and the first `embarch-api build` as next steps — it does not run `doctor` itself. **An inferred board is never written as fact, and several recorded builds are all named rather than one picked** (decision 41). **On a repo whose config exists it installs only the skill and exclude entries it lacks, leaves the config unread and untouched, and exits `0` (decision 60).** `--uninstall` reverses all of it, and `--dry-run` prints the plan and writes nothing; committing the integration for a team is a follow-on step it does not take (decision 12). **Every run registers the repo in umbrella's state; `--container [--runtime docker\|podman]` also writes the agent's container definition and exchange folder outside the repo and prints the person's `git fetch` line, and `--uninstall` removes the folders only after a typed yes (decision 65)** |
| `embarch agent up \| down \| status \| shell [--claude]` | after `init --container` | `up` builds the image when none carries the Containerfile's hash, then starts the container with the vector `init` recorded and Core's address; `down` removes it, keeping the volume and exchange folder; `status` names a hand-edited definition, a differing fingerprint copy, a Core that does not answer or an off-list address that does, exit `1` on any; `shell` enters the clone as the agent user. Docker or Podman; with neither on `PATH` each refuses and names the install (decision 67) |
| `embarch doctor` | anytime | The full check chain. `--json`, carrying `schema_version`. **Nothing in it deletes anything** — `--prune` is unbuilt (decision 26, [prune-policy](../decisions/prune-policy.md)) |
| `embarch status` | anytime, cheap | Is Core up, which class, how many probes — the latter needs a second, authenticated `GET /status`, and no-token/unauthorized/unreachable are reported as themselves, never as a probe count of `0` (decision 46). `--json`, carrying `schema_version` and `success` |
| `embarch up` / `down` | fallback | Installed service first; foreground Core only with `--foreground` |
| `embarch deploy-core` | WSL2 → Windows, during development | Sync, build natively, install a **development Core beside the service** (service stopped, never written), **verify the hash on the copy and `/status`**. `--cancel-run`, `--restore-service`, `--dry-run`, `--print-script` (decision 68) |
| `embarch verify-release [DIR]` | before installing a suite release | Offline check that the unpacked folder (default: the running binary's own) is what the release workflow signed: the manifest's Sigstore bundle under one exact identity and issuer, then every listed file's SHA-256. Fetches nothing; `--refresh-trust-root` alone does. Exit `0` only when everything checked. [interfaces/verify-release.md](../interfaces/verify-release.md); [proposal](../../embarch-release-signing-proposal.md) step 3, EMB-192 |
| `embarch install-core <DIR or archive>` | installing a suite release | Copies the release into an admin-only `release-staging/<n>/`, runs `verify-release`'s check **there**, refuses an older suite than `installed-release.json` unless `--allow-downgrade` (recorded), and writes the record. A failed check writes nothing. Then it installs Core under its own account by one generated script: elevated PowerShell on Windows (decision 69), a root `sh` script on Linux (decision 70). `--dry-run` prints the plan, and on Linux the script, and changes nothing. Self-elevation is a later unit. [interfaces/install-core.md](../interfaces/install-core.md); decisions 61, 69, 70, EMB-338, EMB-339, EMB-340 |

Exit codes follow `embarch-api`'s convention: `0` success, `1` failure with the message on stderr (or folded into the JSON object under `--json`), `2` a malformed invocation.
