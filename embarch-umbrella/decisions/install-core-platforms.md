# embarch-umbrella: decisions — `install-core` on Windows and Linux

**Status:** active, 2026-11-27. Index: [../decisions.md](../decisions.md). The verification and `setup` decisions (61, 71): [install-core.md](install-core.md). Verb: [../spec/commands.md](../spec/commands.md); record: [../interfaces/install-core.md](../interfaces/install-core.md).

### 69 — On Windows, `install-core` then installs Core under its own account by one generated, logged, elevated script (EMB-339)

Implements `notes/hil/12-prevention.md` "The root of trust" after decision 61's verification, as the owner's direction asked. **The record gains `binary_sha256`**, an array of lowercase hex holding the staged `embarch-core`'s hash, beside `binaries` (kept; old records read as empty). Core's `install --service` ([core decision 157](../../embarch-core/decisions/platform.md)) refuses without it, so the script would have failed at step 5 otherwise.

**The script** (`install_core_win.rs`, one function per step, golden-tested) logs from inside the elevated context as `deploy-core`'s does, run through `Start-Process -Verb RunAs`. **Step 0 refuses before anything is written** a store that exists owned by anyone but Administrators, SYSTEM or the service SID (`sc showsid`, so it resolves before registration). Then: (1) `%ProgramFiles%\EmbArch\core\<version>\`, Administrators and SYSTEM full, Users read and execute, the staged binary copied in and hashed again; (2) `%ProgramData%\embarch\store`, inheritance removed, the service, SYSTEM and Administrators full, never emptied; (3) `staging`, Administrators full, the service read, the engineer modify; (4) `token` and `person-token`, written when absent (32 random bytes, 64 hex), the service and Administrators full, the engineer read; (5) the installed binary's `install --service --bind`; (6) start, wait for `RUNNING`, read `store\public-key`, write `core-fingerprint` (SHA-256 of the raw 32-byte key, Core's `keyid`), Administrators write and Users read, print it. Grants are by SID. The transcript parser needs `=== done ===`, an `OK` per step and a 64-hex fingerprint; each failed or silent step is named and the exit is `1`; a missing transcript is a failure (decision 50). `--dry-run` prints the paths and ACLs.

**Deviations, none the owner's to strike:** the verify-and-stage half still runs in the calling process (self-elevation stays a later unit), so the engineer's SID is `whoami`'s in that process, which is not the engineer's if an over-the-shoulder admin ran it; only the default data dir is installed, since Core reads its record there (a `--data-dir` run records and says it stopped); `--bind` is the topology's `Local` address; `%ProgramData%\embarch` itself is left as Windows made it.

**Measured vs assumed:** nothing ran on Windows. The script is tested as text and the parser on literals, the sequence against a fake host; the Windows-gated block type-checked in a throwaway crate for `x86_64-pc-windows-msvc`, the crate's own build being impossible under WSL (decision 61). The `sc showsid` parse, PowerShell 5.1's native-stderr handling, and token files Core accepts are assumed. Debt: [open.md](../open.md).

**Reversal:** Core's `install --service` stops reading the record, or the owner strikes the verb.

### 70 — On Linux, `install-core` installs Core as the `embarch` system user by one generated shell script (EMB-340)

The Linux half of `notes/hil/12-prevention.md` "The root of trust", after decision 61's verification, in decision 69's shape: `install_core_linux.rs`, one function per step, the **same seven steps and transcript lines**, so the transcript parser and the `Host` seam are the Windows module's, reused rather than copied. The script is POSIX `sh`, run as root with the script on stdin (no file for another local user to swap); the verify-and-stage half already needs root, so there is no `sudo` re-launch, and step 0 refuses a non-root run.

**Steps.** (0) refuses before any write: not root, no `systemctl`, the engineer's account missing, or a `store` that exists and is a symlink, not a directory, or not owned by `embarch`. (1) `/opt/embarch/core/<version>/`, root `0755`, the staged binary copied and hashed again. (2) group `embarch-users` and user `embarch` (system, no login, no home) when absent; `embarch` joins `dialout` and `plugdev` where they exist; `embarch` and the engineer join `embarch-users`; `/var/lib/embarch` root `0755`; `store/` `embarch:embarch` `0700`, never emptied. (3) `staging/` `root:embarch-users` `0770`. (4) `token` and `person-token`, written when absent under `umask 077` (so never readable before the `chown`), then `embarch:embarch-users` `0640`. (5) the installed binary's `install --service --bind`, which writes the unit with `User=embarch` (checked in Core's `service.rs`: `Account::User("embarch")` on Linux, so no Core task). (6) start, wait for `active`, write `core-fingerprint` (SHA-256 of the raw key, bytes rebuilt with `printf` octal escapes, no `xxd`) root `0644`, print it. `--dry-run` prints the plan and the whole script with placeholders, and writes nothing.

**Deviations, none the owner's to strike:** the engineer is `$SUDO_USER` read by the calling process and passed in, validated as an ordinary lowercase account name that is not `root` or `embarch` (an unset `SUDO_USER` is refused); **`study_results/` and `logs/` are created `embarch:embarch-users` `0750`**, because Core writes run directories (`token_store::results_root`) and its daily log files (`build_log_file_writer`, read back by `logs::log_dir` for `/logs/recent`) in the data dir beside the tokens, which is root-owned: without them a service Core could not store a run, and would log to stderr only and serve no recent log. The group read is for the engineer, who can then read the log files with Core down; nothing there is theirs to write. Checked in `embarch-core/src`: those two and the read of `installed-release.json` are Core's only data-dir-root accesses (the rest is in `store/`); the unit name `com.embarch.core` is the service label and systemd's file name for it is assumed; only the default `/var/lib/embarch` is installed; the engineer's new group needs a fresh login, which the command says. The engineer is not given the `store`, by design.

**Measured vs assumed:** nothing ran as root. The script is golden-tested per step, passes `sh -n`, the step-0 store check ran against a temp dir (an own-owned store, a symlink, an absent one), and the sequence ran against a fake host. Assumed: `useradd --system --user-group`, `usermod -aG`, `stat -c` (GNU coreutils), the unit's name, and Core accepting `0640` token files it did not create. Debt: [open.md](../open.md).

**Reversal:** the owner strikes the Linux half, or Core's unit stops running as `embarch`.

### 72 — `install-core --agent-in-container` makes the elevated half write one start-and-stop grant, and `down` refuses under a study (EMB-342)

Where the agent runs in a container, `notes/hil/12-prevention.md` "The root of trust" lets the engineer's account start and stop Core's service without elevation and never change it; **the grant is written only by the elevated install, and a later change of the engineer's statement never widens it.** Nothing wrote it before. Without the flag the script has **no grant step at all** (tested on both platforms); with it, step 7 follows step 6. The parser, told a grant was asked for, requires `STEP 7 OK`.

**Windows: one ACE, `(A;;RPWPLC;;;<engineer SID>)`**, added to `com.embarch.core`'s descriptor by `sc sdshow`, an edit, `sc sdset`. The letters, from the SDDL service-rights table: `RP` is SERVICE_START (0x10), `WP` SERVICE_STOP (0x20), `LC` SERVICE_QUERY_STATUS (0x04). Chosen so `sc start`, `sc stop` and `sc query` succeed: each opens the service with its own right, and waiting for `STOPPED` or `RUNNING` is a status query. **Left out on purpose:** `LO` (interrogate) and `CR` (user-defined control), which no start, stop or status call needs; `CC`, `SW` and `DT`, not asked for; `DC` change-config, `WD` write-DAC, `WO` write-owner and `SD` delete, which the design forbids. `add_start_stop_ace(sddl, sid)` is the pure function: text in, text out, the ACE placed at the end of the DACL and before the SACL, every other ACE kept in order, an identical ACE already present returned unchanged (a second install adds nothing), a descriptor with no DACL refused (it would read as "everyone"). The script cannot call Rust, so step 7 makes the same edit in PowerShell and prints the descriptor before and after; **`run_windows_half` recomputes the edit with the pure function and fails if the "after" differs**, naming both. It also catches a service manager that normalises the descriptor on `sdset`.

**Linux: one polkit rule**, `/etc/polkit-1/rules.d/50-embarch-core.rules`, root `0644`, written by `printf` lines to a temp file and `install`ed. `polkit_rule_lines(engineer)` is pure and golden-tested: action `org.freedesktop.systemd1.manage-units`, `unit` equal to `com.embarch.core.service`, `verb` equal to `start` or `stop`, `subject.user` the engineer, result `YES`. It names no other unit and no other verb, and mentions no `AUTH_*` result, so everything else keeps polkit's default. The `.service` suffix is decision 70's assumed unit name; a polkit older than 0.106 reads `.pkla` files, not `.rules`, and gets no grant.

**The statement is recorded** in `installed-release.json` as `agent_in_container` and `agent_in_container_at` (both `serde(default)`, so an older record reads). **It is sticky:** an install without the flag keeps the earlier statement and its date, because nothing here removes a grant and a record that forgot one would understate what the machine allows; stating it again moves the date. Removing a grant is by hand.

**`embarch down` refuses while Core's `/status` shows a study in flight**, and `down --cancel-run` cancels it first through `deploy_dev::clear_study`, as `deploy-core --cancel-run` does. A Core that does not answer has no study, so `down` goes ahead.

**Out of scope:** the passkey case. The design says a registered passkey also means no grant; no passkey registration exists yet, so the flag is the only input. Core's half, trying `start` and `stop` unelevated first, is `embarch-core`'s.

**Measured vs assumed:** nothing ran elevated and no descriptor or polkit directory was touched. Tested: the pure edit (with a SACL, without, twice), the polkit rule as golden text and as written by its shell lines, both scripts with and without the flag, the record, `down` against a fake Core. Assumed: the SDDL letters' effect on a real service manager, that `sdset` keeps the descriptor as written, `.service` as polkit's `unit`, and that re-running `install --service` keeps the descriptor (if it recreates the service the grant is gone while the record says otherwise). Debt: [open.md](../open.md).

**Reversal:** the owner strikes the container topology, or Core stops honouring an unelevated start and stop.
