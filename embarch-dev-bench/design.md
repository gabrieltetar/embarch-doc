# embarch-dev-bench: design

**Status:** draft, 2026-08-04. Scoped and implemented in [gabrieltetar/embarch-dev-bench](https://github.com/gabrieltetar/embarch-dev-bench): the shared `app/` builds and runs on `native_sim`, and the `nordic`/nRF54L15DK workspace built too (NCS v3.4.0 fetched, `ble_bridge_real.c` compiled and linked into a flashable `zephyr.hex`, FLASH 13.18%/RAM 34.51%), though that board was never actually flashed before it broke (decision 4's amendment, decision 26). Companion to [embarch-study-designer/design.md](../embarch-study-designer/design.md), which this doc treats as a given: the `Study`/`DevBenchMessage` types and the COBS/postcard wire protocol are locked in there, not re-litigated here.

## 1. Purpose and scope

`embarch-dev-bench` is the physical rig that plays the DUT's BLE counterpart during a `Study` (`embarch-study-designer/design.md` §1) — it advertises, connects (as central or peripheral), exchanges GATT data, and samples power, per whatever `Study.steps` `embarch-core` relays to it over a serial link. It is Zephyr-based C firmware, cross-vendor by design: "one firmware project" doesn't mean one board or one silicon vendor, it means one shared application implementation that different west workspaces build for different vendor targets (§3).

**v1 scope, explicitly bounded:**
- **BLE + power sampling only** — exactly what `embarch-study-designer`'s `Action`/`GattOperation` enum already models (`BleAdvertise`, `BleConnect`, `DataExchange`, `PowerSampleWindow`, `GattOperation::StreamCapture`). `embarch.md`'s original one-line description ("actively stimulates DUT inputs and senses outputs") is broader than this — GPIO/analog stimulus (driving a button pin, injecting an analog sensor signal) is real future scope, not v1, and isn't modeled in `embarch-study-designer` today. Adding it later means a new `Action` variant there, not just dev-bench firmware work.
- **No physical DUT connector, no power-sampling hardware yet.** v1 is BLE-proximity-only; a DUT is whatever's in the DUT's own physical BLE range. `PowerSampleWindow`/`GattOperation::StreamCapture` stay real types that dev-bench firmware will eventually serve, but the actual sampling hardware (a shunt + ADC, or similar) is out of scope until a specific board/BOM decision is made.
- **No on-board status indication** (LEDs, etc.) — dev-bench's state is observable only through `embarch-core`/`study_status`, not by looking at the board.

## 3. Locked-in design decisions and rationale

1. **Zephyr as the one common RTOS across every board/vendor — not a custom multi-SDK HAL abstraction.** "One firmware project for any board" is interpreted as "any board a Zephyr flavor supports," not "every vendor's own native SDK (ESP-IDF, STM32Cube, Pico-SDK) behind a hand-written abstraction layer." The latter is a materially bigger undertaking — effectively building a small cross-platform embedded framework from scratch (Arduino-core/PlatformIO/mbed's job) — and buys nothing `embarch-dev-bench` specifically needs, since Zephyr already provides vendor-portable BLE host, GPIO, and ADC APIs. This also means `embarch-study-designer/design.md` §3 decision 7 (dev-bench firmware is C, not Rust, because the BLE host stays a C API) doesn't need to be reopened for a broader vendor set — every mainstream vendor's BLE host under Zephyr is the same Zephyr Bluetooth host API regardless of silicon.
2. **One repo, multiple west workspaces (one per vendor family), sharing one application source tree — not one single west workspace, and not one repo per vendor.** A west manifest (`west.yml`) pins exactly one Zephyr revision at a fixed path; a vendor's own Zephyr fork (e.g. Nordic's nRF Connect SDK, decision 3 below) pins its *own* revision, incompatible with mixing into the same manifest as vanilla Zephyr or another vendor's fork. Resolved by giving each vendor family its own west topdir under `workspaces/`, each with its own `west.yml`, while the actual application implementation (`app/`) is written once and referenced (not copied) by every workspace's build. This achieves the part of "one firmware project" that actually matters — one shared implementation, one repo, one git history — without fighting west's one-manifest-one-Zephyr-revision model.
3. **Vendor SDK forks are accepted per family (not insisted-on vanilla Zephyr everywhere) — but application code is restricted to portable Zephyr APIs regardless.** A vendor fork (e.g. NCS) is often the only place brand-new silicon's HAL/BLE controller support lands first — insisting on vanilla-only would risk blocking on upstream support timing for every new board. Accepted trade-off: `app/src/*.c` only calls stable, vendor-neutral Zephyr subsystem APIs (`bt_*`, `gpio_*`, `adc_*`) — never anything NCS-proprietary — so the same source keeps working if a given workspace's pinned revision is later swapped toward vanilla, or if a second workspace picks a different flavor entirely. The cross-vendor Zephyr-revision-reconciliation question (could two families ever share one workspace after all?) is deliberately not solved now — see §4.
4. **First board: nRF54L15DK.** Chosen over nRF54H20DK specifically to avoid taking on `embarch-study-designer/design.md` §3 decision 7's already-flagged nRF54H20 complexity (mandatory *multi-core* `sysbuild` build) for a board whose job here — running the Zephyr BLE host in both central and peripheral roles, bridging serial to Core — doesn't need multiple cores. Single-core, single-image, well-trodden path. *(Correction, 2026-08-04, from the first real build: this decision originally said "standard (non-`sysbuild`) Zephyr build," which is no longer accurate — NCS 3.4's `west build` wraps every application in `sysbuild` regardless, so the output lands in `build/app/zephyr/` and `build/domains.yaml` exists. It stays a single domain named `app` with one image and one flash step, so the substance of the decision — no multi-core image coordination to reason about — holds; only the "non-sysbuild" phrasing was wrong.)* **Amended 2026-08-19: no longer the board Milestone 2 targets.** The physical unit broke before ever being flashed (decision 26) and its RMA replacement never arrived in time to close Milestone 2's Definition of Done; the ESP32-C5-WROOM-1 (decision 26), originally stood up only as an interim substitute, validated the milestone's entire dispatch/handshake/study path end to end first, and Milestone 2's own scope moved onto it (`embarch-decision-reversals.md` row 13, `embarch-dev-bench/milestone-8.md` §2). This doesn't retire the nRF54L15DK from `workspaces/` (§2's tree keeps `nordic/` as a built, currently-inactive workspace) or resolve decision 10's cross-vendor-family question — it's a milestone-scope decision, not a permanent board deprecation.
5. **First workspace (`workspaces/nordic/`) pins nRF Connect SDK (NCS), not vanilla Zephyr.** Follows directly from decision 3: nRF54-family support is an NCS-first (often NCS-only, for the newest parts) proposition. BLE controller for this workspace specifically: **Nordic's SoftDevice Controller** (proprietary, shipped via NCS) over Zephyr's open-source BLE controller — best feature/support coverage on Nordic silicon specifically, at the cost of that specific choice being Nordic-only (a future non-Nordic workspace picks its own controller independently; this isn't a cross-workspace decision).
6. **Core link: a plain UART over the nRF54L15DK's on-board J-Link VCOM, not USB CDC ACM — one interface, no separate log/console interface.** Originally specified as USB CDC ACM; revised once implementation research found the nRF54L15 SoC has no USB device peripheral at all (USB only arrives with the newer nRF54LM20 family) — the DK's USB connector belongs entirely to its on-board SEGGER J-Link debug-probe chip, not the target SoC. That J-Link chip already bridges one of the nRF54L15's real UART peripherals to a virtual COM port on the host (the same VCOM used for the DK's existing debug console) — firmware-side this is a completely ordinary Zephyr UART (`uart_poll_out`/interrupt-driven `uart_*` calls on a physical UART peripheral), with no SEGGER-specific code and no USB device stack anywhere in this firmware. Dev-bench still appears as a plain serial port (`/dev/ttyACM*`/a COM port) when plugged in, still bus-powers the board, still matches Core's own existing DUT serial-log pattern (`embarch-core/design.md` §5) and requires no separate network stack (`embarch-study-designer/design.md` §3 decision 4's reasoning for the hop, unaffected by this revision) — only the physical/peripheral mechanism changed, not the wire protocol or Core-facing behavior. A second interface for dev-bench's own debug/log output was considered and rejected in favor of decision 7 below, same reasoning as before, now just "a second UART instance" rather than "a second CDC ACM interface."
7. **Dev-bench's own log output travels as a new `DevBenchMessage` variant, not as raw interleaved bytes on the shared line.** Literally sharing one byte stream between free-text log lines and COBS-framed `DevBenchMessage`s would corrupt the protocol — COBS frames are self-delimiting, plain log text isn't, so a receiver parsing for frame boundaries would choke on stray log bytes it wasn't expecting. Resolved the same way every other kind of dev-bench-to-Core data already travels: a log line is just another properly-framed message. Implemented as an append-only `DevBenchMessage::LogLine { text: heapless::String<{limits::MAX_LOG_LINE_LEN}> }` variant in `embarch-study-designer` (same discipline as that crate's §3 decision 10) — a small, forward-compatible addition to that crate, not a redesign.
8. **The `embarch-study-designer` Rust staticlib's cross-compilation is invoked automatically as part of `west build` — implemented 2026-08-18, via a direct path-based `cargo rustc` invocation rather than the formal west-managed-module plumbing this decision originally specified.** A CMake custom target (`app/CMakeLists.txt`) runs `cargo rustc --release --target thumbv8m.main-none-eabi --features ffi --lib --crate-type staticlib` against the crate's path (a sibling repo by default, `EMBARCH_STUDY_DESIGNER_PATH` env var override available), rather than requiring a separate manual build/publish step before `west build` can succeed — one build command, as originally intended, just not literally a `west`-manifest `module.yml` project the way the original text specified: the crate is edited locally far more often than pulled from a pinned upstream revision, and this workspace's manifest never actually gained that module entry, so a plain path-based invocation reaches the same practical outcome with less git plumbing. Skipped entirely for `native_sim` (`CONFIG_ARCH_POSIX`) — that workspace keeps `study_ffi_stub.c` (decision 20) permanently, mirroring `ble_bridge_stub.c`'s own reasoning. **Board→Rust-target-triple mapping, resolved for the first board:** nRF54L15's Cortex-M33 core is `thumbv8m.main-none-eabi` — the *soft*-float variant specifically, **not** `-eabihf`: this app's Zephyr build has no hardware-FPU ABI enabled, and a hard-float-ABI staticlib fails to link ("uses VFP register arguments") the moment any code path touches an `f32`, which includes `Sample`'s own field internally, not just this crate's actual FFI-exposed function signatures (none of which pass a float) — found by hitting exactly that link error against the real board before settling on the soft-float target. Confirmed producing a real, flashable `zephyr.hex` for the nRF54L15DK, ~1.2 KB of flash for the whole decode/CRC path. A second board/core extends the CMake if/else this triple selection lives in, not replaces it (§4).
9. **No CI for now.** ~~Matches `embarch-study-designer`'s own precedent (no CI set up there either) — revisit once there's more than one board actually building, so a compile-only `west build` matrix check has more than one target to be useful across.~~ **Superseded 2026-08-15** (`embarch-core/design.md` §3 decision 17, closing item 15 of that day's design-improvement review): a compile-only `west build -b native_sim app` job is worth having even with one board, since it's cheap, hardware-independent, and would have caught the real `BT_LE_ADV_CONN_NAME` breakage below before it was found by hand — a matrix check across boards is still deferred until a second board exists, but "no CI at all" no longer holds.
10. **A second vendor family/board is deliberately left unspecified.** The `workspaces/`-per-vendor-family convention (decision 2) is designed to obviously extend, but no second vendor, board, or Zephyr flavor is committed to yet — keeps the multi-workspace layout honest (built to extend, not pre-built for a hypothetical) rather than speculatively scaffolding for a board that doesn't exist.
11. **BLE pairing: Just Works, bonds kept RAM-only and cleared on `Hello` — no NVS/settings persistence across reboots.** Some real DUTs require pairing/encryption before certain characteristics are accessible, so v1 needs at least Just Works (Zephyr's `CONFIG_BT_SMP`) rather than unencrypted-only. Persisting bonds to flash (Zephyr's Bluetooth settings subsystem) was considered and rejected: a study should always start from a known, clean pairing state rather than accumulate stale bonds across unrelated studies or reboots. Resolved by extending `embarch-study-designer/design.md` §3 decision 12's existing "`Hello` doubles as a hard reset" — a fresh `Hello` now also clears dev-bench's in-RAM BT bonding table, not just its study execution state. A single study's own internal reconnects (if a `Study`'s steps disconnect and reconnect the same DUT) still don't have to re-pair, since nothing clears the bond table mid-study.
12. **Auto-detection via the on-board J-Link's own SEGGER VID plus a product-string/serial-number match, not a custom VID/PID — revised from the original plan once decision 6 moved off USB CDC ACM.** A custom VID (`0xEBAC`)/PID (`0xDB01`) was originally locked in for `embarch-core` to identify dev-bench programmatically among other serial devices (e.g. the DUT's own debug console), the same auto-detection goal as before — but that descriptor would have to be advertised by dev-bench's own USB CDC ACM stack, which decision 6 established doesn't exist on this SoC; the port Core actually sees is enumerated by the on-board J-Link chip, which advertises SEGGER's own USB descriptor (VID `0x1366`), not anything dev-bench firmware controls. `embarch-core` instead identifies dev-bench's port by matching SEGGER's VID plus a product-string or serial-number heuristic (e.g. matching against the specific J-Link's serial number recorded once at setup, since a lab may have more than one SEGGER-probed board plugged in) — entirely an `embarch-core`-side change, no firmware-side VID/PID logic at all. **Implemented 2026-08-04** in `embarch-core`'s `dev_bench.rs`; [embarch-core/design.md](../embarch-core/design.md) §5 is now the source of truth for the actual matching rules (including how it resolves one J-Link exposing several VCOMs), and §4 below carries only what real hardware still has to confirm.
13. **Reversed 2026-08-19/20 — `embarch-core` *can* flash dev-bench firmware now; the exclusion below no longer holds as a blanket rule.** Originally: flashing dev-bench firmware is a direct `west flash` (J-Link/nrfjprog), entirely outside `embarch-core`, because "`embarch-core`'s probe-rs access is explicitly scoped to the DUT — it has no business flashing the bench that's testing that DUT" (`embarch-core/design.md` §1). That was a deliberate separation-of-concerns choice, not a technical limitation, made before dev-bench had any board whose flashing mechanism Core could plausibly share — the nRF54L15DK's SEGGER J-Link genuinely is a separate tool (`nrfjprog`/`west flash`) from anything Core's probe-rs already talked to. It stopped holding the moment a board showed up (the ESP32-C5 interim substitute, decision 26) whose on-chip debug probe `probe-rs` already speaks natively: `embarch-core/design.md` §3 decision 18 adds real, validated support for exactly this — `POST /flash`/`POST /reset` against `chip: "esp32c5"`, over the same native USB-JTAG interface Windows already enumerates, **with zero WSL2↔Windows USB forwarding needed** (Core already runs natively on Windows; the board's USB connector was never a WSL2-side device to forward in the first place). Validated end to end: real flash, real reset-and-run, a real `Hello`/`HelloAck` handshake, and a full physical self-test `Study` completing via `embarch-api`'s existing `run-study` CLI — see that doc's decision 18 for the full mechanism (why `Format::Idf` doesn't work for a Zephyr-built image, and why `Format::Bin` at Zephyr's own merge address does instead). **What this reversal does *not* do:** migrate the nRF54L15DK off its existing `west flash`/J-Link workflow — that board's own SoC (`nrf54l15`) has been in Core's `SOC_TO_CHIP` table since decision 12, but flashing it *through* Core was never attempted this pass, so decision 13's original default stays the practical answer there until someone actually validates it. A human plugging in dev-bench's own on-board debugger and running `west flash` by hand remains entirely correct and unaffected for any board/workspace this hasn't been exercised against yet.
14. **No local hardware watchdog.** `embarch-study-designer/design.md` §3 decision 16's Core-side host watchdog (added specifically because a hung dev-bench can't self-report its own `TimedOut`) is treated as sufficient detection; a self-resetting local `CONFIG_WDT` was considered and deferred rather than rejected outright — it's a cheap addition to revisit if a hung dev-bench in practice needs power-cycling too often for Core's detection alone to be a good enough experience.
15. **One dev-bench, one DUT connection at a time — no multi-connection support.** Matches `embarch-study-designer/design.md`'s existing "one study in flight at a time" model (that crate's §5.1) exactly: testing multiple DUTs in parallel means multiple independent Core+dev-bench pairs, not one dev-bench juggling several BLE connections. Nothing in `embarch-study-designer`'s types models addressing more than one concurrent DUT connection per `Study` anyway. **The enforcement point is firmware, not the controller's link budget** — `ble_bridge_real.c`'s `execute_connect` refuses to open a second link while one is live. *(Correction, 2026-08-04, from the first real build: this decision originally claimed `CONFIG_BT_MAX_CONN` "stays at its default single-connection value." It does stay at its default, but that default is **2** here, not 1, and deliberately so: with the SoftDevice Controller the central role gets `BT_MAX_CONN - BT_CTLR_SDC_PERIPHERAL_COUNT` slots, and `BT_CTLR_SDC_PERIPHERAL_COUNT` defaults to 1 whenever `BT_PERIPHERAL` is enabled — so `BT_MAX_CONN=1` would leave the central role **zero** slots and break every central-role `BleConnect`, while still building and linking cleanly. Verified by actually building it that way: no error, no warning, 1 KB less RAM, and a silently broken role. The board conf now pins `CONFIG_BT_MAX_CONN=2` explicitly with that reasoning in a comment, so the value reads as intentional rather than as slack worth trimming.)*
16. **A `native_sim` workspace, alongside `nordic/`, for host-side iteration without real hardware.** *(Implementation note, 2026-08-04: `ble_bridge_real.c` now implements the full `Action`/`GattOperation` surface — `BleConnect` in both roles and every `DataExchange` operation, not just `BleAdvertise`. That made three additions to the shared internal API, all mirrored in `ble_bridge_stub.c` per this decision's hand-sync cost: `struct outcome` gained a borrowed `captured_data`/`captured_len` pair mirroring `StepResult.captured_data`, `ble_connect_params` gained the `BleAddressKind` the crate's `BleAddress` carries and Zephyr's `bt_addr_le_t` requires, and a `ble_bridge_set_stream_handler` hook was added for `GattOperation::StreamCapture`'s continuous samples — see §4 for why nothing wires that hook up yet.)* Zephyr's `native_sim` board runs a Zephyr application as a native Linux process — useful here for exercising the serial/COBS protocol parsing and the `embarch-study-designer` FFI glue (`study_ffi.c`) without needing the physical nRF54L15DK plugged in. Scoped narrowly: no virtual-PTY serial transport (protocol-parsing/FFI-glue logic is unit-tested directly, in-process, not through a literal serial link — framing correctness itself is `embarch-study-designer`'s own round-trip tests' job, not this workspace's). BLE is stubbed as a **separate source file, not an `#ifdef`-gated branch inside one file**: `ble_bridge_real.c` (Zephyr BT host calls, built by `workspaces/nordic/`) and `ble_bridge_stub.c` (canned `Outcome`s, built by `workspaces/native_sim/`) both implement the same internal C API that `main.c`/`serial_protocol.c` call into, and each workspace's `CMakeLists.txt` picks which one to compile — keeping the real BLE-host-calling code free of stub-only branches (and vice versa), at the cost of the two files needing to be kept in signature-sync by hand, acceptable since that shared internal API is small (mirrors the `Action`/`GattOperation` surface, §1). This keeps the full study-execution flow (serial → dispatch → "BLE" action → result) runnable and testable end-to-end on a host machine, just without a real radio at the end of it.
17. **BLE address: a static random address, fixed at build/boot time — not a resolvable private address (RPA), and not runtime-configurable by Core.** Simplicity and test reproducibility over BLE-privacy realism: dev-bench isn't emulating a privacy-conscious consumer device, it's a test fixture, and a stable address makes logs/captures easier to correlate across runs. Plain Zephyr default behavior, no custom addressing logic needed.
18. **`HelloAck` gains a firmware-identity field: `firmware_version: heapless::String<{limits::MAX_FIRMWARE_VERSION_LEN}>`, a single free-form string, not a structured multi-field type.** `schema_version`/`compatible` alone (`embarch-study-designer/design.md` §3 decision 12) tell Core whether the wire shape matches, but not which actual firmware build is running on the other end of the link — a real gap when something misbehaves and the question is "did this dev-bench even get reflashed with the fix." A single string is the simplest shape that still answers that question; whatever the dev-bench build embeds into it (`git describe` output, a board ID, a build timestamp, some combination) is dev-bench build-tooling's own concern, not fixed at the wire-type level — the append-only discipline (`embarch-study-designer/design.md` §3 decision 10) leaves room for a future structured field alongside this one if a single string ever proves insufficient. Implemented via a new `limits::MAX_FIRMWARE_VERSION_LEN` constant and `STUDY_DESIGNER_SCHEMA_VERSION` bump (v1 → v2) in `embarch-study-designer` — same discipline as any other wire-relevant change to that crate (§3 decision 12), not a new kind of change. 27. **`Action::GattDiscover`/`Action::GattMonitorAll` implemented for real — `embarch-roadmap.md` Milestone 3 (Study Designer: Feature-Branch Iteration), 2026-08-20 — closing the BleAdvertise-only scope decisions 16/21 shipped with.** `serial_protocol.h`/`.c` (not `study_ffi.c`/`essd_study_decode_full` — see this bullet's own correction below) gained a tagged-union `struct dbm_step.action` covering all five `Action` kinds (`embarch-study-designer/src/study.rs`'s own declaration order: BleAdvertise/BleConnect/DataExchange/GattDiscover/GattMonitorAll), so `main.c`'s `dispatch_study` now dispatches `BleConnect`/`DataExchange` for the first time too (already implemented in `ble_bridge_real.c` since decision 16, just never wired to a real decoded `Study` before this pass) alongside the two genuinely new kinds. `ble_bridge_real.c` gained the actual new BLE logic: a wildcard `bt_gatt_discover` walk (`BT_GATT_DISCOVER_PRIMARY`, no UUID filter, run to completion via repeated callbacks rather than the single-result pattern `DataExchange`'s own targeted discovery already used) followed by a per-service wildcard characteristic walk, populating `GattServiceInfo`/`GattCharacteristicInfo` (`embarch-study-designer/design.md` §4.3a); `GattMonitorAll` runs that same walk internally, then subscribes to every characteristic whose discovered properties include Notify or Indicate (a new, capped-at-32 `BLE_MAX_MONITOR_SUBSCRIPTIONS` set of concurrent subscriptions — deliberately *not* sized to the wire type's own absolute worst case, `MAX_DISCOVERED_SERVICES × MAX_CHARS_PER_SERVICE = 128`, which would cost several needless KB of static RAM for a characteristic count no real DUT plausibly reaches; see this bullet's own RAM-budget finding below), buffering incoming notifications as `GattActivityRecord`s until the step's `timeout_ms` expires, with the same "stop capturing, keep what's already buffered" overflow behavior `embarch-study-designer/design.md` §3 decision 32 specifies. UUID expansion (`from_bt_uuid`) handles all three Bluetooth UUID widths a live discovery can actually return — not just the 128-bit custom UUIDs decision 16's existing helpers assumed — since a wildcard service walk also surfaces Zephyr's own built-in 16-bit GAP/GATT services, expanded into the Bluetooth Base UUID form to stay byte-for-byte comparable with `embarch-study-designer/design.md` §3 decision 33's static extraction (which only ever sees a DUT's own custom 128-bit UUIDs, and so will legitimately report *fewer* services than a live `GattDiscover` — an expected, explainable discrepancy, not a bug, per that decision's own dual-source framing).

    `GattActivityRecord.rx_utc_ms` is stamped from `k_uptime_get()` (device uptime), not a UTC-corrected timestamp — this firmware still has no `Hello.host_utc_ms` clock-offset tracking implemented for *any* timestamp, `Sample.rx_utc_ms` included, so this new field inherits §4's already-open "clock-resync accuracy… not validated" item rather than introducing a new one.

    **A real, previously-undetected Kconfig bug found and fixed, from the outset per decision 32's own explicit stack-safety mandate rather than rediscovered the hard way a second time:** both real-hardware board `.conf` fragments (`esp32c5_devkitc_esp32c5_hpcore.conf`, `nrf54l15dk_nrf54l15_cpuapp.conf`) set `CONFIG_MAIN_STACK_SIZE=2048`, silently *overriding* the shared `app/prj.conf`'s own `=8192` — Zephyr merges a board-conf fragment after `prj.conf`, and the later value wins with no warning. Confirmed empirically against a real build's resolved `.config` (`2048`, not `8192`) before fixing it — harmless while `dispatch_study` only ever ran `BleAdvertise` (a shallow call chain), but real `GattDiscover`/`GattMonitorAll` dispatch is the first time this main thread's call depth actually reaches into BLE central-role GATT discovery/subscribe code. Both files now read `8192`, restoring `prj.conf`'s already-vetted margin.

    **A real SRAM-overflow finding, also from decision 32's own flagged risk:** a from-scratch `west build` for the ESP32-C5 failed outright (`region 'sram0_0_seg' overflowed by 25104 bytes`) the first time `struct dev_bench_message`'s union had to hold both `DataExchange`'s up-to-512-byte `Write` payload (multiplied by every step in `struct dbm_study_start.steps[]`) and `StepResult`'s new `gatt_services`/`gatt_activity` fields (dominated by `gatt_activity`'s 32 records × up to 512 bytes each, ≈16.8 KB alone) at the same time. Two fixes, not one: (1) `main.c`'s four separate `static struct dev_bench_message` locals (`send_log_line`/`send_study_done`/`send_step_result`/`handle_hello`) consolidated into one shared `tx_scratch` buffer — safe because this single-threaded RX/dispatch loop never has two outbound messages in flight at once, and the four call sites already only ever ran sequentially; (2) `DBM_MAX_STEPS_PER_STUDY` (a **dev-bench-internal** capacity cap, `serial_protocol.h`) reduced from 64 to 16 — deliberately *not* the crate's own `limits::MAX_STEPS_PER_STUDY` (still 64 there, unaffected; Core/`embarch-api` still validate/CRC a `Study` against that ceiling), sized against every `Study` this suite has actually authored so far (the largest is this milestone's own 3-step self-test) with real headroom, not a proven fuzzing need — a `StudyStart` claiming more steps than this is rejected outright by `dbm_decode_frame` (a real, disclosed capacity limit, not a silent truncation), the same way an oversized `steps_len` already was. With both fixes, a clean `west build` for `esp32c5_devkitc/esp32c5/hpcore` reports `sram0_0_seg` at 90.87% (343,824 / 378,384 B) — fits, but tight: revisit `DBM_MAX_STEPS_PER_STUDY` (or restructure `dev_bench_message` to stop sharing one union across every message direction) before adding anything else RAM-heavy, e.g. Milestone 4's power-sampling work.

    **Real gap found relative to this milestone's own execution plan, folded back rather than silently worked around:** `embarch-study-designer/milestone-9.md` §3.1 (and this doc's own milestone-9.md) named `study_ffi.c`'s `essd_study_decode_full`/`EssdStep` as the FFI decode surface needing extension to cover the four non-`BleAdvertise` action kinds. It doesn't — `study_ffi.h`'s own doc comment already said so before this pass (`essd_study_decode_full` decodes a `Study`, not the `StudyStart` this firmware actually receives over the wire; `main.c`'s real dispatch has never called it, per decision 21's own note) — extending it would have been real, tested work that `dispatch_study` still wouldn't exercise. Left exactly as it was (`Action::BleAdvertise`-scoped, validated-but-unused infrastructure, `study_ffi.h`'s own framing) rather than extended for symmetry with no real caller; the actual extension needed was `serial_protocol.h`/`.c`'s own hand-written decode, which is what this pass did. `embarch-study-designer/milestone-9.md` corrected to match.

    Verified: `west build -b native_sim app` and the (now 19-case, up from 10) `app/tests/serial_protocol` ztest suite both pass; `west build -b esp32c5_devkitc/esp32c5/hpcore app` builds clean (FLASH 6.77%, SRAM 90.87%, per the finding above). Real-hardware dispatch of the new kinds — connecting to an actual DUT, confirming `GattDiscover`'s live result against decision 33's static extraction, a clean `GattMonitorAll` capture — is this milestone's own separate execution step, not yet run as of this decision's own text; see `embarch-dev-bench/milestone-9.md` §3.7-3.9 and this doc's own changelog for whenever that lands.

- 2026-08-04 — `ble_bridge_real.c` went from one wired-up action to the full `Action`/`GattOperation` surface (§3 decision 16's implementation note). `BleConnect` covers both roles: central scans (filtering on `target_address` when set, ignoring non-connectable advertisers) and initiates from the scan callback; peripheral advertises and, when a specific `target_address` was asked for, drops a wrong peer and keeps advertising for whatever of the step's budget remains rather than reporting a Pass against the wrong DUT. `DataExchange` acts as a GATT client: primary-service then characteristic discovery (cached per connection, invalidated on disconnect), then read / write-with-response / notify / indicate / subscribe / stream-capture.
