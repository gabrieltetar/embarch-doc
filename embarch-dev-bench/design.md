# embarch-dev-bench: design

**Status:** draft, 2026-08-04. Scoped and implemented in [gabrieltetar/embarch-dev-bench](https://github.com/gabrieltetar/embarch-dev-bench): the shared `app/` builds and runs on `native_sim`, and the `nordic`/nRF54L15DK workspace now builds too (NCS v3.4.0 fetched, `ble_bridge_real.c` compiled and linked into a flashable `zephyr.hex`). Still never run on a physical board — no hardware has been flashed. Companion to [embarch-study-designer/design.md](../embarch-study-designer/design.md), which this doc treats as a given: the `Study`/`DevBenchMessage` types and the COBS/postcard wire protocol are locked in there, not re-litigated here.

## 1. Purpose and scope

`embarch-dev-bench` is the physical rig that plays the DUT's BLE counterpart during a `Study` (`embarch-study-designer/design.md` §1) — it advertises, connects (as central or peripheral), exchanges GATT data, and samples power, per whatever `Study.steps` `embarch-core` relays to it over a serial link. It is Zephyr-based C firmware, cross-vendor by design: "one firmware project" doesn't mean one board or one silicon vendor, it means one shared application implementation that different west workspaces build for different vendor targets (§3).

**v1 scope, explicitly bounded:**
- **BLE + power sampling only** — exactly what `embarch-study-designer`'s `Action`/`GattOperation` enum already models (`BleAdvertise`, `BleConnect`, `DataExchange`, `PowerSampleWindow`, `GattOperation::StreamCapture`). `embarch.md`'s original one-line description ("actively stimulates DUT inputs and senses outputs") is broader than this — GPIO/analog stimulus (driving a button pin, injecting an analog sensor signal) is real future scope, not v1, and isn't modeled in `embarch-study-designer` today. Adding it later means a new `Action` variant there, not just dev-bench firmware work.
- **No physical DUT connector, no power-sampling hardware yet.** v1 is BLE-proximity-only; a DUT is whatever's in the DUT's own physical BLE range. `PowerSampleWindow`/`GattOperation::StreamCapture` stay real types that dev-bench firmware will eventually serve, but the actual sampling hardware (a shunt + ADC, or similar) is out of scope until a specific board/BOM decision is made.
- **No on-board status indication** (LEDs, etc.) — dev-bench's state is observable only through `embarch-core`/`study_status`, not by looking at the board.

`embarch-dev-bench` talks to `embarch-core` over a plain UART (§3 decision 6), carrying COBS-framed `DevBenchMessage`s exactly as `embarch-study-designer/design.md` §3 decisions 10/12/20 already define. `embarch-core` never talks BLE or samples power itself (`embarch-core/design.md` §1) — that stays entirely inside this firmware.

## 3. Locked-in design decisions and rationale

1. **Zephyr as the one common RTOS across every board/vendor — not a custom multi-SDK HAL abstraction.** "One firmware project for any board" is interpreted as "any board a Zephyr flavor supports," not "every vendor's own native SDK (ESP-IDF, STM32Cube, Pico-SDK) behind a hand-written abstraction layer." The latter is a materially bigger undertaking — effectively building a small cross-platform embedded framework from scratch (Arduino-core/PlatformIO/mbed's job) — and buys nothing `embarch-dev-bench` specifically needs, since Zephyr already provides vendor-portable BLE host, GPIO, and ADC APIs. This also means `embarch-study-designer/design.md` §3 decision 7 (dev-bench firmware is C, not Rust, because the BLE host stays a C API) doesn't need to be reopened for a broader vendor set — every mainstream vendor's BLE host under Zephyr is the same Zephyr Bluetooth host API regardless of silicon.
2. **One repo, multiple west workspaces (one per vendor family), sharing one application source tree — not one single west workspace, and not one repo per vendor.** A west manifest (`west.yml`) pins exactly one Zephyr revision at a fixed path; a vendor's own Zephyr fork (e.g. Nordic's nRF Connect SDK, decision 3 below) pins its *own* revision, incompatible with mixing into the same manifest as vanilla Zephyr or another vendor's fork. Resolved by giving each vendor family its own west topdir under `workspaces/`, each with its own `west.yml`, while the actual application implementation (`app/`) is written once and referenced (not copied) by every workspace's build. This achieves the part of "one firmware project" that actually matters — one shared implementation, one repo, one git history — without fighting west's one-manifest-one-Zephyr-revision model.
3. **Vendor SDK forks are accepted per family (not insisted-on vanilla Zephyr everywhere) — but application code is restricted to portable Zephyr APIs regardless.** A vendor fork (e.g. NCS) is often the only place brand-new silicon's HAL/BLE controller support lands first — insisting on vanilla-only would risk blocking on upstream support timing for every new board. Accepted trade-off: `app/src/*.c` only calls stable, vendor-neutral Zephyr subsystem APIs (`bt_*`, `gpio_*`, `adc_*`) — never anything NCS-proprietary — so the same source keeps working if a given workspace's pinned revision is later swapped toward vanilla, or if a second workspace picks a different flavor entirely. The cross-vendor Zephyr-revision-reconciliation question (could two families ever share one workspace after all?) is deliberately not solved now — see §4.
4. **First board: nRF54L15DK.** Chosen over nRF54H20DK specifically to avoid taking on `embarch-study-designer/design.md` §3 decision 7's already-flagged nRF54H20 complexity (mandatory *multi-core* `sysbuild` build) for a board whose job here — running the Zephyr BLE host in both central and peripheral roles, bridging serial to Core — doesn't need multiple cores. Single-core, single-image, well-trodden path. *(Correction, 2026-08-04, from the first real build: this decision originally said "standard (non-`sysbuild`) Zephyr build," which is no longer accurate — NCS 3.4's `west build` wraps every application in `sysbuild` regardless, so the output lands in `build/app/zephyr/` and `build/domains.yaml` exists. It stays a single domain named `app` with one image and one flash step, so the substance of the decision — no multi-core image coordination to reason about — holds; only the "non-sysbuild" phrasing was wrong.)*
5. **First workspace (`workspaces/nordic/`) pins nRF Connect SDK (NCS), not vanilla Zephyr.** Follows directly from decision 3: nRF54-family support is an NCS-first (often NCS-only, for the newest parts) proposition. BLE controller for this workspace specifically: **Nordic's SoftDevice Controller** (proprietary, shipped via NCS) over Zephyr's open-source BLE controller — best feature/support coverage on Nordic silicon specifically, at the cost of that specific choice being Nordic-only (a future non-Nordic workspace picks its own controller independently; this isn't a cross-workspace decision).
6. **Core link: a plain UART over the nRF54L15DK's on-board J-Link VCOM, not USB CDC ACM — one interface, no separate log/console interface.** Originally specified as USB CDC ACM; revised once implementation research found the nRF54L15 SoC has no USB device peripheral at all (USB only arrives with the newer nRF54LM20 family) — the DK's USB connector belongs entirely to its on-board SEGGER J-Link debug-probe chip, not the target SoC. That J-Link chip already bridges one of the nRF54L15's real UART peripherals to a virtual COM port on the host (the same VCOM used for the DK's existing debug console) — firmware-side this is a completely ordinary Zephyr UART (`uart_poll_out`/interrupt-driven `uart_*` calls on a physical UART peripheral), with no SEGGER-specific code and no USB device stack anywhere in this firmware. Dev-bench still appears as a plain serial port (`/dev/ttyACM*`/a COM port) when plugged in, still bus-powers the board, still matches Core's own existing DUT serial-log pattern (`embarch-core/design.md` §5) and requires no separate network stack (`embarch-study-designer/design.md` §3 decision 4's reasoning for the hop, unaffected by this revision) — only the physical/peripheral mechanism changed, not the wire protocol or Core-facing behavior. A second interface for dev-bench's own debug/log output was considered and rejected in favor of decision 7 below, same reasoning as before, now just "a second UART instance" rather than "a second CDC ACM interface."
7. **Dev-bench's own log output travels as a new `DevBenchMessage` variant, not as raw interleaved bytes on the shared line.** Literally sharing one byte stream between free-text log lines and COBS-framed `DevBenchMessage`s would corrupt the protocol — COBS frames are self-delimiting, plain log text isn't, so a receiver parsing for frame boundaries would choke on stray log bytes it wasn't expecting. Resolved the same way every other kind of dev-bench-to-Core data already travels: a log line is just another properly-framed message. Implemented as an append-only `DevBenchMessage::LogLine { text: heapless::String<{limits::MAX_LOG_LINE_LEN}> }` variant in `embarch-study-designer` (same discipline as that crate's §3 decision 10) — a small, forward-compatible addition to that crate, not a redesign.
8. **The `embarch-study-designer` Rust staticlib is pulled in as a west-managed module, with its cross-compilation invoked automatically as part of `west build`.** A CMake custom command (triggered from `app/CMakeLists.txt`) invokes `cargo build --release --target <triple> --features ffi`, keyed off whatever target architecture the active board implies, rather than requiring a separate manual build/publish step before `west build` can succeed. Chosen over a pre-built/fetched artifact so there's exactly one build command a developer runs, matching how the rest of a Zephyr application already builds. The concrete `<triple>` mapping per board, and the actual west-module wiring (`module.yml`), aren't implemented yet (§4) — `embarch-study-designer/design.md` §7's nRF54 cross-compilation toolchain gap is the same gap this decision needs closed to actually work.
9. **No CI for now.** ~~Matches `embarch-study-designer`'s own precedent (no CI set up there either) — revisit once there's more than one board actually building, so a compile-only `west build` matrix check has more than one target to be useful across.~~ **Superseded 2026-08-15** (`embarch-core/design.md` §3 decision 17, closing item 15 of that day's design-improvement review): a compile-only `west build -b native_sim app` job is worth having even with one board, since it's cheap, hardware-independent, and would have caught the real `BT_LE_ADV_CONN_NAME` breakage below before it was found by hand — a matrix check across boards is still deferred until a second board exists, but "no CI at all" no longer holds.
10. **A second vendor family/board is deliberately left unspecified.** The `workspaces/`-per-vendor-family convention (decision 2) is designed to obviously extend, but no second vendor, board, or Zephyr flavor is committed to yet — keeps the multi-workspace layout honest (built to extend, not pre-built for a hypothetical) rather than speculatively scaffolding for a board that doesn't exist.
11. **BLE pairing: Just Works, bonds kept RAM-only and cleared on `Hello` — no NVS/settings persistence across reboots.** Some real DUTs require pairing/encryption before certain characteristics are accessible, so v1 needs at least Just Works (Zephyr's `CONFIG_BT_SMP`) rather than unencrypted-only. Persisting bonds to flash (Zephyr's Bluetooth settings subsystem) was considered and rejected: a study should always start from a known, clean pairing state rather than accumulate stale bonds across unrelated studies or reboots. Resolved by extending `embarch-study-designer/design.md` §3 decision 12's existing "`Hello` doubles as a hard reset" — a fresh `Hello` now also clears dev-bench's in-RAM BT bonding table, not just its study execution state. A single study's own internal reconnects (if a `Study`'s steps disconnect and reconnect the same DUT) still don't have to re-pair, since nothing clears the bond table mid-study.
12. **Auto-detection via the on-board J-Link's own SEGGER VID plus a product-string/serial-number match, not a custom VID/PID — revised from the original plan once decision 6 moved off USB CDC ACM.** A custom VID (`0xEBAC`)/PID (`0xDB01`) was originally locked in for `embarch-core` to identify dev-bench programmatically among other serial devices (e.g. the DUT's own debug console), the same auto-detection goal as before — but that descriptor would have to be advertised by dev-bench's own USB CDC ACM stack, which decision 6 established doesn't exist on this SoC; the port Core actually sees is enumerated by the on-board J-Link chip, which advertises SEGGER's own USB descriptor (VID `0x1366`), not anything dev-bench firmware controls. `embarch-core` instead identifies dev-bench's port by matching SEGGER's VID plus a product-string or serial-number heuristic (e.g. matching against the specific J-Link's serial number recorded once at setup, since a lab may have more than one SEGGER-probed board plugged in) — entirely an `embarch-core`-side change, no firmware-side VID/PID logic at all. **Implemented 2026-08-04** in `embarch-core`'s `dev_bench.rs`; [embarch-core/design.md](../embarch-core/design.md) §5 is now the source of truth for the actual matching rules (including how it resolves one J-Link exposing several VCOMs), and §4 below carries only what real hardware still has to confirm.
13. **Flashing dev-bench firmware is a direct `west flash` (J-Link/nrfjprog), entirely outside `embarch-core`.** `embarch-core`'s probe-rs access is explicitly scoped to the DUT (`embarch-core/design.md` §1) — it has no business flashing the bench that's testing that DUT. A human plugs in dev-bench's own on-board debugger and runs the standard Zephyr/NCS `west flash` workflow, same as any other Zephyr application.
14. **No local hardware watchdog.** `embarch-study-designer/design.md` §3 decision 16's Core-side host watchdog (added specifically because a hung dev-bench can't self-report its own `TimedOut`) is treated as sufficient detection; a self-resetting local `CONFIG_WDT` was considered and deferred rather than rejected outright — it's a cheap addition to revisit if a hung dev-bench in practice needs power-cycling too often for Core's detection alone to be a good enough experience.
15. **One dev-bench, one DUT connection at a time — no multi-connection support.** Matches `embarch-study-designer/design.md`'s existing "one study in flight at a time" model (that crate's §5.1) exactly: testing multiple DUTs in parallel means multiple independent Core+dev-bench pairs, not one dev-bench juggling several BLE connections. Nothing in `embarch-study-designer`'s types models addressing more than one concurrent DUT connection per `Study` anyway. **The enforcement point is firmware, not the controller's link budget** — `ble_bridge_real.c`'s `execute_connect` refuses to open a second link while one is live. *(Correction, 2026-08-04, from the first real build: this decision originally claimed `CONFIG_BT_MAX_CONN` "stays at its default single-connection value." It does stay at its default, but that default is **2** here, not 1, and deliberately so: with the SoftDevice Controller the central role gets `BT_MAX_CONN - BT_CTLR_SDC_PERIPHERAL_COUNT` slots, and `BT_CTLR_SDC_PERIPHERAL_COUNT` defaults to 1 whenever `BT_PERIPHERAL` is enabled — so `BT_MAX_CONN=1` would leave the central role **zero** slots and break every central-role `BleConnect`, while still building and linking cleanly. Verified by actually building it that way: no error, no warning, 1 KB less RAM, and a silently broken role. The board conf now pins `CONFIG_BT_MAX_CONN=2` explicitly with that reasoning in a comment, so the value reads as intentional rather than as slack worth trimming.)*
16. **A `native_sim` workspace, alongside `nordic/`, for host-side iteration without real hardware.** *(Implementation note, 2026-08-04: `ble_bridge_real.c` now implements the full `Action`/`GattOperation` surface — `BleConnect` in both roles and every `DataExchange` operation, not just `BleAdvertise`. That made three additions to the shared internal API, all mirrored in `ble_bridge_stub.c` per this decision's hand-sync cost: `struct outcome` gained a borrowed `captured_data`/`captured_len` pair mirroring `StepResult.captured_data`, `ble_connect_params` gained the `BleAddressKind` the crate's `BleAddress` carries and Zephyr's `bt_addr_le_t` requires, and a `ble_bridge_set_stream_handler` hook was added for `GattOperation::StreamCapture`'s continuous samples — see §4 for why nothing wires that hook up yet.)* Zephyr's `native_sim` board runs a Zephyr application as a native Linux process — useful here for exercising the serial/COBS protocol parsing and the `embarch-study-designer` FFI glue (`study_ffi.c`) without needing the physical nRF54L15DK plugged in. Scoped narrowly: no virtual-PTY serial transport (protocol-parsing/FFI-glue logic is unit-tested directly, in-process, not through a literal serial link — framing correctness itself is `embarch-study-designer`'s own round-trip tests' job, not this workspace's). BLE is stubbed as a **separate source file, not an `#ifdef`-gated branch inside one file**: `ble_bridge_real.c` (Zephyr BT host calls, built by `workspaces/nordic/`) and `ble_bridge_stub.c` (canned `Outcome`s, built by `workspaces/native_sim/`) both implement the same internal C API that `main.c`/`serial_protocol.c` call into, and each workspace's `CMakeLists.txt` picks which one to compile — keeping the real BLE-host-calling code free of stub-only branches (and vice versa), at the cost of the two files needing to be kept in signature-sync by hand, acceptable since that shared internal API is small (mirrors the `Action`/`GattOperation` surface, §1). This keeps the full study-execution flow (serial → dispatch → "BLE" action → result) runnable and testable end-to-end on a host machine, just without a real radio at the end of it.
17. **BLE address: a static random address, fixed at build/boot time — not a resolvable private address (RPA), and not runtime-configurable by Core.** Simplicity and test reproducibility over BLE-privacy realism: dev-bench isn't emulating a privacy-conscious consumer device, it's a test fixture, and a stable address makes logs/captures easier to correlate across runs. Plain Zephyr default behavior, no custom addressing logic needed.
18. **`HelloAck` gains a firmware-identity field: `firmware_version: heapless::String<{limits::MAX_FIRMWARE_VERSION_LEN}>`, a single free-form string, not a structured multi-field type.** `schema_version`/`compatible` alone (`embarch-study-designer/design.md` §3 decision 12) tell Core whether the wire shape matches, but not which actual firmware build is running on the other end of the link — a real gap when something misbehaves and the question is "did this dev-bench even get reflashed with the fix." A single string is the simplest shape that still answers that question; whatever the dev-bench build embeds into it (`git describe` output, a board ID, a build timestamp, some combination) is dev-bench build-tooling's own concern, not fixed at the wire-type level — the append-only discipline (`embarch-study-designer/design.md` §3 decision 10) leaves room for a future structured field alongside this one if a single string ever proves insufficient. Implemented via a new `limits::MAX_FIRMWARE_VERSION_LEN` constant and `STUDY_DESIGNER_SCHEMA_VERSION` bump (v1 → v2) in `embarch-study-designer` — same discipline as any other wire-relevant change to that crate (§3 decision 12), not a new kind of change. Bumped in the same pass as decision 7's `LogLine` addition (one schema-version bump covering both, per §4's prior note).
19. **Dev-bench firmware validates `steps_crc` itself before running any step — restating, not reopening, `embarch-study-designer/design.md` §3 decision 17.** That decision already specifies this exact behavior at the Core↔dev-bench hop; this firmware's `study_ffi.c` is expected to call the crate's existing `essd_study_decode_and_verify` FFI function (`embarch-study-designer`'s `src/ffi.rs`) for it directly, rather than reimplementing CRC verification — the function already exists and already returns exactly the "did decode succeed / does the CRC match" answer this step needs.
20. **Initial implementation bring-up compiles `study_ffi.c` against a stub, not the real `embarch-study-designer` FFI staticlib, until decision 8's west-module/cross-compile wiring exists.** Mirrors the reasoning already accepted for `native_sim`'s BLE stub (decision 16): getting `main.c`/`ble_bridge_real.c`/`serial_protocol.c` building and running on real nRF54L15DK hardware (even against fixed/fake decode results) doesn't need to wait on the separate, harder problem of cross-compiling and linking a Rust staticlib per board target — that problem is decision 8's to close, and closing it is gated on `embarch-study-designer/design.md` §7's own nRF54 toolchain gap. `study_ffi.c` starts as a stub returning fixed results, gets swapped for real calls into the compiled staticlib once decision 8 lands; no interface change expected at that point, since `study_ffi.c`'s call signatures are dictated by `embarch-study-designer`'s existing FFI surface (that crate's §3 decision 7), not invented by this stub.
21. **`main.c` moves from a fixed demo sequence to real per-`Study` dispatch once `embarch-core`'s `study.rs` sends a real `StudyStart` — scoped now, implemented once that hop exists (2026-08-15, closing item 45 of that day's design-improvement review).** Today's `main.c` runs one hardcoded action+streaming sequence regardless of what (if anything) arrives over serial, standing in for real dispatch since no message ever carried a `Study` before `embarch-study-designer/design.md` §3 decision 24 defined `StudyStart`/`StepResult`/`StudyDone`. The real shape, now that those exist: on receiving `StudyStart`, dev-bench validates `steps_crc` (decision 19, already specified — unchanged), then dispatches each `Step` in order through the existing `ble_bridge_real.c`/`ble_bridge_stub.c` `Action`/`GattOperation` surface (decision 16, already implemented for every action kind), sending a `StepResult` after each one completes and a final `StudyDone` when the study finishes or aborts (per that step's `continue_on_fail`, `embarch-study-designer/design.md` §4.2). This is the real gate item 1 of the review flagged and this doc's §1 already names as the actual scope-blocker for this sub-project — recorded here as the concrete next implementation step, not a new open question.
22. **`GattOperation::StreamCapture`'s samples now have somewhere to go: a stream handler decoding raw notification bytes into batched `Sample`s (2026-08-15, closing item 46).** Previously blocked on `Sample.value` being a single, unit-less `f32` with no accepted way to turn an arbitrary GATT notification's bytes into one — `embarch-study-designer/design.md` §3 decisions 25/27 close that: `Sample` now carries `unit`/`channel_id`, and the wire form is a batched `StreamChunkBatch`, not one frame per sample. `main.c` registers a `ble_bridge_set_stream_handler` callback (the hook decision 16's implementation note already added but left unused) that decodes each raw notification as a sequence of little-endian `f32` values — as many complete 4-byte groups as the notification holds, any trailing partial bytes logged and dropped — and buffers them into a `StreamChunkBatch` (base timestamp from the first sample in the batch, `sample_interval_ms` from the step's own `PowerSampleWindow.sample_rate_hz` when set, or a firmware-side default for a `SensorWaveform` capture with no explicit rate) before sending it once full or once the step ends. `unit`/`channel_id` default to `Unit::Raw`/`0` — a real sensor-specific mapping is dev-bench build-tooling's concern (a compile-time constant per board/sensor), not something this handler decides generically; provisional, same posture as every other hardware-unvalidated constant in this doc.
23. **`BleAddress`'s byte order is now stated where it belongs — in `embarch-study-designer`'s own type docs, not just assumed here (2026-08-15, closing item 47).** `ble_bridge_real.c` has always assumed display order (`AA:BB:CC:DD:EE:FF`, most-significant-byte first, matching `Uuid`'s documented big-endian convention) and reverses on the way into Zephyr's little-endian `bt_addr_le_t` — correct, but previously only asserted here, not in the crate that actually owns the type. `embarch-study-designer/design.md` §4.3 now states this explicitly (see that doc's own changelog); this firmware's assumption is unchanged, now backed by the authoritative source instead of standing alone.
24. **The power-measurement front end moves from "entirely unscoped" to a provisional pick: a Nordic PPK2 driven as an external instrument (2026-08-15, closing item 48's "pick one, even provisionally" framing).** §1 correctly scoped power-sampling hardware as a hardware/BOM decision this document defers — but "entirely unscoped" was also the single largest blocker the 2026-08-15 review identified, since it's what `Sample`'s shape, `data.csv`'s columns, and the achievable sample rate all wait on (§7, `embarch-study-designer/design.md` §7). Provisional pick, **not yet ordered or wired into any workspace**: a Nordic PPK2, driven over USB from whatever machine runs `embarch-core` (or from dev-bench itself, if it turns out to expose a host interface) as an external instrument rather than an on-board shunt+ADC design — the fastest path to exercising the whole `PowerSampleWindow`/`StreamChunkBatch` path end-to-end without a bespoke board respin, and reversible: nothing in `embarch-study-designer`'s wire types assumes the source of a `Sample`, so swapping the PPK2 for on-board sampling hardware later is a firmware-only change. This is a proposal to unblock the roadmap (`embarch-roadmap.md`'s Next bucket, updated to name it), not a locked-in hardware decision — treat it exactly as provisional as this entry says until someone actually acquires and spikes one.
25. **A stale-firmware `doctor` check, and `west flash`'s missing "when do I need to do this" signal, are tied together (2026-08-15, closing items 49/50).** `HelloAck.firmware_version` (decision 18) exists precisely to answer "did this bench get reflashed," but nothing consumed it until now. New `embarch-umbrella` `doctor` check (§ table in `embarch-umbrella/design.md` §5) compares `HelloAck.firmware_version` against the dev-bench repo's own `git describe` (run against whichever `embarch-dev-bench` checkout the engineer has locally, path configured the same way `embarch-api`'s `source_path` is) — a mismatch is exactly the signal item 50 asked for: "you changed dev-bench firmware and haven't reflashed it," surfaced at `doctor` time rather than discovered as a confusing mid-study failure. Decision 13 (flashing stays a manual human `west flash`, outside `embarch-core`) is unchanged — this only adds the *reminder*, not an automated flash step.

- 2026-08-04 — `ble_bridge_real.c` went from one wired-up action to the full `Action`/`GattOperation` surface (§3 decision 16's implementation note). `BleConnect` covers both roles: central scans (filtering on `target_address` when set, ignoring non-connectable advertisers) and initiates from the scan callback; peripheral advertises and, when a specific `target_address` was asked for, drops a wrong peer and keeps advertising for whatever of the step's budget remains rather than reporting a Pass against the wrong DUT. `DataExchange` acts as a GATT client: primary-service then characteristic discovery (cached per connection, invalidated on disconnect), then read / write-with-response / notify / indicate / subscribe / stream-capture. Every action is bounded by one deadline derived from `Step.timeout_ms` — discovery included, not just the final request — with `Notify`/`Indicate` additionally bounded by the `GattOperation`'s own timeout, whichever expires first. A timeout cancels the pending GATT request (`bt_gatt_cancel`) instead of leaving Zephyr owning the params struct, which would fail the next step with `-EBUSY`. `BleAdvertise` was rewritten in the same pass, partly as a bug fix: it used `BT_LE_ADV_CONN_NAME`, which no longer exists in Zephyr 4.x, so the `nordic` workspace could not have compiled; it now builds real advertising data from the Action's own `local_name` and `adv_interval_ms` (previously ignored in favor of `CONFIG_BT_DEVICE_NAME`) and puts service UUIDs in the scan response, failing explicitly if more are requested than a legacy scan response can carry (exactly one 128-bit UUID) rather than silently advertising a subset a DUT would then never find. Requires two new Kconfig symbols in `app/boards/nrf54l15dk_nrf54l15_cpuapp.conf` (`CONFIG_BT_GATT_CLIENT`, `CONFIG_BT_GATT_AUTO_DISCOVER_CCC`) plus a larger `CONFIG_MAIN_STACK_SIZE`, since actions now block on the main thread. Deliberately *not* added: an explicit `bt_conn_set_security()` call — Zephyr's ATT layer already re-runs a request at higher security when a DUT answers with an authentication/encryption error, which is all decision 11's Just Works pairing needs. Verified on `native_sim` (which builds the stub, kept in signature-sync by hand): `west build -b native_sim app` and the 8-case `app/tests/serial_protocol` ztest suite both pass, and feeding a COBS-framed `Hello` in via `-uart_stdinout` still produces the full `HelloAck`(schema 2, `compatible`, `firmware_version`)/`LogLine`/`StreamStart`/`StreamChunk`×3/`StreamEnd`/`LogLine` sequence — so the header changes didn't disturb the serial path.
