## 1. Purpose and scope

`embarch-dev-bench` is the physical rig that plays the DUT's BLE counterpart during a `Study` (`embarch-study-designer/design.md` §1) — it advertises, connects (as central or peripheral), exchanges GATT data, and samples power, per whatever `Study.steps` `embarch-core` relays to it over a serial link. It is Zephyr-based C firmware, cross-vendor by design: "one firmware project" doesn't mean one board or one silicon vendor, it means one shared application implementation that different west workspaces build for different vendor targets (§3).

**v1 scope, explicitly bounded:**
- **BLE + power sampling only** — exactly what `embarch-study-designer`'s `Action`/`GattOperation` enum already models (`BleAdvertise`, `BleConnect`, `DataExchange`, `PowerSampleWindow`, `GattOperation::StreamCapture`). `embarch.md`'s original one-line description ("actively stimulates DUT inputs and senses outputs") is broader than this — GPIO/analog stimulus (driving a button pin, injecting an analog sensor signal) is real future scope, not v1, and isn't modeled in `embarch-study-designer` today. Adding it later means a new `Action` variant there, not just dev-bench firmware work.
- **No physical DUT connector, no power-sampling hardware yet.** v1 is BLE-proximity-only; a DUT is whatever's in the DUT's own physical BLE range. `PowerSampleWindow`/`GattOperation::StreamCapture` stay real types that dev-bench firmware will eventually serve, but the actual sampling hardware (a shunt + ADC, or similar) is out of scope until a specific board/BOM decision is made.
- **No on-board status indication** (LEDs, etc.) — dev-bench's state is observable only through `embarch-core`/`study_status`, not by looking at the board.

## 3. Locked-in design decisions and rationale

1. **Zephyr as the one common RTOS across every board/vendor — not a custom multi-SDK HAL abstraction.** "One firmware project for any board" is interpreted as "any board a Zephyr flavor supports," not "every vendor's own native SDK (ESP-IDF, STM32Cube, Pico-SDK) behind a hand-written abstraction layer." The latter is a materially bigger undertaking — effectively building a small cross-platform embedded framework from scratch (Arduino-core/PlatformIO/mbed's job) — and buys nothing `embarch-dev-bench` specifically needs, since Zephyr already provides vendor-portable BLE host, GPIO, and ADC APIs. This also means `embarch-study-designer/design.md` §3 decision 7 (dev-bench firmware is C, not Rust, because the BLE host stays a C API) doesn't need to be reopened for a broader vendor set — every mainstream vendor's BLE host under Zephyr is the same Zephyr Bluetooth host API regardless of silicon.
2. **One repo, multiple west workspaces (one per vendor family), sharing one application source tree — not one single west workspace, and not one repo per vendor.** A west manifest (`west.yml`) pins exactly one Zephyr revision at a fixed path; a vendor's own Zephyr fork (e.g. Nordic's nRF Connect SDK, decision 3 below) pins its *own* revision, incompatible with mixing into the same manifest as vanilla Zephyr or another vendor's fork. Resolved by giving each vendor family its own west topdir under `workspaces/`, each with its own `west.yml`, while the actual application implementation (`app/`) is written once and referenced (not copied) by every workspace's build. This achieves the part of "one firmware project" that actually matters — one shared implementation, one repo, one git history — without fighting west's one-manifest-one-Zephyr-revision model.
3. **Vendor SDK forks are accepted per family (not insisted-on vanilla Zephyr everywhere) — but application code is restricted to portable Zephyr APIs regardless.** A vendor fork (e.g. NCS) is often the only place brand-new silicon's HAL/BLE controller support lands first — insisting on vanilla-only would risk blocking on upstream support timing for every new board. Accepted trade-off: `app/src/*.c` only calls stable, vendor-neutral Zephyr subsystem APIs (`bt_*`, `gpio_*`, `adc_*`) — never anything NCS-proprietary — so the same source keeps working if a given workspace's pinned revision is later swapped toward vanilla, or if a second workspace picks a different flavor entirely. The cross-vendor Zephyr-revision-reconciliation question (could two families ever share one workspace after all?) is deliberately not solved now — see §4.
4. **First board: nRF54L15DK.** Chosen over nRF54H20DK specifically to avoid taking on `embarch-study-designer/design.md` §3 decision 7's already-flagged nRF54H20 complexity (mandatory *multi-core* `sysbuild` build) for a board whose job here — running the Zephyr BLE host in both central and peripheral roles, bridging serial to Core — doesn't need multiple cores. Single-core, single-image, well-trodden path. *(Correction, 2026-08-04, from the first real build: this decision originally said "standard (non-`sysbuild`) Zephyr build," which is no longer accurate — NCS 3.4's `west build` wraps every application in `sysbuild` regardless, so the output lands in `build/app/zephyr/` and `build/domains.yaml` exists. It stays a single domain named `app` with one image and one flash step, so the substance of the decision — no multi-core image coordination to reason about — holds; only the "non-sysbuild" phrasing was wrong.)* **Amended 2026-08-19: no longer the board Milestone 2 targets.** The physical unit broke before ever being flashed (decision 26) and its RMA replacement never arrived in time to close Milestone 2's Definition of Done; the ESP32-C5-WROOM-1 (decision 26), originally stood up only as an interim substitute, validated the milestone's entire dispatch/handshake/study path end to end first, and Milestone 2's own scope moved onto it (`embarch-decision-reversals.md` row 13, `embarch-dev-bench/milestone-8.md` §2). This doesn't retire the nRF54L15DK from `workspaces/` (§2's tree keeps `nordic/` as a built, currently-inactive workspace) or resolve decision 10's cross-vendor-family question — it's a milestone-scope decision, not a permanent board deprecation.
5. **First workspace (`workspaces/nordic/`) pins nRF Connect SDK (NCS), not vanilla Zephyr.** Follows directly from decision 3: nRF54-family support is an NCS-first (often NCS-only, for the newest parts) proposition. BLE controller for this workspace specifically: **Nordic's SoftDevice Controller** (proprietary, shipped via NCS) over Zephyr's open-source BLE controller — best feature/support coverage on Nordic silicon specifically, at the cost of that specific choice being Nordic-only (a future non-Nordic workspace picks its own controller independently; this isn't a cross-workspace decision).
6. **Core link: a plain UART over the nRF54L15DK's on-board J-Link VCOM, not USB CDC ACM — one interface, no separate log/console interface.** Originally specified as USB CDC ACM; revised once implementation research found the nRF54L15 SoC has no USB device peripheral at all (USB only arrives with the newer nRF54LM20 family) — the DK's USB connector belongs entirely to its on-board SEGGER J-Link debug-probe chip, not the target SoC. That J-Link chip already bridges one of the nRF54L15's real UART peripherals to a virtual COM port on the host (the same VCOM used for the DK's existing debug console) — firmware-side this is a completely ordinary Zephyr UART (`uart_poll_out`/interrupt-driven `uart_*` calls on a physical UART peripheral), with no SEGGER-specific code and no USB device stack anywhere in this firmware. Dev-bench still appears as a plain serial port (`/dev/ttyACM*`/a COM port) when plugged in, still bus-powers the board, still matches Core's own existing DUT serial-log pattern (`embarch-core/design.md` §5) and requires no separate network stack (`embarch-study-designer/design.md` §3 decision 4's reasoning for the hop, unaffected by this revision) — only the physical/peripheral mechanism changed, not the wire protocol or Core-facing behavior. A second interface for dev-bench's own debug/log output was considered and rejected in favor of decision 7 below, same reasoning as before, now just "a second UART instance" rather than "a second CDC ACM interface."
7. **Dev-bench's own log output travels as a new `DevBenchMessage` variant, not as raw interleaved bytes on the shared line.** Literally sharing one byte stream between free-text log lines and COBS-framed `DevBenchMessage`s would corrupt the protocol — COBS frames are self-delimiting, plain log text isn't, so a receiver parsing for frame boundaries would choke on stray log bytes it wasn't expecting. Resolved the same way every other kind of dev-bench-to-Core data already travels: a log line is just another properly-framed message. Implemented as an append-only `DevBenchMessage::LogLine { text: heapless::String<{limits::MAX_LOG_LINE_LEN}> }` variant in `embarch-study-designer` (same discipline as that crate's §3 decision 10) — a small, forward-compatible addition to that crate, not a redesign. **Amended 2026-08-26 (decision 38): `CONFIG_LOG` is now `y`.** For its first three weeks this decision was implemented as `CONFIG_LOG=n` plus a handful of hand-written `send_log_line()` calls, which read as though this decision had *chosen* to have no logging subsystem. It hadn't — what it forbids is unframed log text on the shared wire, and a log backend that emits `LogLine`s satisfies it exactly. Decision 38 turns the subsystem on without changing a word of this decision's substance or a byte of the wire.
8. **The `embarch-study-designer` Rust staticlib's cross-compilation is invoked automatically as part of `west build` — implemented 2026-08-18, via a direct path-based `cargo rustc` invocation rather than the formal west-managed-module plumbing this decision originally specified.** A CMake custom target (`app/CMakeLists.txt`) runs `cargo rustc --release --target thumbv8m.main-none-eabi --features ffi --lib --crate-type staticlib` against the crate's path (a sibling repo by default, `EMBARCH_STUDY_DESIGNER_PATH` env var override available), rather than requiring a separate manual build/publish step before `west build` can succeed — one build command, as originally intended, just not literally a `west`-manifest `module.yml` project the way the original text specified: the crate is edited locally far more often than pulled from a pinned upstream revision, and this workspace's manifest never actually gained that module entry, so a plain path-based invocation reaches the same practical outcome with less git plumbing. Skipped entirely for `native_sim` (`CONFIG_ARCH_POSIX`) — that workspace keeps `study_ffi_stub.c` (decision 20) permanently, mirroring `ble_bridge_stub.c`'s own reasoning. **Board→Rust-target-triple mapping, resolved for the first board:** nRF54L15's Cortex-M33 core is `thumbv8m.main-none-eabi` — the *soft*-float variant specifically, **not** `-eabihf`: this app's Zephyr build has no hardware-FPU ABI enabled, and a hard-float-ABI staticlib fails to link ("uses VFP register arguments") the moment any code path touches an `f32`, which includes `Sample`'s own field internally, not just this crate's actual FFI-exposed function signatures (none of which pass a float) — found by hitting exactly that link error against the real board before settling on the soft-float target. Confirmed producing a real, flashable `zephyr.hex` for the nRF54L15DK, ~1.2 KB of flash for the whole decode/CRC path. A second board/core extends the CMake if/else this triple selection lives in, not replaces it (§4).
9. **No CI for now.** ~~Matches `embarch-study-designer`'s own precedent (no CI set up there either) — revisit once there's more than one board actually building, so a compile-only `west build` matrix check has more than one target to be useful across.~~ **Superseded 2026-08-15** (`embarch-core/design.md` §3 decision 17, closing item 15 of that day's design-improvement review): a compile-only `west build -b native_sim app` job is worth having even with one board, since it's cheap, hardware-independent, and would have caught the real `BT_LE_ADV_CONN_NAME` breakage below before it was found by hand — a matrix check across boards is still deferred until a second board exists, but "no CI at all" no longer holds.
10. **A second vendor family/board is deliberately left unspecified.** The `workspaces/`-per-vendor-family convention (decision 2) is designed to obviously extend, but no second vendor, board, or Zephyr flavor is committed to yet — keeps the multi-workspace layout honest (built to extend, not pre-built for a hypothetical) rather than speculatively scaffolding for a board that doesn't exist.
11. **BLE pairing: Just Works, bonds kept RAM-only and cleared on `Hello` — no NVS/settings persistence across reboots.** Some real DUTs require pairing/encryption before certain characteristics are accessible, so v1 needs at least Just Works (Zephyr's `CONFIG_BT_SMP`) rather than unencrypted-only. Persisting bonds to flash (Zephyr's Bluetooth settings subsystem) was considered and rejected: a study should always start from a known, clean pairing state rather than accumulate stale bonds across unrelated studies or reboots. Resolved by extending `embarch-study-designer/design.md` §3 decision 12's existing "`Hello` doubles as a hard reset" — a fresh `Hello` now also clears dev-bench's in-RAM BT bonding table, not just its study execution state. A single study's own internal reconnects (if a `Study`'s steps disconnect and reconnect the same DUT) still don't have to re-pair, since nothing clears the bond table mid-study. **Amended 2026-08-26 (decision 37):** "cleared on `Hello`" is now *also* "cleared at study end", explicitly, rather than relying on the next `Hello` to happen to arrive first — and "nothing clears the bond table mid-study" is no longer unconditionally true, because `Action::BleUnbond` ([embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 50) exists precisely so an author can. Neither changes this decision's substance: bonds are still RAM-only, and a study still starts from a clean pairing state.
12. **Auto-detection via the on-board J-Link's own SEGGER VID plus a product-string/serial-number match, not a custom VID/PID — revised from the original plan once decision 6 moved off USB CDC ACM.** A custom VID (`0xEBAC`)/PID (`0xDB01`) was originally locked in for `embarch-core` to identify dev-bench programmatically among other serial devices (e.g. the DUT's own debug console), the same auto-detection goal as before — but that descriptor would have to be advertised by dev-bench's own USB CDC ACM stack, which decision 6 established doesn't exist on this SoC; the port Core actually sees is enumerated by the on-board J-Link chip, which advertises SEGGER's own USB descriptor (VID `0x1366`), not anything dev-bench firmware controls. `embarch-core` instead identifies dev-bench's port by matching SEGGER's VID plus a product-string or serial-number heuristic (e.g. matching against the specific J-Link's serial number recorded once at setup, since a lab may have more than one SEGGER-probed board plugged in) — entirely an `embarch-core`-side change, no firmware-side VID/PID logic at all. **Implemented 2026-08-04** in `embarch-core`'s `dev_bench.rs`; [embarch-core/design.md](../embarch-core/design.md) §5 is now the source of truth for the actual matching rules (including how it resolves one J-Link exposing several VCOMs), and §4 below carries only what real hardware still has to confirm.
13. **Reversed 2026-08-19/20 — `embarch-core` *can* flash dev-bench firmware now; the exclusion below no longer holds as a blanket rule.** Originally: flashing dev-bench firmware is a direct `west flash` (J-Link/nrfjprog), entirely outside `embarch-core`, because "`embarch-core`'s probe-rs access is explicitly scoped to the DUT — it has no business flashing the bench that's testing that DUT" (`embarch-core/design.md` §1). That was a deliberate separation-of-concerns choice, not a technical limitation, made before dev-bench had any board whose flashing mechanism Core could plausibly share — the nRF54L15DK's SEGGER J-Link genuinely is a separate tool (`nrfjprog`/`west flash`) from anything Core's probe-rs already talked to. It stopped holding the moment a board showed up (the ESP32-C5 interim substitute, decision 26) whose on-chip debug probe `probe-rs` already speaks natively: `embarch-core/design.md` §3 decision 18 adds real, validated support for exactly this — `POST /flash`/`POST /reset` against `chip: "esp32c5"`, over the same native USB-JTAG interface Windows already enumerates, **with zero WSL2↔Windows USB forwarding needed** (Core already runs natively on Windows; the board's USB connector was never a WSL2-side device to forward in the first place). Validated end to end: real flash, real reset-and-run, a real `Hello`/`HelloAck` handshake, and a full physical self-test `Study` completing via `embarch-api`'s existing `run-study` CLI — see that doc's decision 18 for the full mechanism (why `Format::Idf` doesn't work for a Zephyr-built image, and why `Format::Bin` at Zephyr's own merge address does instead). **What this reversal does *not* do:** migrate the nRF54L15DK off its existing `west flash`/J-Link workflow — that board's own SoC (`nrf54l15`) has been in Core's `SOC_TO_CHIP` table since decision 12, but flashing it *through* Core was never attempted this pass, so decision 13's original default stays the practical answer there until someone actually validates it. A human plugging in dev-bench's own on-board debugger and running `west flash` by hand remains entirely correct and unaffected for any board/workspace this hasn't been exercised against yet.
14. **No local hardware watchdog.** `embarch-study-designer/design.md` §3 decision 16's Core-side host watchdog (added specifically because a hung dev-bench can't self-report its own `TimedOut`) is treated as sufficient detection; a self-resetting local `CONFIG_WDT` was considered and deferred rather than rejected outright — it's a cheap addition to revisit if a hung dev-bench in practice needs power-cycling too often for Core's detection alone to be a good enough experience.
15. **One dev-bench, one DUT connection at a time — no multi-connection support.** Matches `embarch-study-designer/design.md`'s existing "one study in flight at a time" model (that crate's §5.1) exactly: testing multiple DUTs in parallel means multiple independent Core+dev-bench pairs, not one dev-bench juggling several BLE connections. Nothing in `embarch-study-designer`'s types models addressing more than one concurrent DUT connection per `Study` anyway. **The enforcement point is firmware, not the controller's link budget** — `ble_bridge_real.c`'s `execute_connect` refuses to open a second link while one is live. *(Correction, 2026-08-04, from the first real build: this decision originally claimed `CONFIG_BT_MAX_CONN` "stays at its default single-connection value." It does stay at its default, but that default is **2** here, not 1, and deliberately so: with the SoftDevice Controller the central role gets `BT_MAX_CONN - BT_CTLR_SDC_PERIPHERAL_COUNT` slots, and `BT_CTLR_SDC_PERIPHERAL_COUNT` defaults to 1 whenever `BT_PERIPHERAL` is enabled — so `BT_MAX_CONN=1` would leave the central role **zero** slots and break every central-role `BleConnect`, while still building and linking cleanly. Verified by actually building it that way: no error, no warning, 1 KB less RAM, and a silently broken role. The board conf now pins `CONFIG_BT_MAX_CONN=2` explicitly with that reasoning in a comment, so the value reads as intentional rather than as slack worth trimming.)*
16. **A `native_sim` workspace, alongside `nordic/`, for host-side iteration without real hardware.** *(Implementation note, 2026-08-04: `ble_bridge_real.c` now implements the full `Action`/`GattOperation` surface — `BleConnect` in both roles and every `DataExchange` operation, not just `BleAdvertise`. 22. **SUPERSEDED 2026-08-25 — see the note at the end of this entry.** **`GattOperation::StreamCapture`'s samples now have somewhere to go: a stream handler decoding raw notification bytes into batched `Sample`s (2026-08-15, closing item 46).** Previously blocked on `Sample.value` being a single, unit-less `f32` with no accepted way to turn an arbitrary GATT notification's bytes into one — `embarch-study-designer/design.md` §3 decisions 25/27 close that: `Sample` now carries `unit`/`channel_id`, and the wire form is a batched `StreamChunkBatch`, not one frame per sample. `main.c` registers a `ble_bridge_set_stream_handler` callback (the hook decision 16's implementation note already added but left unused) that decodes each raw notification as a sequence of little-endian `f32` values — as many complete 4-byte groups as the notification holds, any trailing partial bytes logged and dropped — and buffers them into a `StreamChunkBatch` (base timestamp from the first sample in the batch, `sample_interval_ms` from the step's own `PowerSampleWindow.sample_rate_hz` when set, or a firmware-side default for a `SensorWaveform` capture with no explicit rate) before sending it once full or once the step ends. `unit`/`channel_id` default to `Unit::Raw`/`0` — a real sensor-specific mapping is dev-bench build-tooling's concern (a compile-time constant per board/sensor), not something this handler decides generically; provisional, same posture as every other hardware-unvalidated constant in this doc.

    **Superseded 2026-08-25 by [embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 39 — and the reason is that this handler was making an assumption it was never in a position to make.** "Decode each raw notification as a sequence of little-endian `f32` values" is **an interpretation of what a specific DUT's bytes mean**, sitting in dev-bench firmware, where no engineer declared it. It is a plausible guess — many sensor streams really are `f32` arrays — and it is wrong for a log, wrong for a packed 16-bit ADC stream, and wrong for anything framed. That is exactly the category `embarch-study-designer/design.md` §3 decision 35 rules out, arrived at here from the streaming side rather than the GATT side. Under decision 39 dev-bench **forwards arrival-stamped bytes and interprets nothing**; the `f32` reading becomes one engineer-declared `StreamEncoding::Samples { layout, .. }` among several, chosen host-side by whoever actually knows. The deferred "compile-time constant per board/sensor" this entry ends on is retired with it — there is no longer a firmware-side place for that constant to live, which is the point.

28. **`Action::GattMonitorStart`/`GattMonitorStop` and the streamed GATT transcript — `embarch-study-designer/design.md` §3 decision 36, 2026-08-25.** The firmware half of that decision, in three parts.

    **A capture window that spans steps.** `execute_gatt_monitor_all`'s body is split into `monitor_subscribe_all` (discovery + subscribe-to-everything) and `monitor_unsubscribe_all` (teardown), so `GattMonitorAll` keeps its exact previous behaviour — subscribe, wait out the step, tear down — while `GattMonitorStart` runs only the first half and leaves the subscriptions armed, and `GattMonitorStop` runs only the second. A `monitor_window_open` flag tracks it, cleared on disconnect (a window can't outlive the connection whose subscriptions it holds, or a later `Stop` would unsubscribe against a freed `conn`) and on `Hello` (which is already a hard reset, decision 12/16). `main.c`'s `dispatch_study` closes a window the study left open before sending `StudyDone`.

    **Emitting the transcript from BLE callback context.** `ble_bridge.h` gains a sink (`ble_bridge_set_transcript_sink`) that `ble_bridge_real.c` calls at every GATT event in either direction — connect/disconnect, discovery start, each service and characteristic found, each subscribe/unsubscribe, each read/write request and response, each notification/indication, and each error. Entries are built as a **stack local, not a shared static**: the sink is called from both Zephyr's BT RX thread (anything inbound) and whichever thread called `ble_bridge_execute` (anything outbound), and a shared staging buffer would tear under a notification arriving mid-emit. That ~290-byte frame is why `CONFIG_BT_RX_STACK_SIZE` is raised in both real-hardware board fragments — left alone it would have failed as an intermittent stack overflow under exactly the notification bursts this feature exists to capture.

    **Getting entries onto the wire without stalling BLE.** `main.c`'s sink does one bounded copy into a `k_msgq` (`K_NO_WAIT` — blocking the BT RX thread on a full queue would stall the very notifications being recorded; a dropped entry is counted and reported over `LogLine` instead, and Core logs that at `warn`, because a transcript silently claiming to be exhaustive when it isn't is the exact failure decision 36 exists to remove). A dedicated TX thread drains it. That makes a **second writer to the link UART**, which the previous single-threaded-loop assumption didn't allow for, so `send_message` became `send_message_locked` under a new `link_tx_mutex` that every sender now holds across *build-and-send* — the build half is what actually races, since every sender builds into the shared `tx_scratch`.

    **A real SRAM finding, measured not predicted — the second time this board has produced one (decision 27).** The TX thread's first version kept its own `struct dev_bench_message`, and the ESP32-C5 build **overflowed `sram0_0_seg` by 2720 bytes at link time**: that union is sized by its largest member (`dbm_study_start`, ~10 KB) regardless of which tag a given send uses. Fixed by having the TX thread build into the same `tx_scratch` every other sender uses — the mutex above is what makes one buffer safe for two threads — rather than by shrinking a limit. `DBM_MAX_TRANSCRIPT_PAYLOAD_LEN` is 244 (one full 247-byte ATT MTU minus the 3-byte ATT header) rather than `DBM_MAX_PAYLOAD_LEN`: the Rust type accepts up to 512, this firmware never produces more than one MTU's worth, and each queue slot costs real RAM. Sending fewer bytes than the receiving type can hold is always wire-legal; the reverse is not. `CONFIG_BT_L2CAP_TX_MTU`/`BT_BUF_ACL_{RX,TX}_SIZE` are raised to match — Zephyr's defaults would cap a notification at 62 bytes, fragmenting a shell response into rows that each look like a separate event.

    **The encoding is hand-written C and pinned against Rust.** `serial_protocol.c` gained the `DBM_TAG_GATT_TRANSCRIPT_RECORD` encode arm and the two new field-less action tags in both encode and decode. Nothing in this firmware's own tests would catch it drifting from what postcard expects — a reordered field or a `u8` written as a varint decodes into plausible-looking garbage, not an error — so the exact COBS frame is asserted in `tests/serial_protocol`, and the identical pre-COBS body is asserted from the Rust side in `embarch-study-designer`. Both must break together.

    31/31 ztests pass on `native_sim` and the app still builds there. Everything the paragraph above says is Phase B's remains Phase B's — including the retired tag 10 this firmware still sends.

    **(b) A pass-through role for a DUT signal — designed, not built, and deliberately not blocking anything.** [embarch-topology/design.md](../embarch-topology/design.md) §3 decision 18 gives a DUT signal a declared route, one of which is `Route::ViaDevBench { rx_pin, tx_pin }`: dev-bench receives on a declared pin and relays the bytes to Core over its existing link, as an ordinary tap. **dev-bench does not have the spare pins or the firmware for this today**, which is precisely why that decision made the bypass a first-class route rather than a workaround — [embarch-outpost](../embarch-outpost/design.md) ships against a USB-UART bridge on the Core machine and is not blocked on this bench.

    When it is built, **dev-bench passes bytes through and interprets nothing** — the same rule as (a), which is what makes it the same mechanism rather than a new one. Not decode-and-summarise: outpost record semantics depend on a specific DUT build's manifest, so a summarising bench would need reflashing whenever the DUT's manifest changed, and would be carrying DUT-specific knowledge that decision 35 rules out. The open hardware questions are real and unanswered: which pins are actually free on the ESP32-C5, whether a UART at the outpost's eventual baud can be received without loss while BLE is active, and whether relaying it fits alongside everything else the existing link already carries mid-study.

    **Amendment 2026-08-25: two more things join Phase B's firmware pass, both settled after Phase A closed** ([embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 39's own amendment). **A sibling `streams_crc`** on `StudyStart` after `streams`, checked here exactly as `steps_crc` already is — this decoder's `dbm_crc32` digests the one contiguous encoded-`steps` span today, and the new seal is a second contiguous span it already walks, plus one varint; `steps_crc`'s own definition does not move, so the existing pin's meaning is unchanged. **And `Step.power_sample` is retired**, which this firmware is uniquely well placed to confirm costs nothing: the encoder writes that `Option` byte as `None` unconditionally and the decoder reads-and-discards it, so the change is one write and one read deleted — net-negative firmware, the same bar (a) already sets. Both share **one** dev-bench wire bump with the rest of Phase B, and both `StudyStart` pinned COBS frames regenerate against `embarch-study-designer`'s own re-dumped pre-COBS bodies. Note the schema constant itself splits in two at the same time ([embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 12's amendment); the number this firmware compares at `Hello`/`HelloAck` is the **dev-bench wire** one.

30. **The link's inbound path made interrupt-driven, closing a silent 128-byte ceiling on every `StudyStart` — 2026-08-25.** `main.c`'s dispatch loop read the link UART itself: `receive_message` called `uart_poll_in` directly and `k_sleep(K_MSEC(1))` whenever the FIFO happened to be empty. At this link's 1 Mbaud (this board's own overlay), one millisecond of sleep is ~100 bytes of arrivals, against an ESP32 hardware FIFO 128 bytes deep — so **any inbound frame larger than the FIFO lost whatever landed while the reader was asleep.** `dbm_decode_frame` then failed on the truncated result and the loop simply `continue`d, which is the worst possible presentation: Core saw no reply of any kind and reported `"step timed out — no message received from dev-bench"` on step 0, indistinguishable from a dead link or a wedged board.

    **Why it went unnoticed until now.** Every study this suite had ever authored fit in the FIFO. The first stimulate-and-capture study (`embarch-study-designer/design.md` §3 decisions 36/41/42) is 132 payload bytes — the first one large enough to cross the line, which is why the whole feature had never once worked on hardware despite every unit test passing. The boundary was then confirmed directly rather than inferred, by sweeping a single step's `Write` payload length: frames of ~128 bytes completed, ~134 bytes timed out with no message, repeatably. After the fix, ~450-byte frames complete.

    An ISR now drains the FIFO into a `ring_buf` (`link_rx_ring`) and `receive_message` parses frames out of that, so frame parsing can never be what the FIFO is waiting on (`CONFIG_UART_INTERRUPT_DRIVEN=y`, `CONFIG_RING_BUFFER=y`). The buffer is sized to **scheduling latency, not to a whole frame** — deliberately 2 KB rather than `DBM_MAX_FRAME_LEN`, which is the worst-case 64-step `StudyStart` (~10 KB) this board cannot spare at ~96% SRAM (decision 27's own RAM finding). It doesn't need to be frame-sized: the parser drains continuously, and Core sends exactly `Hello` then `StudyStart` and then waits (`embarch-study-designer/design.md` §3 decision 24), so nothing arrives during the long `ble_bridge_execute` calls the loop blocks in. Overruns are counted and reported as a `LogLine` rather than dropped silently — the entire point of the change is that a lost inbound byte must never again look like a dead link. A poll-mode fallback is kept behind the same `#ifdef` for a platform with no interrupt-driven UART mode (native_sim, if the app is ever built for it); it carries the original ceiling and is not what real hardware uses.

    **Test-methodology change this forced.** Every `StudyStart` test in the ztest suite round-tripped through `dbm_encode_frame` first, so a decoder bug this file's own encoder mirrored exactly would pass all of them while failing against Core. The suite now also decodes the **real bytes `embarch-core` puts on the wire** for a four-step study, COBS-framed by an independent encoder written in the test itself, generated by `embarch-study-designer/tests/firmware_test_vectors.rs`.

31. **16-bit UUIDs were reported two bytes out of place — 2026-08-25.** `from_bt_uuid` wrote a `BT_UUID_TYPE_16` value into `out_be[0..2]`, but a 16-bit UUID expands to `0000xxxx-0000-1000-8000-00805F9B34FB` (Core Spec Vol 3, Part B) — offsets **2 and 3**. Live discovery therefore reported the Device Information Service as `180a0000-0000-1000-8000-00805f9b34fb` instead of `0000180a-…`, and every other 16-bit service and characteristic likewise.

    **Not cosmetic.** `Uuid::parse` in `embarch-study-designer` expands `"180a"` correctly, so a `DataExchange` authored against *any* 16-bit UUID could never match the same characteristic discovery had just reported — the two representations disagreed, and the study failed to find a service plainly visible in its own discovery output. 128-bit UUIDs were never affected (they take the byte-reversing branch), which is exactly why every custom-service study to date worked and this survived since decision 27 introduced the multi-width expansion. The 32-bit branch was always correct: a 32-bit UUID really does occupy offsets 0..3.

32. **`Action::BleConnect.target_name` — an advertised-name scan filter (`embarch-study-designer/design.md` §3 decision 43), 2026-08-25.** `scan_cb` already received the advertising payload and discarded it (`ARG_UNUSED(buf)`); it now parses Local Name AD elements and connects only to a matching advertiser, ANDed with the pre-existing `target_address` filter.

    **Names and connectable packets arrive separately, and two earlier attempts at this got it wrong.** With active scanning a peripheral's name usually lives in its scan response, which is not itself connectable, so the name and the connectable advertisement are two different callbacks in an order this code does not control. The first attempt kept a single "last address whose name matched" slot and connected on the *next* connectable advertisement from it. That fails outright, because `BT_LE_SCAN_ACTIVE` sets `BT_LE_SCAN_OPT_FILTER_DUPLICATE` — each advertiser is reported at most once per scan, so there *is* no next advertisement to match against. Scanning now uses the same type/interval/window with `BT_LE_SCAN_OPT_NONE`; the cost is more callbacks per second, bounded by the step's own timeout.

    The bookkeeping is now **keyed by advertiser address** (`struct scan_seen_entry`: address, best name seen, whether it has ever sent a connectable advertisement), which removes the ordering dependency entirely — whichever packet completes the pair triggers the connect, rather than only the connectable-arrives-second order. Matching is **exact**; a loose match would reintroduce the very failure decision 43 exists to remove, just less visibly.

    **Reporting what a failed scan saw, at two levels of detail.** `Outcome::fail_reason` is 64 bytes (`limits::MAX_FAIL_REASON_LEN`) — enough for a comma-separated name list, and the first version wasted a third of it echoing the name that was *asked* for, truncating the one name that mattered. So the compact list goes there, and the per-advertiser detail (address, connectable or not, and crucially **whether a name was advertised at all**) goes through a new `ble_log_sink` hook (`ble_bridge.h`) that `main.c` forwards as `LogLine` messages. That second level exists because a name-only report cannot distinguish "the DUT is silent" from "the DUT is on the air but advertises no name" — and the second is invisible to a name filter by construction. Live: a five-minute scan for a DUT's configured `CONFIG_BT_DEVICE_NAME` reported only unrelated names, leaving exactly those two possibilities open.

    The log sink is deliberately a **separate hook from the transcript sink**, with the opposite threading contract: it is only ever invoked from the dispatch thread inside `ble_bridge_execute`, so its sink may write the link UART directly, whereas the transcript sink is called from Zephyr's BT RX thread and must enqueue. Names are collected in the scan callback and only *sent* once the step resolves, for exactly that reason. Before this hook the bridge could only speak through a 64-byte `fail_reason`.

33. **`Hello`'s "hard reset" didn't wait for its own disconnect — 2026-08-25.** `ble_bridge_reset()` called `bt_conn_disconnect()` and returned. That only *requests* the disconnect: `active_conn` stays populated until `disconnected_cb` runs on Zephyr's BT RX thread. So the next study's `BleConnect` could execute while the previous connection was still tearing down and fail with `"already connected to a different peer"` — despite a `Hello` having just been processed, whose whole documented contract (decisions 11/12/16) is that it *is* a hard reset.

    Found running two back-to-back studies against two different addresses: the first attempt failed, the byte-identical retry passed. That asymmetry is the signature of a race, not of a configuration problem, and it's worth naming because "just run it again" would have hidden it indefinitely — this bench already has a known re-run-and-it-works flake from Milestone 3, which is exactly the cover a bug like this hides under.

    Now waits on `disconn_sem` with a fixed 2-second bound. Fixed rather than caller-supplied because `ble_bridge_reset` is `void` and is a reset, not a step, so it has no timeout budget to draw from; two seconds is far longer than a local disconnect needs, and timing out anyway leaves exactly the behavior this replaces, so the change can only improve matters.

    **Also this pass:** `SCAN_SEEN_MAX` raised 8 → 24 → **256**, at the user's call. The first real census hit the 8-entry cap and said so ("more than this firmware records"); the next found **12** distinct advertisers in three minutes, which put 24 one busy room away from truncating again. A cap that silently truncates defeats the diagnostic entirely — "not in the list" has to mean "not on the air", not "the list was full". 256 entries is ~9 KB of static RAM and takes this board to **98.44% SRAM** (5.9 KB free), affordable only because it's a flat table of 35-byte entries rather than anything frame-sized — contrast decision 29's ring buffer, which explicitly could *not* be sized to a worst-case frame. Lookup is a linear scan per advertisement: a few hundred byte-comparisons against a step timeout measured in seconds.

34. **dev-bench registers pairing callbacks and dispatches `BleSecurity`; "Just Works pairing needs no auth callbacks" was wrong — 2026-08-25.** `ble_bridge_real.c`'s own header comment stated the opposite as settled design: *"NOT handled here, deliberately: elevating the link to an encrypted/paired one. Zephyr's own ATT layer already re-runs a request at higher security when a DUT answers with an authentication/encryption ATT error, and decision 11's Just Works pairing needs no auth callbacks, so an explicit `bt_conn_set_security()` call would only duplicate that."* Both halves fail against a DUT that requires an authenticated link.

    **The mechanism, and it is a fact about our own code plus Zephyr, not an inference about any DUT.** dev-bench calls `bt_conn_auth_cb_register()` nowhere at all. With no callbacks registered, Zephyr's `get_io_capa()` returns `BT_IO_CAPA_NO_INPUT_OUTPUT`, and `sec_level_reachable()` then refuses `BT_SECURITY_L4` outright — so **L4 is unreachable from this bench regardless of what any study asks for**, and no amount of ATT-error-driven retry gets there: the ATT layer re-runs a request at higher security, but "higher" is still bounded by what the pairing can actually achieve. The second half fails for a different reason: this DUT does not wait to be asked. It calls `bt_conn_set_security(conn, BT_SECURITY_L4)` itself, 200 ms after connect (`CONFIG_BLE_SECURITY_REQ_DELAY_MS`), so elevation happens before any ATT request has been made to fail.

    **What it looked like from here, and why this decision exists at all:** connect `Pass`, then `"disconnected during service discovery"`, deterministically, 4 of 4 attempts — while the same discovery walked an Apple device, a `0x1910` device, and two `7dfc*` devices without trouble. A failed elevation is invisible to a bench that has no concept of elevation, so it surfaced as a discovery bug for a session. **Stated as the hypothesis it is:** the attribution of that specific failure to this specific gap is unvalidated on hardware — the boards were detached before it could be tested. What is *not* hypothetical is that L4 is unreachable as this firmware stands, and that the DUT requires it.

    **The fix.** Register `passkey_display` + `passkey_confirm`, the pair that makes `get_io_capa()` return `BT_IO_CAPA_DISPLAY_YESNO` — the capability L4 requires — with `passkey_confirm` calling `bt_conn_auth_passkey_confirm()` immediately and logging the numeric value rather than comparing it. Dispatch `Action::BleSecurity` ([embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 44) through `bt_conn_set_security()`, wait on the `security_changed` callback (or a disconnect) within the step's own `timeout_ms`, and report the **achieved** level in the `StepResult`. A link already at or above the requested level is a `Pass`: the DUT's own 200 ms self-elevation regularly wins that race, and a bench that called that an error would fail on the success case. The header comment above gets deleted, not amended — it is the load-bearing kind of wrong, and it is what a reader would otherwise trust.

    **Auto-confirm is right here and would be wrong almost anywhere else, so it is stated rather than left implied.** A bench has no human at it; unattended runs are the entire point. What that buys is protection against a passive eavesdropper on the pairing exchange, and **not** protection against an active man-in-the-middle — nobody compares the six digits, so "L4" here names the key strength and the pairing method, not a verified peer. Anyone reading a `StepResult` that says `L4` should read it that way.

    **Implemented 2026-08-26, and the hypothesis this decision flagged as unvalidated is now validated.** Its own text said: *"the attribution of that specific failure to this specific gap is unvalidated on hardware — the boards were detached before it could be tested."* It has now been tested. Against the real DUT, with the callbacks registered and an `Action::BleSecurity { level: L4 }` step in front of it, `GattDiscover` returns **7 services**; without security established it had returned nothing but `"disconnected during service discovery"`, deterministically, across every prior attempt. Three identical runs. The attribution holds.

    **Two things the runtime confirmed rather than left inferred, both worth having asked for.** The pairing method that actually ran is logged, not deduced from the callback set: dev-bench reports `LE SC Numeric Comparison (authenticated)` — which is what the `passkey_display` + `passkey_confirm` pair was chosen to produce, and the log is the only thing that would have said so had it landed on Just Works instead. And the derivation itself was **read out of this workspace's own Zephyr** (`subsys/bluetooth/host/smp.c`'s `get_io_capa`, v4.4.0) rather than recalled, which mattered: `BT_SMP_IO_DISPLAY_YESNO` requires *both* function pointers non-NULL with LE SC available, so registering only the confirm half yields `NO_INPUT_OUTPUT` and `gen_method_sc` then resolves to Just Works — silently unauthenticated, capping the link at L3. `passkey_entry` is deliberately left NULL for the mirror-image reason: it would make this `KEYBOARD_DISPLAY`, a different row of the same matrix, which against a DisplayOnly peer selects Passkey Entry — a method needing six digits only the *peer* is displaying, which an unattended bench cannot supply.

    **The callbacks never log.** All of them run on Zephyr's BT RX thread, and `ble_bridge.h`'s `ble_log_sink` contract is explicit that a log line is only ever emitted from the caller's own thread, because `main.c`'s sink takes the link TX mutex and writes the UART. Each callback records what it saw in a plain static and returns; the dispatch thread turns the record into one diagnostic line after the wait completes. Same reasoning as decisions 27/36's transcript queue, applied to a second sink.

    **Decision 11 reaffirmed, asked and confirmed rather than assumed:** bonds stay RAM-only and cleared on every `Hello`, so every study pairs from scratch. The alternative — persisting bonds so a run can reuse one — was put up explicitly, because clear-on-every-`Hello` composed with a DUT that requires pairing means a full pairing exchange per study, and was declined. A hermetic run that starts from a known state is worth one pairing exchange, and a bench that carries state between studies is the harder thing to debug. The `bt_unpair(BT_ID_DEFAULT, BT_ADDR_LE_ANY)` in `ble_bridge_reset()` stays.

35. **Dev-bench decodes one step at a time from the retained `steps` span, instead of expanding the whole study into a static array — and `DBM_MAX_STEPS_PER_STUDY` goes away with it, 2026-08-25.** Decision 21 solved a real stack problem by giving `StudyStart` a static `struct dbm_study_start` with a fixed `steps[]` array, then shrank that array from the crate's 64 to a dev-bench-local **16** to keep it affordable. Both were reasonable at the time. Together they cost about 9.2 KB of permanently-resident RAM (`16 × (DBM_MAX_PAYLOAD_LEN + 64)`), sized for a worst-case step that almost no step is — and they introduced a divergence nobody had written down: **the host accepts a 20-step study and the wire silently refuses it**, because `MAX_STEPS_PER_STUDY` is still 64 in `embarch-study-designer` and nothing reconciles the two numbers. A design pass found this by reading `serial_protocol.h`, not a test.

    The decoder keeps the raw `steps` bytes it has already received and decodes step N into a **single** `struct dbm_step` at dispatch time. RAM drops to roughly one frame plus one step. The step ceiling disappears entirely — dev-bench stops having an opinion about study length, and `MAX_STEPS_PER_STUDY` goes back to being the one authority ([embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 46).

    **Crucially, `steps_crc` is still verified before step 0 runs.** The span walker this needs already exists: decision 39's `streams_crc` work built exactly that walker over the adjacent span, at a cost of +654 bytes this doc already recorded as item 3's price arriving early. Walking a span to dispatch from it is the same motion as walking one to digest it, so the expensive part is paid for.

    **Streaming steps from Core one at a time — the user's own first instinct, and a better memory answer on paper — was put up and declined.** `StudyStart` would carry metadata only and Core would send each step as dev-bench finished the last: smallest possible RAM, smallest frames. It loses two things that were deliberately bought. `steps_crc` could no longer be checked before execution begins — it would become a running digest verified at the end, so dev-bench starts executing step 0 without knowing the study is intact, which inverts the guarantee the seal exists for. And a serial round-trip lands between every step, folding link latency into exactly the timing `Step.delay_before_ms` was added to make authorable (decision 30's neighbourhood, Milestone 6). Recorded rather than discarded: if a study ever gets long enough that even the raw frame is a problem, this is the next move, and the trigger is that specific.

36. **Dev-bench reports its own chip ID in `HelloAck`, read through Zephyr's `hwinfo` — 2026-08-25.** The firmware half of [embarch-core/design.md](../embarch-core/design.md) §3 decision 35 and [embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 47. Since decision 26's port migration, dev-bench's runtime serial link is a *physically separate USB device* from its JTAG connection — so Core could confirm "the enrolled probe is attached" and "some dev-bench answered on the link" without either implying the other. This is the one thing the bench can say about itself that ties them together.

    **`hwinfo_get_device_id()`, not a raw register read, and that was the repo owner's call over two alternatives.** Reading `EFUSE_RD_MAC_SYS0/SYS1` directly would have produced a string byte-identical to what `embarch-topology` reads over JTAG, needing no host-side relation at all — but it hardcodes an ESP32-specific register address into firmware that is meant to move back to a Nordic board (decision 4's amendment is a milestone-scope decision, not a permanent deprecation). `hwinfo` is the portable call, and the cost lands where it can be paid: `embarch-topology` declares the relation between the two encodings once, per chip. On this part it turns out to be **derivable rather than guessed** — Zephyr's `hwinfo_esp32.c` reads those same two registers, at the same two addresses, and reorders their bytes into the base MAC.

    `CONFIG_HWINFO=y` in the shared `prj.conf`; `read_hardware_id()` is guarded on it and reports an **empty string** without it, so `native_sim` (no device-ID driver) still builds and still handshakes — it simply cannot answer. A bench that cannot answer says nothing rather than sending a substitute, because a plausible-looking invented ID would defeat the whole check. Core is where "no ID" acquires its meaning, and it passes rather than refuses.

    Built for real on both targets: `esp32c5_devkitc/esp32c5/hpcore` links with `CONFIG_HWINFO_ESP32=y` and a real `z_impl_hwinfo_get_device_id`, and the `serial_protocol` ztest suite passes 33/33 on `native_sim` — including the first cross-language pin of a `HelloAck` frame. **Never run on the physical board**: none has been attached since this was written.

37. **Three things real hardware changed about decision 34, plus `BleUnbond` and a bond lifetime that no longer depends on a `Hello` arriving — 2026-08-26.** Decision 34 designed the pairing side and was right about it. This is the implementation pass, and what running it against the DUT actually cost.

    **`-EBUSY` is not a failure, and this is the one that mattered.** The first real study reported `bt_conn_set_security(L4) failed (-16)` on its security step — and the step *after* it then ran at L4. Zephyr returns `-EBUSY` when a security procedure is already in flight (`smp.c`'s `SMP_FLAG_PAIRING`/`SMP_FLAG_ENC_PENDING`), which is exactly what decision 34 itself predicted the DUT would do: it calls `bt_conn_set_security` on its own, 200 ms after connect. Decision 34 anticipated the *race* and said a link already at or above the requested level is a `Pass`; it did not anticipate arriving in the middle. Failing there reported "could not establish security" about a link that was one second from being secured — worse than useless, because it points at the wrong side. So `-EBUSY` now means *wait for the procedure already running and judge what it reaches*, and only if that settles below what the study asked for, request again on the study's own behalf. Two attempts, not a retry loop: `bt_conn_set_security` resets `conn->required_sec_level` on error, so the in-flight procedure targets whatever the peer asked for rather than the study's level, and one further request after it completes closes exactly that gap. Found by running it, not by reading it — and it is invisible from any single-peer test where dev-bench asks first.

    **`Action::BleUnbond` dispatch, and it drops the link.** [embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 50's firmware half: `bt_unpair(BT_ID_DEFAULT, BT_ADDR_LE_ANY)`, then *wait for the disconnect*. Zephyr's `bt_unpair` disconnects a peer whose keys it clears, and returning while `active_conn` is still populated is precisely the race decision 27's `ble_bridge_reset` already had to fix once — the next `BleConnect` failing with "already connected to a different peer" and passing on retry, which is the signature of a race rather than a configuration problem. Every bond is cleared rather than only the connected peer's: decision 15 holds one connection at a time, so the two are the same set, and "clear the table" is what an author means by "drop the bond".

    **A study is a bond's lifetime, said in the firmware rather than inferred from the protocol.** Decision 11 clears bonds on every `Hello`, and Core does send one before every study — so bonds were already effectively per-study, *by coincidence of the protocol* rather than by anything dev-bench does. `dispatch_study` now clears them at study end explicitly. The failure this removes is the one where a second run of the same study behaves differently from the first, and it costs one line; the reason it is placed *before* the transcript drain rather than after is that the clear disconnects the peer, and that disconnect deserves to reach Core with everything else instead of arriving behind its own `StreamClose`. If "persist for a study" ever turns out to mean *across* studies, this call is the one line that moves.

    **Auth callbacks are registered before `bt_enable`, deliberately.** Zephyr latches `bt_auth` into an SMP context the first time it needs a capability, so a peer that connected and initiated pairing before registration ran would latch NULL — `NO_INPUT_OUTPUT`, Just Works, unauthenticated — with nothing in the resulting failure pointing at registration order. This is the same class of failure as decision 34's own: a silently weaker pairing that looks like a peer problem.

    **What is still not claimed.** Nothing here has been validated against a DUT that presents `NO_INPUT_OUTPUT`. Against such a peer the spec's own matrix forces Just Works whatever dev-bench declares, L4 becomes unreachable, and the step will `Fail` reporting the level it did reach — which is the correct behaviour and is untested. The DUT this bench has requires L4 and supplies the capability for it, so the degraded path has had no opportunity to run.

38. **`CONFIG_LOG` is on, and every record it produces reaches Core as a `LogLine` and lands in a debug file — 2026-08-26.** Decision 7 established the *channel* for dev-bench's log output and was implemented with the logging subsystem itself switched off (`CONFIG_LOG=n`), so only deliberate `send_log_line()` calls ever travelled. That cost more than it looked like it did, and the cost is written down in this firmware's own source: `handle_hello`'s uptime/reset-cause diagnostic exists *because* of it. A study failed on 2026-08-26 with Core reporting a one-byte COBS frame; the two candidate explanations were "dev-bench sent a malformed message" and "dev-bench died mid-study", and nothing observable could separate them, because — in that comment's own words — "this firmware runs with `CONFIG_BOOT_BANNER=n` and `CONFIG_LOG=n`, so a reboot is completely silent from Core's side." Every `LOG_ERR` in the BT host, every driver complaint, and the entire Zephyr fatal-error dump compiled to nothing.

    **`app/src/dev_bench_log.c`: a Zephyr log backend, not a second transport.** It formats each record through `log_output` (level marker on, timestamp off — see below), splits on `\n` so a `LOG_HEXDUMP` becomes one line each, replaces any byte outside printable ASCII so Core's line-oriented debug file stays one record per line, and hands the result to a sink `main.c` installs. It knows nothing about the UART or the message union, which is what makes it linkable in a ztest against a capturing sink (`app/tests/dev_bench_log`, 6 cases) rather than only testable on hardware.

    **Deferred mode is load-bearing, not a restated default.** In immediate mode a backend runs in the caller's context — ISRs included — and this sink takes `main.c`'s `link_tx_mutex` and blocks on `uart_poll_out`: illegal from an ISR, and a ~1.3 ms stall per line everywhere else, on a bench whose whole job is measuring someone else's timing. `CONFIG_LOG_MODE_DEFERRED` moves every backend call onto the log processing thread, which is what makes a *third* link writer (alongside the dispatch loop and the transcript TX thread, decision 36) safe. The one exception is the fatal path: `log_panic()` switches to synchronous processing inside the faulting context, so the sink is told to skip the mutex and write directly — accepting that it may interleave with a frame some now-halted thread had half-written, because getting the fault out is the entire point and Core resyncs on the next delimiter anyway.

    **The boot backlog is what actually makes a reboot visible.** Core opens the serial port per study, so anything written before the first `Hello` is shifted out to nobody. So the backend holds formatted lines (8 slots, ~1 KB) until a sink is installed, which `handle_hello` does immediately after putting `HelloAck` on the wire, flushing the backlog right behind it. Overflow drops the *oldest* and reports the count as its own line — never silently, same discipline as decision 36's transcript counter. `main.c` logs one `LOG_INF` at startup naming the firmware version, so a boot always has a record even when nothing else spoke.

    Two knobs deliberately set against their defaults, for reasons that are not obvious: **`CONFIG_LOG_BACKEND_UART=n`** is the single most important line in `prj.conf`'s logging block — that backend defaults to `y` whenever a UART console exists, and this board's console *is* the protocol link, so leaving it alone would write raw text onto the COBS wire, the precise failure decision 7 exists to prevent. And **`CONFIG_LOG_PRINTK=y`** is a *protection* rather than a convenience: with it, a stray `printk` anywhere in Zephyr comes out as a framed `LogLine` instead of corrupting a frame. That turns a prerequisite this project previously had to *check* into one it now *holds* — the ESP32-C5 overlay's own comment had to record "no stray `printk` on this path — checked, not assumed" before a decode failure could be read at all.

    **`CONFIG_LOG_DEFAULT_LEVEL=2` (warn), with the app's own module pinned at `INF`.** *(Superseded 2026-08-26 by decision 39 — the level is now compiled in at `DBG` and filtered at runtime per study. The bandwidth reasoning below is why decision 39 exists and is unchanged; only the mechanism is. What follows is left as written because it is the argument decision 39 inherits.)* The BT host at info level is chatty, and every line is ~1.3 ms of a wire the study protocol is also using. Raising it (or adding `CONFIG_BT_LOG_LEVEL_INF`) is the knob for a BLE debugging session and a poor permanent default. No per-line firmware timestamp for the same budget reason: `log_output`'s costs 19 of the 128 available bytes, and Core stamps arrival on the same clock every other Core-mediated record uses. Ordering — what a log is actually read for — survives either way, since deferred processing hands records to a backend in the order they were made.

    **What paid for it, and the real finding underneath.** The logging subsystem costs ~11.2 KB of ESP32-C5 SRAM, of which **~5.1 KB is code**: Espressif's own linker script forces `log_core`/`log_output`/`log_msg`/`cbprintf_complete` into IRAM, which on this SoC is carved out of `sram0_0_seg`. That is not negotiable from the application, and this board had 5.7 KB free — the exact figure decision 37's changelog entry wrote down for "the next feature to add state to this firmware." Measured, not estimated: a `ram_report` diff between a `CONFIG_LOG=n` and a `CONFIG_LOG=y` build, plus section sizes, because the first four estimates were all wrong in different directions.

    The room came from a buffer that was sized for a message that cannot arrive. `main.c`'s `receive_message` staged inbound frames in `DBM_MAX_FRAME_LEN` (19,887 bytes) — a bound set by **`StepResult`**, which dev-bench only ever *sends*. Core sends dev-bench exactly two messages, `Hello` and `StudyStart`, whose worst case is 9,415 bytes. The new `DBM_MAX_INBOUND_FRAME_LEN` says so explicitly and frees ~10.5 KB, so the whole feature lands at **+736 bytes** net (372,688 → 373,424 of 378,384) rather than 11 KB over. Deliberately scoped to the application's own RX buffer and *not* to `dbm_decode_frame`'s staging buffer, which stays general: this project's round-trip tests decode `StepResult`s through that decoder precisely to prove encode and decode agree, and narrowing it would trade a real test for RAM. The narrower bound is safe rather than merely smaller because of the overflow branch that goes with it — an oversized inbound frame is dropped, resynced on, and now *logged*, where before it was silent.

    **Validated live, end to end, on the real bench and the real Windows service**, not only in the build: a reset ESP32-C5 dev-bench, and `C:\ProgramData\embarch\logs\dev-bench.log.<date>` containing `<inf> dev_bench: dev-bench up: fw f8d72157-dirty, wire schema v12` — a Zephyr log record held across boot, flushed at handshake, framed, received, and stored with its level marker intact — followed by the handshake diagnostic and the study's own boundary markers. Core's half is [embarch-core/design.md](../embarch-core/design.md) §3 decision 37, including the two Core-side changes this needed that only running it surfaced. **No wire schema change**: `LogLine` already existed, so an old Core and a new bench (or the reverse) stay compatible — the one ordering constraint is that Core's decision 37 must be deployed before this firmware is flashed, since only the new Core tolerates a `LogLine` arriving ahead of `HelloAck`.

39. **A study says how loud the bench should be, and the level is filtered at runtime rather than compiled in — 2026-08-26.** Decision 38 kept the link quiet with `CONFIG_LOG_DEFAULT_LEVEL=2`, i.e. by compiling out everything above warn. The bandwidth argument behind that was right and is unchanged — a 128-byte `LogLine` is ~1.3 ms of a 1 Mbaud wire the study protocol is also using, and the Zephyr BT host at `INF` is genuinely chatty. The *mechanism* was wrong: a compile-time ceiling makes the choice **once, for every study, at whatever level whoever last edited `prj.conf` picked**, so the one study that needed the BT host's own account of a failure could only get it by editing a Kconfig, rebuilding, and reflashing the bench. Decision 38 had made the bench's log available and made it available *always*, which is the same defect from the other side.

    **So the study says.** `Study.dev_bench_log_level` ([embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 51) crosses on `StudyStart`; `main.c` applies it when a study starts and reverts to `DEV_BENCH_LOG_BOOT_LEVEL` (warn) when it ends. `prj.conf` now compiles everything in at `DBG` and turns on `CONFIG_LOG_RUNTIME_FILTERING`, so raising verbosity for one run costs a submitted field rather than a reflash. An idle bench is exactly as quiet as decision 38 left it.

    **Reverted in two places, not one.** At the end of `dispatch_study`, and again in `handle_hello` — because a study that dies mid-run never reaches the first, and `Hello` is already this firmware's hard reset ([embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 12). Verbosity is study state like the bond table (decision 11's 2026-08-26 amendment), and it gets the same treatment for the same reason: the next study must not inherit it.

    **This app's own module holds at `INF` even while a study asks for less.** "The BT host should be quiet" is not the same request as "this firmware should stop saying what it is doing" — the boot record and the handshake diagnostics are what decision 38 exists for, and they would vanish the moment a study asked for `Warn`. Matched by module name (`DEV_BENCH_LOG_APP_MODULE`) because Zephyr exposes no way to ask for another translation unit's log source id. The single exception is an explicit `Off`, which is taken literally and silences everything including the fatal dump — which is precisely why `Off` is not the default.

    **`dev_bench_log_set_level` returns the level it actually reached**, because `log_filter_set` clamps a request to what the build compiled in, and a study that asked for `Debug` against a build that only contains `Info` would otherwise get a quieter log than it asked for with nothing saying so. Reported only on a mismatch. One subtlety that is a real trap rather than a detail: the answer folds in **only** sources that were asked for the requested level, excluding the app-module floor above — otherwise an honoured request for `Warn` reports back as `Info`, i.e. as a clamp that never happened, and the caller acts on it. That is asserted directly (`test_set_level_reports_the_level_it_actually_reached`).

    **Measured on both boards.** ESP32-C5: **+1,872 bytes** of SRAM (373,424 → 375,296 of 378,384, **99.18%**, leaving 3,088 free) — the cost is `CONFIG_LOG_RUNTIME_FILTERING`'s per-source filter word, not the compiled-in `DBG` strings, which are rodata and land in flash on both supported boards (`drom0_0_seg` 0.88% of 8 MB; `irom0_0_seg` 4.73%). nRF54L15DK: +168 bytes of RAM (76.10% of 256 KB) and +2.9% of flash. **3,088 bytes is thin and worth writing down** — the next feature to add state to this firmware inherits it, exactly as decision 37's changelog entry passed 5.7 KB to decision 38 and decision 38 spent it.

    **Four things real hardware changed, none of which any test caught first.** The mechanism above was green on `native_sim` and demonstrably did nothing useful on a board, four times in a row, for four unrelated reasons — worth listing individually because each is a different trap:

    *(a) The runtime filter is applied too late to protect the boot backlog.* Every source sits at the **compiled** level from log-init until something first calls `log_filter_set`, and `main()` is far too late: the backlog came back full of `<dbg> os: z_tick_sleep` from early boot, which had pushed out the boot record decision 38 exists to carry. So this backend now checks the level **itself** in `process()`, independent of Zephyr's filter. The runtime filter is the efficient half — it stops a record being created — but it cannot be the *correct* half, because it is only in force from whenever it was first set.

    *(b) A `printk` outranks everything.* `CONFIG_LOG_PRINTK` (decision 38's wire protection) routes printk through the log subsystem as `LOG_LEVEL_INTERNAL_RAW_STRING`, which **is** `LOG_LEVEL_NONE`, i.e. `0`, i.e. below every level — and Zephyr logs those unconditionally by design. Espressif's HAL announces itself over printk at boot, so those lines sailed past the idle filter and filled the backlog in turn. They are treated as `Info` here. Reading the macro also found a latent crash: for these records Zephyr stores an `is_raw` **flag** in the source field rather than a source pointer, so the app-module lookup would have dereferenced address `1`.

    *(c) Forwarding a log record generates log records.* At `Debug` the capture came back as an unbroken alternation of `<dbg> os: z_impl_k_mutex_unlock` and `<wrn> log: N record(s) dropped` — the sink takes `link_tx_mutex`, the kernel traces the unlock at DBG, that record is forwarded, which takes the mutex again. `DEV_BENCH_LOG_KERNEL_CEILING` holds the `os` module at warn whatever a study asks, which breaks the loop at the source. Nothing a study wanted is lost: kernel tracing is not the bench's account of the DUT.

    *(d) Deferred logging judges a record at forward time, not at creation time.* The log thread wakes on a 10-record threshold or a **1 second** timeout, and a short study finishes in ~50 ms — so a `Debug` study reverted to idle before its own records were looked at, and they were dropped under a level that was not in force when they were made. `dev_bench_log_set_level` now calls `log_flush()` **before** changing the level, so no record straddles a change in either direction.

    **And one that is purely a Zephyr API sharp edge:** `LOG_MODULE_REGISTER(dev_bench, LOG_LEVEL_INF)` is a *compile-time* ceiling, so every `LOG_DBG` in `main.c` was compiled out of existence and a study asking for `Debug` got the bench's own step-by-step account of nothing. Runtime filtering can only reduce below the compiled level, never raise above it. Both this module and the test's second module are registered at `DBG` now.

    **Validated on the real bench, same study submitted twice.** At `Warn`: two boundary markers and nothing else. At `Debug`: the full HCI trace — `bt_hci_core`, `bt_conn`, `bt_hci_driver_esp32`, raw HCI bytes (`01 0a 20 01 01`, LE Set Advertising Enable), the `[cut]` marker on hexdumps too long for a `LogLine`, no `os` records, and `<wrn> log: 191 log record(s) dropped` at the head of the burst. **That last line is a real limitation, not a defect**: `CONFIG_LOG_BUFFER_SIZE` is 1 KB and a `Debug` burst overruns it. It is *reported* rather than silent, which is the property that matters; raising the buffer is the knob, and it costs SRAM this board does not have to spare.

    **The wire pin is mutation-tested, which is the only reason it means anything.** Schema v13 appends one varint to `StudyStart`, and a decoder that simply *ignored* the trailing byte would still decode every frame and still pass every other assertion in the suite. So the cross-language vector generator emits `Debug` (4) rather than the `Warn` (2) default — a value the C struct would not contain by accident — and the three vector tests assert the decoded value. Verified by breaking the decoder on purpose: 3 tests fail, and pass again when it is restored. 15 ztest cases in `app/tests/dev_bench_log` (9 new, including a second translation unit registering the app's own module name so the floor is tested against a real match, and one test per hardware finding below), 39 in `app/tests/serial_protocol`.

40. **Selective monitoring, GattNotify tap routing, and 37 KB of SRAM back — 2026-08-26.** This firmware's half of [embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decisions 52/53/54/55, at wire schema **v14**.

    `monitor_subscribe_all` becomes `monitor_subscribe_matching(deadline, params)` — `params == NULL` is the unfiltered walk `ACTION_GATT_MONITOR_ALL`/`START` always did, and a target list is `ACTION_GATT_MONITOR_SELECTED`/`SELECTED_START`. **The two differ in what an unsubscribed characteristic means**, which is the only interesting part: unfiltered, skipping one is routine because nothing named it; filtered, every target is something the study said it expects, so a target that matched no discovered characteristic — or matched one that can neither notify nor indicate — **fails the step naming which**. Both are reported separately because they are different mistakes with different fixes: a typo'd UUID and a read-only characteristic.

    **A GattNotify tap routes; it does not subscribe.** `transcript_sink_cb` is the one place every captured notification already passes through, so one entry now fans out to the declared transcript tap *and* to every open `DBM_STREAM_SRC_GATT_NOTIFY` tap whose characteristic matches — the transcript getting its postcard-encoded entry, the tap getting the **raw ATT value with nothing around it**, because Core decodes those bytes against a layout describing the DUT's packet rather than a dev-bench record wrapping it. A tap arming its own subscription was rejected: a `WholeStudy` tap opens before the `BleConnect` step, so there is nothing to subscribe on yet, and it would give one characteristic two independent subscribers to reconcile.

    That costs 16 bytes per tap — `struct dbm_stream_tap` now keeps a GattNotify tap's `characteristic_uuid`, having skipped those 32 bytes outright before. **Addressing, not meaning**: `encoding` stays deliberately unkept, and which characteristic's notifications go to which tap id is exactly the same kind of fact as `source_tag`, which this node has always had to know because this node is the one that sends the record. The service UUID stays skipped — a notification identifies itself by characteristic.

    **The measurement that makes this decision worth its own entry:** deleting `gatt_activity`'s inline buffer (32 × 528 bytes here, plus the same again in `struct dbm_step_result_payload`) takes `sram0_0_seg` on the ESP32-C5 from **90.87% → 81.12%**, ~37 KB, on the board whose SRAM has overflowed twice already (§3 decisions 27, 28, 38). `DBM_MAX_RAW_LEN` shrinks with it and `StudyStart` is this firmware's largest message again for the first time since schema v4 — reversing the growth decision 32 introduced.

    Verified: `west build -b native_sim app` and `-b esp32c5_devkitc/esp32c5/hpcore app` both clean, 42/42 ztest cases pass. Three of those are new and one is deleted with the field it covered; the two pinned `StepResult` frames are each one COBS code byte shorter, and the populated-`security_level` one is where a still-writing encoder would show up as a wrong *value* rather than a wrong length.


41. **dev-bench runs a `.eap` state machine, and the manifest crosses the wire to get here — 2026-08-26.** This firmware's half of [embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decisions 58-62, at wire schema **v15**. Until this pass **nothing had ever executed a `.eap` file except that crate's own host-side reference interpreter**: the mechanism was real, tested and sealed, and end to end unrunnable.

    **The first thing this pass found is that the wire did not carry it.** Decisions 58-62 shipped `Study.protocols`, `Study.protocols_crc`, `Action::RunProtocol` and `StepResult.protocol`, and stopped one field short — `DevBenchMessage::StudyStart` had no `protocols` at all, so a `RunProtocol` step named an index into something this node had never been sent. That is [embarch-decision-reversals.md](../embarch-decision-reversals.md) row 68. The two fields are **appended after `dev_bench_log_level`**, not inserted beside `streams_crc`: postcard is positional and this protocol's rule is that a new field goes on the end. Decision 39's amendment's structural rule — each seal immediately follows the one contiguous span it covers — is satisfied by `protocols_crc` following `protocols`, which is a property of the pair rather than of where the pair sits.

    **Three files, and the split mirrors the crate's own.** `eap.h` holds the wire types (`eap.rs`), `eap_interp.c`/`.h` holds the semantics (`eap_interp.rs`), and `ble_bridge_real.c`'s `execute_run_protocol` holds the BLE half. `eap.h` is its own header rather than part of `serial_protocol.h` because three unrelated things need those types and none needs the other two — and `ble_bridge.h` has never known the link protocol, which is why `BLE_MAX_PAYLOAD_LEN` is a duplicate of `DBM_MAX_PAYLOAD_LEN` rather than an include.

    **`eap_interp.c` takes events and returns instructions, and has no radio in it.** No Zephyr, no BLE, no clock: a caller feeds it arrivals and timer expiries and reads back the writes it wants performed. That is what makes the semantics testable — `app/tests/serial_protocol` drives the **real worked BDS download**, decoded out of the pinned frame Core would send, through the same sequences `embarch-study-designer/tests/eap_worked_protocols.rs` drives the Rust reference through. Chief among them the one that is easy to get wrong because it already was once ([embarch-decision-reversals.md](../embarch-decision-reversals.md) row 66): an `on_event` arm with no `otherwise` consumes the frame and stays put *without re-entering*, while `otherwise: goto <this state>` re-enters, re-sends the flow-control ack and restarts the stall watchdog. A pump loop needs the second, and both are pinned.

    **Names are dropped, all of them but `StateDef.name`.** Every cross-reference inside a resolved `ProtocolDef` is already an index — a `goto` is a states index, an `on_event` a frames index, a `write` a sources index — so this firmware compares no strings, and the one it keeps is the one `ProtocolOutcome.final_state` reports back. Exactly what `struct dbm_stream_tap` does when it keeps 12 bytes and discards `name`/`encoding` (decision 40). The decoder still *walks* every discarded name: postcard carries no per-field length.

    **`struct eap_operand` is packed, and that one attribute is worth ~12 KB.** Its `literal` is an `int64_t` because `Operand::Literal` is an `i64`, and an operand is the most-multiplied thing in a manifest — two per condition, two per expression, one per write field, times arms, times states, times protocols, times the two `struct dev_bench_message` statics main.c holds. Naturally aligned it is 16 bytes, **six of them padding**; packed it is 10. Two protocols at the crate's own count ceilings go from ~25 KB of SRAM to ~13 KB on that alone. The cost is byte-wise loads of `literal` on a target without misaligned access, on a path that runs once per notification.

    **One count cap below the crate's, and one cap that is not a count.** Every `.eap` ceiling here is the crate's own value except `DBM_MAX_EVENT_ARMS_PER_STATE`, which is **2** against the crate's 4: an arm is the heaviest thing a state holds and is multiplied by states, by protocols, and by those two statics, so the crate's 4 costs ~9 KB more than 2 does, and **both worked protocols use one arm per state.** Refused by name at decode, never truncated — the `DBM_MAX_STEPS_PER_STUDY` posture, and sharper here: a state machine missing a transition still runs, and branches wrongly while looking correct.

    The cap that is not a count is `DBM_MAX_PROTOCOLS_WIRE_LEN`, **3 KB over the whole `protocols` span**. It exists because the eleven count ceilings multiply into a wire bound nothing would ever send: at those ceilings one `ProtocolDef` can *encode* to ~7.4 KB, almost all of it names this firmware discards, and sizing the staging buffers for two of those costs ~30 KB — against a real worked protocol whose entire `StudyStart` is **398 bytes**. A byte cap says the true thing ("this bench accepts a manifest up to this big") where a product of eleven ceilings says a false one. It is checked on the *walked* span, after the walk, because postcard gives no way to know a sequence's byte length without crossing it.

    **A third instance of reversals row 60's finding, in the other direction.** `main.c`'s TX staging buffer was sized `DBM_MAX_FRAME_LEN` — the *general* bound, which is `StudyStart`'s — for a message dev-bench cannot produce: Core is the only sender of a `StudyStart`. That was ~6.6 KB before this schema version and would have been ~9.7 KB after it, since `DBM_MAX_STUDY_START_LEN` now carries the protocols span too. `DBM_MAX_OUTBOUND_FRAME_LEN` is `StepResult`'s bound and the buffer shrinks from 9,270 to 3,082 bytes. Scoped to the *application's* buffer for the same reason `DBM_MAX_INBOUND_RAW_LEN` is: `dbm_encode_frame`'s own staging buffer stays general, because the round-trip tests encode a `StudyStart` through it and narrowing it would trade a real test for RAM.

    **The measured cost, which §7 of the crate's doc recorded as unmeasured.** From-scratch ESP32-C5 build, `sram0_0_seg` **81.12% → 87.04%** (306,960 → 329,360 B, **+22,400**). Where it went, by symbol: the two `struct dev_bench_message` statics 9,984 → 18,752 each (+17,536 together — the storage), `raw.0`/`raw.1`/`rx_buf` 9,232/9,232/9,414 → 12,312/12,312/12,507 (+9,253 — the wire bound), against −6,188 from the TX buffer above, plus ~1.4 KB for the notification queue and per-source subscribe params. The estimate the design pass sized against was **17,496 B for a `ProtocolDef`**; the real C structure is **4,376**, and the wire bound rather than the storage turned out to be the dominant term.

    That is 49 KB free, on a board that has overflowed three times. Not comfortable, and the levers are written down rather than left to be rediscovered: `tx_scratch` still carries a whole `struct dbm_study_start` it can never hold, which a TX-only message type would reclaim (~15.7 KB), and `DBM_MAX_PROTOCOLS_WIRE_LEN` is a knob with three buffers on it.

    **What a `RunProtocol` step does on the bench.** Wildcard discovery, then each declared source resolved against the DUT's real GATT table — a source the DUT does not have **fails the step naming it**, decision 53's rule for a named target rather than the subscribe-to-everything walk's log-and-skip. Every source at least one frame reads from gets subscribed; a source only ever written to (a control point) deliberately does not, because subscribing to it would be this bridge deciding something the manifest did not say. Then the loop: perform the write the interpreter asks for, wait on a 4-slot notification queue for whichever comes first of a frame, the state's own deadline or the step's, and feed it back. Notifications and writes both reach the GATT transcript, so a protocol run is as visible in a capture as any other step. **A dropped notification is counted and reported**, because a run that missed a frame reached the wrong state and a result that did not say so would be the silently-incomplete capture this suite keeps arriving at from other directions. Subscriptions are torn down unconditionally at the end: a protocol run is scoped to one step by construction, unlike a monitor *window*.

    **An acknowledged write is waited for and still never triggers a transition.** `with_response` selects the ATT operation and nothing else (§3 decision 60): on the DUT this was designed against, a control-point write's response confirms only that the write was accepted, and the authoritative answer arrives later on a different characteristic. Waiting keeps two writes from being in flight at once; arrivals during the wait queue up rather than being lost.

    **`ble_bridge_stub.c` reports no protocol at all**, the third time it refuses to manufacture a claim (after `captured_data` and `security_level`): a `RunProtocol` step on `native_sim` runs no machine, so there is no state it stopped in, and `has_protocol` staying false reads as "no protocol ran" — which is the truth. The semantics are covered where they can be covered honestly, by driving `eap_interp.c` directly.

    Verified: `west build -b native_sim app` and `-b esp32c5_devkitc/esp32c5/hpcore app` both clean, **57/57** ztest cases (up from 42). Fifteen are new: the pinned `StudyStart`-carrying-a-real-manifest decode asserted field by field, a corrupt-protocol-span check proving the third seal fails alone, a pinned populated `StepResult.protocol` frame, eight interpreter-semantics cases mirroring the crate's own, and four capacity cases including a control that the same shape at exactly the caps still decodes. **Never run against a real DUT** — see §4.

    **Deployed and live-validated the same day, for what can be validated without a manifest.** Core redeployed to the Windows service and this firmware reflashed in one sitting, which the moved wire required: `GET /dev-bench/hello` reports `schema_version: 15, compatible: true, firmware_version: '79857be2'` with `link_identity: match`. A two-step `BleAdvertise` study then ran end to end and completed `Pass`/`Pass` — the first time `StepResult.protocol` has crossed a real link, hand-encoded here as the appended `0x00` and landing in `events.json` as `"protocol": null` on a step that ran no protocol. That is the *whole* v15 wire exercised except the one path that needs a manifest nobody has authored.

    **The live pair was already broken before this pass, and nothing had said so.** Core was serving wire v13 against a bench flashed to v14 — the handshake refused, correctly and loudly, but only to whoever called `/dev-bench/hello` by hand. `embarch doctor`'s check 11, the one whose entire job is "`study_designer_schema_version` agrees", is a hardcoded `Warn` stub whose stated reason ("`embarch-study-designer` isn't wired into `embarch-core`/`embarch-api` as a dependency yet") stopped being true long ago — see [embarch-umbrella/design.md](../embarch-umbrella/design.md) §7 and [embarch-decision-reversals.md](../embarch-decision-reversals.md) row 71.


## 4. Open questions / future work

- **A `StepResult` carrying a failure reason arrives short of its own declared length because *dev-bench resets in the middle of transmitting it*. Found 2026-08-27, root-caused the same day, not fixed.**

  A study step failed and `embarch-core` refused the frame — *"failed to decode DevBenchMessage ... The original data was not well encoded"* — then dropped the connection and failed the whole study on a **dev-bench connection error**, never saying a step had failed at all. So the one message whose job is to explain a failure was the one message that could not get through.

  **The cause is a bench reboot, and the truncation is its shadow.** The proof is an uptime comparison, not a byte pattern: the link handshaked at `uptime 899843 ms`, the short frame arrived at `17:25:39.647`, and the *next* handshake reported `uptime 46320 ms` — placing the reset at `17:25:39.8`, within 150 ms of the frame. dev-bench dies partway through putting the frame on the wire, so the frame stops where the transmitter stopped. Everything that had looked like a transport fault follows from that:

  | observation | what a mid-send reset explains |
  |---|---|
  | the tail is missing and the prefix is byte-perfect | transmission got that far and no further |
  | the last byte can be *corrupt* — `0x38` arrived as `0xf8` on one run | the line went idle mid-byte, so the remaining bits sampled as the idle `1` |
  | nothing follows: no `StudyDone`, no `StreamClose`, silence to the deadline | the bench is rebooting, not continuing |
  | only long frames lose their tail | short ones finish transmitting before the window the crash falls in |
  | it is **intermittent** — the identical 88-byte frame decoded fine on study `f13f6a82`, whose bench did not reset | a crash, not a boundary |

  **"The number that identifies it is 16" was wrong, and the number was the whole basis of the previous diagnosis.** Six captured occurrences, with the shortfall counted against the COBS block the code byte describes (the code byte included, the `0x00` delimiter excluded — see below):

  | study | code byte says | block arrived | short by |
  |---|---|---|---|
  | `b38562b2` | `0x51` = 81 | 66 | 15 |
  | `d653f3e9` | `0x51` = 81 | 64 | 17 |
  | `b2f1c81e` | `0x58` = 88 | 71 | 17 |
  | `61e3b5a0` | `0x51` = 81 | 68 | 13 |
  | `978ca133` | `0x58` = 88 | 71 | 17 |
  | `beadc399` | `0x51` = 81 | 68 | 13 |
  | `f13f6a82` | `0x58` = 88 | **88 — complete** | — |

  Not one of them is 16. The original table's two rows both read 16 because Core's own message subtracted a delimiter-inclusive length from a delimiter-exclusive claim — **an off-by-one in the diagnostic became the identifying fact of the bug**, and a fixed number is what made "find the 16-byte boundary in the TX path" look like the next step. There is no boundary; there is a crash with variable timing. Core's arithmetic is corrected ([embarch-core/design.md](../embarch-core/design.md) §3 decision 40).

  **What is still not known is why it resets**, and the honest state of the evidence is thin:

  - **`reset cause` is useless on this board.** Every handshake today reported `0x00000000`, including the one 46 seconds after a confirmed reboot. `send_reset_diagnostics` clears the cause each handshake precisely so the next one is meaningful, so this is the ESP32-C5 `hwinfo` driver declining to classify rather than a stale flag. The **uptime** is the load-bearing half, exactly as that function's own comment says.
  - **No crash dump arrived** — which is itself a finding about §4's own "the fatal-error path decision 38 opens is designed and untested" bullet. This is the case that would exercise it. Either the reset is not a Zephyr panic (a hardware reset — brownout under simultaneous radio TX and UART TX is the hypothesis worth testing first, and it fits a mid-byte abort), or `log_panic()`'s synchronous path does not deliver. **Distinguishing those two is the next step, and it is cheap**: the forced `k_panic()` behind a debug-only build that bullet already proposes.
  - Length-dependence is real but is a *consequence*: a `Pass` `StepResult` is ~25-30 bytes and has always decoded, because it finishes before the crash window.

  **Three things that were ruled out by experiment, so nobody re-runs them.** The outpost trace stream is not involved — study `978ca133` removed that tap and changed nothing else, and failed identically. ACL-buffer exhaustion is not the trigger — `978ca133` logged **no** `No available ACL buffers!` at all and still died. And it is not Core's read path: with Core keeping the link (below), it polled a live port for 13 seconds and received nothing.

  **The previous diagnosis was "a truncation in transit, not a malformed encoding", and that half stands** — the field layout is self-consistent right to where it stops, and `serial_protocol.c`'s `DBM_TAG_STEP_RESULT` case does write all four trailing `Option` bytes on the `Fail` path. Reading it as "the encoder forgot the trailing options" was wrong then and is still wrong. What was wrong was the inference *from* "in transit" to "the wire or the staging buffer lost bytes": the sender stopped existing, which is a third possibility neither reading covered. **Two wrong diagnoses in a row on the same fault, both well-evidenced** — see [embarch-decision-reversals.md](../embarch-decision-reversals.md) rows 91 and 92.

  **Core's half is fixed and deployed, and it is what produced the root cause.** An undecodable frame now costs *the frame*, not the link ([embarch-core/design.md](../embarch-core/design.md) §3 decision 40) — the posture every other part of this suite takes, and exactly why an outpost frame carries its own CRC ([embarch-outpost/design.md](../embarch-outpost/design.md) §3 decision 5). That change is what let a run keep reading past the bad frame and observe the *silence* after it, which is the observation the whole diagnosis rests on. **The bench-side fix is still open**: whatever resets dev-bench on this path.

  **How it used to present, because it was misleading twice over.** The study reported a *transport* error at the step *before* the one named in the frame, and nothing in the message said a step failed. It also looked exactly like a schema mismatch, which it is not — `GET /dev-bench/hello` reported `schema_version: 15, compatible: true` throughout. Check that before going down that road.

  **It predates the work that found it**: the same frame, same step, at 06:39 UTC the same day, on the previous Core build and the previous DUT firmware.

- **~~A `.eap` protocol has never run against a real DUT (decision 41).~~ Closed 2026-08-27 — and it found four things, which is what every previous first-real-run in this doc did (decisions 30, 31, 33, 34, 37).** Everything below the radio had been covered and none of it exercised `execute_run_protocol`'s BLE half; running it did. What the radio half turned out to hold:

  **All four are fixed as of 2026-08-27** (`embarch-dev-bench` `9a8f0df`), except the schema half of 4 — see each item. What they were:

  **1. `protocol_notify_q` is four slots deep, and that is a data-loss path, not a throughput limit.** A DUT that bursts several notifications per control write — the reference-dut pushes `CONFIG_BDS_CHUNKS_PER_REQUEST` (4) — overruns it, and the interpreter dropped **275** notifications in one 5-minute step. The queue's own warning is honest about the machine (`its final state is NOT trustworthy`) and silent about the *capture*: a `StreamSource::GattNotify` tap on a protocol source is fed from `transcript_emit` **inside the dequeue loop**, so a dropped notification never reaches the tap either, and nothing sets that tap's `truncated` flag. The study reported 28,548 bytes and `truncated: false` for a capture missing 275 records ([embarch-decision-reversals.md](../embarch-decision-reversals.md) row 73).

  **Fixed 2026-08-27.** The asymmetry was the whole bug: the transcript's own drops set the flag and the protocol queue's could not, because they had no way out of `ble_bridge_real.c` and no per-tap counter to land in. Both halves now exist. `ble_bridge.h` gained a **drop sink** alongside the transcript sink and under the same BT-RX-thread contract — one call per notification the interpreter's queue drops, naming the characteristic it would have carried. It is deliberately *not* a transcript entry with a new kind: a `GattNotify` tap's file is the characteristic's raw bytes, and a marker record in it would corrupt the capture this is trying to describe. `main.c` gained `tap_dropped[]`, per tap, and `StreamClose.dropped` now carries each tap's own loss instead of the transcript's for one tap and a hardcoded 0 for every other. All three loss paths land there: `transcript_q` full (charged to every open tap that wanted the entry, since one entry legitimately feeds several), an unencodable record in the TX thread (charged to the tap it was being built for), and the bridge's queue (charged only to `GattNotify` taps on that characteristic — the transcript never had that entry to lose, and counting it there would overstate a number an engineer reads as "rows missing from this file").

  **Verified against real hardware by A/B, not by a successful capture.** The reproduction study kept dying to finding 3 below before its protocol could run, so the proof came from running one identical study against the *old* and *new* bench firmware in the same sitting: both lost three transcript entries to a full queue, and the `nus-shell` tap reported `truncated: false` on `79857be2` and `truncated: true` on `9a8f0df2`. Same bytes, same drops, one honest answer and one silent one — which is a sharper demonstration than a clean capture would have been.

  The workaround an author has today, and it is a real one rather than a consolation: put the **bulk** characteristic on a `GattMonitorSelectedStart` window and leave the protocol only the low-rate control/status pair. `monitor_notify_cb` emits straight from the BT RX thread with no four-slot queue in the way, the two subscriptions do not collide as long as they name *different* characteristics, and the same 5-minute study went from 28,548 bytes with 275 silent losses to **714,927 bytes with none**. That the workaround exists is why this is written here rather than fixed in a hurry — but the tap's silent truncation is a correctness bug and wants either a deeper queue, a drop counter routed into the tap's `truncated`, or both.

  **A monitor window and a protocol source must not name the same characteristic.** Zephyr's `bt_gatt_subscribe` skips the CCC write when another subscription already covers the handle (`has_subscription`), returning 0 without ever calling the subscribe callback — so `protocol_subscribe_sources`' `k_sem_take(&ccc_sem, ...)` blocks to the step deadline and the run times out having done nothing. Found by reading `gatt.c` before authoring, not by hitting it.

  **2. `GattMonitorStop`'s fire-and-forget teardown outlives its own step.** The CCC-clear writes are deliberately not waited on (there is no budget left by then), so the *next* step starts while the DUT is still notifying. A `RunProtocol` step following a monitor window ran its discovery into that backlog and lost the link twice, at a different discovery phase each time. A `delay_before_ms` on the following step is the authorable fix and it worked; that the fix has to be authored per-study is the part worth revisiting.

  **3. The radio's buffers are the binding constraint, and a chatty DUT is enough to exhaust them.** With the DUT's shell log streaming over NUS at ~10 records/second, the bench answered with 24 consecutive `No available ACL buffers!` and dropped 92 transcript entries before the link died. Nothing dev-bench does causes this and nothing it does survives it either.

  **This got sharper on 2026-08-27, and it is now the thing blocking a `RunProtocol` reproduction on this bench.** Six consecutive studies died at the same place — the step immediately after a `GattMonitorStop` — and the HCI reason (finding 4's fix) named it: `0x08`, supervision timeout. The ACL exhaustion is not caused by the shell log this time; `log halt` was issued first, and the bench's log shows the `No available ACL buffers!` run **beginning before pairing completes**, i.e. the DUT is saturating the link from the moment it connects. Three things were ruled out by experiment rather than reasoning: the DUT's own accumulated state (a `reset` between runs changed nothing), a wedged BDS transfer (an explicit `BDS_CMD_ABORT` first step changed nothing), and the settle interval (3 s died inside discovery; 5 s and 12 s died before the next step even started, and a `GattMonitorSelectedStart` opened in the gap as a keepalive died the same way). It is **not** a regression from the drop-sink work: the identical study on the previous firmware fails identically.

  What that leaves is a DUT-side or radio-side cause this bench can observe and not fix. It matters beyond one study, because a five-minute `RunProtocol` drain **did** complete on 2026-08-26 against the same two boards — so whatever this is, it is either intermittent or something about the bench's state changed between those days. Unresolved.

  **And later the same day it stopped being reportable at all, which is why it has been so hard to pin down.** Three more studies died here, and every one of them surfaced as a *transport* error — `failed to decode DevBenchMessage ... The original data was not well encoded` — with no mention that a step had failed, let alone why. The `StepResult` carrying the diagnosis arrives short of its own declared length, because dev-bench resets partway through sending it, and Core discarded it and dropped the link (see the bullet below for the root cause, found 2026-08-27 afternoon). The two findings compose in the worst direction: **finding 4's fix is what made the reason long enough to trigger it.** Keeping the HCI byte turned `disconnected during service discovery` into `disconnected during … (HCI 0x08, supervision timeout)`, which pushed the frame from ~30 bytes to 81-88 — and only frames that long fail to finish transmitting before the crash. So the improvement that made this diagnosable is the same change that stopped the diagnosis being delivered, and the failure presented as if the link, not the DUT, were at fault.

  **Refined 2026-08-27 afternoon, and it is now a statement about the DUT rather than about the bench: the reference-dut cannot service a GATT operation within the supervision timeout while PPG is running.** Two runs of the same eleven steps, reordered, separate the two:

  | order | what ran before the failing step | failing step | reason |
  |---|---|---|---|
  | as authored | nothing had started PPG | `nus-sensor01-start` (the NUS write that starts it) | `disconnected during write (HCI 0x08, supervision timeout)` |
  | batchmgr pair moved *after* the NUS window | `sensor01 start` had run and returned `All SENSOR01 measurements started successfully` | `batchmgr-stop` | `disconnected during service discovery (HCI 0x08, supervision tim` |

  The BDS service discovery that dies in the second run is the *same* discovery that passed as step 2 in the first — the difference is only that PPG is now flowing. So the link dies at whatever GATT operation follows PPG starting, and moving the steps around only moves which one that is. That also explains why the settle intervals, the `reset` between runs and the explicit `BDS_CMD_ABORT` all changed nothing: none of them stops PPG. **This is a DUT-side fault, observable from this bench and not fixable in it**, and it is what blocks a traced PPG capture — not the tracer, and not the frame truncation. Still `Unresolved`.

  **4. `disconnected_cb` throws away the disconnect reason** — see the next bullet.

- **~~`disconnected_cb` opens with `ARG_UNUSED(reason)`~~ — fixed 2026-08-27, except the wire half (found and fixed the same day).** The HCI reason distinguishes a supervision timeout from a MIC failure from the peer hanging up from unacceptable connection parameters — four different findings that need four different fixes, and all four currently print the same sentence. Two consecutive real runs died this way and the reason had to be reconstructed from whatever else happened to be in the log at the time. The byte is now kept and every one of the twelve `disconnected during X` sites goes through a single `outcome_disconnected()` helper — a helper rather than twelve edited format strings, so the thirteenth call site cannot quietly be a bare literal again. An unnamed reason still prints its hex value; the name is a convenience on top and never the only thing carried, which is also why the hex comes *before* the name in a 64-byte `fail_reason` that truncates. The reason table's values were read out of this workspace's own `hci_types.h` rather than from memory.

  It earned itself immediately: the first run on the new firmware failed `disconnected during service discovery (HCI 0x08, supervision tim…)`, where the same failure on the previous firmware had said only `disconnected during service discovery`. `0x08` is `BT_HCI_ERR_CONN_TIMEOUT`, and knowing that is what turned finding 3 below from a guess into a diagnosis.

  **Still open, deliberately: the byte does not reach `StepResult`.** That is a wire field and a schema bump, and this pass was not moving the wire. Until it does, the reason is legible in the failure text and not machine-readable. [embarch-decision-reversals.md](../embarch-decision-reversals.md) row 78.

- **`tx_scratch` holds a `struct dbm_study_start` it can never contain, and that is now ~15.7 KB (decision 41).** `struct dev_bench_message`'s union is sized by its largest member, dev-bench never *sends* a `StudyStart`, and main.c holds two of those statics. The TX *staging buffer* was right-sized this pass; the message struct behind it was not, because splitting a TX-only message type out means either two encoders or a conversion, and doing it inside a pass that already moved the wire would have put a real refactor behind a schema change. It is the single largest remaining lever on this board's SRAM and it is a self-contained change with its own tests. Trigger: the next thing that needs more than the 49 KB now free.

None acquired a new argument this pass. They are settled-deferred, not unexamined — which is worth writing down, because a long open-questions list otherwise reads as a backlog rather than as a set of decisions to wait.

- 2026-08-04 — `ble_bridge_real.c` went from one wired-up action to the full `Action`/`GattOperation` surface (§3 decision 16's implementation note). `BleConnect` covers both roles: central scans (filtering on `target_address` when set, ignoring non-connectable advertisers) and initiates from the scan callback; peripheral advertises and, when a specific `target_address` was asked for, drops a wrong peer and keeps advertising for whatever of the step's budget remains rather than reporting a Pass against the wrong DUT. `DataExchange` acts as a GATT client: primary-service then characteristic discovery (cached per connection, invalidated on disconnect), then read / write-with-response / notify / indicate / subscribe / stream-capture. Every action is bounded by one deadline derived from `Step.timeout_ms` — discovery included, not just the final request — with `Notify`/`Indicate` additionally bounded by the `GattOperation`'s own timeout, whichever expires first. A timeout cancels the pending GATT request (`bt_gatt_cancel`) instead of leaving Zephyr owning the params struct, which would fail the next step with `-EBUSY`. `BleAdvertise` was rewritten in the same pass, partly as a bug fix: it used `BT_LE_ADV_CONN_NAME`, which no longer exists in Zephyr 4.x, so the `nordic` workspace could not have compiled; it now builds real advertising data from the Action's own `local_name` and `adv_interval_ms` (previously ignored in favor of `CONFIG_BT_DEVICE_NAME`) and puts service UUIDs in the scan response, failing explicitly if more are requested than a legacy scan response can carry (exactly one 128-bit UUID) rather than silently advertising a subset a DUT would then never find.
