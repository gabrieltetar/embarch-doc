# embarch-dev-bench decisions: Monitoring windows and their subscriptions

**Status:** active, 2026-11-10.

The capture window that spans steps, what a monitor subscription that failed means, and what the steps inside an open window may do to it. Split verbatim out of [dispatch.md](dispatch.md) on 2026-11-10, when 55 would not fit there.

Index: [../decisions.md](../decisions.md). Current truth: [../spec.md](../spec.md).

### 28 — A capture window that spans steps, and a transcript that leaves BLE context safely
`GattMonitorAll`'s body split into subscribe and teardown halves, so it keeps its exact previous behaviour while `GattMonitorStart` runs only the first and leaves subscriptions armed and `GattMonitorStop` runs only the second. A window cannot outlive the connection whose subscriptions it holds: a disconnect drops them, and the `Stop` that closes it then calls no GATT function and reports `Disconnected` (decision 54; this used to say the flag clears on disconnect, which the code never did). `Hello` clears it as a hard reset. Dispatch closes a window a study left open before finishing. **Inside an open window**, a one-shot `GattMonitorAll` or `GattMonitorSelected` is refused by name and a `GattMonitorStart` closes the window before opening its own; every other step runs and leaves the window intact (decision 55).

**Emitting the transcript from BLE callback context** is what shaped the rest: entries are built as a **stack local, not a shared static**, because the sink is called from both Zephyr's BT RX thread and the dispatch thread and a shared staging buffer would tear under a notification arriving mid-emit. That ~290-byte frame is why the BT RX stack is raised on both boards — left alone it would have failed as an intermittent stack overflow under exactly the notification bursts this feature exists to capture. The sink does one bounded non-blocking copy into a queue drained by a dedicated TX thread, because blocking the BT RX thread on a full queue would stall the very notifications being recorded; **a dropped entry is counted and reported rather than leaving a transcript silently claiming to be exhaustive.** That made a **second writer to the link**, which the single-threaded assumption had not allowed for, so every sender now holds a mutex across *build-and-send*.

**The second SRAM overflow:** the TX thread's first version kept its own message struct, and the build overflowed by 2,720 bytes at link time — that union is sized by its largest member regardless of which tag a send uses. Fixed by having the TX thread build into the same shared buffer, **rather than by shrinking a limit**. The transcript payload bound is one ATT MTU rather than the general payload maximum: the Rust type accepts more, this firmware never produces more than one MTU's worth, and each queue slot costs real RAM. **Sending fewer bytes than the receiving type can hold is always wire-legal; the reverse is not.** Zephyr's default MTU would have capped a notification at 62 bytes, fragmenting a shell response into rows that each look like a separate event.

**The encoding is hand-written C and pinned against Rust.** Nothing in this firmware's own tests would catch it drifting from what postcard expects — a reordered field or a `u8` written as a varint decodes into plausible-looking garbage, not an error — so the exact frame is asserted here and the identical pre-COBS body from the Rust side. Both must break together.

### 54 — A monitor subscription that did not land is never counted, and a disconnect never passes
The subscribe walk the four monitor actions share now reads its own answer, as the single-subscription and protocol paths did. Each characteristic gets one verdict: subscribed, a CCC write the DUT refused (its ATT error in the row's status byte), no CCC descriptor, dropped by the host before it landed, a write that could not start or timed out, or the subscription limit. Only the first is a `SUBSCRIBED` row and counted; each other is an `ERROR` row naming which. **A missing CCC costs one characteristic, not the step**: Zephyr reports it only through notify with NULL, which used to wake nothing, so the walk sat out its budget.

**What fails the step:** a selective target whose subscription did not land, named with its verdict; **and an unfiltered walk that subscribed to nothing**, whether nothing could notify or every attempt failed. Each characteristic is unnamed and may be skipped, but the whole set is what the step asked for, and a capture that passes empty is what this family exists to refuse. A disconnect anywhere in the walk is `Disconnected`; the capture wait no longer resets one away.

**No GATT call without a live link.** Each call uses one checked snapshot of the connection, and teardown after a drop calls nothing: monitor and protocol subscriptions are `VOLATILE`, so the host removes them on the disconnect even for a bonded peer. A CCC answer wakes only the wait for its own params, so a fire-and-forget unsubscribe answering late cannot pass another characteristic. A `RunProtocol` source with no CCC now fails by name instead of timing out. **Built, not observed**: every path here runs only against a real BLE peer.

### 55 — Steps inside an open window leave it intact, and each notification is one row
A window spans steps, and four things those steps did to it are fixed here, each traced through Zephyr's `gatt.c` rather than observed.

**A one-shot monitor inside an open window is refused by name.** It reused the window's subscription slots, and zeroing slots still linked in the host's intrusive list cut that list: most of the window's characteristics kept a CCC enabled on the DUT with no subscriber left, and its `Stop` passed. *Rejected: closing and reopening the window*, which leaves an unreported gap in a capture whose point is to span the steps inside it.

**A window's rows carry the UUIDs copied at subscribe time** (32 B a slot, 1 KB of RAM on each board), not an index into the discovery table that every later `GattDiscover`, monitor or `RunProtocol` step zeroes and refills. A row arriving during or after such a walk named the wrong characteristic or none, and a `GattNotify` tap matching on the label missed it uncounted.

**A subscription another already covers does not wait.** When a live subscription on the same handle covers the new one, Zephyr writes no CCC and calls nothing back, so a `DataExchange` subscribe, or a `RunProtocol` source inside an unfiltered window (every source it reads), sat out its step as `TimedOut`. The bridge mirrors the host's rule over the subscriptions it armed and counts a covered one as subscribed. **While a monitor subscription holds a handle, it alone writes that handle's rows**: Zephyr hands each notification to every subscriber, so unblocking the wait would otherwise record each frame twice and send it to a tap twice.

**No params struct is zeroed while Zephyr can still call through it.** `Hello`'s reset forgets the single subscription's handle instead of zeroing the struct its CCC-clear write still holds. A walk zeroes a slot only when nothing can reach it, which holds because a teardown's CCC-clear writes precede the walk's discovery on the one ATT bearer.
