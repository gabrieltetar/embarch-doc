# embarch-dev-bench decisions: Capture taps

**Status:** active, 2026-09-02.

The generic byte-forwarding pipeline, notify-tap routing, and the tap that was never closed.

Index: [../decisions.md](../decisions.md). Current truth: [../spec.md](../spec.md).

### 29 — The generic inbound pipeline: the bench forwards bytes and interprets nothing
This is strictly *less* firmware: the `f32` grouping loop, the trailing-partial handling, the interval derivation and the unit defaults all go away, replaced by "stamp arrival, copy bytes". The transcript collapses into the same generic record type, and the bench's own log gains a reserved tap.

**A paragraph in this doc described work that was already done, in the one place a reader would go to find out what was left.** It named four deletions still pending and **none of them was in the tree** — a previous phase had already removed them. Recorded rather than quietly corrected, because "this firmware still interprets payloads" was the load-bearing half of the pass's own net-negative-size expectation, and it was false. So the pass was **purely additive** and the size claim it inherited could not be met.

`struct dbm_stream_tap` stores 12 bytes per tap rather than mirroring the wire type's ~80: it keeps the id, the source tag and the scope, and **drops `name` and `encoding` outright** — an encoding is what a payload *means*, and a firmware holding one would be holding the exact knowledge this decision took away from it. The decoder still *walks* the fields it discards, because postcard has no per-field length and the scope is unreachable without parsing past them.

**Two real behaviour changes, both consequences of capture being declared rather than implicit.** A study that declares no transcript tap now gets **no transcript at all**, where the old dedicated tag sent every entry unconditionally whether anything upstream wanted it. And a signal tap is skipped here entirely — Core opens that one on its own carrier, and the bench announcing it too would put two producers on one id. **The retired tag's value is left burned rather than reused:** the earlier stream tags were reused on the argument that no firmware carrying the old shapes had ever been flashed, and that argument is spent the moment one has.

**The reserved log tap is not firmware.** The upstream sketch had the bench opening a second channel for its own log; what shipped is Core synthesising the tap and rendering the log frames it already receives. Strictly less firmware, less link traffic and less SRAM on a board then at 98.5% of its SRAM, to move bytes that were crossing the link anyway — and it closes the same asymmetry, which is the only thing the tap was for.

**Adding `streams_crc` made the pass net-positive firmware, against the expectation that it would shrink**, because it required teaching C to walk a `StreamTap` at all — the expectation assumed this decoder already walked that span, and it never did, since the field was appended *after* `steps_crc` precisely so it would not have to. Not wasted: tap decoding needs the walker anyway, so it is that cost arriving early. **A leftover found walking the encoder against the Rust type rather than by a test:** the result message was still writing two `Option` bytes for two fields retired from the Rust type a version earlier — on the message it sends most. Both suites stayed green because each agreed with itself, since that message predated the both-languages pinning rule, which applied to *new* records.

*(b) A pass-through role for a DUT signal — designed, not built.* The bench would receive on a declared pin and relay bytes to Core as an ordinary tap. **It has neither the spare pins nor the firmware today**, which is why the outpost's bypass route is a first-class route rather than a workaround. When built, the bench **passes bytes through and interprets nothing** — the same rule as (a), which is what makes it the same mechanism rather than a new one. Not decode-and-summarise: outpost record semantics depend on a specific DUT build's manifest, so a summarising bench would need reflashing whenever that changed.

### 40 — Selective monitoring, notify-tap routing, and 37 KB of SRAM back
The subscribe walk becomes parameterised: no target list is the unfiltered walk it always did, and a target list is the selective action. **The two differ in what an unsubscribed characteristic means**, which is the only interesting part: unfiltered, skipping one is routine because nothing named it; filtered, every target is something the study said it expects, so a target that matched no discovered characteristic — **or matched one that can neither notify nor indicate** — fails the step naming which. Reported separately because they are different mistakes with different fixes: a typo'd UUID and a read-only characteristic.

**A notify tap routes; it does not subscribe.** The transcript sink is the one place every captured notification already passes through, so one entry now fans out to the transcript tap *and* to every open notify tap whose characteristic matches — the tap getting the **raw ATT value with nothing around it**, because Core decodes those bytes against a layout describing the DUT's packet rather than a bench record wrapping it. *Rejected: a tap arming its own subscription* — a whole-study tap opens before the connect step, so there is nothing to subscribe on yet, and it would give one characteristic two independent subscribers to reconcile. The 16 bytes per tap this costs is **addressing, not meaning**: which characteristic's notifications go to which tap id is the same kind of fact as the source tag, which this node has always had to know because this node sends the record.

**The measurement that makes this its own entry:** deleting the inline activity buffer takes the ESP32-C5 from **90.87% → 81.12%** of SRAM, ~37 KB, on the board whose SRAM had overflowed twice already — and `StudyStart` becomes this firmware's largest message again for the first time since schema v4, reversing the growth decision 27 introduced.

### 42 — A whole-study tap is closed by `close_all_taps()`, not by a step index past the last one
Dispatch ended every run by syncing taps to one past the last step, on the premise its own comment stated: *"no scope covers it, so this closes whatever is still open."* True of a step-window scope and **false of a whole-study one** — the covers predicate answers true at every index, deliberately, because a predicate over a declared scope has no business knowing where a study ends. The suite even pinned both halves of the contradiction in one test, nine lines apart.

So a whole-study tap was **never closed, never sent a close message, and never delivered the dropped count** Core turns into the truncated flag. Its `truncated: false` was not a measurement — **it was the absence of one, and it is indistinguishable on disk from a clean capture.**

**Measured, not predicted.** The same drain study run twice minutes apart, differing only in its transcript tap's scope: a step-window scope dropped 16 entries and reported `truncated: true`; a whole-study scope dropped **31** and reported `false`. **The run that lost twice as much is the run that claimed to be complete** — and that study's three most load-bearing taps were all whole-study, so all three flags were unfalsifiable at once, while an investigation into whether a capture had a gap rested on them.

The fix makes end-of-study closing its own concern rather than a step index chosen to fall outside every window. **The predicate is left exactly as it was** — it is correct, and special-casing the end of a study inside it would desync the two ends of the link for no gain. The generalisable half: **a mechanism that reports loss only on a transition needs the transition to be guaranteed, and "no scope covers step N+1" was a guarantee nobody had checked against every scope variant.**
