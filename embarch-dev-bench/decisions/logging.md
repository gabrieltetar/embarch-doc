# embarch-dev-bench decisions: Logging

**Status:** active, 2026-09-02.

Turning Zephyr's log subsystem on without corrupting the wire, and letting a study choose how loud the bench is.

Index: [../decisions.md](../decisions.md). Current truth: [../spec.md](../spec.md).

### 38 — `CONFIG_LOG` is on, and every record reaches Core as a framed line
Decision 7 established the *channel* and was implemented with the subsystem itself switched off, so only deliberate hand-written calls travelled. **That cost more than it looked like, and the cost is written in this firmware's own source:** a study failed with Core reporting a one-byte frame, the two candidate explanations were "the bench sent a malformed message" and "the bench died mid-study", and nothing observable could separate them — because with the boot banner and the log subsystem both off, **a reboot is completely silent from Core's side**. Every error in the BT host, every driver complaint, and the entire fatal-error dump compiled to nothing.

**A Zephyr log backend, not a second transport.** It formats each record, splits on newlines so a hexdump becomes one line each, replaces bytes outside printable ASCII so Core's line-oriented file stays one record per line, and hands the result to a sink `main.c` installs. It knows nothing about the UART or the message union, which is what makes it linkable in a ztest against a capturing sink rather than only testable on hardware.

**Deferred mode is load-bearing, not a restated default.** In immediate mode a backend runs in the caller's context — ISRs included — and this sink takes the link mutex and blocks on a UART write: illegal from an ISR, and a ~1.3 ms stall per line everywhere else, **on a bench whose whole job is measuring someone else's timing**. Deferred mode moves every backend call onto the log thread, which is what makes a *third* link writer safe. The exception is the fatal path: the panic hook switches to synchronous processing inside the faulting context, so the sink skips the mutex and writes directly — accepting that it may interleave with a frame some now-halted thread had half-written, because getting the fault out is the entire point and Core resyncs on the next delimiter.

**The boot backlog is what actually makes a reboot visible.** Core opens the port per study, so anything written before the first `Hello` is shifted out to nobody. The backend holds formatted lines until a sink is installed, which the handshake does immediately after putting the ack on the wire, flushing the backlog right behind it. Overflow drops the **oldest** and reports the count as its own line — never silently.

**Two knobs deliberately set against their defaults.** Turning off the UART log backend is the single most important line in the logging config: it defaults to `y` whenever a UART console exists, and this board's console *is* the protocol link, so leaving it alone would write raw text onto the wire — the precise failure decision 7 exists to prevent. And routing `printk` through the log subsystem is a **protection rather than a convenience**: a stray `printk` anywhere in Zephyr comes out as a framed line instead of corrupting a frame, which turns a prerequisite this project previously had to *check* into one it now *holds*.

**What paid for it, and the real finding underneath.** The subsystem costs ~11.2 KB of ESP32-C5 SRAM, of which **~5.1 KB is code**, because Espressif's linker script forces the log core into IRAM, which on this SoC is carved out of the same segment. Not negotiable from the application — and this board had 5.7 KB free. **Measured, not estimated:** a RAM-report diff between builds plus section sizes, because the first four estimates were all wrong in different directions.

**The room came from a buffer sized for a message that cannot arrive.** The inbound staging buffer used the *general* frame bound — set by the result message, which dev-bench only ever *sends*. Core sends exactly two messages, whose worst case is 9,415 bytes. Saying so explicitly freed ~10.5 KB, so the whole feature landed at **+736 bytes net** rather than 11 KB over. Deliberately scoped to the application's buffer and *not* the decoder's staging buffer, which stays general because the round-trip tests decode result messages through it precisely to prove encode and decode agree. The narrower bound is safe rather than merely smaller **because of the overflow branch that goes with it** — an oversized inbound frame is dropped, resynced on, and now *logged*, where before it was silent.

### 39 — A study says how loud the bench should be, filtered at runtime rather than compiled in
Decision 38 kept the link quiet by compiling out everything above warn. **The bandwidth argument was right and is unchanged** — a full line is ~1.3 ms of a wire the study protocol is also using, and the BT host at info is genuinely chatty. **The mechanism was wrong:** a compile-time ceiling makes the choice once, for every study, at whatever level whoever last edited the config picked, so the one study that needed the BT host's own account of a failure could only get it by editing a Kconfig, rebuilding and reflashing. Decision 38 had made the bench's log available and made it available *always*, which is the same defect from the other side.

So the study says. The level crosses on `StudyStart`, is applied when a study starts, and reverts when it ends — **in two places, not one**, because a study that dies mid-run never reaches the first, and `Hello` is already the hard reset. Verbosity is study state like the bond table and gets the same treatment for the same reason: the next study must not inherit it.

**This app's own module holds at info even while a study asks for less.** "The BT host should be quiet" is not the same request as "this firmware should stop saying what it is doing" — the boot record and the handshake diagnostics are what decision 38 exists for, and they would vanish the moment a study asked for warn. Matched by module *name*, because Zephyr exposes no way to ask for another translation unit's log source id. The single exception is an explicit `Off`, taken literally and silencing everything including the fatal dump — which is why `Off` is not the default.

**The setter returns the level it actually reached**, because the filter call clamps a request to what the build compiled in, and a study asking for debug against an info build would otherwise get a quieter log with nothing saying so. One subtlety that is a real trap rather than a detail: the answer folds in **only** sources that were asked for the requested level, excluding the app-module floor — otherwise an honoured request for warn reports back as info, i.e. as a clamp that never happened, and the caller acts on it.

**Four things real hardware changed, none of which any test caught first** — green on `native_sim` and demonstrably useless on a board, four times, for four unrelated reasons:

- **The runtime filter is applied too late to protect the boot backlog.** Every source sits at the *compiled* level from log-init until something first calls the filter setter, and `main()` is far too late: the backlog came back full of early-boot kernel tracing, which had pushed out the boot record decision 38 exists to carry. The backend now checks the level **itself**, independent of Zephyr's filter. The runtime filter is the efficient half — it stops a record being created — but it cannot be the *correct* half, because it is only in force from whenever it was first set.
- **A `printk` outranks everything.** Routing printk through the log subsystem (decision 38's wire protection) tags those records at a level *below* every level, and Zephyr logs them unconditionally by design — so a HAL announcing itself over printk at boot sailed past the idle filter and filled the backlog in turn. Reading the macro also found a latent crash: for these records Zephyr stores a flag in the source field rather than a pointer, so the app-module lookup would have dereferenced address 1.
- **Forwarding a log record generates log records.** At debug the capture came back as an unbroken alternation of a kernel mutex-unlock trace and "N records dropped" — the sink takes the link mutex, the kernel traces the unlock, that record is forwarded, which takes the mutex again. A kernel-module ceiling breaks the loop at the source, and nothing a study wanted is lost: kernel tracing is not the bench's account of the DUT.
- **Deferred logging judges a record at forward time, not creation time.** The log thread wakes on a record threshold or a one-second timeout, and a short study finishes in ~50 ms — so a debug study reverted to idle before its own records were looked at, and they were dropped under a level that was not in force when they were made. The setter now flushes **before** changing the level, so no record straddles a change in either direction.

**And one pure Zephyr API sharp edge:** registering a module at info is a *compile-time* ceiling, so every debug statement in `main.c` was compiled out of existence and a study asking for debug got the bench's own step-by-step account of nothing. **Runtime filtering can only reduce below the compiled level, never raise above it.**

**The wire pin is mutation-tested, which is the only reason it means anything.** The schema bump appends one varint, and a decoder that simply *ignored* the trailing byte would still decode every frame and pass every other assertion in the suite. So the cross-language vector generator emits a value the C struct would not contain by accident, and the vector tests assert the decoded value. Verified by breaking the decoder on purpose: three tests fail, and pass again when it is restored.

**Validated on the real bench, same study submitted twice.** At warn: two boundary markers and nothing else. At debug: the full HCI trace including raw HCI bytes, the cut marker on hexdumps too long for one line, no kernel records, and **"191 log record(s) dropped" at the head of the burst — a real limitation, not a defect**, since the log buffer is 1 KB and a debug burst overruns it. It is *reported* rather than silent, which is the property that matters; raising the buffer is the knob, and it costs SRAM this board does not have.
