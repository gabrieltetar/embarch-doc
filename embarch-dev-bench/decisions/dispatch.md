# embarch-dev-bench decisions: Dispatching a study, and the GATT actions

**Status:** active, 2026-09-02.

How a `Study` becomes executed steps, the discovery and monitoring actions, and the two SRAM overflows they cost.

Index: [../decisions.md](../decisions.md). Current truth: [../spec.md](../spec.md).

### 14 — No local hardware watchdog
Core's host-side watchdog exists specifically because a hung bench cannot self-report a timeout, and is treated as sufficient detection. A self-resetting local watchdog was **deferred rather than rejected** — a cheap addition to revisit if a hung bench in practice needs power-cycling too often for Core's detection alone to be a good enough experience.

### 21 — `main.c` dispatches a real `Study` instead of a fixed demo sequence
On `StudyStart` the protocol layer computes the CRC over the raw wire bytes of `steps` and reports whether it matches, plus whether any step's action is unsupported. Both are checked **before running anything**: a mismatch or an unsupported action logs why and reports the study not completed **with no step results at all**, rather than partially dispatching. Otherwise it walks the steps in order, sending a result after each and a final message at completion or an early stop.

**A real stack-safety fix, not originally scoped, found implementing this:** the message union grew to ~4.6 KB once it had to hold a full 64-step `StudyStart` (worst-case frame ~8.2 KB), so every scratch buffer that used to be stack-allocated became `static` and both stack sizes were raised. A genuinely new risk this message's size introduced, not present before it existed.

### 22 — The stream handler that decoded notifications into samples — superseded, and why
It decoded each raw notification as a sequence of little-endian `f32` values, buffered into a batch. **Superseded, because that handler was making an assumption it was never in a position to make.** "Decode each notification as `f32`s" is **an interpretation of what a specific DUT's bytes mean**, sitting in firmware, where no engineer declared it. It is a plausible guess — many sensor streams really are `f32` arrays — and it is wrong for a log, wrong for a packed 16-bit ADC stream, and wrong for anything framed. Exactly the category the suite's no-inference rule excludes, arrived at from the streaming side rather than the GATT side. Under decision 29 the bench **forwards arrival-stamped bytes and interprets nothing**; the `f32` reading becomes one engineer-declared encoding among several, chosen host-side by whoever actually knows. The deferred "compile-time constant per board/sensor" this entry ended on is retired with it — there is no longer a firmware-side place for that constant to live, which is the point.

### 27 — `GattDiscover` and `GattMonitorAll` for real, closing the advertise-only scope
The decode layer gained a tagged union covering all five action kinds, so dispatch now reaches `BleConnect`/`DataExchange` for the first time too (implemented since decision 16, never wired to a real decoded study) alongside the two new kinds. The bridge gained a wildcard primary-service walk run to completion via repeated callbacks, then a per-service characteristic walk; `GattMonitorAll` runs that same walk internally, then subscribes to everything notify- or indicate-capable, with a subscription cap deliberately **not** sized to the wire type's absolute worst case, which would cost several needless KB for a characteristic count no real DUT plausibly reaches.

**Two real bugs found by checking the discovered data rather than just the `Pass`.** A wildcard primary-service callback hands back the *declaration* attribute's own type UUID — identical for every service — while the service's own UUID arrives separately in a field the function had fetched into a local and never used. **Every real-hardware discovery result up to that point reported the same wrong UUID for every service**; per-characteristic UUIDs were unaffected. Found by hand-decoding a live result's raw bytes to show someone what was actually discovered — not by inspection, and not by tests, which do not run against a real BLE stack.

**A Kconfig bug found from the outset rather than the hard way a second time:** both real-hardware board fragments set the main stack to 2048, silently *overriding* the shared config's 8192 — Zephyr merges a board fragment after the base config and the later value wins with no warning. Confirmed against a real build's resolved config before fixing. Harmless while dispatch only ran advertise (a shallow chain); real discovery is the first time this thread's depth reaches into central-role GATT code.

**The first SRAM overflow:** a from-scratch build failed by 25 KB the first time the message union had to hold both a 512-byte write payload times every step *and* the new result fields at once. Two fixes: four separate static message buffers consolidated into one shared `tx_scratch` — safe because this single-threaded loop never has two outbound messages in flight — and a local step cap cut 64 → 16, deliberately *not* the crate's constant, sized against every study actually authored. **An oversized study is rejected by name, not silently truncated.** (Both were later undone: decision 35 removed the cap, decision 40 the field.)

**A real gap folded back rather than worked around:** the milestone plan named the *FFI* decode surface as the thing needing extension. It didn't — that surface decodes a `Study`, not the `StudyStart` this firmware receives, and dispatch has never called it, so extending it would have been real tested work that dispatch still would not exercise. The extension actually needed was the hand-written decode. **Left exactly as it was rather than extended for symmetry with no caller.**

*Unresolved:* a real flake rate on the connect-and-discover path — of four attempts, two failed before a clean result, and successful runs reported different live service counts for the identical build, suggesting the wildcard walk's completion is timing-sensitive against this DUT. Not root-caused; would need BLE-stack-level tracing.

### 28 — A capture window that spans steps, and a transcript that leaves BLE context safely
`GattMonitorAll`'s body split into subscribe and teardown halves, so it keeps its exact previous behaviour while `GattMonitorStart` runs only the first and leaves subscriptions armed and `GattMonitorStop` runs only the second. A window flag is cleared on disconnect — a window cannot outlive the connection whose subscriptions it holds, or a later `Stop` would unsubscribe against a freed connection — and on `Hello`, which is already a hard reset. Dispatch closes a window a study left open before finishing.

**Emitting the transcript from BLE callback context** is what shaped the rest: entries are built as a **stack local, not a shared static**, because the sink is called from both Zephyr's BT RX thread and the dispatch thread and a shared staging buffer would tear under a notification arriving mid-emit. That ~290-byte frame is why the BT RX stack is raised on both boards — left alone it would have failed as an intermittent stack overflow under exactly the notification bursts this feature exists to capture. The sink does one bounded non-blocking copy into a queue drained by a dedicated TX thread, because blocking the BT RX thread on a full queue would stall the very notifications being recorded; **a dropped entry is counted and reported rather than leaving a transcript silently claiming to be exhaustive.** That made a **second writer to the link**, which the single-threaded assumption had not allowed for, so every sender now holds a mutex across *build-and-send*.

**The second SRAM overflow:** the TX thread's first version kept its own message struct, and the build overflowed by 2,720 bytes at link time — that union is sized by its largest member regardless of which tag a send uses. Fixed by having the TX thread build into the same shared buffer, **rather than by shrinking a limit**. The transcript payload bound is one ATT MTU rather than the general payload maximum: the Rust type accepts more, this firmware never produces more than one MTU's worth, and each queue slot costs real RAM. **Sending fewer bytes than the receiving type can hold is always wire-legal; the reverse is not.** Zephyr's default MTU would have capped a notification at 62 bytes, fragmenting a shell response into rows that each look like a separate event.

**The encoding is hand-written C and pinned against Rust.** Nothing in this firmware's own tests would catch it drifting from what postcard expects — a reordered field or a `u8` written as a varint decodes into plausible-looking garbage, not an error — so the exact frame is asserted here and the identical pre-COBS body from the Rust side. Both must break together.
