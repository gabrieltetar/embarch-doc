- 2026-08-25 — **Milestone 6's "Still open" rewritten; it had been wrong about its own blocker.** The DUT that "advertised slowly and under an unexpected name" had been bricked by EmbArch's own `--erase`, and a session of BLE scan diagnostics went into explaining damage the suite caused. Recovered, the real blocker is a DUT that requires an MITM-authenticated L4 link before it permits service discovery against a bench that registers no pairing callbacks and therefore cannot reach L4 at all. Four design decisions written in response (study-designer 44/45, dev-bench 34, ui 12), plus core 32 and api 41 for the erase capability itself; none implemented. Two reversal rows (19, 20). The milestone stays open.
- 2026-08-25 — **Milestone 7 Phase B item 3 implemented, closing Phase B.** dev-bench decodes and stores its declared taps, opens and closes them from their `StreamScope` as steps advance, and sends the GATT transcript as `StreamChunkBatch` records on the tap that declared it — retiring tag 10 from the wire for real, with its discriminant left burned. 34/34 ztests on `native_sim`, `native_sim` and `esp32c5` both building, `embarch-core` 106 tests on Linux and native Windows, `embarch-study-designer` 75, every other repo green and unchanged. **Both of the item's premises turned out to be wrong**, and both are recorded rather than absorbed: the payload interpretation it was scoped to delete was already deleted in Phase A (so the phase ends net bigger, not smaller — reversal row 35), and the reserved `dev-bench` log tap needed Core rather than dev-bench (row 36). Not deployed. **The live Core is now three schema steps behind `main`, and a `DEV_BENCH_WIRE_SCHEMA_VERSION` bump is in that gap — so the Core redeploy and a dev-bench reflash have to happen in the same sitting** ([embarch-dev-workflow.md](embarch-dev-workflow.md) §4a).
- 2026-08-25 — **Milestone 7 Phase B item 2 implemented — across five repos, not the one the milestone scoped.** `embarch-api` got what item 2 was written for: `study_stream_data`/`list_study_streams` with the three old tools and subcommands kept unchanged as aliases, and `run_study --reflash none|dev-bench|dut|both` / `--allow-version-mismatch`, sequenced check → build → flash → submit, never running `git checkout` anywhere. But decision 40's override and `VersionSource::FlashedThisRun` had **nowhere to land** — so `embarch-study-designer` gained `Provenance.overrides` at host schema **9 → 10** (`DEV_BENCH_WIRE_SCHEMA_VERSION` stays 9, the first time the split actually separates the numbers) and `embarch-core` gained two query parameters on `POST /study`. Two unanticipated results: the DUT half of Core's version gate became live, since supplying a flashed version is what makes `requires.firmware_version` checkable at all; and the two reflash halves sequence *differently* — the bench is flashed then read back, the DUT is verified then flashed — which is decision 40's verification asymmetry appearing as control flow, and means a wrong tree fails without touching the board. Reversal row 28 came out of reading unrelated code on the way past: Core's `erase` documents a vendor-tool delegation the tree does not contain. Green across all seven code repos, Core on Linux and native Windows; **not deployed, and the live Core is now two schema steps behind — Core still deploys before api.**
