## 1. Why this is phased, and why the phases are ordered this way

Milestone 7 spans seven repos, which is too much for one pass. The ordering is not preference — it is a real dependency chain plus one deliberate exception:

- **Phase A must be first.** `embarch-study-designer`'s types are compiled into `embarch-core`, `embarch-api`, `embarch-ui`, *and* dev-bench firmware. Nothing else can be built against a schema that hasn't landed.
- **Phase C (the outpost module itself) is deliberately out of that chain.** It emits bytes down a UART and depends on nothing in this suite — it can be written and built in parallel with A/B by a separate thread. It is also the only phase whose *validation* needs hardware that does not exist yet (§5).
- **Phase E is last and needs a physical bench**, including a USB-UART bridge nobody has bought yet.

**The timing risk below did not decay: Phase A landed while Milestone 6's firmware was still unflashed**, so decisions 29 and 39 stayed a reshape rather than becoming a migration. Nothing about the ordering below changes; the note is kept because it is still live for Phase B, which is where the reshape actually reaches dev-bench's behavior.

**One timing risk, stated up front because it decays.** [embarch-dev-bench/design.md](../embarch-dev-bench/design.md) §3 decision 29 and [embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 39 reverse wire shapes that are **code-complete and deployed but never flashed or run** (roadmap Milestone 6). That is precisely what made the reversal cheap. If Milestone 6's dev-bench firmware gets flashed and validated before Phase A/B land, the reshape stops being free and becomes a migration. Sequence accordingly, or accept the cost knowingly.

**Repo:** [gabrieltetar/embarch-outpost](https://github.com/gabrieltetar/embarch-outpost), cloned as a sibling of `embarch-doc` and given its first commit this pass. Everything here is [design.md](design.md) §3 decisions 1–9 and §5.

[embarch-decision-reversals.md](../embarch-decision-reversals.md) row 38.
2. ~~Record ring + drain thread + `uart_tx()`, overflow = drop, count, emit a gap record.~~ — done. The ring is a Vyukov-style lock-free MPSC queue, **not** a `k_spinlock`, for a reason worth keeping: the emit path runs inside interrupt context at arbitrary priority, and an `irq_lock` there raises the interrupt latency of every unrelated ISR by the length of the trace write — a trace whose cost is a latency floor on other interrupts distorts what it measures. A slot publishes `reservation + 1` rather than `reservation`, which is what makes the ring correct straight out of BSS: the first hooks fire during kernel startup, so there is no moment at which running an initialiser would be safe rather than a race.
3. ~~`TRACING_USER` hooks; ISR identity via `__get_IPSR() - 16`, on both enter and exit.~~ — done. Zephyr's `tracing_user.c` declares every `sys_trace_*_user()` `__weak` and empty, so defining a strong one is the entire integration contract. One thing the design listed that does not exist: **`sys_trace_idle_exit()` has no user hook** — Zephyr routes it to `CONFIG_CPU_LOAD` alone — so idle exit is recovered host-side from the next thread-switch-in, which is what actually ends the span.
4. ~~`OUTPOST_EVT` + the marker registration list; an unregistered ID must be a build error.~~ — done, and it is a build error whether or not markers are compiled in. **What this item actually cost was keeping the table in the image at all**: nothing in the firmware reads it, so `--gc-sections` deletes it and the build still succeeds, producing a manifest with no markers. `zephyr_iterable_section()` has no effect on the template-`.ld` path; a `zephyr_linker_sources(RODATA ...)` `KEEP()` survives the Zephyr link and is collected out by the host link that makes `zephyr.exe`. A `volatile` reference holds on every target. Row 41.
5. ~~Records `{cycles, kind, a, b}`; postcard + COBS on drain; periodic header carrying build ID, runtime cycle rate, layout version.~~ — done, with two shape corrections. **The header is a frame type, not a record kind** — its fields do not fit the fixed record, and as a frame a host attaching mid-stream finds it at a COBS boundary without decoding anything. **It carries no manifest CRC**, because there cannot be one (item 6 and row 37). A record is ~12 bytes rather than the ~8 design §3 decision 4 quoted, since postcard varints make an absolute cycle count five bytes (row 39).
6. ~~**Manifest generator** — post-link CMake step emitting `outpost-manifest.json`.~~ — done, and it resolves more than the item asked for: `_sw_isr_table`'s `arg` as well as its `isr`, because Nordic's nrfx glue registers one shared `nrfx_isr` trampoline per peripheral and 8 of the reference-dut's 13 IRQs would otherwise carry that one useless name (row 42); and the kernel's own `z_main_thread`/`z_idle_threads`, which between them account for most of a quiet trace. Two build-system traps found here **produce a wrong manifest rather than an error**, so both are written into design §5.4: Zephyr's `extra_post_build_commands` hook fires on `zephyr.elf`, which on `native_sim` is a relocatable object with all-zero symbol addresses upstream of the real link; and the names of the final target and file are set after module CMakeLists run, so the step has to defer to the end of Zephyr's own directory scope.

**Definition of done — met 2026-08-26.** Builds for `native_sim` **and** for the real reference-dut target (`dut_dev@7/nrf54l15/cpuapp`). A `native_sim` run produces a decodable stream: 41 frames, 848 records, every record kind including gaps, zero CRC failures, zero framing failures, zero lost frames, and records in non-decreasing cycle order. The generator resolves **13 real ISRs and 5 real threads** out of the reference-dut ELF. 13 ztests pin the wire format against literal bytes; the end-to-end test additionally asserts that a manifest with the wrong build ID is **refused** rather than applied.

**Overhead is deliberately not a gate here**, decided 2026-08-25 at the user's call and recorded in [design.md](design.md) §7: get the pipeline working end to end first, and characterize overhead once there is a real trace to compare against. **Two things Phase C must not be read as closing, both still open in [design.md](design.md) §7:** every wire constant in §5.3 is an unmeasured default — a host process writing to a pty sustains a rate no UART will, so the `native_sim` run proves correctness and nothing about cost — and no outpost byte has crossed a real UART on any board.

### 4a. What closing Phase C fired — the manifest halves in Core and api

[embarch-core/design.md](../embarch-core/design.md) §3 decision 30(c) and [embarch-api/design.md](../embarch-api/design.md) §3 decision 39 were settled and deliberately not built, closed under one shared named trigger: **Phase C emitting a real `outpost-manifest.json`.** It fired, and both shipped in the same pass rather than being recorded as newly-owed work.

- **Core** — `POST /flash` takes an optional `manifest` multipart part and `manifest_path` JSON field. Manifests are held **per chip**, replaced by a flash that carries one and **cleared** by a flash of the same chip that does not; keyed by chip because `POST /flash` is also how dev-bench's firmware is written, and clearing the DUT's manifest because the bench was reflashed would be wrong. A study snapshots the binding into its own results directory at *start*, so a flash during a long study cannot swap the answer out from under a capture in progress. The trace is decoded post-hoc from the complete raw file, on the failure path too.
- **Refusal, and what it costs.** A build-ID mismatch costs the **names**, never the capture: rows are still written with an empty `name` column, and `streams/index.json` gains a `note` saying why, so an unnamed trace is never mistaken for a named one. What is refused is applying the *wrong* manifest.
- **api** — `embarch-core-client`'s `flash` finds `outpost-manifest.json` **beside the artifact it is about to send** and attaches it, rather than taking it as a parameter. Decision 39's own reasoning is why: the failure mode is forgetting, and there are a dozen `flash` call sites across `tools.rs`/`cli.rs`/`reflash.rs`, every one of them a place to forget. It also means nothing needs to know which board it is talking to — a dev-bench build leaves no manifest beside its artifact.
- **The type layer did have to move, which this plan did not anticipate.** `StreamEncoding::OutpostTrace { manifest_crc }` encoded a mechanism decision 9 had already reversed and bound it at the wrong moment, so it becomes a unit variant at **dev-bench wire schema v11 / host v13** — a wire change, since `StreamEncoding` rides `StudyStart` inside every `StreamTap`. Row 37.
- **Definition of done — met.** `embarch-study-designer` 77 tests plus its whole feature matrix (including `alloc` and `std` standalone, which had **never** built — row 43); `embarch-core` 116 (was 106) on Linux and in a native Windows `cargo.exe --release` build; `embarch-api` and `embarch-core-client` green; `embarch-ui`/`embarch-umbrella`/`embarch-topology` green and unchanged; 34/34 dev-bench ztests on `native_sim` with the main app building for both `native_sim` and `esp32c5` (`sram0_0_seg` unchanged at 372,624 B). Clippy `--all-targets -- -D warnings` clean everywhere. **Not deployed**, and the live Core is now three schema steps behind `main`.
- **One thing fixed on the way past, worth more than the change that surfaced it.** dev-bench's hand-mirrored `STUDY_FFI_STUB_SCHEMA_VERSION` was stale again at 9 — one bump after being found four bumps stale and fixed, with a comment saying nothing compares it against the crate. It is now read out of the crate's own source at CMake configure time. Row 44.

## 5. Phase D — UI, and Phase E — hardware bring-up

**D** ([embarch-ui/design.md](../embarch-ui/design.md) §3 decisions 10, 11) — **CLOSED 2026-08-26**, with one item deliberately not built and four the one-line scope did not mention.

Built: signal-route rows in the Topology tab with the diagram drawing a `Direct` signal **around** the dev-bench node; the post-hoc Trace view; `requires` prefilled from live bench state with `any` as a visible checkbox; a mismatch shown before the run with both strings; `Declared` rendered visibly weaker than verified. Plus **tap authoring**, which this line did not mention and which the phase could not do without — `embarch-ui` authored no taps at all, so a Trace view would have had nothing this UI could ever produce to render.

**Not built: reflash in the run dialog.** `run_study --reflash` is `embarch-api` orchestration (check → build → flash → submit, over project config and build machinery `embarch-ui` does not have), and Core's `POST /study` accepts nothing that flashes. Settled with the user as scoped-out rather than resolved by duplicating that orchestration or by inventing an `embarch-ui` → `embarch-api` dependency; the run dialog says so, and [embarch-ui/design.md](../embarch-ui/design.md) §5 carries it as an open question.

**"a build-ID mismatch not rendered at all" is corrected here**, and this line was already stale when it was written: Phase C settled that Core writes the rows *unnamed* with the reason in `streams/index.json`, so the requirement is never rendering it as a **named** trace. Row 45.

**Four things the one-word scope (`embarch-ui`) missed** — the same pattern Phase B recorded for two of its four items:
- `embarch-core-client` had no `/signals` methods at all, so Phase D touched **`embarch-api`**'s workspace. Shared crate before consumer.
- Core needed **`GET /serial-ports`**: "a serial-port pick from Core's own enumeration" had no enumeration, and `/dev-bench/port` VID-gates, which would hide exactly the bridge a `Direct` route names. That in turn needed **`embarch-topology`**'s `hardware::list_serial_ports`, so five repos, not one.
- Core needed **`GET /study/{id}/streams`**: `streams/index.json`'s `note` — Phase C's own field for saying why a trace has no names — had no HTTP caller, so over HTTP a refused trace and a named one were indistinguishable. A new route rather than a field on `StreamRef`, which would have been a host schema bump for Core-side bookkeeping dev-bench never sees.
- Core needed **`DELETE /signals/{name}`**: decision 10's "this tab is the only human surface there is" plus an idempotent-by-name declare means the only place that can state a wire could not retract one.

**Validated without hardware, and without touching anything deployed.** A dev Core built from `main` ran in a private mount namespace with a scratch `/var/lib`, so every enrollment/signal/study write landed in a scratchpad and the live Windows service was untouched: signals declared, moved and removed for real over HTTP, all three new routes answering, and both a named and a manifest-refused trace rendered from the committed `native_sim` capture. **The live Core turned out to predate `GET /signals` entirely** — it answers `404` — so the plan's assumption that the Topology half could be exercised against it was wrong; that is what `Snapshot::signals_error` exists for, and it is row 46.

**E** — **attempted 2026-08-26, and this line was right where the phase's own handoff was wrong.** Everything it names as missing is still missing, and that is the finding.

**Done, and none of it needed the wire.** The live Windows Core was redeployed from `main` (it was further behind than row 46 recorded — its `Step` still carried `power_sample`, so it computed a different `steps_crc` for identical steps) and dev-bench reflashed to schema v11 in the same sitting; they handshake `compatible: true`, `link_identity: "match"`. The **load repartition** is built in the Trace view ([embarch-ui/design.md](../embarch-ui/design.md) §3 decision 10's amendment (f)), and building it found that idle is double-counted by construction. The **outpost snippet** is written for the real reference-dut, the module is pinned in that repo's `west.yml` at a full SHA, and the tracing image is **built and flashed onto the real DUT** — where it still advertises, connects and serves GATT with the tracer compiled in. En route, decision 33's watchdog test was run against the pre-fix Core and then the fixed one, closing [embarch-core/design.md](../embarch-core/design.md) §10's host-side-watchdog item, open since 2026-08-20.

**Blocked, and the block is physical.** The DUT's trace UART reaches the host over **no serial port at all** — established by flashing a console build, *proving it running* over BLE, and then finding zero bytes on the J-Link's own VCOM for this DUT and a permanently-low line on the one real USB-UART bridge on the bench. So the bridge and the wire this line asked for in the first place are exactly what Phase E still needs: an adapter's RX on **P1.05** (not the schematic's `DBG_TX` P1.04 — crossed nets on rev 6 and rev 7) plus a ground. [design.md](design.md) §3 decision 16, which had asserted no bridge was needed, is amended with the evidence; [embarch-decision-reversals.md](../embarch-decision-reversals.md) rows 49–53.

**A second blocker the scope line could not have known about**, and it is not the outpost's fault: the saved studies all stimulate through the Nordic UART Service, which does not appear in this DUT's GATT table. Verified as **not** an instrumentation effect by running the same study against a build with the outpost compiled out — it fails identically. So even with the wire, a stimulus has to be sorted before a capture shows load rather than idle. That is DUT-side work and the repo owner has it.

First real capture is still what sizes every Kconfig default in §5.3, and none of them is measured.
