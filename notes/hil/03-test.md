# HIL notes: the Test mode

**Status:** draft, 2026-11-15.

## What a Test is

**Technical conformance with a verdict**, as pre-compliance evidence ([The report](#the-report)). A **test suite** (USB PD R3.2 is one) holds an exhaustive set of **tests**; the engineer or agent **selects** the tests to run. A suite's tests are **grouped by bench**, so one run can span **one or more benches**, one after another. A suite is **premade** (shipped with EmbArch, [04-premade-suites.md](04-premade-suites.md)) or **custom** (written in the firmware repo by the engineer and agent). **A custom suite reuses a premade test by copying it into the firmware repo and editing it freely**, and **the copy keeps `derived_from: <test id>@<suite version>`**, so the report shows every verdict-deciding field it changed ("limit widened from 4.75–5.25 V to 4.5–5.5 V"); a copy with a loosened limit never reads as the premade test.

## One test

**A test is a study plus verdict rules; there is no new step format.** It carries:

- the **study** it runs, a host study or a dev-bench study;
- the **requirement IDs** it checks, and the **revision range** of the spec it applies to;
- the **bench** it needs, and the **config** of that bench, by name;
- a **precondition**, the state it starts from: `reset`, `power_cycle`, `detach` or `none`. **The default is a DUT reset plus each bench board's idle command, before every test**, so one test's leftovers (a PPS contract kept alive, a swapped role) are never the next one's start, and reordering tests cannot change their results. LabGrid's strategies are the precedent ([09](09-trust-model.md#prior-art));
- **`requires`**: other tests it depends on, so a failed or skipped one skips it, with that reason;
- a **run count**, default 1. **Each run gets its own verdict, the guard band applied per run, and the test's verdict is its worst run's** in the severity order below (review round 2, recommended); so a pass only if every run passes, and one inconclusive run makes the test inconclusive. A flaky behaviour gets a count above 1 in its own test;
- **limits** on its **measurements** ([02-study.md](02-study.md#measurements)), each wider than its measurement's uncertainty allows ([The verdict](#the-verdict)).

## The verdict

**Decided by code, never by the agent**, and one of six:

| Verdict | Means |
|---|---|
| **pass** | Every limit held, on every run, on complete evidence |
| **fail** | The DUT broke a limit or a marker rule |
| **error** | The setup could not judge the DUT: a bench board, an instrument or a port failed, or the smoke check did |
| **inconclusive** | The evidence the verdict rests on is incomplete: a truncated capture, a truncated reply, a gap across the measured window, a number that did not parse. **Or a result inside a limit's guard band**, between its acceptance limit and its tolerance limit, with the reason "guard band" (owner, review round 1). **The band lies on both sides of the tolerance limit**, its width w either way, so a result just outside the limit is inconclusive too, not a fail: ILAC-G8's conditional pass and conditional fail, both read as inconclusive (review round 2, recommended) |
| **skipped** | Not run, with the reason: not applicable, hook unmapped, bench missing, not selected, a `requires` not met, stopped by an error |
| **cancelled** | The run was cancelled |

**A step's failure is charged by what it addressed**, which Core derives from the step's target and no study writes (review round 2, recommended): a step on a DUT signal, or a limit on a DUT measurement, can fail the DUT; a step on a bench board or an instrument that fails is an **error**, so a cable that falls out never reads as a DUT failing conformance. Today a lost port is `Fail` whatever it addressed ([embarch-core decision 95](../../embarch-core/decisions/host-study.md)), so this is new in Core. Today's step outcomes map as follows (review round 2, recommended):

| Core's step outcome (decision 95, 105) | On a DUT signal | On a bench board or an instrument |
|---|---|---|
| `Pass` (`until` seen, a prompt confirmed) | pass, then the limits decide | pass, then the limits decide |
| `Fail`, `refused_on` seen | **fail** | **error** |
| `TimedOut`, `until_not_seen` (bytes, no marker) | **fail**: the DUT did not do it in time | **error** |
| `Fail`, `empty_reply` (no byte at all), or a lost port | **error**: a silent console is the setup's until shown otherwise | **error** |
| A prompt `prompt_timed_out` or `prompt_cancelled` | **inconclusive** for an observation prompt; **error** for any other kind | — |

**Declared numeric limits** act on top of a passing step. **A person may enter a verdict by hand**, through any surface the ledger has today, MCP included (owner, review round 1); **it is an entry in Core's run log**, made through a Core route that records the token's scope, the repo's row being its mirror (review round 2, recommended); **it is attributed by that token**, so one entered with the agent's token reads "manual verdict, relayed by the agent", one entered with the person's reads as theirs; **a relayed manual verdict is listed apart and never counts in a requirement's verdict or in coverage**, and `verify` reports every manual verdict as not recomputed (review round 2, recommended).

**Core parses the number at step time.** A host-study step declares a pattern and a unit; Core records the number beside the raw reply in `events.json`. This is the "declared numeric parse" the [host-study proposal](../../embarch-host-study-proposal.md) left for later ("What is left", item 2). **Numbers computed over a capture are Core's too**, through the shared crate as each test ends ([02-study.md](02-study.md#measurements)); `verify` reapplies the same patterns to the raw replies and the same reducers to the captures ([06](06-report-and-publish.md#verify)).

**A limit is checked against what can measure it.** Each measurement source declares its **resolution** and its **uncertainty** `U`, with its coverage factor and its basis (an instrument's datasheet or calibration certificate, a bench board's characterisation, or the engineer's declaration, marked as such) ([02](02-study.md#measurements)). **A test is refused when it is defined if no result could be judged against its limit**, one rule for both decision rules, with w = 0 under simple acceptance and `U` the expanded uncertainty at its declared coverage factor: **a two-sided limit band must be wider than 2 × max(w, `U`)**, and **a one-sided limit must sit more than max(w, `U`) inside the range its source measures**; the same check is made with the source's resolution in place of `U`; **the go card shows every limit with its `U` and w** (review round 2, recommended). A host stamp through a USB serial bridge is not a sub-millisecond clock (inferred, not measured), so a PD timing requirement is measured on the bench board's own clock. **The report states its decision rule**, simple acceptance or a guard band, as ISO/IEC 17025 asks of a statement of conformity; under a guard band, **w is a stated multiple of the measurement's `U`** (w = U keeps the chance of a false accept under 2.5 %, ILAC-G8; [11](11-prior-art.md#classical-hil-frameworks-formats-and-report-tooling)), and the multiple is part of the decision rule the report states. **A premade test states its decision rule, and the default is a guard band with w = `U`**; **under simple acceptance, the report states beside the rule that a result at the limit may be a false accept with a probability of up to 50 %** (ILAC-G8) (review round 3, recommended). Where each measurement's `U` comes from, a derived, `dut` or `person` measurement included: [02](02-study.md#measurements).

**The severity order**, used wherever verdicts combine (runs into a test, tests into a requirement, a run's summary line), adapted from OpenTAP's: **error > fail > inconclusive > cancelled > skipped > pass** (review round 2, recommended). Error ranks highest because a setup that could not judge the DUT voids what it measured. **OpenTAP puts Aborted above Fail; here cancelled sits below fail and inconclusive**, since a cancel says nothing about the DUT and must not hide a fail already measured, and skipped, which OpenTAP does not have, sits just above pass ([11](11-prior-art.md#classical-hil-frameworks-formats-and-report-tooling)). **Every combined verdict is shown with its per-verdict counts** ("error: 1 error, 2 fail, 5 pass"), so an error never hides a fail (review round 3, recommended).

## Benches

- **A suite ships each bench as a saved-bench description**: parts, cables and configs, no probe serials. **Selecting a suite copies its benches into the firmware repo's `embarch/topologies/`**, where the project can edit them, which keeps the owner's 2026-11-01 call that saved benches live in the firmware repo ([embarch-ui decision 73](../../embarch-ui/decisions/saved-benches.md)).
- **Setting a bench up is a human step in the Topology view**: open the saved bench, wire it, **Make live**, which applies the declarations and proposes each probe binding ([decision 90](../../embarch-ui/decisions/bench-live.md)); **the CLI does the same in the person's terminal**, so a Test needs no UI ([12](12-prevention.md#the-root-of-trust-core-under-its-own-account)) (review round 3, recommended).
- **A config change inside one bench is a `Prompt` naming the config**, which host studies already do ([embarch-study-designer decision 88](../../embarch-study-designer/decisions/host-prompt.md); [embarch-ui decision 99](../../embarch-ui/decisions/operator-prompt.md)).
- **The same DUT unit moves from bench to bench.** The runner checks its hardware ID on every bench and refuses a different unit. **A Test needs a DUT**: a bench with none, which a Study may use, is refused when the test is defined, naming the bench ([13](13-research-phase.md#a-bench-with-no-dut)) (owner, 2026-11-18).
- **Hardware safety is an authoring concern, not a runtime limit** (owner, review round 1): no envelope is enforced at execution. What a test puts on the DUT (a VBUS level, a load current) is reviewed against the DUT's ratings when the test is written and confirmed, and the run preview shows it again before the start ([Selecting and rerunning](#selecting-and-rerunning)).

## A run

**Core runs it, so a run survives the session that started it.** Core never reads a firmware repo, so **embarch-api resolves the selection** into one file, **`run.json`**, and sends it to Core with the definitions it was expanded from. **Core re-expands it through the shared crate and refuses a `run.json` it does not reproduce from confirmed definitions and inputs** (review round 2, recommended). Core runs it and keeps the results in its run log; **the repo's result rows are a mirror of that log, and where the two disagree the log wins** ([12](12-prevention.md#what-core-then-guarantees-in-code); review round 2).

1. **Group by bench.** All selected tests for bench A run, then bench B, and so on. **One lease for the whole run, held by the run itself**: the go transfers the session's lease to the run, the session's token reaches no hardware until the run ends, and the lease then returns to the session (review round 2, recommended).
2. **Between benches, an operator prompt** says which saved bench to set up, with what is missing. **Only the person answers a prompt**: in the UI's prompt modal, or by telling the agent, which relays their exact words with `answer_prompt`. **The agent never answers one on its own.** **A prompt declares its kind**, `setup`, `action`, `observation` or `clearance`, and **Core refuses a relayed answer to an observation or a clearance**, whose answer is itself evidence or a person's safety; an action prompt names the measurement that confirms the action (owner, review round 1; [12](12-prevention.md#operator-prompts-by-kind)). **"Relayed" is decided by the token's scope, never by `answered_by`**, which the caller writes; that amends [embarch-core decision 105](../../embarch-core/decisions/host-prompt.md), which trusts `answered_by` for nothing. **A prompt's kind is part of the test the engineer confirms** ([The DUT's inputs](#the-duts-inputs)), so a study cannot relabel an observation as a setup (review round 2, recommended). **While the run waits on a setup prompt between benches, Core admits the person's setup calls** (Make live's declarations, an enrolment) with the person's token; every other call stays refused (review round 2, recommended).
3. **Before a bench's first test, a smoke check**: the topology the bench needs is live, the DUT's and every board's identity validates, each companion board answers a hello, each instrument answers an identity query (its `*IDN?` reply goes in the report), and **the DUT's image is read back through the probe**, its load segments' SHA-256 compared with the artifact Core flashed. **Every bench board's image is read back too, and compared with the bench firmware the installed EmbArch release ships**, whose hashes sit in Core's protected store with its copy of the suites, so a custom test and a Study have the same reference as a premade one (a suite version also names the release it was validated with), since a bench board the agent reflashed could report anything; **every measurement carries `bench_image`**: `released`, `unreleased` (a bench board on a development build, as EmbArch's own work makes) or `unverified` (a board with no probe to read it through); **an `unreleased` image carries the scope of the token that flashed it, from Core's call log, carried into the signed record**, or "unknown" where Core did not flash it, so "bench firmware flashed by the agent" is told apart from EmbArch's own development builds flashed by the person, and an attested report says which beside the verdict (review round 3, recommended). **It is shown beside each value it touches and in the appendix, and a verdict resting on an `unreleased` or `unverified` board reads "pass, bench firmware unreleased" (or unverified)**, never a bare pass; it does not change the verdict itself (review round 2, recommended). The report then says "the chip holds the artifact Core flashed", or "a claim" with the reason when read-out protection blocks the read; **which source built the artifact is the build's claim**, not Core's observation ([06](06-report-and-publish.md#the-audit-appendix)). A failing check names the piece, runs no test on that bench, and is an **error** for each of them. **Before a Study on a bench with no DUT**, the DUT's identity and image are skipped and the audit appendix says "no DUT on this bench" and the declared subject in their place ([13](13-research-phase.md#a-bench-with-no-dut)) (owner, 2026-11-18); **only when Core's own state shows the `dut` role empty**, never on the study's word (owner, 2026-11-19).
4. **Nothing else touches the bench while a run is in flight**: Core refuses every hardware call over HTTP, whoever sends it, Live reads included, since the run's own steps run inside Core and use no route; the exceptions are a prompt's answer, the person's setup calls of item 2, **a cancel**, always admitted and recorded with its token's scope, and reads of the run's status (owner, review round 1; the exceptions review round 2, recommended; [12](12-prevention.md#what-stays-outside-prevention-and-is-said-so)).
5. **What a failure stops.** A failed **step** ends its **test**, with the study's teardown, as host studies already do. **A fail ends only its own test**: the bench goes on to its next test, which starts from its own precondition. **An error ends its bench**, because the setup is no longer trustworthy, and the run goes on to the next bench. **A cancel ends the whole run.** **`stop_on_fail`**, a run option off by default, ends the run at the first fail, for a debugging session; the tests it leaves are **skipped**, reason "stopped after a fail". *Replaces the owner's first answer, "a failure ends its own bench" (owner, review round 1).*
6. **Watching a run.** One `test_status` call answers the current bench, the current test, the verdicts so far, and a waiting prompt with its text, from any session; each study's own events stay available underneath.
7. **Retention.** **A run's entry in Core's run log and its signed records are never swept.** A Test run's captures count as one unit in Core's retention sweep (`EMBARCH_STUDY_RESULTS_KEEP`, 50 runs), **are never swept while the run is unpublished**, and may be swept once it is published, since the zip holds them; a Study's captures follow the same rule (review round 2, recommended).
8. **Sequential only.** Two benches acting at the same moment are out of scope; Core runs one study at a time and a host study cannot drive the dev bench.
9. **A long run survives a restart as far as it got.** A Core restart leaves the run `interrupted`, its verdicts so far kept. **Resuming is a new run of the pending remainder**, linked to the first, with the image read back again. **Core keeps the host awake while a run holds the lease** (the need on Windows is inferred, not measured). **Publishing either run of a resumed pair publishes both, as one zip**, each with its own run record (review round 3, recommended).
10. **Core signs a record of the whole run** as it ends, a cancel or an interruption included: `run.json`'s hash; **the selection as Core expanded it at the go**, every test of the suite applicable to the confirmed DUT inputs with its status (selected; not applicable, with the condition that excluded it; hook unmapped; not selected); each selected test's record hash and verdict, or the signed reason it has none (skipped, cancelled, never reached); and the run it resumes, if any. **The report's coverage and its list of tests that did not run come from this record**, not from embarch-api (review round 3, recommended).

## Selecting and rerunning

- **Selection narrows by applicability, then picks.** The runner keeps the tests that apply to the DUT's role and capabilities and to the benches that exist, then the engineer or agent picks by test ID or tag.
- **A selection is saved as a test plan** in the firmware repo, to rerun it ("our PD regression set").
- **`run.json` is the resolved run**: every test expanded to a concrete study, the DUT's inputs substituted, limits, benches, configs, preconditions, the suite's commit, the plan's hash, and each capability with its provenance. **A premade test is a template**, expanded here: one pass per PDO the DUT advertises, say. `run.json` is hashed, kept by Core, carried in the zip, and is what `verify` recomputes against ([06](06-report-and-publish.md#verify)).
- **A preview before the start, and the go.** **The go card is rendered from Core's record of `run.json`**, not from the agent's words: the tests per bench, every prompt with its kind, what will be powered and at what level (from the instrument and bench-board steps), each custom or derived test's diff against what was confirmed, every input still unconfirmed, and an upper bound on the duration from the timeouts. The agent may show the same preview in the chat as a convenience. **The engineer's go starts the run; it binds the run's id, `run.json`'s hash, a nonce Core issued for that card and an expiry, and is used once**, so an old go cannot start a run again (review round 2, recommended). **`run_test` prepares a run and never starts one**: embarch-api sends `run.json` and its definitions to Core with the agent's token, and Core re-expands it, registers a prepared run with its id, and renders that run's card. **The go, given with the person's token, starts it and takes the lease from the session that prepared it**, which must hold the lease at that moment; otherwise Core refuses the go and says why (review round 3, recommended).
- **The rerun rule is today's ledger rule**, computed from Core's run log rather than the repo's mirror (review round 2, recommended): a test is pending when the DUT image hash differs from its last pass, or it never ran, failed, or its commit was rebased away.

## The DUT's inputs

A test may need two kinds of input about the DUT:

- **Capabilities**: its role (source, sink, dual-role), its PDOs, which swaps it supports, and the like. They decide applicability.
- **Hooks**: a named action the DUT must take itself, such as `dut.request_pr_swap` for a swap the DUT initiates. **A hook maps to a DUT shell command or to an operator prompt** ("press the button"); **a hook with no mapping skips its test, and the coverage list says why.**

**Every input that decides a verdict needs the engineer's confirmation** (owner, review round 1): capabilities, hook mappings, limits, run counts, the revision tested against. **What is confirmed, as a unit** (review round 2, recommended): **a custom or derived test, whole, by the hash of its definition** (its study, steps and markers, parse patterns, reducer windows, preconditions, prompt kinds, limits, uncertainties, decision rule, and the requirement IDs it claims), with its diff against the premade test it was copied from; **an unmodified premade test needs none**, pinned by its suite version, and **"unmodified" means identical to Core's own copy of that suite version**, installed into its protected store with Core and updated only by the elevated install, since the definitions embarch-api sends are in the agent's reach (review round 2, recommended). **A Core in the engineer's own account reads its premade suites from a suite checkout its configuration names**, so a contributor edits a suite and runs it with no elevation, every report from that Core being unattested anyway; **a plan pinned to a suite version Core does not hold** runs the installed one with a warning ([04](04-premade-suites.md#decided)), or, to run the pinned one, runs its tests as custom tests, each confirmed by its hash, and the report says the suite was not Core's (review round 3, recommended). **Each DUT input, field by field**; and **the plan's selection, by the go**. Coverage counts only confirmed tests. **The agent proposes; a proposal is not used until the engineer confirms it**, and **a confirmation is made in the UI only, or the CLI where there is no UI** (owner, review round 1). **It binds the hash of exactly what was confirmed and is kept by Core**, outside the firmware repo the agent can edit (owner, review round 1): an input edited after its confirmation is unconfirmed again, and the preview says so. Who confirmed what, when and through which surface is shown in the appendix. How Core makes this hold against an agent that tries to forge one: [12-prevention.md](12-prevention.md). Otherwise an agent that read the source and decided "this DUT cannot PR_Swap" would drop the swap tests as not applicable, and the coverage would still look complete.

**Each capability carries its provenance**, listed in the report:

| Provenance | Where it comes from |
|---|---|
| `measured` | Read off the wire: the PD partner captures the DUT's Source_Capabilities |
| `decoded` | The atlas, from the build (a USB PD PDO is already decoded, [atlas design](../../embarch-atlas/design.md#firmware-configuration-against-a-standard)), or `atlas.toml`'s declared values |
| `confirmed` | Proposed by the agent, confirmed by the engineer |
| `declared` | Typed by the engineer, or read from the DUT's **VIF** (Vendor Info File, the XML a PD compliance tool takes; Zephyr's `scripts/generate_usb_vif` builds one from the devicetree) (owner, review round 1) |

**Where a capability can be measured, a declared or decoded value is checked against the measured one**, which is a test in its own right: **it runs first on its bench, and every test expanded from that capability `requires` it**, so a mismatch skips them with the reason instead of running them on a wrong expansion (review round 2, recommended). Every answer is saved in the test plan, so it is asked once per project on one machine, not once per run; **a confirmation lives in that machine's Core**, so a second machine confirms again, which is the edge of the suite's single-engineer scope ([embarch.md](../../embarch.md) §5). **A hook mapping is proposed by the agent** from the firmware's shell (its source, or a live `help`) and lands in the plan once the engineer says yes.

## It grows out of the ledger

**EmbArch Test replaces the hardware test ledger by growing out of it** ([embarch-api decision 98](../../embarch-api/decisions/ledger.md), [tools](../../embarch-api/interfaces/tools-ledger.md)). The ledger's three files and its computed pending view are kept and renamed: **`embarch/tests/` holds the custom suites, the test plans and a mirror of the results** (Core's run log is the record, [A run](#a-run)), **and `ledger_show`, `ledger_pending` and `ledger_add` become `test_show`, `test_pending` and `test_add`**; `tests.toml`'s `needs` becomes a bench; rows a person entered by hand stay possible, and **`test_add` makes one through Core's manual-verdict route** ([The verdict](#the-verdict)), so it is an entry in Core's run log first and the repo's row its mirror (review round 3, recommended). **`embarch/` stays untracked** until EmbArch is published and other engineers use it (owner, review round 1), so the report pins each definition file by its hash ([06](06-report-and-publish.md#the-audit-appendix)). **The ledger is not yet verified on a bench**, so nothing about it is a measurement yet.

## The report

**Published the same way as a Study** ([06-report-and-publish.md](06-report-and-publish.md)), **organised by requirement**: each verdict cites the run behind it. **A requirement passes when every one of its tests that ran passed** (owner, review round 1); its skipped tests do not block the pass and are listed under it with their reasons. **With no test of it run, it is `not verified`, never a pass. Otherwise its verdict is its tests' worst, in the severity order above**, skipped tests left out. A pass with tests skipped reads "pass, N of M tests run" (the `not verified` rule and this qualifier: review round 2, recommended).

- **It names the standard and the revision tested against**, as the engineer confirmed it, and each test's revision range, as a statement of conformity must (ISO/IEC 17025) (review round 3, recommended).
- **It lists every applicable test that did not run, and why**, from the skip reasons above, so a partial run never reads as full conformance; **the list is Core's signed selection** ([A run](#a-run), item 10) (review round 3, recommended).
- **It counts the standard, not only the selection**: the standard's requirements applicable to this role (with an atlas), those the suite has a test for, those selected, run and passed. **The suite's, the selection's and the run's counts are Core's; the standard's count comes from the atlas and is labelled as the atlas's**, an input, not Core's observation (review round 3, recommended).
- **It lists every run of each test on the same unit**, published or not, with its verdict, **from Core's run log**, grouped by DUT image and by test-definition hash, so a rebuild or an edited test does not hide the failures before it: a pass after four failures shows the four failures, and says which came before the firmware or the test changed (review round 2, recommended).
- **It carries a fixed statement**: pre-compliance evidence, **not a certification** by any standards organisation or certification programme (USB-IF's among them), and **not an accredited test report** (EmbArch is not an ISO/IEC 17025 laboratory).
- **It names the unit under test**: **the hardware ID Core reads off the chip**, which keys the run history, so no declaration can split one unit's failures from its passes; **where read-out protection blocks that read**, the history is keyed on the probe's enrolment and the declared serial, and every report of that unit says "unit identity not read: its history may be split"; the serial the engineer declares and its board revision beside it, a person's act (review round 2, recommended); **and who is responsible**: the person who gave the go and the person who published. **A token carries a scope, not a name**, so **the person's name is declared once in Core's store with the person's token**, and shown as declared; **a publish made with the agent's token reads "published by the agent"**, and becomes the person's when they approve it on the card (review round 3, recommended).

## Open

- **A partial run's requirement pass.** The owner's rule lets a requirement pass with tests skipped for a gap (a hook unmapped, a bench missing), shown as "pass, N of M tests run". Review round 2 rated that high for a client reading the report (G6): such a pass reads as covered. Kept as answered; for the owner to look at again.
- **Moving an existing ledger to `embarch/tests/`**: whether the first `test_*` call moves `embarch/ledger/` or reads both. To decide with the rename.
- **A safety check at definition** (review round 2, recommended): an energising step (an instrument output on, a bench board's power request) that follows a prompt asking a person to handle the bench is refused unless a clearance prompt stands between them. Consistent with the owner's "safety at authoring", since it is checked when the test is defined; not yet the owner's.
