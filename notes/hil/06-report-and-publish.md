# HIL notes: the report and publishing

**Status:** draft, 2026-11-15.

Shared by the Study and the Test: one publish mechanism, one zip shape, one audit appendix, one `verify`.

## Publish

- **An explicit step.** A finished run is a draft; **`publish <run id>`** (an MCP tool and a subcommand; renamed from `study_publish`, owner, review round 1) publishes it, a Study run or a Test run alike, a Test run as one zip for the whole run. **Choosing what to publish does not choose what the reader sees**: a report lists every run of the same test or study on the same unit, published or not, with its verdict (owner, review round 1), **read from Core's run log**, the repo's rows being its mirror, and grouped by DUT image and definition hash so a rebuild hides nothing ([03](03-test.md#the-report)) (review round 2, recommended). A pass after four failures shows the four failures. **The zip carries the log's segment for that unit**, so the list can be checked rather than trusted: every entry from the unit's first to the log's signed head, this unit's in full and every other by its hash and a hash of its unit key. **A Core's log starts once**: a new store, a reinstall or a new key writes a first entry naming the previous head where it is known, "log started anew" where it is not, and **every report states the log's key fingerprint, its first entry's date and its entry count, and that runs on any other Core, a development Core included, are not in it** (review round 3, recommended).
- **Two interop exports in every zip** (owner, review round 1): **JUnit XML**, the de-facto CI summary, and **OCP Test & Validation v2.0 JSON Lines** (MIT, under JSON Schema), the structured one ([11](11-prior-art.md#classical-hil-frameworks-formats-and-report-tooling)). **Neither is lossless; EmbArch's own record is.** **No verdict but pass maps to a passing outcome**; `skipped` maps to JUnit's `<skipped>`, which is not a pass but which most CI does not fail on, so a gate that must fail on a skip reads its reason. A requirement's `not verified` is carried in each of its tests' properties, since JUnit and OCP T&V have no requirement level (review round 2, recommended). **A qualified verdict keeps its qualifier in both exports**: "bench firmware unreleased" (or unverified, or flashed by the agent), "N of M tests run", "relayed" and the attestation label travel as JUnit properties and OCP T&V metadata on each test, and the run's own as properties of the suite and the run (review round 3, recommended):

  | Verdict | JUnit | OCP T&V status, result |
  |---|---|---|
  | pass | (no child) | COMPLETE, PASS |
  | fail | `<failure>` | COMPLETE, FAIL |
  | error | `<error>` | ERROR, NOT_APPLICABLE |
  | inconclusive | `<failure type="inconclusive">` | ERROR, NOT_APPLICABLE, verdict in metadata |
  | cancelled | `<error type="cancelled">` | ERROR, NOT_APPLICABLE, verdict in metadata |
  | skipped | `<skipped>` with the reason | SKIP, NOT_APPLICABLE |
- **One zip with everything**: the PDF report, the study file, `run.json` for a Test ([03](03-test.md#selecting-and-rerunning)), `events.json`, `measurements.json` ([02](02-study.md#measurements)), **Core's signed records of every test and study in it, and Core's signature over the manifest** ([12](12-prevention.md#what-core-then-guarantees-in-code)) (review round 2, recommended), **`report-data.json`**, the operator's notes, the prose files the agent wrote for the run, the hash manifest, and **every capture twice: the raw `.bin` (the evidence) and its CSV rendering (what a reader opens).** **It also carries `report.typ` and the Typst packages it used, so the PDF can be rebuilt from the zip alone**, with no repo and no network. **It is not for a repo.**
- **`report-data.json` holds every claim in the report that is not prose**: each test's and requirement's verdict with its qualifier, the per-verdict counts, the coverage counts, the tests that did not run and why, every run of each test on the unit, the unit's identity, who gave the go and who published, the fixed statement and the attestation label. **Core writes and signs it at publish**, from its run log and signed records, never embarch-api; the PDF's fixed sections and `report.typ` render those claims from it (review round 3, recommended).
- **What Core's signature covers, and what it does not.** At publish Core hashes every file it produced (captures, `events.json`, `measurements.json`, `run.json`, its records, `report-data.json`, the log segment) and signs the manifest only where those hashes are its own. **The files embarch-api made** (the PDF, the two exports, `report.typ`, the Typst packages, the prose, the notes) **are listed in the manifest as embarch-api's**: Core's signature says they were in the zip, and **their faithfulness rests on `verify`'s checks**, never on that signature (review round 3, recommended).
- **Written to a local folder set in embarch-api's configuration, with no default**: publish refuses until the folder is configured, and says how. Sending the zip anywhere else stays a human step. **Publish runs where the agent's embarch-api runs**, inside the container in the attested topology, so the folder and its zips are in the agent's reach: **a zip is trusted through `verify` and Core's log entry of its manifest hash, never through where it sits** (review round 3, recommended). **`report.typ` is compiled with Typst's root set to the run's staged files**, so it can read nothing else of the machine into the PDF or the zip (review round 3, recommended).
- **Named `<date>-<slug>-<id8>.zip`**: the date, the study's slug (a Test run's suite name), the first 8 characters of the run ID.
- **The operator's notes come in as a `notes` parameter**: the agent asks the person and passes their words verbatim. A UI form comes later. **Notes passed with the agent's token read "relayed by the agent"; notes typed on the card with the person's token read as the person's** (review round 2, recommended).
- **A publish is never overwritten** (owner, review round 1; *replaces "republishing overwrites"*). `publish` of the same run again writes **`-r2`**, then `-r3`, each naming the revision it supersedes and that revision's manifest hash; the earlier zips stay. **The manifest's own hash is also recorded outside the zip**, **in Core's run log**, signed, so a zip edited after publish is detectable without trusting the zip (review round 2, recommended).

## Verify

**`embarch-api verify <zip>`** (owner, review round 1), open source like the rest, so a client runs it with no trust in the machine that produced the zip. Its checks, in order (review round 2, recommended):

0. **The signatures**: Core's signature over the manifest and over each test's and study's record verifies **against a key fingerprint the client got from the engineer out of band**, never against the one the report prints, which is shown only to compare by eye; every capture, `events.json`, `measurements.json` and `run.json` in the zip is a subject of a signed record. **Attested means the key matches a fingerprint from Core's elevated install**, which the engineer hands the client with the zip; any other key, a development Core's included, verifies the zip's integrity and says **"origin unattested"**, whatever its record claims about itself ([12](12-prevention.md#the-root-of-trust-core-under-its-own-account)).
1. **The manifest**: every file's SHA-256 matches.
2. **The measurements**: every step-time number re-parsed from the raw replies with `run.json`'s patterns, and every derived measurement recomputed from the raw captures, **with the shared crate's version the signed records name**, matches `measurements.json`; a zip from a crate version `verify` lacks is reported as not recomputed, never as matching.
3. **The verdicts**: every verdict recomputed from `run.json`, the step outcomes in `events.json` and the measurements matches the signed records and `report-data.json`, the requirement roll-up included; **the run's signed record accounts for every test `run.json` selected**, by a test record or a signed reason for its absence ([03](03-test.md#a-run), item 10) (review round 3, recommended).
4. **The PDF's text**: every number in the rendered PDF matches a signed measurement, is listed in the appendix (untagged, tagged or hardcoded), or sits in an exempt context ([02](02-study.md#the-report)). So the PDF, which embarch-api assembles, cannot carry a number the signed data does not. **Citations and tags are checked in the sources**, the prose files and `report.typ` the zip carries, rescanned for each number's citation and tag, since a PDF's text keeps neither (review round 3, recommended).
5. **The labels**: the attestation line on the report's first page and each person's act's attribution match what the signed records say.
6. **The report's other claims**: `report-data.json` recomputed from the signed records and the log segment matches its signed copy, and **every verdict word, count, run listed, label and the fixed statement the PDF prints matches it** (review round 3, recommended).
7. **The exports**: JUnit XML and OCP T&V regenerated from the signed records match the zip's, so CI never reads a verdict the records do not hold (review round 3, recommended).
8. **The log segment**: the chain recomputes from the segment's first entry to the signed head, and **every entry keyed on this unit is in the report's list of runs** (review round 3, recommended).

**What `verify` cannot recompute**: what Core read from the hardware, the identities, the image readback, an instrument's `*IDN?`, a bench board's reported version. For those it checks Core's signature, and the report says they rest on Core. It answers each check with what it compared, and names the embarch-api version that produced the zip and the one that verified it. **This is what lets a reader check the report without trusting the agent** ([09](09-trust-model.md)): measurements and verdicts are pure functions of files the zip carries, and the files are Core's.

## The report

- **Rendered by embarch-api, to PDF, with Typst built into the binary**: no external tool to install, plots drawn as SVG and embedded. The Typst version is recorded in the appendix, since output depends on it. **The stack** (owner, review round 1): the `typst` and `typst-pdf` crates (Apache-2.0) through `typst-as-lib` (MIT), packages vendored under a local root so no registry is contacted, **plots with lilaq (MIT), not cetz (LGPL-3.0)**, `PdfOptions.ident` and `timestamp` set for stable re-renders.
- **A plot over a large capture draws per-bin min and max, never an average**, as the UI's series route already does ([embarch-ui interfaces](../../embarch-ui/interfaces.md)); the raw file in the zip holds the detail.
- **A Study's body is its own `report.typ`**, free in shape, compiled against the run's measurements and files ([02-study.md](02-study.md#the-report)).
- **A Test's body is organised by requirement**: each verdict cites the run behind it; **every applicable test that did not run is listed, with why**; the standard's own coverage is counted; the unit and who is responsible are named; and **a fixed statement says it is pre-compliance evidence, not a certification and not an accredited test report** ([03-test.md](03-test.md#the-report)).
- **Each prose block names its author**, `agent (<model id>)` or a person, and **every untagged number in prose that matches no measurement is listed** in the appendix ([02](02-study.md#the-report)).

## The audit appendix

**Appended by embarch-api to every report; a study cannot leave it out.**

| Item | What it holds |
|---|---|
| **Observed by Core** | The DUT image's SHA-256 as Core flashed it, and **whether the chip holds it** by readback, or why that is a claim ([03](03-test.md#a-run)); each bench board's image against EmbArch's released firmware, and its reported version; the unit's and every board's identity; Core's build and key fingerprint; the shared crate's version |
| **Claimed by the build** | The git branch, commit and **whether the tree was dirty**, the toolchain, the build host: what embarch-api reports, in the agent's reach, so labelled a claim (review round 2, recommended) |
| **Pinned inputs** | The study file's hash, and for a Test `run.json`'s, the plan's and the suite's version and commit; embarch-api's build; the Typst version; the lease holder |
| **Attestation** | **Which held for the person's acts, as Core observed it**: "person-scoped token", "passkey" or "agent-scoped only"; the engineer's statement that the agent ran in a container, labelled as the engineer's statement, since Core sees a token's scope and not where the agent ran (review round 2, recommended); **that statement is a person's act kept in Core's store**, shown with its date; **with the passkey, the label lists which acts a touch signed** and which went with the token alone (review round 3, recommended) |
| **Definition files** | Each definition the run read (study, test, plan, bench) by its hash, since `embarch/` is untracked ([03](03-test.md#it-grows-out-of-the-ledger)) |
| **Instruments** | Each instrument's `*IDN?` reply, read at the smoke check, and its calibration due date and its uncertainty as the engineer declared them (**a person's act**, refused with the agent's token, and carried into Core's signed record (review round 2, recommended)), **checked against the date of each measurement it made** (a long or resumed run can cross a due date) (review round 3, recommended): a verdict resting on a measurement from an instrument past its due date is **inconclusive**, reason "calibration expired" (review round 2, recommended); an undeclared date is shown as undeclared beside every measurement it touches. **A calibration declaration names the instrument's serial and its certificate reference**, and a declaration whose serial differs from the `*IDN?` reply is not applied; **a bench board's characterisation carries a date and a validity period**, checked the same way (review round 3, recommended). Each bench board's characterisation, where it times or measures |
| **Measurements** | Every measurement: value, unit, resolution, uncertainty, `by`, the instrument or board and its `bench_image`, and the capture file and rows it came from |
| **Decision rule** | Simple acceptance or a guard band, per limit ([03](03-test.md#the-verdict)) |
| **Limits and losses** | Truncated captures, dropped records, overrides such as `--allow-version-mismatch`, inconclusive verdicts and why, and what is measured against what is assumed |
| **Inputs and their provenance** | For a Test, each DUT capability (`measured`, `decoded`, `confirmed`, `declared`), each hook mapping, and who confirmed each |
| **The study design** | The study as submitted, and a readable list of its steps, taps and checks; for a test copied from a premade one, its `derived_from` and every verdict-deciding field changed |
| **Every run** | Every run of the same test or study on the same unit, from Core's run log, grouped by image and definition hash, with its verdict and whether it was published |
| **Prose** | Each block and its author, and the token that entered it; every untagged, tagged and hardcoded number ([02](02-study.md#the-report)) |
| **Plots** | Each plot cites the file it was drawn from |
| **Operator and setup notes** | Who ran it, which bench, cables and fixtures, conditions: typed in by the person at publish time; each prompt's answer, its kind, and **the token's scope it came with** (person, or relayed by the agent) beside the surface (`ui`, `mcp`, `cli`) (review round 2, recommended) |
| **Hash manifest** | SHA-256 of every file in the zip, and the revision it supersedes |

**The DUT's firmware version is a claim unless it was read back**: without the readback, nothing reads it off a DUT, so it means "this run built and flashed this tree" ([studies guide §2](../../suite/studies-guide.md)). The appendix says which, in those words.

## Open

- **A zip's own size**: a long capture is in it twice, raw and rendered. No limit decided; measure on the first real Study.
- **How a plot drawn by EmbArch's helper is marked in the PDF**, so `verify` can tell its axis ticks from a number in the text.
- **Whether `typst-pdf` renders byte-identically** across machines; `verify` does not depend on it, since it checks the PDF's numbers, not its bytes.
