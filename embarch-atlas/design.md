# embarch-atlas: design

**Status:** active, 2026-11-23. This doc is the source of truth for the decisions it states below; the `embarch-atlas` repo's `DESIGN.md` (a long working draft, dated 2026-09-30, which still says it will move here) carries the detail each section points at, and it is the code's own reference. The repo is public on GitHub. The human surface is [embarch-ui decisions 52-54](../embarch-ui/decisions/atlas-tab.md).

**[`research/`](research/) is still raw intake, not folded:** the landscape survey (five notes, 2026-09), findings and not decisions, deleted once the design that consumes them is written; [its README](research/README.md) records the scope the survey was run under. The repo has its own `research/` of document-pipeline notes, separate from this one. See [embarch.md](../embarch.md) §2 for the suite lineage (the original `gabrieltetar/embarch` C#/WPF static-analysis GUI) and §3 for its one-line purpose. [suite/roadmap.md](../suite/roadmap.md) says where it sits in the suite's plan.

## Which image the build describes

`embarch-atlas build` pins an atlas to one image's `edt.pickle` and `.config`. Under a multi-image sysbuild (application plus MCUboot) that is the application's, chosen by `domains.yaml` `default:`, else by the app directory's name, else the build fails naming the pickles it found. `build` and the Kconfig extraction choose through one function (`kconfig.image_dir`), so the two never describe different images. A build dir the caller names (`config --build`, `dt_node`) passes the app the atlas was built for, read from the atlas stamp, so it picks the same image `build` did. The detail is in the repo's `DESIGN.md`.

## Which families' pin use `join` decodes

`dt.json` holds devicetree pin use (pinctrl states, GPIO phandles, GPIO-routed interrupts) for two families: STM32 (`pinmux`, controllers `gpio[a-z]`, pins `PA4`) and Nordic nRF (`nordic,nrf-gpio` controllers by `port` or label digit, pinctrl `psels` through the `NRF_PSEL(fun, port, pin)` encoding with pull from `bias-*`, pins `P0.04`). `pin_decoder` records which; for any other family it is null, the pin map's DT column is empty, and `checks.md` says the pin-level checks had no input instead of listing them as run. On Nordic targets `dt-no-driver` folds the SoC infrastructure nodes nrfx drives without a Zephyr device (DPPIC, PPIB, MPC, UICR, GPIOTE) as expected.

## Firmware configuration against a standard

A standard's requirement record may carry a `fw_check`: inputs read from the build's devicetree and Kconfig and from values the engineer declares in `atlas.toml` (`[standards."<doc_id>"]`: a port's maximum power, which node is which port), a guard, and an expression. `join` evaluates each against the pinned build, and `mismatch_report build=<dir>` against another; a failure is a `config-vs-standard` candidate citing the requirement's page and the file:line that set the value. The first decode helpers are USB PD's (a PDO or APDO word to its type, voltages and currents). The rule is in the repo's `DESIGN.md`, "Firmware configuration against a standard".

## Measuring a lookup against recorded sessions

`scripts/replay.py` in the `embarch-atlas` repo scans a project's Claude Code transcripts for the shell calls a lookup replaces (a table of named patterns: `grep` over a `.config`, `diff` of two such greps), re-runs each read-only against the current build dir, runs the mapped lookup with its pages followed against a temporary copy of the atlas dir, and prints calls and characters before and after, numbers only. It is not a CLI verb or an MCP tool, because it reads private transcripts; it never executes a recorded command, only an argument vector rebuilt from a matched pattern. The rule is in the repo's `DESIGN.md`, "The replay harness".

## Pages of any PDF as images

`pdf pages <file> [--pages 4-7] [--dpi 80] [--tiles COLSxROWS] [--crop X,Y,W,H] [--out dir]` renders a page range of any PDF, with or without a text layer, to PNGs in a scratch directory the image `Read` tool opens at its default settings. It needs no atlas and no imaging library, only poppler (`pdfinfo`, `pdftotext`, `pdftoppm` with its `-x -y -W -H` crop). Per page it first prints whether a usable text layer exists (at least 40 non-space characters), so a caller reads `pdftotext` when it can, then one line per PNG: page, tile, pixel size, path. `--crop` is in PDF points from the displayed page's top-left; tiles divide the crop evenly, the last column and row taking the remainder. Not an MCP tool. Detail: the repo's `DESIGN.md`.

## Web page or PDF as text

`fetch-text <url|file> [--json]` turns an http(s) URL or a local HTML or PDF file into plain text: scripts, styles and tags removed, entities unescaped, whitespace collapsed (standard-library `html.parser`, no new dependency). A bot challenge, captcha or rate-limit page (HTTP 403/429/503 with a short body, or a short page carrying a known interstitial phrase) is never printed as content: exit 3, `blocked: true` on stderr, or in the `--json` result. A PDF reuses `pdf pages`' poppler helpers (`pdftotext`). Not an MCP tool. Detail: the repo's `DESIGN.md`. It is the atlas's one network call, a standalone research verb outside the document pipeline: nothing it fetches is distilled or enters the library, so it does not reopen the owner's 2026-11-17 rejection of an opt-in fetcher inside the pipeline (owner decision 2026-11-18, EMB-208).

## Strain-budget derive helper

`derive strain-budget <file.toml|json>` (`src/embarch_atlas/strain.py`) turns a load case (force with lever arm, or a moment; optional axial force and torque), a section (solid round, round tube, rectangular flexure), a material and a bridge readout (gauge factor, quarter/half/full, excitation, ADC noise as a density with bandwidth or as rms) into section modulus, second moment, bending, axial and torsional strain, a tube's inner-wall strain, tip deflection, bridge output per microstrain, the noise-limited resolvable strain and the SNR. Every row is `(derived)` and names its textbook formula; every input carries its unit as text and a missing or wrong unit is refused with one line. **It is a standalone helper outside the build and the pipeline**: it reads no atlas, no document and no netlist, so the pipeline above has not grown a mechanics model, and it is a CLI verb only, not an MCP tool (the lookup count stays twenty-three). Not modelled, and named in its output: stress concentration, shear deflection, the Poisson-ratio gain of a transverse gauge pair, gauge nonlinearity, temperature, bridge imbalance, torque on a rectangular section. Detail: the repo's `DESIGN.md`.

## Transport

**Settled: `embarch-atlas` is its own MCP server, not a tool on `embarch-api`'s surface.** `embarch-atlas mcp` serves the lookups over stdio (`src/embarch_atlas/mcp_server.py`, the optional `mcp` extra in `pyproject.toml`) and is registered per project in `.mcp.json`. The repo shows that the engine is Python (`requires-python >= 3.12`), while `embarch-api` is Rust and gains no dependency on it; no document records a deliberation beyond that, so this section records the outcome, not a reasoning. The cost the earlier open question named, a second server for a client to register, is the one taken. Nothing about the transport remains open.

## A target with no Zephyr board yet

A target may state `no_board = true` in `atlas.toml` when its PCB has no Zephyr board; a forgotten `board` still fails. `build` then writes an atlas pinned to the target and firmware commit whose stamp says there is no build and why, with no worktree and no west build, and `join` runs every step that reads no build artifact. `status` and `MAP.md` name each output that is absent for that reason (the build artifacts, `kconfig.json`, `dt.json`, `in_use.json`, `codecheck`, `limits`, the RM worklist, and the `config`, `dt_node`, `footprint`, `stacks`, `code` and `states` lookups, which answer that the target has no board yet) and each that is reduced (pin map, checks, MAP, graph, `register`, the second-look queue). A normal `build` supersedes it once the board exists. The rule and the per-output list are in the repo's `DESIGN.md` under principle 6 and "A target with no Zephyr board yet".

## Bumping when HEAD moves

Opt-in: `embarch-atlas hook install <target>` writes `post-commit`, `post-checkout`, `post-merge` and `post-rewrite` blocks that start a detached worker; it waits until HEAD has been quiet and no rebase or merge is in progress, then runs `update` under the bump lock (a second bump is refused). Every bump records its outcome in `bump/state.json`, so a stopped or failed one (a translation behind its source, a west workspace off its manifest, a build failure) says why on the MAP's stale line and every `src:` line, and the previous atlas answers until the new one has joined. The hook never runs a second look; `second-look queue --used` batches the backlog's facts that sessions' answers returned. A session may invoke the skills that build or update an atlas (owner, 2026-11-10). Detail: the repo's `DESIGN.md`, "Bumping when HEAD moves".

## Standards and specifications

A `standard` (a bus, protocol or power specification, an IEC/IEEE/JEDEC standard) binds a role, not a part: the join never ties it to a board part, and MAP.md lists it under "Other documents". It is distilled lazily, as the reference manual is: only the sections in its `worklist.json` (`embarch-atlas doc sections <doc> --add <sec> --why <text>`), chosen by the engineer or from measured use (`doc sections --suggest` ranks the sections sessions' `find_text` and `doc_section tier=text` lookups landed in). A frozen section is never redone. Check W holds a requirement's modality to the normative keyword in its quote. Detail: the repo's `DESIGN.md`, "Standards and specifications".

## Protocol records

A standard's applicability tables are one `applicability` record per cell (item, role, condition, initiator or responder, the level as printed), and a state machine written one subsection per state is `state` and `transition` records checked against its state diagram. The `applies` lookup answers what a role must support, and `transitions` what a state does and which states react to a message or timer; the same kinds fit a datasheet's state machine. The fields, checks L and E, and both lookups are in the repo's `DESIGN.md`.

A part with no register map (firmware sends a command, waits, reads a fixed frame) is a `frame` record for the reply's layout (byte by byte, each status bit and the one count) and a `transfer` record per variant of the count's conversion to the physical value. `q decode <DT label> <hex bytes>` (and the `decode` MCP tool, the twenty-first lookup) decodes bytes the engineer already read: each status bit by name, the count in decimal, and the value from the datasheet's transfer function with the board's range and unit read from the part's devicetree node, pages cited. A count outside the range is reported as the number the equation gives (negative below the minimum) and said to be out of range, never clamped, because that is what a driver's own reading hides. It sends nothing to the board, and a part whose layout or transfer function is not distilled, or whose node lacks a property the function needs, gets an answer naming what is missing, never a guessed layout. The record fields are in the repo's `DESIGN.md`.

`q rc_timing <board>:<net>` (MCP `rc_timing`, the twenty-second lookup; `src/embarch_atlas/rctiming.py`) gives the worst-case time range for one node of a single series R and C to cross the receiving pin's guaranteed VIH (charging from 0 V, `t = tau * ln(V / (V - Vth))`) or VIL (discharging from the rail, `t = tau * ln(V / Vth)`), over the R and C tolerances from `bom.json`, the rail's range from its regulator's VOUT `limit` record, and the receiving part's VIH or VIL record. Each input is cited to its record or BOM line, or named ASSUMED (a tolerance the caller passes, a capacitor's EIA temperature class from its description); no margin is added unless passed, and then it is printed beside the result. Any other network, and any missing tolerance, regulator or threshold fact, is named and never approximated. Full contract in the code repo's `DESIGN.md`.

`q shell-commands [<root>]` (MCP `shell_commands`, the twenty-third lookup; `src/embarch_atlas/shellcmds.py`) lists the Zephyr shell commands the pinned build's image has, so a session no longer works them out with throwaway scripts over the ELF and `compile_commands.json`. It reads `zephyr.elf` alone, never the sources: a subcommand its Kconfig compiled out is absent, because only the image says what is in it. A root's table gives each subcommand's mandatory and optional argument counts, help text (Zephyr 4.4's structured `SHELL_HELP` description, with its usage; a help pointer that is not printable text gives none, never bytes) and the source file and line of the table; sets added with `SHELL_SUBCMD_ADD`, like `kernel`'s, are listed too; a dynamic set names its getter and, for the device list, the image's devices. `build` writes it as `shell.json` beside `kconfig.json`; it records the ELF's modification time and the answer says STALE when the ELF changed since. A build with no shell gets an inventory saying so. It does not feed `live.py`'s read-only shell allowlist, which stays as it is: deriving it from a build could widen what runs on a board unasked. Detail in the code repo's `DESIGN.md`.

The live tools (`shell`, `shell_run`, `reg_read*`, `live_stacks`, `core_state`) take an optional `lease_token`, the value embarch-api's `lease_take` returned, so a session that holds the bench lease can use them without releasing it: the atlas MCP server's environment was fixed at start, so exporting `EMBARCH_LEASE_TOKEN` cannot reach it. The token goes to the `embarch-api` CLI's environment for that call only and is scrubbed from every failure text; a `409` naming the lease makes `shell` answer "the command did not run", since Core refused before it opened a port. Detail in the code repo's `DESIGN.md`.

## A cite of another document rests no frozen unit

`doc freeze` keys a unit on the pages it cites in its own document. A cite that names another document (`other-doc p.7`) is left out of those pages, by the same test check M uses to tell the two apart (`check.split_cites`, `find_sibling`); a unit that cites only other documents rests on every page. The other choice, filing the page under the other document, would need a second set of page hashes and a second `thaw-check` rule, since `thaw-check` reads only its own document's pages (2026-11-13, EMB-109). The detail is in the repo's `DESIGN.md`.

## A shared datasheet library, and a copy of every file an atlas read

`[project] library` in `atlas.toml` names one local folder the engineer fills by hand, outside any firmware repo. `inventory` reads it beside the sources folder and `missing` re-reads it once the boards' parts are known; a library file enters the manifest only when tied to a board part or the MCU role (the others serve other projects), and the sources folder's file wins an identical one. `doc prep` and `schematic` copy the file they read to `files/<sha256>/<name>` in the atlas directory and `doc.json` `path` names the copy, so a replaced or deleted original changes nothing already built. The tool never writes into the library and never fetches a document it distils (`fetch-text`, above, is outside the pipeline). Owner decision 2026-11-17; the detail is in the repo's `DESIGN.md`, "Where documents come from". **Left open:** no test drives the schematic ingest's copy or a board PDF kept only in the library (no synthetic Smart PDF exists), a schematic's `source_file` still names the original, and `join` and `build` do not refresh the manifest, so a library file is tied only at the next `inventory` or `missing`.

`net_find` lists every net whose name matches a pattern (a case-insensitive substring, or a glob when it holds `*`, `?` or `[`) across all boards, one line per net as `<board>:<net>  <ref-pin> ...`, sorted by board then net; `board=` narrows it. It is the nineteenth lookup and the second one that reads the netlists directly: `net_trace` takes one exact name, so a bus family used to cost a script over `boards/<B>/netlist.json`. Registered read-only on the MCP server. The reasoning is in the repo's `DESIGN.md`, "Query surface".

`parts <board> <ref>...` returns one line per reference: MPN, value, tolerance, rating (voltage and power) and DNP flag, and the net on each pin, then the references not found on the board. It is the twentieth lookup, reads `boards/<B>/bom.json` and `netlist.json` directly (no atlas needed) and is read-only on the MCP server. `schematic` stores `tolerance`, `voltage` and `power` on every BOM record, from a dedicated schematic parameter when there is one and otherwise from the description (`RES SMD 86.6K OHM 1% 1/16W 0402`), and records `null` (shown `unknown`) rather than guess when neither carries them; `parts.md` rows show a known tolerance as `tol=<x>`. The parsing rules are in the repo's `DESIGN.md`.

## Reading an Altium project's sources: `cad`

`embarch-atlas cad <project dir | .PrjPcb> [--rev <commit>] [--variant <name>] [--json]` reads a project's `.SchDoc` sheets (the ones its `.PrjPcb` lists, not a directory glob) through `olefile`, an optional extra, and prints components (designator, part number, value, unique ID) and per-pin nets; with `--variant` it lists the parts that variant does not fit, matched by unique ID, and any variation whose unique ID is no longer in the schematic. `--rev` reads every file with `git show` and checks nothing out. The output has `netlist.json`'s shape with `method: "altium-schdoc"` so a later unit (`tasks/atlas/083`) can compare it with a PDF-built atlas. It is ladder rung 1 used as a read-only cross-check: it writes no atlas state, feeds neither `schematic` nor `join`, and is a CLI verb only (the lookup count stays twenty-three). **Verified only on synthetic projects**: the record layout beyond the kinds the issue names (length prefix, coordinates, pin ends, parameter names, variant keys) is nine assumptions the repo's `DESIGN.md` lists, none checked against a real `.SchDoc`. The owner-side debt is one run on a real project. Detail: the repo's `DESIGN.md`, "Native EDA project".

`embarch-atlas board-diff --cad <project> --board <label> [--rev] [--variant] [--json]` is the second half: it compares that read with the `boards/<label>/netlist.json` an atlas built from the same project's PDF and reports parts on one side only, part-number or value differences, pins on one side only, pins on another net, and a net renamed after release (same pins, new name) as a name-only difference. Names match through the joined board nets and their `aliases`, never per sheet. A net the PDF left auto-named that the CAD names is reported as named by the CAD, not as a difference. With `--variant` the parts the variant does not fit are listed against the PDF's all-fitted view on their own line and do not count toward the exit code. Exit 0 when nothing differs, 1 when something does, 2 on a refusal; it writes no atlas state and is a CLI verb only (the lookup count stays twenty-three). Detail: the repo's `DESIGN.md`, "`board-diff`".

## Which package's pinout `net_trace` reads

When a part's datasheet distils several package pinouts, `net_trace` and the rest of the join read the pin records of the package the board fits, never the first (EMB-236; decision 2026-11-23, atlas/091). The package is the engineer's `bindings.json` `packages` entry, else inferred in order from the netlist component's `footprint`/`package` text naming exactly one package, the schematic's pin names agreeing with exactly one package and contradicted by none, or the pin count matching exactly one. Inference is a heuristic: the netlist writers do not emit a footprint yet, so in practice names and pin count carry it. A part none of these singles out shows the schematic pin name with "package not resolved" and a reason, and feeds nothing upstream. Detail: the repo's `DESIGN.md`, `pin` records. **Left open:** the exact GND-for-OUT misread the issue reported was not reproduced; an unresolved package already yielded no record before this change, now it says why.

## Where a pad's port comes from

A module's pad number is not the SoC's pin number, so a pad the symbol leaves unnamed took its port from a net named after it or from nowhere (EMB-237, atlas/092). The module datasheet's `pin` records now carry an optional `port`: the SoC port behind the pad. `build_pin_map` (`join.py`) takes a pad's port from the symbol's pin name, then that `port` (`port_source` `module pad table`), then the datasheet's pin number, then a net named after the port; the DT use follows from whichever gives one (EMB-243, atlas/094). The symbol wins over a disagreeing pad table, and `pins.json` `port_conflict` says so. The datasheet procedure now tells the translator to write `port` per pad of a module's pad table in the form `build_pin_map` reads, and the record schema's `port` pattern rejects a malformed one (EMB-245, atlas/096). Tested on synthetic records only: no real module datasheet translation was checked.
