## Which image the build describes

`embarch-atlas build` pins an atlas to one image's `edt.pickle` and `.config`. Under a multi-image sysbuild (application plus MCUboot) that is the application's, chosen by `domains.yaml` `default:`, else by the app directory's name, else the build fails naming the pickles it found. `build` and the Kconfig extraction choose through one function (`kconfig.image_dir`), so the two never describe different images. A build dir the caller names (`config --build`, `dt_node`) passes the app the atlas was built for, read from the atlas stamp, so it picks the same image `build` did. The detail is in the repo's `DESIGN.md`.

## Which families' pin use `join` decodes

`dt.json` holds devicetree pin use (pinctrl states, GPIO phandles, GPIO-routed interrupts) for two families: STM32 (`pinmux`, controllers `gpio[a-z]`, pins `PA4`) and Nordic nRF (`nordic,nrf-gpio` controllers by `port` or label digit, pinctrl `psels` through the `NRF_PSEL(fun, port, pin)` encoding with pull from `bias-*`, pins `P0.04`). `pin_decoder` records which; for any other family it is null, the pin map's DT column is empty, and `checks.md` says the pin-level checks had no input instead of listing them as run. On Nordic targets `dt-no-driver` folds the SoC infrastructure nodes nrfx drives without a Zephyr device (DPPIC, PPIB, MPC, UICR, GPIOTE) as expected.

## Firmware configuration against a standard

A standard's requirement record may carry a `fw_check`: inputs read from the build's devicetree and Kconfig and from values the engineer declares in `atlas.toml` (`[standards."<doc_id>"]`: a port's maximum power, which node is which port), a guard, and an expression. `join` evaluates each against the pinned build, and `mismatch_report build=<dir>` against another; a failure is a `config-vs-standard` candidate citing the requirement's page and the file:line that set the value. The first decode helpers are USB PD's (a PDO or APDO word to its type, voltages and currents). The rule is in the repo's `DESIGN.md`, "Firmware configuration against a standard".

## A target with no Zephyr board yet

A target may state `no_board = true` in `atlas.toml` when its PCB has no Zephyr board; a forgotten `board` still fails. `build` then writes an atlas pinned to the target and firmware commit whose stamp says there is no build and why, with no worktree and no west build, and `join` runs every step that reads no build artifact. `status` and `MAP.md` name each output that is absent for that reason (the build artifacts, `kconfig.json`, `dt.json`, `in_use.json`, `codecheck`, `limits`, the RM worklist, and the `config`, `dt_node`, `footprint`, `stacks`, `code` and `states` lookups, which answer that the target has no board yet) and each that is reduced (pin map, checks, MAP, graph, `register`, the second-look queue). A normal `build` supersedes it once the board exists. The rule and the per-output list are in the repo's `DESIGN.md` under principle 6 and "A target with no Zephyr board yet".

## Bumping when HEAD moves

Opt-in: `embarch-atlas hook install <target>` writes `post-commit`, `post-checkout`, `post-merge` and `post-rewrite` blocks that start a detached worker; it waits until HEAD has been quiet and no rebase or merge is in progress, then runs `update` under the bump lock (a second bump is refused). Every bump records its outcome in `bump/state.json`, so a stopped or failed one (a translation behind its source, a west workspace off its manifest, a build failure) says why on the MAP's stale line and every `src:` line, and the previous atlas answers until the new one has joined. The hook never runs a second look; `second-look queue --used` batches the backlog's facts that sessions' answers returned. A session may invoke the skills that build or update an atlas (owner, 2026-11-10). Detail: the repo's `DESIGN.md`, "Bumping when HEAD moves".

## Standards and specifications

A `standard` (a bus, protocol or power specification, an IEC/IEEE/JEDEC standard) binds a role, not a part: the join never ties it to a board part, and MAP.md lists it under "Other documents". It is distilled lazily, as the reference manual is: only the sections in its `worklist.json` (`embarch-atlas doc sections <doc> --add <sec> --why <text>`), chosen by the engineer or from measured use (`doc sections --suggest` ranks the sections sessions' `find_text` and `doc_section tier=text` lookups landed in). A frozen section is never redone. Check W holds a requirement's modality to the normative keyword in its quote. Detail: the repo's `DESIGN.md`, "Standards and specifications".

## Protocol records

A standard's applicability tables are one `applicability` record per cell (item, role, condition, initiator or responder, the level as printed), and a state machine written one subsection per state is `state` and `transition` records checked against its state diagram. The `applies` lookup answers what a role must support, and `transitions` what a state does and which states react to a message or timer; the same kinds fit a datasheet's state machine. The fields, checks L and E, and both lookups are in the repo's `DESIGN.md`.

## A cite of another document rests no frozen unit

`doc freeze` keys a unit on the pages it cites in its own document. A cite that names another document (`other-doc p.7`) is left out of those pages, by the same test check M uses to tell the two apart (`check.split_cites`, `find_sibling`); a unit that cites only other documents rests on every page. The other choice, filing the page under the other document, would need a second set of page hashes and a second `thaw-check` rule, since `thaw-check` reads only its own document's pages (2026-11-13, EMB-109). The detail is in the repo's `DESIGN.md`.
