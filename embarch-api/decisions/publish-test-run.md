### 144 - `publish` takes a Test run's id too: one zip, a PDF organised by requirement, and no notes, prose or `report.typ`

**Telling the two apart.** `publish::run` asks Core `GET /test-runs/{id}` (`CoreClient::is_test_run`, a `404` is "not a Test run") **after** every local refusal of a Study's `report.typ` and **before** it sends anything else; a Test run goes to `publish_test::run`, a Study continues unchanged. One function still stands behind the tool and the subcommand (112). **[Assumed]:** a run id is never both a Study's and a prepared Test run's, since Core mints both from one id space.

**The calls** are the Study's over Core's three Test routes (core 148 to 150): `POST /test-runs/{id}/report-data`; `report-data.json` and `run.json` fetched at the pending revision (the PDF reads those two and nothing else); the PDF rendered; `POST .../publish` with the hash of each file made here; the manifest, then every subject, each checked against its digest. What the PDF read must equal what Core signed, `report-data.json` and `run.json` both, or nothing is written. **The shared crate gained four additive methods**, no existing type changed: `is_test_run`, `test_report_data`, `test_publish`, `test_publish_file`.

**The zip** is the manifest's subjects as Core serves them (each study run's files under `studies/<study_id>/`, `run.json`, `result.json`, `test-run.dsse.json`, `report-data.json` and its envelope, the run-log segment, the call-log segment when named) plus `manifest.dsse.json` and five files of this crate's: `report.pdf`, `report.typ`, `appendix.typ` and the two exports ([145](publish-test-export.md)). It is named `<date>-<suite id slug>-<id8>[-r<N>].zip` and never overwritten (112). **Nothing is built from an earlier zip:** Core refuses a swept Test run and does not restore it (core 149), so a revision rebuilds from Core and only reads the earlier manifest's hash for the appendix.

**The PDF is generated, never a Test's own.** It is Typst source whose every value is a string literal (114), from `report-data.json` alone: the fixed statement as Core wrote it (a data file with none is refused, so a report never prints without it), the run, suite and overall verdict, the unit and who gave the go and published, each requirement with its verdict, counts, qualifiers in words (`n_of_m_run` as "3 of 5 tests run", from the `{n, m}` beside it in the study designer's roll-up) and the tests skipped under it with their reasons, each test citing the run and study runs behind it, the tests that did not run, every run of each test on the unit with its verdict, **a failed one included**, and the roll-up rules. The appendix is the Test's own: Core's observation (call log as a Study's), `run.json`'s SHA-256, the plan hash `run.json` carries, the suite, the attestation, the manual verdicts, what is not carried, the manifest and the revision superseded.

**A Test run takes no `notes`, `prose` or `report`:** Core has no `adopt` route for one, so they are refused by name before Core is asked anything. **Not done, each stated in the appendix or here:** a resumed pair (EMB-370 is not built; core 149 says it will publish as one zip, and this publishes one run); **the decision rule per limit**, since `report-data.json` carries the roll-up `rules` and no limit or guard band, so the PDF says so instead of inventing them; `verify` of a Test zip (EMB-382); the standard's requirement count (core carries none).

**Measured:** against a mock Core, a fixture Test run with two requirements, one `not_verified` for a test skipped as `requires_not_met`, one `pass` qualified "bench firmware unreleased" with "3 of 5 tests run" and a test with an earlier failed run: every Core file is in the zip byte for byte, the hashes sent are the zip's own, the PDF text holds each of those and the statement. **Not run:** a real Core, a real Test run, `verify` on the zip.
