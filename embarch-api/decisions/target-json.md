### 19 — A readable build-dir prefix, a `target.json` beside the output, and a hash this crate owns
`extra_args` folds into the directory name via a hash, since an arbitrary flag can contain directory-unsafe characters — but **a bare hash makes a directory listing undebuggable to a human staring at it**. Two additions without touching the hash: every other axis spelled out ahead of it, and a `target.json` recording the full resolved selection, so `cat target.json` recovers exactly what produced that directory.

**The hash itself moved to a crate-owned FNV-1a on 2026-09-05**, from `std::collections::hash_map::DefaultHasher`, whose output the standard library documents as free to change between Rust releases. A build-directory name is a key a *later run* recomputes to find its own cache, so the one thing it may not depend on is the toolchain that compiled the binary. Nothing would have failed loudly: a bump renames every `-args*` directory, the next build misses its cache and builds beside the old one, and the old one becomes an orphan no selection reaches and [`embarch-umbrella` decisions](../../embarch-umbrella/decisions/projects.md) 26 forbids pruning, because it still belongs to a *valid* target — the worst orphan shape there is, one `rustup update` away. Found by doctor check 16 counting per-target build directories, not by anything breaking. Three calls:

- **FNV-1a spelled out in `zephyr.rs`, not a keyed SipHash and not a dependency.** `extra_args` comes from this machine's own config, never an untrusted caller, so there is no hash-flooding threat to answer — only accidental collision over a few short flags, which 64 bits cover; and a key is one more thing to keep in step with names already on disk. *Rejected: a sanitised non-hash spelling* — it keeps this entry's readable-listing property, but an arbitrary flag has no length bound and its escaping is a second thing to hold stable, while `target.json` already answers "what produced this directory" better than a name can.
- **The encoding length-prefixes each argument**, so `["-p", "always"]` and `["-p always"]` cannot collide the way a plain join lets them.
- **A test pins the hash to a hard-coded literal** (`build_dir_name_args_hash_matches_a_hard_coded_literal`). That is the whole point: the pre-existing test asserted stability *within one process*, which `DefaultHasher` satisfied perfectly while renaming everything on upgrade. If the new one fails, the fix is almost never to update the literal.

**Directories already named by the old scheme are orphaned by this change, deliberately and once.** No migration, and none is soundly buildable: recomputing an old name means reproducing the `DefaultHasher` output of whichever toolchain wrote it — the one value this crate cannot know. So the choice was one orphaning now, at a known moment, with an entry saying so, against an unbounded number later, silently. Blast radius: only projects passing `extra_args`, only those built before this date; every other name is byte-identical across the change. Those directories are safe for a **human** to delete and still off-limits to `doctor --prune` (decision 26) — and they carry no `target.json` either, since that shipped the same day, so from the outside they are indistinguishable from any other unattributable directory.

**The file is written as of 2026-09-05, and was stated as current truth for three months before that** — [../interfaces/config.md](../interfaces/config.md) described it as behaviour while a `target.json` grep over the whole crate matched nothing but the docs. Built rather than retired because something else was already deferred on it: [`embarch-umbrella` decisions](../../embarch-umbrella/decisions/projects.md) 26 has no other sound per-directory evidence of *which* target produced a directory, the name being unparseable back into one — board, app and snippet names all contain `-`. Three calls the entry above did not make:

- **The file is the descriptor value itself**, the same `serde_json::Value` a tool response echoes back, not a second serialization of the same facts — so a directory's provenance and the answer its caller was given cannot drift apart. It goes out through `json_out` like every other JSON object this crate emits, so it carries `schema_version` (decision 50) rather than becoming the one machine-read shape without it — and this file is read by a *different repo*, which is the case that promise was made for. *Rejected: a version counter of its own.*
- **Written after the build command, only into a directory that already exists, and it never creates one.** A manifest beside a directory no build produced is manufactured evidence, not evidence; and writing *before* the build would put this crate's correctness in front of `west build -d`'s, to gain a provenance file. A **failed** build's directory gets one too — that is the listing entry a reader most needs explained.
- **Absence means "unattributable", never "orphaned", and the write is best-effort.** Every directory built before this shipped has no `target.json`, so a consumer reading absence as "no valid target claims this" would delete exactly the directories it has no evidence about. That rule is also what makes losing the file to a write error the right trade against failing a build that would otherwise have succeeded. Only a `zephyr-west` target gets one: a `static` project resolves no selection (decision 51) and dev-bench builds into west's default `build/`.
