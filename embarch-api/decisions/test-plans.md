### 134 - `test_propose` and `test_plan`: the agent proposes, the engineer confirms, and the repo holds custom suites, plans and the benches a suite brings

**The layout (pinned by the task, read in parallel by `ui/120`).** `embarch/tests/suites/<suite>/` holds a custom suite: its `suite.json` and, per test, `<test id>/test.json` with its study file beside it (a manifest line's `file` is `<test id>/test.json`, relative to `suite.json`, the crate's rule). `embarch/tests/plans/<plan>.json` is a plan. `embarch/tests/results.jsonl` is reserved for the results mirror and not written here. **This follows the issue's `suites/` level, not HIL 02's `embarch/tests/<suite>/<test id>/`**, and it is not [decision 132](person-mirror.md)'s `tests/<name>.test.toml` either: 132's writer has no caller and its kinds were a recommendation the owner may strike, so these files are written by `hil_repo`, which follows no link at any step and refuses a name outside `[a-z0-9][a-z0-9._-]*`. A suite, test id, plan and study file name are each one such step. The ledger's `embarch/ledger/` stays where it is ([98](ledger.md)); a test there and a test here are two ledgers of two things until HIL 03's "Open" renames the tools.

**`test_propose` checks, then sends, then writes.** (1) The crate: a test must parse as `hil_test::TestDef` and pass `check()`; with a `study` and a `bench` (they go together, as Core's `400` says) it also runs `hil_check::check_test` with the `measured` map the caller gives. **A refusal is the crate's own text, one line per refusal, and Core is never called**; nothing is written. (2) `POST /definitions` with `kind` `test`, `capability` or `hook`; the reply's hash is returned, and when Core's standing is `unconfirmed` the answer says it waits for the engineer's confirmation on the card or in the terminal. **This crate never confirms and cannot: the confirmation routes refuse the agent's token** ([core 133](../../embarch-core/decisions/definitions.md)). (3) Only after Core kept it, a test given a `suite` is written under `embarch/tests/suites/<suite>/`, so the repo never holds a test Core refused. An unreachable Core keeps nothing in either place. A manifest that does not parse is left alone and reported. A new manifest gets version `0.1.0` and `validated_with: unvalidated`, since no EmbArch release validated a custom suite; its line carries `TestDef::hash()`, which is what Core compares.

**The study's hash is the tool's to fill.** `study.hash` is the SHA-256 of the study file's bytes as written, a number an agent cannot compute reliably; leave it out and the tool writes the study as pretty JSON, hashes those bytes and fills it. A hash given that does not match is refused, naming the right one. *Rejected: trusting a given hash,* which the crate does not check (its "later unit").

**`test_plan` is three things on one tool.** With `plan` and a `definition`: parse as `hil_test::Plan`, write or update `embarch/tests/plans/<plan>.json`, then select the suite it names. With `plan` alone: read it back. With a `suite` and nothing to write: list the tests that apply to the DUT's capabilities (the plan's, or `capabilities` given) **grouped by bench**, the not-applicable ones apart with the condition that excluded them (`applies_when`, and a template's capability being absent). A suite is a repo suite first, else one of Core's premade suites, read through `GET /suites` and `GET /definitions/<hash>`. **This is a listing, not the expansion**: Core re-expands a run from confirmed definitions ([HIL 03](../../notes/hil/03-test.md), "A run"), and the listing does not decide hook mapping or a requires chain.

**"Selecting" a suite is writing a plan that names it** (the natural trigger, owner's note in the task): each bench of the suite's manifest is copied to `embarch/topologies/<slug>.toml`, the slug derived from the bench's name as [embarch-ui 73](../../embarch-ui/decisions/saved-benches.md) derives one, the description's JSON written as TOML with nulls dropped. **A saved bench is never overwritten**: a file already there that parses to the same value is `unchanged`; any other is `left_alone`, reported with a diff of lines (`-` the saved bench's, `+` the suite's). A name taken with other content is the engineer's file, edited. Listing a suite does not select it.

**Not verified:** against a mock Core only. A premade suite's manifest read through `GET /definitions/<manifest hash>` assumes Core serves a held manifest there; if it does not, selecting a premade suite reports its benches were not copied and says why. The Windows path of the writer is the plain `std::fs` one and has not been built there. See [open/bench-verification.md](../open/bench-verification.md).
