### 146 - A Test run's zip is told by `test-run.dsse.json` and `run.json`, and check 3 recomputes every verdict through the shared crate

**Telling the two apart.** The zip has `test-run.dsse.json` and `run.json` and no `record.dsse.json` (`src/verify_test.rs`); anything else is a Study's, and its checks, check 3's "a Study has no verdict" answer included, are untouched (`check_manifest` and `check_chain` gained a parameter and a function, the Study's calls unchanged).

**Check 0** opens the manifest, the Test run's record and `report-data.dsse.json`, and each `studies/<id>/record.dsse.json`; `run.json` and `result.json` must be subjects of the Test run's record, every study file a subject of its own study record, and each study record must name this zip's `run.json` and be the file the Test run's record names by hash. **Checks 1, 2, 8, 9** are the Study's own functions over the Test run's files (2 per study folder; 8 with the `test_run` entry for the record and each study record). **Check 4** is the Study's; its "numbers only `appendix.typ` prints" partial reads pass when check 6 regenerates `report.typ` and `appendix.typ` whole.

**Check 3.** Per test of `run.json`: the signed Test record must have an entry (a test with none fails by name; a null verdict needs the signed reason `not_run`, `interrupted` is partial). Each run with a study is recomputed by `judge_run` from `run.json`'s limits, the study's `events.json`, `measurements.json` and `study.json`, then `judge_test`, and compared with `result.json`, the study record's `test.run`, the Test record and `report-data.json`. Then the requirement roll-up and the summary, with manual verdicts read from the run-log segment, against `report-data.json`. **Copies of Core:** `judge_steps`, `judge_measurements`, `outcome_of`, `manual_rows`, `runs_on_unit` and `report-data.json`'s field list, pinned by `tests/verify_test_run.rs` only, so they can drift; **[Assumed]** a run was judged with the behaviours `report-data.json`'s `rules` name (Core records none per run).

**What the zip cannot give, by name.** A step's target (DUT or bench) is Core's live topology and is in no file: every signal whose step was refused or whose `until` was not seen is read both ways, and the check is partial if the readings disagree (the signed one must be among them, else it fails). A skipped or errored result (the executor's note is set) and a cancelled run are taken from `result.json`; the image readback, identities and `*IDN?` rest on Core's signature. The output says each so.

**Checks 5, 6, 7.** 5: go_by, published_by and the label from the segment, manifest, declarations and counted manual verdicts. 6: every field of `report-data.json` rebuilt, `report.typ` and `appendix.typ` regenerated byte for byte (the two version lines aside) and the PDF's text held to the run, status, label, go_by, published_by and revision. 7: both exports regenerated from `report-data.json` and each study's `measurements.json`.

**Not checked by this version:** a run whose status is not `completed`, `cancelled` or `deadline`, or that resumes another (`core/178`): checks 3, 5 and 6 answer so, and nothing is guessed.

**Measured:** a fixture Test run (one host study, two requirements, a test never reached) signed with a real key and published through a mock Core passes every check; a verdict flipped in `report-data.json`, a test's record dropped, a limit in `run.json` altered, a run verdict flipped against its study record, a file altered after signing and an export changed each fail the check that names it. **Not run:** a real Core's zip, a refusal on a signal of unknown target.
