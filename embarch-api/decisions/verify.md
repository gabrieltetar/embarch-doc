# embarch-api decisions: `verify`

**Status:** active, 2026-11-22 (`tasks/api/170`, HIL M1.11, first half).

Decisions 118 to 121, 129 and 140. Index: [../decisions.md](../decisions.md). Surface: [../interfaces/verify.md](../interfaces/verify.md). Source: `notes/hil/06-report-and-publish.md`, "Verify". Checks 4, 6 and 9 are `tasks/api/171`'s.

### 118 - `verify` is a CLI-only subcommand that needs no config, no Core and a public key

It is dispatched in `main` before config resolution, like `versions` and `guide`, so a reader with nothing but the zip and a key runs it; it has no MCP tool (an agent verifying its own zip proves nothing), recorded as a `CliOnly` asymmetry in `tool_subcommand_parity`. It lives behind the `pdf` feature because check 7 regenerates exports through `publish_export`. `embarch-core`'s signing doc gives the key as a fingerprint (the SHA-256 of the public key), and a fingerprint cannot verify an Ed25519 signature, so the flag is `--public-key`; the fingerprint is derived from it. The crate depends on `ed25519-dalek` (`verify_strict`, no `rand`) and turns on the shared crate's `reducers` feature, which `embarch-core` already runs.

### 119 - A key not matched by an attested fingerprint verifies integrity and says "origin unattested"

`--attested-fingerprint` is what the reader got from the engineer's elevated install. Equal to the key's SHA-256: attested. Otherwise the result, text and JSON, carries 06's words: the signatures prove integrity only, since the agent can read an unattested Core's key. This is not a failure and does not change the exit code; a key that does not verify the signatures is (check 0). Every Core is unattested in milestone 1, so the first real zip will always say so. The report prints the fingerprint of the key it used, never one read from the zip.

### 120 - Exit 0 means no check failed, and a partial check says what it did not recompute

A check is `pass`, `FAIL`, `partial`, `not checked by this version` or `not applicable`. Exit 1 only on `FAIL`; `--json`'s `complete` is true only when every check ran in full, so a caller that wants more than "nothing contradicted" reads it. Check 2 re-runs each measurement's reducer at the behaviour the signed record names over `streams/<tap>.csv`, and compares the value, the reducer and the behaviour; its step half is [decision 140](#140---check-2-recomputes-each-exchange-steps-outcome-and-each-step-number-from-the-recorded-reply). It does not read a Text tap's markers (so `interval` and `value_at_marker` are not recomputed), and does not compare `uncertainty`, `by` or `incomplete`, which rest on the bench topology and the run's truncation flags that the zip does not carry. A behaviour this build lacks is "not recomputed", never a match.

### 121 - Check 8's chain starts from the segment's first entry, and the publish's own entry is out of reach

The segment is `{entry, hash}` lines; each hash is the SHA-256 of the entry's `serde_json` bytes, `prev` the line before's, `seq` consecutive. A first entry whose `prev` is not all zeros is noted, not failed (a later segment is allowed). The last hash and the line count must equal `run_log.head` and `run_log.length` in the signed manifest. The run's `run` entry must exist once, name `record.dsse.json`'s hash and each capture's; a discard of the run fails. Since `core/145` the same check reads `call-log-segment.jsonl` against the record's `observed.call_log` (header, range, hash rule of Core's `CallLog::segment_bytes`, each cited `{seq, hash}`); a zip with neither reads "no call log" and passes, one with only one of them fails. `cites` is not yet Core's key: no record cites an entry. The publish's entry and any later revision are after the head and are not checkable offline; the result says so. Check 5 reads the same segment for the adoptions and the run's `go_by`, which it recomputes the label from (Core's rule: a person's act is `go_by`, the publisher, an adoption or a declaration with the person's scope), so a forged label fails without trusting `report-data.json`.

### 129 - `core-key` prints the key only after Core's signature over a fresh nonce's frame checks, sends no token, and writes nothing

`verify` needs Core's key out of band and nothing printed it; the guide's `curl` with a fixed nonce checked nothing. `embarch-api core-key [--json]` (CLI only, like `verify`; it needs the config only to find the Core `status` reaches) draws 16 random bytes as the nonce, calls `POST /auth/challenge`, and rebuilds the frame `embarch-core-auth-v1\n<core_nonce>\n<nonce>` from [Core decision 110](../../embarch-core/interfaces/signing.md) itself. It prints only if `frame` equals that string, the Ed25519 signature over it verifies under `public_key`, and `keyid` is the SHA-256 of that key; otherwise it exits 1 saying which. Output: the 64-hex key and the fingerprint `verify` already computes (`verify::sha`, one definition). **No token is sent** (the route takes none, and the point is learning which Core answers first), and **the key is written nowhere**: not into the config, and `verify` does not learn to read it, so the key stays out of band for `verify`. One call is added to `embarch-core-client` (`auth_challenge`, `ChallengeAnswer`; it sends through `dispatch_with` with no bearer), which `embarch-ui` shares. **Measured:** unit tests with a real key (good, wrong key, other nonce, wrong keyid) and a mock Core (no `Authorization` header; a replayed answer exits 1). **Assumed:** a live Core's answer, not run here.

### 140 - Check 2 recomputes each Exchange step's outcome and each step number from the recorded reply

Each `events.json` step is found in the signed `study.json` by its `list`, `index` and `inner_index`. An `Exchange` step's outcome is recomputed from the reply, `reply_truncated`, `until` and `refused_on` by Core's `judge` rule (`embarch-core/src/host_study.rs`): the refusal marker in the reply is `Fail`, else the marker is `Pass`, else an empty reply is `Fail`, else `TimedOut`. **That is a copy of `judge`, not an import** (Core exports no such function, and `verify` reads no Core crate); `tests/verify.rs` pins it on a fixture, and a change to `judge` must change both. A reply that cannot decide it is `partial` and named, never a match: a cut reply with a `refused_on` that is not in the kept part, a lost port, and a marker that sits in a reply under `match_after_echo` (the echo is not recorded). A step with a `parse` is re-parsed with `embarch_study_designer::host_study::parse_step_number`, the one Core calls, and its number and `incomplete` flags compared with the step's `parsed` and with the `measurements.json` row of that name, step and iteration. The names a study's `parse` and prompt `answer` declare count as declared measurements. An `Instrument` step's outcome (the ack) and a step missing from the study file by `list` and `index` (a zip from before `events.json` recorded them) stay `partial`, so a milestone-1 zip still passes.
