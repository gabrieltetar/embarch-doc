### 112 - One function behind the tool and the subcommand, the folder a setting with no default, a zip never overwritten

`embarch_api::publish::run(core, folder, request, now)` is the whole publish; the MCP tool and `publish <run_id>` only read the config and print. **`[publish] folder`** is a config table with `deny_unknown_fields` and **no default** (06: "no default"): absent, `run` returns `NO_FOLDER_MESSAGE` before any Core call, so a refused publish adopts no note. The key lives in `embarch-firmware-build`'s `Config`, additive and `#[serde(default)]`. **A name is `<date>-<slug>-<id8>.zip`, `-r<N>` from revision 2**, opened with `create_new`: a second publish whose revision Core answers the same refuses rather than replaces, and Core's revision, never a count here, is the suffix. A `report.typ` that sets its own footer is refused by a lexical test (`footer`, optional space, `:`), before Core is asked; it is a refusal of the page-number rule only, **not check 9's syntax-tree whitelist, which is M1.11's and `tasks/api/168`'s**. **[Assumed]:** a crude test is enough, since a false refusal names the argument to remove.

### 113 - The order of calls, what the PDF reads, and what Core cannot yet serve

**Order:** adopt the notes (so `report-data` sees them), `report-data`, fetch what the report reads, render, `publish` with the hashes of every file made here, then fetch every manifest subject and the four publish files, check each subject's digest, write the zip. **What the report reads before the manifest exists:** `report-data.json` (served at the pending revision), the captures' renderings and the step outcomes (the existing `/stream`, `/streams`, `/steps` routes, which serve today), and `measurements.json` through the files route at the pending revision, **which Core does not serve before publish** (its handler reads the manifest). The gap is Core's, filed as EMB-241; this unit does not work around it by computing the file. A `404` reads "absent" and the post-publish manifest decides: **a manifest naming `measurements.json` that was not read gives a warning, the zip is still written, `success` is false**, since a PDF without its measurements is a defect the person must be told of and a zip is evidence either way; a manifest naming a file Core will not serve writes **no** zip. **Consistency:** every staged file is compared with the manifest's copy, and a difference writes nothing. **Measured:** against a mock Core, including a byte-for-byte rebuild of the PDF from the zip. **Not run:** a real Core, and a real study's publish.

### 114 - What the zip holds that is this crate's: Core's renderings as the CSVs, every package, a generated appendix and exports that are pure functions

**CSV beside raw is Core's rendering**, a subject of the signed manifest, not a second one made here: a `Raw` tap has none, and an unsigned CSV in the zip would be the one file a reader could not tell from Core's. A rendered tap is staged as `streams/<name>.csv` (`.txt` for a `Text` tap), the names `result-layout.md` gives. **[Assumed]:** an `OutpostTrace` tap's rendering has the same name; a mismatch shows as a warning, not a wrong file. **Packages: every embedded file** when the study brings a `report.typ` (the dependency closure of what it imports is not computed; 1.2 MB before compression), none for the generated one. **The appendix and the data section are generated as Typst source in which every value is a string literal**, so no run's data can be read as markup, and carry no import. **The exports are functions of the signed data only** so `verify` regenerates them. **Qualifiers** are the five milestone 1 can derive: `bench_firmware_unverified`, `rests_on_dut_report`, `declared_by_study`, `declared_by_agent`, `relayed`. **[Assumed]:** the OCP T&V lines match the format's JSON Schema; they were written from the note and the format's published shape, **not validated against the schema**. **Not here:** the numeric-oracle listing, authorship and revisions built from an earlier zip (`tasks/api/168`); `report.typ` is not parsed.
