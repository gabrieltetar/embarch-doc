# embarch-api: design

**Status:** draft, 2026-07-17. This document supersedes the chat-history discussion that produced it — treat this file, not a conversation transcript, as the source of truth going forward. Append changes to the Changelog (§13) rather than silently editing history above it.

## 1. Purpose and scope

`embarch-api` is the layer between an MCP client (e.g. Claude Code, or any other MCP-speaking agent or tool) — or a human directly at a terminal, via its own CLI (§3.10) — and `embarch-core`. Core owns the debug probe and serial connection and deliberately "has no idea the EmbArch API or any MCP client exist" — it just exposes 4 bearer-token-authed HTTP endpoints (`/status`, `/flash`, `/reset`, `/serial-log`). embarch-api is what gives those endpoints meaning to an agent or a human: it exposes them as MCP tools and CLI subcommands, and adds the one capability Core intentionally does not have — running a project's build and handing the resulting artifact to Core's `/flash`.

embarch-api is **not**:
- A multi-user or multi-tenant service. Each engineer runs their own full stack (own embarch-api, own embarch-core).
- A database-backed system. All state is a single TOML config file.
- A toolchain-aware build system. It runs whatever command a project's config specifies and does not understand `west`, `idf.py`, `arduino-cli`, or any other tool's internals.

**Out of scope for this document:** repository bootstrap (`git init`, an initial commit, `README.md`, CI, `LICENSE`) and the actual test code described in §7.1. Both are real, necessary work — this repo has no git history yet, and §7.1's testing strategy has no test files behind it — but they're implementation/process work, not design decisions, so they're deliberately left for a separate pass rather than specified here.

## 2. Architecture overview

```
       build_command subprocess (west / arduino-cli / etc.)
                                  |
MCP client --stdio(spawn)--> embarch-api --HTTP+Bearer--> embarch-core --probe-rs/serialport--> hardware
                                  |
                  human, direct: `embarch-api <subcommand> ...`
```

`embarch-api` is reached two ways: over MCP stdio by an MCP client (Claude Code, or any other MCP-speaking agent/tool), and directly via its own CLI subcommands (`build`, `flash`, `build-and-flash`, `reset`, `serial-log`, `list-projects` — §3.10, §5a) by a human at a terminal with no agent in front of them. Both converge on the same `config.rs`/`build.rs`/`core_client.rs` modules and the same per-project build lock — there is no separate code path for "CLI mode," mirroring the exact MCP-vs-CLI convergence `embarch-core/design.md` already established between its own HTTP API and its CLI (§2, §9 there). The MCP client spawns embarch-api as a local subprocess and talks MCP over stdio; the CLI is instead a direct, one-shot invocation with no client software mediating it. Either way, embarch-api talks plain HTTP to embarch-core, authenticating with the same `EMBARCH_TOKEN` Core itself expects. Build commands run as subprocesses of embarch-api, in the source tree of whichever project was named.

## 3. Locked-in design decisions and rationale

1. **Single user, single Core instance.** No multi-tenancy, no user/permission model, no database. This was explicitly revisited mid-design — the original framing raised "what if EmbArch API is multi-tenant, make it full" — but the resolution was that each engineer runs their own complete stack (their own embarch-api talking to their own embarch-core), so there is no multiplexing to design for. Revisit this document if that assumption ever changes.
2. **Language: Rust**, matching embarch-core. Reuses Core's structuring patterns (an `AppState`-equivalent, `anyhow`-based error handling) and keeps the whole project to one toolchain.
3. **Purpose: MCP server, CLI, and build orchestrator.** The three responsibilities embarch-api adds on top of Core are (a) exposing Core's capabilities as MCP tools for any MCP client, (b) exposing the identical capabilities as CLI subcommands for a human with no MCP client in front of them (§3.10), and (c) running a configured build command and feeding the artifact to Core's `/flash`.
4. **MCP transport: stdio**, with the MCP client spawning embarch-api directly, when no subcommand is present on the command line (§3.10 governs the alternative). This was chosen over exposing embarch-api's MCP surface as its own HTTP+API-key service. The consequence: the trust boundary for embarch-api's *inbound MCP* interface is simply "whoever can spawn the process" — there is no bearer token, API key, or session concept protecting the MCP surface itself. This is a deliberate simplification, not an oversight; if embarch-api is ever run detached from an interactive MCP client session (e.g. reachable over a network), this decision needs revisiting. Note this is entirely separate from the *outbound* credential embarch-api needs to talk to Core — see §9. This decision governs MCP mode specifically; embarch-api also has a second, human-facing inbound interface — see §3.10.
5. **Build orchestration: generic configurable command per project, not toolchain-specific logic.** Originally motivated by an assumption that the two real projects this manages day one used different toolchains (Zephyr/`west` vs. Arduino-CLI/PlatformIO) — on inspection both turned out to be Zephyr/`west`-based (see §4's note on `project-b-mkr`), but the generic-command design is kept regardless: it's the right call on its own merits (no toolchain-specific logic to maintain, works for whatever a future project uses) even though the original two-toolchain premise didn't hold.
6. **Persistence: a single TOML config file, no database.** Matches the single-user, single-Core scope — there's no multi-row data (users, boards-across-tenants, audit trails) that would justify SQLite or Postgres.
7. **Deployment: same machine as Core today, but Core's base URL stays configurable, never hardcoded to `127.0.0.1`.** Core's own README already flags a possible future move to a Raspberry Pi reachable over LAN; embarch-api should not bake in an assumption that will break when that happens.
8. **This document is the durable design record.** Core's README references "the design discussion" without pointing anywhere — this file is meant to be that pointer for embarch-api going forward.
9. **Dependency choices are locked, not incidental.** MCP protocol/transport: the `rmcp` crate (`server` + `transport-io` features), using its `tool_router`/`tool_handler` procedural-macro pattern — chosen over hand-rolling JSON-RPC, since MCP's schema/handshake plumbing isn't worth re-deriving per project. HTTP client: `reqwest` built on `rustls` rather than `native-tls`, specifically to avoid pulling in a system OpenSSL dependency — keeps embarch-api trivially buildable on whatever machine an engineer's Core happens to run on (§9). CLI: `clap` (derive). Config parsing: `toml` + `serde`. MCP tool parameter schemas: `schemars`'s `JsonSchema` derive, which `rmcp` requires to generate each tool's declared input schema. Exact versions are pinned in `Cargo.toml`/`Cargo.lock`, not restated here.
10. **A CLI subcommand interface, invoked directly by a human, added alongside MCP — not a separate service, not a separate binary.** `embarch-api build|flash|build-and-flash|reset|serial-log|list-projects <args>` runs the identical `config.rs`/`build.rs`/`core_client.rs` orchestration MCP's `tools.rs` already calls (§10), mirroring the pattern `embarch-core` established between its own CLI and HTTP API (`embarch-core/design.md` §2, §9): two front-ends, one set of modules underneath, neither privileged over the other. This closes a real gap: without it, an engineer with no MCP client in front of them (no Claude Code, no other agent) had no way to invoke embarch-api's build orchestration at all, and would have had to either run the build manually or call embarch-core's HTTP endpoints directly — bypassing embarch-api's config-driven `build_command`, artifact-freshness check, and timeout/process-group handling entirely. **Subcommand presence is the mode switch**: no subcommand → MCP stdio server (§3.4, fully backward compatible with every existing MCP client config that spawns `embarch-api --config <path>`); a subcommand present → run that one operation as a human-facing CLI call and exit. See §5a for the subcommand surface, §8 for the CLI's trust boundary, §10 for `cli.rs`. This decision is recorded ahead of implementation — no `cli.rs` exists yet in the actual source tree; see `milestone-1.md` for the execution plan.
11. **Core's address may be declared as `base_url = "auto"`, resolved per-process at first use — not written down as a literal address at setup time.** *(Shipped 2026-08-05 — see §4, §7, and [embarch-umbrella/design.md](../embarch-umbrella/design.md) §3 decision 9.)* The WSL2⟷Windows split (§9) reaches Core at the WSL2 host-gateway IP, which changes across WSL2 restarts, so a literal IP in the config is guaranteed to go stale — and did: this project's real `config.toml` carried `172.22.128.1` while `embarch-core/design.md` §7 recorded `172.29.64.1`. Resolution belongs here rather than in `embarch-umbrella`'s setup step precisely because the value has to be right *at the moment a build is flashed*, not at the moment setup last ran, and `embarch-api` is the process present then. This does not weaken §3.7 — Core's address is still never hardcoded to `127.0.0.1`; `auto` is an explicit opt-in that makes localhost merely one candidate, and an explicit URL still wins outright.

12. **Zephyr/west projects get live target discovery instead of a static per-board `[[projects]]` entry; every other build system keeps today's fully-static schema, unchanged.** A Zephyr board's buildable surface (which boards, SoCs/cpuclusters, variants, hardware revisions, apps) is a property of the *current* state of `boards/*/board.yml` and `app/*/`, not something safe to snapshot into a config file once — and not every combination `board.yml` *declares* is real ([embarch-zephyr.md](../embarch-zephyr.md) §2.1's revision-backing gotcha, §2.2's variant-less-build gotcha). Full board-qualifier grammar/revision/snippet/sysbuild background lives in [embarch-zephyr.md](../embarch-zephyr.md), not here. Implementation history and the real-repo bugs that shaped this decision are in this section's own Changelog (§13) and [embarch-decision-reversals.md](../embarch-decision-reversals.md) — *(trimmed 2026-08-15, closing item 60 of that day's design-improvement review: this decision previously carried ~70 lines of dated implementation narrative that belonged in the changelog per `DOC-PROTOCOL.md` §5, not in the current-state decision text)*.

    **For a project detected as Zephyr/west-shaped** (`boards/*/*.yml` plus at least one `app/*/CMakeLists.txt` under `source_path` — the same shape `init` recognizes via [embarch-umbrella/design.md](../embarch-umbrella/design.md) §3 decision 13's `build/build_info.yml` check): `[[projects]]` stores only what can't be derived from the repo and doesn't change as it evolves:

    ```toml
    [[projects]]
    name = "reference-dut-fw"
    source_path = "/path/to/repo"
    discovery = "zephyr-west"        # new field; omitted = "static", today's schema, fully unchanged
    west_binary = "/path/to/.venv/bin/west"
    build_dir_root = "embarch/build" # per-target subdirectories computed under this, never shared
                                      # (embarch-umbrella/design.md §3 decision 10)
    flash_format = "hex"
    build_timeout_secs = 900
    default_snippets = ["ble-shell"]        # optional
    default_extra_args = ["-p", "always"]   # optional
    ```

    Everything else is resolved **live, per call, never cached into config**:
    - **Board/variant/revision/app enumeration** is pure filesystem + YAML reads — no `west` invocation, cheap enough to re-run on every `list_targets` call.
    - **File-backing validation** — a (board, soc, cpucluster, variant?, revision) tuple is real only if: a real `.dts` file exists for that (board, soc, cpucluster, variant) combination (`dts_exists`); the revision equals `board.yml`'s declared default (implicitly backed) or a revision-suffixed overlay/defconfig exists; and, for a board using a custom (non-standard) revision format, the board's own revision logic doesn't reject the combination. A SoC with named product variants also gets one synthesized variant-less candidate per cpucluster ([embarch-zephyr.md](../embarch-zephyr.md) §2.2), run through the same gate.
    - **Build directory**: `build_dir_root/<board>-<variant-or-'default'>-<revision>-<app>-<snippets-or-none>-<extra_args-hash>/`, one per distinct target, satisfying [embarch-umbrella/design.md](../embarch-umbrella/design.md) §3 decision 10 without a human naming each one.
    - **Artifact path**: `<build dir>/zephyr/zephyr.hex` (or whatever `flash_format` implies) — searched for, not assumed at a fixed layout, per [embarch-zephyr.md](../embarch-zephyr.md) §4's sysbuild note.
    - **`artifact_path_for_core`**: computed at call time against the resolved build dir, whenever `embarch-api` runs under WSL2 — never hand-written or stored.
    - **`chip`**: resolved from the selected SoC via `embarch-core`'s `POST /resolve-chip` (`embarch-core/design.md` §3 decision 8), consulting the project's own `soc_chip_overrides` first (§3 decision 13) — `embarch-api` holds no SoC→chip table of its own. An unmapped SoC with no override is a call-time error pointing at `probe-rs chip list`. One project can span more than one SoC (`ref_nrf54dk` does, across three), so "one chip per project" was never the right shape.

    **New tool: `list_targets(project)`** (MCP tool + `list-targets` CLI subcommand). For a `zephyr-west` project, returns every validated (board, soc, cpucluster, variant, revision, app) tuple, plus `snippets_by_app` (every real `-S` snippet under `app/<app>/snippets/**/snippet.yml`, [embarch-zephyr.md](../embarch-zephyr.md) §3), `default_snippets`, and `default_extra_args`. Never cached at any granularity — caching would reintroduce the exact staleness this decision exists to eliminate.

    `build`, `flash`, `build_and_flash`, and `reset` each take four optional selection params — `board`, `variant`, `revision`, `app` — validated against the live scan before any command is assembled, plus `snippets`/`extra_args` below. **Selection is never guessed, but it is narrowed**: whatever subset is given filters the live-scanned set; exactly one match proceeds directly, more than one is a call-time error listing the narrowed remainder, none given lists everything `list_targets` would. `reset` needs the same four params as `flash` — it calls Core with a `chip` too, and a `zephyr-west` project has none stored to fall back to. `flash`'s `firmware_path` override bypasses *build*-target resolution (which directory/artifact) but not *chip* resolution — there's still no stored chip to fall back to for a `zephyr-west` project.

    **`snippets`** — a fifth, purely additive param, not a narrowing axis (a snippet choice doesn't change which target tuple exists, [embarch-zephyr.md](../embarch-zephyr.md) §3), validated against `available_snippets` for the resolved app. Omitting it (or an empty list) falls back to the project's `default_snippets`, not "no snippets" — the sentinel `["none"]` forces zero snippets over a configured default (§3 decision 21). A non-empty explicit list overrides the default entirely, it does not add to it. Folded into `Target::build_dir_name`.

    **`extra_args`** — opaque passthrough (e.g. `["-p", "always"]`), unvalidated (no real-file list to check an arbitrary flag against, same posture as `discovery = "static"`'s whole `build_command`, decision 5), inserted right after the `build` subcommand and before `-b`. Falls back to `default_extra_args` on an empty selection, same override-not-additive semantics as `snippets`. Folded into `Target::build_dir_name` via a hash of the unsorted argument list (flag order can be meaningful; an arbitrary flag can contain directory-unsafe characters).

    **For a `discovery = "static"` project** (the default — every project configured before this decision, and every non-Zephyr project after it), nothing changes: `build_command`/`chip`/`artifact_path`/`artifact_path_for_core` stay exactly as documented in §4, and `build`/`flash`/`build_and_flash`/`reset` ignore the five new params entirely. A static project that still wants a selectable menu can declare one by hand:

    ```toml
    [[projects.targets]]
    name = "target-a"
    build_command = ["make", "TARGET=a"]   # overrides the project-level fields when this target is selected
    chip = "..."
    artifact_path = "..."
    ```

    `list_targets` on a static project returns these rows verbatim if any exist; if none do, it errors with the exact TOML shape above rather than a bare "not applicable."

    **The one existing principle this scopes an exception into:** decision 5's "generic configurable command per project, not toolchain-specific logic" stays true for *how* a command runs (still an opaque argv, still no shell) and for every non-Zephyr project unconditionally — but `embarch-api` now has to understand Zephyr's board-qualifier grammar and file conventions well enough to assemble that argv for a `zephyr-west` project. Deliberate, scoped cost, not a reversal of decision 5.

13. **A per-project `soc_chip_overrides` table gives a `zephyr-west` project an escape hatch for a SoC `embarch-core`'s `/resolve-chip` doesn't know about (2026-08-15, closing item 2 of that day's design-improvement review).** Decision 12 removed the old `chip` field entirely for a `zephyr-west` project, and `/resolve-chip` 404s naming the unmapped SoC — but there was nowhere to *write the answer* once `probe-rs chip list` (or `embarch-core`'s new `chip-list` subcommand, `embarch-core/design.md` §10) found the right string. New optional `[[projects.soc_chip_overrides]]` table, `zephyr-west`-only: `{ soc = "esp32c3", chip = "ESP32C3" }` entries, consulted by `resolve.rs` *before* calling `/resolve-chip` — a hit short-circuits the HTTP call entirely (no reason to ask Core about a SoC the operator already resolved by hand), a miss falls through to `/resolve-chip` exactly as today. Keeps Core's own mapping table as the source of truth for the common case (decision 12's original rationale, unchanged) while giving the uncommon case a real fix instead of a dead end.
14. **`embarch-api` starts in MCP mode even when Core is unreachable at startup — the eager connectivity check becomes a warning, not a refusal (2026-08-15, closing item 3... wait, item 5).** §7's "startup connectivity check" previously refused to start the MCP server at all on a failed `GET /status`, which meant every one of the nine MCP tools vanished from the agent's view with no way to learn why — directly contradicting §5's own rule that failures should come back as tool text an agent can reason about. Resolved: the startup check still runs and still logs a clear warning, but no longer blocks the server from starting. `status` reports the unreachability with the same "Core unreachable at `<base_url>`" text the check already produces; every hardware-facing tool (`build`/`flash`/`reset`/`serial_log`/`list_targets` for a `zephyr-west` project needing `/resolve-chip`) fails per-call with that same message plus the resolved-candidate list (`base_url = "auto"`'s candidate race, §3.11/§7) rather than never being callable at all. `list_projects` is unaffected either way, matching its existing Core-down tolerance (§7).
15. **`/flash`'s artifact transfer keeps `firmware_path` on a same-machine topology, and gains multipart only where nothing worked before (2026-08-15, closing item 9's `embarch-api`-side half — `embarch-core/design.md` §3 decision 10 is the Core-side half).** `resolve.rs` now decides per call: if `embarch-umbrella/design.md` §3 decision 6's topology probe (already run for `base_url = "auto"`, §3.11) classifies the resolved Core as `local` or `wsl-host` (the two classes where a filesystem is actually shared, directly or via `artifact_path_for_core`'s existing WSL2 UNC bridge), `flash`/`build_and_flash` keep sending `firmware_path` exactly as today — no behavior change, no redundant copy of a potentially large artifact, since that path is already validated against real hardware (milestone-1). For a `remote` Core (topology v, `embarch-umbrella/design.md` §4), which previously could not flash at all, they now send the artifact as multipart bytes instead. `artifact_path_for_core`, its WSL2 UNC computation, and `embarch-umbrella`'s `doctor` check 9 are all unchanged by this decision — only topology v gains a working path it didn't have before.
16. **`--json`'s error object gains `error_kind`, matching Core's new structured error body — and covers failures that never reach Core at all (2026-08-15, closing item 11's `embarch-api`-side half).** Core's `{code, message, cause}` (`embarch-core/design.md` §3 decision 12) gives `embarch-api` a real error kind to pass through instead of parsing prose: a Core-originated failure's `code` becomes `--json`'s `error_kind` verbatim. For a failure that never reaches Core — an unloadable config, a build that failed before any HTTP call, an unresolvable `zephyr-west` target — `error_kind` takes one of a small `embarch-api`-native set (`config_error`, `build_failed`, `target_unresolved`, `core_unreachable`) instead. This retires §12's "CLI exit-code granularity" open item as a distinct problem — a script that needs to branch on failure kind now has `error_kind` in `--json`, not a reason to invent a finer-grained exit-code taxonomy on top of it.
17. **`embarch-api` checks Core's new `contract_version` at the same point it already checks `study_designer_schema_version` — item 13's `embarch-api`-side half.** `core_client.rs`'s `status()` call (§7) now also compares `/status`'s `contract_version` (`embarch-core/design.md` §3 decision 13) against a compiled-in `EXPECTED_CORE_CONTRACT_VERSION` constant, warning (not refusing — matching `embarch-umbrella/design.md` §3 decision 14's existing warn-only version-skew posture) on mismatch, in the same log line the existing schema-version check already produces.
18. **Truncation keeps head *and* tail, not just the last ~64KB (2026-08-15, closing item 28).** §6's existing truncation (each captured stream capped before returning through MCP) kept only the tail — for a Zephyr build, the *first* compiler error is usually the actionable one, and a long build's early failure could scroll entirely out of a tail-only cap by the time `cmake`/`ninja` finish emitting later, less useful output. Changed to a head+tail split (e.g. the first ~32KB and the last ~32KB of a ~64KB total budget, with the truncation marker naming how much was dropped from the middle) — unchanged for anything already under the cap.
19. **`extra_args`' hash-only build-dir name gets a readable prefix, plus a `target.json` recording the full resolved selection (2026-08-15, closing item 29).** Decision 12's `extra_args` folds into `Target::build_dir_name` via a hash of the (unsorted) argument list, since an arbitrary flag can contain directory-unsafe characters — but a bare hash makes `embarch/build/<hash>/` undebuggable to a human staring at a directory listing. Two additions, no change to the hash itself (still what disambiguates two otherwise-identical targets): the directory name gains a readable prefix ahead of the hash (`<board>-<variant-or-default>-<revision>-<app>-<snippet-list-or-none>-<extra-args-hash>/`, i.e. every other axis spelled out, only `extra_args` hashed); and each build directory gets a `target.json` written alongside the build output, recording the full resolved `Target` (every axis, snippets, and the literal `extra_args` list) — so a human (or an agent) can `cat target.json` to recover exactly what produced that directory without reverse-engineering a hash.
20. **A project-level `default_target` config field documents and pins the common single-target case, and the narrowing-to-singleton behavior itself is now stated as a caveat, not left implicit (2026-08-15, closing item 30).** Decision 12's narrowing (an unambiguous partial selection proceeds without erroring) means a call that works today can start erroring once a second board/variant lands in the repo — silently changing behavior as the repo grows, with nothing in the doc warning a reader this could happen. Stated explicitly here now. New optional `default_target: { board?, variant?, revision?, app? }` per-project config field (`zephyr-west` only): when set, it's applied as the *base* selection before a call's own params narrow further — a call's own `board`/`variant`/etc. still override the default per-field, but omitting all four now resolves against the pinned default instead of the live-scanned full set, keeping a repo's common case stable even after a second target is added.
21. **A sentinel value forces "no snippets" over a configured `default_snippets` (2026-08-15, closing item 31).** Decision 12's snippet support had no way to override a non-empty `default_snippets` down to nothing — omitting `snippets` falls back to the default, and there was no third state between "use the default" and "use this explicit list." New reserved literal: `snippets = ["none"]` (a single-element list containing the literal string `"none"`, chosen since `"none"` can't itself collide with a real Zephyr snippet name — `available_snippets` names are directory-derived identifiers, not reserved words) means "build with zero snippets regardless of `default_snippets`," validated and stripped before the `-S` flags are assembled. Any other explicit list, including one containing `"none"` alongside other names, is a call-time error naming the ambiguity, rather than a silently-wrong interpretation.
22. **The uncached live Zephyr scan's cost-bound assumption is stated, not left implicit (2026-08-15, closing item 32).** Decision 12 deliberately never caches `list_targets`' filesystem+YAML scan, reasoned as "already cheap enough" — but no bound was ever written down for what "cheap enough" assumes about repo size. Stated here: the design assumes a `boards/`/`app/` tree in the same order of magnitude as the reference-dut repo this decision was built against (single-digit boards, low tens of variant/revision/app combinations, low hundreds of files touched by the scan) — comfortably sub-100ms on ordinary local storage. A repo an order of magnitude larger (hundreds of boards) hasn't been measured against this assumption; if `list_targets` or `build`'s pre-assembly validation ever becomes perceptibly slow in practice, that's the signal to revisit caching, not a reason to add it pre-emptively now.
23. **No new `doctor` MCP tool — `embarch-api` stays unaware `embarch-umbrella` exists, and an agent shells out to `embarch doctor --json` directly instead (2026-08-15, closing item 33).** Adding a `doctor` tool to `embarch-api`'s own MCP surface would mean `embarch-api` either reimplementing `embarch-umbrella`'s full diagnostic chain (`embarch-umbrella/design.md` §5) or gaining a dependency on the `embarch` binary — both break the deliberate one-way relationship §11a already establishes (`embarch-umbrella` shells out to `embarch-api`'s CLI; never the reverse). Resolved instead by stating explicitly, here, what was previously left for an agent to discover on its own: an agent hitting a misconfiguration it can't diagnose from `embarch-api`'s own tool errors should invoke `embarch doctor --json` as a shell command (assuming `embarch-umbrella/design.md` §3's `setup` already put it on `PATH`), not assume `embarch-api` has an equivalent tool of its own.
24. **`--json`'s object schema gains a `schema_version: u32` field, versioned from the start rather than after a UI depends on the unversioned shape (2026-08-15, closing item 34).** §5a's `--json` output has no version marker today; `embarch-umbrella/design.md` §10's anticipated UI is exactly the kind of external consumer that would otherwise have no way to detect a future breaking shape change. Bumped by hand only when a field is renamed/removed/retyped — matching the same discipline `STUDY_DESIGNER_SCHEMA_VERSION` and `embarch-core`'s new `contract_version` (§3 decision 13 there) already establish for their own wire shapes.
25. **§4 states plainly that config resolution happens once, at process start, binding an MCP session to whichever repo spawned it (2026-08-15, closing item 35).** True today and probably the right behavior (an MCP client's spawn cwd is exactly "which repo am I working in" for the session's lifetime) — but §4's cwd-upward search (2026-08-13's addition) never said so explicitly, leaving a reader to infer it. Stated here as a property of the design, not a gap: switching repos mid-session means reconnecting the MCP client (restarting `embarch-api`), same as any other config change (§12's "no hot-reload" item).
26. **`serial_log`'s `port` param falls back to `GET /dev-bench/port` when neither the call nor the project config supplies one (2026-08-15, closing item 36).** §5 previously left `port` with no fallback at all — a call omitting it and a project with no configured `serial_port` simply errors. Since `embarch-core` can already answer "which port is dev-bench on" (`embarch-core/design.md` §4/§5), and a DUT's own serial console is a different, project-specific port that config already covers, this fallback is narrowly for the dev-bench case: if `port` is still unresolved after the existing project-config fallback, `embarch-api` calls Core's `GET /dev-bench/port` and uses that if it returns one, before finally erroring. Minor ergonomics, no new failure mode — a `404` from that call just means the existing "no port resolved" error, unchanged.
27. **`embarch-api` validates a `Study`'s `limits`-module capacities at submit time, before the HTTP call to Core, not only relying on Core's own decision-18 check (2026-08-15, closing item 41).** Capacity validation lived only in Core (`embarch-study-designer/design.md` §3 decision 18), but `embarch-api` is the one holding the file for `--study-file` (§5a) — a JSON exceeding a `limits` bound today fails with a raw `serde`/deserialize error inside `embarch-api`, before Core's friendlier decision-18 message (naming the offending field) ever runs. `run_study`/`run-study` now runs the same `limits`-module checks (via `embarch-study-designer`'s exported validation helpers) immediately after parsing the JSON and before the HTTP call, surfacing the same field-naming error text a human would otherwise only get from Core — Core's own check (§3 decision 18) is unchanged and stays the authoritative, un-bypassable gate for any other caller.
28. **`run_study`/`run-study` compute and fill `steps_crc` when it's absent from the submitted JSON, implementing `embarch-study-designer/design.md` §3 decision 26 (2026-08-15, closing item 4's `embarch-api`-side half).** Calls this crate's exported `steps_crc()` over `Study.steps` and overwrites whatever value (including a missing/zero one) was present, immediately before validation (decision 27 above) and the `POST /study` call — a hand-authored `--study-file` no longer needs a human to compute a CRC-32 by hand, closing the gap between decision 17's integrity check and the suite's symmetric-human/agent principle (`embarch.md` §5). A caller that already computed a correct value is unaffected, since recomputation is idempotent.
29. **§5/§5a gain `study_power_data`/`study_waveform_data` rows, matching the names `embarch-study-designer/design.md` §6 locks in (2026-08-15, closing item 44).** Previously left as "a small remaining item, deferred to whichever milestone implements this surface" — named now, ahead of implementation, same posture every other planned-but-unbuilt row in these two tables already uses.
30. **§7.1's testing strategy gains a named tier: a scripted smoke harness, not just "mocked unit tests plus manual live runs" (2026-08-15, closing item 16).** Every real bug found in this project to date came from a live run against a real Core or real repo (decision 12's whole implementation history is nothing but this), not from the still-unwritten unit-test suite §7.1 describes — that's a real, working methodology, just an unnamed and unrepeatable one. New named tier, **`scripts/smoke.sh`** (or equivalent): spins up a throwaway `embarch-core` instance (a temp token, a random port, `run` in the foreground) plus a small synthetic fixture repo (a minimal `boards/`/`app/` tree, same shape as decision 12's own test fixtures) already used for the live verifications recorded throughout this doc's changelog, and re-runs a fixed script of `list_targets`/`build`/`flash`/`reset` calls against them — not a substitute for §7.1's mocked unit tests (still the acceptance criteria for anything below the process boundary), but a repeatable version of the ad hoc live-verification pattern every decision-12 changelog entry already describes doing by hand.

## 4. Configuration schema reference

Config path resolution, in order: **`--config <path>`**, then **`EMBARCH_API_CONFIG`**, then — *added 2026-08-13, revising this section's original text* — **a cwd-upward search for `embarch/embarch.toml`** (`find_config_upward` in `main.rs`), consulted only when neither explicit source is set. The original text here said the path is "not inferred from cwd... since the MCP client controls the spawn cwd... that shouldn't be a hidden assumption" — true as an argument against cwd-inference as the *only* mechanism, but not against it as a last-resort *fallback* behind two explicit ones: an explicit `--config`/env var still always wins outright, so nothing already relying on either changes behavior. What changed the calculus: an engineer working across several firmware repos (the real, current situation — this suite already has more than one) has no single `EMBARCH_API_CONFIG` value that's ever correct, and a separate `claude mcp add` per repo isn't "no `--config` needed," it's "typed once instead of every call." Walking up from cwd looking for the conventional `embarch/embarch.toml` (below) — the same pattern `git`/`west` themselves use for their own config/workspace root — makes it work per-repo with zero registration and zero env var, for every firmware repo, not just one hand-configured at a time.

**Conventional location: `<firmware-repo>/embarch/embarch.toml`**, one complete config per firmware repo, scaffolded by `embarch init` ([embarch-umbrella/design.md](../embarch-umbrella/design.md) §3 decision 10). Two consequences worth stating: a repo-scoped config means `list_projects` inside a firmware repo can only offer that repo's projects, and `[core]` is duplicated into every such file (accepted for v1; the include/fragment alternative is §12's open item).

Design choices to preserve:
- **`build_command` is an argv array, not a shell string.** Runs via `tokio::process::Command` with no shell interposed, avoiding quoting/injection ambiguity and shell-dialect differences (bash vs. cmd.exe vs. sh). Projects that genuinely need shell features (pipes, `&&`, sourcing a venv) use the explicit escape hatch: `build_command = ["bash", "-lc", "source .venv/bin/activate && west build ..."]`.
- **`env` is additive**, merged onto embarch-api's own inherited environment, not a full-profile replacement. PATH and toolchain setup remain the responsibility of whatever launches embarch-api.
- **`chip` / `flash_format` are opaque pass-through strings.** embarch-api does not validate them against probe-rs's target database — that validation belongs to Core/probe-rs, and duplicating it here would be a maintenance trap.

**Why `build` and `flash` stay separate as well as offering `build_and_flash`:** the common agent-driven workflow ("make this change work on hardware") wants one call, and bundling prevents accidentally flashing a stale/failed artifact after a build error. But fast iteration on compiler errors shouldn't require touching hardware every call, and re-flashing the same artifact after a manual board reset shouldn't require a full rebuild — hence all three stay available.

**Error-handling rule, applied to every tool:** expected/recoverable failures (nonzero build exit code, Core returning 4xx/5xx, a missing artifact) come back as `CallToolResult::error(...)` content — never `Err(McpError)` — so the calling agent sees the actual failure text (e.g. a compiler error) and can reason about it. `Err(McpError)` is reserved for true protocol-level problems, like embarch-api's own config being unloadable at all.

**One documented exception:** every tool that takes a `project` argument looks it up against the config first, and an unknown/mistyped project name comes back as `Err(McpError::invalid_params(...))`, not `CallToolResult::error`. This is deliberate, not an oversight: MCP's `invalid_params` exists precisely for "the request itself is malformed," which a bad project name is, as distinct from "the request was well-formed but the operation failed" (a build error, a Core failure) — the case the general rule above covers.

**`--json` flag** (`embarch-api --config <path> --json build <project>`): switches a subcommand's stdout from a human-readable summary to a single JSON object carrying the same fields the equivalent MCP tool result carries (e.g. `{"schema_version": 1, "success": bool, "exit_code": i32|null, "stdout": "...", "stderr": "...", "artifact_path": "...", "artifact_fresh": bool}`), so a script (e.g. `milestone-1.md`'s west-runner wrapper) doesn't have to scrape human text. `schema_version` (§3 decision 24, 2026-08-15) is bumped by hand only on a breaking shape change. Default (no `--json`) prints readable text for an engineer typing the command directly.

**Error handling and exit codes**: a CLI has no equivalent of MCP's protocol-level-vs-tool-level distinction (§5's `CallToolResult::error` vs. `Err(McpError)` split, or the `invalid_params` project-name exception) — there is no protocol layer underneath a CLI invocation. Instead:
- Success → exit code `0`; result on stdout (human text, or the `--json` object).
- Any failure — unknown project name, config load failure, build failure (nonzero exit/timeout/killed), Core unreachable, Core returning 4xx/5xx, missing artifact — → exit code `1`; a one-line error message on stderr. If `--json` was passed, the error goes into the same JSON object on stdout instead (`"success": false`, `"error": "...", "error_kind": "..."`) rather than to stderr, so a script only has to check the process exit code, not which stream carried the result.
- Malformed invocation itself (missing required arg, unknown subcommand) is handled by `clap` before any of this runs, using clap's own exit code (`2`) and usage text — unchanged, not part of this design.
- **Exit code stays a single `1` for every failure kind** (e.g. no distinct code for "build failed" vs. "project not found" vs. "Core unreachable") — but as of 2026-08-15 (§3 decision 16), `--json`'s new `error_kind` field gives a scripted caller the finer-grained signal directly, without needing a matching exit-code taxonomy invented on top of it.

## 6. Build orchestration details

- **Working directory**: `source_path` joined with `build_cwd` if set, else `source_path`. Validated to exist before spawning; if not, returns a tool-level error rather than panicking.
- **`artifact_path` resolution**: resolved relative to that same build directory (`build_dir()` = `source_path` + `build_cwd` if set, else `source_path` alone), not to `source_path` alone unconditionally. The load-bearing distinction `build_cwd` encodes is *where the build command's process cwd actually is* — for a `west build <app-path>` invocation, that's wherever `west` is invoked from, which is **not necessarily** the app subdirectory itself: `west`'s default build output dir is `<cwd>/build`, so if the real invocation runs from `source_path` and passes the app path as a positional argument (rather than `cd`-ing into it), `build_cwd` must stay unset even though the app lives in a subdirectory — setting `build_cwd` to that subdirectory in that case makes `resolved_artifact_path()` look in a `build/` directory that never gets written to. `project-a-board` (§4) hit exactly this: confirmed fixed by reading its own `build/build_info.yml`'s recorded `west.command` after a real build, which showed the invocation's cwd was `source_path` with the app path as a trailing argument, not `source_path/app/project-a` as `build_cwd`. A project that gets this wrong would report a fresh artifact that's actually a stale leftover (if one happens to exist at the wrong resolved path from an earlier config), or never find the real one at all.
- **Environment**: inherits embarch-api's own process environment, overlaid with the project's `env` table.
- **Capture**: `Stdio::piped()` for both stdout and stderr, drained by **two concurrent tokio tasks** — draining only one pipe while the other fills its OS buffer is a classic way for a child process to hang.
- **Truncation**: each captured stream is capped (e.g. last ~64KB, with an explicit "truncated" marker) before it goes back through MCP, so an unbounded build log doesn't blow up the tool response or the agent's context.
- **Timeout**: `build_timeout_secs` (project override, else a sane default) wraps the wait via `tokio::time::timeout`. On timeout, the **process group** is killed, not just the immediate child — build tools like `west`/`cmake`/`make` fork subprocesses that a plain `kill()` would orphan.
- **Exit-code handling**: `0` → proceed to the artifact check. Nonzero → reported as a build failure with captured output, artifact check skipped. `None` (killed/timed out/signaled) → reported explicitly as "timed out"/"killed", distinct from a compiler error, so a hang isn't misdiagnosed as a code problem.
- **Artifact freshness check**: the artifact path's existence and mtime are recorded *before* spawning. After a zero exit code, the file must now exist, and if it existed before, its mtime must be newer than the build-start time. Without this, a build that fails partway through (or a misconfigured `artifact_path`) could silently "succeed" by pointing at a stale binary from a previous build — the worst possible failure mode for hardware bring-up.
- **Concurrency**: one build (or `build_and_flash`) in flight per project name at a time, enforced by a lightweight per-project async lock. This is separate from Core's own hardware lock — it guards against two overlapping calls stomping the same build output directory, not against USB contention (Core already owns that).

## 7. Core HTTP client

- Built once at startup from `[core]` config: `base_url`, the resolved token, and a `reqwest::Client`. When `base_url` is the literal `"auto"` (§3.11), the address instead resolves on first use by racing a short-timeout `GET /status` at an ordered candidate list — `127.0.0.1:<port>`, then the WSL2 default-gateway IP when running under WSL2, then `host:<port>` if set — taking the first that answers, where a `401` counts as an answer (Core is there, the token is wrong: a distinct problem needing a distinct error message). The resolved address is cached for the process lifetime only, never written back to config, so a WSL2 restart's new gateway IP is picked up by the next invocation with no config edit. **Resolution must be lazy, not eager**: the startup connectivity check below is MCP-mode-only by design, and `list_projects` deliberately works with Core down — resolving `auto` at config-load time would regress both. `embarch-umbrella` needs the identical candidate race for its own `doctor`/`status` ([embarch-umbrella/design.md](../embarch-umbrella/design.md) §3 decision 6), and the resolution is that it is **written once there and copied here verbatim, module and tests together** — not extracted into a shared crate, and not reimplemented (§3 decision 15 there, which carries the reasoning and the drift mitigations). Expect to receive it as a self-contained module with no umbrella-specific types on its boundary. Token resolution (`CoreConfig::resolve_token`) runs through `token_discovery.rs`'s chain — `token`/`token_env`, then a machine-wide token-file fallback (same-OS path, or the WSL2⟷Windows-translated path when running under WSL2) — before failing; full detail in [embarch-token.md](../embarch-token.md).
- **Auth injection**: every request uses `.bearer_auth(&token)`, rendering `Authorization: Bearer <token>` — matching Core's exact-string check in `auth_middleware` (`api.rs`).
- **Per-call timeouts**, not one global client timeout: `status`/`reset`/`serial_log` use short budgets, `flash` gets its own longer one, since flashing can legitimately take much longer than a status check.
- **Error body handling**: Core's handlers return `(StatusCode, String)` on failure, which axum renders as a **plain-text body**, not JSON. embarch-api must parse JSON only on 2xx responses and read the body as plain text on non-2xx, folding it into the error message — attempting to `serde_json` a non-2xx body would fail and mask Core's actual error text. As of `embarch-core/design.md` §4/§11, that string is the full `anyhow` causal chain (`{e:?}`), not just Core's outermost context message — embarch-api's CLI/MCP error text should print it verbatim rather than truncating to a first line, since the actual cause (e.g. a probe-rs I/O error) is often further down the chain.
- **Startup connectivity check**: `main.rs` calls `GET /status` once during init, before starting the MCP server loop. If Core is unreachable, embarch-api refuses to start and reports a clear "Core unreachable at `<base_url>`" error rather than starting successfully and only surfacing the problem on the first tool call. This is a fail-fast choice, not a correctness requirement — Core could in principle come up later — but for a single-engineer local tool, catching a misconfigured `base_url` or a Core that forgot to launch at startup is more useful than a confusing failure three tool calls into a session.
- **Startup connectivity check is MCP-mode only.** The check above applies when embarch-api starts as an MCP server (§3.4). In CLI mode (§3.10), no eager connectivity check runs before dispatch — each subcommand's own Core call surfaces an "unreachable Core" error exactly as MCP would, and `list_projects` (which never calls Core) still works even with Core down entirely, which matters when debugging config alone.

### 7.1 Testing strategy

**Status: specified, not yet implemented** — no test files exist in the repo yet. The scenarios below are the acceptance criteria test code should satisfy, not a description of tests already written.

- `core_client.rs`, tested against a mocked HTTP server (e.g. `wiremock`), not a real embarch-core instance:
  - every outgoing request carries `Authorization: Bearer <token>` with the resolved token (inline or from `token_env`)
  - `status`/`reset`/`flash`/`serial_log` each honor their own configured timeout independently — a slow mock on one endpoint doesn't eat into another's budget
  - a non-2xx mock response is read as plain text and folded verbatim into the returned error — never handed to a JSON parser (§7's plain-text-vs-JSON rule)
  - a 2xx mock response deserializes into the matching response struct (`StatusResponse`, `FlashResponse`, `ResetResponse`, `SerialLogResponse`); malformed JSON on a 2xx surfaces a clear parse error rather than panicking

- `build.rs`, tested with fake `build_command`s (small scripts standing in for `west`), not a real toolchain:
  - exit code 0 plus a freshly-written artifact reports build success and artifact freshness both true
  - a nonzero exit reports build failure, with the artifact-freshness check skipped entirely
  - a command that outlives `build_timeout_secs` is killed as a process group (§6, unix) and reported distinctly as "timed out" — not conflated with a normal nonzero exit
  - a command that writes heavily to one of stdout/stderr while barely touching the other still completes without hanging — regression coverage for the two-pipe-must-drain-concurrently invariant (§6)
  - output beyond the captured-stream cap is truncated exactly on a UTF-8 character boundary, with the truncation marker present
  - an artifact that already existed before the build, with its mtime left untouched, is **not** treated as fresh even when the build exits 0 — the freshness check (§6) must distinguish "the build overwrote it" from "the build never touched it"

- No integration tests against a real embarch-core process are planned for v1 — the mocked-boundary approach was chosen specifically to keep tests independent of hardware/probe state.
- **Named tier, 2026-08-15 (§3 decision 30): a scripted smoke harness, `scripts/smoke.sh` or equivalent** — a throwaway `embarch-core` instance plus a small synthetic fixture repo, re-running a fixed sequence of `list_targets`/`build`/`flash`/`reset` calls. Not a substitute for the mocked unit tests above; a repeatable version of the live-verification pattern this doc's own changelog already shows being done by hand for every decision-12 milestone.

## 8. Security model

- **Inbound (MCP) trust boundary**: "whoever can spawn the embarch-api process." No API key, bearer token, or session exists at this layer — see §3.4.
- **Inbound (CLI) trust boundary**: identical reasoning to the MCP case, restated as "whoever can run the `embarch-api` binary locally, with a config file it can read." There's no additional session/token layer distinguishing a CLI invocation from an MCP-spawned one; both terminate at the same OS-level question of who can execute the binary and read its `--config`. One difference worth calling out, not a different trust boundary: an MCP-spawned process's lifetime and stdio are entirely owned by the spawning client, whereas the CLI is directly interactive — a human can run `embarch-api build <project>` themselves, immediately, with no client software mediating. This doesn't change *who* is trusted, it's just the path a human actually exercises day to day (§3.10).
- **Outbound (Core) credential**: `EMBARCH_TOKEN`, the same shared secret Core itself was started with, held either inline in config (`token`), via an env var (`token_env`, §4), or — if neither is set — discovered from the machine-wide token file Core generates (`token_discovery.rs`, §7). Full lifecycle (generation, storage, transport, rotation, threat model, known gaps) is documented in [embarch-token.md](../embarch-token.md) rather than here, including the file-permissions guidance for the inline `token` case.

## 9. Deployment model

Today: embarch-api (WSL2) and embarch-core (native Windows) run on the same physical machine as independent processes, embarch-api reaching Core over the WSL2⟷Windows network boundary rather than `127.0.0.1` — confirmed working end-to-end during milestone-1 (`embarch-core/design.md` §7). embarch-api never assumes `127.0.0.1`; Core's base URL is always a config value, because Core's own README already anticipates moving to a Raspberry Pi reachable over LAN.

**Artifact-transfer gap — closed for the WSL2-same-PC case (milestone-1 §3.3), still open for a genuinely separate machine.** Core's `/flash` endpoint takes a `firmware_path` string and reads it from *its own local disk*, so a path meaningful to the build side isn't automatically meaningful to Core. For the WSL2-same-PC topology (embarch-api building in WSL2, Core running natively on Windows on the same physical box), this is solved by `artifact_path_for_core` (§4): a per-project config field carrying the artifact's `\\wsl.localhost\<distro>\...` UNC form, which `flash`/`build_and_flash` send to Core instead of the WSL2-local path. Confirmed working against real hardware: a `west`-built `.hex` was flashed onto the physical nRF54L15 board this way. Two caveats found during that validation, both still open (§12): the field isn't yet populated in the real `config.toml` for `project-a-board` (validated so far via the CLI's `--firmware-path` override, not the config field itself), and the UNC path a caller would compute from `resolved_artifact_path()` (§6) doesn't currently match where `west build` actually wrote the artifact for this project. **This does not generalize** to Core running on a genuinely separate machine (e.g. a future Pi deployment reached over a real LAN, not a WSL2⟷host loopback) — that case still has no mechanism to get the artifact's bytes onto Core's filesystem at all, and remains the open gap: extending Core's `/flash` to accept a multipart upload, requiring a shared network mount, or adding an explicit "push artifact" step ahead of `/flash`.

## 10. Module layout

No `service.rs` equivalent (contrast with Core) — stdio MCP servers are spawned per-session by the MCP client, and the CLI subcommand mode (§3.10) is likewise a one-shot invocation, not a background OS service.

```
embarch-api/src/
├── main.rs        — clap CLI: `--config <path>` (falls back to EMBARCH_API_CONFIG, then a cwd-upward search for embarch/embarch.toml), an optional subcommand
│                    (`build`, `flash`, `build-and-flash`, `reset`, `serial-log`, `list-projects`, `list-targets`),
│                    and a `--json` flag (§5a); tracing→stderr init in both modes (stdout is the JSON-RPC
│                    transport in MCP mode, and is reserved for CLI-mode result/`--json` output in CLI mode);
│                    builds Config + CoreClient; dispatches to either the MCP stdio server (no subcommand, §3.4)
│                    or `cli.rs::run` (subcommand present, §3.10)
├── config.rs      — TOML schema structs (including `Discovery`/`StaticTarget`, §3 decision 12), load_from_path(),
│                    validation (unique project names, path existence, discovery-branched required fields)
├── core_client.rs — reqwest wrapper around Core's 5 endpoints (incl. `resolve_chip`, §3 decision 12),
│                    bearer-token injection, error mapping
├── token_discovery.rs — machine-wide token-file discovery fallback for `CoreConfig::resolve_token()`
│                    (§7): same-OS path, or WSL2⟷Windows path translation when running under WSL2
├── zephyr.rs      — §3 decision 12: board.yml/app live scan, cross-product target generation, file-backing
│                    revision/variant validation, board-qualifier/build-dir/artifact-path assembly, narrowing
│                    selection. Pure filesystem + YAML reads, no `west` invocation, no Core/network dependency
├── resolve.rs     — §3 decision 12: the one place every MCP tool/CLI subcommand branches on `discovery`,
│                    turning a `ProjectConfig` + `Selection` into a `build::BuildPlan` + chip +
│                    `artifact_path_for_core` — calls `core_client::resolve_chip` for a zephyr-west project,
│                    reads stored config fields directly for a static one
├── build.rs       — subprocess execution for a discovery-agnostic `BuildPlan` (§6, §3 decision 12)
├── tools.rs       — rmcp #[tool_router]/#[tool_handler] MCP surface; thin glue over config/resolve/build/core_client
└── cli.rs         — human-facing CLI subcommand surface (§5a), shipped; thin glue over the same
                     config/resolve/build/core_client modules tools.rs calls; formats results as human text
                     or `--json`, maps outcomes to process exit codes (§5a)
```

## 11. Relationship to embarch-core

Core owns all direct hardware access — `probe-rs` (flashing/reset) and `serialport` (UART log reads) live exclusively in Core. embarch-api never links against either crate; every hardware operation goes through Core's HTTP API. embarch-api's own domain is orchestration: turning a project name into a build, and a build's artifact into a Core `/flash` call, plus exposing all of it as MCP tools and CLI subcommands (§3.10, §5a).

## 11a. Relationship to embarch-umbrella

`embarch-umbrella` writes this project's config and shells out to its CLI to verify things, but is never in the runtime path — nothing routes through it once setup is done, and `embarch-api` has no knowledge that it exists (the same one-way relationship `embarch-core` has toward `embarch-api`, §11). Specifically, umbrella owns: scaffolding `<firmware-repo>/embarch/embarch.toml` (§4), registering this binary as an MCP server, putting it on `PATH`, and diagnosing a broken stack via `doctor`. Two `doctor` checks are capabilities this doc previously deferred and now expects to live there rather than here — `build_command[0]` resolving on `PATH` (§12), and an `artifact_path_for_core` that doesn't name the same file as `artifact_path` (§9, §12) — both of which are preflight diagnosis, not build orchestration. See [embarch-umbrella/design.md](../embarch-umbrella/design.md) §5, §9.

## 12. Open questions / future work

- **PATH/toolchain preflight validation** (e.g. confirming `west`/`arduino-cli` resolve on PATH before attempting a build, for a faster/clearer error than a raw `os error 2`) — still deferred from `embarch-api` itself, and now expected to land as `embarch-umbrella`'s `doctor` check 7 instead ([embarch-umbrella/design.md](../embarch-umbrella/design.md) §5, §11a above). The reasoning for keeping it out of the build path is unchanged: a build failure surfaces naturally as a nonzero-exit/error-output report, and preflight-checking every build would add latency to the common case to improve one uncommon error message. As a *diagnostic* run on demand, it's worth having — which is exactly what `doctor` is.
- **Config fragments / `include`**, so `[core]` isn't duplicated into every firmware repo's `embarch/embarch.toml` (§4). Deferred rather than rejected — `[core]` is three lines once `base_url = "auto"` lands (§3.11), which is what makes the duplication tolerable for v1.
- **Config hot-reload** — deferred from v1. Config loads once at startup; picking up edits requires restarting the MCP session (reconnecting the client).
- ~~**The artifact-transfer gap** described in §9, for a future Core-on-a-different-machine deployment.~~ — resolved 2026-08-15: §3 decision 15 (`embarch-core/design.md` §3 decision 10 is the Core-side half) adds a multipart-upload path used specifically for a `remote` topology; the WSL2-same-PC path via `artifact_path_for_core` is unchanged.
- **`serial_log` stays one-shot (capture for `duration_ms`, return, done) — not streaming.** This was a deliberate choice, not an oversight: Core's `/serial-log` endpoint is itself a bounded-duration capture rather than a stream, and MCP tool calls are fundamentally synchronous request/response. Building real streaming into embarch-api would require Core to grow a streaming mode first — out of scope for embarch-api to decide unilaterally, since Core "has no idea embarch-api or any MCP client exist" (§1). If long-running log tailing becomes a real workflow need, an agent can already approximate it by calling `serial_log` repeatedly with fresh `duration_ms` windows; true streaming is deferred until Core's API grows to support it.
- **Adding projects to the config remains manual TOML editing** — no `add_project` MCP tool or CLI subcommand planned (distinct from the `build`/`flash`/etc. subcommands added in §3.10, which invoke existing config, they don't mutate it). Confirmed choice, consistent with §3.6's "no database, single config file" philosophy: not enough churn in the project list to justify a second way to mutate it. **Partially superseded by §3 decision 12**: a `discovery = "zephyr-west"` project no longer needs a config mutation to add a board/variant/revision/app at all — `list_targets` discovers it live. This item's reasoning still holds fully for `discovery = "static"` projects and for adding a whole new *project* (as opposed to a target within one).
- ~~**§3 decision 12's open sub-questions**~~ — resolved 2026-08-13, folded into decision 12 itself rather than left here.
- ~~**CLI exit-code granularity**~~ — resolved 2026-08-15 (§3 decision 16): `--json`'s new `error_kind` field gives a scripted caller a failure-kind signal without inventing a distinct exit code per failure kind; the exit code itself stays a single `1` for any failure, unchanged.
- ~~**`--json` schema stability**~~ — resolved 2026-08-15 (§3 decision 24): `--json`'s object now carries `schema_version: u32`, bumped by hand only on a breaking shape change.
- **RESOLVED** — `artifact_path_for_core` was not populated in the real `config.toml` for `project-a-board`. Now set, using the corrected (`build_cwd`-less) workspace-root UNC path below, and confirmed to load correctly (`list-projects`). This closes the artifact-path gap for this project's config-only `flash`/`build_and_flash`, not just the `--firmware-path`-override path validated earlier (§9). Not yet re-validated against real hardware without the CLI override — worth a follow-up `build_and_flash` hardware run to confirm end-to-end, since only the manual-override form has actually flashed the physical board so far.
- **RESOLVED** — `resolved_artifact_path()` didn't match where `west build` actually wrote `project-a-board`'s artifact. Root cause confirmed by reading the project's own `build/build_info.yml` (recorded `west.command`): the real invocation runs with cwd = `source_path` itself, passing the app directory (`app/reference-dut`) as a positional argument to `west build`, not by `cd`-ing into it first — so west's default `<cwd>/build` output dir is `source_path/build`, never `source_path/app/reference-dut/build` as the old `build_cwd = "app/reference-dut"` assumed. Fixed by removing `build_cwd` from this project's config and moving the app path into `build_command`'s argv instead (`config.toml`, `config.example.toml`'s project #1 corrected the same way as a general lesson — §6). `build_and_flash` and a config-only `flash` (no `--firmware-path`) are now expected to work correctly for `project-a-board`; re-validate against real hardware to confirm (carries into whatever milestone next touches this project's flash path).
- **RESOLVED** — artifact-freshness check was racy under wall-clock jitter, observed on WSL2. §6's freshness check compares a filesystem mtime against a `SystemTime::now()` read taken just before the build subprocess spawns (`build.rs`'s `artifact_is_fresh`). An isolated repro on this WSL2 machine (spawn a child that writes a file, compare its mtime to the parent's pre-spawn timestamp) showed the child's file mtime landing a few milliseconds *before* the parent's own timestamp on some runs — not filesystem mtime-resolution truncation (confirmed ext4, nanosecond resolution), most likely Hyper-V/WSL2 clock-sync jitter between reads taken microseconds apart. Effect: a build that just genuinely wrote a fresh artifact could be reported as stale, causing `build_and_flash` (and the CLI's `flash`) to refuse to flash a good build. A monotonic-clock (`Instant`) fix, considered first, doesn't actually apply here — filesystem mtimes are wall-clock (`SystemTime`) values with no `Instant` equivalent to compare against, so there's no way to bracket the build with a monotonic reading and still compare it to the mtime. Fixed instead with a small fixed tolerance (`FRESHNESS_CLOCK_GRACE`, 500ms) added to the mtime side of the comparison in `artifact_is_fresh` — cheap because a real build takes at least seconds, so 500ms of grace can't mask a genuinely stale artifact left over from a previous run, only absorb the observed sub-second clock jitter.
