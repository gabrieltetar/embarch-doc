# embarch-api: design

**Status:** active, 2026-07-17. This document supersedes the chat-history discussion that produced it — treat this file, not a conversation transcript, as the source of truth going forward. Append changes to the Changelog (§13) rather than silently editing history above it.

## 1. Purpose and scope

`embarch-api` is the layer between an MCP client (e.g. Claude Code, or any other MCP-speaking agent or tool) — or a human directly at a terminal, via its own CLI (§3.10) — and `embarch-core`. Core owns the debug probe and serial connection and deliberately "has no idea the EmbArch API or any MCP client exist" — it just exposes 4 bearer-token-authed HTTP endpoints (`/status`, `/flash`, `/reset`, `/serial-log`). embarch-api is what gives those endpoints meaning to an agent or a human: it exposes them as MCP tools and CLI subcommands, and adds the one capability Core intentionally does not have — running a project's build and handing the resulting artifact to Core's `/flash`.

embarch-api is **not**:
- A multi-user or multi-tenant service. Each engineer runs their own full stack (own embarch-api, own embarch-core).
- A database-backed system. All state is a single TOML config file.
- A toolchain-aware build system. It runs whatever command a project's config specifies and does not understand `west`, `idf.py`, `arduino-cli`, or any other tool's internals.

**Out of scope for this document:** repository bootstrap (`git init`, an initial commit, `README.md`, CI, `LICENSE`) and the actual test code described in §7.1. Both are real, necessary work — this repo has no git history yet, and §7.1's testing strategy has no test files behind it — but they're implementation/process work, not design decisions, so they're deliberately left for a separate pass rather than specified here.

## 2. Architecture overview

```
       build_command subprocess (west / arduino-cli / etc.)
                                  |
MCP client --stdio(spawn)--> embarch-api --HTTP+Bearer--> embarch-core --probe-rs/serialport--> hardware
                                  |
                  human, direct: `embarch-api <subcommand> ...`
```

`embarch-api` is reached two ways: over MCP stdio by an MCP client (Claude Code, or any other MCP-speaking agent/tool), and directly via its own CLI subcommands (`build`, `flash`, `build-and-flash`, `reset`, `serial-log`, `list-projects` — §3.10, §5a) by a human at a terminal with no agent in front of them. Both converge on the same `config.rs`/`build.rs`/`core_client.rs` modules and the same per-project build lock — there is no separate code path for "CLI mode," mirroring the exact MCP-vs-CLI convergence `embarch-core/design.md` already established between its own HTTP API and its CLI (§2, §9 there). The MCP client spawns embarch-api as a local subprocess and talks MCP over stdio; the CLI is instead a direct, one-shot invocation with no client software mediating it. Either way, embarch-api talks plain HTTP to embarch-core, authenticating with the same `EMBARCH_TOKEN` Core itself expects. Build commands run as subprocesses of embarch-api, in the source tree of whichever project was named.

## 3. Locked-in design decisions and rationale

> **Numbering note (2026-08-25): there is no decision 31 — the list runs 30, 32, 33.** The MCP-schema fix logged below as "new decision 31" ended up numbered **33**, and five cross-references in this file still pointed at the vacant 31 until they were corrected while implementing Milestone 7 Phase B item 2. The gap is left rather than closed by renumbering, for the same reason `embarch-study-designer` declined to renumber its schema constants: every reference already written elsewhere would become ambiguous about which scheme it was counted in. Read "decision 31" in an older doc or commit message as decision 33 — and note that `embarch-core` has its own, unrelated, very-much-real decision 31, which several references here legitimately point at.

1. **Single user, single Core instance.** No multi-tenancy, no user/permission model, no database. This was explicitly revisited mid-design — the original framing raised "what if EmbArch API is multi-tenant, make it full" — but the resolution was that each engineer runs their own complete stack (their own embarch-api talking to their own embarch-core), so there is no multiplexing to design for. Revisit this document if that assumption ever changes.
2. **Language: Rust**, matching embarch-core. Reuses Core's structuring patterns (an `AppState`-equivalent, `anyhow`-based error handling) and keeps the whole project to one toolchain.
3. **Purpose: MCP server, CLI, and build orchestrator.** The three responsibilities embarch-api adds on top of Core are (a) exposing Core's capabilities as MCP tools for any MCP client, (b) exposing the identical capabilities as CLI subcommands for a human with no MCP client in front of them (§3.10), and (c) running a configured build command and feeding the artifact to Core's `/flash`.
4. **MCP transport: stdio**, with the MCP client spawning embarch-api directly, when no subcommand is present on the command line (§3.10 governs the alternative). This was chosen over exposing embarch-api's MCP surface as its own HTTP+API-key service. The consequence: the trust boundary for embarch-api's *inbound MCP* interface is simply "whoever can spawn the process" — there is no bearer token, API key, or session concept protecting the MCP surface itself. This is a deliberate simplification, not an oversight; if embarch-api is ever run detached from an interactive MCP client session (e.g. reachable over a network), this decision needs revisiting. Note this is entirely separate from the *outbound* credential embarch-api needs to talk to Core — see §9. This decision governs MCP mode specifically; embarch-api also has a second, human-facing inbound interface — see §3.10.
5. **Build orchestration: generic configurable command per project, not toolchain-specific logic.** Originally motivated by an assumption that the two real projects this manages day one used different toolchains (Zephyr/`west` vs. Arduino-CLI/PlatformIO) — on inspection both turned out to be Zephyr/`west`-based (see §4's note on `project-b-mkr`), but the generic-command design is kept regardless: it's the right call on its own merits (no toolchain-specific logic to maintain, works for whatever a future project uses) even though the original two-toolchain premise didn't hold.
6. **Persistence: a single TOML config file, no database.** Matches the single-user, single-Core scope — there's no multi-row data (users, boards-across-tenants, audit trails) that would justify SQLite or Postgres.
7. **Deployment: same machine as Core today, but Core's base URL stays configurable, never hardcoded to `127.0.0.1`.** Core's own README already flags a possible future move to a Raspberry Pi reachable over LAN; embarch-api should not bake in an assumption that will break when that happens.
8. **This document is the durable design record.** Core's README references "the design discussion" without pointing anywhere — this file is meant to be that pointer for embarch-api going forward.
9. **Dependency choices are locked, not incidental.** MCP protocol/transport: the `rmcp` crate (`server` + `transport-io` features), using its `tool_router`/`tool_handler` procedural-macro pattern — chosen over hand-rolling JSON-RPC, since MCP's schema/handshake plumbing isn't worth re-deriving per project. HTTP client: `reqwest` built on `rustls` rather than `native-tls`, specifically to avoid pulling in a system OpenSSL dependency — keeps embarch-api trivially buildable on whatever machine an engineer's Core happens to run on (§9). CLI: `clap` (derive). Config parsing: `toml` + `serde`. MCP tool parameter schemas: `schemars`'s `JsonSchema` derive, which `rmcp` requires to generate each tool's declared input schema. Exact versions are pinned in `Cargo.toml`/`Cargo.lock`, not restated here.
10. **A CLI subcommand interface, invoked directly by a human, added alongside MCP — not a separate service, not a separate binary.** `embarch-api build|flash|build-and-flash|reset|serial-log|list-projects <args>` runs the identical `config.rs`/`build.rs`/`core_client.rs` orchestration MCP's `tools.rs` already calls (§10), mirroring the pattern `embarch-core` established between its own CLI and HTTP API (`embarch-core/design.md` §2, §9): two front-ends, one set of modules underneath, neither privileged over the other. This closes a real gap: without it, an engineer with no MCP client in front of them (no Claude Code, no other agent) had no way to invoke embarch-api's build orchestration at all, and would have had to either run the build manually or call embarch-core's HTTP endpoints directly — bypassing embarch-api's config-driven `build_command`, artifact-freshness check, and timeout/process-group handling entirely. **Subcommand presence is the mode switch**: no subcommand → MCP stdio server (§3.4, fully backward compatible with every existing MCP client config that spawns `embarch-api --config <path>`); a subcommand present → run that one operation as a human-facing CLI call and exit. See §5a for the subcommand surface, §8 for the CLI's trust boundary, §10 for `cli.rs`. This decision is recorded ahead of implementation — no `cli.rs` exists yet in the actual source tree; see `milestone-1.md` for the execution plan.
11. **Core's address may be declared as `base_url = "auto"`, resolved per-process at first use — not written down as a literal address at setup time.** *(Shipped 2026-08-05 — see §4, §7, and [embarch-umbrella/design.md](../embarch-umbrella/design.md) §3 decision 9.)* The WSL2⟷Windows split (§9) reaches Core at the WSL2 host-gateway IP, which changes across WSL2 restarts, so a literal IP in the config is guaranteed to go stale — and did: this project's real `config.toml` carried `172.22.128.1` while `embarch-core/design.md` §7 recorded `172.29.64.1`. Resolution belongs here rather than in `embarch-umbrella`'s setup step precisely because the value has to be right *at the moment a build is flashed*, not at the moment setup last ran, and `embarch-api` is the process present then. This does not weaken §3.7 — Core's address is still never hardcoded to `127.0.0.1`; `auto` is an explicit opt-in that makes localhost merely one candidate, and an explicit URL still wins outright.

12. **Zephyr/west projects get live target discovery instead of a static per-board `[[projects]]` entry; every other build system keeps today's fully-static schema, unchanged.** A Zephyr board's buildable surface (which boards, SoCs/cpuclusters, variants, hardware revisions, apps) is a property of the *current* state of `boards/*/board.yml` and `app/*/`, not something safe to snapshot into a config file once — and not every combination `board.yml` *declares* is real ([embarch-zephyr.md](../embarch-zephyr.md) §2.1's revision-backing gotcha, §2.2's variant-less-build gotcha). Full board-qualifier grammar/revision/snippet/sysbuild background lives in [embarch-zephyr.md](../embarch-zephyr.md), not here. Implementation history and the real-repo bugs that shaped this decision are in this section's own Changelog (§13) and [embarch-decision-reversals.md](../embarch-decision-reversals.md) — *(trimmed 2026-08-15, closing item 60 of that day's design-improvement review: this decision previously carried ~70 lines of dated implementation narrative that belonged in the changelog per `DOC-PROTOCOL.md` §5, not in the current-state decision text)*.

    **For a project detected as Zephyr/west-shaped** (`boards/*/*.yml` plus at least one `app/*/CMakeLists.txt` under `source_path` — the same shape `init` recognizes via [embarch-umbrella/design.md](../embarch-umbrella/design.md) §3 decision 13's `build/build_info.yml` check): `[[projects]]` stores only what can't be derived from the repo and doesn't change as it evolves:

    ```toml
    [[projects]]
    name = "reference-dut-fw"
    source_path = "/path/to/repo"
    discovery = "zephyr-west"        # new field; omitted = "static", today's schema, fully unchanged
    west_binary = "/path/to/.venv/bin/west"
    build_dir_root = "embarch/build" # per-target subdirectories computed under this, never shared
                                      # (embarch-umbrella/design.md §3 decision 10)
    flash_format = "hex"
    build_timeout_secs = 900
    default_snippets = ["ble-shell"]        # optional
    default_extra_args = ["-p", "always"]   # optional
    ```

    Everything else is resolved **live, per call, never cached into config**:
    - **Board/variant/revision/app enumeration** is pure filesystem + YAML reads — no `west` invocation, cheap enough to re-run on every `list_targets` call.
    - **File-backing validation** — a (board, soc, cpucluster, variant?, revision) tuple is real only if: a real `.dts` file exists for that (board, soc, cpucluster, variant) combination (`dts_exists`); the revision equals `board.yml`'s declared default (implicitly backed) or a revision-suffixed overlay/defconfig exists; and, for a board using a custom (non-standard) revision format, the board's own revision logic doesn't reject the combination. A SoC with named product variants also gets one synthesized variant-less candidate per cpucluster ([embarch-zephyr.md](../embarch-zephyr.md) §2.2), run through the same gate.
    - **Build directory**: `build_dir_root/<board>-<variant-or-'default'>-<revision>-<app>-<snippets-or-none>-<extra_args-hash>/`, one per distinct target, satisfying [embarch-umbrella/design.md](../embarch-umbrella/design.md) §3 decision 10 without a human naming each one.
    - **Artifact path**: `<build dir>/zephyr/zephyr.hex` (or whatever `flash_format` implies) — searched for, not assumed at a fixed layout, per [embarch-zephyr.md](../embarch-zephyr.md) §4's sysbuild note.
    - ~~**`artifact_path_for_core`**: computed at call time against the resolved build dir, whenever `embarch-api` runs under WSL2 — never hand-written or stored.~~ **Retired 2026-08-18** (§9): superseded by `flash` uploading the artifact's bytes directly for any topology that doesn't share a filesystem, rather than computing a path Core is assumed to be able to open. No `Resolved` field, no config field, no computation — see §9 for the full replacement mechanism.
    - **`chip`**: resolved from the selected SoC via `embarch-core`'s `POST /resolve-chip` (`embarch-core/design.md` §3 decision 8), consulting the project's own `soc_chip_overrides` first (§3 decision 13) — `embarch-api` holds no SoC→chip table of its own. An unmapped SoC with no override is a call-time error pointing at `probe-rs chip list`. One project can span more than one SoC (`ref_nrf54dk` does, across three), so "one chip per project" was never the right shape.

    **New tool: `list_targets(project)`** (MCP tool + `list-targets` CLI subcommand). For a `zephyr-west` project, returns every validated (board, soc, cpucluster, variant, revision, app) tuple, plus `snippets_by_app` (every real `-S` snippet under `app/<app>/snippets/**/snippet.yml`, [embarch-zephyr.md](../embarch-zephyr.md) §3), `default_snippets`, and `default_extra_args`. Never cached at any granularity — caching would reintroduce the exact staleness this decision exists to eliminate.

    `build`, `flash`, `build_and_flash`, and `reset` each take four optional selection params — `board`, `variant`, `revision`, `app` — validated against the live scan before any command is assembled, plus `snippets`/`extra_args` below. **Selection is never guessed, but it is narrowed**: whatever subset is given filters the live-scanned set; exactly one match proceeds directly, more than one is a call-time error listing the narrowed remainder, none given lists everything `list_targets` would. `reset` needs the same four params as `flash` — it calls Core with a `chip` too, and a `zephyr-west` project has none stored to fall back to. `flash`'s `firmware_path` override bypasses *build*-target resolution (which directory/artifact) but not *chip* resolution — there's still no stored chip to fall back to for a `zephyr-west` project.

    **`snippets`** — a fifth, purely additive param, not a narrowing axis (a snippet choice doesn't change which target tuple exists, [embarch-zephyr.md](../embarch-zephyr.md) §3), validated against `available_snippets` for the resolved app. Omitting it (or an empty list) falls back to the project's `default_snippets`, not "no snippets" — the sentinel `["none"]` forces zero snippets over a configured default (§3 decision 21). A non-empty explicit list overrides the default entirely, it does not add to it. Folded into `Target::build_dir_name`.

    **`extra_args`** — opaque passthrough (e.g. `["-p", "always"]`), unvalidated (no real-file list to check an arbitrary flag against, same posture as `discovery = "static"`'s whole `build_command`, decision 5), inserted right after the `build` subcommand and before `-b`. Falls back to `default_extra_args` on an empty selection, same override-not-additive semantics as `snippets`. Folded into `Target::build_dir_name` via a hash of the unsorted argument list (flag order can be meaningful; an arbitrary flag can contain directory-unsafe characters).

    **For a `discovery = "static"` project** (the default — every project configured before this decision, and every non-Zephyr project after it), nothing changes: `build_command`/`chip`/`artifact_path` stay exactly as documented in §4, and `build`/`flash`/`build_and_flash`/`reset` ignore the five new params entirely (`artifact_path_for_core` no longer exists for either discovery mode — §9). A static project that still wants a selectable menu can declare one by hand:

    ```toml
    [[projects.targets]]
    name = "target-a"
    build_command = ["make", "TARGET=a"]   # overrides the project-level fields when this target is selected
    chip = "..."
    artifact_path = "..."
    ```

    `list_targets` on a static project returns these rows verbatim if any exist; if none do, it errors with the exact TOML shape above rather than a bare "not applicable."

    **The one existing principle this scopes an exception into:** decision 5's "generic configurable command per project, not toolchain-specific logic" stays true for *how* a command runs (still an opaque argv, still no shell) and for every non-Zephyr project unconditionally — but `embarch-api` now has to understand Zephyr's board-qualifier grammar and file conventions well enough to assemble that argv for a `zephyr-west` project. Deliberate, scoped cost, not a reversal of decision 5.

13. **A per-project `soc_chip_overrides` table gives a `zephyr-west` project an escape hatch for a SoC `embarch-core`'s `/resolve-chip` doesn't know about (2026-08-15, closing item 2 of that day's design-improvement review).** Decision 12 removed the old `chip` field entirely for a `zephyr-west` project, and `/resolve-chip` 404s naming the unmapped SoC — but there was nowhere to *write the answer* once `probe-rs chip list` (or `embarch-core`'s new `chip-list` subcommand, `embarch-core/design.md` §10) found the right string. New optional `[[projects.soc_chip_overrides]]` table, `zephyr-west`-only: `{ soc = "esp32c3", chip = "ESP32C3" }` entries, consulted by `resolve.rs` *before* calling `/resolve-chip` — a hit short-circuits the HTTP call entirely (no reason to ask Core about a SoC the operator already resolved by hand), a miss falls through to `/resolve-chip` exactly as today. Keeps Core's own mapping table as the source of truth for the common case (decision 12's original rationale, unchanged) while giving the uncommon case a real fix instead of a dead end.
14. **`embarch-api` starts in MCP mode even when Core is unreachable at startup — the eager connectivity check becomes a warning, not a refusal (2026-08-15, closing item 3... wait, item 5).** §7's "startup connectivity check" previously refused to start the MCP server at all on a failed `GET /status`, which meant every one of the nine MCP tools vanished from the agent's view with no way to learn why — directly contradicting §5's own rule that failures should come back as tool text an agent can reason about. Resolved: the startup check still runs and still logs a clear warning, but no longer blocks the server from starting. `status` reports the unreachability with the same "Core unreachable at `<base_url>`" text the check already produces; every hardware-facing tool (`build`/`flash`/`reset`/`serial_log`/`list_targets` for a `zephyr-west` project needing `/resolve-chip`) fails per-call with that same message plus the resolved-candidate list (`base_url = "auto"`'s candidate race, §3.11/§7) rather than never being callable at all. `list_projects` is unaffected either way, matching its existing Core-down tolerance (§7).
15. **`/flash`'s artifact transfer keeps `firmware_path` on a same-machine topology, and uploads bytes instead everywhere a shared filesystem can't be assumed (design-only 2026-08-15, closing item 9's `embarch-api`-side half; actually implemented 2026-08-18, and with a wider trigger condition than originally designed — §9 carries the full story).** Originally scoped to trigger only for a `remote` Core (topology v), on the theory that `local`/`wsl-host` always share a filesystem — 2026-08-18 found that premise false for `wsl-host` specifically, when Core runs as the installed Windows service rather than in the foreground (Session 0 can't reach `\\wsl.localhost` at all, §9). `CoreClient::flash` (`core_client.rs`) now branches on `TopologyClass` instead: `Local` (same machine, or a declared explicit `base_url`) keeps sending `firmware_path` as JSON, unchanged; `WslHost` *and* `Remote` both upload the artifact's bytes as `multipart/form-data`. `artifact_path_for_core` and its WSL2 UNC computation are fully retired, not left unchanged as originally planned — see §9 for why keeping them stopped making sense once bytes-upload covers `WslHost` too. `embarch-core/design.md` §3 decision 10 is the Core-side half, also actually implemented this pass (previously design-only despite §4's endpoint table already documenting the multipart body shape as if it existed).
16. **`--json`'s error object gains `error_kind`, matching Core's new structured error body — and covers failures that never reach Core at all (2026-08-15, closing item 11's `embarch-api`-side half).** Core's `{code, message, cause}` (`embarch-core/design.md` §3 decision 12) gives `embarch-api` a real error kind to pass through instead of parsing prose: a Core-originated failure's `code` becomes `--json`'s `error_kind` verbatim. For a failure that never reaches Core — an unloadable config, a build that failed before any HTTP call, an unresolvable `zephyr-west` target — `error_kind` takes one of a small `embarch-api`-native set (`config_error`, `build_failed`, `target_unresolved`, `core_unreachable`) instead. This retires §12's "CLI exit-code granularity" open item as a distinct problem — a script that needs to branch on failure kind now has `error_kind` in `--json`, not a reason to invent a finer-grained exit-code taxonomy on top of it.
17. **`embarch-api` checks Core's new `contract_version` at the same point it already checks `study_designer_schema_version` — item 13's `embarch-api`-side half.** `core_client.rs`'s `status()` call (§7) now also compares `/status`'s `contract_version` (`embarch-core/design.md` §3 decision 13) against a compiled-in `EXPECTED_CORE_CONTRACT_VERSION` constant, warning (not refusing — matching `embarch-umbrella/design.md` §3 decision 14's existing warn-only version-skew posture) on mismatch, in the same log line the existing schema-version check already produces.
18. **Truncation keeps head *and* tail, not just the last ~64KB (2026-08-15, closing item 28).** §6's existing truncation (each captured stream capped before returning through MCP) kept only the tail — for a Zephyr build, the *first* compiler error is usually the actionable one, and a long build's early failure could scroll entirely out of a tail-only cap by the time `cmake`/`ninja` finish emitting later, less useful output. Changed to a head+tail split (e.g. the first ~32KB and the last ~32KB of a ~64KB total budget, with the truncation marker naming how much was dropped from the middle) — unchanged for anything already under the cap.
19. **`extra_args`' hash-only build-dir name gets a readable prefix, plus a `target.json` recording the full resolved selection (2026-08-15, closing item 29).** Decision 12's `extra_args` folds into `Target::build_dir_name` via a hash of the (unsorted) argument list, since an arbitrary flag can contain directory-unsafe characters — but a bare hash makes `embarch/build/<hash>/` undebuggable to a human staring at a directory listing. Two additions, no change to the hash itself (still what disambiguates two otherwise-identical targets): the directory name gains a readable prefix ahead of the hash (`<board>-<variant-or-default>-<revision>-<app>-<snippet-list-or-none>-<extra-args-hash>/`, i.e. every other axis spelled out, only `extra_args` hashed); and each build directory gets a `target.json` written alongside the build output, recording the full resolved `Target` (every axis, snippets, and the literal `extra_args` list) — so a human (or an agent) can `cat target.json` to recover exactly what produced that directory without reverse-engineering a hash.
20. **A project-level `default_target` config field documents and pins the common single-target case, and the narrowing-to-singleton behavior itself is now stated as a caveat, not left implicit (2026-08-15, closing item 30).** Decision 12's narrowing (an unambiguous partial selection proceeds without erroring) means a call that works today can start erroring once a second board/variant lands in the repo — silently changing behavior as the repo grows, with nothing in the doc warning a reader this could happen. Stated explicitly here now. New optional `default_target: { board?, variant?, revision?, app? }` per-project config field (`zephyr-west` only): when set, it's applied as the *base* selection before a call's own params narrow further — a call's own `board`/`variant`/etc. still override the default per-field, but omitting all four now resolves against the pinned default instead of the live-scanned full set, keeping a repo's common case stable even after a second target is added.
21. **A sentinel value forces "no snippets" over a configured `default_snippets` (2026-08-15, closing item 31).** Decision 12's snippet support had no way to override a non-empty `default_snippets` down to nothing — omitting `snippets` falls back to the default, and there was no third state between "use the default" and "use this explicit list." New reserved literal: `snippets = ["none"]` (a single-element list containing the literal string `"none"`, chosen since `"none"` can't itself collide with a real Zephyr snippet name — `available_snippets` names are directory-derived identifiers, not reserved words) means "build with zero snippets regardless of `default_snippets`," validated and stripped before the `-S` flags are assembled. Any other explicit list, including one containing `"none"` alongside other names, is a call-time error naming the ambiguity, rather than a silently-wrong interpretation.
22. **The uncached live Zephyr scan's cost-bound assumption is stated, not left implicit (2026-08-15, closing item 32).** Decision 12 deliberately never caches `list_targets`' filesystem+YAML scan, reasoned as "already cheap enough" — but no bound was ever written down for what "cheap enough" assumes about repo size. Stated here: the design assumes a `boards/`/`app/` tree in the same order of magnitude as the reference-dut repo this decision was built against (single-digit boards, low tens of variant/revision/app combinations, low hundreds of files touched by the scan) — comfortably sub-100ms on ordinary local storage. A repo an order of magnitude larger (hundreds of boards) hasn't been measured against this assumption; if `list_targets` or `build`'s pre-assembly validation ever becomes perceptibly slow in practice, that's the signal to revisit caching, not a reason to add it pre-emptively now.
23. **No new `doctor` MCP tool — `embarch-api` stays unaware `embarch-umbrella` exists, and an agent shells out to `embarch doctor --json` directly instead (2026-08-15, closing item 33).** Adding a `doctor` tool to `embarch-api`'s own MCP surface would mean `embarch-api` either reimplementing `embarch-umbrella`'s full diagnostic chain (`embarch-umbrella/design.md` §5) or gaining a dependency on the `embarch` binary — both break the deliberate one-way relationship §11a already establishes (`embarch-umbrella` shells out to `embarch-api`'s CLI; never the reverse). Resolved instead by stating explicitly, here, what was previously left for an agent to discover on its own: an agent hitting a misconfiguration it can't diagnose from `embarch-api`'s own tool errors should invoke `embarch doctor --json` as a shell command (assuming `embarch-umbrella/design.md` §3's `setup` already put it on `PATH`), not assume `embarch-api` has an equivalent tool of its own.
24. **`--json`'s object schema gains a `schema_version: u32` field, versioned from the start rather than after a UI depends on the unversioned shape (2026-08-15, closing item 34).** §5a's `--json` output has no version marker today; `embarch-umbrella/design.md` §10's anticipated UI is exactly the kind of external consumer that would otherwise have no way to detect a future breaking shape change. Bumped by hand only when a field is renamed/removed/retyped — matching the same discipline `STUDY_DESIGNER_SCHEMA_VERSION` and `embarch-core`'s new `contract_version` (§3 decision 13 there) already establish for their own wire shapes.
25. **§4 states plainly that config resolution happens once, at process start, binding an MCP session to whichever repo spawned it (2026-08-15, closing item 35).** True today and probably the right behavior (an MCP client's spawn cwd is exactly "which repo am I working in" for the session's lifetime) — but §4's cwd-upward search (2026-08-13's addition) never said so explicitly, leaving a reader to infer it. 36. **`main` spawns the entire tokio runtime (`block_on` included) on a dedicated thread with an explicit 512 MiB stack, fixing two previously-separate-looking stack-overflow bugs with one change — Milestone 3, 2026-08-24.** The first real GATT-sized `study_status` call (a real 3-step Milestone 3 study, `BleConnect`->`GattDiscover`->`GattMonitorAll`, against real hardware) reproduced `embarch-study-designer/design.md` §7's already-tracked debug-build `Study`/`StudyResult`-deserialization stack overflow for real in production — not just in a test or a tiny 2-step fixture (decision 33's own finding) — crashing the live MCP server repeatedly (each crash silently respawned a fresh process, `Connection closed` on the client side) and the `study-status` CLI subcommand run directly.

    **First fix attempt didn't work, and why matters:** `tokio::runtime::Builder::thread_stack_size` only sizes threads the runtime itself spawns (worker/blocking-pool threads) — the top-level future driven by `block_on` still runs on whatever thread calls it, which for a plain `#[tokio::main] fn main` is the process's own main thread, at the OS/platform default stack size, with no `Builder` knob to change it. Confirmed by reproducing the crash again with `thread_stack_size(64 MiB)` alone still set: `thread 'main' has overflowed its stack`, naming `main` explicitly, not a tokio worker.

    **Real fix:** `main` now does `std::thread::Builder::new().stack_size(512 * 1024 * 1024).spawn(|| { tokio::runtime::Builder::new_multi_thread()...build()?.block_on(async_main()) })` — the same "spawn a thread with an explicit stack size" idiom `embarch-api`'s own tests already use for the identical underlying cause (`study.rs`'s `self_test_fixture_round_trips_end_to_end`), now applied to the real binary. 64 MiB (this repo's own `RUST_MIN_STACK` test precedent) was empirically insufficient against this real, GATT-heavy payload — 512 MiB was needed. Verified against the real live study: `study_status` now returns full `gatt_services`/`gatt_activity` content correctly, no crash, via both the CLI and MCP.

Since `async_main`'s entire body — including the CLI startup path — now always runs inside the dedicated 512 MiB thread regardless of build profile, a `--release` build of `list-projects` was re-tested and now runs clean.     **BUILT 2026-08-26 — the shared trigger fired, and the implementation is a rule rather than a parameter.** [embarch-outpost](../embarch-outpost/design.md) Phase C emits a real manifest, so this half and [embarch-core/design.md](../embarch-core/design.md) §3 decision 30(c)'s receiver shipped in the same pass, exactly as one trigger governing both was supposed to produce.

    `embarch-core-client::flash` looks for `outpost-manifest.json` **beside the firmware it is about to send** and attaches it — as `manifest_path` on the JSON body for a Local Core, as a `manifest` part on the multipart body for `WslHost`/`Remote`, where a path on this side is not openable on that one.

    **Derived from the firmware path rather than added as a parameter, and that follows from this decision's own reasoning.** It says the engineer never handles this file "because the failure mode of forgetting is not a visible error but a silently mislabelled trace." A parameter is a thing a caller can forget, and there are a dozen `flash` call sites across `tools.rs`, `cli.rs` and `reflash.rs` — every one of them a place to forget it. A rule applied inside the client cannot be. It also means nothing needs to know which board it is talking to: a dev-bench build leaves no manifest beside its artifact, so none is sent, and Core's own clear-on-flash keeps that from disturbing the DUT's binding.

    **`study_stream_data` needed no outpost-specific work**, which is the parameterised tool paying for itself: it already serves any declared tap by name, so an `outpost` tap's `*.trace.csv` and its raw `.bin` (with `raw=1`) are reachable the day Core starts writing them.

    The paragraph below is kept as the record of why this waited a day.

    **Settlement 2026-08-25 (Milestone 7 Phase B item 2): the manifest half is deferred under Core's own trigger, and that is a decision rather than a silence.** `CoreClient::flash` would need a `manifest` part on the multipart body and a `manifest_path` field on the JSON one — and Core's `POST /flash` accepts neither, deliberately: [embarch-core/design.md](../embarch-core/design.md) §3 decision 30's Settlement 2 closed manifest storage, selection, verification and refuse-to-render as four mechanisms with nothing able to exercise any of them. Nothing emits an `outpost-manifest.json` today, so there is nothing here to pick up and nowhere to put it, and building the sender against an absent receiver is a tested surface with no caller — the shape [embarch-topology/design.md](../embarch-topology/design.md) §3 decision 18's amendment (b) already records as a mistake worth not repeating. **The trigger is identical to Core's, on purpose: [embarch-outpost](../embarch-outpost/design.md) Phase C emitting a real `outpost-manifest.json` from a real ELF.** One trigger for both halves, because a manifest sender and a manifest receiver are useless apart. Written here rather than only in a changelog line so item 2 is not later read as having shipped a third of its scope silently.

    **Implemented 2026-08-25 (item 2), except the manifest above.** `study_stream_data { study_id, name, raw? }` and `list_study_streams { study_id }` exist as MCP tools and as `study-stream-data`/`list-study-streams` CLI subcommands; `embarch-core-client` gained `get_study_stream`, built on the same `get_study_csv` helper the three aliases already shared, so all four calls have one implementation of timeouts, auth, and the `404`-is-expected posture. **Three things this half settled:**

    - **`list_study_streams` needed no new Core route, and confirming that was the work.** `GET /study/{id}` already returns the whole `StudyResult` inline once a study is `"completed"`, and `StudyResult.streams` has been written there since item 1 — so the tool is a projection of a call that already existed. A listing endpoint Core does not need is exactly the surface this suite keeps deciding not to build.
    - **`truncated` is what the listing is *for*, so it is carried verbatim and named loudly.** `StreamRef.truncated` is set both when a retention rotation deleted a segment and when a `StreamClose` reported a non-zero `dropped` — two different losses a reader cares about identically. A listing that dropped the flag would hand back a capture that reads complete and is not, which is worse than no listing. Both the MCP description and the CLI's human output say so in as many words, and `bytes_written: 0` is presented as its own distinct fact: a tap that was declared and captured nothing is not the same as a tap that was never declared.
    - **The three aliases' descriptions were updated, not frozen — and this is the third open question item 2 was handed.** Decision 33's don't-move-ground-under-a-live-client posture protects a client's *working invocation*: same tool name, same parameters, same bytes back. It does not protect stale prose, and `study_waveform_data`'s text still described "StreamCapture steps", an `Action` retired at schema v8. Leaving a description that is simply false is the mislabelling class this whole area keeps closing. So the names and parameters are untouched, the returned bytes are pinned byte-identical by a test in Core, and the text now says what each alias actually resolves (which tap answers which alias), that it is an alias kept for one release, and that `list_study_streams` is where truncation lives — which the aliases structurally cannot report.

40. **`run_study` gains a reflash selector, and `embarch-api` will not check out a git revision to satisfy a version requirement — 2026-08-25.** The orchestrating half of [embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 40. A `Study` declares which dev-bench and DUT builds it is meant to run against; this is where a human or agent says what to do about it.

    **`run_study(..., reflash: "none" | "dev-bench" | "dut" | "both")`**, defaulting to `"none"` — the safe default, since flashing is the destructive-ish half and a study that merely observes a board you just flashed by hand should not silently reflash it. `"none"` with a version mismatch is a hard failure naming both strings, not a warning; `--allow-version-mismatch` proceeds and the override is recorded in `StudyResult.provenance` rather than honoured silently.

    **`embarch-api` never runs `git checkout` to reach a required version, and this is the load-bearing constraint.** "Reflash" means: build and flash the configured project **as the working tree currently stands**, then verify the version that produced matches what the `Study` requires — and fail, naming both, when it doesn't. It does not mean "make my tree be that version." Manipulating an engineer's working tree to satisfy a test harness is a genuinely destructive act on the thing they are actively editing, and this repo already has a recorded instance of that class of overreach being flagged (`embarch-roadmap.md` Milestone 5's own opening). The failure message says which revision the study wants; moving the tree there stays the engineer's decision.

    Sequencing is check → build → flash → `POST /study`, all here, because Core has no build system (`embarch-core/design.md` §3 decision 31). Core still independently gates on the dev-bench version, so this orchestration is convenience, not the enforcement point.

    **Implemented 2026-08-25 (Milestone 7 Phase B item 2) — and item 2 turned out not to be an `embarch-api`-only item, which is stated here rather than folded into a summary.** The milestone scoped it as "api". Building it moved `embarch-study-designer` (a new `Provenance` field, host schema v10) and `embarch-core` (`POST /study`'s two query parameters, and the gate reading them) as well, for a reason visible only once four facts are put together: the override had to be *recorded in the result*, `StudyResult` had no field for one, `VersionSource::FlashedThisRun` was a variant nothing could produce, and neither signal could ride inside the `Study` body without contradicting the decision that created them. Whatever shape those took was always going to be a schema question. Full account of the wire shape and why it is a query parameter: [embarch-core/design.md](../embarch-core/design.md) §3 decision 31's 2026-08-25 amendment.

    **What lives here: the sequencing, and the two things only this process knows.**

    - **`run_study(..., reflash, allow_version_mismatch, project?, <target selection>)`.** `reflash` defaults to `"none"`. `--allow-version-mismatch` is passed through to Core as `?allow_version_mismatch=1`; a DUT reflash sends `?flashed_firmware_version=<string>`. Core gates again, independently, so nothing here is the enforcement point — what this adds is the choice, and the chance to fail *before* doing something destructive.
    - **`run_study` gains a `project` parameter after all, and only for the DUT reflash.** §5's "no `project` param" note stands for what it was about: a study targets whatever DUT is connected through Core's dev-bench link, not one of this file's configured projects. *Rebuilding that DUT's firmware* is a different thing and is project-shaped — there is nowhere else a build target could come from — so the parameter (plus the usual `board`/`variant`/`revision`/`app`/`snippets`/`extra_args`) appears exactly when it becomes meaningful, and `reflash = "dut"` without it is a clear error rather than a guess at which configured project was meant. Passing it where it means nothing is ignored, not rejected: an operator who always passes it should not have to remember to stop.
    - **The two halves sequence differently, and the difference *is* the verification asymmetry showing up as control flow.** dev-bench is **flashed and then read back** — its version is genuinely observable over `GET /dev-bench/hello`, so verification is a measurement and can only happen after the flash. The DUT is **verified and then flashed** — nothing can be read back off it, so the only check available is against the tree about to be built, which means a study asking for a revision this tree is not at fails *without touching the board at all*. That is strictly better than the alternative, and it fell out of the asymmetry rather than being designed for.
    - **A dev-bench reflash resets the bench, and forgetting to would have looked like a link failure.** Flashing halts the core rather than starting it running (decision 32's own `reset_dev_bench` note), so an unreset bench never answers `Hello` and every check afterwards times out against a halted chip.
    - **The bench check is skipped entirely when the study says `any`.** That is a real answer, and opening the bench's serial link to confirm a comparison that is vacuous is a hardware touch for nothing.
    - **Where the DUT's version string comes from, stated as the limitation it is.** A new optional `version_command` on a `[[projects]]` entry (§4), defaulting to `git describe --always --dirty --abbrev=8` — the same invocation `embarch-dev-bench`'s own build embeds and `embarch-umbrella`'s doctor check 13 already compares against, so the default is the suite's existing convention rather than a new one. **It describes the tree that was built, not the image that is running**, and nothing in this suite can read a version off a DUT to confirm the build embedded it. A project whose build stamps something else declares the command that produces it; EmbArch does not guess, for the same reason [embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 35 keeps firmware semantics out of anything this suite derives on its own. `FlashedThisRun` therefore means "this run put the build of this tree on the board" — stronger than `Declared`, which nobody checked at all; weaker than `ReportedByDevBench`, which is a measurement.
    - **The no-`git checkout` rule is enforced against the config file too, not just against this crate's own code.** `version_command` is somewhere `["git", "checkout", "v1.2.3"]` could plausibly be typed as an attempt at "make the version be this" — so `reflash.rs` refuses any `git` argv naming a tree-mutating subcommand, matching **any** argument rather than the one in subcommand position (`git -C /elsewhere checkout main` puts a path where the subcommand looks like it should be). It over-rejects, deliberately: the cost of a false positive is renaming an argument, and the cost of a false negative is somebody's uncommitted work.

    **Two things Core's own half establishes about this one, recorded 2026-08-25 (Milestone 7 Phase B item 1) rather than left for this item to rediscover.** First, **Core's gate is live**: `POST /study` already rejects a stale bench with a `409` naming both strings, before `StudyStart` is sent, so nothing here has to enforce anything — this item adds the *choice* about what to do about a mismatch, not the check. Second, and less obvious: **`VersionSource::FlashedThisRun` is unreachable from Core and structurally has to be produced here.** `POST /flash` and `POST /study` are separate calls with nothing linking them, deliberately — the alternative would be Core keeping a persisted "last thing I flashed" record, which is the staleness pattern `embarch-topology/design.md` §3 decision 3 forbids. So Core writes `firmware_source: Declared` on every study today, and the only process that can honestly say otherwise is the one that just did the flashing. **Whatever shape that takes, it is this item's to design** — Core's `POST /study` has no field for it yet, and adding one is a schema question this item has to answer rather than assume.

41. **`--erase` and the MCP `erase` argument exist, and their tool text has to say what erase actually is — 2026-08-25.** The surface half of [embarch-core/design.md](../embarch-core/design.md) §3 decision 32: `flash`/`build_and_flash` take `erase: bool`, the CLI takes `--erase`, and both forward it to `POST /flash`. Requested directly and built the same day; the same day it bricked a real nRF54L15.

    **The design point here is not the flag, it is the description an agent reads.** Every other argument on these tools is a routine knob — a chip name, a path, a probe serial — and an agent reaching for one more of those costs nothing. `erase` is the only argument in this surface that can leave a board unrecoverable by any other tool in the suite, and an LLM picking it because "a clean flash sounds more thorough" is a realistic failure mode, not a contrived one. So the MCP description states plainly that it performs a **destructive full-chip erase**, that a non-erase flash cannot undo it, and that it is not needed for a normal reflash — and `--erase`'s CLI help says the same. Defaults to `false` everywhere, and `false` is never sent implicitly as `true` by any convenience path.

    `embarch-api` does not choose the erase mechanism and must not grow its own: which tool performs the erase, and whether a target supports one at all, is Core's (decision 32 there). A refusal from Core — "this target has no configured vendor erase tool" — is surfaced verbatim rather than retried by another route.

42. **`base_address` is a per-project config field, not a per-call parameter, 2026-08-25.** A `flash_format = "bin"` artifact carries no address of its own, so flashing one needs an offset — and `embarch-api` had no way to supply it. The consequence was concrete rather than theoretical: the ESP32-C5 validation flashed via a hand-written `POST /flash` straight to Core, **bypassing `embarch-api` entirely for that step**, because there was no config-driven path through it. Core's endpoint already accepted the offset; only this side was missing.

    It goes in `[projects.*]` alongside `flash_format`, and wins the same argument `flash_format` already won: the offset is a fact about how the project builds, not something that varies from call to call, so an agent should never have to know or supply a hex number to flash a board. A per-call parameter, and a config-default-with-per-call-override, were both put up and declined — the override shape has a real precedent here (`--firmware-path` overrides the configured artifact path) but that flag exists to flash *something other than what the project builds*, which is a genuinely per-call intent; an offset is not.

    Opaque pass-through, same posture as `chip`/`flash_format` (§3 decision 8's principle): `embarch-api` does not validate it against the target's memory map — that belongs to Core/probe-rs, and duplicating it here would be the maintenance trap that decision already names.

    **Implemented 2026-08-25.** Almost all of the plumbing already existed: `resolve::Resolved` has carried a `base_address` field to every `flash`/`build_and_flash` call site since dev-bench's own pipeline, and both `resolve_static` and `resolve_zephyr` were hardcoding it to `None` — this decision is the config field that finally fills it, not a new path through the code. Two shape details worth stating because they aren't free choices: the field is a **TOML integer** (`base_address = 0x2000`, using TOML's own hex literal) while Core's endpoint takes a **hex-or-decimal string**, so `resolve::format_base_address` does the `{:#x}` round trip — which lands a config-driven flash on byte-identical wire form to a dev-bench flash, whose `dev_bench::BASE_ADDRESS` constant is already written `"0x2000"`. And a `bin` project that omits it is **not** a config-load failure, despite being wrong in practice: the "required in practice" in §4's row is advice, not a check, because enforcing it is one step from validating the offset itself, which is exactly what the paragraph above declines to do. Nothing about how a `hex`/`elf` project loads changes — the field defaults to absent.

43. **`embarch-api` writes to one rolling per-machine logfile, so [embarch-ui](../embarch-ui/design.md) can show its logs at all, 2026-08-25.** Core's `/logs/recent` + `/logs/stream` pattern (`embarch-core/design.md` §3 decision 29) assumes a long-running service with a logfile to mediate. `embarch-api` is the opposite: spawned per Claude Code session as an MCP server, or run once as a CLI and gone. There is no process to ask, and by the time anyone wants to look at a one-shot's output the process has exited.

    Every invocation — MCP server or one-shot CLI, both — appends to a single rolling file under the machine data dir, each line tagged with pid and mode so interleaved sessions stay separable. `embarch-ui`'s Debug tab tails it with the same reader it already points at Core's file ([embarch-ui/design.md](../embarch-ui/design.md) §3 decision 13). This works for the one-shot case specifically because the record outlives the process, which is the property no endpoint-based design can have here.

    **Deliberately not: shipping lines to Core over a new log-sink endpoint.** That would put everything in one place and reuse the mediation Core already has — but it breaks §1's invariant that Core "has no idea `embarch-api` or any MCP client exist," which is load-bearing well beyond logging. Also declined: doing nothing on the grounds that an MCP client already surfaces its server's stderr and a CLI prints to the terminal in front of you. Both are true and neither survives the case that matters — wanting to know what an agent's `embarch-api` did twenty minutes ago, in a session that is closed.

    **Implemented 2026-08-25, with one correction to this decision as written and two defects found.** `src/logging.rs` installs the subscriber; the path lives in `embarch_core_client::api_log`, the crate `embarch-api` and [embarch-ui](../embarch-ui/design.md) both already depend on, so the writer and the reader resolve it from one definition rather than two. Daily rotation, 7-file retention, `api.log.<yyyy-MM-dd>` — deliberately the same scheme as Core's own file so one reader shape covers both.

    **The correction: per-user, not "the machine data dir."** That phrase meant `%ProgramData%\embarch` / `/var/lib/embarch`, which `embarch-core` established. It works for Core, which runs as a Windows service. It does not work here: `embarch-api` runs as the engineer, and `/var/lib` is `root`-owned — creating a subdirectory there is permission-denied for a normal user, verified on this bench rather than assumed. The file is now under `$XDG_DATA_HOME`/`$HOME/.local/share/embarch/api/logs` (`%LOCALAPPDATA%\embarch\api\logs` on Windows). Both alternatives were worse: hard-failing makes logging depend on a one-time `sudo`, and "machine dir if writable, else per-user" is a runtime probe that can land the writer and the reader in different places. Nothing is lost — §3 decision 1's single-engineer scope means there is no second user to be machine-wide *for*.

    **Both modes had to be given something to log.** The MCP path already emitted a startup line; a one-shot CLI run emitted nothing at all, since no subcommand calls `tracing` on its own — the file would have stayed empty for exactly the invocations this decision names. Two lines now bracket every CLI run: the parsed subcommand (clap's derived `Debug`, so its arguments come with it) and the exit code. `Cli::parse()` also moved ahead of logging setup, since the presence of a subcommand is the only thing that says which mode this process is.

    **Defect found, in Core's file rather than this one:** `embarch-core` tees one ANSI-colored stream to stderr and its logfile, so every line in the deployed Core's log carries SGR escape sequences — which `embarch-ui`'s Debug tab has been rendering as literal garbage since it shipped. `embarch-api` avoids it by writing two layers (colored stderr, un-colored file) instead of one teed writer, and `embarch-ui` strips escapes at render so the deployed Core is readable too. **Second defect, and the sharper one:** the two-layer form has no filter of its own — `tracing_subscriber::fmt()`'s builder defaults to `INFO` and a bare `registry()` defaults to nothing — so the first build of this module wrote `hyper`/`reqwest` `TRACE` into the file. Caught by reading the file, not by a test; the level is now stated explicitly.

44. **~~Two gaps~~ Three gaps in `run_study`'s own contract — two found by the first study that carried a protocol, one found the next day. All three fixed 2026-08-27 (`3c42252`, and (c) still open).** Neither is a design question; both are the surface having been extended past the code that implements it, and both are recorded here because the *tool text* still describes the old behavior, which is what a caller reads.

    **(a) `reflash = "dut"` flashes and does not reset.** The dev-bench half of `reflash.rs` resets explicitly, with a comment saying why ("a bench that is never reset never replies to `Hello`"); the DUT half calls `core.flash(...)` and falls straight through to submitting the study. So a study that asks to be run against freshly-built firmware runs against **whatever was already on the board**, and reports a successful reflash in `provenance` while doing it. This is exactly the coupling [embarch-dev-workflow.md](../embarch-dev-workflow.md) §4a records as "Coupling 1a" — *"flashing does not reset the target… it presents as 'I flashed it and nothing changed'"* — written up as a hazard for hand-driven flashing and then left sitting inside the one call whose whole purpose is to remove hand-driven flashing. Found by reading `reflash.rs` before trusting it; worked around by calling `build_and_flash` + `reset` separately, which is what the doc tells a human to do anyway. **Fixed 2026-08-27:** the DUT path now resets after flashing, with the same explicit comment the bench path carries.

    **(b) `reseal` recomputes two of the study's three seals.** `protocols_crc` shipped as a deliberate sibling of `steps_crc`/`streams_crc` ([embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 58 — "the study's **third** seal", checked independently so a mismatch names which third is corrupt), and Core validates all three. `study.rs`'s `reseal` overwrites the first two. Every study to date had `protocols: []`, whose CRC is stable, so nothing noticed. A study carrying a real protocol is rejected `400` unless its author computed the third seal, and the only way to do that is to link this crate and call `protocols_crc` — which is what the first real `.eap` study had to do. The MCP tool description and the CLI help both still said *"Both seals (steps_crc over steps, streams_crc over streams) are recomputed and overwritten"*, which was a statement about which seal a caller was silently responsible for.

    **Fixed 2026-08-27**, along with the tool description, the CLI help and three comments that all carried the hardcoded "both". The regression test asserts against a **non-empty** `protocols` list deliberately: `protocols_crc(&[])` is 0, so a protocol-free study cannot distinguish "recomputed to 0" from "never written" — which is precisely how every existing reseal test passed against a function that never touched the field. Confirmed live against the deployed Core the same day, by submitting several studies with all three seals explicitly zeroed and having each accepted.

    **(c) `--snippet`/`snippets` is accepted and silently ignored for a project configured with an explicit `build_command`, and the build reports success — open.** `build reference-dut-roadrunner --snippet ble-shell --snippet outpost` returned `success: true, artifact_fresh: true` having produced an image whose `.config` said `# CONFIG_EMBARCH_OUTPOST is not set`. The CLI help already says snippets are "only meaningful for a `discovery = "zephyr-west"` project", and that is documentation rather than a gate — the flags reach a code path that has nowhere to put them and drops them. This is the same shape as (a), (b) and [embarch-decision-reversals.md](../embarch-decision-reversals.md) row 73: **an input accepted, quietly discarded, and reported as success.** The rule this suite keeps re-deriving is that a flag which cannot be honoured must fail rather than be ignored. Recorded rather than fixed because the right fix is a decision — reject, or teach the `build_command` path to splice `-S` flags in — and the pass that found it was mid-deploy. Row 81.

    Both wanted fixing in the same pass and neither was, because the session that found them was validating a firmware protocol and stopping to change `embarch-api` would have swapped which thing was being tested. [embarch-decision-reversals.md](../embarch-decision-reversals.md) rows 75–76.

45. **"There is exactly one dev-bench board" was a premise, it was written into `dev_bench.rs` as constants, and it has now been falsified twice by the same physical bench — 2026-08-31.** Decision 32 created the dev-bench pipeline deliberately outside `[[projects]]`, and that half is still right: dev-bench is not a DUT anyone configures per repo. But it drew a second conclusion from that — *therefore* its board, chip, flash format and flash offset are facts the suite already knows, so they belong in Rust as `BOARD`/`CHIP`/`FLASH_FORMAT`/`BASE_ADDRESS` rather than in config. The bench has since been an nRF54L15DK, then an ESP32-C5 when the DK broke ([embarch-dev-bench/design.md](../embarch-dev-bench/design.md) decision 26), and an nRF54L15DK again today (that doc's decision 43).

    The two boards agree about **none** of the four, plus a fifth nobody had noticed was a variable at all:

    | | nRF54L15DK | ESP32-C5-DevKitC |
    |---|---|---|
    | `board` | `nrf54l15dk/nrf54l15/cpuapp` | `esp32c5_devkitc/esp32c5/hpcore` |
    | `chip` | `nRF54L15` | `esp32c5` |
    | `flash_format` | `hex` | `bin` |
    | `base_address` | — (a hex carries its own) | `0x2000` |
    | `artifact_path` | `build/app/zephyr/zephyr.hex` | `build/zephyr/zephyr.bin` |

    The artifact path is the one that would have been missed by a change that only made "board" configurable: it differs because **NCS turns sysbuild on by default and vanilla Zephyr does not**, which puts the image a directory deeper. That is not a property of the board, the chip, or the format — it is a property of which SDK the workspace pulls, and no rule over the other four predicts it. Read off a real build rather than reasoned about.

    So all five move to `[dev_bench]`, and **none of them is defaulted.** A default would have to pick one of the two boards, and picking wrong means building the wrong image and handing it to Core to flash through the wrong debug interface at the wrong chip. That is the class of silent-wrong-answer this suite refuses elsewhere on principle — [embarch-core/design.md](../embarch-core/design.md) §7's `artifact_path_for_core` UNC-guessing retrospective is the same lesson. A missing field is a startup error naming it, which is cheap; a wrong default is not. Validation also gained the `flash_format`/`base_address` pairing rule `[[projects]]` entries already lived under (decision 42), applied here for the first time now that the format is declared rather than fixed.

    **What stays a constant, legitimately:** the `app` directory name. That is `embarch-dev-bench`'s own repo layout — `workspaces/*/app` is a symlink to the one shared `app/`, identical for every vendor family — not a property of any board. And `lock_key` stays `"dev_bench"`: which board it is now varies, but the bench is still one at a time.

## 4. Configuration schema reference

Config path resolution, in order: **`--config <path>`**, then **`EMBARCH_API_CONFIG`**, then — *added 2026-08-13, revising this section's original text* — **a cwd-upward search for `embarch/embarch.toml`** (`find_config_upward` in `main.rs`), consulted only when neither explicit source is set. The original text here said the path is "not inferred from cwd... since the MCP client controls the spawn cwd... that shouldn't be a hidden assumption" — true as an argument against cwd-inference as the *only* mechanism, but not against it as a last-resort *fallback* behind two explicit ones: an explicit `--config`/env var still always wins outright, so nothing already relying on either changes behavior. What changed the calculus: an engineer working across several firmware repos (the real, current situation — this suite already has more than one) has no single `EMBARCH_API_CONFIG` value that's ever correct, and a separate `claude mcp add` per repo isn't "no `--config` needed," it's "typed once instead of every call." Walking up from cwd looking for the conventional `embarch/embarch.toml` (below) — the same pattern `git`/`west` themselves use for their own config/workspace root — makes it work per-repo with zero registration and zero env var, for every firmware repo, not just one hand-configured at a time.

**Conventional location: `<firmware-repo>/embarch/embarch.toml`**, one complete config per firmware repo, scaffolded by `embarch init` ([embarch-umbrella/design.md](../embarch-umbrella/design.md) §3 decision 10). Two consequences worth stating: a repo-scoped config means `list_projects` inside a firmware repo can only offer that repo's projects, and `[core]` is duplicated into every such file (accepted for v1; the include/fragment alternative is §12's open item).

**`[core]`** (one instance):

See `embarch-api/config.example.toml` for the maintained, runnable example with real values filled in.

Design choices to preserve:
- **`build_command` is an argv array, not a shell string.** Runs via `tokio::process::Command` with no shell interposed, avoiding quoting/injection ambiguity and shell-dialect differences (bash vs. cmd.exe vs. sh). Projects that genuinely need shell features (pipes, `&&`, sourcing a venv) use the explicit escape hatch: `build_command = ["bash", "-lc", "source .venv/bin/activate && west build ..."]`.
- **`env` is additive**, merged onto embarch-api's own inherited environment, not a full-profile replacement. PATH and toolchain setup remain the responsibility of whatever launches embarch-api.
- **`chip` / `flash_format` are opaque pass-through strings.** embarch-api does not validate them against probe-rs's target database — that validation belongs to Core/probe-rs, and duplicating it here would be a maintenance trap.

The identical sequence against a `--release` build of the same binary, same real Core and dev-bench, completed cleanly end to end. **Fixed for real 2026-08-24 (decision 36)**, once a real GATT-sized study reproduced it in production rather than a tiny fixture: `main` now spawns the whole runtime on a dedicated 512 MiB-stack thread. Not a fix to the type itself (still tracked as an open item in `embarch-study-designer/design.md` §7, in case another consumer hits the same shape without this workaround) — this crate's own exposure is closed.

**Why `build` and `flash` stay separate as well as offering `build_and_flash`:** the common agent-driven workflow ("make this change work on hardware") wants one call, and bundling prevents accidentally flashing a stale/failed artifact after a build error. But fast iteration on compiler errors shouldn't require touching hardware every call, and re-flashing the same artifact after a manual board reset shouldn't require a full rebuild — hence all three stay available.

**Error-handling rule, applied to every tool:** expected/recoverable failures (nonzero build exit code, Core returning 4xx/5xx, a missing artifact) come back as `CallToolResult::error(...)` content — never `Err(McpError)` — so the calling agent sees the actual failure text (e.g. a compiler error) and can reason about it. `Err(McpError)` is reserved for true protocol-level problems, like embarch-api's own config being unloadable at all.

**One documented exception:** every tool that takes a `project` argument looks it up against the config first, and an unknown/mistyped project name comes back as `Err(McpError::invalid_params(...))`, not `CallToolResult::error`. This is deliberate, not an oversight: MCP's `invalid_params` exists precisely for "the request itself is malformed," which a bad project name is, as distinct from "the request was well-formed but the operation failed" (a build error, a Core failure) — the case the general rule above covers.

**`--json` flag** (`embarch-api --config <path> --json build <project>`): switches a subcommand's stdout from a human-readable summary to a single JSON object carrying the same fields the equivalent MCP tool result carries (e.g. `{"schema_version": 1, "success": bool, "exit_code": i32|null, "stdout": "...", "stderr": "...", "artifact_path": "...", "artifact_fresh": bool}`), so a script (e.g. `milestone-1.md`'s west-runner wrapper) doesn't have to scrape human text. `schema_version` (§3 decision 24, 2026-08-15) is bumped by hand only on a breaking shape change. Default (no `--json`) prints readable text for an engineer typing the command directly.

**Error handling and exit codes**: a CLI has no equivalent of MCP's protocol-level-vs-tool-level distinction (§5's `CallToolResult::error` vs. `Err(McpError)` split, or the `invalid_params` project-name exception) — there is no protocol layer underneath a CLI invocation. Instead:
- Success → exit code `0`; result on stdout (human text, or the `--json` object).
- Any failure — unknown project name, config load failure, build failure (nonzero exit/timeout/killed), Core unreachable, Core returning 4xx/5xx, missing artifact — → exit code `1`; a one-line error message on stderr. If `--json` was passed, the error goes into the same JSON object on stdout instead (`"success": false`, `"error": "...", "error_kind": "..."`) rather than to stderr, so a script only has to check the process exit code, not which stream carried the result.
- Malformed invocation itself (missing required arg, unknown subcommand) is handled by `clap` before any of this runs, using clap's own exit code (`2`) and usage text — unchanged, not part of this design.
- **Exit code stays a single `1` for every failure kind** (e.g. no distinct code for "build failed" vs. "project not found" vs. "Core unreachable") — but as of 2026-08-15 (§3 decision 16), `--json`'s new `error_kind` field gives a scripted caller the finer-grained signal directly, without needing a matching exit-code taxonomy invented on top of it.

## 6. Build orchestration details

- **Working directory**: `source_path` joined with `build_cwd` if set, else `source_path`. Validated to exist before spawning; if not, returns a tool-level error rather than panicking.
- **`artifact_path` resolution**: resolved relative to that same build directory (`build_dir()` = `source_path` + `build_cwd` if set, else `source_path` alone), not to `source_path` alone unconditionally. The load-bearing distinction `build_cwd` encodes is *where the build command's process cwd actually is* — for a `west build <app-path>` invocation, that's wherever `west` is invoked from, which is **not necessarily** the app subdirectory itself: `west`'s default build output dir is `<cwd>/build`, so if the real invocation runs from `source_path` and passes the app path as a positional argument (rather than `cd`-ing into it), `build_cwd` must stay unset even though the app lives in a subdirectory — setting `build_cwd` to that subdirectory in that case makes `resolved_artifact_path()` look in a `build/` directory that never gets written to. `project-a-board` (§4) hit exactly this: confirmed fixed by reading its own `build/build_info.yml`'s recorded `west.command` after a real build, which showed the invocation's cwd was `source_path` with the app path as a trailing argument, not `source_path/app/project-a` as `build_cwd`. A project that gets this wrong would report a fresh artifact that's actually a stale leftover (if one happens to exist at the wrong resolved path from an earlier config), or never find the real one at all.
- **Environment**: inherits embarch-api's own process environment, overlaid with the project's `env` table.
- **Capture**: `Stdio::piped()` for both stdout and stderr, drained by **two concurrent tokio tasks** — draining only one pipe while the other fills its OS buffer is a classic way for a child process to hang.
- **Truncation**: each captured stream is capped (e.g. last ~64KB, with an explicit "truncated" marker) before it goes back through MCP, so an unbounded build log doesn't blow up the tool response or the agent's context.
- **Timeout**: `build_timeout_secs` (project override, else a sane default) wraps the wait via `tokio::time::timeout`. On timeout, the **process group** is killed, not just the immediate child — build tools like `west`/`cmake`/`make` fork subprocesses that a plain `kill()` would orphan.
- **Exit-code handling**: `0` → proceed to the artifact check. Nonzero → reported as a build failure with captured output, artifact check skipped. `None` (killed/timed out/signaled) → reported explicitly as "timed out"/"killed", distinct from a compiler error, so a hang isn't misdiagnosed as a code problem.
- **Artifact freshness check**: the artifact path's existence and mtime are recorded *before* spawning. After a zero exit code, the file must now exist, and if it existed before, its mtime must be newer than the build-start time. Without this, a build that fails partway through (or a misconfigured `artifact_path`) could silently "succeed" by pointing at a stale binary from a previous build — the worst possible failure mode for hardware bring-up.
- **Concurrency**: one build (or `build_and_flash`) in flight per project name at a time, enforced by a lightweight per-project async lock. This is separate from Core's own hardware lock — it guards against two overlapping calls stomping the same build output directory, not against USB contention (Core already owns that).

## 7. Core HTTP client

**Lives in the shared `embarch-core-client` crate, not this repo's own `src/`, as of 2026-08-24 (§3 decision 37).** Everything below still describes current, accurate behavior — the code just moved to `crates/embarch-core-client/src/client.rs` (`CoreClient`) plus `lib.rs` (`CoreConfig`) and `token_discovery.rs`, so `embarch-ui` depends on the identical implementation. `embarch-api`'s own `config.rs` re-exports `CoreConfig` unchanged.

**Two additions on 2026-08-26 (Milestone 7 Phase D), both for `embarch-ui` rather than for this crate, and one of them is why Phase D touched this repo at all.**

- **`declare_signal`/`list_signals`/`remove_signal`, `list_serial_ports`, `study_streams`.** `POST`/`GET /signals` had shipped on Core in Phase B and this crate had a wrapper for **neither** — so `embarch-ui`, which reaches Core only through here and depends on `embarch-topology` not at all, had no path to a feature that already existed. `SignalLink`/`SignalRoute`/`SignalDirection`/`SerialPortResponse` are **mirrors** of `embarch-topology`'s types rather than those types, for the same reason `AlertResponse`/`EnrolledBoardResponse` already are: the real ones sit behind that crate's `hardware` feature, which is what links `probe-rs`/`serialport`, and §11's "no hardware knowledge" boundary means this crate never does. That leaves a coupling **no crate in the suite can typecheck** — nothing compiles both sides — so it is pinned from each side against the same JSON literal, here and in `embarch-core`, each test naming the other. `AlertResponse` and `EnrolledBoardResponse` still have the same unpinned coupling.
- **`version.rs`, moved out of this repo's own `reflash.rs`.** `DEFAULT_VERSION_COMMAND`, `derive_version` and `reject_tree_mutating_command` now live in `embarch-core-client::version`, re-exported by `reflash.rs` so every call site and doc reference keeps its path. Forced by decision 11 in [embarch-ui/design.md](../embarch-ui/design.md): that tab prefills a study's `requires.firmware_version` from the configured project's own `git describe`, and `embarch-ui` cannot depend on `embarch-api` — the suite has no such dependency direction anywhere. The alternative was a second copy of that argv **and** of the never-move-the-tree rule, in a crate that would never see this one's tests. `tests::the_reflash_path_never_moves_the_tree` stays here, because the constraint is about *this crate's reflash path* regardless of where the function enforcing it is defined.

- Built once at startup from `[core]` config: `base_url`, the resolved token, and a `reqwest::Client`. When `base_url` is the literal `"auto"` (§3.11), the address instead resolves on first use by calling `embarch_topology::software::resolve_software_topology(port, host, None)` — a short-timeout `GET /status` race over an ordered candidate list (`127.0.0.1:<port>`, then the WSL2 default-gateway IP when running under WSL2, then `host:<port>` if set), taking the first that answers, where a `401` counts as an answer (Core is there, the token is wrong: a distinct problem needing a distinct error message). The resolved address is cached for the process lifetime only, never written back to config, so a WSL2 restart's new gateway IP is picked up by the next invocation with no config edit. **Resolution must be lazy, not eager**: the startup connectivity check below is MCP-mode-only by design, and `list_projects` deliberately works with Core down — resolving `auto` at config-load time would regress both. A declared literal `base_url` still skips this call entirely and is trusted outright (unchanged) — only `"auto"` calls the crate.

    **Moved into `embarch-topology`, 2026-08-21** (`embarch-topology/design.md` §3 decisions 2, 3) — this used to be `embarch-umbrella`'s candidate-race module, copied here verbatim module-and-tests-together rather than extracted into a shared crate (§3 decision 15 there carried the reasoning: the suite deliberately avoided a shared-logic crate at the time). That reasoning was reversed suite-wide once a real incident (a stale env-var-based topology override surviving a port migration undetected, `embarch-topology/design.md` §1) showed the actual cost of two copies existing at all — not drift between them, but that a manual-override escape hatch is exactly the kind of thing that goes stale silently. `topology.rs`/`env.rs`/`probe.rs` are deleted from this repo outright; `core_client.rs` calls the shared crate directly. Token resolution (`CoreConfig::resolve_token`) runs through `token_discovery.rs`'s chain — `token`/`token_env`, then a machine-wide token-file fallback (same-OS path, or the WSL2⟷Windows-translated path when running under WSL2) — before failing; full detail in [embarch-token.md](../embarch-token.md).
- **Auth injection**: every request uses `.bearer_auth(&token)`, rendering `Authorization: Bearer <token>` — matching Core's exact-string check in `auth_middleware` (`api.rs`).
- **Per-call timeouts**, not one global client timeout: `status`/`reset`/`serial_log` use short budgets, `flash` gets its own longer one, since flashing can legitimately take much longer than a status check.
- **Error body handling**: Core's handlers return `(StatusCode, String)` on failure, which axum renders as a **plain-text body**, not JSON. embarch-api must parse JSON only on 2xx responses and read the body as plain text on non-2xx, folding it into the error message — attempting to `serde_json` a non-2xx body would fail and mask Core's actual error text. As of `embarch-core/design.md` §4/§11, that string is the full `anyhow` causal chain (`{e:?}`), not just Core's outermost context message — embarch-api's CLI/MCP error text should print it verbatim rather than truncating to a first line, since the actual cause (e.g. a probe-rs I/O error) is often further down the chain.
- **Startup connectivity check**: `main.rs` calls `GET /status` once during init, before starting the MCP server loop. If Core is unreachable, embarch-api refuses to start and reports a clear "Core unreachable at `<base_url>`" error rather than starting successfully and only surfacing the problem on the first tool call. This is a fail-fast choice, not a correctness requirement — Core could in principle come up later — but for a single-engineer local tool, catching a misconfigured `base_url` or a Core that forgot to launch at startup is more useful than a confusing failure three tool calls into a session.
- **Startup connectivity check is MCP-mode only.** The check above applies when embarch-api starts as an MCP server (§3.4). In CLI mode (§3.10), no eager connectivity check runs before dispatch — each subcommand's own Core call surfaces an "unreachable Core" error exactly as MCP would, and `list_projects` (which never calls Core) still works even with Core down entirely, which matters when debugging config alone.

### 7.1 Testing strategy

**Status: specified, not yet implemented** — no test files exist in the repo yet. The scenarios below are the acceptance criteria test code should satisfy, not a description of tests already written.

- `core_client.rs`, tested against a mocked HTTP server (e.g. `wiremock`), not a real embarch-core instance:
  - every outgoing request carries `Authorization: Bearer <token>` with the resolved token (inline or from `token_env`)
  - `status`/`reset`/`flash`/`serial_log` each honor their own configured timeout independently — a slow mock on one endpoint doesn't eat into another's budget
  - a non-2xx mock response is read as plain text and folded verbatim into the returned error — never handed to a JSON parser (§7's plain-text-vs-JSON rule)
  - a 2xx mock response deserializes into the matching response struct (`StatusResponse`, `FlashResponse`, `ResetResponse`, `SerialLogResponse`); malformed JSON on a 2xx surfaces a clear parse error rather than panicking

- `build.rs`, tested with fake `build_command`s (small scripts standing in for `west`), not a real toolchain:
  - exit code 0 plus a freshly-written artifact reports build success and artifact freshness both true
  - a nonzero exit reports build failure, with the artifact-freshness check skipped entirely
  - a command that outlives `build_timeout_secs` is killed as a process group (§6, unix) and reported distinctly as "timed out" — not conflated with a normal nonzero exit
  - a command that writes heavily to one of stdout/stderr while barely touching the other still completes without hanging — regression coverage for the two-pipe-must-drain-concurrently invariant (§6)
  - output beyond the captured-stream cap is truncated exactly on a UTF-8 character boundary, with the truncation marker present
  - an artifact that already existed before the build, with its mtime left untouched, is **not** treated as fresh even when the build exits 0 — the freshness check (§6) must distinguish "the build overwrote it" from "the build never touched it"

- No integration tests against a real embarch-core process are planned for v1 — the mocked-boundary approach was chosen specifically to keep tests independent of hardware/probe state.
- **Named tier, 2026-08-15 (§3 decision 30): a scripted smoke harness, `scripts/smoke.sh` or equivalent** — a throwaway `embarch-core` instance plus a small synthetic fixture repo, re-running a fixed sequence of `list_targets`/`build`/`flash`/`reset` calls. Not a substitute for the mocked unit tests above; a repeatable version of the live-verification pattern this doc's own changelog already shows being done by hand for every decision-12 milestone.

## 8. Security model

- **Inbound (MCP) trust boundary**: "whoever can spawn the embarch-api process." No API key, bearer token, or session exists at this layer — see §3.4.
- **Inbound (CLI) trust boundary**: identical reasoning to the MCP case, restated as "whoever can run the `embarch-api` binary locally, with a config file it can read." There's no additional session/token layer distinguishing a CLI invocation from an MCP-spawned one; both terminate at the same OS-level question of who can execute the binary and read its `--config`. One difference worth calling out, not a different trust boundary: an MCP-spawned process's lifetime and stdio are entirely owned by the spawning client, whereas the CLI is directly interactive — a human can run `embarch-api build <project>` themselves, immediately, with no client software mediating. This doesn't change *who* is trusted, it's just the path a human actually exercises day to day (§3.10).
- **Outbound (Core) credential**: `EMBARCH_TOKEN`, the same shared secret Core itself was started with, held either inline in config (`token`), via an env var (`token_env`, §4), or — if neither is set — discovered from the machine-wide token file Core generates (`token_discovery.rs`, §7). Full lifecycle (generation, storage, transport, rotation, threat model, known gaps) is documented in [embarch-token.md](../embarch-token.md) rather than here, including the file-permissions guidance for the inline `token` case.

## 9. Deployment model

Today: embarch-api (WSL2) and embarch-core (native Windows) run on the same physical machine as independent processes, embarch-api reaching Core over the WSL2⟷Windows network boundary rather than `127.0.0.1` — confirmed working end-to-end during milestone-1 (`embarch-core/design.md` §7). embarch-api never assumes `127.0.0.1`; Core's base URL is always a config value, because Core's own README already anticipates moving to a Raspberry Pi reachable over LAN.

**Artifact-transfer gap — closed for the WSL2-same-PC case (milestone-1 §3.3) *only when Core runs in an interactive session*; a real, previously-unknown gap when Core runs as the installed Windows service, found 2026-08-18 (`embarch-api/milestone-7.md` §3.7).** Core's `/flash` endpoint takes a `firmware_path` string and reads it from *its own local disk*, so a path meaningful to the build side isn't automatically meaningful to Core. For the WSL2-same-PC topology (embarch-api building in WSL2, Core running natively on Windows on the same physical box), this is solved by `artifact_path_for_core` (§4): a per-project config field carrying the artifact's `\\wsl.localhost\<distro>\...` UNC form, which `flash`/`build_and_flash` send to Core instead of the WSL2-local path. Confirmed working against real hardware — but **only** with Core running as a plain foreground `run`, not as the installed service.

**The gap:** `\\wsl.localhost\...` UNC shares are exposed by a per-session network provider tied to the interactive user's logon session. Core's installed Windows service runs as `LocalSystem` in **Session 0**, which has no such provider — `GetLastError`/`os error 67` ("the network name cannot be found") reading the exact same path that resolves fine (`Test-Path` succeeds) from an interactive PowerShell in Session 1. Confirmed by direct A/B test: identical `flash` call against identical config failed against the installed service, succeeded seconds later with the only change being Core switched to a foreground `run` in the interactive session. This is not about which account the service logs on as (Windows services always run in Session 0 regardless of account) — it's Session 0 isolation itself. **Every prior "confirmed working" claim for this mechanism (milestone-1, and this decision's own text until now) was validated against a foreground Core, never the installed service** — the installed-service path had simply never been used for a real config-only flash before this milestone.

**Resolved 2026-08-18, same day it was found — option (b) below, implemented and confirmed against real hardware against the actual installed service (not a foreground workaround).** Of the candidates considered — (a) always run Core in the foreground for this topology, giving up autostart-on-boot (defeats `embarch-umbrella/design.md` decision 3's whole point); (b) extend the `remote`-topology multipart-upload path (§3 decision 15 below — which turned out to be design-only, never actually implemented, itself a real doc/reality gap found while building this fix) to `WslHost` too; (c) some way to grant the Session 0 service access to the interactive session's `\\wsl.localhost` mount (no known mechanism) — (b) shipped.

`CoreClient::flash` (`core_client.rs`) now branches on the already-resolved `TopologyClass` (extended to track this, not just the address): `Local` (same machine, or a declared explicit `base_url` — the `embarch-dev-workflow.md` §2 dev-loop case) sends `firmware_path` as JSON exactly as before, unchanged. `WslHost`/`Remote` read the artifact's bytes directly and `POST` them as `multipart/form-data` instead — Core's `/flash` (`chip_resolve.rs`'s sibling, `api.rs`'s `flash_handler`) now accepts either body shape on the same endpoint, dispatching on `Content-Type`, matching what §4's endpoint table already documented but §3 decision 10 had never actually implemented. This is strictly more general than the UNC mechanism it replaces for these two classes: it works identically whether Core is foreground or an installed service, so **`artifact_path_for_core` is fully retired** — removed from `embarch-api`'s config schema (`config.rs`) and from `Resolved` (`resolve.rs`), not just superseded for one topology. All three call sites (`cli.rs`'s `flash`/`build_and_flash`, `tools.rs`'s MCP equivalents) now always pass the plain WSL2-local artifact path; `CoreClient::flash` decides transport, not the caller. `env.rs`'s `wsl_unc_path`/`wsl_distro_name` helpers (this doc's own copy, distinct from `embarch-umbrella/init.rs`'s scaffold-time copy — see the open item below) are deleted as dead code alongside them.

Live-validated end-to-end against the real reference-dut board: `build`/`flash`/`build_and_flash`/`reset` (`embarch-api/milestone-7.md` §3.6–3.8, §3.10) all succeeded via CLI against the **installed** Windows service — not the foreground workaround this finding was originally worked around with. New tests: `embarch-core`'s `api.rs` gained 4 unit tests hand-constructing real `multipart/form-data` bodies (round-trip, default format, missing-`chip`, missing-`firmware`-part) — 19 total, up from 15; `embarch-api` stays at 45 (no new tests added there — this module has no existing mock-HTTP-server test infrastructure to hook into, consistent with how the rest of this hardware-adjacent boundary is tested, live rather than mocked). `cargo build`/`cargo clippy --all-targets -- -D warnings`/`cargo test` clean on both repos, both Linux and the real Windows target.

Two older caveats from the original 2026-07-21 validation, and now this finding itself, are all superseded rather than separately relevant: the field wasn't populated in the real `config.toml` at the time (moot — the field no longer exists), the UNC path computed didn't match `west build`'s real output location (moot, same reason), and the Session 0 gap this section spent most of its text on (fixed, above). **This does not generalize** to Core running on a genuinely separate machine reached over a real LAN (a future Pi deployment) needing a different kind of fix — that case already gets multipart too now (it was `Remote`'s design all along), so it's covered by the same code path, not a remaining gap.

**New open item this fix surfaced**: `embarch-umbrella/init.rs` still scaffolds a fresh config with `artifact_path_for_core` populated (its own separate, "lifted verbatim" copy of the UNC-computation helpers, per decision 15's liftable-copy pattern) — now writing a field `embarch-api` no longer reads at all. Not fixed here (different repo, out of scope for this pass); `embarch-umbrella/design.md` needs its own correction to stop scaffolding a field that does nothing.

## 11. Relationship to embarch-core

Core owns all direct hardware access — `probe-rs` (flashing/reset) and `serialport` (UART log reads) live exclusively in Core. embarch-api never links against either crate; every hardware operation goes through Core's HTTP API. embarch-api's own domain is orchestration: turning a project name into a build, and a build's artifact into a Core `/flash` call, plus exposing all of it as MCP tools and CLI subcommands (§3.10, §5a).

## 11a. Relationship to embarch-umbrella

`embarch-umbrella` writes this project's config and shells out to its CLI to verify things, but is never in the runtime path — nothing routes through it once setup is done, and `embarch-api` has no knowledge that it exists (the same one-way relationship `embarch-core` has toward `embarch-api`, §11). Specifically, umbrella owns: scaffolding `<firmware-repo>/embarch/embarch.toml` (§4), registering this binary as an MCP server, putting it on `PATH`, and diagnosing a broken stack via `doctor`. Two `doctor` checks are capabilities this doc previously deferred and now expects to live there rather than here — `build_command[0]` resolving on `PATH` (§12), and an `artifact_path_for_core` that doesn't name the same file as `artifact_path` (§9, §12) — both of which are preflight diagnosis, not build orchestration. See [embarch-umbrella/design.md](../embarch-umbrella/design.md) §5, §9.

## 12. Open questions / future work

- **A `[[projects]]` `board` is a hardware fact, and this file has been deriving it from build artifacts.** `config.toml`'s reference-dut entry said `roadrunner@2/nrf54l15/cpuapp` from 2026-08-06 to 2026-08-27, with an inline comment presenting that value as authoritative because *"its own `build/build_info.yml` recorded `roadrunner@2/nrf54l15/cpuapp`"*. That is a derivation from an artifact left by whatever someone last typed, not a statement about the board on the desk — which is an `dut_dev` revision 7. Cost: a day of `embarch-outpost` bring-up spent measuring a UART that was faithfully transmitting into the wrong pin, across two well-evidenced and wrong diagnoses ([embarch-decision-reversals.md](../embarch-decision-reversals.md) rows 83–85).

  **The rule this violates is one this suite already wrote down** — [embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 35, which forbids presenting an inference about a DUT as established fact. `board` is the most load-bearing DUT fact in this file. Two things would have caught it, and neither exists: `init` could refuse to *write* a board it inferred from `build_info.yml` without the operator confirming it, and `validate`/`status` could compare the configured board against something the attached hardware actually reports. The second is the real fix and the harder one; the first is cheap and would have been enough here.

- **PATH/toolchain preflight validation** (e.g. confirming `west`/`arduino-cli` resolve on PATH before attempting a build, for a faster/clearer error than a raw `os error 2`) — still deferred from `embarch-api` itself, and now expected to land as `embarch-umbrella`'s `doctor` check 7 instead ([embarch-umbrella/design.md](../embarch-umbrella/design.md) §5, §11a above). The reasoning for keeping it out of the build path is unchanged: a build failure surfaces naturally as a nonzero-exit/error-output report, and preflight-checking every build would add latency to the common case to improve one uncommon error message. As a *diagnostic* run on demand, it's worth having — which is exactly what `doctor` is.
- **Config fragments / `include`**, so `[core]` isn't duplicated into every firmware repo's `embarch/embarch.toml` (§4). Deferred rather than rejected — `[core]` is three lines once `base_url = "auto"` lands (§3.11), which is what makes the duplication tolerable for v1.
- **Config hot-reload** — deferred from v1. Config loads once at startup; picking up edits requires restarting the MCP session (reconnecting the client).
- ~~**The artifact-transfer gap** described in §9, for a future Core-on-a-different-machine deployment.~~ — resolved 2026-08-15: §3 decision 15 (`embarch-core/design.md` §3 decision 10 is the Core-side half) adds a multipart-upload path used specifically for a `remote` topology; the WSL2-same-PC path via `artifact_path_for_core` is unchanged.
- **`serial_log` stays one-shot (capture for `duration_ms`, return, done) — not streaming.** This was a deliberate choice, not an oversight: Core's `/serial-log` endpoint is itself a bounded-duration capture rather than a stream, and MCP tool calls are fundamentally synchronous request/response. Building real streaming into embarch-api would require Core to grow a streaming mode first — out of scope for embarch-api to decide unilaterally, since Core "has no idea embarch-api or any MCP client exist" (§1). If long-running log tailing becomes a real workflow need, an agent can already approximate it by calling `serial_log` repeatedly with fresh `duration_ms` windows; true streaming is deferred until Core's API grows to support it.
- **Adding projects to the config remains manual TOML editing** — no `add_project` MCP tool or CLI subcommand planned (distinct from the `build`/`flash`/etc. subcommands added in §3.10, which invoke existing config, they don't mutate it). Confirmed choice, consistent with §3.6's "no database, single config file" philosophy: not enough churn in the project list to justify a second way to mutate it. **Partially superseded by §3 decision 12**: a `discovery = "zephyr-west"` project no longer needs a config mutation to add a board/variant/revision/app at all — `list_targets` discovers it live. This item's reasoning still holds fully for `discovery = "static"` projects and for adding a whole new *project* (as opposed to a target within one).

- **RESOLVED** — `artifact_path_for_core` was not populated in the real `config.toml` for `project-a-board`. Now set, using the corrected (`build_cwd`-less) workspace-root UNC path below, and confirmed to load correctly (`list-projects`). This closes the artifact-path gap for this project's config-only `flash`/`build_and_flash`, not just the `--firmware-path`-override path validated earlier (§9). Re-validated against real hardware 2026-08-18 (`embarch-api/milestone-7.md` §3.6–3.9): config-only `build`/`flash`/`build_and_flash` all succeeded against the real reference-dut board, via both the CLI and — the first time for any project in this suite — an MCP client (Claude Code).
- **RESOLVED** — `resolved_artifact_path()` didn't match where `west build` actually wrote `project-a-board`'s artifact. Root cause confirmed by reading the project's own `build/build_info.yml` (recorded `west.command`): the real invocation runs with cwd = `source_path` itself, passing the app directory (`app/reference-dut`) as a positional argument to `west build`, not by `cd`-ing into it first — so west's default `<cwd>/build` output dir is `source_path/build`, never `source_path/app/reference-dut/build` as the old `build_cwd = "app/reference-dut"` assumed. - **RESOLVED** — artifact-freshness check was racy under wall-clock jitter, observed on WSL2. §6's freshness check compares a filesystem mtime against a `SystemTime::now()` read taken just before the build subprocess spawns (`build.rs`'s `artifact_is_fresh`). An isolated repro on this WSL2 machine (spawn a child that writes a file, compare its mtime to the parent's pre-spawn timestamp) showed the child's file mtime landing a few milliseconds *before* the parent's own timestamp on some runs — not filesystem mtime-resolution truncation (confirmed ext4, nanosecond resolution), most likely Hyper-V/WSL2 clock-sync jitter between reads taken microseconds apart. Effect: a build that just genuinely wrote a fresh artifact could be reported as stale, causing `build_and_flash` (and the CLI's `flash`) to refuse to flash a good build. A monotonic-clock (`Instant`) fix, considered first, doesn't actually apply here — filesystem mtimes are wall-clock (`SystemTime`) values with no `Instant` equivalent to compare against, so there's no way to bracket the build with a monotonic reading and still compare it to the mtime. Fixed instead with a small fixed tolerance (`FRESHNESS_CLOCK_GRACE`, 500ms) added to the mtime side of the comparison in `artifact_is_fresh` — cheap because a real build takes at least seconds, so 500ms of grace can't mask a genuinely stale artifact left over from a previous run, only absorb the observed sub-second clock jitter.

- **Config fragments / `include`, config hot-reload, one-shot `serial_log`, and manual TOML project adds all stay deliberately deferred** — reaffirmed unchanged by the 2026-08-25 suite-wide design pass, which re-read each of them rather than carrying them forward unexamined. Each already records its own reasoning above and none acquired a new argument this pass; they are settled-deferred, not unexamined.
