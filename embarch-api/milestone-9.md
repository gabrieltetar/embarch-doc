## 1. Goal, restated for embarch-api

## 6. Changelog

- 2026-08-24 — **Milestone closed: §3.1–3.7 all confirmed for real, after finding and fixing a real production stack-overflow bug that was silently blocking every one of them from returning a usable result.** The first real GATT-sized `study_status` call (this milestone's own `BleConnect`->`GattDiscover`->`GattMonitorAll` fixture, run for real against the live boards) `SIGABRT`-crashed the live MCP server on every attempt (each crash silently respawned a fresh process, surfacing to this session only as `Connection closed`) and the `study-status` CLI subcommand run directly — `embarch-study-designer/design.md` §7's already-tracked debug-build stack-overflow risk, previously only reproduced against a tiny 2-step fixture, finally real against production-shaped data. Root-caused and fixed in `embarch-api/design.md` decision 36: `Builder::thread_stack_size` alone doesn't cover the thread that calls `block_on`; `main` now spawns the whole runtime on a dedicated `std::thread` with an explicit 512 MiB stack. With that fix live, the full chain ran clean: `list_targets` (§3.1), `build_and_flash` (§3.2), a real `BleConnect` (`Pass`) -> `GattDiscover` (`Pass`, 8 real services) -> `GattMonitorAll` (`Pass`, clean empty capture) both via MCP and via the CLI (§3.4–3.6), and the `hw_lock`/`study_lock` concurrency check in the harder ordering — a `build_and_flash` issued while a dev-bench study was in flight, neither affected the other (§3.7). **A real, not-yet-root-caused flakiness also found, not papered over:** of 4 real end-to-end attempts, 2 failed before a clean 3-`Pass` result (one `BleConnect` itself failing with a generic BLE controller error `HCI 0x1f`, one disconnecting mid-`GattDiscover`), and the two successes reported different live GATT-service counts (8 vs. 3) for the identical firmware build. Doesn't block this milestone (its own bar — one clean end-to-end run — was met twice), but is a real reliability gap; full account in `embarch-dev-bench/milestone-9.md` §6, since it's a DUT/BLE-stack-level finding, not this repo's own code.
