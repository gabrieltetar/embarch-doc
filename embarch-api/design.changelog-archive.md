# design.md: changelog archive

- 2026-08-25 — **Decision 43 implemented, and the decision itself corrected on one point.** New `src/logging.rs`: pid/mode-tagged lines to one daily-rolling file, written by both modes, alongside the stderr that was already there. **"Under the machine data dir" turned out to be unimplementable as written** — `embarch-api` runs as the engineer and `/var/lib` is `root`-owned (verified, not assumed), so the file is per-user instead; §3 decision 1's single-engineer scope is what makes that a correction rather than a compromise. The path is defined once, in `embarch-core-client::api_log`, because [embarch-ui](../embarch-ui/design.md) reads the same file and a path resolved twice eventually disagrees with itself.

  **Three things the work turned up that the decision did not predict.** A one-shot CLI run logged *nothing* — no subcommand calls `tracing` — so the file would have stayed empty for the exact invocations decision 43 exists for; two bracketing lines (subcommand, exit code) now record every run. `embarch-core`'s logfile carries ANSI escapes, because it tees one colored stream to stderr and file, and `embarch-ui`'s Debug tab has been rendering them as garbage since it shipped; this crate writes two layers instead, and the UI strips escapes so the deployed Core reads correctly too. And the two-layer form silently lost the `INFO` default that `fmt()`'s builder supplies and `registry()` does not — the first build wrote `hyper`/`reqwest` `TRACE` to disk.

  Live-validated end to end, not just built: real CLI invocations wrote real tagged lines, and a running `embarch-ui` served them over both `/api/api-logs/recent` and its SSE stream. `cargo build`/`test` (55, up from 53; `embarch-core-client` 17, up from 11)/`clippy --all-targets -- -D warnings` clean.
- 2026-08-25 — **Decision 42 implemented: `base_address` is now a real `[[projects]]` field.** `ProjectConfig.base_address: Option<u64>` (TOML hex literal), formatted to Core's hex string by the new `resolve::format_base_address` and threaded through the two `resolve` arms that had been hardcoding `None`; surfaced in `list_projects` (both MCP and CLI) so the offset a project flashes at is inspectable without opening the config. **The gap this closes was in configuration, not in code** — every call site downstream of `Resolved` already passed the field, so the ESP32-C5 validation's hand-written `POST /flash` was bypassing `embarch-api` for the want of one config key. Deliberately no new validation: a `bin` project omitting the offset still loads (see the decision's own text for why). `config.example.toml` documents it on the `hex` example, where it is *not* needed, since that is where a reader meets `flash_format` first. `cargo build`/`test` (53, up from 49)/`clippy --all-targets -- -D warnings` clean.

- 2026-08-25 — **Milestone 7 Phase B item 2 implemented — and it was not an `embarch-api`-only item, which is worth saying plainly rather than folding into a summary.** Two decisions landed and one was deliberately deferred.

  **Decision 39's stream half:** `study_stream_data { study_id, name, raw? }` and `list_study_streams { study_id }` as MCP tools and as `study-stream-data`/`list-study-streams` subcommands; `embarch-core-client` gained `get_study_stream` on the same helper the three aliases already shared. `list_study_streams` needed **no new Core route** — `GET /study/{id}` has returned the whole `StudyResult` inline since item 1 — and the field it exists to surface is `truncated`, which the three aliases structurally cannot report. The three old tools and three old subcommands are unchanged in name, parameters and returned bytes (pinned by a new `embarch-core` test asserting each alias returns **byte-for-byte** what its replacement does); their *descriptions* were updated, because decision 33's don't-move-ground posture protects a working invocation and not stale prose, and `study_waveform_data`'s text was still describing an `Action` retired at schema v8.

  **Decision 39's manifest half: deferred, under `embarch-core`'s own trigger** (Phase C emitting a real `outpost-manifest.json`), written into the decision rather than left silent. Core's `POST /flash` accepts neither a `manifest` part nor a `manifest_path`, by an explicit decision of its own; a sender against an absent receiver is a tested surface with no caller.

  **Decision 40, which is where the scope moved.** `run_study` gained `reflash` (`none`/`dev-bench`/`dut`/`both`), `allow_version_mismatch`, and — only for a DUT reflash — `project` plus the usual target-selection params. New `src/reflash.rs` holds the check → build → flash → submit sequence and the no-`git checkout` refusal, which now also guards the config file's own `version_command`, since `["git", "checkout", "v1.2.3"]` is exactly what someone would type there meaning "make the version be this". **Item 2 also moved `embarch-study-designer` and `embarch-core`**: the override had to be recorded in a `StudyResult` that had no field for it, and `VersionSource::FlashedThisRun` was a variant nothing could produce — so `Provenance` gained `overrides` (host schema v10, the first bump that moves that constant alone) and `POST /study` gained two query parameters. **The most useful thing the work turned up:** supplying the flashed version is also what makes `requires.firmware_version` checkable, so the DUT half of Core's gate went from documented-but-unimplementable to live.

  **Two smaller findings.** The two halves sequence *differently* — dev-bench is flashed then read back, the DUT is verified then flashed — which is decision 40's verification asymmetry appearing as control flow, and means a wrong tree fails without touching the board. And this file had **no decision 31** and five references pointing at the gap (§3's new numbering note).

  `cargo build`/`test` (49, up from 45)/`clippy --all-targets -- -D warnings` clean here and in `embarch-core-client` (11 tests, up from 7); `embarch-study-designer`, `embarch-core` (98 tests, up from 90, Linux **and** native Windows), `embarch-ui`, `embarch-umbrella` and `embarch-topology` all green. Not deployed — and the live Core is now two schema steps behind, so Core still deploys before api.

- 2026-08-25 — **Rebuilt against `embarch-study-designer` schema v9** (Milestone 7 Phase B item 0). Decisions 39/40's own api work — manifest transport, `study_stream_data`/`list_study_streams`, `run_study --reflash`/`--allow-version-mismatch` — is still unstarted. What changed here: `study.rs`'s `recompute_steps_crc` became `reseal_study`, recomputing **both** of a `Study`'s seals (`steps_crc` and the new `streams_crc`) with a `ResealError` that names which one failed to compute; the two CLI/MCP description strings that told callers a study needs "power_sample steps" to have power data now name a `PowerFrontEnd` stream tap, since the field they referenced no longer exists; and both `tests/fixtures/*.json` shed their now-meaningless `power_sample: null` keys.

  **`embarch-core-client`'s `post_study` now checks Core's `study_designer_schema_version` before submitting** — `embarch-study-designer/design.md` §3 decision 12's api<->Core half, which had been documented since 2026-07-28 and never actually built on either side. Placed in `post_study` rather than at each caller because the CLI and the MCP tool both submit through that one method, and a drift detector only one of them runs is not a detector; `GET /status` is already this hop's connection-establishment check, so it is one cheap read immediately before the submit. A mismatch is a downcastable `SchemaVersionMismatch`, the same idiom `StudyConflictError` uses. **A Core serving no version at all is refused, not waved through** — it is a Core predating the field, which is exactly the drift the field detects. Note this is stricter than §3 decision 17's warn-only posture for `contract_version`: that one is a warning because a renamed HTTP field degrades gracefully, while a drifted `Study` shape fails in whatever way serde happens to fail, mid-study. **Operational consequence:** the currently-deployed live Core serves no version, so it must be redeployed before this `embarch-api` can submit anything. `cargo build`/`test` (40/40)/`clippy --all-targets -- -D warnings` clean.
