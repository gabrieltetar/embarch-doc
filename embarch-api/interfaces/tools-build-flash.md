# embarch-api: build and flash tools

**Status:** active, 2026-09-02. Split out of [tools.md](tools.md) 2026-09-10 (`tasks/api/053`) — see that file's header for the one-table premise this section still honours.

| Tool / subcommand | Params | Behaviour |
|---|---|---|
| `build` | `project`, `P`, `build_variant?`, `vs?`, `pristine?`, `verbose?` | Runs the configured or call-time-assembled build command. Selection is validated against the live scan **before** assembly. **Answers with the verdict below, not the log**; `verbose` (CLI `--verbose`) gives the old answer — success, exit code, stdout/stderr truncated to 64 KB, artifact path and freshness — plus `log_path`. `build_variant` builds a `[projects.build_variants.<name>]` in its own directory; `pristine` passes `-p always` (refused on a `static` project's default build); `vs` names another variant, or `default`, to compare memory against ([decisions](../decisions/build.md) 103) |
| `flash` | `project`, `P`, `firmware_path?`, `build_variant?`, `erase?` | Core `POST /flash` with the resolved chip, format and offset. `build_variant` flashes that variant's artifact. `firmware_path` flashes an already-built or one-off file — bypassing *build*-target resolution, but a `zephyr-west` project still needs enough selection to resolve the **chip**, none being stored |
| `build_and_flash` | `project`, `P`, `build_variant?`, `vs?`, `pristine?`, `verbose?`, `erase?` | Runs `build`, flashing only if it succeeded **and** the freshness check passed. Returns both sub-results; `build` is the verdict, or the old shape with `verbose` |
| `reset` | `project`, `P` | Core `POST /reset` with the resolved chip. Same selection as `flash`, same reason |
| `mem_read` | `ranges` (`ADDRESS[:WORDS]` strings), `role?` (`dut`) or `probe_serial?` (decision 95) | Core `POST /live/mem-read`: 32-bit words of the role's target, every range read under one halt of a running core, which is then let run again; returns the words, `found`, `left`, `halt_count`, `halted_us` and the deprecated `halted` (decision 83). Raw words; the atlas's `reg_read` decodes registers by name |
| `core_state` | `role?` (`dut`) or `probe_serial?` (decision 95), `halt?` (false), `samples?` (8, 1 to 64) | Core `POST /live/core-state` (core decision 97): where the core is, read-only. Default never halts: `DHCSR` then `samples` `DWT_PCSR` PCs 1 ms apart then `DHCSR`; `halt=true` halts once (counted in `halt_count`), reads R0-R12, SP, LR, PC, xPSR, CONTROL, PRIMASK and `SCB_ICSR`, and puts the core back as found. Answers `found`, `left`, `halt_count` (decision 83) |
| `serial_log` | `signal?` (preferred), `port_wait_ms?`, `project`, `port?`, `baud?`, `duration_ms?` | **Preferred: `signal`**, a declared signal's name: Core `GET /serial-log?signal=` resolves its USB serial to the port's current name, reads at the signal's baud and waits `port_wait_ms` for a re-enumerating port; no project or port needed ([decisions](../decisions/serial-log-signal.md) 94; needs a Core that accepts `signal` there, an older one answers 400). Fallback for an undeclared port: Core `GET /serial-log`, opening the named port on **Core's own machine** — not the caller's. Falls back to the project's configured port and baud, then 115200 / 2000 ms; **no further fallback exists** — a `port` unresolved either way is a plain error naming the project, not a reach for `GET /dev-bench/port` (that link is dev-bench's, a different question — see `list_serial_ports` below). `duration_ms` is bounded by Core's own cap on this route — see Core's `/serial-log` interface doc for the current number. The result carries Core's `truncated`: `true` means the byte cap cut the capture short and `lines` is only a prefix; `false` is complete; `null` (plus a `truncation_note`) means this Core did not report it, never "complete". The CLI prints the same marker, as `study-streams` does ([decisions](../decisions/client-crate.md) 58) |
| `list_serial_ports` | — | Core `GET /serial-ports`: every USB serial port **Core's own machine** currently enumerates, unnarrowed. Use it to discover a value for `serial_log`'s `port` when a project has no configured `serial_port` — the value wanted is whatever Core's OS recognises (e.g. a Windows COM name when Core runs on Windows and the caller is WSL2), not a port name guessed from the caller's own machine. An empty list is a real answer, not an error. Also what makes a declared signal's `direct`-route `port_serial` findable at all — see [tools-topology.md](tools-topology.md) |

**`erase` defaults to `false` and is never implicitly `true`.** The MCP description and the CLI help both spell out what it does to a board, at a length no other argument here gets — that wording is itself the design point, and [decisions](../decisions/tool-wrapping.md) 41 is where it is argued and where a change to it belongs. Core performs the erase and decides whether a target supports one; a refusal comes back verbatim. Since `embarch-core` decision 84 `erase` skips alias and non-writable regions (STM32 option bytes) and never chip-erases, and every flash result (MCP JSON, CLI JSON and the CLI's text line) carries `erased`, the ranges blanked (`[]` without `erase` or after a vendor tool); an older Core omits it and the client reads `[]`.

**Why `build` and `flash` stay separate as well as bundled:** the common agent workflow wants one call, and bundling prevents flashing a stale artifact after a build error — but iterating on compiler errors should not touch hardware every call, and a re-flash after a board reset should not need a rebuild.

**The verdict** ([decisions](../decisions/log-capture.md) 102) is read out of the build's whole log: `success`, `exit_code`, `timed_out`, `seconds`; `warnings` (distinct) and `first_warnings` (up to ten, `file:line: message`, paths relative to the build's working directory); `first_error` (the first compiler, Kconfig, CMake, devicetree, `dtc` or linker error with the lines that belong to it — a source excerpt, a CMake message body, the warnings a Kconfig abort is about — and nothing printed after it; at most 20 lines, 3,000 B); `memory` (`{region: {used_bytes, total_bytes}}` from the last linker table; `memory_from_previous_build: true` when nothing relinked and the figures are the previous build's); `artifact_path`, `artifact_fresh`; `log_path`. When the log has ztest or twister lines: `tests` (one line per case, `PASS suite.case`, or per twister scenario when there are no case lines; up to 100, the rest counted in `tests_not_listed`) and `first_failing_assertion`. Beside it: `target`, `pristine` (why the directory was wiped, when it was), and with `vs` an object `{build_variant, delta: {region: {delta_bytes}}, baseline_finished_at}` or `{build_variant, error}`. The CLI prints one status line (`build ok 'p [bench]' in 0.5s: 1 warning(s), FLASH 19828/262144 B, …; artifact fresh: …`), the `vs` line, warnings, the error block, test lines and `log: …`.

**The whole log** — both pipes in the order they were read, untruncated — is `embarch-build.log` inside the build directory, beside `target.json`, with `embarch-build.json` (`success`, `memory`, `finished_at`) beside it; a build whose plan names no directory (a `static` project's default build) keeps both under `<temp dir>/embarch-build-logs/<key>-<hash>.*`.

**Build variants** (`[projects.build_variants.<name>]`, [decisions](../decisions/build.md) 103) pass `-DEXTRA_CONF_FILE=a;b`, `-DEXTRA_DTC_OVERLAY_FILE=…` and one `-DNAME=VALUE` per define after `west build`'s `--`; Zephyr resolves a relative path against the app directory. A `zephyr-west` variant builds in `<build_dir_root>/<target dir>.<name>`, a `static` one in `<build cwd>/build-<name>`, its artifact at `artifact_path` with `build/` replaced by that directory. Config load refuses the reserved name `default`, a name other than 1–40 of `[A-Za-z0-9_-]`, a variant setting nothing, an entry with `;`, a define with `-D` or no `=`, an unknown key, and on a `static` project a `build_command` that is not a plain `west build` (program `west`, then `build`, no `-d`/`--build-dir`/`--`) or an `artifact_path` not under `build/`.
