# embarch-api: study tools and subcommands

**Status:** active, 2026-09-04.

Submitting a study, reading its result, and watching it live. The rest of the surface: [tools.md](tools.md). Why: [../decisions/study-reads.md](../decisions/study-reads.md), [../decisions/study-reflash.md](../decisions/study-reflash.md), [../decisions/surface.md](../decisions/surface.md). Current truth: [../spec.md](../spec.md).

MCP tools are `snake_case`, CLI subcommands `kebab-case`, over one implementation ([tools.md](tools.md)). `P` is the project-selection set defined there.

| Tool / subcommand | Params | Behaviour |
|---|---|---|
| `run_study` | `study` (MCP) / `--study-file <path>` (CLI), `reflash?`, `allow_version_mismatch?`, `project?`, `P` | Recomputes and overwrites **all three seals**, then Core `POST /study`, returning `{ study_id }` at once alongside what it reflashed. `reflash` is `none` (default) / `dev-bench` / `dut` / `both`, building the tree **as it stands** — never `git checkout`. `project` is required only by `dut`/`both`: a *study* is not project-shaped, rebuilding a DUT's firmware is. `allow_version_mismatch` proceeds past an unsatisfied requirement, the override **recorded**, never silently honoured. **A pinned bench version Core did not report is always refused, override or not**; a bench requirement of `any` is the way to run against such a Core ([decisions](../decisions/study-reflash.md) 105). Sends the project checkout's `build_commit`, `build_dirty` and (`zephyr-west`) `build_toolchain` as claims, each only when read ([decisions](../decisions/build-claims.md) 111) |
| `study_status` | `study_id` | Core `GET /study/{id}`'s fields verbatim, plus two a host study fills: `host_result`, its record, and `pending_prompt`, a `Prompt` waiting for a person; both null otherwise ([host-study tools](tools-host-study.md)). **CLI only:** `--follow` watches the study live instead (below); without it, one snapshot |
| `study_watch` (MCP) | `study_id`, `wait_secs?`, `max_events?`, `include_samples?` | Subscribes to Core `GET /study/{id}/events` and returns every step, status change and (optionally) sample batch pushed in the window, in order. Bounded because an MCP call is request/response: `wait_secs` defaults to 60, caps at 600 — `complete: true` means terminal, otherwise call again. `include_samples` defaults to **false**, counting `SampleBatch`/`GattTranscript` per tap instead of listing them; the bulk data's exit is `study_stream_data` |
| `study_stream_data` | `study_id`, `name`, `raw?` | One declared tap's capture, by the name the study gave it. Rendered file where the encoding has one; `raw` serves the bytes. **Nothing here inspects content to decide** — an encoding is declared, never sniffed. A non-UTF-8 capture returns a clear error saying that is *expected* for a raw tap, pointing at `--out`, not a decode failure reading like the capture broke |
| `study_measurements` | `study_id` | A finished run's own `measurements.json` **unchanged**, before any publish: `GET /study/{id}/measurements` (`embarch-core` [measurements interface](../../embarch-core/interfaces/measurements.md)), no summary and no reshaping, so prose cites `value`, `unit`, `by`, `u_source`, `declared_by` as written. Lease-open. Core's four refusals reach the caller by name in the error, from `embarch-core-client`'s `MeasurementsRefusal`: `no-such-run` (404), `still-running` (409), `no-measurements` (422: none declared, not completed, or a host study with no `parse` step; recognised by the status, or a body `code` of `no_measurements`, never by Core's wording), `files-gone` (410). CLI `study-measurements <study_id> [--out]`. Measured by `core_client_http.rs` against a mock Core (the file byte for byte and each refusal); a live Core's answer is not run here |
| `list_study_streams` | `study_id` | Per declared tap: `name`, `bytes_written`, and **`truncated`** — the reason this exists, since the three retired fixed-channel aliases structurally could not report it. `bytes_written: 0` means a tap was declared and captured nothing, a different fact from one never declared |
| `study_stream_load` | `study_id`, `name` | An `OutpostTrace` tap's own load repartition — per-subject load shares and the coverage line — computed once on Core, `GET /study/{id}/stream/{name}/load` verbatim (`embarch-core` decision 62; suite decision 4). Not a fourth encoding-driven rendering of `study_stream_data`: no `raw` choice, one shape always. `{rows, rows_dropped_by_cap, row_cap, rows_unparsed, summary: {unit, window_extent, gap_extent, gap_fraction, records_lost, has_time_base, thread_extent, idle_record_extent, isr_extent, unaccounted_extent, below_resolution_spans, subjects: [{key, label, unnamed, kind, entries, measured_spans, total_extent, share, excluded_spans, excluded_extent, gap_crossing_spans, open_ended_spans, open_started_spans, below_resolution_spans}]}}`. Three refusals relayed as errors, never smoothed into an empty answer: the tap is not an `OutpostTrace` (`400`), the tap has not rendered yet (`404`, same reason `list_study_streams`' own tap-level note would give), or the rendered CSV's columns don't match this build's expectation (`422`, `embarch-ui` decision 10 (trace)'s pin carried across) |
| `export_audio` / `export-audio` | `study_id`, `name`, `study_file` (`--study-file`), `out_dir?` (`--out-dir`) | A framed analog tap as 16-bit PCM mono WAV at its declared rate, one file per gap-free segment, with an Audacity label file and `cue ` points per file, in the study's export folder ([decision 130](../decisions/audio-export.md)). Fetches the tap's raw capture (`study_stream_data` with `raw`), reads rate, layout and folder from `study_file`. `{export_dir, sample_hz, resolution_bits, files: [{wav, labels, first_sample_index, samples, markers}], gaps: [{after_segment, expected_index, got_index, missing_samples, backwards}], gaps_file, warnings}`. Refused with a reason for a tap with no declared rate. No lease |

**A submission over a capacity bound is refused here, before the HTTP call, naming every field it overflowed and that field's limit** ([decisions](../decisions/study-reads.md) 27) — counts for the four lists, **bytes** for a name, and one closing line saying the bounds are dev-bench's compile-time buffer sizes and cannot be raised for one submission. Same message on both front-ends. A failure that was *not* a capacity overflow still reports `serde`'s own schema error, which for that case is the better one.

CLI data subcommands take `[--out <path>]`. **`--out` is how a binary capture gets out intact** — a raw tap's bytes are not text, and the no-`--out` path writes them to stdout untouched. `list-study-streams` marks a short capture on its own row, not a column an eye slides past.

**`list-studies [--limit N]` is a CLI-only read verb** (EMB-405; no MCP tool, a test says so): Core's `GET /studies`, no lease, newest first by `started_utc_ms` (a study with none after those that have one, by id), `--limit` keeping the first N. `--json` is `{success, keep, studies: [{study_id, study_name, status, started_utc_ms, ended_utc_ms, taps, note}]}`; a tap is `{name, encoding, encoding_kind, rendered}`, `encoding_kind` the flat `raw`/`text`/`samples`/`gatt_transcript`/`outpost_trace`/`struct`, and `taps` is null (never empty) where Core could not read them. Shape fixed by `embarch-promptu`'s `docs/contract.md` 15.3.

## Watching a study live

`study-status --follow` (CLI) and `study_watch` (MCP) are **an addition to polling, never a replacement** — `study_status` with no flag is still one snapshot. Both consume the same client ([decisions](../decisions.md) 48, 49); they differ only in that a CLI user can be handed a stream and an MCP caller cannot.

- **`event: lagged` is a reported fact, not an error.** Core emits it deliberately when a subscriber falls behind, rather than skipping messages silently. The CLI prints a `[lagged]` line inline and repeats the count in its summary; the MCP result carries a `lagged: {events, note}` object. Both say the same: the events are missing **from this live feed only**, the study is unaffected, and `study_status` holds the complete record. Neither fails the call. **Not `list_study_streams`**, which reads the same `result` and answers `streams: null` until the study is terminal — so during a `lagged`, which is by definition mid-run, it adds nothing `study_status` does not already say.
- **A dropped or refused stream falls back to polling** `GET /study/{id}` and says so on its own line (`transport` in the MCP result, `[polling]` on the CLI) with the reason. No reconnect: Core keeps no replay, so reconnecting would resume with a silent hole. The genuine failures are neither mechanism answering and an **unknown study id** (a 404 on the opening poll, even with the stream open): the CLI exits non-zero naming the id (`--json`: an error object), `study_watch` returns an error naming it, both at once rather than after `wait_secs`.
- **`interrupted` ends a follow as its own outcome** (a `.partial` record with no job; Core never moves it on). CLI: prints `study <id>: interrupted — ...` to stderr, **exits 1**, and the `--json` summary has `status: "interrupted"`, `success: false`. `study_watch`: `complete: true`, `status: "interrupted"`, plus a `note` (null otherwise). `completed` and `failed` are unchanged.
- **A `Text` tap's chunks arrive as `StreamText` and are counted, not listed, by default** (`embarch-core` decision 70). Every study carries the reserved `dev-bench` console, so listing its chunks individually would fill `max_events` and omit the step completions the tool exists to report — `text_chunks` gives `{chunks, bytes}` per tap, alongside `sample_batches` and `gatt_entries`, and `include_samples: true` lists all three instead. The CLI prints each chunk on one `[text step N]` line with escapes visible, because a chunk is carried **verbatim**: it can end mid-line and mid-character, and printing it raw would splice unrelated chunks into lines neither tap sent.
- **`events_omitted` (this crate's `max_events` cap) and `lagged` (Core's) are different facts**, reported as two. A caller told only that events are missing cannot tell which happened, and the remedies differ.
- **CLI `--follow --json` is NDJSON**, not one object: one compact record per line, ending with a `{"type": "summary", ...}` line. The only `--json` here shaped that way, and it has to be — a stream cannot be one object. `--follow-timeout <secs>` stops watching early and **exits 1**; a study that *fails* still exits 0 (an `interrupted` one exits 1, above), because reporting a failed study is a successful report.
