# embarch-core decisions: The dev bench's analog capture

**Status:** active, 2026-11-24.

How Core gets a dev bench's analog blocks to the tap decoder of [streams.md](streams.md) decision 125: finding and opening the samples port (126), and the session's prompts around a capture (127).

Index: [../decisions.md](../decisions.md). Current truth: [../spec.md](../spec.md).


## The samples port

### 126 — A study with an analog source opens the dev bench's samples port, found from its recorded identity

2026-11-24 (EMB-480; the owner's EMB-469 decisions 1 and 13). Decision 125 decodes the blocks once bytes reach a tap; this is what brings them there. **A study whose `StreamSource::AnalogInput` (tag 5) is declared opens the enrolled dev bench's samples CDC ACM port before `StudyStart` is sent, and holds it exclusively until the run ends.** Before, because the source writes its start header once, when the study starts it, and a closed port would lose it; the port's stale input is cleared on open (bytes before the first header are refused by decision 125's decoder, which would otherwise put a refusal row at the head of every recording). It is not scoped by `StreamScope`: the header does not repeat, so a port opened at step 3 cannot show the stream's start.

**The port is found from identity and order, never a name.** The dev bench is one USB device with three ports (`embarch-dev-bench` decision 61: control, samples, SMP, each with an interface string). **The OS does not give Core the string**: `serialport`'s `UsbPortInfo` has VID, PID, serial, manufacturer, product and an interface *number*, nothing else. So Core takes the control port's recorded identity (decision 124's `control_port`, `embarch-topology` decision 50), requires its VID to be the dev bench's (`0xEBAC`) and a serial and an interface to be recorded, lists the ports with that VID, PID and serial in interface-number order, and takes the one after the control port, the firmware declaring them control, samples, SMP. Rejected: matching the string "EmbArch samples", which nothing reports; recording a samples interface at enrollment, a second field to keep true beside the control port's and no more known than the order. **Whether the OS reports the interface numbers in the firmware's order, and which interface of a CDC function it reports, is not established by reading code** and is owed to a bench run.

**A samples port that cannot be found refuses the study before anything starts**, with the reason: no recorded identity (`409`, say how to record one), a recorded port that is not a dev bench or lacks a serial or interface (`409`), the bench not enumerated or no port after its control port (`404`, as for decision 124), the OS giving no interface numbers (`409`), the port held by another study or a failed open (`409`). Nothing is flashed, reset or sent first; the study lock is released. **The reader is Core's own thread**, the one a direct signal tap uses, so the start header and blocks take the path of every other tap's bytes into decision 125's decoder, and it stops with the rest of Core's own ports on every exit: the end, a failure, a timeout, a panic. **A device study has no cancel route** (`POST /study/{id}/cancel` is for a host study, which declares no analog source), so "cancel" is the failure and timeout exits. A read error on the samples port ends the reader and sets the tap's `lost_at_source`, so the capture reads as short rather than complete. Measured: unit tests with a fake port, no hardware (the header and a 5-minute 32 ksps stream through the real reader: every byte kept, no gap or refusal row; absent port refused with `open` never called; stop closes and releases the port). A real session over the CDC link is owed to the bench.

## The session

### 127 — A session study raises its Start prompt before `StudyStart`, saves the run fields, and ends at the cap or when Done is answered

2026-11-24 (EMB-482; the owner's EMB-469 decision 10; `embarch-study-designer` decision 106's `SessionSpec`). Until now Core only exempted a session's recording from the sweep (decision 125). **The prompts reuse the host study's machinery and add no second one**: the one prompt slot, `PromptPending` / `PromptResolved` on the study's event stream, `pending_prompt` on `GET /study/{id}` and `POST /study/{id}/prompt`, which `embarch-api`'s `answer_prompt` and the UI's modal already call (decision 105). A prompt gains an optional `session {phase: "start"|"done", run_fields: [{name, label, required}]}`, and an answer an optional `run_fields: [{name, value}]`; both are absent for a host study, so its bytes are unchanged, and no existing route changed shape or meaning.

**Order.** `POST /study` refuses what needs no person first (validation, the version gate, the bench's identity, the outpost pre-flight, and for an analog source that a samples port *exists*), registers the job, answers `202`, and the rest runs on a task: **Start is raised and awaited; then the samples port is opened; then `StudyStart` is sent.** The port opens after Start, not before, because opening clears the OS's stale input and a person may take minutes, which would put their wait's noise at the head of the recording. The cost: a port that exists when checked but fails to open fails the job after the person answered. The version gate stays synchronous (its `StudyStart` is held back, nothing else changes), so a mismatch is still `409` before anyone is asked. A `StudyStart` that fails to send is now the job's `failed` where a plain study answers `502`, because the `202` has gone. A Start that is cancelled, or unanswered for **an hour** (decision 105's cap, for the same reason: it holds the study lock), fails the job; nothing was sent to the bench and no results directory exists. **The dev-bench link is held idle while Start waits; that it and the DUT survive minutes of it is not established by reading code and is owed to a bench run.**

**Answers.** Checked under the slot's lock with `validate_run_answers`: unknown, repeated, or missing required fields, and a value over the field's limit, are `400` with the reason, and **the prompt stays pending** so the person corrects it. Run fields on any other prompt are `400`. They are saved in `session.json` beside `events.json` (declared order, `answered_by`, when sampling started, how it ended), written before a byte is captured so a run that fails still says what it was, and again at the end. It is not a signed subject: adding it to the record's subjects would change decision 110's format, which this unit does not.

**Who may answer, by token scope (decision 109).** **Start: the person's token only**, `403` for the agent's. The run fields label a recording as that person's, and an agent would be inventing the serial and the room; `embarch-api`'s `answer_prompt` therefore cannot answer a Start, and the UI can. The precedent is discarding a run. **Done: either token**, because it only ends a capture the cap would end anyway, so an agent that started the run may stop it. Done can only be `confirmed` (`400` for `cancelled`): there is nothing to cancel.

**The cap and Done.** Done is raised when `StudyStart` has gone out, its deadline the cap, and stays up for the whole capture: **answering it is how a person ends the capture early.** Sampling ends at the first of: Done confirmed, the cap (`max_duration_ms` from `StudyStart`), or the bench's `StudyDone`. Whatever ends it, Done resolves with `PromptResolved`: `confirmed`, `timed_out` at the cap (so the person sees the end), `study_ended` when the bench finished first, `study_failed`. The run loop looks at the prompt and the cap before every receive and cuts the receive to 20 ms. An early end is `completed`, not `failed`: the session asked for it. **`done_text` is therefore on screen while the capture runs**, and the designer has to word it for that; the alternative read, raising Done only after the capture, leaves a person no way to stop one early. **Core stops capturing; it cannot tell the bench to stop**, because the dev-bench wire has no abort message and adding one is a wire change. Core stops its taps and the samples reader, closes the link, and seals what it has. What the bench does afterwards (it may run its remaining steps) is owed to a bench run.

**No session, no change.** A study with no `session` takes the old path untouched. **Measured:** unit tests, no hardware: waiting on Start; run fields saved and ordered; each bad answer refused with its reason and the prompt kept; both scopes; a short cap ends sampling and resolves Done `timed_out`; Done answered ends it early; the route through the real handlers. **Not run:** a session against a real bench; the run loop's own polling (it needs a live link and is covered only by the pieces above). The UI's modal sends the run fields since embarch-ui decision 107, driven headless against a stub Core; `answer_prompt` holds the agent's token, which Start refuses by design.
