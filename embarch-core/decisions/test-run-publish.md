### 148 — A Test run's `report-data.json` is the crate's roll-up over what the executor judged, with every run on the unit listed

`tasks/core/175`, EMB-373; `notes/hil/06`, "Publish", and `03`, "The report". `POST /test-runs/{id}/report-data` is 116's step for a Test run, in `src/test_publish.rs`; the signing, manifest, log segments and `published` entry are `publish.rs`'s (`sign_manifest`, `call_log_segment_of`), shared: a Study's publish was moved onto them with its output unchanged.

The data (`kind: "test_run"`, deterministic, no clock) is read from the prepared record, the signed record (144), `result.json`, the study records the run amended (145, 146) and the run log. **Core decides no verdict.** Each test's `{verdict, reason, qualifiers}` is what the executor judged and signed (`result.json`'s hash is checked against the record's subject), and every requirement and the run's summary is `embarch-study-designer`'s `Rules::latest().requirement` / `combine` over them, the behaviours recorded in `rules`. It lists `tests`; `requirements` (verdict, per-verdict counts, qualifiers, `n_of_m`, `skipped_tests` with reasons, `relayed_listed_apart`); `not_run` (a selected test left skipped or never reached, and every selection entry not `selected`, each with its reason); `coverage` from the record's selection; `manual_verdicts` (147); and `runs_on_unit`: **every** `test` entry on the unit, failed ones included, grouped by test, requirement IDs, DUT image and definition hash, each with its log position. It carries the unit (hardware ID, declared serial, the person's latest `unit_declared`), the person's name, `go_by`, `published_by`, the fixed statement (pre-compliance evidence, not a certification, not an accredited test report), the attestation label (119) and `standard` with `requirement_count: null` and `atlas: {joined: false, note}`: Core joins no atlas, so the count is always absent.

**Manual verdicts.** A person's counts toward the requirements of the test it names (test and definition hash, on this unit) as the latest of that pair, with `rests_on_person_observation`; the agent's (`relayed`) goes to the roll-up marked `relayed`, which counts it nowhere and tallies it in `relayed_listed_apart`. One naming no test of this run is listed `in_run: false` and joins nothing. A unit whose identity was not read keeps no history or manual verdicts, and the summary carries `unit_identity_not_read`.

**A test the run never reached** (no result: an interrupted run) is read by the roll-up as skipped for `stopped_by_error`, a gap, so its requirement is `not_verified`; the data names the true reason (`not_run`, `interrupted`). **[Assumed]**: the crate's closed reasons have none for "the run died".

**Not done:** a test the selection excluded (`hook_unmapped`, `bench_missing`, `not_selected`) is not in `run.json`, so its requirements are unknown here: it is in `not_run` and `coverage`, and cannot make a requirement `not_verified` or add to `n_of_m`.

**Measured:** unit tests over the real routes, a signing key and a run log, with a fixture Test run and two study runs: the requirement fields equal the crate's roll-up; a requirement with a test skipped for `requires_not_met` reads `not_verified` and lists the test and reason; an earlier failed run of a test on the unit is listed; a relayed manual verdict is listed apart and a person's counts. **Not run:** a real Test run.

### 149 — A Test run's publish is one manifest over every study run's files, entered in the run log under the run id

`POST /test-runs/{id}/publish` takes `{files}` and refuses as 116 does, rebuilding and comparing `report-data.json`; a verdict, declaration or run on the unit entered since is a `409`, since it changes the data. The manifest `subject` is each study run's Core files under `studies/<study_id>/`, `run.json` (its canonical bytes, which hash to the record's `run.json` subject; written at `report-data`), `result.json`, `test-run.dsse.json`, `report-data.json`, `report-data.dsse.json`, `run-log-segment.jsonl` (every line before the entry, as a Study's) and, when the record names a range, `call-log-segment.jsonl`. Files go under `test-runs/<run_id>.publish/r<N>/`. The `published` entry carries **`run_id` and no `study_id`**, which is what retention reads: the run's studies are released (144) and swept as one unit. A revision counts the `published` entries naming the run and names the one it supersedes.

**Refused:** `404` a run Core never prepared; `409` a run that has not ended, has no signed record, a record, result or study record gone or not the file the chain names, or a study whose captures were discarded. A Test run whose studies the sweep took is refused, **not restored**: handing a Test run's files back is not built.

**A resumed pair** (EMB-370, not landed) is not built. Once resume exists, the later run's record names the earlier in `resumes` (144) and the pair will publish as one zip: `report-data` reads the earlier record through that link and reports each test's latest verdict across the pair, the manifest names both records, both `result.json` and both runs' study files, and a `published` entry is made for each run id so retention releases both. Today `resumes` is carried in the data and not followed.

**Not done:** no route serves a revision's files, which embarch-api needs to build the PDF (filed as a follow-up).

**Measured:** unit tests over the real routes: the manifest verifies under a DSSE v1 check, names every study's files, run.json, result.json and the record, and is entered with the run id; the studies are released; a second publish is revision 2 naming the first; a publish before `report-data` and over a swept study are refused. **Not run:** a real Test run's publish, a third-party DSSE verifier, the native Windows build.
