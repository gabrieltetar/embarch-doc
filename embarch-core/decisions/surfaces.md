# embarch-core decisions: Error and version surfaces

**Status:** active, 2026-09-17.

The error body and contract version that were designed and not built, whether `/status` needs a content identity on top of its version, and how a hardware-identity error tells its own two shapes apart.

Index: [../decisions.md](../decisions.md). Current truth: [../spec.md](../spec.md). The human enrollment surface split out to [enrollment.md](enrollment.md) 2026-09-11 (below), a real topical seam under `DOC-COMPACTION.md` §3 rather than a squeeze.

### 13 — `core_version` on `/status`; no hand-bumped `contract_version` (built 2026-09-03)
The only cross-boundary version check was the study schema, so nothing over HTTP could say which build answered — a deploy that silently did not land was indistinguishable from one that did (`embarch-dev-workflow.md` §4a: `deploy-core` reports `landed` either way, and its length check cannot discriminate a rebuild of one constant). `/status` now serves `core_version` from `env!("CARGO_PKG_VERSION")`. **Mechanical, not maintained**: `Cargo.toml`'s version tracks the release tags, so the field cannot drift from the build serving it. Consumers **warn, not refuse** on a version difference — this decision's original posture, unchanged.

**The `contract_version` half is retired rather than built.** It was to be hand-bumped only for a wire-visible change, and nothing forces the bump: the failure mode is a number reading "same" across contracts that differ, worse than no number — this entry's own history is the evidence, since the endpoint table described all three designed fields as shipped **for months when none were**. `core_version` covers the case mechanically and **over**-warns rather than under-warns, the safe direction for a warn-not-refuse consumer. Revisit if a skew warning is ever silenced as too noisy to act on; that is the first evidence a finer-grained number would earn its keep.

The served field set is pinned by a test on `StatusResponse`'s serialized keys (`api.rs`), so **adding** a field without editing [../interfaces.md](../interfaces.md)'s `/status` row fails the suite. That test, not a note, answers the "described as shipped when it wasn't" shape here.

### 67 — No content hash on `/status` today; a self-hash is the right question, filed rather than built (2026-09-17)
`embarch-umbrella` doctor check 15 compares served `core_version` against expected and is blind to a same-version rebuild whose deploy silently did not land — decision 13's `core_version` can't distinguish two builds sharing one `Cargo.toml` version. `embarch-umbrella/open.md` named this repo as the one to decide whether `/status` should carry a content identity to close it.

**A git SHA baked in at compile time proves *what source was compiled*, not what bytes are running** — blind to a dirty working tree (this suite rebuilds on-bench, uncommitted, routinely) and to a non-reproducible build, where two builds of one commit differ in bytes under one SHA. A build timestamp shares that blind spot and says nothing about content besides. **Only a self-hash of the running executable** — `std::env::current_exe()`, hashed once — answers the literal "did the deploy land" question.

**Decided: yes — filed as a separate task, a wire-schema bump not landed here (`tasks/core/088`).** This closes for content the gap decision 13 closed for version: today the check is manual, hashing the file on both ends after a deploy, filesystem access required; a served field makes it reachable over HTTP. **Cost:** hash once at process start into a cached static, not per request — the running bytes can't change mid-run, so re-hashing per `/status` call buys nothing and costs a full-binary read every time. Adds a new hashing dependency; none of this crate's current ones hash. Field name, shape, and truncation are the implementation task's to decide.

**Trigger to reverse to "no":** none identified — decision 13 was built, not deferred, on this identical reasoning for version.

### 68 — `binary_sha256` on `/status`: full lowercase-hex SHA-256, cached once (2026-09-17)
Implements decision 67's yes. **Shape:** full 64-char lowercase hex, not truncated — a consumer string-compares it against its own hash of the deployed artifact. **Dependency:** `sha2`, already resolved transitively via `probe-rs` → `espflash` at `0.11.0`; pinned direct rather than adding a second copy (`Cargo.toml`'s comment has the `cargo tree` check). **Failure mode:** `null` if `std::env::current_exe()` or the read fails — `/status` still serves the rest; a caller reads `null` as unknown, not a mismatch.

### 12 — A `{code, message, cause}` JSON error body — deferred, and it is not Core's alone
Plain-text errors suit a human reading a CLI error, but `doctor --json` and a UI need to branch on error *kind*; a `{code, message, cause}` body would also retire the "finer CLI exit codes" idea, since a script branching on failure kind wants a field, not an exit code. Still worth building, and **deliberately not built here.**

Its value is **entirely** in consumers branching on `code`, which makes the `code` enum a wire contract shared with `embarch-api`, `embarch-ui` and `embarch-umbrella`'s `doctor` — a cross-repo sequenced change (`embarch-fleet/protocol.md` §8), not a Core-local one. Core-side alone it's ~40 error-construction sites re-shaped, each needing a stable `code`, while every consumer still reads plain text: the whole cost and none of the benefit. **Trigger:** the first consumer that must distinguish two error kinds sharing one HTTP status and cannot. (Decision 59 below is that trigger firing for one route alone: a `kind` field scoped to `POST /validate`'s JSON body, not the general enum this entry defers.)

### 55 — `study_schema_mismatch` retired as a name; no `code` enum exists to hold it (2026-09-10)
`open.md` read this as a stray member missing from an otherwise-real `code` enum. Reading the code settled it: `embarch-core` has no `code` enum at all (decision 12 defers building it) — `study_schema_mismatch` was never a member of anything, just a name proposed in prose for a future enum and left unreconciled. Retired: nothing to make reachable without building decision 12's body, and no seat is owed by prior mention if that enum is ever built — decision 12's own trigger earns any member its place.

### 59 — `POST /validate`'s `TopologyMismatch` gets a `kind` field; "not attached" is not "mismatch" (2026-09-11)
`live_hardware_id: None` (probe unplugged, ordinarily) and `Some(x)` disagreeing with the recorded ID were both rendered under one `topology mismatch` lead, JSON and plain text alike — opposite conditions (`embarch-topology` decision 20: a disagreeing ID means the wrong board is on the desk and needs a human; an absent readback means nobody has plugged in yet, the ordinary bench state). `.claude/leg.md` handles the two oppositely — one leaves a task `open`, the other alerts a human — so matching on the leading phrase routed the common case (unplugged) into the one that costs sleep.

**Resolved by adding `kind: "not_attached" | "mismatch"`** to `ValidateMismatchResponse`, set from `live_hardware_id.is_none()` — a field, not prose, so a caller branches on it rather than on `reason`'s wording (decision 12's deferred `code` enum exists for exactly this reason; `NotEnrolled`'s downcastable shape, decision 28, is the same idiom one level up). `"not_attached"` answers `503`, keeping `409` for `"mismatch"` alone. **`fix_it_url` is `None` on the `"not_attached"` arm** — the fix for a detached probe is a USB cable, not the Topology tab, and one URL for both invited the confusion the lead already caused. `flash`/`reset` (`hardware.rs`) and `study.rs`'s dev-bench gate ran the same check through the same `{e:?}` chain — fixed the same way in plain text (`describe_topology_error`/`describe_gate_error`): a different leading clause, not a status code, since both already fold every gate failure into one status regardless of kind.

**Corrected 2026-09-17 (`core/074`) — the completeness claim below does not hold.** `TopologyMismatch` already carried `live_hardware_id`, so no change was needed there to add `kind` — but `embarch-topology`'s own doc comment on that field was wrong, since corrected (prose-only, `topology/056`): `None` means the probe was not found in `Lister::list_all()` at all. Every failure *after* that lookup succeeds — `.open()`, the power check, `attach`, core-select, or the hardware-ID read itself (`validate_known_timed`, `embarch-topology/src/hardware/validate.rs`) — returns a bare, non-downcastable `anyhow::Error`, no alert logged, never a `TopologyMismatch` (confirmed via `describe_topology_error`/`describe_gate_error`'s `None` arms and `validate_handler`'s `Err(internal_err(e))`, `src/api.rs`/`src/study.rs`). All four call sites (`/validate`, `/flash`, `/reset`, `study.rs`'s dev-bench gate) fall through to their own generic error path: `500` on the first three (`validate_handler`'s `Err(internal_err(e))`), folded into `502` on the fourth. Whether this deserves its own `kind` arm is left open; today it's an accepted, undocumented gap.

**Settled 2026-09-17 (`core/077`) — the gap above stays collapsed into `"not_attached"` as a considered choice.** `embarch-topology` decision 34 (`topology/058`) routed all five failures through `raise()`, each with `live_hardware_id: None`, so they downcast to `TopologyMismatch` and land on `classify_topology_mismatch`'s `is_none()` arm: `kind: "not_attached"`, `503`, no `fix_it_url` — same as a genuinely unplugged board. **No third `kind` was added.** `.claude/leg.md`'s binary split leaves a not-attached role's task `open`, and alerts only for a live ID that disagrees — none of the five new causes is an identity question, so all five belong `open`. Against that, a third value is a wire change reaching `ValidateMismatchResponse`, `embarch-api`'s `TopologyMismatchError` classification, its `tools.rs`/`cli.rs` text, any `embarch-ui` rendering, and the user guide — for a distinction `reason` already carries. No consumer today reads `kind` needing it (`embarch-ui`, the user guide: no hits on `kind`/`not_attached`) — decision 12's trigger has not fired.

**One real gap this did surface, filed rather than fixed here:** `embarch-api`'s `validate` tool appends a fixed `"— plug it in; this is not a topology mismatch"` suffix to every `"not_attached"` case, written when absence was the only reachable cause — wrong five times out of six now. Dropped to `embarch-doc/inbox/` as `embarch-api`'s own task.

**This crate's plain-text paths got one no-wire-change fix:** `describe_topology_error`/`describe_gate_error`'s `is_none()` lead read `"probe not attached for role …"` unconditionally — false for the five new causes, whose `reason` says the probe "is attached but could not be opened". Now `"probe unavailable for role …"`, neutral either way; `kind`'s wire value is untouched.
