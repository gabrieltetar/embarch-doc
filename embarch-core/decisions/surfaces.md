# embarch-core decisions: Error and version surfaces

**Status:** active, 2026-09-17.

The error body and contract version that were designed and not built, whether `/status` needs a content identity on top of its version, and how a hardware-identity error tells its own two shapes apart.

Index: [../decisions.md](../decisions.md). Current truth: [../spec.md](../spec.md). The human enrollment surface split out to [enrollment.md](enrollment.md) 2026-09-11 (below), a real topical seam under `DOC-COMPACTION.md` §3 rather than a squeeze.

### 13 — `core_version` on `/status`; no hand-bumped `contract_version` (built 2026-09-03)
The only cross-boundary version check was the study schema, so nothing talking to Core **over HTTP** could say which build answered — the version was reachable only by running the binary, and a deploy that silently did not land is indistinguishable from one that did (`embarch-dev-workflow.md` §4a: `deploy-core` reports `landed` either way, and its own length check cannot discriminate a rebuild of one constant). `/status` now serves `core_version` from `env!("CARGO_PKG_VERSION")`. **Mechanical, not maintained**: `Cargo.toml`'s version already tracks the release tags, so the field cannot drift from the build serving it. Consumers **warn, not refuse**, on a difference from the version they were built against — this decision's original posture on skew, unchanged.

**The `contract_version` half is retired rather than built.** It was to be hand-bumped only for a wire-visible change, and nothing forces the bump: the failure mode is a number reading "same" across contracts that differ, which is worse than no number, and this entry's own history is the evidence — the endpoint table described all three designed fields as shipped **for months when none were**. `core_version` covers the case mechanically and **over**-warns rather than under-warns, the safe direction for a warn-not-refuse consumer. Revisit if a `core_version` skew warning is ever silenced as too noisy to act on; that is the first real evidence a finer-grained number would earn its keep.

The served field set is pinned by a test on `StatusResponse`'s serialized keys (`api.rs`), so **adding** a field without editing [../interfaces.md](../interfaces.md)'s `/status` row fails the suite. That test, not a note, is what answers the "described as shipped when it wasn't" shape here.

### 67 — No content hash on `/status` today; a self-hash is the right question, filed rather than built (2026-09-17)
`embarch-umbrella` doctor check 15 compares served `core_version` against expected and is blind to a same-version rebuild whose deploy silently did not land — decision 13's `core_version` cannot distinguish two builds sharing one `Cargo.toml` version. `embarch-umbrella/open.md`'s standing bullet named this repo as the one to decide whether `/status` should carry a content identity to close it.

**A git SHA baked in at compile time proves *what source was compiled*, not what bytes are running** — blind to a dirty working tree (this suite rebuilds on-bench, uncommitted, routinely) and to a non-reproducible build, where two builds of one commit differ in bytes under one SHA. A build timestamp shares that blind spot and adds its own: it says nothing about content. **Only a self-hash of the running executable** — `std::env::current_exe()`, hashed once — answers the literal question a "did the deploy land" check needs.

**Decided: yes — filed as a separate task, a wire-schema bump not landed here (`tasks/core/088`).** This closes the same gap for content that decision 13 closed for version: today the check is done by hand, hashing the file on both ends after a deploy, filesystem access required; a served field makes it reachable over HTTP instead. **Cost:** hash once at process start into a cached static, not per request — the running process's own bytes cannot change under it mid-run, so re-hashing per `/status` call buys nothing and costs a full-binary read every time. Adds a new hashing dependency; none of this crate's current ones hash. Field name, shape, and whether the hash is truncated are the implementation task's to decide.

**Trigger to reverse to "no":** none identified — decision 13 was built, not deferred, on this identical reasoning for version.

### 12 — A `{code, message, cause}` JSON error body — deferred, and it is not Core's alone
Plain-text errors suit a human reading a CLI error, but `doctor --json` and a UI need to branch on error *kind*; a `{code, message, cause}` body would also retire the "finer CLI exit codes" idea, since a script branching on failure kind wants a field, not an exit code. Still worth building, and **deliberately not built here.**

Its value is **entirely** in consumers branching on `code`, which makes the `code` enum a wire contract shared with `embarch-api`, `embarch-ui` and `embarch-umbrella`'s `doctor` — so this is a cross-repo sequenced change (`embarch-fleet/protocol.md` §8), not a Core-local one. Core-side alone it is ~40 error-construction sites re-shaped, every one needing a stable `code` invented for it, while every consumer still reads plain text: the whole cost and none of the benefit. **Trigger:** the first consumer that must distinguish two error kinds sharing one HTTP status and cannot. (Decision 59 below is that trigger firing for one route alone: a `kind` field scoped to `POST /validate`'s own JSON body, not the general enum this entry defers.)

### 55 — `study_schema_mismatch` retired as a name; no `code` enum exists to hold it (2026-09-10)
`open.md` read this as a stray member missing from an otherwise-real `code` enum. Reading the code settled it: `embarch-core` has no `code` enum at all (decision 12 defers building it) — `study_schema_mismatch` was never a member of anything, just a name proposed in this decision's prose for a future enum and left unreconciled. Retired: nothing to make reachable without building decision 12's body, and no seat is owed to it by prior mention if that enum is ever built — decision 12's own trigger earns any member its place.

### 59 — `POST /validate`'s `TopologyMismatch` gets a `kind` field; "not attached" is not "mismatch" (2026-09-11)
`live_hardware_id: None` (probe unreachable — unplugged, ordinarily) and `Some(x)` disagreeing with the recorded ID were both rendered under one `topology mismatch` lead, JSON and plain text alike — opposite conditions (`embarch-topology` decision 20: a disagreeing ID means the wrong board is on the desk and a human must reconcile it; an absent readback means only that nobody has plugged in yet, the most ordinary bench state). `.claude/leg.md`'s operating rule handles the two oppositely — one leaves a task `open`, the other alerts a human — so matching on the leading phrase routed the more common case (unplugged) into the one that costs someone sleep.

**Resolved by adding `kind: "not_attached" | "mismatch"`** to `ValidateMismatchResponse`, set from `live_hardware_id.is_none()` — a field, not prose, so a caller branches on it rather than on `reason`'s wording (decision 12's deferred `code` enum exists for exactly this reason; `NotEnrolled`'s downcastable shape, decision 28, is the same idiom one level up). `"not_attached"` answers `503`, keeping `409` for `"mismatch"` alone. **`fix_it_url` is `None` on the `"not_attached"` arm** — the fix for a detached probe is a USB cable, not the Topology tab, and one URL for both invited the confusion the lead already caused. `flash`/`reset` (`hardware.rs`) and `study.rs`'s dev-bench handshake gate ran the identical check and rendered both conditions through the same `{e:?}` chain — fixed the same way in plain text (`describe_topology_error`/`describe_gate_error`): a different leading clause, not a status code, since both callers already fold every gate failure into one status regardless of kind.

**Corrected 2026-09-17 (`core/074`) — the completeness claim below does not hold.** `TopologyMismatch` already carried `live_hardware_id`, so no change was needed there to add `kind` — but `embarch-topology`'s own doc comment on that field was itself wrong and has since been corrected (prose-only, `topology/056`): `None` means the probe was not found in `Lister::list_all()` at all. Every failure *after* that lookup succeeds — `.open()`, the target-power check, `attach`, core-select, or the hardware-ID read itself (`validate_known_timed`) — returns a bare, non-downcastable `anyhow::Error`, with no alert logged, never a `TopologyMismatch`. All four call sites that run this check (`/validate`, `/flash`, `/reset`, and `study.rs`'s dev-bench gate) fall through to their own generic, undistinguished error path for this whole class of failure: a `500` on the first three, folded into the existing `502` on the fourth. Whether any of this deserves its own `kind` arm is left open, not decided here; today it is an accepted, undocumented-until-now gap.

**Settled 2026-09-17 (`core/077`) — the gap above is now live, and stays collapsed into `"not_attached"` as a considered choice.** `embarch-topology` decision 34 (`topology/058`) routed all five failures through `raise()`, each with `live_hardware_id: None`, so they now downcast to `TopologyMismatch` and land on `classify_topology_mismatch`'s `is_none()` arm: `kind: "not_attached"`, `503`, no `fix_it_url` — same as a genuinely unplugged board. **No third `kind` was added.** Downstream handling is identical for both causes: `.claude/leg.md`'s binary split leaves a not-attached role's task `open`, and alerts only for a live ID that actually disagrees — none of the five new causes is an identity question, so all five belong on the `open` side. Against that, a third value is a wire change reaching `ValidateMismatchResponse`, `embarch-api`'s `TopologyMismatchError` classification and its `tools.rs`/`cli.rs` text, any `embarch-ui` rendering, and the user guide — for a distinction `reason` already carries in full. No consumer today reads `kind` needing that distinction — decision 12's own trigger has not fired.

**One real gap this did surface, filed rather than fixed here:** `embarch-api`'s `validate` tool appends a fixed `"— plug it in; this is not a topology mismatch"` suffix to every `"not_attached"` case, written when absence was the only reachable cause — wrong five times out of six now, fixable with no new `kind`. Dropped to `embarch-doc/inbox/` as `embarch-api`'s own task.

**This crate's plain-text paths got one no-wire-change fix in this unit:** `describe_topology_error`/`describe_gate_error`'s `is_none()` lead read `"probe not attached for role …"` unconditionally — false for the five new causes, whose own `reason` says the probe "is attached but could not be opened". Now `"probe unavailable for role …"`, neutral either way; `kind`'s wire value is untouched.
