# embarch-core decisions: Error and human surfaces

**Status:** active, 2026-09-02.

The error body and contract version that were designed and not built, and the endpoints a human or a UI reaches enrollment and topology through.

Index: [../decisions.md](../decisions.md). Current truth: [../spec.md](../spec.md).


## Errors and version handshakes

### 13 — `core_version` on `/status`; no hand-bumped `contract_version` (built 2026-09-03)
The only cross-boundary version check was the study schema, so nothing talking to Core **over HTTP** could say which build answered — the version was reachable only by running the binary, and a deploy that silently did not land is indistinguishable from one that did (`embarch-dev-workflow.md` §4a: `deploy-core` reports `landed` either way, and its own length check cannot discriminate a rebuild of one constant). `/status` now serves `core_version` from `env!("CARGO_PKG_VERSION")`. **Mechanical, not maintained**: `Cargo.toml`'s version already tracks the release tags, so the field cannot drift from the build serving it. Consumers **warn, not refuse**, on a difference from the version they were built against — this decision's original posture on skew, unchanged.

**The `contract_version` half is retired rather than built.** It was to be hand-bumped only for a wire-visible change, and nothing forces the bump: the failure mode is a number reading "same" across contracts that differ, which is worse than no number, and this entry's own history is the evidence — the endpoint table described all three designed fields as shipped **for months when none were**. `core_version` covers the case mechanically and **over**-warns rather than under-warns, the safe direction for a warn-not-refuse consumer. Revisit if a `core_version` skew warning is ever silenced as too noisy to act on; that is the first real evidence a finer-grained number would earn its keep.

The served field set is pinned by a test on `StatusResponse`'s serialized keys (`api.rs`), so **adding** a field without editing [../interfaces.md](../interfaces.md)'s `/status` row fails the suite. That test, not a note, is what answers the "described as shipped when it wasn't" shape here.

### 12 — A `{code, message, cause}` JSON error body — deferred, and it is not Core's alone
Plain-text errors suit a human reading a CLI error, but `doctor --json` and a UI need to branch on error *kind*; a `{code, message, cause}` body would also retire the "finer CLI exit codes" idea, since a script branching on failure kind wants a field, not an exit code. Still worth building, and **deliberately not built here.**

Its value is **entirely** in consumers branching on `code`, which makes the `code` enum a wire contract shared with `embarch-api`, `embarch-ui` and `embarch-umbrella`'s `doctor` — so this is a cross-repo sequenced change (`embarch-fleet/protocol.md` §8), not a Core-local one. Core-side alone it is ~40 error-construction sites re-shaped, every one needing a stable `code` invented for it, while every consumer still reads plain text: the whole cost and none of the benefit. **Trigger:** the first consumer that must distinguish two error kinds sharing one HTTP status and cannot.

### 55 — `study_schema_mismatch` retired as a name; no `code` enum exists to hold it (2026-09-10)
`open.md` carried it as "reachable by nothing: it names a member of the error `code` enum that does not exist" — read as a stray member missing from an otherwise-real enum. The code was read to settle it: `embarch-core` has no `code` enum at all, real or reachable — decision 12 above is exactly the record of that shape being designed and deliberately not built. `study_schema_mismatch` was never a member of anything; it was a name proposed in this decision's prose for a future enum, then left there with nothing to reconcile it against. There is no member to make reachable without building the `{code, message, cause}` body decision 12 defers — out of scope here and cross-repo besides. The name is retired: this entry replaces the mention decision 12 used to carry, and `../open.md`'s bullet is gone rather than left dangling. If the deferred `code` enum is ever built, `study_schema_mismatch` is not owed a seat in it by prior mention — the trigger in decision 12 is what earns any member its place.

## The human enrollment surface

### 25 — `GET /enroll`, a static page served by Core (retired 2026-08-24, see `embarch-ui` decision 1)
Two lessons outlived it. **Real hardware I/O and the system-file write it produces belong in Core**, which already does that under `hw_lock` — a second process calling the same function does not share that lock. And a page a browser navigates to **cannot attach a bearer token**, so it had to ask a human to paste one; `embarch-ui` holds a server-side client instead, which is why it could replace this outright. No unauthenticated route is left.

### 27 — `POST /dev-bench/link`, declaring the runtime link as its own fact
Port detection came back genuinely ambiguous between dev-bench's bridge and the DUT's own J-Link VCOM, because the only signal it had — the enrolled bench probe's *JTAG* serial — can never match a bridge that is a different physical USB device. The endpoint reaches the crate-side setter against the live Core because the standalone CLI equivalent hit exactly the NTFS permission wall this pattern predicts.

**Then `interface` was added and `serial` became optional.** A serial was named as *the* declared fact because the ambiguity it was written for was between two USB devices, which serials distinguish perfectly. The nRF54L15DK is where a serial cannot help at all: its link is on the DK's onboard J-Link — the same device as its JTAG probe — exposing **two** VCOMs under one serial, so both serials narrow to a *pair* and stop. Detection resolved such a pair by silently taking the lowest, and on this DK the console is the higher one: the guess was wrong and the bench answered nothing while the endpoint reported a confident result. **Neither field is a `400`** rather than a silent no-op — an input that cannot be honoured must fail, not be ignored.

### 28 — `POST /validate` and `GET /alerts`, reachable without touching hardware
Every live-identity re-check only ran as a side effect of `flash`/`reset`/the handshake touching hardware, so there was no way to ask "is the board enrolled as this role still the one attached" on its own. Three outcomes, each a distinct named shape rather than one generic error — which needed a typed `NotEnrolled` in the topology crate, since that branch previously raised a non-downcastable error: enough for a CLI's generic fallback, not enough to tell "not configured yet" from "a real I/O error".

### 50 — `POST /validate`'s body adds `validated_at_utc_ms`, additive, alongside the unchanged `confirmed_at_utc_ms` (2026-09-07)
Two `/validate` calls minutes or days apart both returned the same `confirmed_at_utc_ms` — enrolment time, unmoving since the record was made — so a caller reading it as freshness got a plausible, wrong answer, silently, in the safe-looking direction (`embarch-topology/tasks/topology/009`). `embarch-topology` decision 26 added `validate_serial_timed`/`validate_role_timed`, returning `Validation { board, validated_at_utc_ms }` alongside the unchanged `validate_serial`/`validate_role` — this crate is linked in-process, not called over the wire, so the old signatures stay callable for every other call site (`hardware::flash`/`reset`, the dev-bench handshake) rather than forcing a same-instant break. `POST /validate`'s handler is the only place that assembles this endpoint's wire body, so it is the one place that has to switch to the `_timed` variant and add the new field before it means anything to any consumer.

**Additive, not a wire-schema bump.** `ok`, `role`, `hardware_id` and `confirmed_at_utc_ms` keep their names, types and meanings; `validated_at_utc_ms` is a new field alongside them. Checked, not assumed: no `deny_unknown_fields` guards this response anywhere in the four repos that mirror its shape by hand (`embarch-api`'s `embarch-core-client::ValidateResponse` derives plain `Deserialize`), and `interfaces/topology.md` already documents `/validate`'s body as open-ended rather than closed. `confirmed_at_utc_ms` is untouched — still enrolment time, still wire-visible across those four repos, deliberately left alone. Three consumers were filed against this task: `tasks/api/045` landed (`a687baf`); `tasks/umbrella/041` and `tasks/ui/020` both closed unsatisfiable (`e0dc52b`) — each mirror keeps deserializing regardless of when, or whether, it picks the new field up. See decision 57, below, for what replaced the latter two's intent.

### 57 — `EnrolledBoardResponse` does not grow a persisted validation timestamp; the existing field gets an honest label instead (`tasks/core/027`)
Decision 50 put `validated_at_utc_ms` on `POST /validate` alone, because that is the one place `Validation` exists to draw it from. `tasks/umbrella/041` and `tasks/ui/020` — the two consumers decision 50 filed to actually *show* it — both closed unsatisfiable: `doctor` calls no hardware-touching route by design, and the Topology tab renders `EnrolledBoardResponse`, which `POST /validate` never returns. Neither surface can reach the field decision 50 shipped, so the defect `embarch-topology` decision 26 named — enrolment time misread as freshness — is still live on both surfaces a human actually reads.

**Not fixed by persisting a second timestamp.** `EnrolledBoard` — the struct `confirmed_at_utc_ms` lives on — is `embarch-topology`'s storage, not this crate's; giving `EnrolledBoardResponse` a real last-validation instant means `embarch-topology`'s enrollment file gains a field, `POST /validate`'s handler writes it back on every successful check, and every board enrolled before that write existed comes back with no honest value for it. That last part is not a detail: a bare `Option<u64>` reading `None` as "never validated" would be a lie about every board on the bench today, each of which has passed `/validate` calls this suite simply never recorded. A `None` that instead means "not yet recorded, ask `/validate`" is defensible, but it is a new durable fact, a migration, and a storage-format decision that belongs to `embarch-topology`, not to a `core`-scoped change — exactly the reasoning decision 26 already gave for not renaming `confirmed_at_utc_ms` itself.

**The label is the whole fix.** `confirmed_at_utc_ms` already means exactly one thing — the instant `embarch-topology::hardware::enroll` last wrote this record — and every passive reader's job is to say that, not to imply a live check backs it. Both readers can use the same words: render it as **"Enrolled"** (or "Enrolled at"), never "Last validated" or "Validated" — and if a reader wants to say something is stale, it has to call `POST /validate` and show `validated_at_utc_ms` from that response, not treat `confirmed_at_utc_ms` as a proxy for it. Filed to the queue rather than assumed: `tasks/umbrella/<NNN>` (label the enrollment timestamp `doctor` already has no display for, if one is ever added) and `tasks/ui/<NNN>` (relabel the Topology tab's existing `confirmed_at_utc_ms` cell, if it renders one, away from any freshness wording) — both dropped to `embarch-doc/inbox/` rather than filed here, since `tasks/umbrella/` and `tasks/ui/` are not this scope's to write.

*Rejected:* persisting and serving a second timestamp on `EnrolledBoardResponse` — the arm `tasks/core/027` posed as the alternative — declined because its store change lives in a repo this task cannot write, and half-landing the response side without the storage side underneath it would ship a field with no correct value to put in it, the suite's worst-named failure mode by decision 26's own account.
