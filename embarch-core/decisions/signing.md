# embarch-core decisions: Signing a study run's record

**Status:** active, 2026-11-21 (`tasks/core/129`, the plan's unit M1.5, `notes/hil/14`).

Index: [../decisions.md](../decisions.md). Current truth: [../spec.md](../spec.md). Surface: [../interfaces/signing.md](../interfaces/signing.md). Siblings: [auth.md](auth.md) (decision 109, whose `Scope` the predicate carries), [study-record.md](study-record.md) (the run's files).

### 110 — Core signs each study run's record with an Ed25519 key: a DSSE envelope over an in-toto Statement, and a challenge that signs only a fixed frame

A published zip must be checkable without trusting the agent that carried it (`notes/hil/12-prevention.md`, item 1). **The key** is generated at first start under the engineer's account (milestone 1 is an unattested Core) and kept beside the token files as `signing-key`: the 32-byte seed as 64 hex characters, `0600` from creation on Linux, the same `icacls` lockdown as the tokens on Windows (decision 53, **unrun on Windows for this file**). A file that is not 64 hex characters stops Core starting, as a bad token would. Its fingerprint, the DSSE `keyid`, is SHA-256 of the raw public key.

**The library is `ed25519-dalek` 2** (the notes' unverified suggestion, now checked: it builds here and its signatures pass an independent DSSE check written in the tests from the DSSE v1 text alone), built `default-features = false, features = ["std", "zeroize"]`, with the seed drawn by `rand` already in the tree, so dalek's own `rand_core` 0.6 stays out. **Cost:** it brings `sha2` 0.10 beside this crate's 0.11 and `base64` 0.22 beside a 0.23 already resolved, both small and both accepted. DSSE itself is written in-house (`signing.rs`, about 15 lines of pre-authentication encoding), as the notes expected.

**The envelope** is standard DSSE: `payloadType` `application/vnd.in-toto+json`, `payload` the Statement in standard base64, `signatures[{keyid, sig}]` with `sig` base64 of the Ed25519 signature over `DSSEv1 <len type> <type> <len payload> <payload>`. It is written as `record.dsse.json` in the study's results directory **before the job reads `completed`**, and a run whose record cannot be written is `failed`, never completed unsigned. Device studies (`POST /study`) and host studies (`POST /host-studies`) are both sealed; a run that ends in a connection failure or a panic has no complete record and is not.

**The Statement** is in-toto v1. Its **subjects are the SHA-256 of every file the run has when it ends**, by path relative to the directory: `events.json`, `measurements.json` and `study.json` when present, and every regular file under `streams/` (the raw captures and their renderings, sorted). The list comes from the files present, so M1.7's `measurements.json` becomes a subject with no change to this code (a test supplies one). **`study.json` is the submitted study as Core received it**: host studies already kept it, and a device study now keeps its `Study` under the same name (`GET /study/{id}/line-counts` answers `404` for a device study's file rather than a parse error). The serialisation is canonical (RFC 8785) by construction: `serde_json`'s map is ordered by key, and the predicate holds only strings, booleans and integers.

**The predicate type is the URN `urn:embarch:predicate:study-run:v1`** (a name for a shape, not a page; this unit's choice). **Its `observed` and `claimed` halves are kept apart, and nothing moves between them.**
- `observed`: Core's version; the run's `provenance` as Core wrote it into `events.json` (null for a host study); `image_status: "unverified"` (every board is, in milestone 1, `notes/hil/14`); the **declarations ledger**; and `behaviours`, copied from `measurements.json` when it exists (empty until M1.7), where the shared crate's reducer versions will be.
- `claimed`: `build` `{commit, dirty, toolchain}`, **told by embarch-api** as the query parameters `build_commit`, `build_dirty`, `build_toolchain` on both study routes, validated for shape (`400` otherwise) and never checked, since Core cannot read the firmware repo; `null` when the caller sent none.

**The declarations ledger** records, in memory, the scope of the token behind each declaration Core saw since it started: `role` (`POST /probes/enroll`, `PUT /probes/enrolled/{role}/board`), `signal`, `instrument`, `bootload_ports` and `dev_bench_link`, dropped when the route that retracts one runs. **The predicate carries `witnessed_since_utc_ms` beside the entries**, so a declaration made before this Core started, or one the ledger does not watch, is visibly outside what it vouches for rather than silently "agent". It is not persisted: M1.6's protected store is where it should live ([open.md](../open.md)).

**The challenge signs a frame, never bytes.** `POST /auth/challenge` takes `{"nonce": <32 to 128 lowercase hex characters, an even count>}` and signs `embarch-core-auth-v1`, a newline, Core's own 32-byte nonce in hex, a newline, the caller's nonce. Both nonces are validated hex, so no caller input can add a line or change the tag, and the tag cannot begin a DSSE pre-authentication string (`DSSEv1 …`), so a signature over a frame is no signature over a record. Nothing else signs: no route takes a payload to sign. **The route takes no token**, the one exception to "every route requires the bearer token", because its purpose is a client checking which Core answers before it sends one (`notes/hil/12-prevention.md`); it sits in `signing.rs`, outside `build_router`'s swept `.route(` lines, and a test drives it with none. It returns the frame, Core's nonce, the `keyid`, the public key and the signature; the answer is Core's own word, and a client trusts it only by matching `keyid` to a fingerprint it got elsewhere (the fingerprint file is a later unit). It is not rate limited: a signature over a frame costs microseconds and signs nothing a caller chose.

**Measured:** the unit tests: an independent DSSE verification passes, fails when the payload or a signature byte changes, and fails under another key; a changed capture no longer matches its subject's hash; `measurements.json` joins the subjects; build claims stay out of `observed`; a host run is sealed before `completed`; the key is made once, reused, `0600`, and a malformed file is refused; the challenge signs exactly its frame, fresh Core nonce each time, no token, and every caller-shaped payload (DSSE text, embedded newlines, wrong length, uppercase) is `400`. **Assumed:** the Windows ACL on `signing-key`; that a third-party DSSE verifier other than the tests' own accepts the envelope (the encoding follows the DSSE v1 text, no other implementation was run); that `sha256` hex digests in `subject[].digest` are what such a verifier expects (in-toto's field name for it).

**Out of scope, stated:** the hash-chained run log that holds each Statement's hash (M1.6), `measurements.json` itself (M1.7), signing the publish manifest (M1.8), an attested install, the fingerprint file, and making any route refuse by scope.
