### 133 — Core keeps HIL definitions by hash, reads premade suites from a checkout, and records a person's confirmation in the run log

Core read no firmware repo and kept no test definition, and nothing recorded that a person had confirmed one. **A definition** (a test, suite manifest, plan, bench, capability or hook mapping) is posted to `POST /definitions` by either token, checked by `embarch-study-designer`'s `hil-test` checks (`TestDef::check`, `SuiteManifest::check`, `Plan::check`, and `hil_check::check_test` when the request carries the study and the bench the test names) so Core and embarch-api refuse the same definition for the same reason, and kept as `definitions/<sha256>.json` in the store, the hash being the crate's `definition_hash`. Posted twice, kept once. An invalid one is `422` with the crate's reason.

**Premade suites** are read, on every call, from the checkout `EMBARCH_SUITES_DIR` names: every `suite.json` up to three folders down, indexed by suite id and version with the manifest's hash, each test counted only when its file hashes to the manifest's line. **A test identical to one of those is `premade` and needs no confirmation; one byte changed is another hash and reads `unconfirmed`.** Read per call so a contributor's edit is seen at once; a release install's own store (a suite copy installed with Core) is a later unit, and with no variable nothing is premade. The layout under the checkout is **assumed**, not measured, until the suites repo exists.

**A confirmation** binds the hash of exactly what was confirmed. `GET /confirmations/pending` (either token) lists the kept definitions that are neither premade, held nor confirmed. `GET /confirmations/{hash}/card` returns the card's data, and for a definition still waiting a nonce: 32 random bytes, for that hash, single use, ten minutes (chosen, the go nonce's figure), held in memory so a restart voids them. `POST /confirmations {hash, nonce, surface?}` spends the nonce, whatever the outcome, and appends a `confirmed` entry to the run log with the kind, the hash, the token's scope and the surface the caller names (a label; the scope is the token's, never a field the caller writes). **A suite version Core does not hold** is confirmed once, as a unit, by its manifest hash; the entry says `core_holds: false`, and a test its manifest lists then reads `confirmed_with_suite`.

**The card and the confirmation are the person's on every Core, a development one included**, which is stricter than decision 132: `PERSON_ROUTES` is service-only, a development Core serving the person's table to either token. A confirmation an agent could make is no confirmation (`notes/hil/12-prevention.md`, item 4), and a development Core's reports are unattested anyway, so the stricter rule costs nothing there but the CLI step. So a second table, `token_store::CONFIRMATION_ROUTES`, refused to the agent's token by the same `person_middleware` whatever `person_only` says, and the route-classing test counts it with `PERSON_ROUTES`. Defence in depth: both handlers check the scope again, as the discard does (decision 112). The nonce is a guard against a page the agent controls, not against an agent that holds the person's token, which decision 132 already names as unfixed.

**The owner may strike three choices.** Plan choice 7: confirmations are run-log entries, so the chain proves their order against runs and publishes; the alternative is a chain of their own. Plan choice 8: the route names. Plan choice 11: the suites checkout is an environment variable; a Core config key is the alternative.

**Not here:** the prepare route and the go (EMB-364), which will spend the same nonce kind for a card of its own; the report's wording that a suite was not Core's; the passkey form of the touch; the elevated install's signed suite store. **Measured:** unit tests post a definition twice and find one file, refuse an invalid one with the crate's reason, refuse the agent's token on the card and the post on a development and a service Core, enter the person's confirmation once and refuse the same nonce again, read an edited definition as unconfirmed, and read a premade test as needing none and a one-byte change as needing one. **Assumed:** the checkout layout, and that ten minutes suffices. **Not run:** a native Windows build.
