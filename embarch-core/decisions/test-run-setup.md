### 139 — Before each bench after the first the executor raises a `setup` prompt, and while it waits Core admits the setup calls

**The prompt.** `drive` calls `Env::setup` before every bench but the first (not after a cancel, not once the run has ended). `CoreEnv` publishes it in the one prompt slot, **under the run's id as `study_id`** so `POST /study/{run_id}/prompt` answers it and `GET /test-runs/{id}` shows it as `waiting_prompt`. Its `kind` is `setup`, its step `setup:<bench>`, its `bench_config` the bench's configuration from `run.json`, and its text names the bench and a `missing` list. **The list is empty**: the smoke check runs after the prompt, on what the person set up ([143](smoke-check.md)), so the text says nothing is checked yet.

**The window.** `AppState::setup_window` holds the run's id from the prompt's publish to its end, whichever way it ends. While it matches the run in flight, `lease_middleware` admits `SETUP_ADMITTED`, besides `RUN_ADMITTED` (135, 137): enrolment (`POST /probes/enroll`, the enrolled and by-serial deletes, the board assignment), `POST` and `DELETE` of signals, `PUT` and `DELETE` of instruments and of bootload ports, and `POST /dev-bench/link`. Either token is admitted whole, as `RUN_ADMITTED` is, since the run holds the lease — on a development Core: on a `--service` Core the person-only routes of [132](auth.md) still refuse the agent's token `403`, because that layer runs before this one; **every call is entered in the run log as `test_run_setup_call` with the token's scope**, so the agent's is labelled the agent's. Every other gated call is `409` as before, and every call is `409` outside the window.

**How it ends.** The window closes when the prompt is answered, times out (`SETUP_WAIT_MS`, 15 min, **chosen, not measured**; each bench after the first adds it to the run's deadline) or the run is cancelled, which ends the run. A `declined` or timed-out prompt is an `error` on its bench (`bench_step_failed`, the rest `stopped_by_error`) and the run goes on to the next. `test_run_setup_ended` enters the answer and `relayed`.

**Who answers.** Either token. A setup claim is the one kind the agent may relay (138): its answer is accepted and recorded with `scope: agent` and `relayed: true`, never refused.

**Measured:** unit tests over a fake bench (a prompt before the second bench naming it and its configuration, none before the first, a decline and a timeout each an `error` on that bench, a cancel ending the run, the deadline's allowance); the real prompt answered with the agent's token and recorded relayed; the middleware admitting a setup call with either token only while the window is open and `409` outside it, `POST /flash` and `/reset` refused throughout. **Not run:** a real two-bench run on a bench (**debt**: enrol a board between two benches of a fixture run, in the person's session), and a native Windows build.
