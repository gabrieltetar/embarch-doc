## Platform and process

### 1, 2, 7, 17 — Rust, probe-rs as a library, Axum, `spawn_blocking`, and CI everywhere
probe-rs is called as a library, not shelled out to: no subprocess or output-scraping, and typed errors. Axum for one toolchain across the stack and because its `State`/middleware model fits `AppState`. Both probe-rs and `serialport` are synchronous, so every hardware call goes through `spawn_blocking` — a slow flash must never stall the runtime. The intent was that CI run `build`/`clippy -D warnings`/`test` per push on every repo that lacked it, plus a `native_sim` build for dev-bench, which would have caught a real Zephyr API breakage before it was found by hand.

**Release (2026-11-17):** `release.yml`'s four-target build now hands its archives to one `sign-and-publish` job that signs each with cosign and uploads asset and bundle; see [spec.md](../spec.md) §3 "Release assets". Still no per-push test workflow. **Corrected 2026-09-08 — "CI everywhere" was never built, and this repo is one of the repos it was not built in.** Measured across all nine repos: `embarch-core` has `release.yml` and **no test workflow at all**, so nothing runs `build`/`clippy`/`test` on a push here. The only per-push Rust test workflows in the suite are `embarch-study-designer`'s and `embarch-topology`'s; `embarch-doc` has `docs-ci.yml`. The `native_sim` job is `embarch-dev-bench`'s own decision 9 and is also unbuilt — that repo has never had a `.github` directory. **The heading keeps "CI everywhere" because the decision *numbers* are permanent ([DOC-CONVENTIONS.md](../../DOC-CONVENTIONS.md)) and this title is how they are cited elsewhere — nothing has ever decided whether a title may be amended, so this is a choice rather than a rule, and it is recorded as one. What the heading names is what was decided; the clause above is not what exists.** What actually checks a change in this repo is [embarch.md](../../embarch.md) §5's table: the fleet's own merge gate ([the protocol](../../../embarch-fleet/protocol.md) §10), run per branch by a supervisor, and nothing else.

### 3 — `service-manager` for install; self-elevation here rather than in every caller
One code path registers `run` as a systemd unit, launchd job, or Windows Service. **Registration is not the whole job:** systemd and launchd accept "the process stayed alive", but Windows kills a start that has not called `StartServiceCtrlDispatcherW` and reported `SERVICE_RUNNING` within 30 s, however healthy the process — so `run` attempts the real SCM handshake first on Windows and falls back to foreground only when SCM did not launch it. All four subcommands **self-elevate**, because a human running `embarch-core install` and `embarch-umbrella` shelling out to it hit the same wall; fixing it here fixes both callers. Re-launching the *same already-running binary* adds no new trust step. Hence also `update <new-exe>`: stop, rename aside (Windows will not overwrite a running image), copy, start, roll back on failure.

*Rejected:* printing the command for a human to re-run elevated — a transcription-error opportunity, and it left updating an installed Core with no supported path at all.

### 106 — `install` over a registered Windows service rewrites it in place; a reinstall keeps `Environment`; the restart policy is applied with `sc failure`
Measured 2026-10-29 on the live `com.embarch.core` (`umbrella/033`): `install` over a registration died on `[SC] CreateService FAILED 1073` and changed nothing; an `uninstall` + `install` dropped `EMBARCH_SIGNAL_BAUD`, written by hand under the service's `Environment` value, and `sc qfailure` showed no restart actions, because `service_manager`'s `sc` backend ignores `restart_policy`. **Decided:** on Windows, when the service's registry key exists, `install` stops it, rewrites `ImagePath` (quoted exe, `run --bind <bind>`), merges `Environment`, applies failure actions and starts it. Chosen over refusing because a refusal naming `uninstall` first is the route that destroyed the environment. The merge keeps every existing entry and replaces only `EMBARCH_TOKEN`, and only when one is set; the kept names (never values) are printed. Fresh installs and rewrites both run `sc failure reset= 3600 actions=` five `restart/5000` steps, the policy the code always claimed. An explicit `uninstall` still discards everything. Since [decision 157](platform.md) the rewrite is under `install --service` only. Linux and macOS are unchanged; their backends honour the policy. **Unverified on Windows:** [open.md](../open.md). Since 157 only `install --service --bind` rewrites; `doctor` check 17's fix lines (`tasks/umbrella/095`) still name `install --bind`.

*Rejected:* refusing with a message; `sc config binPath=` (quoting through `sc.exe` is the crate's `shell_escape` problem, and the registry value is the same field).

### 157 — `install --service` registers only a binary a signed release listed, under Core's own account; a plain `install` registers nothing
**Decided 2026-11-26** (EMB-324), implementing `notes/hil/12-prevention.md` "The root of trust": only a signed release runs as the service account. Before, `install` registered `current_exe()` with `run --bind` and no account (the `sc` backend passes none, which Windows takes as its default service account, unchecked here), and `update` replaced `current_exe()` in place. **Now:** `install --service --bind <addr>` first hashes its own binary and refuses, before any elevation or service-manager call, unless `<data dir>/installed-release.json` exists and lists that SHA-256 ([shape](../interfaces/installed-release.md)); it then registers `run --service --bind <addr>` under `NT SERVICE\com.embarch.core` on Windows (`sc config <service> obj=` after the create or the in-place rewrite of decision 106) or `User=embarch` on Linux and macOS (`ServiceInstallCtx.username`). Decision 106's rewrite in place applies to this path only. `install` without `--service` registers nothing and names `embarch deploy-core`. `update` refuses a registration whose `ImagePath`, unit or plist runs `--service`: a signed release replaces it through the elevated install. `start`, `stop`, `uninstall` are unchanged. **Who writes the record:** the elevated install of a signed release (EMB-339 Windows, EMB-340 Linux, both later); nothing here writes it, so until then `install --service` always refuses. The `embarch` Linux user is created by EMB-340, not here. Tests assert on the built arguments and account, never a real registration; the Windows-gated half type-checks only on a machine with a Windows C toolchain. **Unverified on Windows and Linux:** [open.md](../open.md) carries no entry (it is at its line); the first elevated install is the check. **Callers:** `embarch-umbrella` still calls `install --bind`; it now registers nothing, and moving it is that sub-project's.

*Rejected:* a hash in the registration instead of a record (nothing could name a second release); trusting the file's presence alone.

### 100 — `--version` names the commit Core was built from
**Decided 2026-10-28**, suite task 047; the stamp and why are `embarch-umbrella` [decision 57](../../embarch-umbrella/decisions/build-identity.md). `embarch-core --version` prints `embarch-core <version> (commit <8 hex>[, dirty])`, still one line on stdout (`tests/version_stdout.rs` pins the commit). `/status`'s `core_version` stays `CARGO_PKG_VERSION` (decision 13): the commit is not added to the wire, because `binary_sha256` already identifies the bytes that answer. The service build on Windows is made from an rsync copy with no `.git`; `deploy-core` passes the Linux checkout's commit in, and a build made by hand there says `(commit unknown)`.
