### 153 — A finished test is checkpointed as it ends, so an interrupted run keeps its verdicts, and a resume is a new run of the rest

**The checkpoint.** After each test the executor writes `test-runs/<run_id>.checkpoint.json`: `{run_id, results, smoke_checks}`, every `TestResult` so far and every bench's smoke findings, replaced whole (written beside it, renamed over). The seam is `Env::checkpoint`, called by `drive` after each result; the real bench writes the file, a fake records the calls. A failed write is logged and the run goes on: a lost checkpoint costs the verdicts after the last good one, never the run.

**At the next start** `seal_interrupted` reads the checkpoint of each started run with no record, writes `result.json` (`status` `interrupted`, the kept results, the smoke checks), then seals as 144 does. A finished test keeps the verdict, reason, qualifiers and note it signed; the test in flight and every later one has a null verdict and `reason` `interrupted`. Because the smoke findings are kept, `unit_key` and each test's `dut_image` survive, and each finished test's study is amended with its test as at any end (145). The study the interrupted test left is not amended. A run with no checkpoint (killed before its first test ended, or sealed by an earlier Core) seals as before, every test `interrupted`. The run's `result.json` now exists, so `GET /test-runs/{id}` answers `interrupted` with the kept verdicts. A result this function wrote before dying is redone; one the executor wrote is its own end and is left.

**`POST /test-runs/{run_id}/resume {run_id}`** prepares a new run of what the interrupted run left, `201` as a prepare with `resumes`, `pending` and `kept`. **Chosen: cut the new run from the interrupted run's own record, not re-expanded.** Re-expanding needs the definitions and study files as they are today; a resume must run the tests the person already saw, and a definition edited since would otherwise change them under the same `resumes` link. So: `run.json` keeps its tests with no kept result, in order, and its benches with a pending test; `resumes` names the first run; a test that `requires` a test the first run passed no longer requires it (the pass is kept, in the first run's record), and one that requires a test that did not pass keeps the requirement and is `requires_not_met`. The card, inputs, studies and energising steps are the old ones cut to the pending tests, the selection is the first run's. The new run has its own hash, card, nonce and **go**; the go takes the session's lease as any go does, since a restart restored none. Its smoke check reads the images back again, because it is a run and `drive` smoke-checks each bench before its first test.

**Refused.** `404` no such run; `409` for a run never started, in flight, ended another way (`completed`, `cancelled`, `deadline`), already resumed (naming the run that did), with nothing pending, or a `run_id` already prepared; `400` a bad id. A resume is marked `<run_id>.resumed.json`, written once by hard link before the new record, so two resumes of one run cannot both succeed; a failed write of the record removes it.

**Not built.** Publishing a resumed pair as one zip (149 stays as written).

**Assumed:** a checkpoint written after each test is as fresh as the executor can make it, and a crash between a test's end and its write loses that one verdict. **Measured:** unit tests over the real `drive`, router, a key and a run log: every test checkpointed; an interrupted run signed with its finished verdicts and the rest `interrupted`; a resume with the pending tests only, `resumes` set, once only, needing its own go; its bench smoke-checked. **Not run:** a real Core restart under a run on a bench, and the native Windows build.
