# embarch-core decisions: Stopping a device study

**Status:** active, 2026-11-24.

How Core tells the dev bench to stop a study it is running: at a session's Done and cap, and on cancel. Builds on the analog capture of [analog-capture.md](analog-capture.md) decisions 126 and 127.

Index: [../decisions.md](../decisions.md). Current truth: [../spec.md](../spec.md).

## The stop

### 128 — Core sends `StudyStop` at Done, at the cap and on cancel, and ends the run on the bench's `StudyDone` or a bounded timeout; `POST /study/{id}/cancel` admits any device study

2026-11-24 (EMB-486; `embarch-study-designer` `StudyStop`, EMB-485, wire schema 17; amends 126 and 127). Decisions 126 and 127 stopped only Core's side: the bench kept sampling and a device study could not be cancelled. **Core now sends `DevBenchMessage::StudyStop { reason }`: `Done` when a session's Done is confirmed, `Cap` at its cap, `Cancel` on the cancel route.** It then keeps reading, so every open tap's `StreamClose` and the samples port's bytes still arrive, until the bench's `StudyDone` or `STOP_TIMEOUT` (5 s), and only then closes its own ports and seals. The bench is documented to send each open tap's `StreamClose`, then `StudyDone { completed: false }`, and to take up to about 2 s for it (teardown clears bonds); **5 s is that plus margin and is reasoned, not measured**, bounded because a bench that never answers must not hold the study lock. The run loop looks at the cancel flag first (it wins a tie with Done), then the Done prompt and the cap, every 20 ms for any device study, session or not.

**Which ended the run is recorded.** `session.json` keeps `ended_by` (`done`, `cap`, `cancelled`, `study_done`, `failed`) and a new `stop_closed_by`: `study_done` (the bench answered), `timeout`, or `send_failed`; it is absent when the bench's own `StudyDone` came first and nothing was sent. The log and the dev-bench debug file say the same, with the taps still open on a timeout. **A Done or cap that gets no answer is still `completed`**: the session asked for the early end and the capture is intact, so the record, not the job's status, says the bench never confirmed. **A cancel is `failed` with a reason** (`cancelled: ...`, saying whether the bench answered or did not within the bound), as any device run that did not finish: the existing statuses are kept, and a host study's cancel, which ends `completed` with a reason, is unchanged.

**A stop that races the study's own end is harmless.** A bench with no study running answers `StudyStop` with a log line only, so Core never waits on a bench that already finished: a `StudyDone` read before the stop is the run's end and no stop is sent; one that arrives after it is read as the answer, and `completed: true` there is a finished study whatever Core had asked (so a cancel that lost the race reads `completed`). **Not distinguished:** a bench failure whose `StudyDone { completed: false }` lands in the same instant as a stop reads as the stop's; the failed step's own `StepResult` is on record either way.

**The route.** `POST /study/{id}/cancel` sets the flag of the device study in flight (a second slot beside the host study's, so the host path is untouched) and answers `202 {status: "cancelling"}` at once; the run thread does the sending and waiting, and the job reads `failed` (or ends) when it is done. A session study cancelled while its Start prompt waits ends the wait (the prompt resolves `study_cancelled`), and nothing was sent to the bench. **Either token may cancel**, as either may answer Done: it only ends a run early, invents no label for a recording, and an agent that started a run has to be able to stop it. The host route was already open to both. `embarch-api` and the UI have no cancel call for any study today (`/study/{id}/cancel` is only on the lease gate's exempt list), so neither needed a change to reach a device study; a tool or button is a feature of its own.

**Not stopped by this:** a run that fails before the loop (the results directory, a stream store) or on its watchdog, which sends no `StudyStop`. **Measured:** unit tests over a scripted bench through the real run loop, no hardware: each of Done, cap and cancel sends its reason and ends on `StudyDone`, after the tap's `StreamClose`; a silent bench ends on the timeout; a stop racing the end, and no stop after the end; the route sets a device flag and leaves the host's alone; a cancel in the Start wait. **Owed to the bench:** a real stop, its real `StudyDone` time against the 5 s, and the samples port's last bytes arriving before it.
