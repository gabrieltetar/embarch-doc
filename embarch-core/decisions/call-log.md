Sibling: [run-log.md](run-log.md) (decision 111, whose chain this follows), [lease.md](lease.md) (decision 93, whose `LEASE_GATED` list this logs).

### 122 — Core logs every call to a gated route in a hash chain of its own, refusals included, and says it holds Core's calls only

The live log in a firmware repo, an atlas write-back's receipt and the signed record's `verify` check 8 cite what was done to the bench. The run log holds runs, not the calls inside and outside them, so a session could flash, read and reset with no trace a reader could check. **The log** is `call-log.jsonl` beside `run-log.jsonl`, the run log's line shape (`{entry, hash}`, `prev` all zeros first, `seq` the position), checked by the same `verify_lines`. No sweep, discard or restart touches it; a restart re-reads the head once and carries on.

**One entry per call to a route in `lease::LEASE_GATED`**, made by a layer outside `lease_middleware` and inside `auth_middleware`: a call the lease refuses is seen (`409`), and a gated route added later is logged with no handler change. Why a layer and not a call in each handler: a refusal never reaches a handler, and a handler written next year would otherwise be a gap nobody noticed. A host study's or dev-bench study's own steps stay in its `events.json`; the study's start is the one logged call.

**An entry holds** `at_utc_ms`, method, matched route, path parameters, the request body's SHA-256 and the body itself when it is JSON of at most 4096 bytes (chosen, not measured: every JSON body today is far under it; a firmware upload is its hash alone), the token's `Scope`, the lease holder and purpose or null, the status, the answer's SHA-256, and `board`: `{role, probe_serial, chip, image_sha256}` where a handler named one through `call_log::board_note()` (`/flash`, `/reset`, the two live reads today), `image_sha256` being `last_images`' hash for that chip or `"unknown"`.

**Reads fold.** `POST /live/mem-read`, `/live/core-state`, `/validate`, `GET /serial-log` and `/dev-bench/hello` are reads; the rest are actions and never fold. Consecutive identical reads (same route, parameters, request hash, scope, lease, status and answer hash) fold: the first is chained at once and its answer cites it, the repeats are counted in memory and written as one `fold` entry (`first_seq`, `count`, `first_utc_ms`, `last_utc_ms`) when a different gated call arrives, the lease is released, or Core stops cleanly. A chained entry is never rewritten. Why: a poll loop of a thousand identical reads would bury the calls that matter. A crash loses at most the pending count, never a chained entry; `GET /call-log` shows the pending count as `pending_fold`. A lease that expires with no release leaves its fold pending until the next different call.

**Each gated answer names its entry** in `X-Embarch-Call-Seq` and `X-Embarch-Call-Hash`; a folded repeat names the first entry and adds `X-Embarch-Call-Repeat`. `GET /call-log?from=&to=` returns the range (at most 1000) with `verified`, `head` and `length`; it is in `LEASE_OPEN`, touches no hardware, and is not itself logged.

**It is Core's calls, and only those.** Hardware reached without Core (the topology CLI's own hardware feature, a probe tool by hand) is not in it, and a reader must not read its absence as "nothing happened".

**Not here:** a quota (161). A log that cannot be written is decision 158. `board` is not yet named by `/bootload`, `/validate`, the exchange and capture routes (`open.md`).

**Measured:** unit tests call every `LEASE_GATED` route under a held lease and find one entry each with its scope; five identical `mem-read` calls chain one entry and fold four, and a different call between reads folds nothing; an edited, removed or reordered line names its line; a broken log is not extended. Nothing was run on a board.

### 156 — Core switches every declared output off at each start and each graceful stop, and the call log says so in a `start` and a `stop` entry

A Core stop or start used to leave every bench output as it was: `embarch-topology` (decision 49) lets an instrument declare `safe_off` lines and a signal one `safe_off` line, but nothing sent them, and foreground `run` ran `serve(..., pending())`, so SIGTERM and Ctrl-C ran nothing, not even the fold flush. The design is `notes/hil/12-prevention.md`, "The root of trust".

**The start order is the contract:** bind the port; read the tokens and logs; send the safe-off; write the `start` entry; serve. A bind that fails names the address and says another Core may hold it, and nothing has been sent, which is why the bind is first: a second Core must not switch off the outputs a running one is using. **A graceful stop** (SCM Stop, SIGTERM and Ctrl-C through tokio's signal handling, all ending `serve`) drains the last request, cancels the host study, Test run or device study in flight and waits for it to release `study_lock` and `run_lock` (its teardown has run), takes `hw_lock`, sends the safe-off, then writes the pending fold and the `stop` entry. The waits are 60 s for the study and 10 s for `hw_lock`, **chosen, not measured**; when one runs out the safe-off runs regardless and the `stop` entry says so (`study_ended`, `hw_lock_held`), because an output left on is worse than a teardown cut short.

**The safe-off sends declared lines only** (`safe_off.rs`): an instrument's through `instrument::run` with its own terminators, pacing and acknowledgement, a signal's through the function an `Exchange` step uses with a newline added. Core builds no command. A declaration with none, a port not enumerated, a signal Core does not write and a failed send are each a result and none stops the start or the other lines; a table that cannot be read is one result. **Why a start does not refuse on a failed safe-off:** that is the fail-closed rule, which `notes/hil/14-implementation-plan.md` puts in its own phase; today's `start` entry is the record a later rule will read.

**A kill, a crash or a power loss runs no safe-off; the next start does.** The `start` entry's `previous` is `"clean stop"` only when the log's last entry is a `stop`, so a kill reads `"not a clean stop"` and an empty log `"log started anew"`; `previous_stop_utc_ms` names the last `stop` either way, which is "the time it was stopped". `last_images` is `"unknown"` in every start entry, because the image log is in memory. Entry shapes: [../interfaces/call-log.md](../interfaces/call-log.md); later work (the call log failing closed, EMB-328, then EMB-329) builds on them.

**Measured:** unit tests with a fake bench: every declared line is sent before the first route answers and again after the last request and before the `stop` entry (the call log's length at each send is 0 and then 2); a declaration with no line, an absent port, a failed send, a non-writable signal and an unreadable table are each a result; a study in flight has its flag raised and its lock released before the safe-off; a study that never ends is waited for only the bounded time; a start on a taken port fails naming the address; after a dropped Core (no `stop`) the next start reads "not a clean stop" and the chain recomputes. **Not run:** a real instrument, a real bench board, SIGTERM or Ctrl-C on a process, or the SCM Stop (hardware-verification debt, `tasks/core/181`).

### 158 — Core refuses every gated call but a cancel while it cannot write its call log, starts no new step, and keeps a reserved tail for the safe-off

Decision 122 served a call whose entry could not be written, so an agent could act on the bench with nothing a reader could check. The design is `notes/hil/12-prevention.md`, item 3. **Core is in the *cannot-log* state** when an append fails (any error, a chain that does not verify included) or when free space in the call log's folder is below the reserved tail; **the next append that succeeds with room left clears it**, and the space check is made afresh at each gated call, so room returning clears it too. EMB-329's quota builds on this state: it is `CallLog::gate` and `cannot_log`, a reason string and one flag, nothing else.

**In it, every gated route answers `503`** naming the call log and why, **except `POST /study/{study_id}/cancel`**, which is served and entered if it can be. The layer asks before the handler runs, outside the lease layer and inside the auth layer, so an unauthenticated call is still `401` and a refusal replaces `409`. A call whose entry fails *after* its handler ran is served; the next one is refused. **How a failed-write state ends:** the refusal's own entry is the probe, so the first refusal after the writer recovers is entered (`status` 503) and the call after it is served. A space-only refusal is **not** entered, because the tail is for the safe-off.

**A host study in flight starts no new step.** Before each step, each `Repeat` pass and each teardown step, the backend is asked; a step list stops with "the call log cannot be written ... no new step was started", and the teardown, which runs only while it can be logged, is replaced by Core's safe-off (decision 156), run once under `hw_lock`. `events.json` carries `teardown_replaced` (the safe-off's results, null when the teardown ran) and `stopped_reason` says so. The safe-off is entered as one `safe_off` entry per result (`why`, `result`) **without asking the gate**; were the tail spent, Core still switches off and says it could not log in its tracing log. **Not covered:** a device study's steps are the bench firmware's, which Core can only ask to stop; Core does not stop one for the call log (`open.md`).

**The reserved tail** is `(outputs + 2) x 8192 B`: one entry per declared safe-off line (an instrument with none counts one, each signal one), a `start` and a `stop`, read from the declarations at each gate. The 8192 B per entry is **assumed, not measured**. The `start`, `stop` and `safe_off` entries do not ask the gate. The call log stays a file of its own, so a full one never stops the key or the run log being read. Free space is `statvfs` or `GetDiskFreeSpaceExW`, behind a `Store` seam tests make fail or fill.

**Measured:** unit tests with that seam: every gated route but a cancel answers `503` naming the call log while writes fail, nothing is written meanwhile, and after the writer recovers the next call is refused-and-entered and the one after is served and logged; free space below the tail refuses with no entry while a cancel is served and the `safe_off` entries land; a study that cannot log starts no new step and runs the safe-off in place of its teardown. **Not run:** the Windows free-space call (compiled on no Linux build), a full real disk, a real instrument.
