### 93 — `/lease`: one session holds the whole bench across calls, and a hardware request without its token is refused `409` by name

`hw_lock` serialises single requests and nothing longer. A session's unit of work is a sequence (flash, reset, a dozen exchanges, a register read), and between any two calls another session could flash its own image, after which every reply describes the wrong firmware with nothing to say so. The field answer (two sessions on one DUT and one bench board, 2026-10-08 on) was a `mkdir` lock directory: 62 holds by 8 sessions, one collision, and a reflash after every take because nobody could know what the other had left. It held only while every session remembered the rule, and it could not see calls made through `embarch-atlas`'s live tools.

**The shape.** `POST /lease {holder, purpose?, ttl_s}` answers `201` with `{token, holder, purpose, started_at, expires_at, ttl_s}`, the token shown once. `PUT /lease {ttl_s?}` renews (to `ttl_s` from now, its own TTL when omitted) and `DELETE /lease` releases (`204`); both need the token, in the `X-Embarch-Lease` header. `GET /lease` returns the lease without its token, or `404`. A second `POST` while one is live is `409` naming the first. A `PUT`/`DELETE` with no live lease is `404`; with the wrong token, `409`.

**It covers the whole bench, not one board.** The field sessions always used both boards together, a per-board lease would need a board vocabulary Core does not have (a chip is not a role, and a signal is neither), and two leases would bring a lock-order problem for nothing. If a second use appears that wants one board, that is a new decision.

**While a lease is live, a request to a gated route without its token is `409`**, plain text, naming holder, purpose, start and expiry. With no lease live nothing changes: every route behaves as before, which the existing tests cover unchanged. The check is a middleware inside `auth_middleware`, keyed on the registered path pattern, so it needs no edit in a handler. The gated set is `lease::LEASE_GATED`: `/flash`, `/reset`, `/bootload`, `PUT`/`DELETE /bootload/ports`, `/serial-log`, `/dev-bench/hello`, `/probes/enroll`, the three enrollment writers, `/dev-bench/link`, `POST`/`DELETE /signals*` (the registry writes, which take `hw_lock` and change what an exchange reaches), `/signals/{name}/exchange`, `/live/mem-read`, `/validate` and `POST /study`. Everything else is `lease::LEASE_OPEN`: enumeration and other reads, the `GET` of a capture or a study's record, and `/lease` itself. **A test requires every route to be in exactly one list**, so a route added later cannot skip the question.

**Starting or stopping a background capture is a hardware call under the lease; reading one is not.** `POST /signals/{name}/capture` opens a port and records what the DUT prints for up to 600 s, so a session that does not hold the lease starts one the holder never asked for and then has `POST /bootload` refused by name against its port; `DELETE` ends the holder's recording. Decision 92's capture takes no `hw_lock`, and the lease does not change that: it is a separate gate that asks only who may start the sequence. A capture started under a lease keeps running if the lease expires (it is bounded by its own `max_s`). `GET .../capture` stays open, since it returns bytes the capture already holds and moves no board.

**A study in flight is not interrupted.** `POST /study` is gated at submit; taking a lease while a study runs succeeds and does not stop it, since a lease is a promise about *new* requests and the study already holds `study_lock`.

**Expiry is lazy and needs no human.** There is no timer: a lease is live iff `now < expires`, evaluated on every check, so a crashed holder frees the bench at its TTL with no sweep to fail. `ttl_s` is `1..=14400` (four hours); out of range is `400`. **[assumed]**: the cap is reasoned from the field's longest hold, 1.4 h (6.3 h across 62 holds), not measured against anything. The lease is in memory: a Core restart drops it and frees the bench (the safe direction), and the holder learns of it as a `404` on its next renew.

**`GET /status` carries two additive fields**, `lease` (the view, or `null`) and `last_images`: per chip, the last image Core flashed or bootloaded since it started, `{chip, probe_serial, path, sha256, flashed_at, lease_holder}`. `sha256` is of the bytes Core read from the path just before flashing (`null` if unreadable), `path` is `(uploaded)` for a multipart flash and `(bootload image)` for `POST /bootload`, and the record is written only after the flash succeeded. **An absent entry means unknown, not "nothing flashed"**: the record is in memory, so a restart empties it and a flash by another tool does not appear. A session that takes the bench compares `sha256` with its own image to decide whether it must reflash. This does not reverse the spec's "no persisted current-firmware record": nothing is persisted, and nothing treats it as truth.

**The client half is `embarch-api`'s**: the MCP server and CLI take, renew and send the token, with the token carried in an environment variable so `embarch-atlas`'s live calls inherit it (inbox drop, `tasks/core/099`).
