# embarch-core decisions: Writing to a declared signal

**Status:** active, 2026-10-26.

Index: [../decisions.md](../decisions.md). Current truth: [../spec.md](../spec.md). HTTP surface: [../interfaces/topology.md](../interfaces/topology.md).

### 79 — `POST /signals/{name}/exchange`: one written line and its reply, inside one `hw_lock` hold

An agent working a DUT needs its shell: write `kernel uptime`, read the reply. Until now that meant a hand-written serial script on the Core machine per session, outside Core and outside its lock, racing anything Core did to the same board. The DUT's console is a declared signal ([`embarch-topology`](../../embarch-topology/decisions.md) decision 37 makes a direct `host-to-dut` or `bidirectional` one writable), so the write belongs on the signal routes.

**An exchange, not a session.** The port is opened, the line written, the reply read until `until` appears or `timeout_ms` passes, and the port closed, all inside one `hw_lock` hold. A held-open session would keep the lock across an agent's thinking time and block every flash and reset on the bench; a shell is command-and-reply anyway. `timeout_ms` defaults to 2,000 and is capped at `serial::MAX_DURATION_MS` (10,000) for `/serial-log`'s reason (decision 58): under the shared client's 15 s timeout. A request is checked before the lock: an empty or over-4 KiB `write`, an empty `until`, a timeout outside the range are `400`s.

**Bytes in, bytes out.** The reply is lossy UTF-8 with the DUT's escape codes left in (`embarch-outpost` decision 11's pass-through posture): stripping colour or matching a prompt is the caller's job, and a caller that wants the raw console still has it. Pending input is discarded before the write by default, so the reply is this command's, not an earlier log line's tail. DTR is asserted, because a Zephyr CDC ACM shell may wait for it; a bridge without the control line is not refused. The read is capped at 256 KiB.

**The rate is the signal's own** (`baud` in the declaration), else `EMBARCH_SIGNAL_BAUD`; the same rule now applies where a study opens a signal tap and where the outpost pre-flight reads its header.

**`until` is matched only after the echo of what was written** (`match_after_echo`, on by default). Found on the first real DUT: a Zephyr CDC ACM shell prints a fresh prompt the moment the port opens and DTR rises, before the command's echo and output, so a plain match ended every read on that prompt with an empty reply. A console that does not echo turns it off.

`404` when nothing is declared under the name; `409` when the signal is declared but not writable, or its port is not enumerable now.

**Rejected: a raw `?port=` write like `/serial-log`'s read.** A write is the one operation that can change a board's state; naming it by a declared signal means the port, the direction and the rate are facts someone stated, and a `dut-to-host` trace can never be written by mistake.

**Amended 2026-10-06: `port_wait_ms`.** A caller that has just flashed or reset the DUT finds its USB CDC ACM console gone for a few seconds while the device re-enumerates, and the exchange answered `409` at once, so every agent wrote a sleep-and-retry loop. `port_wait_ms` (default 0, max 10,000, checked before `hw_lock`) makes Core poll enumeration every 250 ms for that long, and only for a declared direct port that is missing (`embarch-topology` decision 40's `SignalMismatch`); any other failure answers at once. The wait holds `hw_lock`, as the exchange it precedes does. The client adds it to the request's timeout.


**Amended 2026-10-26: the write has its own deadline (`core` task 097).** `serialport` uses one timeout for both directions, and the port was opened at 50 ms for the read poll. A Zephyr CDC ACM device still draining earlier input stops taking bulk OUT packets, so a 357-character line outran 50 ms, the Windows write was cut short mid-transfer, and `write_all` resent from a count that no longer matched what had left: the device saw the line with a hole near the end and the exchange answered as if nothing was wrong. Now the port's timeout is set to the request's `timeout_ms` for the write, then back to 50 ms for the read; the write loops on `TimedOut`/`WouldBlock`/zero-length results until the same `timeout_ms` deadline, and past it the exchange fails naming how many of the line's bytes were taken, instead of returning a reply to a damaged line. The read's own deadline starts after the write (superseded by task 107, below). Measured: only against a fake port that stalls and takes short bursts (unit tests); the real-device behaviour is a hardware-verification debt (task 097).

**Amended 2026-10-26 (task 107): one `timeout_ms` covers write and read together.** The amendment above read as a fresh `timeout_ms` for the reply, so a device that took its line just inside the write deadline held `hw_lock` and the HTTP request for up to `2 × timeout_ms`, past the 15 s client timeout the cap was sized under. There is now one deadline, started when the write starts: the read gets whatever the write left of it, and a line that ate the budget still gets one read pass. The write's per-call port timeout is set to what remains of that deadline before each attempt, so a blocking write cannot outlast it either. The bound: an exchange takes at most `timeout_ms` plus one 50 ms read poll (plus scheduler slack), and `port_wait_ms` before it; the cap (10,000) and the client's `timeout_ms + port_wait_ms` addition are unchanged and the rationale holds. Measured against a fake port only (a unit test with a line taken ~300 ms into a 400 ms budget ends inside 650 ms); a real port's blocking-write behaviour is the same hardware-verification debt as task 097.

**Amended 2026-10-26 (task 098): the reply now says what happened on the wire (decision 85).** The read no longer stops at the first `until` match when it falls mid-line, a read error after the write is a `200` with `port_lost` rather than a `500`, and the answer carries more fields. Why, and the numbers: decision 85.

### 85 — An exchange answers with what the wire did: bytes, echo, write, port loss, and, when silent, the port and the core

Field use on a USB PD charger board (2026-09-09 to 2026-10-20) found 10 of 122 `signal_exchange` calls back with `text: ""`, `until_seen: false` from five different causes (a board held in reset by a shield jumper; a shell starved after cabling; the DUT hung; the wrong build; the signal pointed at a USB-UART bridge while the shell was on USB CDC ACM), two `500`s for a command that had in fact run, and 14 of 29 replies waiting for a mid-line marker (`pd: `) that stopped inside the line. Decision 79 cites; this adds.

**The response states.** `bytes_read`; `echo_seen` (the written line, minus its line ending, appeared in the reply: a live shell); `written` (`write_all` and `flush` both succeeded; always `true` in an answer, since a write that fails is an error whose text says `nothing was written` or how many bytes were taken); `port_lost` (a read error other than a timeout after the write: `text` holds what arrived, the command ran, and the answer is a `200`). The `500` is gone for that case on purpose: a state-changing command that answered `500` was sent again. A failure to open the port or to write stays an error; a flush failure says the line was written and may have gone out.

**Silence is annotated, not diagnosed.** When no byte came back, `port_identity` (VID, PID, product, serial of the port that was opened, so a USB-UART bridge is told from the DUT's own USB device) and `core_state` are added. `core_state` reads `DHCSR` through the guarded attach of decision 80, twice 3 ms apart (`S_RETIRE_ST` clears on read, so the second read says whether instructions retired), and decodes `S_HALT`, `S_SLEEP`, `S_LOCKUP`, `S_RESET_ST`, `S_RETIRE_ST`. It is a PPB read: it never halts the core (unlike decision 81's reads) and is right on a sleeping STM32G0 with no DMA clock. If the signal's role has no enrolled probe, or the probe cannot be used, `core_state` carries `unavailable` and the reason instead of a register. A port wait (decision 79's `port_wait_ms`) that runs out adds the same `core_state`, as text in its `409`, since there is no port to identify. Core names what it sees and does not name a cause: that stays the caller's inference. **On these two paths decision 79's bound grows:** the probe open, the attach and both reads run after the deadline, still inside the same `hw_lock` hold, so a silent exchange or a spent port wait takes 79's bound plus one guarded attach and 3 ms (the attach is not measured). At the 10,000 ms cap the 15 s client timeout leaves about 5 s for it.

**`until` found mid-line reads on.** After the first match (after the echo, as before) the read ends when a `\r` or `\n` follows the match, or the port has been quiet for 40 ms (`QUIET_GAP`), or the deadline passes, so `pd: ` returns `pd: ok\r\n`, and a prompt with nothing after it returns 40 ms later, not at the deadline. The cost is that 40 ms on every prompt-terminated exchange.

**Measured vs assumed.** Measured: the unit tests against a fake port (each branch of the response; both unavailable branches of `core_state`). Assumed: the 40 ms gap (one UART burst at the rates in use; not measured against a real shell) and that the guarded attach never halts and does not disturb a running core (decision 80's premise; not exercised for this read). Hardware-verification debt on task 098: a board held in reset, a board halted by a debugger, and a command that drops the CDC ACM port. The native Windows build was not run.

### 96 — An ambiguous declared serial is a `409`, never waited on, and every caller says the candidates

`embarch-topology` decision 46 added `SignalAmbiguous`: a direct signal's declared USB serial matches several ports. Core's callers of `resolve_signal_port` keep their existing statuses, and the ambiguity rides them: `POST /signals/{name}/exchange` and `POST /signals/{name}/capture` answer `409` (a configuration conflict, not a 500 or a 404) with `{e:#}`, whose text lists every candidate port and interface; a study tap and the outpost pre-flight return the same text as their error string (they were `{e:?}`, now `{e:#}`, the one-line form). `resolve_port_waiting` waits only on a `SignalMismatch` with a declared serial, so an ambiguity, which is present rather than missing, returns at once; `resolve_port_waiting_with` takes the resolver so a test pins that with no port enumerated. Measured by test, not on hardware.
