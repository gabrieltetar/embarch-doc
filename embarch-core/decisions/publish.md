### 116 — Publish is two routes, `report-data` then `publish`, because the PDF is built from the first and listed in the second

`report-data.json` must exist before embarch-api can render the PDF and the exports, and the manifest must list those files by hash, so one route cannot carry both. **`POST /study/{id}/report-data`** writes `report-data.json` and `report-data.dsse.json` into `study_results/<id>/publish/r<N>/` (`N` is the number of `published` entries for the run, plus one) and answers the data. It writes nothing to the log and may be asked again. **`POST /study/{id}/publish`** takes `{files: [{name, sha256}]}`, embarch-api's own files, rebuilds `report-data.json`, **refuses `409` if its bytes differ from the file on disk** (a note was adopted since, or the publishing token's scope differs from the asker's), hashes every file Core produced, signs the manifest and appends the `published` entry. **Core's files** are `events.json`, `measurements.json`, `study.json`, `record.dsse.json`, every file under `streams/`, `report-data.json`, `report-data.dsse.json`, `run-log-segment.jsonl` and, for a run whose record names a call-log range, `call-log-segment.jsonl`: they are the manifest's `subject`. **embarch-api's files** are `predicate.embarch_api_files`, never subjects: Core's signature says they were in the zip, not that they are faithful (`notes/hil/06`). A name Core produces is refused `400` in that list. The manifest is a DSSE envelope under decision 110's key (`urn:embarch:predicate:publish-manifest:v1`), and **`manifest_sha256` is the SHA-256 of the envelope file's bytes**. `report-data.json` is signed as a Statement whose subject is the plain file and whose predicate is the data, so a standard DSSE check yields the data and the plain file is checked against it. **Files are fetched** through `GET /study/{id}/publish/{revision}/files/{name}`, which serves Core's five publish files and any file the revision's manifest names, nothing else; **at the pending revision** (the next number, once `report-data` has written its file, no manifest yet) it also serves the run's own Core files, so embarch-api can render the PDF and exports before `publish` signs them (EMB-241). That revision and those names only, so the route is no general file read, and the bytes are the run directory's, the ones the manifest then hashes. A run with no signed record, or whose captures were discarded, is refused `409`. **Not done:** the Test-phase claims `notes/hil/06` lists (verdicts, the requirement roll-up, the atlas's requirement count), the fixed statement, and a segment narrowed to a unit: **the segment is every log line before the publish's own entry**, from line 0. **The call log's segment** (`tasks/core/145`) is the entries in the run's range from its record, headed by a line naming the entry before it and the head at the end; a run sealed without the range gets none; no `schema` bump, the field being additive. `report-data.json` carries the range's head and count since `core/148` (119).

### 117 — A note or a prose block reaches Core through `POST /study/{id}/adopt`, which records the token's scope and the SHA-256 of the text

The route takes `{kind: note|prose, name, text}` and appends an `adopted` entry to the run log: `scope`, `text_sha256` (Core hashes the UTF-8 text it received) and the time; **the text is not kept**, so it is in the zip and the hash is Core's. `report-data.json` carries the latest adoption of each `(kind, name)` with its attribution: a note with the agent's token reads **"relayed by the agent"**, with the person's **"the person's"**; a prose block reads "entered with the agent's token" or "the person's token" (the model id is embarch-api's claim, not Core's). `verify` check 5 hashes the zip's note and prose files against these. A name is a relative file name (printable ASCII, 200 bytes, no `..`), a text is 1 MiB at most.

### 118 — A publish records the run log's head beside the manifest hash, and takes both under the log's write lock

The `published` entry gains `revision`, `log_head` (the head of the chain the segment ends at, which is also the entry's own `prev`) and `report_data_sha256`; the manifest's predicate repeats `run_log.head` and `length`. **The head is read, the segment written, the manifest signed and the entry appended inside `RunLog::append_with`'s lock**, so a run that ends meanwhile cannot come between the head a publish names and its entry. This closes the tail-anchor item for a tail cut before the recorded head; `verify` check 8 comparing it is M1.11's, and a cut after the last publish stays undetectable ([open.md](../open.md)). **`POST /study/{id}/published`** (decision 111) stays as the bare record of a hash, with none of these fields. **A `run` entry gains `go_by`**, the scope of the token that began the run (`POST /host-studies` now reads its scope).

### 119 — `report-data.json` is deterministic, carries no verdict, and labels attestation from the two labels a milestone 1 Core can reach

It holds `run_status` (`completed` when the run's `clean` is true, else `step_failed`; `interrupted` and `cancelled` are not produced, as no record of such a run exists), per-outcome step counts, the study name and `provenance` as the declared subject, `go_by`, `published_by`, the adoptions, the record's `image_status`, declarations, call-log head, range and count (when the record has them; `core/148`) and `claimed.build` (a claim, labelled), Core's version and `keyid`, and the record's hash. **It carries no clock and no run-log head**, so `publish` can recompute it byte for byte; and no `tests`, `requirements` or `verdicts` key, tested. **The attestation label** is "person's acts not protected" when any act was the person's (the go, the publish, an adoption, a declaration) and "agent-scoped only" otherwise, with `core_attested: false`: **every Core is unattested in milestone 1**, and the labels that need a container statement or a passkey are not reachable. **[Assumed]:** that this pair is the right milestone 1 reading of `notes/hil/06`'s closed list.

**Measured:** unit tests over a fixture run through the real routes: the manifest and the report-data verify under a standard DSSE check written from the spec's text, fail on a changed byte, and name every Core file by a hash that matches the served bytes; embarch-api's file is listed and not a subject; the head recorded equals the log's head before the publish and the segment ends there; a second publish is revision 2 naming the first; a note from each token is attributed as above, with the text's hash; the refusals. **Not run:** a real study's publish, a third-party DSSE verifier, and the Windows ACL on the new files, which are under `study_results/`.

### 120 — A run the retention sweep took is restored by `PUT /study/{id}/restore/{name}`, one file at a time, each checked against a manifest Core signed and logged

`report-data` and `publish` read the run's own files, and the sweep removes the whole `study_results/<id>/`, publish directories included. **`PUT /study/{id}/restore/manifest.dsse.json`** takes the earlier revision's manifest and accepts it only if its SHA-256 is the `manifest_sha256` of a `published` entry the run log holds **for this run** (`422` otherwise); it waits in `restored/<sha>.json`. **`PUT /study/{id}/restore/{name}`** takes a Core run file (`events.json`, `measurements.json`, `study.json`, `record.dsse.json`, `streams/*`) and accepts it only if an accepted manifest lists `name` as a `subject` with the bytes' digest: `409` before any manifest, `422` for a name that is no subject, a revision output (`report-data.*`, the segment, the manifest) or a wrong digest, and nothing is written on a refusal. The body is raw, up to 1 GiB. **Nothing the caller supplies is trusted on its word:** the hash of Core's own signed envelope is in Core's own chained log, and each file is bound to it by that envelope's digests, so a forged manifest or file cannot pass. **`report-data` and `publish` then run unchanged**, from the restored files; while the directory is empty, or an accepted manifest names a Core file not yet handed back, they answer `409` naming it (they answered `500` on a swept run), so a half-restored run never signs a short manifest. `supersedes` and the revision number come from the log, as before. The envelope's signature is not re-verified: the logged hash already says these are the bytes Core wrote. **Not done:** restoring embarch-api's own files (they are the caller's to resend and are not subjects), and a limit on how long `restored/` lives (the sweep takes it with the run). **Measured:** unit tests through the routes, a run published, swept, restored, republished as revision 2 naming revision 1, and each refusal. **Not run:** a real sweep on the Windows service.
