### 111 — Core keeps a hash-chained run log that nothing sweeps, retention leaves unpublished captures alone, 

A report must be checkable against a record the agent that wrote it could not quietly shorten (`notes/hil/06`, `13`). **The log** is `run-log.jsonl` beside the token files, one line `{entry, hash}` per entry, `hash` the SHA-256 of the entry's serialisation (`serde_json`'s map is key-ordered, so it is reproducible) and the entry's `prev` the previous line's `hash`, 64 zeros for the first, `seq` its position. **Three entry types:** `run` (one per study run, device and host, written when the run ends, completed or failed: `study_id`, `kind`, `status`, `reason`, `clean`, `ended_utc_ms`, `record_sha256`, `captures` `[{name, sha256}]`); `published` (`manifest_sha256` and the `scope` that recorded it); `discarded` (`scope`, `files_removed`). Removing or reordering a line breaks a `prev`; altering one breaks its `hash`; `GET /run-log` returns the chain with `verified`, and a log that does not verify is **never extended** (it stays as found). A run's record names its call-log range (`observed.call_log`, `tasks/core/145`). **What it cannot show:** a cut of the *tail* leaves a valid chain, so a reader needs the head from somewhere the log cannot reach, which is what a publish recording the head beside the manifest hash is for (M1.8; [open.md](../open.md)).

**Nothing sweeps it.** The retention sweep walks `study_results/` and a discard deletes capture files; a discard does not, and the retention sweep reads it but never writes it, and a restart reads the same file. A run is entered once, only if it began on this Core (`begin` at the point the job is registered), so a run that crashed mid-way leaves no entry and, with no entry, is sweepable.

**The entry carries the hash of `record.dsse.json`** (null for a run that failed before it was signed). Why: the record already names every capture by hash, so the entry's own `captures` repeat that on purpose, because a discard deletes the captures but the log line, which is chained, keeps them; and binding the record's hash into the chain means a replaced record is a mismatch against a log the person can compare with the published zip. Cost: one hash at run end.

**Retention sweeps no capture before publish.** `EMBARCH_STUDY_RESULTS_KEEP` still bounds what is kept, but of the runs the log has not seen published or discarded **every one stays and none counts toward the bound**; the newest `KEEP` of the others stay, the rest go as before. `GET /studies` lists by the same split (decision 69's own rule). **If the log cannot be read, parsed or verified, the set of unpublished runs is unknown, so the sweep deletes nothing** and Core logs why at `error`, the same posture as a log that is never extended; `GET /studies` then lists every study on disk and reports `keep: 0`, since it must not show fewer than the sweep leaves. **The cost is disk the engineer now owns:** a run never published keeps its captures until someone acts, so an engineer who scans a great deal and publishes little sees the results directory grow past `KEEP` runs; `embarch doctor` check 16 already reports count and size. **What the engineer does about it is the discard route** (decision 112), which turns a run into one retention may sweep. A run with no entry (made before this Core) counts as an ordinary run and is swept as before.

**Measured:** the unit tests: the chain recomputes across runs, publishes, discards and a reopened log; a removed, reordered, altered or first-cut entry names its line; a broken log is not extended; retention keeps an unpublished run past `KEEP` and sweeps a published one, and sweeps nothing for a corrupted, tampered or unopenable log (the `error` log line is not asserted). **Assumed:** that an append-only file with `sync_data` is durable enough for an unattested Core; the file's own ACL (Windows `icacls`, like `signing-key`'s) is unrun. The discard is decision 112 below.

### 112 — Only the person discards a run that did not end clean: the first route Core refuses by scope

**The discard** (`POST /study/{id}/discard`) deletes every file under the run's `streams/` and appends `discarded`; `events.json`, `study.json`, `record.dsse.json` and the run's `run` entry with its capture hashes stay. **Either token may discard a run that ended clean (`completed` with every step `Pass`) and that no publish rests on.** **Only the person's token may discard** one that failed, errored, timed out or was inconclusive, or one with a `published` entry (the zip's captures rest on it): the agent's is refused `403` with plain text, `refused: <why>, and only the person's token may discard its captures. Nothing was deleted. Ask the person to discard it, or to run it with the person token (decision 112).`, and nothing is written. A run whose `events.json` cannot be read is not clean, so the doubt falls to the person. `404` for a run the log does not hold, `409` for one still running or already discarded. **The refusal an agent will meet:** a status it can branch on (`403`) and a message that names the cause and who can do it; there is no scope in a body, because errors outside `/validate` are plain text (decision 12). **This is the first route Core refuses by scope**; decision 109 is unchanged for every other route, and the routes in this file are lease-open (they touch files, never a port).

**A pending requirement** (`notes/hil/13`) is a Test-phase notion milestone 1 does not have: the hook is the `clean` test in `RunLog::discard`, and `open.md` says so rather than inventing a requirement store.

**Publish** is M1.8's and M1.10's; this unit gives `POST /study/{id}/published` `{manifest_sha256}` (either token, the scope recorded) and `GET /study/{id}/log` (the run's entry, its latest publish and discard, the head), tested with a fixture hash.

**Measured:** the agent's discard of a `Fail` and a `TimedOut` run is refused `403` over HTTP with the files and the log untouched; the person's succeeds with the entry and capture hash still in place; the agent may discard a clean unpublished run and not a published one.
