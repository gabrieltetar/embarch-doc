# embarch-core: design

**Status:** draft, 2026-07-17. Written to document the existing `embarch-core` implementation — the design discussion that produced it happened as a chat, not a durable record; this file is meant to be that durable record going forward. Append changes to the Changelog (§11) rather than silently editing history above it.

## 1. Purpose and scope

`embarch-core` is the OS-level service that owns the debug probe (flash/reset) and the serial console log. It is deliberately the lowest layer in EmbArch: it has no idea the EmbArch API or Claude Code exist. It exposes five bearer-token-authed HTTP endpoints and holds the hardware connection so nothing else has to fight over the USB port.

embarch-core is **not**:
- Aware of "projects," toolchains, or build commands. It takes a bare `chip` / `firmware_path` / `format` per call — the concept of a named project with its own build config lives entirely in `embarch-api`.
- A build system. It flashes whatever file it's given; it never invokes `west`, `arduino-cli`, or anything else.
- Multi-tenant. It's one process, one hardware connection, one shared token, matching the single-engineer scope of the whole EmbArch stack (see `embarch-api/design.md` §3.1).

## 2. Architecture overview

```
embarch-api --HTTP+Bearer--> embarch-core --probe-rs/serialport--> hardware
                                    ^  |
                                    |  +--serial (UART/USB CDC, COBS-framed postcard)--> embarch-dev-bench firmware
                                    |                                                    (BLE central/peripheral + power sampling)
                         embarch-core CLI (same machine)
```

`embarch-core` is reached two ways: over HTTP by `embarch-api` (the normal Claude-Code-driven path), and directly via its own CLI (`main.rs`'s `run`/`install`/`uninstall`/`start`/`stop`/`detect-dev-bench` subcommands) for local operation and service management. Both paths converge on the same `hardware`/`serial`/`dev_bench` modules and the same `hw_lock` — there is no separate code path for "CLI mode." `detect-dev-bench` is the second front-end for `GET /dev-bench/port` specifically (§4, §5), keeping that capability reachable by a human with no HTTP client and no running service, per `embarch.md` §5's both-front-ends principle.

**Partly implemented:** the second hardware relationship, bridging `/study` HTTP calls from `embarch-api` to `embarch-dev-bench` over a second, independent serial link. *Which port dev-bench is on* is now answered for real by `dev_bench.rs` (§5, `GET /dev-bench/port`); everything past that — opening the port, the `Hello`/`HelloAck` handshake, relaying a `Study` — is still design-only. See §4's `/study` rows and [embarch-study-designer/design.md](../embarch-study-designer/design.md) §5, which is the source of truth for that surface's design (recorded there ahead of code, same pattern `embarch-api/design.md` §3.10 used for its CLI decision).

## 3. Locked-in design decisions and rationale

1. **Language: Rust**, with **probe-rs used as a library, not shelled out to as a CLI.** Calling `probe_rs::flashing`/`probe_rs::probe` directly (rather than spawning a `probe-rs` binary) avoids subprocess/parsing overhead and gives typed errors (`anyhow::Context`) instead of scraping CLI output.
2. **HTTP framework: Axum.** Chosen for the same reason `embarch-api` also ended up in Rust (per its design doc) — one toolchain across the whole stack, plus Axum's `State`/middleware model maps cleanly onto the `AppState { token, hw_lock }` shape Core needs.
3. **Cross-platform service install via the `service-manager` crate.** `install`/`uninstall`/`start`/`stop` register, remove, and control the same `run` command as a systemd unit on Linux, a launchd job on macOS, or a Windows Service via `sc.exe` — one code path, OS detection handled entirely inside the crate (`service.rs`'s `manager()`), not hand-rolled per-OS logic. `start`/`stop` exist specifically so `embarch-umbrella` doesn't re-derive per-OS service control in a second codebase ([embarch-umbrella/design.md](../embarch-umbrella/design.md) §3 decisions 4/7). **All four require elevated privileges** — root/polkit for a systemd *system* unit, Administrator for a Windows Service — which is not a Windows-only tax as was previously assumed; confirmed on Linux, where an unprivileged `start` fails with systemd's "Interactive authentication required."

    **Correction, 2026-08-12 ([embarch-umbrella/milestone-6.md](../embarch-umbrella/milestone-6.md) §3.8):** "one code path" was true for *registering* the service, but not for what happens once it's launched. `service-manager` only handles `sc create`/`systemctl enable`/`launchctl load`-style registration; it has no opinion on what the registered binary itself must do once running. systemd (`Type=simple`) and launchd both consider "the process stayed alive" sufficient, so `run()` — a plain foreground server, no different from a human running it at a console — worked as the service body on both. Windows does not: `sc create`-registered binaries must call back into `StartServiceCtrlDispatcherW` promptly and report `SERVICE_RUNNING`, or SCM kills the start attempt after a 30-second timeout (Win32 error 1053, System log 7009/7000) — regardless of whether the process itself is working fine. This had never been caught because no prior testing had installed Core as a real boot service on Windows; every earlier "smoke test" used a throwaway foreground instance. Fixed in `service.rs`'s new `windows`-only module (the `windows-service` crate): `Run` now tries the real SCM handshake first on Windows, falling back to the plain foreground path only when `StartServiceCtrlDispatcherW` fails with `ERROR_FAILED_SERVICE_CONTROLLER_CONNECT` (not launched by SCM at all — a human at a console, same as always). Verified for real: installed and started as an actual Windows service on the daily-use machine, `doctor` all green.
4. **A single `hw_lock: Arc<Mutex<()>>` serializes all hardware access.** `/flash`, `/reset`, and `/serial-log` each acquire it for the duration of the call. This is what actually enforces "nothing else has to fight over the USB port" — without it, a CLI-triggered flash and an HTTP-triggered reset could race on the same probe.
5. **Bearer-token auth via Axum middleware, not "trust the local port."** Core may end up reachable over a real network (WSL2-to-Windows today, or a LAN if Core moves to a Pi — see §7), so an unauthenticated HTTP surface isn't acceptable even at single-engineer scale. The check is a plain exact-string compare against `EMBARCH_TOKEN` (`auth_middleware` in `api.rs`) — deliberately not OAuth or anything session-based, matching the single-user scope.
6. **Default bind address `0.0.0.0`, not `127.0.0.1`.** This is deliberate, not an oversight (`main.rs`'s CLI help text says so explicitly): the point of Core is to be reachable from WSL2 if Core runs native on Windows, or from the LAN if Core later moves to a Raspberry Pi. `--bind`/`--port` remain overridable.

    **Amendment, 2026-08-15 (item 17 of that day's design-improvement review — see `.claude/design-improvements-2026-08-15.md`, local working notes): reversed to default `127.0.0.1`, widened explicitly rather than by default.** The review's point stands on its own merits, independent of any incident: `0.0.0.0` + no TLS (§6 below) + a static bearer token + `/flash` reading an arbitrary local path, in a process that may run as `LocalSystem` on Windows, is a security posture nobody had actually assessed as a whole — each piece was individually documented, never composed. `0.0.0.0` was also broader than any topology in `embarch-umbrella/design.md` §4 actually needs: topologies i/ii/iv (Core and API on the same machine, no WSL2 split) only ever need loopback, and only topology iii (WSL2⟷Windows) needs the WSL2 gateway address reachable, which is narrower than every interface. Resolved: Core's own default (no `--bind` given) is now `127.0.0.1`. Widening it is `embarch-umbrella`'s job at `setup` time (`embarch-umbrella/design.md` §3 decision 3), not Core's own default — `setup` detects topology iii and passes `--bind 0.0.0.0` (or, once available, the specific WSL2 gateway address) only when that topology is actually what it found, via the same install/service-registration step that already configures the token and PATH. A foreground `run` with no `--bind` still binds loopback-only, matching the new default. This is a breaking behavior change for anyone who was relying on the old default without an explicit `--bind` — called out in the changelog (§11) for exactly that reason.
7. **Blocking hardware calls always run through `tokio::task::spawn_blocking`.** `probe-rs` and `serialport` are synchronous APIs; every handler in `api.rs` wraps its hardware call in `spawn_blocking` so a slow flash or a serial read with a multi-second `duration_ms` never stalls the Tokio runtime's async executor.
8. **A Zephyr-SoC-name→probe-rs-chip mapping lives here, resolved via a new endpoint, not duplicated as a table in `embarch-api`.** *(Decided 2026-08-13, shipped 2026-08-14. Full context: `embarch-api/design.md` §3 decision 12's open question on where this table should live.)* `embarch-api` needs to turn a Zephyr SoC name (e.g. `nrf54l15`, from a `discovery = "zephyr-west"` project's live board scan) into a probe-rs chip target string (`nRF54L15`) before calling `/flash`/`/reset` — and it's about to call one of those anyway, so resolving it via a call here costs nothing extra and keeps exactly one copy of the mapping, in the one process that actually links `probe-rs` and can therefore validate a mapped name against the real target database rather than trusting a hardcoded string. New endpoint: `POST /resolve-chip`, body `{"soc": "nrf54l15"}` → `{"chip": "nRF54L15"}` on a known mapping, or a `404` (plain text, same convention as `/dev-bench/port`) naming the unmapped SoC when there is no entry — `embarch-api`'s existing unmapped-SoC fallback (point at `probe-rs chip list`) is unchanged for that case. Complements, rather than replaces, §10's open `chip-list` item: `resolve-chip` is the automatic common-case path, `chip-list` remains the human-facing fallback when a SoC has no mapping yet.

    **Implemented as `chip_resolve.rs`** (§8): a small `SOC_TO_CHIP` table covering this suite's real Nordic hardware family (nRF51/52/53/91/54L series), matched case-insensitively and exactly (no prefix/fuzzy matching — a plausible-but-wrong match here would silently pick the wrong physical target). The mapped candidate is then looked up in `probe_rs::config::Registry::from_builtin_families()` before being returned, so a table entry that's gone stale against a future probe-rs version fails exactly like an unmapped SoC rather than succeeding here and only failing later, confusingly, at `/flash`. A unit test (`every_table_entry_resolves_against_the_real_registry`) checks every table entry against the real registry so drift fails a test run, not a live call. Smoke-tested live against a running Core: `nrf54l15`/`NRF54L15` both resolve to `nRF54L15`, an unmapped SoC (`esp32c3`) 404s naming the SoC, and the route still enforces bearer-token auth like every other endpoint. `cargo build`/`cargo clippy --all-targets -- -D warnings`/`cargo test` (4 new unit tests) clean.

9. **`open_first_probe()` grows a serial-number selector — decided ahead of dev-bench hardware existing, per §5's own open item.** Closes item 8 of the 2026-08-15 design-improvement review: dev-bench itself *is* a second debug probe (the DK's on-board J-Link, §5), so the moment dev-bench exists, "more than one probe attached" stops being the edge case §10 used to defer and becomes the normal state on any machine running both a DUT probe and a dev-bench. `/flash`/`/reset` gain an optional `probe_serial: Option<String>` body field, matched against `ProbeInfo.serial_number` (already surfaced via `/status`); omitted, behavior is unchanged — `open_first_probe()` as today, correct for the common single-probe case. More than one probe present with `probe_serial` omitted now returns a `400` naming every candidate's serial number, rather than silently picking one — a wrong-target flash is a worse failure mode than a loud one. `embarch-api`'s config schema gains a matching optional `probe_serial` per-project field (`embarch-api/design.md` §4), passed through unchanged.
10. **`/flash` accepts a multipart file upload as an alternative to `firmware_path`, closing the artifact-transfer gap for a genuinely separate machine.** Item 9 of the review, tracked previously as an open gap in three docs (`embarch-api/design.md` §9, this doc's own §7, `embarch-umbrella/design.md` §3 decision 8): `firmware_path` only ever worked when the caller and Core share a filesystem (same machine, or the WSL2-same-PC UNC-path special case). `POST /flash` now accepts **either** its existing JSON body (`firmware_path`, unchanged, still the right choice when Core and the caller do share a filesystem — no need to re-upload bytes that are already locally readable) **or** a `multipart/form-data` body carrying the firmware bytes directly plus the same `chip`/`format` fields, written to a temp file under Core's own data directory before flashing and deleted after. `embarch-api` prefers multipart only for a `remote` Core (`embarch-umbrella/design.md` §3 decision 6's topology classes) — the one class with no working transfer mechanism at all today; `local` and `wsl-host` keep using `firmware_path` (via `artifact_path_for_core`'s existing UNC translation for `wsl-host`), since that's already a validated, zero-copy path on real hardware (milestone-1) and multipart would only add the cost of re-uploading bytes for no benefit there. This closes topology v's "flash doesn't work at all" gap without touching the mechanism the suite's primary daily-use topology (iii) already depends on — `artifact_path_for_core`, `wsl_unc_path`, and `doctor` check 9 stay exactly as they are for that case, not retired.
11. **Core gains an optional config file, next to the machine-wide token file — an explicit env var still wins.** Item 10 of the review: every Core knob today (`EMBARCH_TOKEN`, `EMBARCH_DEV_BENCH_PORT`/`_PRODUCT`/`_SERIAL`/`_INTERFACE`, `--bind`/`--port`) is env-var-only, and passing environment to an installed OS service is exactly the class of bug that already cost this suite a real debugging session (§3 decision 3's correction, the `sc.exe` registry gap). A config file sidesteps that class of bug permanently, the same way the token file already does for `EMBARCH_TOKEN` specifically (§8): `%ProgramData%\embarch\core.toml` / `/var/lib/embarch/core.toml`, read once at `run()` startup, holding the same knobs the env vars cover today (`bind`, `port`, `dev_bench_port`/`dev_bench_product`/`dev_bench_serial`/`dev_bench_interface`). Precedence, matching `token_store`'s existing explicit-wins pattern (§6): an explicit env var or CLI flag still overrides the config file value; the config file overrides Core's built-in defaults; nothing set falls through to today's defaults unchanged. Written by `embarch-umbrella`'s `setup` (§3 decision 3's amendment above is the first real consumer — the resolved `--bind` value for topology iii lands here rather than needing to be re-derived from the environment on every service start), not hand-edited as the common case, though nothing stops a human from writing it directly. `install`/`start` no longer need `service-manager`'s `environment` passthrough for anything this file now covers — narrowing, not eliminating, §10's still-open Windows-registry-write validation item (only an explicit `EMBARCH_TOKEN` override still needs it, per that item's own text).
12. **A stable `{code, message, cause}` JSON error body replaces the plain-text `anyhow` chain on every non-2xx response.** Item 11: today's handler errors are `(StatusCode::INTERNAL_SERVER_ERROR, String)`, rendered as **plain text** (§4) — fine for a human reading a CLI error, but `embarch-umbrella`'s `doctor --json` and a future UI (`embarch-umbrella/design.md` §10) both need to branch on error *kind*, not just prose. New shape, still non-2xx (status codes unchanged): `{"code": "probe_not_found" | "chip_unmapped" | "flash_failed" | "auth_failed" | "study_conflict" | ..., "message": "<one-line summary>", "cause": "<full anyhow chain, {e:?}, unchanged from today>"}` — `code` is a small, append-only enum stringified for JSON, `message` is fit for direct display, `cause` preserves everything §4/§11's earlier "don't lose the causal chain" fix already established. `embarch-api`'s `--json` output gains a matching `error_kind` field, populated from `code` when the failure came from Core, or a small `embarch-api`-native equivalent (`config_error`, `build_failed`, `core_unreachable`) for failures that never reach Core at all. This also retires `embarch-api/design.md` §12's deferred "CLI exit-code granularity" item — a script that needs to branch on failure kind now has `error_kind` in `--json` rather than needing a finer-grained exit code.
13. **`/status` gains `core_version: String` and `contract_version: u32`, giving `embarch-api` a version handshake beyond the study-schema check it already has.** Item 13: today's only version check across the API↔Core boundary is `study_designer_schema_version` (§3 decision 8's neighbor via `/status`, `embarch-study-designer/design.md` §3 decision 12) — there's no way for `embarch-api` to notice it's talking to a Core built from a materially different `api.rs` contract (a renamed field, a changed error shape) until a call actually breaks. `core_version` is Core's own `CARGO_PKG_VERSION` (already wired to `--version`, §11's 2026-08-05 entry); `contract_version` is a small integer bumped by hand only when a *wire-visible* HTTP contract change happens (a field renamed/removed, a status code's meaning changed) — independent of `core_version`'s semver, matching the same "bump only when the wire shape changes" discipline `STUDY_DESIGNER_SCHEMA_VERSION` already established. `embarch-api` compares its own compiled-in `EXPECTED_CORE_CONTRACT_VERSION` against `/status`'s value and warns (not refuses, matching `embarch-umbrella/design.md` §3 decision 14's existing warn-not-refuse posture for version skew) on mismatch. `embarch-umbrella`'s manifest-version comparison (`doctor` check 1) is unaffected — this is the API↔Core contract specifically, not the release-archive bundling check.
14. **`hw_lock` contention now returns a `503` "busy" response instead of blocking the caller until `flash_timeout_secs` elapses client-side.** Item 19: with per-repo `embarch-api` configs (§3 decision 12 there), two `embarch-api` processes hitting one Core is a normal occurrence, not a bug — but today the second caller just blocks silently on the mutex until its own client-side timeout gives up, indistinguishable from Core being genuinely unresponsive. `/flash`/`/reset`/`/serial-log` now attempt `hw_lock.try_lock()` first; on contention, they return `503` immediately with a body naming which operation currently holds the lock (tracked via a small `Mutex<Option<&'static str>>` alongside `hw_lock` itself, set/cleared by whichever handler holds the guard) rather than queuing. `embarch-api` surfaces a `503` as a distinct, retryable "Core busy" error (via §12's new `code`) rather than the generic timeout text it reports today.
15. **The dev-bench serial link's ownership is explicit: `study.rs` (once implemented) holds it open for the duration of a study, exclusively, via the existing one-study-at-a-time lock — `GET /dev-bench/port`'s enumeration stays lock-free.** Item 20: nothing previously stated what happens if `/dev-bench/port` (pure USB-descriptor enumeration, §4/§5, opens nothing) is called while a study has the actual port open — the answer was already implicit in the two operations never touching the same resource (enumeration never opens the port), but wasn't written down. Stated here so it doesn't need re-deriving later: `/dev-bench/port` remains safe to call at any time, including mid-study, since it never opens the serial connection itself; the one-study-at-a-time lock `embarch-study-designer/design.md` §5.1 already specifies is what actually arbitrates the port itself, and stays entirely separate from `hw_lock` (which governs the DUT probe/serial connection, a different physical link) — no new lock needed, just this clarification that the existing one already covers it.
16. **`tracing` output gets a defined per-OS log file, with rotation — closing item 12 of the 2026-08-15 design-improvement review.** Today's `tracing` output goes wherever the process's stderr happens to land, which is a real file only for a foreground `run` a human is watching — for an installed OS service (§3.3), it's whatever the service manager captured, if anything (the 1053 bug, §3 decision 3's correction, was diagnosed from the Windows Event Log purely by luck, not by design). New: `tracing-appender`'s daily-rolling file writer, in addition to (not instead of) the existing stderr output, at `%ProgramData%\embarch\logs\core.log` / `/var/lib/embarch/logs/core.log` — the same machine-wide-path convention `token_store.rs` already establishes (§8) — retaining the last 7 daily files before deleting the oldest. New `embarch-core logs [--tail N]` CLI subcommand (pure file read, no hardware access, same posture as `chip-list`/`detect-dev-bench`) prints the current log file's last `N` lines (default 50); `embarch-umbrella`'s `doctor` surfaces the same tail as a new informational line so a human doesn't need to know the path (`embarch-umbrella/design.md` §5).
17. **CI (`cargo test`/`clippy` on push, plus a `native_sim` build for dev-bench) is added across every repo that doesn't have it yet — closing item 15.** Only `embarch-doc` has CI today (`DOC-PROTOCOL.md` §5); a free `west build -b native_sim` would have caught the real `BT_LE_ADV_CONN_NAME` breakage (`embarch-dev-bench/design.md`'s 2026-08-04 changelog entry) before it was found by hand. New `.github/workflows/ci.yml` per repo (`embarch-core`, `embarch-api`, `embarch-umbrella`): `cargo build`/`cargo clippy --all-targets -- -D warnings`/`cargo test` on every push/PR, mirroring what's already being run by hand before every commit per this doc's own changelog. `embarch-dev-bench` additionally supersedes its own decision 9 ("no CI for now") — see that doc's own changelog for the corresponding entry — with a compile-only `west build -b native_sim app` job, cheap and hardware-independent, plus the existing `ztest` suite.

## 4. Endpoint reference

All routes require `Authorization: Bearer <token>` (see §6).

| Method | Path | Body / Query | Response |
|---|---|---|---|
| `GET` | `/status` | `?probes=1` (optional) | `{ status: "ok", probes: [ProbeInfo]?, study_designer_schema_version: u32, core_version: String, contract_version: u32 }` — `probes` (§3 decision 13's neighbor; item 23) is now included only when `?probes=1` is passed, since enumerating USB probes on every call is real per-call cost `embarch-umbrella/design.md` decision 11 explicitly wants `status`/`doctor` polling to stay cheap against; a bare `GET /status` omits the field entirely (not an empty list — `null`, so a caller can tell "not asked for" from "none found"). `study_designer_schema_version` is `embarch-study-designer`'s wire-schema constant (`embarch-study-designer/design.md` §3 decision 12); `core_version`/`contract_version` (§3 decision 13) are the new API↔Core version handshake. |
| `POST` | `/flash` | JSON: `{"chip": "...", "firmware_path": "...", "format": "elf", "probe_serial": "..."?}`, **or** `multipart/form-data` (§3 decision 10) carrying `chip`/`format`/`probe_serial` fields plus a `firmware` file part | `{ flashed: true, chip }` |
| `POST` | `/reset` | `{"chip": "...", "probe_serial": "..."?}` | `{ reset: true }` |
| `GET` | `/serial-log` | `?port=...&baud=115200&duration_ms=2000` | `{ port, lines: [String] }` |
| `GET` | `/dev-bench/port` | — | `{ port_name, detected_by, vendor_id, product_id, serial_number, product, interface }` — which serial port `embarch-dev-bench` is on (§5). `404` (plain text) when no port matches, which is an expected state (bench unplugged), not a Core failure; `500` for an ambiguous match or an unreadable USB bus. Every field but `port_name`/`detected_by` is nullable, since an explicitly-configured port need not be USB-enumerable. |
| `POST` | `/resolve-chip` (§3 decision 8) | `{"soc": "nrf54l15"}` | `{ chip: "nRF54L15" }`, or `404` (plain text, naming the SoC) when unmapped. Takes no `hw_lock` — pure lookup, no hardware touched. |
| `POST` | `/study` — **planned, not yet implemented** | `Study` (JSON) | `{ study_id: Uuid, status: "accepted" }`, or `409 Conflict` (body: in-flight `study_id`) if a study is already running |
| `GET` | `/study/{study_id}` — **planned, not yet implemented** | — | `{ status: "pending"\|"running"\|"completed"\|"failed", current_step: u32?, total_steps: u32?, result: StudyResult?, reason: String? }` |
| `GET` | `/study/{study_id}/power-data` — **planned, not yet implemented** | — | Raw CSV bytes (`Content-Type: text/csv`) |

The three `/study*` rows bridge to `embarch-dev-bench` over the new serial hop (§2) rather than to Core's own probe/serial hardware, and are async/job-based rather than blocking, unlike the five rows above — see [embarch-study-designer/design.md](../embarch-study-designer/design.md) §5.1 for full rationale and semantics (one study in flight at a time via a dedicated lock separate from `hw_lock`, no cancel endpoint in v1, in-memory job retention until restart). That document, not this one, is the source of truth for this surface until it's implemented, at which point this table and the rest of this section should be updated to match reality rather than the plan.

`chip` is an opaque probe-rs target name (e.g. `STM32F407VG`, `nRF52840_xxAA`, `esp32c3`) — Core does not validate it beyond whatever `probe.attach()` itself rejects. `format` is one of `elf` / `bin` / `hex` / `uf2` / `idf`, parsed by `hardware::parse_format`; an unrecognized value is rejected with an explicit error rather than silently defaulting. `firmware_path` is read from Core's own local disk — the caller is responsible for getting the file onto whatever machine Core runs on (see §7).

`/dev-bench/port` is the one endpoint that doesn't take `hw_lock`: it only reads USB descriptors the OS already enumerated and opens nothing, same as `/status`'s probe listing.

Handler errors return `(StatusCode::INTERNAL_SERVER_ERROR, String)`, rendered by Axum as a **plain-text body**, not JSON — callers (embarch-api's `core_client.rs`) must parse JSON only on 2xx and read non-2xx bodies as plain text. The `String` is the full `anyhow` error chain (`format!("{e:?}")` in `internal_err`, `api.rs`), not just the outermost `.context(...)` message — an earlier version used `Display` (`{e}`), which silently dropped every underlying cause (e.g. a real probe-rs I/O error collapsed to the single word "flashing failed"). `internal_err` also logs the same chain server-side via `tracing::error!` before returning it, so a failure is visible in Core's own log even if the caller never surfaces the response body. Found and fixed during milestone-1 §3.3 hardware validation, when a genuine `/flash` failure (a WSL2 path Core's Windows process couldn't open) was completely undiagnosable from either the HTTP response or Core's log until this was fixed.

## 5. Hardware access details

- **Probe selection: serial number, falling back to first-and-only (§3 decision 9).** `open_first_probe()` in `hardware.rs` now takes an optional `probe_serial` — when given, it matches `ProbeInfo.serial_number` exactly (from `Lister::list_all()`, the same enumeration `/status?probes=1` surfaces) and errors listing every candidate if none match or more than one is ambiguous; when omitted, behavior is unchanged from before this decision — the first probe found, correct for the still-common single-probe case, but no longer the *only* case now that dev-bench (a second on-board J-Link, §5 below) makes two probes the normal state the moment dev-bench hardware exists.
- **Probe attach is per-call, not held open.** Each `flash`/`reset` call opens the probe, attaches to the target `chip`, does the operation, and lets the session drop — there's no persistent probe connection held across requests. This trades a little latency per call for not having to reason about a stale/broken persistent session.
- **`hw_lock` scope.** The mutex guard is held for the entire handler body (`_guard = state.hw_lock.lock().await`), so a `/flash` in progress blocks a concurrent `/reset` or `/serial-log` from starting, rather than just serializing at the probe-rs call level.
- **Serial log is a fixed-duration capture, not a stream.** `serial::read_log` opens the port, reads in a poll loop with a 200ms per-read timeout until `duration_ms` elapses, then returns the accumulated lines. There's no long-lived streaming/subscription endpoint — each call is a bounded snapshot.
- **Dev-bench port auto-detection matches SEGGER's VID, not a custom one** (`dev_bench.rs`, implementing [embarch-dev-bench/design.md](../embarch-dev-bench/design.md) §3 decision 12). The nRF54L15 SoC has no USB device peripheral, so dev-bench firmware owns no USB descriptor at all — the port Core sees belongs to the DK's on-board J-Link, advertising SEGGER's VID `0x1366`. Detection is therefore: enumerate serial ports, keep the USB ones with that VID, then narrow by product string, J-Link serial number, and USB interface index. The rules, in precedence order:
  - `EMBARCH_DEV_BENCH_PORT` bypasses detection entirely and is honored even if the OS doesn't currently enumerate it — the operator said which port it is, so a missing port is the subsequent open's error to report. Same explicit-env-var-wins shape as `token_store::resolve_token` (§6).
  - **Product string:** substring match, default needle `jlink`, overridable via `EMBARCH_DEV_BENCH_PRODUCT` (empty string = match on VID alone). Both sides are normalized to lowercase alphanumerics first, which is what makes one needle cover Linux's `J-Link`, Windows' `JLink CDC UART Port`, and a standalone probe's `SEGGER J-Link`. A port reporting *no* product string is **not** excluded — an absent descriptor field is unknown, not disproof.
  - **Serial number:** `EMBARCH_DEV_BENCH_SERIAL`, the specific J-Link's serial recorded once at setup. This is what disambiguates two SEGGER-probed boards in the same lab.
  - **Ambiguity:** more than one candidate that all share one serial number (i.e. several VCOM interfaces of a single J-Link, common on Nordic DKs) resolves to the **lowest USB interface index** with a `tracing::warn!` listing the alternatives; `EMBARCH_DEV_BENCH_INTERFACE` overrides. More than one candidate across *different* probes is a `500` listing them rather than a guess.
  - Requires `serialport`'s non-default `usbportinfo-interface` feature for that interface index (Cargo.toml).
  The whole heuristic is a pure function over an already-enumerated port list (`dev_bench::select`), so it's unit-tested against synthesized port lists — no hardware and no environment variables involved. What that can't cover is whether a real nRF54L15DK's J-Link actually exposes more than one VCOM, and whether the lowest interface index is the one wired to the target's UART — see §10.

## 6. Security model

Auth is a single shared secret, `EMBARCH_TOKEN`, checked via exact-string comparison in `auth_middleware` against every request's `Authorization` header. The value itself comes from `token_store::resolve_token()` (called from `main.rs`'s `run()`): an explicit `EMBARCH_TOKEN` env var wins if set; otherwise the machine-wide token file (`token_store.rs`, §8) is reused if present, or generated and persisted on first startup. Full lifecycle (generation, storage, transport, rotation, threat model, known gaps) is documented in [embarch-token.md](../embarch-token.md) rather than here — that includes the no-per-caller-identity limitation. The insecure `dev-token-change-me` fallback this replaced is gone entirely (milestone-2, §11).

## 7. Deployment model

**Confirmed via milestone-1 (2026-07-21):** `embarch-core` runs natively on Windows (built with `cargo build --release` against a native Windows checkout — a `\\wsl$`-mounted source tree was deliberately avoided, per the milestone plan), reachable from a WSL2 guest via the `0.0.0.0` bind at the WSL2 session's dynamic host-gateway IP (`ip route show default` from inside WSL2 — `172.29.64.1` on this machine, expected to change across WSL2 restarts). Windows Firewall did not need an explicit inbound rule: this machine's WSL networking mode is the newer "WSL (Hyper-V firewall)" NAT, whose `Get-NetFirewallHyperVProfile` profiles default to `DefaultInboundAction: NotConfigured` (permissive) rather than the regular Public-profile Windows Firewall (which the host's other network adapters were categorized as, and which would likely have blocked an unsolicited inbound connection). Building natively on Windows required installing Visual Studio Build Tools' "Desktop development with C++" workload for `link.exe` — a bare `rustup`-installed toolchain alone is not sufficient, since only the MSVC target ships without a bundled linker.

**An installed, autostarting OS service is the intended normal deployment, not a foreground `run`.** §3.3's `install`/`uninstall` already provide this on all three OSes; what's new is stating it as the default rather than an option, because it's what makes the rest of the suite need no launcher: if Core is up at boot, then `embarch-api` — which is invoked per-use, either spawned by an MCP client or run directly by a human — always finds a Core already running, and there is nothing for anyone to start. See [embarch-umbrella/design.md](../embarch-umbrella/design.md) §3 decision 3, which is the sub-project that makes sure `install` actually got run. A foreground `run` remains fully supported and is the right choice for debugging Core itself.

**Anticipated move: a LAN-reachable Raspberry Pi.** The `0.0.0.0` default bind and the CLI's cross-platform service install already anticipate this — no code changes should be needed to point Core's HTTP server at a Pi and reach it over the LAN.

**Artifact-transfer gap, shared with embarch-api's design doc §9 — closed for the WSL2-same-PC case, and now closed for a genuinely separate machine too (§3 decision 10, 2026-08-15).** `/flash`'s `firmware_path` is read from Core's own local disk, so a WSL2-built artifact's path is meaningless to a Windows-hosted Core, and a genuinely separate machine (a future Pi deployment) has no shared filesystem at all. The WSL2-same-PC case stays closed exactly as it was, via `embarch-api`'s `artifact_path_for_core` config field sending Core the artifact's `\\wsl.localhost\<distro>\...` UNC form — confirmed working end-to-end during milestone-1 (a real `west`-built `.hex` flashed onto the physical nRF54L15 board via this path), and left alone since it's a validated, zero-copy mechanism for the suite's primary daily-use topology. §3 decision 10 closes the *previously-unsolved* general case instead: `/flash` also accepts a `multipart/form-data` body carrying the firmware bytes directly, used only when Core and the caller genuinely don't share a filesystem (a `remote` topology, `embarch-umbrella/design.md` §4 row v) — the case that, until this decision, had no mechanism at all and couldn't flash.

## 9. Relationship to embarch-api

Core has zero knowledge of embarch-api, MCP, Claude Code, or the concept of a "project" — it only ever sees the endpoints' bare parameters (`chip`, `firmware_path`, `format`, `port`, `baud`, `duration_ms`). Every project-name-to-config mapping, build orchestration, and MCP tool surface lives entirely in `embarch-api` (see `embarch-api/design.md`). The embarch-core CLI is a second, independent caller of the exact same HTTP API used by embarch-api — not a privileged or special code path — which is why `install`/`uninstall` still just point the OS service manager back at the `run` subcommand, on every OS, rather than a dedicated service-mode subcommand. (On Windows specifically, `run` itself now branches internally — §3 decision 3's correction — but that's `run` self-detecting SCM vs. a human at a console, not a second subcommand `install` has to know about.)

## 10. Open questions / future work

- **ESP-IDF UART-bootloader flashing is explicitly out of v1 scope, not a forgotten gap (2026-08-15, closing item 26 of that day's design-improvement review).** probe-rs's `Format::Idf` covers some ESP flashing via USB-JTAG, but the classic UART bootloader path most ESP-IDF workflows use isn't covered, and this suite's real day-one projects (`embarch-api/design.md` §4) are both Zephyr/`west`-based — there is no real ESP-IDF project driving this today. The planned escape hatch, if one is ever needed, stays an `esptool` subprocess fallback in `hardware.rs`; revisit only when a real ESP-IDF project needs flashing, rather than speculatively building it now.
- **`EMBARCH_TOKEN` is a single shared static token, not per-caller credentials.** Tracked as an open question in [embarch-token.md](../embarch-token.md) §8, which is the source of truth for the token's full lifecycle — see §6 above.
- **Dev-bench auto-detection (§5) has never met a real dev-bench.** The heuristic and its ambiguity handling are unit-tested, but two things can only be confirmed against a physical nRF54L15DK: whether its on-board J-Link exposes more than one VCOM interface at all, and — if it does — whether the lowest USB interface index is the one bridged to the target SoC's UART rather than some other CDC function. If the ordering turns out to be the other way round on Windows or Linux, the fix is a changed default in `dev_bench::select`, not a new mechanism (`EMBARCH_DEV_BENCH_INTERFACE` already covers it manually). Also unverified: whether Windows' reported product string for that VCOM actually normalizes to something containing `jlink`.
- **`embarch-core chip-list [filter]` — the human-facing fallback for an unmapped SoC, scoped together with `embarch-api`'s override table rather than separately (2026-08-15, closing item 24, alongside `embarch-api/design.md` §3's new `soc_chip_overrides` decision, item 2).** Core links `probe-rs` as a library (§3.1) and so already holds its target database, but nothing exposes it — a user configuring an override has to `cargo install probe-rs-tools` and run `probe-rs chip list` to find the right string in the first place. New `chip-list [filter]` CLI subcommand: pure enumeration with no hardware access (same posture as `detect-dev-bench`), listing every probe-rs target name matching an optional case-insensitive substring filter. This is the fallback a `soc_chip_overrides` entry's value comes from (`embarch-api/design.md` §3), and `embarch-umbrella`'s `init` can offer it as candidates instead of writing a placeholder ([embarch-umbrella/design.md](../embarch-umbrella/design.md) §10). **Complementary to, not superseded by, §3 decision 8's `/resolve-chip`**: that endpoint covers the automatic common-case mapping for a known Zephyr SoC; this subcommand plus the override table together cover the case it doesn't know about. Not yet implemented in code — this entry records the scoping decision ahead of it, per `DOC-PROTOCOL.md` §5's "recorded ahead of code" pattern already used elsewhere in this doc.
- **The `sc.exe`-installed-Windows-service environment gap (milestone-1 §3.5) has a fix applied in code (milestone-2, §11), and §3 decision 11's new config file (2026-08-15, closing item 27) makes real-hardware validation of it far less urgent, though not fully moot.** A real Windows service install/start is now verified (§3 decision 3's correction) — but that run didn't set an explicit `EMBARCH_TOKEN` at install time, so `install()`'s `winreg`-based `Environment` registry write (only reached when one *is* set) still hasn't actually executed on real Windows hardware. §3 decision 11's config file means the common case (an auto-generated token, §8) never touches this code path at all — only someone who specifically wants an *explicit* (not auto-generated) token on an installed Windows service still needs it validated, which is a narrower and lower-priority case than before this decision existed.
