# embarch-core: design

**Status:** draft, 2026-07-17. Written to document the existing `embarch-core` implementation — the design discussion that produced it happened as a chat, not a durable record; this file is meant to be that durable record going forward. Append changes to the Changelog (§11) rather than silently editing history above it.

## 1. Purpose and scope

`embarch-core` is the OS-level service that owns the debug probe (flash/reset), the serial console log, and (since Milestone 2) the `embarch-dev-bench` serial link. It is deliberately the lowest layer in EmbArch: it has no idea the EmbArch API or Claude Code exist. It exposes a bearer-token-authed HTTP API (§4) and holds the hardware connections so nothing else has to fight over a USB port.

embarch-core is **not**:
- Aware of "projects," toolchains, or build commands. It takes a bare `chip` / `firmware_path` / `format` per call — the concept of a named project with its own build config lives entirely in `embarch-api`.
- A build system. It flashes whatever file it's given; it never invokes `west`, `arduino-cli`, or anything else.
- Multi-tenant. It's one process, one hardware connection, one shared token, matching the single-engineer scope of the whole EmbArch stack (see `embarch-api/design.md` §3.1).

## 2. Architecture overview

```
embarch-api --HTTP+Bearer--> embarch-core --probe-rs/serialport--> hardware
                                    ^  |
                                    |  +--serial (UART/USB CDC, COBS-framed postcard)--> embarch-dev-bench firmware
                                    |                                                    (BLE central/peripheral + power sampling)
                         embarch-core CLI (same machine)
```

`embarch-core` is reached two ways: over HTTP by `embarch-api` (the normal Claude-Code-driven path), and directly via its own CLI (`main.rs`'s `run`/`install`/`uninstall`/`start`/`stop`/`detect-dev-bench`/`logs` subcommands) for local operation and service management. Both paths converge on the same `hardware`/`serial`/`dev_bench` modules and the same `hw_lock` — there is no separate code path for "CLI mode." `detect-dev-bench` is the second front-end for `GET /dev-bench/port` specifically (§4, §5), keeping that capability reachable by a human with no HTTP client and no running service, per `embarch.md` §5's both-front-ends principle.

**Implemented and live-validated (Milestone 2, 2026-08-19/20):** the second hardware relationship, bridging `/study*`/`/dev-bench/hello` HTTP calls from `embarch-api`/`embarch-umbrella` to `embarch-dev-bench` over a second, independent serial link. *Which port dev-bench is on* is answered by `dev_bench.rs` (§5, `GET /dev-bench/port`); opening the port, the `Hello`/`HelloAck` handshake, and relaying a `Study` are `study.rs`/`dev_bench_link.rs` (§8), confirmed against the real ESP32-C5 — see §4's `/study*`/`/dev-bench/hello` rows and [embarch-study-designer/design.md](../embarch-study-designer/design.md) §5, the source of truth for that surface's design.

## 3. Locked-in design decisions and rationale

1. **Language: Rust**, with **probe-rs used as a library, not shelled out to as a CLI.** Calling `probe_rs::flashing`/`probe_rs::probe` directly (rather than spawning a `probe-rs` binary) avoids subprocess/parsing overhead and gives typed errors (`anyhow::Context`) instead of scraping CLI output.
2. **HTTP framework: Axum.** Chosen for the same reason `embarch-api` also ended up in Rust (per its design doc) — one toolchain across the whole stack, plus Axum's `State`/middleware model maps cleanly onto the `AppState { token, hw_lock }` shape Core needs.
3. **Cross-platform service install via the `service-manager` crate.** `install`/`uninstall`/`start`/`stop` register, remove, and control the same `run` command as a systemd unit on Linux, a launchd job on macOS, or a Windows Service via `sc.exe` — one code path, OS detection handled entirely inside the crate (`service.rs`'s `manager()`), not hand-rolled per-OS logic. `start`/`stop` exist specifically so `embarch-umbrella` doesn't re-derive per-OS service control in a second codebase ([embarch-umbrella/design.md](../embarch-umbrella/design.md) §3 decisions 4/7). **All four require elevated privileges** — root/polkit for a systemd *system* unit, Administrator for a Windows Service — which is not a Windows-only tax as was previously assumed; confirmed on Linux, where an unprivileged `start` fails with systemd's "Interactive authentication required."

    **Correction, 2026-08-12 ([embarch-umbrella/milestone-6.md](../embarch-umbrella/milestone-6.md) §3.8):** "one code path" was true for *registering* the service, but not for what happens once it's launched. `service-manager` only handles `sc create`/`systemctl enable`/`launchctl load`-style registration; it has no opinion on what the registered binary itself must do once running. systemd (`Type=simple`) and launchd both consider "the process stayed alive" sufficient, so `run()` — a plain foreground server, no different from a human running it at a console — worked as the service body on both. Windows does not: `sc create`-registered binaries must call back into `StartServiceCtrlDispatcherW` promptly and report `SERVICE_RUNNING`, or SCM kills the start attempt after a 30-second timeout (Win32 error 1053, System log 7009/7000) — regardless of whether the process itself is working fine. This had never been caught because no prior testing had installed Core as a real boot service on Windows; every earlier "smoke test" used a throwaway foreground instance. Fixed in `service.rs`'s new `windows`-only module (the `windows-service` crate): `Run` now tries the real SCM handshake first on Windows, falling back to the plain foreground path only when `StartServiceCtrlDispatcherW` fails with `ERROR_FAILED_SERVICE_CONTROLLER_CONNECT` (not launched by SCM at all — a human at a console, same as always). Verified for real: installed and started as an actual Windows service on the daily-use machine, `doctor` all green.

    **Self-elevation, 2026-08-18 (reverses [embarch-umbrella/design.md](../embarch-umbrella/design.md) §3 decision 7's "umbrella never elevates itself" stance — see that decision for the full before/after and the real friction that prompted it).** `install`/`uninstall`/`start`/`stop` (and a planned `update`, below) now self-elevate here, in `service.rs`, rather than failing and telling a human to re-run the same command in a shell they opened themselves. This is the one place that belongs: both a human running `embarch-core install` directly *and* `embarch-umbrella`'s `up`/`down`/`setup` shelling out to this same CLI (decision 3's "one code path" — `embarch-umbrella/design.md` §3 decisions 4/7) hit the identical privilege wall, so elevating here fixes it for both callers at once rather than teaching umbrella a second copy of the same logic.

    Mechanism, per OS, gated to exactly the one privileged subcommand being run — never a standing elevated process, never the whole CLI session:
    - **Windows:** re-launch this same `.exe` with `ShellExecuteW`'s `"runas"` verb, passing through the original subcommand and args; wait for the child to exit and propagate its exit code. Triggers the standard UAC consent dialog once.
    - **Linux:** prefer `pkexec` (polkit's GUI prompt) when a display is present (`$DISPLAY`/`$WAYLAND_DISPLAY` set and `pkexec` on `PATH`) — matches the systemd-system-unit polkit prompt this decision's original text already found unprivileged `start` demanding; fall back to `sudo` (interactive terminal prompt) otherwise.
    - **macOS:** `osascript -e 'do shell script "..." with administrator privileges'`, launchd's equivalent GUI admin prompt; fall back to `sudo` for a headless session (e.g. over SSH, no WindowServer).
    - **No GUI and no TTY (CI, a script, a headless remote session):** none of the above can prompt anyone. Falls back to decision 7's original behavior — print the exact command and exit nonzero — since there's no one there to click through a dialog anyway.

    Re-launching the *same already-running binary* elevated adds no new "trust an unseen artifact" step beyond what decision 7's original text already flagged for `setup` — the human already chose to run this exact binary unprivileged; self-elevation reuses that same trust decision instead of asking them to separately open an elevated shell and retype/paste a command by hand (which was also a transcription-error opportunity this removes). A declined prompt (UAC "No", polkit/`sudo` cancelled) surfaces as a clear "elevation declined" error, not a silent hang.

    **Motivating case:** this was prompted by a real gap, not a hypothetical one — updating an already-installed Core's binary (e.g. deploying a newer build with a bugfix or a new endpoint) had no supported path at all, degrading to manual `Stop-Service`/copy/`Start-Service` surgery in an elevated shell opened by hand (found live, 2026-08-18, deploying `/resolve-chip` — §8 below — to the real Windows machine ahead of `embarch-api/milestone-7.md`).

    **Implemented and validated live the same day.** New `elevate.rs`: `is_elevated()` (Windows: `OpenProcessToken`/`GetTokenInformation(TokenElevation)`; Unix: `geteuid() == 0`), and `ensure_elevated_or_fallback()`, called at the top of `install`/`uninstall`/`start`/`stop`/`update` in `service.rs`. Windows re-launches via `ShellExecuteExW`'s `"runas"` verb (`windows-sys`, new direct dependency), waits on the returned process handle, propagates its exit code; `ERROR_CANCELLED` (1223) is reported as a clear "elevation declined" error rather than a generic failure. Linux/macOS paths (`pkexec`→`sudo`, `osascript`→`sudo`) are written but unexercised — this machine is Windows, and macOS stays reasoned-only per this suite's standing posture (§10). New `update <new-exe-path>` subcommand: stops the service (best-effort), renames the current binary aside (Windows won't allow overwriting a running process's own image file in place — this is the standard self-update idiom, and works identically on Unix even though not strictly required there), copies the new one into place, starts the service, and rolls back to the renamed-aside original if the new binary fails to start.

    **Live validation, real machine, ahead of `embarch-api/milestone-7.md`:** from a non-elevated shell, `embarch-core.exe stop` (self-elevated, no manual UAC step) actually stopped the running service — confirmed via `Get-Service`, not just the CLI's own exit code — and `start` afterward actually started it again on the newly-deployed binary. `cargo build`/`cargo clippy --all-targets -- -D warnings`/`cargo test` (15 tests) clean on both Linux (dev machine) and the real Windows target.
4. **A single `hw_lock: Arc<Mutex<()>>` serializes all hardware access.** `/flash`, `/reset`, and `/serial-log` each acquire it for the duration of the call. This is what actually enforces "nothing else has to fight over the USB port" — without it, a CLI-triggered flash and an HTTP-triggered reset could race on the same probe.
5. **Bearer-token auth via Axum middleware, not "trust the local port."** Core may end up reachable over a real network (WSL2-to-Windows today, or a LAN if Core moves to a Pi — see §7), so an unauthenticated HTTP surface isn't acceptable even at single-engineer scale. The check is a plain exact-string compare against `EMBARCH_TOKEN` (`auth_middleware` in `api.rs`) — deliberately not OAuth or anything session-based, matching the single-user scope.
6. **Default bind address `0.0.0.0`, not `127.0.0.1`.** This is deliberate, not an oversight (`main.rs`'s CLI help text says so explicitly): the point of Core is to be reachable from WSL2 if Core runs native on Windows, or from the LAN if Core later moves to a Raspberry Pi. `--bind`/`--port` remain overridable.

    **Amendment, 2026-08-15 (item 17 of that day's design-improvement review — see `.claude/design-improvements-2026-08-15.md`, local working notes): reversed to default `127.0.0.1`, widened explicitly rather than by default.** The review's point stands on its own merits, independent of any incident: `0.0.0.0` + no TLS (§6 below) + a static bearer token + `/flash` reading an arbitrary local path, in a process that may run as `LocalSystem` on Windows, is a security posture nobody had actually assessed as a whole — each piece was individually documented, never composed. `0.0.0.0` was also broader than any topology in `embarch-umbrella/design.md` §4 actually needs: topologies i/ii/iv (Core and API on the same machine, no WSL2 split) only ever need loopback, and only topology iii (WSL2⟷Windows) needs the WSL2 gateway address reachable, which is narrower than every interface. Resolved: Core's own default (no `--bind` given) is now `127.0.0.1`. Widening it is `embarch-umbrella`'s job at `setup` time (`embarch-umbrella/design.md` §3 decision 3), not Core's own default — `setup` detects topology iii and passes `--bind 0.0.0.0` (or, once available, the specific WSL2 gateway address) only when that topology is actually what it found, via the same install/service-registration step that already configures the token and PATH. A foreground `run` with no `--bind` still binds loopback-only, matching the new default. This is a breaking behavior change for anyone who was relying on the old default without an explicit `--bind` — called out in the changelog (§11) for exactly that reason.

    **Actually implemented 2026-08-24, nine days after being recorded design-only, and only once `embarch-topology/milestone-1.md` item 6 asked for the `embarch-umbrella setup` wiring this amendment always depended on.** Two real gaps found closing it, both worse than "no code yet": (1) `main.rs`'s `Run { bind }` had never actually been changed off the old `0.0.0.0` default — the amendment was recorded here but never landed in code. (2) Far more load-bearing: `service::windows::run_service` (the actual code path the live Windows Core runs under, since SCM dispatch bypasses `Command::Run`'s own parsed `bind`/`port` entirely) **hardcoded `"0.0.0.0"` directly**, discarding whatever `--bind` a service was ever registered with — every Windows deployment of this crate has been unconditionally wide-open on every interface regardless of any CLI flag, since before this decision was even written. Fixed: `Run`'s and the new `Install { bind }`'s default is now genuinely `127.0.0.1` (`DEFAULT_BIND`); `service::install` bakes `--bind <addr>` into the service's registered start command; `service::windows::try_dispatch(bind, port)` stashes those already-parsed values in a `OnceLock` (the only way around `define_windows_service!`'s fixed `service_main` signature) for `run_service` to actually read, replacing the hardcode. `embarch-umbrella/design.md` §3 decision 3's own `setup` half is wired in the same pass — see that doc's changelog. Verified live: the real Windows Core was uninstalled, rebuilt, and reinstalled with `install --bind 0.0.0.0` (matching what its actual WSL2⟷Windows topology needs, via `recommended_bind_address`), confirmed via `sc qc` showing `run --bind 0.0.0.0` in the registered `BINARY_PATH_NAME`, and `GET /status`/`GET /enroll` reachable from WSL2 afterward exactly as before — same effective address, now actually wired instead of coincidentally hardcoded.
7. **Blocking hardware calls always run through `tokio::task::spawn_blocking`.** `probe-rs` and `serialport` are synchronous APIs; every handler in `api.rs` wraps its hardware call in `spawn_blocking` so a slow flash or a serial read with a multi-second `duration_ms` never stalls the Tokio runtime's async executor.
8. **A Zephyr-SoC-name→probe-rs-chip mapping lives here, resolved via a new endpoint, not duplicated as a table in `embarch-api`.** *(Decided 2026-08-13, shipped 2026-08-14. Full context: `embarch-api/design.md` §3 decision 12's open question on where this table should live.)* `embarch-api` needs to turn a Zephyr SoC name (e.g. `nrf54l15`, from a `discovery = "zephyr-west"` project's live board scan) into a probe-rs chip target string (`nRF54L15`) before calling `/flash`/`/reset` — and it's about to call one of those anyway, so resolving it via a call here costs nothing extra and keeps exactly one copy of the mapping, in the one process that actually links `probe-rs` and can therefore validate a mapped name against the real target database rather than trusting a hardcoded string. New endpoint: `POST /resolve-chip`, body `{"soc": "nrf54l15"}` → `{"chip": "nRF54L15"}` on a known mapping, or a `404` (plain text, same convention as `/dev-bench/port`) naming the unmapped SoC when there is no entry — `embarch-api`'s existing unmapped-SoC fallback (point at `probe-rs chip list`) is unchanged for that case. Complements, rather than replaces, §10's open `chip-list` item: `resolve-chip` is the automatic common-case path, `chip-list` remains the human-facing fallback when a SoC has no mapping yet.

    **Implemented as `chip_resolve.rs`** (§8): a small `SOC_TO_CHIP` table covering this suite's real Nordic hardware family (nRF51/52/53/91/54L series), matched case-insensitively and exactly (no prefix/fuzzy matching — a plausible-but-wrong match here would silently pick the wrong physical target). The mapped candidate is then looked up in `probe_rs::config::Registry::from_builtin_families()` before being returned, so a table entry that's gone stale against a future probe-rs version fails exactly like an unmapped SoC rather than succeeding here and only failing later, confusingly, at `/flash`. A unit test (`every_table_entry_resolves_against_the_real_registry`) checks every table entry against the real registry so drift fails a test run, not a live call. Smoke-tested live against a running Core: `nrf54l15`/`NRF54L15` both resolve to `nRF54L15`, an unmapped SoC (`esp32c3`) 404s naming the SoC, and the route still enforces bearer-token auth like every other endpoint. `cargo build`/`cargo clippy --all-targets -- -D warnings`/`cargo test` (4 new unit tests) clean.

9. **`open_first_probe()` grows a serial-number selector — decided ahead of dev-bench hardware existing, per §5's own open item.** Closes item 8 of the 2026-08-15 design-improvement review: dev-bench itself *is* a second debug probe (the DK's on-board J-Link, §5), so the moment dev-bench exists, "more than one probe attached" stops being the edge case §10 used to defer and becomes the normal state on any machine running both a DUT probe and a dev-bench. `/flash`/`/reset` gain an optional `probe_serial: Option<String>` body field, matched against `ProbeInfo.serial_number` (already surfaced via `/status`); omitted, behavior is unchanged — `open_first_probe()` as today, correct for the common single-probe case. More than one probe present with `probe_serial` omitted now returns a named error listing every candidate's serial number, rather than silently picking one — a wrong-target flash is a worse failure mode than a loud one (returned as a `500` via the existing generic `internal_err` path, same as any other `hardware::flash`/`reset` failure — not the `400` this bullet originally said, since the ambiguity is only discoverable once `hardware::open_probe` actually calls `Lister::list_all()`, not at the request-validation layer `base_address` parsing uses for its own `400`s). `embarch-api`'s config schema gains a matching optional `probe_serial` per-project field (`embarch-api/design.md` §4), passed through unchanged.

    **Real design/code drift found and closed, Milestone 3 (Study Designer: Feature-Branch Iteration), 2026-08-20 — this decision, and §5's own bullet below, had both described this as already implemented; the actual `hardware.rs` still only had the original single-probe `open_first_probe()`, doc comment and all, unchanged since before this decision was written.** Surfaced for real, not found by inspection: the first time this milestone's dev-bench-flashing pipeline (`embarch-api/design.md`'s own new decision) actually ran with both a DUT's J-Link and dev-bench's ESP JTAG probe attached simultaneously, flashing genuinely picked the wrong one and failed with a real probe-rs attach error (`interface Jtag must be selected for this operation (currently using interface Swd)`) — exactly the failure mode this decision was written to prevent, on the first real occasion two probes existed at once. Closed for real now: `open_first_probe` renamed `open_probe(probe_serial: Option<&str>)`, `hardware::flash`/`hardware::reset` both gained the parameter, and `api.rs`'s `FlashRequest`/`FlashArgs`/`ResetRequest` (JSON and multipart bodies both) thread it through. `cargo build`/`cargo test`/`cargo clippy --all-targets -- -D warnings` clean on the native `x86_64-unknown-linux-gnu` target — Core's actual deployment target is Windows (§1), which this environment cannot cross-compile for (no MSVC/Windows-SDK headers available; confirmed by trying, not assumed), so the fix is verified on Linux and awaits a Windows-side rebuild+restart before it's live against real hardware. A second, incidental finding the same session: `study.rs`'s own `finish_job` test triggers the already-tracked `embarch-study-designer/design.md` §7 debug-build stack-overflow risk for the first time inside embarch-core specifically (not just embarch-api, where it was first found) — `StepResult` growing to carry `gatt_services`/`gatt_activity` (that crate's decisions 31/32) pushed it over a default test-thread stack; passes with `RUST_MIN_STACK` raised, same already-accepted debug-build-only posture, no code fix attempted here (that crate's own §7 item, not reopened).
10. **`/flash` accepts a multipart file upload as an alternative to `firmware_path`, closing the artifact-transfer gap for a genuinely separate machine.** Item 9 of the review, tracked previously as an open gap in three docs (`embarch-api/design.md` §9, this doc's own §7, `embarch-umbrella/design.md` §3 decision 8): `firmware_path` only ever worked when the caller and Core share a filesystem (same machine, or the WSL2-same-PC UNC-path special case). `POST /flash` now accepts **either** its existing JSON body (`firmware_path`, unchanged, still the right choice when Core and the caller do share a filesystem — no need to re-upload bytes that are already locally readable) **or** a `multipart/form-data` body carrying the firmware bytes directly plus the same `chip`/`format` fields, written to a temp file under Core's own data directory before flashing and deleted after. `embarch-api` prefers multipart only for a `remote` Core (`embarch-umbrella/design.md` §3 decision 6's topology classes) — the one class with no working transfer mechanism at all today; `local` and `wsl-host` keep using `firmware_path` (via `artifact_path_for_core`'s existing UNC translation for `wsl-host`), since that's already a validated, zero-copy path on real hardware (milestone-1) and multipart would only add the cost of re-uploading bytes for no benefit there. This closes topology v's "flash doesn't work at all" gap without touching the mechanism the suite's primary daily-use topology (iii) already depends on — `artifact_path_for_core`, `wsl_unc_path`, and `doctor` check 9 stay exactly as they are for that case, not retired.
11. **Core gains an optional config file, next to the machine-wide token file — an explicit env var still wins.** Item 10 of the review: every Core knob today (`EMBARCH_TOKEN`, `EMBARCH_DEV_BENCH_PORT`/`_PRODUCT`/`_SERIAL`/`_INTERFACE`, `--bind`/`--port`) is env-var-only, and passing environment to an installed OS service is exactly the class of bug that already cost this suite a real debugging session (§3 decision 3's correction, the `sc.exe` registry gap). A config file sidesteps that class of bug permanently, the same way the token file already does for `EMBARCH_TOKEN` specifically (§8): `%ProgramData%\embarch\core.toml` / `/var/lib/embarch/core.toml`, read once at `run()` startup, holding the same knobs the env vars cover today (`bind`, `port`, `dev_bench_port`/`dev_bench_product`/`dev_bench_serial`/`dev_bench_interface`). Precedence, matching `token_store`'s existing explicit-wins pattern (§6): an explicit env var or CLI flag still overrides the config file value; the config file overrides Core's built-in defaults; nothing set falls through to today's defaults unchanged. Written by `embarch-umbrella`'s `setup` (§3 decision 3's amendment above is the first real consumer — the resolved `--bind` value for topology iii lands here rather than needing to be re-derived from the environment on every service start), not hand-edited as the common case, though nothing stops a human from writing it directly. `install`/`start` no longer need `service-manager`'s `environment` passthrough for anything this file now covers — narrowing, not eliminating, §10's still-open Windows-registry-write validation item (only an explicit `EMBARCH_TOKEN` override still needs it, per that item's own text).

    **Narrowed 2026-08-21 — still design-only (the `core_config.rs`/`core.toml` this decision describes was never actually written; §8's module layout corrected to say so), and now scoped to `bind`/`port` only.** `embarch-topology/design.md` §3 decision 9 abandons the four `dev_bench_*` knobs outright, not just their env-var form — there is no config-file equivalent for them either, by the same reasoning (a config-file override left stale is exactly as capable of silently winning over reality as an env var left stale; enrollment, not any override mechanism, is the intended fix). If `core.toml` is ever actually implemented, `bind`/`port` are the only fields left for it to hold.
12. **A stable `{code, message, cause}` JSON error body replaces the plain-text `anyhow` chain on every non-2xx response.** Item 11: today's handler errors are `(StatusCode::INTERNAL_SERVER_ERROR, String)`, rendered as **plain text** (§4) — fine for a human reading a CLI error, but `embarch-umbrella`'s `doctor --json` and a future UI (`embarch-umbrella/design.md` §10) both need to branch on error *kind*, not just prose. New shape, still non-2xx (status codes unchanged): `{"code": "probe_not_found" | "chip_unmapped" | "flash_failed" | "auth_failed" | "study_conflict" | ..., "message": "<one-line summary>", "cause": "<full anyhow chain, {e:?}, unchanged from today>"}` — `code` is a small, append-only enum stringified for JSON, `message` is fit for direct display, `cause` preserves everything §4/§11's earlier "don't lose the causal chain" fix already established. `embarch-api`'s `--json` output gains a matching `error_kind` field, populated from `code` when the failure came from Core, or a small `embarch-api`-native equivalent (`config_error`, `build_failed`, `core_unreachable`) for failures that never reach Core at all. This also retires `embarch-api/design.md` §12's deferred "CLI exit-code granularity" item — a script that needs to branch on failure kind now has `error_kind` in `--json` rather than needing a finer-grained exit code.
13. **`/status` gains `core_version: String` and `contract_version: u32`, giving `embarch-api` a version handshake beyond the study-schema check it already has.** Item 13: today's only version check across the API↔Core boundary is `study_designer_schema_version` (§3 decision 8's neighbor via `/status`, `embarch-study-designer/design.md` §3 decision 12) — there's no way for `embarch-api` to notice it's talking to a Core built from a materially different `api.rs` contract (a renamed field, a changed error shape) until a call actually breaks. `core_version` is Core's own `CARGO_PKG_VERSION` (already wired to `--version`, §11's 2026-08-05 entry); `contract_version` is a small integer bumped by hand only when a *wire-visible* HTTP contract change happens (a field renamed/removed, a status code's meaning changed) — independent of `core_version`'s semver, matching the same "bump only when the wire shape changes" discipline `STUDY_DESIGNER_SCHEMA_VERSION` already established. `embarch-api` compares its own compiled-in `EXPECTED_CORE_CONTRACT_VERSION` against `/status`'s value and warns (not refuses, matching `embarch-umbrella/design.md` §3 decision 14's existing warn-not-refuse posture for version skew) on mismatch. `embarch-umbrella`'s manifest-version comparison (`doctor` check 1) is unaffected — this is the API↔Core contract specifically, not the release-archive bundling check.
14. **`hw_lock` contention now returns a `503` "busy" response instead of blocking the caller until `flash_timeout_secs` elapses client-side.** Item 19: with per-repo `embarch-api` configs (§3 decision 12 there), two `embarch-api` processes hitting one Core is a normal occurrence, not a bug — but today the second caller just blocks silently on the mutex until its own client-side timeout gives up, indistinguishable from Core being genuinely unresponsive. `/flash`/`/reset`/`/serial-log` now attempt `hw_lock.try_lock()` first; on contention, they return `503` immediately with a body naming which operation currently holds the lock (tracked via a small `Mutex<Option<&'static str>>` alongside `hw_lock` itself, set/cleared by whichever handler holds the guard) rather than queuing. `embarch-api` surfaces a `503` as a distinct, retryable "Core busy" error (via §12's new `code`) rather than the generic timeout text it reports today.

21. **`flash`/`reset` attach via plain `Probe::attach`, not `attach_under_reset` — tried, found unsafe, reverted; `reset` gains a best-effort hardware reset pulse instead, targeting the real failure it was actually chasing (2026-08-20, Milestone 3, Study Designer: Feature-Branch Iteration).** Real hardware scare, not a hypothetical: the reference-dut DUT needed a manual `west flash --recover` after this milestone's first real flash of a new branch, and dev-bench's native USB-JTAG/serial port stopped answering the app's serial protocol correctly after repeated flash/reset cycles — both looking, at first, like hardware got corrupted. Root-caused instead (two independent, real, well-documented `probe-rs`/target quirks, not firmware corruption): a target that's run long enough to reach a low-power sleep state can stop responding to a *plain* SWD attach at all (the debug port itself goes quiet); separately, the ESP32-C5's on-chip USB-Serial/JTAG peripheral's reset only resets the *core* (what `Core::reset` already did, and still does) without re-sampling the chip's boot-strapping pins, so it can stay latched in ROM download mode across a reset instead of returning to normal SPI boot — fully explaining this milestone's earlier `HelloAck` decode failures too (a chip stuck in its ROM bootloader was never running the app's protocol at all, no framing bug required). First attempted fix, `Probe::attach_under_reset` on both `flash` and `reset`, made things worse, not better: it broke attach entirely against the real DUT with a clean, immediate `Timeout while attaching to target under reset` — `attach_under_reset` needs the target's physical reset pin wired to the debug connector, which this DUT's board doesn't do (confirmed by the DUT being genuinely connected, powered, and otherwise reachable at the time). Reverted both functions back to plain `attach`, and instead added a narrower, targeted fix to `reset` only: before attaching, it now calls `Probe::target_reset()` — a genuine hardware reset pulse via the probe's own reset line, distinct from the software/debug-register reset `Core::reset` performs — best-effort: a probe/board without a wired reset pin (the same DUT, again) returns a clean `NotImplemented`/`CommandNotSupportedByProbe`, treated as a no-op rather than a failure, falling straight through to today's unchanged `Core::reset()` behavior. `flash` itself was never actually the failing step (every flash this milestone reported real success) so it needed no reset-strategy change at all, only the `attach_under_reset` revert. Code-complete, built/tested/`clippy`-clean on Linux, deployed to the live Windows service — **not yet live-validated against real dev-bench hardware**, paused mid-verification once the deeper vulnerability decision 22 records was recognized: even a correct attach/reset strategy does nothing to confirm the probe answering to a given `probe_serial` is still wired to the board that serial is *labeled* as.

    **Logging added, re-run, root cause found for real — `target_reset()`'s `NotImplemented` was never about wiring; it's `espusbjtag` not implementing it at all, and the real fallback surfaces a second, more serious real-hardware problem (2026-08-21).** With per-branch logging in place, the exact same reset showed `target_reset()` hitting the quiet no-op branch — and reading `probe-rs` 0.31.0's own `espusbjtag` driver source explains why: `target_reset()` there is a hardcoded `Err(NotImplemented)`, unconditionally, regardless of any wiring — but the same driver's lower-level `target_reset_assert`/`target_reset_deassert` genuinely call `self.protocol.set_reset(..)`, a real signal.     **Resolved for real, 2026-08-21 — the actual fix was never a DTR/RTS root cause at all: a web search of Espressif's own troubleshooting docs settled the mechanism, and the real unblock was moving dev-bench's link off this peripheral entirely.** Espressif's own docs confirm this decision's original diagnosis almost verbatim: "the USB-Serial/JTAG peripheral can only trigger a core reset, which does not re-sample the boot strapping pin," and their own documented fix is `--after watchdog-reset` — deliberately arming the RTC watchdog to fire immediately, a genuine full-system reset, "a hack (hijacking the RTC WDT)." Neither `Core::reset()` nor this decision's own `target_reset`/`reset_via_assert_deassert` pulse is that — both are core-level resets, so neither was ever going to fully clear the symptom on this peripheral.     **What actually closed the loop, in order, once the link moved to that second port:** (1) the CP2102N USB-UART bridge chip needed its Windows driver installed (`CM_PROB_FAILED_INSTALL` until then — Windows has no inbox driver for it, unlike native USB CDC-ACM); (2) `board_gate::enforce_for_serial` structurally couldn't enroll the bridge chip's own serial (no JTAG capability at all), fixed by the new role-based `enforce_for_role` (decision 22's own update); (3) the board's core had been sitting halted since its last `flash` (flashing halts, it never resumes on its own — a `reset_dev_bench` call was the missing step, not a code bug); (4) once all three were addressed, a real self-test `Study` completed end to end for the first time against the new link — `HelloAck` (`firmware_version dc4cc079-dirty`, `compatible: true`) → `StepResult`(Pass)×2 → `StudyDone{completed:true}` — confirmed both via Core's own log and a direct `GET /study/{id}` call. This decision's `target_reset`/`reset_via_assert_deassert` fix (above) remains real and live-confirmed to fire a genuine pulse — it's just no longer the thing standing between dev-bench and a working link, since the link isn't on this peripheral anymore. `dev_bench.rs`'s own detection heuristic needed a matching update — see `embarch-core/design.md` §5's own text and `dev_bench.rs`'s module doc comment for the new `SILABS_VID` recognition and why `ESPRESSIF_VID` was removed as a link candidate entirely.

22. **A new probe/board identity-verification gate — closing a real vulnerability found investigating decision 21's hardware scare, Milestone 3, 2026-08-20.** `probe_serial` (decision 9) reliably disambiguates *which probe* a call means — confirmed working, repeatedly, this session — but it does nothing to confirm the probe answering to that serial is still physically wired to the board its config entry *labels* it as. That label is, and can only ever be, a human's one-time act of physically isolating a board and noting its probe's serial — nothing in a USB descriptor says "I'm wired to the DUT," and no software, including Core itself, can independently re-derive that association. The label can go stale (a probe moved to a different board during rework, a serial mistyped once and never touched again) with nothing today to notice — a live, real risk once two boards share a chip family (`embarch-dev-bench/design.md`'s own ESP32-C5-is-interim decision plans an eventual nRF54L15DK dev-bench, identical in family to this exact DUT), since `probe.attach(chip, ...)` structurally can't catch a same-family mismatch the way it can catch attaching as the wrong architecture entirely.
    - **A new machine-local table, `known_boards.toml`, next to Core's existing token file (§8's `token_store` convention: `%ProgramData%\embarch\known_boards.toml` / `/var/lib/embarch/known_boards.toml`)** — one entry per `{probe_serial, role, chip, hardware_id, confirmed_at_utc_ms}` (`known_boards.rs`; `confirmed_at` is UTC milliseconds since the epoch, not an RFC 3339 string — `study.rs`'s own `current_utc_ms()` convention, reused rather than pulling in a date-formatting dependency for a value nothing needs to parse back). `hardware_id` is the target chip's own factory-burned unique ID (`hardware_id.rs`: Nordic `FICR.DEVICEID`/`FICR.INFO.DEVICEID`, Espressif's eFuse-derived MAC — one readback implementation per chip family, `chip_resolve.rs`'s same families), read live over the debug port — independent of which probe or cable answers, so it survives a probe getting physically moved to a different board in a way a bare serial number can't.
    - **A new `POST /probes/enroll { role, chip }`, the only sanctioned way to populate or update an entry.** Lists currently-attached probes; anything other than exactly one is a hard refusal naming every candidate (never a guess) — this is the enforcement point behind "plug in only the board you mean, then confirm," turning a human's physically-scoped act into the one thing that can ever create or change this table, exactly as decision 9's own probe-selection philosophy already insists on for ambiguity generally. On exactly one candidate: attaches as `chip`, reads its live `hardware_id`, writes the entry, returns what got recorded.
    - **`flash`/`reset` (and `POST /study`'s dev-bench handshake) gain a precondition, run after `open_probe` resolves an actual probe (so it applies even when the caller passed no `probe_serial` at all): look up that probe's serial in `known_boards`.** Not found → hard refusal ("unrecognized probe, enroll it first"). Found → read the live `hardware_id` and compare to the recorded value; mismatch → hard refusal naming both values ("recorded as `<role>` with hardware ID `A`, but the attached chip reports `B` — enroll it again if this is a deliberate change"). Only a clean match proceeds. Fails closed in both branches — an unenrolled or now-mismatched probe blocks the operation entirely, never a guess, matching every other ambiguity-handling precedent in this doc (§5's dev-bench detection, decision 9's probe selection).
    - **Considered and rejected: a live interactive popup at flash-time instead of a pre-populated table.** Core is a Windows/systemd/launchd *service* (§3 decision 3) — a service can't paint UI on the interactive desktop (Session-0 isolation on Windows; the equivalent `LaunchDaemon`-vs-`LaunchAgent` split on macOS) without a second, always-running, per-OS-autostarted helper process and an IPC protocol to talk to it, none of which exists today, and Linux tray/notification support is itself inconsistent across desktop environments (GNOME needs a separate extension) — real, ongoing surface for a problem the `known_boards` table already solves as a plain, inspectable local file. It also degrades correctly for a headless Core (§7's anticipated Raspberry Pi move, where no interactive desktop session exists at all to paint a popup on in the first place) — fails closed exactly the same way, rather than needing a second, headless-specific confirmation mechanism.
    - **Considered and complementary, not a substitute: cross-checking a firmware artifact's own declared build target against the resolved project.** Would catch "picked the wrong artifact path," a real but different failure mode — it doesn't verify the *physical chip*, and a build's own self-declared target is exactly as capable of being stale as the config this whole decision exists to stop trusting blindly. Not adopted as part of this decision; nothing stops it being layered on later.
    - **Deliberately not delegated to embarch-api or the `Study` schema.** This is genuinely Core-local knowledge — which physical probe is wired to which physical board, on this one machine — not a build-artifact concern (`embarch-api`'s config, §9) or something a portable `Study` schema should ever carry (`embarch-study-designer/design.md`'s own portability goals; `run_study` deliberately has no `project` param today for the same reason, §4). `embarch-api/design.md` decision 34 wraps `POST /probes/enroll` as `enroll_probe`/`enroll-probe` on its MCP/CLI surfaces, matching every other Core capability's two-layer wrapping — but the knowledge itself, and the gate that enforces it, live here.
    - **Implemented 2026-08-20.** New modules: `known_boards.rs` (the TOML table — load/find/upsert, next to `token_store.rs`'s file), `hardware_id.rs` (the per-chip-family readback), `board_gate.rs` (`enforce`/`enforce_for_serial`/`enroll` — the actual gate and `POST /probes/enroll`'s implementation). `hardware.rs`'s probe-selection logic (decision 9) was factored out into a new `pub(crate) resolve_probe`, shared by `open_probe` *and* `board_gate` rather than copied a second time — the exact kind of drift that let decision 9's own selector go unimplemented as long as it did is the reason this one's written to share, not duplicate, that logic. `flash`/`reset` both call `board_gate::enforce` before their own attach; `study.rs`'s dev-bench handshake (`hello_handler`/`post_study_handler`) calls `board_gate::enforce_for_serial` keyed on the USB serial number `dev_bench::detect()` already reads off the same physical connection, since that path never calls `open_probe` at all. `cargo build`/`cargo test` (54 passed)/`cargo clippy --all-targets -- -D warnings` clean on Linux. **Not yet deployed to the live Windows Core, and not yet live-validated against either real board** — in particular, `hardware_id.rs`'s nRF54L15 address (`FICR.INFO.DEVICEID` at `0xFFC304`/`0xFFC308`) is sourced from a real user's DevZone report reading that address successfully, not independently confirmed against this suite's own DUT; see that file's own doc comment for exactly what the resumed hardware validation needs to check first, and how a wrong-but-stable address would (and wouldn't) surface.

    - **Gained `board_gate::enforce_for_role`, 2026-08-21 — a structural gap found the moment dev-bench's link and its debug probe stopped being the same physical USB device.** `enforce_for_serial`'s whole mechanism assumed the dev-bench link's own USB serial number *is* a JTAG-probe serial (true only when the link and the debug probe are the same physical connection — the ESP32-C5's native USB-Serial/JTAG peripheral, before `embarch-dev-bench/design.md` decision 26's 2026-08-21 move to a second, dedicated USB-UART bridge chip). A plain UART bridge chip has no JTAG/SWD capability at all, so it can never appear as a `POST /probes/enroll` candidate (`hardware::resolve_probe`'s enumeration only ever sees real debug probes) and its own serial can never be a `known_boards` key — calling `enforce_for_serial` with it always failed with "not enrolled," a structural dead end, not a missing enrollment step. New `enforce_for_role(role: &str)` looks up the already-enrolled board by `known_boards` role instead of by the link's own serial, and re-verifies identity over that entry's own recorded JTAG-probe connection — the wire carrying `DevBenchMessage` traffic and the wire identity gets confirmed over no longer need to be the same one, as long as both reach the same physical chip. `study.rs`'s dev-bench handshake (`hello_handler`/`post_study_handler`) now calls `enforce_for_role(dev_bench::KNOWN_BOARDS_DEV_BENCH_ROLE)` unconditionally rather than threading the detected port's own serial number through at all. Both functions now share a `verify_known_board` helper for the actual attach/readback/compare logic, avoiding a second copy of it. `cargo build`/`cargo test` (63 passed)/`cargo clippy --all-targets -- -D warnings` clean on Linux; **live-validated on the real Windows service** the same day — see decision 21's own update for the full end-to-end self-test this unblocked.

    - **Moved out of this crate entirely into `embarch-topology`, 2026-08-21 (same day, later) — this decision's own text above is kept as the historical record of how/why the gate was built, but `known_boards.rs`, `hardware_id.rs`, and `board_gate.rs` no longer exist in this repo.** The stale-`EMBARCH_DEV_BENCH_SERIAL` incident that motivated `embarch-topology` (`embarch-topology/design.md` §1) is this exact mechanism's own override path going stale undetected — the fix is a shared crate Core calls live rather than a second copy of this logic anywhere else that could drift. `board_gate::enforce`/`enforce_for_serial`/`enforce_for_role`/`enroll` are now `embarch_topology::hardware::validate_serial`/`validate_role`/`enroll` (`hardware.rs`'s `flash`/`reset` and `study.rs`'s dev-bench handshake call them directly); `known_boards.toml` is now that crate's own `enrollment.toml`, at a crate-owned path under the same `%ProgramData%\embarch` / `/var/lib/embarch` root; `hardware_id.rs`'s per-chip-family readback moved verbatim. New behavior this move added, not just a relocation: mismatches are now durably logged to an alert log and live-pushed to `embarch-topology`'s own UI if one is running, returned as a structured `topology-mismatch` error with a fix-it URL (`embarch-topology/design.md` §3 decisions 8, 12) — Core's callers get this automatically, with no code of their own. `hardware.rs` keeps the hardware-I/O-specific plumbing (`resolve_probe`/`open_probe`, actually opening a probe-rs session) and calls the crate only for "is this still the enrolled board" (`embarch-topology/design.md` §4). `cargo build`/`cargo test` (`RUST_MIN_STACK=67108864`, a pre-existing, documented requirement unrelated to this move — see §10)/`cargo clippy --all-targets -- -D warnings` all clean on Linux against the real crate dependency. **The nRF54L15 `FICR.INFO.DEVICEID` address's live-validation status (§10's own item on this) is now `embarch-topology`'s open question, not this repo's** — nothing about moving the code changed whether that address has been confirmed against real hardware.

23. **Env var overrides for dev-bench port detection (`EMBARCH_DEV_BENCH_PORT`/`_PRODUCT`/`_SERIAL`/`_INTERFACE`) are gone outright, 2026-08-21 — not deprecated, not detected-when-stale, removed.** `embarch-topology/design.md` §3 decision 9: these four were exactly the mechanism behind the incident that motivated `embarch-topology` in the first place (a stale `EMBARCH_DEV_BENCH_SERIAL` registry value surviving a runtime-link port migration undetected, `embarch-topology/design.md` §1). `dev_bench.rs`'s `Filter` (now `embarch_topology::hardware`'s own dev-bench port module) no longer reads any of the four — the only disambiguation signal left is the dev-bench-role enrollment fallback that decision 22 already added, which was always the stronger signal (a live hardware-ID readback at enrollment time) even back when the env var still existed as a second, parallel way to say the same thing. This is a real behavior change for anyone who was relying on one of these four env vars: there is no replacement knob, by design — enroll the board instead (`POST /probes/enroll`, or `embarch-topology enroll --role dev-bench`).

24. **`study.rs` never materializes a full `StudyResult` host-side, in memory or on the stack — every result is written to `events.json` and pushed live the instant it arrives, closing `embarch-study-designer/design.md` §7's stack-overflow finding for good on Core's side, 2026-08-21.** That §7 item, and a from-scratch measurement done while investigating the topology-merge deploy on the live Windows Core (§ below), pinned the actual number down: `StudyResult` is **~1.3 MB** purely from `embarch-study-designer`'s `no_std` worst-case-capacity fields (`heapless::Vec<StepResult, 64>` × `StepResult`'s own `gatt_activity: Option<Vec<GattActivityRecord, 32>>`, each record up to 512 bytes) — reserved unconditionally by the type regardless of how much a given study actually populates. `study.rs` used to (a) accumulate every `StepResult` into a plain `Vec` for the study's whole duration, (b) convert that into a `heapless::Vec<StepResult, 64>`/`StudyResult` only once, at `StudyDone`, and (c) keep that value resident inside `StudyJob` in the in-memory job registry *forever* (no expiry) — and `GET /study/{study_id}` cloned it out by value on every single call. Steps (b) and (c) both reproduced a real `SIGABRT`/stack-overflow, on both Linux and native Windows, in `cargo test`; deserializing back into the same type (attempted while writing a regression test for this fix) overflowed too, confirming it's the *type itself*, not just one code path, that's unsafe to hold host-side.

    Fixed by making `events.json` genuinely incremental, matching the treatment `data.csv`/`waveform.csv` already had (`embarch-study-designer/design.md` §3 decision 20) and the per-step-arrival streaming the wire protocol already does (`embarch-study-designer/design.md` §3 decision 24's own `DevBenchMessage::StepResult` framing, which `study.rs` was receiving correctly all along and simply not carrying through to disk): a new `EventsJsonWriter` opens `events.json.partial` at `StudyStart`, writes one `StepResult` to it — by reference, never the whole `StudyResult` — the instant each `DevBenchMessage::StepResult` arrives, and finalizes (writes empty `validations`, renames to `events.json`) only at a genuine `StudyDone`. An aborted/failed study leaves the `.partial` file behind as a diagnostic artifact rather than a completed result, the same posture decision 16 (`embarch-study-designer/design.md` §3) already established for `data.csv`/`waveform.csv` surviving a crash mid-study. `StudyJob` (the in-memory registry entry) drops its `result` field entirely — it now only ever holds `status`/`current_step`/`total_steps`/`reason`, all small and cheap to clone. `GET /study/{study_id}` (unchanged external shape) fills in `result` by reading `events.json` back off disk as a `serde_json::Value` once `status` is `"completed"`, the same pattern `power_data_handler`/`waveform_data_handler` already use for `data.csv`/`waveform.csv` — never by holding a duplicate copy resident.

    **New: `GET /study/{study_id}/events` (SSE), a live-push companion to polling.** Every `StepCompleted`/`SampleBatch`/`StatusChanged` is broadcast the instant Core processes it — a step result, a decoded power/waveform sample batch, or the job's own status changing — over one process-wide `tokio::sync::broadcast` channel (`AppState::study_events`; one channel is enough since `StudyLock` never lets two studies run concurrently), filtered server-side to the `study_id` in the URL. Mirrors `embarch-topology`'s own durable-log-plus-live-push shape (`embarch-topology/design.md` §3 decision 12) applied to study progress instead of a topology mismatch. A slow subscriber gets an explicit `event: lagged` frame rather than silently missing messages. This is a real, deliberate reversal of `embarch-study-designer/design.md` §3 decision 9's original "reports progress/result via polling" framing — polling still works (`GET /study/{study_id}`), but nothing about a result is held back until the study finishes any more, at any layer, all the way out to whoever's watching. `embarch-api`/CLI consumption of this new endpoint is **not yet built** — tracked as open work, not silently assumed.

    `StudyEvent::StepCompleted`'s own `StepResult` field is `Box`ed — `clippy::large_enum_variant` caught it immediately (a single `StepResult` is tens of KB, dwarfing the enum's other variants) even though a lone `StepResult` was never the stack-overflow risk decision 24 exists to fix; boxing it here is about keeping `StudyEvent` cheap to move/clone through the broadcast channel, not a second instance of the same bug.

26. **`flash`/`reset` diagnose an unpowered target before attaching, instead of surfacing `probe-rs`'s raw ARM/access-port error chain, 2026-08-23.** Found live against the real nRF54L15 DUT during this session's own enrollment work: the board was genuinely unpowered, and every attach attempt failed with a generic, low-level error a human has to already know how to interpret. New `embarch_topology::hardware::check_target_powered(&mut probe)` (`embarch-topology/design.md` §3 decision 16) reads the probe's own sensed target-voltage pin (`Probe::get_target_voltage`) immediately after `open_probe` and before `attach`, in both this repo's two attach sites (`flash`, `reset`) — `embarch-topology`'s own `enroll`/`validate_known` attach sites carry the other half of the same fix, since both live in that crate. 28. **New `POST /validate` and `GET /alerts` — an explicit, non-destructive way to reach `embarch_topology::hardware::validate_role`/`recent_alerts` over HTTP, closing `embarch-topology/design.md` §5's "MCP/agent-invoked calls... not yet even wired up to test against" open item, 2026-08-24.** Every existing live-identity re-check (decision 8's "one implementation, multiple call sites") only ever ran as a side effect of `flash`/`reset`/the dev-bench handshake actually touching hardware — there was no way for a human or an agent to ask "is the board enrolled as `role` still the one attached" on its own, without also flashing or resetting something, and no way to see the alert history short of reading `embarch-topology`'s own durable log file directly.

`chip` is an opaque probe-rs target name (e.g. `STM32F407VG`, `nRF52840_xxAA`, `esp32c3`) — Core does not validate it beyond whatever `probe.attach()` itself rejects. `format` is one of `elf` / `bin` / `hex` / `uf2` / `idf`, parsed by `hardware::parse_format`; an unrecognized value is rejected with an explicit error rather than silently defaulting. `firmware_path` is read from Core's own local disk — the caller is responsible for getting the file onto whatever machine Core runs on (see §7).

`/dev-bench/port` is the one endpoint that doesn't take `hw_lock`: it only reads USB descriptors the OS already enumerated and opens nothing, same as `/status`'s probe listing.

Handler errors return `(StatusCode::INTERNAL_SERVER_ERROR, String)`, rendered by Axum as a **plain-text body**, not JSON — callers (embarch-api's `core_client.rs`) must parse JSON only on 2xx and read non-2xx bodies as plain text. The `String` is the full `anyhow` error chain (`format!("{e:?}")` in `internal_err`, `api.rs`), not just the outermost `.context(...)` message — an earlier version used `Display` (`{e}`), which silently dropped every underlying cause (e.g. a real probe-rs I/O error collapsed to the single word "flashing failed"). `internal_err` also logs the same chain server-side via `tracing::error!` before returning it, so a failure is visible in Core's own log even if the caller never surfaces the response body. Found and fixed during milestone-1 §3.3 hardware validation, when a genuine `/flash` failure (a WSL2 path Core's Windows process couldn't open) was completely undiagnosable from either the HTTP response or Core's log until this was fixed.

## 5. Hardware access details

- **Probe selection: serial number, falling back to first-and-only (§3 decision 9) — actually implemented 2026-08-20, not before, despite this bullet's own prior claim.** `open_probe(probe_serial: Option<&str>)` in `hardware.rs` (renamed from `open_first_probe`) takes the optional selector — when given, it matches `ProbeInfo.serial_number` exactly (from `Lister::list_all()`, the same enumeration `/status`'s `probes` surfaces) and errors listing every candidate if none match or more than one is ambiguous; when omitted, behavior is unchanged from before this decision — the first probe found when exactly one is attached, or a named error listing every candidate when more than one is (no longer a silent pick). See decision 9's own text for the real gap this closed and how it was found.
- **Probe attach is per-call, not held open.** Each `flash`/`reset` call opens the probe, attaches to the target `chip`, does the operation, and lets the session drop — there's no persistent probe connection held across requests. This trades a little latency per call for not having to reason about a stale/broken persistent session.
- **`hw_lock` scope.** The mutex guard is held for the entire handler body (`_guard = state.hw_lock.lock().await`), so a `/flash` in progress blocks a concurrent `/reset` or `/serial-log` from starting, rather than just serializing at the probe-rs call level.
- **Serial log is a fixed-duration capture, not a stream.** `serial::read_log` opens the port, reads in a poll loop with a 200ms per-read timeout until `duration_ms` elapses, then returns the accumulated lines. There's no long-lived streaming/subscription endpoint — each call is a bounded snapshot.
- **`/serial-log` was never actually meant to reach the DUT's own console UART — only `embarch-dev-bench`'s link (2026-08-18, correcting `embarch-api/design.md` §26's premise).** The endpoint is a generic `serialport` open-and-poll over whatever `port` it's given (above), so nothing in code stops pointing it at a DUT-wired UART, and `embarch-api/design.md` §26 had explicitly described that as a real, intended use ("a DUT's own serial console is a different, project-specific port"). Found wrong investigating `embarch-api/milestone-7.md` §3.10's empty capture against the real reference-dut board: the design's actual intent is that Core's serial link exists for `embarch-dev-bench` (§2's architecture diagram), not for a DUT's own console — plenty of real products (this reference-dut included, once its `ble-shell` snippet is in play, see below) have no wired console output at all in the configs that matter, so treating a DUT's own UART as a first-class `/serial-log` target was a premise nothing had actually confirmed. `embarch-decision-reversals.md` row 11 records this; `embarch-api/design.md` §26 corrected to match.
- **Confirmed, incidentally, in this same investigation: `reference-dut-fw`'s `ble-shell` snippet explicitly disables its DUT's physical UART.** `app/reference-dut/snippets/ble-shell/ble-shell.overlay` sets `zephyr,shell-uart`/`zephyr,console` to a `zephyr,nus-uart` node and disables `&uart20`; `ble-shell.conf` sets `CONFIG_UART_CONSOLE=n`/`CONFIG_CONSOLE=n`/`CONFIG_UART_BT=y` — shell and log output move entirely onto BLE NUS. This is project-specific color, not the reason `/serial-log` returned nothing (the point above holds regardless of snippet); the board's *default* config (no `ble-shell`) does keep `CONFIG_UART_CONSOLE=y` on physical `uart20` per the `dut_dev` board defconfig.
- **Dev-bench port auto-detection matches a recognized VID, not a custom one** (`dev_bench.rs`, implementing [embarch-dev-bench/design.md](../embarch-dev-bench/design.md) §3 decision 12). Two boards, two different reasons the target has no USB descriptor of its own to give Core something board-specific to match on: the nRF54L15 SoC has no USB device peripheral at all, so the port Core sees belongs to the DK's on-board SEGGER J-Link (VID `0x1366`); the ESP32-C5 *does* have a native USB Serial/JTAG peripheral, but it enumerates under Espressif's own generic VID (`0x303A`, confirmed empirically against the real board — Windows reports `USB\VID_303A&PID_1001&MI_00`), not a per-project custom one. **Extended 2026-08-19/20** (`embarch-dev-bench/milestone-8.md` §3.1, closing that milestone's last open item) to recognize both VIDs, rather than SEGGER's alone. Detection is therefore: enumerate serial ports, keep the USB ones with either recognized VID, then narrow by product string, serial number, and USB interface index. The rules, in precedence order:

  **Revised 2026-08-21 (`embarch-dev-bench/design.md` decision 26's update, decision 21's own resolution above): Espressif's VID (`0x303A`) is no longer a link candidate at all, and a third VID joined the list.** Real hardware-scare investigation (decision 21) established that the ESP32-C5's native USB-Serial/JTAG peripheral is a genuinely bad fit for dev-bench's runtime link (boot-strap pins never re-sampled on reset, a genuine hardware reset pulse wedges its host-side USB CDC driver, a DTR/RTS-on-open gotcha reproduces that wedge on demand) — the fix was moving the link to the board's second, dedicated USB-C port's own Silicon Labs CP210x USB-UART bridge chip (`SILABS_VID`, `0x10C4`, confirmed empirically: Windows reports `USB\VID_10C4&PID_EA60` once its VCP driver is installed — no inbox Windows driver exists for it, unlike native CDC-ACM). `ESPRESSIF_VID` is kept defined (still used by `hardware.rs`'s wholly separate probe-enumeration path, since JTAG flashing/reset stay on that same physical port) but dropped from `select`'s own candidate filter entirely, so it plays no further part in *link* detection — see that constant's own doc comment (`dev_bench.rs`) for the full reasoning. A second, related fix landed the same day: the dev-bench-role `known_boards` serial fallback (below) recorded a JTAG probe's serial, which can never equal a plain USB-UART bridge chip's own serial (it has no JTAG capability to enroll under) — narrowing on a non-matching fallback serial now only applies when doing so still leaves at least one candidate, rather than silently zeroing out a real match or manufacturing a misleading "excluded by an env var" out of genuine multi-device ambiguity nothing actually configured. An explicit `EMBARCH_DEV_BENCH_SERIAL`/`_PORT` remains the correct, supported way to pin dev-bench's own link port when a DUT's own SEGGER-VID probe is attached at the same time — the fallback was never able to resolve that specific ambiguity for a split link/probe topology, and doesn't try to.
  - `EMBARCH_DEV_BENCH_PORT` bypasses detection entirely and is honored even if the OS doesn't currently enumerate it — the operator said which port it is, so a missing port is the subsequent open's error to report. Same explicit-env-var-wins shape as `token_store::resolve_token` (§6). Not needed for the ESP32-C5's own link port (`SILABS_VID`) when it's the only recognized-VID device attached — still needed (or `EMBARCH_DEV_BENCH_SERIAL` set explicitly) whenever a DUT's own SEGGER-VID probe is attached at the same time, since the dev-bench-role fallback can't resolve that specific ambiguity (§5's revision above).
  - **Product string:** substring match, default needle `jlink`, overridable via `EMBARCH_DEV_BENCH_PRODUCT` (empty string = match on VID alone). Both sides are normalized to lowercase alphanumerics first, which is what makes one needle cover Linux's `J-Link`, Windows' `JLink CDC UART Port`, and a standalone probe's `SEGGER J-Link`. **The *default* needle is scoped to SEGGER-origin candidates only** — the ESP32-C5's own Windows friendly name (`USB Serial Device`) has nothing "jlink"-shaped to match, so applying the SEGGER default there would wrongly exclude every real Espressif candidate; an explicitly-set `EMBARCH_DEV_BENCH_PRODUCT` still narrows candidates of either VID, same as always. A port reporting *no* product string is **not** excluded — an absent descriptor field is unknown, not disproof.
  - **Serial number:** `EMBARCH_DEV_BENCH_SERIAL`, the specific probe/board's serial recorded once at setup. This is what disambiguates two same-VID candidates in the same lab. **Amended 2026-08-20 ([embarch-decision-reversals.md](../embarch-decision-reversals.md) row 14): when `EMBARCH_DEV_BENCH_SERIAL` itself is unset, `Filter::resolve` (renamed from `Filter::from_env`) falls back to `known_boards.toml`'s `"dev-bench"`-role entry's `probe_serial`, if one has been enrolled (`design.md` §3 decision 22).** Real, not hypothetical: the SEGGER-VID-plus-`jlink` heuristic's whole premise — "the only SEGGER-VID device around is dev-bench's own board" — broke the first time a *different*, unrelated J-Link (the reference-dut DUT's own) was attached alongside dev-bench: its VCOM matches the identical heuristic, and detection correctly refused to guess between two real boards (`500`, ambiguous) rather than picking wrong. Rather than requiring a second, separately-typed env var for a fact `POST /probes/enroll` already captured once — dev-bench's own exact serial, cross-checked against a live hardware-ID readback, a stronger guarantee than an operator-typed string — this reuses that record. `known_boards.rs` gained `find_by_role`; `role` is otherwise unvalidated (decision 22), so `"dev-bench"` (`dev_bench::KNOWN_BOARDS_DEV_BENCH_ROLE`) is the one place a specific value is treated as conventional, and only as an opt-in default — the lookup failing (unreadable/corrupt file) degrades to no fallback plus a logged warning, never a hard failure. `cargo build`/`cargo test` (55 passed)/`cargo clippy --all-targets -- -D warnings` clean on Linux and the real Windows target; **not yet live-confirmed** — deployed to the live Windows Core the same session this was found, but `detect-dev-bench`'s ambiguity hadn't yet been re-run against it as of this writing.
  - **Ambiguity:** more than one candidate that share both VID *and* serial number (i.e. several VCOM interfaces of a single probe, common on Nordic DKs) resolves to the **lowest USB interface index** with a `tracing::warn!` listing the alternatives; `EMBARCH_DEV_BENCH_INTERFACE` overrides. Matching on serial number *without* also requiring the same VID was a real latent bug found extending this to a second VID: two candidates from entirely different device families that both happen to report no serial number looked like "one probe, multiple VCOMs" and got silently collapsed rather than flagged ambiguous — fixed by requiring VID equality too. More than one candidate across genuinely different probes/boards is a `500` listing them rather than a guess.
  - Requires `serialport`'s non-default `usbportinfo-interface` feature for that interface index (Cargo.toml).
  The whole heuristic is a pure function over an already-enumerated port list (`dev_bench::select`), so it's unit-tested against synthesized port lists — no hardware and no environment variables involved. Live-validated against the real ESP32-C5 (2026-08-19/20): `GET /dev-bench/port` returns `detected_by: "espressif-vid-match"` on `COM12` with no manual override set. What's still only unit-tested, not live-confirmed, is whether a real nRF54L15DK's J-Link actually exposes more than one VCOM, and whether the lowest interface index is the one wired to the target's UART — see §10.

## 6. Security model

Auth is a single shared secret, `EMBARCH_TOKEN`, checked via exact-string comparison in `auth_middleware` against every request's `Authorization` header. The value itself comes from `token_store::resolve_token()` (called from `main.rs`'s `run()`): an explicit `EMBARCH_TOKEN` env var wins if set; otherwise the machine-wide token file (`token_store.rs`, §8) is reused if present, or generated and persisted on first startup. Full lifecycle (generation, storage, transport, rotation, threat model, known gaps) is documented in [embarch-token.md](../embarch-token.md) rather than here — that includes the no-per-caller-identity limitation. The insecure `dev-token-change-me` fallback this replaced is gone entirely (milestone-2, §11).

## 7. Deployment model

**Confirmed via milestone-1 (2026-07-21):** `embarch-core` runs natively on Windows (built with `cargo build --release` against a native Windows checkout — a `\\wsl$`-mounted source tree was deliberately avoided, per the milestone plan), reachable from a WSL2 guest via the `0.0.0.0` bind at the WSL2 session's dynamic host-gateway IP (`ip route show default` from inside WSL2 — `172.29.64.1` on this machine, expected to change across WSL2 restarts). Windows Firewall did not need an explicit inbound rule: this machine's WSL networking mode is the newer "WSL (Hyper-V firewall)" NAT, whose `Get-NetFirewallHyperVProfile` profiles default to `DefaultInboundAction: NotConfigured` (permissive) rather than the regular Public-profile Windows Firewall (which the host's other network adapters were categorized as, and which would likely have blocked an unsolicited inbound connection). Building natively on Windows required installing Visual Studio Build Tools' "Desktop development with C++" workload for `link.exe` — a bare `rustup`-installed toolchain alone is not sufficient, since only the MSVC target ships without a bundled linker.

**An installed, autostarting OS service is the intended normal deployment, not a foreground `run`.** §3.3's `install`/`uninstall` already provide this on all three OSes; what's new is stating it as the default rather than an option, because it's what makes the rest of the suite need no launcher: if Core is up at boot, then `embarch-api` — which is invoked per-use, either spawned by an MCP client or run directly by a human — always finds a Core already running, and there is nothing for anyone to start. See [embarch-umbrella/design.md](../embarch-umbrella/design.md) §3 decision 3, which is the sub-project that makes sure `install` actually got run. A foreground `run` remains fully supported and is the right choice for debugging Core itself.

**Anticipated move: a LAN-reachable Raspberry Pi.** The `0.0.0.0` default bind and the CLI's cross-platform service install already anticipate this — no code changes should be needed to point Core's HTTP server at a Pi and reach it over the LAN.

**Artifact-transfer gap, shared with embarch-api's design doc §9 — real story is messier than this section originally recorded; see the 2026-08-18 correction below before trusting anything above it.** `/flash`'s `firmware_path` is read from Core's own local disk, so a WSL2-built artifact's path is meaningless to a Windows-hosted Core, and a genuinely separate machine (a future Pi deployment) has no shared filesystem at all.

**Corrected 2026-08-18.** This section originally claimed decision 10 (multipart for a `remote` topology) shipped 2026-08-15 and that the WSL2-same-PC case's UNC mechanism was "confirmed working end-to-end" and could be "left alone." Neither held up: decision 10 was never actually implemented despite this text (and §4's endpoint table) describing it as done — no `multipart` feature on `axum`, no multipart-handling code in `api.rs` at all, found only because `embarch-api` needed a real fix and went looking for the multipart path this doc said already existed. And the UNC mechanism's "confirmed working" claim was true only for Core running in the foreground — the installed Windows service runs as `LocalSystem` in Session 0, which can't reach `\\wsl.localhost` at all (`embarch-api/design.md` §9's full account).

**Actually implemented 2026-08-18, and with a wider scope than originally designed.** `/flash` (`api.rs`'s `flash_handler`) now genuinely accepts a `multipart/form-data` body — `chip`/`format` fields plus a `firmware` file part, dispatched on `Content-Type` rather than a separate route — alongside the existing JSON body, on the one documented endpoint. Bytes are written to a `tempfile::NamedTempFile` (new dependency) that outlives the blocking `hardware::flash` call, then deleted. Used not just for a `remote` topology as originally scoped, but for `WslHost` too — `embarch-api`'s fix for the Session 0 finding needed exactly this, and it's the same mechanism either way. 4 new unit tests hand-construct real multipart bodies (round-trip, default format, missing-`chip`, missing-`firmware`-part) — 19 total, up from 15. `cargo build`/`cargo clippy --all-targets -- -D warnings`/`cargo test` clean, including on the real Windows target. `artifact_path_for_core` is retired entirely on the `embarch-api` side (its own §9) — this section's earlier claim that it stays "validated" and "left alone" no longer applies to anything, since nothing computes or sends that value anymore.

## 9. Relationship to embarch-api

Core has zero knowledge of embarch-api, MCP, Claude Code, or the concept of a "project" — it only ever sees the endpoints' bare parameters (`chip`, `firmware_path`, `format`, `port`, `baud`, `duration_ms`). Every project-name-to-config mapping, build orchestration, and MCP tool surface lives entirely in `embarch-api` (see `embarch-api/design.md`). The embarch-core CLI is a second, independent caller of the exact same HTTP API used by embarch-api — not a privileged or special code path — which is why `install`/`uninstall` still just point the OS service manager back at the `run` subcommand, on every OS, rather than a dedicated service-mode subcommand. (On Windows specifically, `run` itself now branches internally — §3 decision 3's correction — but that's `run` self-detecting SCM vs. a human at a console, not a second subcommand `install` has to know about.)
