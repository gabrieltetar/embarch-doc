## 1. Goal, restated for Core

Unlike Milestones 1 and 2, this milestone needs **no new Core code** by default — `study.rs`'s passthrough is already generic over whatever `Action`/`StepResult` shape `embarch-study-designer` defines (`design.md` §9's own framing: Core links the crate as a real dependency and relays/(de)serializes its types verbatim, never hardcoding a column or field). The two new `Action` variants and `StepResult` fields ([embarch-study-designer/milestone-9.md](../embarch-study-designer/milestone-9.md) §3.2) should reach `events.json` correctly the moment Core is rebuilt against the updated crate — no `study.rs` changes anticipated. This milestone's real job is **validating a scenario Core has never actually been exercised against: a DUT probe connection and a dev-bench study running in the same session**, and confirming that passthrough claim empirically rather than by inspection alone.

## 2. Scope for this milestone

- **No new endpoints, no new decision anticipated.** If §3.2 finds `events.json` doesn't actually carry the new fields correctly (a real serde/postcard mismatch, not just a hypothetical), that becomes real, unplanned work — tracked here as a risk (§5), not pre-scoped as a step.
- **The concurrency scenario is new: `hw_lock` (DUT probe, via `embarch-api`'s `build_and_flash`) and `study_lock` (dev-bench serial link, via `run_study`) are exercised together for the first time.** `design.md` §3 decision 15 already states they're independent locks over independent physical connections — this milestone is the first time both are actually held in the same real session (flash the reference-dut DUT, then run a study against dev-bench while that DUT is powered and running), not just reasoned about.
- **Out of scope:** any new `/study*` endpoint behavior; power-data/waveform-data (still correctly empty for this milestone's fixture, same as Milestone 2); the DUT's own serial console (`design.md` §5's existing note that `/serial-log` was never meant to reach a DUT's console, unaffected here).

## 3. Steps

### 3.1 Rebuild against the updated `embarch-study-designer` dependency

Bump to whatever version/path [embarch-study-designer/milestone-9.md](../embarch-study-designer/milestone-9.md) produces; `cargo build`/`cargo test`/`cargo clippy --all-targets -- -D warnings` clean, with no `study.rs` source changes expected (§1).

### 3.2 Confirm `events.json` carries `gatt_services`/`gatt_activity` correctly, for real

Run the milestone's actual `Study` (via [embarch-api/milestone-9.md](../embarch-api/milestone-9.md)) and inspect the resulting `events.json` by hand: `StepResult.gatt_services`/`gatt_activity` present, correctly shaped, and matching what [embarch-dev-bench/milestone-9.md](../embarch-dev-bench/milestone-9.md) §3.7–3.9 actually captured — not just "the build succeeded."

### 3.3 Flash the reference-dut DUT via `hw_lock` while dev-bench's `study_lock` is idle, then run a study while the DUT stays powered

Sequence: `build_and_flash` the reference-dut DUT (acquires and releases `hw_lock`), then `run_study` against dev-bench (acquires `study_lock`) while the just-flashed DUT is still powered and advertising — confirming the two locks really do govern independent physical connections in practice, not just in the design's own reasoning (`design.md` §3 decision 15).

### 3.4 Attempt a `/flash` (or `/reset`) call against the DUT *while* a study is in flight against dev-bench

The inverse ordering from §3.3 — confirm a `hw_lock`-guarded call succeeds (or fails only for reasons unrelated to `study_lock`) while `study_lock` is held by an in-progress `GattMonitorAll` capture, proving the two really don't contend.

### 3.5 End-to-end validation via `embarch-api`

The actual Definition of Done for this milestone as a whole: [embarch-api/milestone-9.md](../embarch-api/milestone-9.md)'s full sequence (flash the DUT, connect, discover, monitor, forward into `events.json`) run for real, not just this doc's own steps in isolation.

## 6. Changelog

- 2026-08-21 — **Resolved for real: a full self-test `Study` completed end to end over the new UART link, closing decision 21's `target_reset`/`HelloAck` investigation for good.** Three more real fixes were needed beyond the port move itself, all found live: the CP2102N bridge chip's Windows driver installed by hand (no inbox driver — `CM_PROB_FAILED_INSTALL` until then); `board_gate::enforce_for_role` added, since `enforce_for_serial`'s whole mechanism assumed the link's own USB serial is a JTAG-probe serial, structurally untrue for a plain UART bridge chip with no JTAG capability at all; and a missed `reset_dev_bench` call after the rebuild (the core had been sitting halted since its last flash — flashing halts, it never resumes on its own). End result, confirmed via Core's own log and a direct `GET /study/{id}` call: `HelloAck` (`compatible: true`) → `StepResult`(Pass)×2 → `StudyDone{completed:true}` — the first time this link has ever worked. `dev_bench.rs` also gained `SILABS_VID` and dropped `ESPRESSIF_VID` as a link candidate, plus a fix to the dev-bench-role serial fallback for the new split link/probe topology (a DUT's own SEGGER-VID probe attached alongside dev-bench no longer silently misresolves) — built, tested (64 passed), clippy-clean, but not yet deployed to the live Windows service as of this entry (blocked purely on a UAC prompt). `design.md` decisions 21/22/§5 and `embarch-dev-bench/design.md` decision 26 all updated with the full narrative.
- 2026-08-21 — **The DTR/RTS-wedge investigation turned out to be chasing the wrong port: dev-bench's runtime link has moved to the DK's second, dedicated UART USB-C port instead, sidestepping the native USB-Serial/JTAG peripheral's quirks entirely.** An already-written devicetree overlay change (restoring the board's own upstream `uart0` console/link default) had been sitting uncommitted and unbuilt in `embarch-dev-bench` since earlier this same milestone — found investigating the DTR/RTS gotcha, when it turned out the ESP32-C5-DevKitC-1 has two USB-C ports, and `uart0` was wired to the second one all along. Built and flashed for real (`build_and_flash_dev_bench`, after a pristine rebuild cleared a stale-artifact issue) — JTAG flashing/reset stay on the native port; the runtime link needs the second cable connected too. Not yet live-validated: waiting on that physical connection, then a temporary foreground `run` with `EMBARCH_DEV_BENCH_PORT` set (the installed service has no env-var path, decision 11). `embarch-dev-bench/design.md` decision 26 and `design.md` decision 21 both updated.
- 2026-08-21 — **User replug recovered the write-level wedge, but `HelloAck` still timed out — pointing at `embarch-dev-bench/design.md` decision 26's own DTR/RTS-on-open gotcha rather than the stuck-in-download-mode theory, and a diagnostic confirmed one specific bad DTR/RTS combination.** Post-replug, `GET /status`/`detect-dev-bench` looked clean and `run_study`'s `Hello` write succeeded, but the handshake itself timed out — the *original* symptom, now surviving a full physical power cycle, which rules out "stuck in ROM download mode" (a power cycle is the cleanest reset there is). Replicating decision 26's own successful workaround (a raw serial open outside Core) with `DtrEnable=true, RtsEnable=false` reproduced the write-level wedge again immediately. Needs another physical replug, then a controlled sweep of the remaining combinations — not yet done. `design.md` decision 21 and `embarch-dev-bench/design.md` decision 26 both updated.
- 2026-08-21 — **Root cause confirmed, real fallback shipped and live-confirmed to fire a genuine reset pulse — which immediately reproduced this milestone's own original hardware scare, deterministically, on the first real pulse ever sent.** `target_reset()`'s `NotImplemented` on dev-bench's probe turned out to be `probe-rs` 0.31.0's `espusbjtag` driver never implementing it at all (confirmed by reading its source), not a wiring gap — but the same driver's `target_reset_assert`/`target_reset_deassert` are real. New `hardware::reset_via_assert_deassert` drives those by hand (assert, hold 50ms, deassert) as a fallback; live log shows real `reset_assert!`/`reset_deassert!` events ~51ms apart, the first genuine hardware pulse dev-bench's ESP32-C5 has ever received from Core. Immediately after, `run_study`'s `Hello` write failed with `os error 121` (`ERROR_SEM_TIMEOUT`) — a Windows-driver-level failure, earlier and different from the `HelloAck` protocol timeout this investigation started from — unchanged after +3s and +8s retries (not a re-enumeration timing issue), while `GET /status` kept showing the same device's JTAG interface fine throughout. This is essentially the *original* incident that motivated decision 21 in the first place ("dev-bench's native USB-JTAG/serial port stopped answering... after repeated flash/reset cycles"), now reproduced on demand by the fix meant to prevent it. Paused here rather than retrying further against possibly-already-wedged hardware — recovering the CDC interface likely needs a physical USB replug, which only the user can do. `design.md` decision 21 updated with the full narrative.
- 2026-08-20/21 — **First real attempt at the outstanding DoD item, `target_reset()`-fix live-validation — enabled by decision 16's log file (finally implemented for real, see `design.md`'s own changelog), inconclusive.** `reset_dev_bench` against the real ESP32-C5 reported success; `embarch-core logs --tail 80` immediately after showed a completely clean two-attach cycle (decision 22's board-identity gate, then `Core::reset()`) with zero warnings or errors anywhere. - 2026-08-20 — **A real hardware scare during §3's own execution paused it entirely, and surfaced a genuine, unplanned prerequisite (`design.md` decisions 21/22).** After the `probe_serial` fix (below) deployed, the reference-dut DUT needed a manual `west flash --recover` and dev-bench's native USB port stopped answering the app's serial protocol — both looking, briefly, like real hardware damage from this milestone's own flashing. Root-caused instead to two genuine `probe-rs`/target quirks, not corruption: a target that's been running can stop responding to a plain SWD attach once asleep, and the ESP32-C5's USB-Serial/JTAG peripheral's core-only reset doesn't re-sample boot-strap pins, explaining this milestone's earlier `HelloAck` failures too (a chip stuck in ROM download mode, never running the app's protocol at all). That investigation then surfaced a deeper, still-open vulnerability: `probe_serial` says *which probe*, never *whether it's still wired to the board its config labels it as* — a gap only a human can ever resolve, and a real one given `embarch-dev-bench/design.md`'s own eventual same-chip-family dev-bench plan. Decision 22 (design-only, a new Core-local `known_boards` table plus a guarded `POST /probes/enroll` and a live hardware-ID cross-check gate before `flash`/`reset`/`POST /study`) is now a hard, unplanned prerequisite blocking this milestone's remaining real-hardware steps (§3.2–§3.5) until implemented.
