**Target:** suite/studies-guide.md §3a — the "no part of EmbArch joins the two" sentence
**Was:** "nothing here links a BLE advertiser to an enrolled probe — enrolment identifies a board by hardware ID and debug probe, the census identifies it by advertised name, and no part of EmbArch joins the two."
**Now:** As of `embarch-dev-bench` decision 44, the per-advertiser census (the bench's log sink, not the 64-byte `fail_reason`) also carries an advertiser's Manufacturer Specific Data element when it sent one — company ID plus up to 4 payload bytes, hex, with a cap-exceeded note when there were more. For this bench's DUT family, the client firmware's own source claims (unconfirmed on air — `tasks/api/029` is the pending live test) that the last two payload bytes are `s_ficr_id[6]`/`s_ficr_id[7]`, the same bytes Core reads over the debug probe as `hardware_id`'s tail — so an operator can now compare that hex by eye against an enrolled `hardware_id`'s suffix.

What still holds: nothing in EmbArch automates that comparison, the correspondence is read off client source rather than measured on air, and it is a client-firmware convention, not a general join — a DUT that never sends Manufacturer Specific Data, or a different client family with a different convention, gets none of this from the census. §3a's own operator-does-the-deciding framing should stay; only "no part of EmbArch joins the two" needs softening to something like "the census can now carry a byte string worth comparing to an enrolled hardware ID by hand, for DUT families whose firmware puts it there — nothing joins them automatically, and the correspondence itself is unconfirmed on air."
