## Linear reads

### 79 — `linear_list_issues` lists a team's issues in a named state, and no agent falls back to the connector

Decided 2026-11-10 (EMB-11). An agent reading a queue (every issue in a team's "Fleet Ready") had no desk tool: `linear_my_issues` lists only the user's assigned open issues, `linear_search` matches title words or one key. The tool is `linear_list_issues(team_key, state, project?)` over `POST /linear/issues`. **Not scoped to the session's desk**, unlike the other list tools: the caller names the team, and any connected workspace's team answers. The team is found by key (case ignored) across every workspace; the state is matched by name, case ignored, against that team's own states, and a miss is an error listing the ones it has, never an empty list; `project` is matched by name and narrows the list, a name no project has gives an empty one.

**Filtering.** The API-key backend filters on Linear's side: `issues(filter: {team: {id}, state: {name: {eq}}, project: {name: {eqIgnoreCase}}})`. The Linear-MCP backend (68) passes `team`, `state` and `project` to its `list_issues`, which takes a state by name or type, so it **also filters after fetching**: only rows whose status is exactly the resolved name stay. Both read 50 a page, newest update first, up to `MINE_CAP` (500) per call, and the answer carries `truncated` and a `note` when the cap cut the list, as 59 does for assigned issues. Closed states are listable (naming "Done" works); unlike `/linear/open` this is not an open-issue read. Tested by unit on both backends' row and cursor handling and the cap's cut; no live workspace was called.

**The policy, 29 applied and not a new rule:** where the desk has no tool for a read, a session says so and the gap is filed against the desk; it does not use Claude's own Linear connector. `plugin/skills/desk/SKILL.md` says so in one place.

### 81 — `linear_get_file` reads an image or file an issue lists, and only one it lists

Decided 2026-11-10 (EMB-14). A screenshot or file pasted into an issue is a Linear upload link in its text that no desk tool could fetch (the links need the workspace's credentials and expire within minutes), so an agent read the words and missed the rest, and 29 leaves it no other route. **Listing.** `linear_get_issue` gains `files`: every `https://uploads.linear.app/…` link in the description and in **all** the comments read (up to the 500 cap of 59, not only the 25 returned), and the issue's attachment records, each `{url, title, found}` with `found` = `description`, `comment <id> by <author>` or `attachment`, once per URL. **The tool.** `linear_get_file(key, url)` over `POST /linear/issue/{key}/file` reads the issue afresh, **refuses any URL that read does not list** (an error naming the issue; never a general fetch through the owner's tokens), then fetches at call time. **Answer.** An image (not SVG) is MCP image content beside a line naming it; a text (`text/*`, JSON, XML, SVG, or an unlabelled UTF-8 body) is text; anything else, or a text over 200 KB, is written owner-only to `<data folder>/linear-files/<KEY>/<name>` (name from the URL, sanitised) and its path returned. **Cap: 10 MiB** [chosen, not measured: well above a screenshot or a log, below what is worth sending a model or holding in memory]; a bigger file is refused naming its size, by `Content-Length` before the body and by a running count after it.

**The credential goes only to Linear's upload host.** An attachment record's URL is free text an issue's author wrote, so a fetch of a link out of Linear is sent bare, and only `https` links to a public hostname are fetched (no login, port, IP address or `localhost`). A redirect to another host drops the header. **API-key backend:** `Authorization: <key>`, bare as GraphQL takes it; the attachment records come in the one GraphQL read. **Linear-MCP backend (68):** the sign-in's token as a bearer; if the host refuses it, the server's own `extract_images` is asked for the image; a file that is no image has no second way. Either failure says it was the MCP sign-in, names the status the host gave and what `extract_images` said, and never returns an empty success. **Assumed, not measured** (no live workspace was touched): that the upload host takes the bare key and the MCP bearer, that `extract_images` takes `markdown`, and that the MCP `get_issue` includes `attachments` unasked (its field list is not widened, since an unknown field may fail the read; absent, only upload links list on that backend). Debt: one real issue with an image, a PDF and an attachment, on each backend. **Rejected:** a general `fetch_url` (the owner's tokens through any URL), listing only the returned 25 comments' links (an older comment's screenshot would be unreadable), returning every file inline (a PDF or a long log fills the context).
