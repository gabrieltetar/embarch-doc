# embarch reversals: rows 93-109

| 93 | The DUT-side link loss is triggered by a specific pair of control writes preceding the NUS write → **the trigger is not a step, it is a *state*: once the sensor is running, the DUT cannot service a GATT operation inside the supervision timeout, and whichever operation comes next is the one that dies.** Moving the pair later moved the failure with it. **That also retires three experiments recorded as inconclusive** — settle intervals, a reset between runs, an explicit abort first step — **because none of them stops the sensor.** The clean-run corollary is the useful half: the reordered study captured 691 KB of trace with no loss, **so the tracer and the transport are both fine and the blocker is entirely the DUT** | bench |
| 94 | A study reporting "no message received before the deadline" received nothing, so the silence is the whole of the evidence → **Core was holding 699 bytes of the bench's own boot banner in a private buffer with no code path that could mention it.** The deframer accumulates until a delimiter, and **this board's console *is* the protocol UART**, so a rebooting chip writes fourteen lines of plain ASCII with **no delimiter anywhere in it** — never framed, never decoded, never logged, never counted. **The reset row 92 spent an uptime comparison to establish had been announcing itself in clear text the whole time.** **A framed protocol whose deframer discards non-conforming bytes will report "nothing arrived" for the one class of message most likely to explain a fault: the bytes that were never meant to be protocol** | core 40 |
| 95 | Row 93: the link loss is a *state* — once the sensor runs, the DUT cannot service a GATT operation in time — i.e. a CPU or radio load problem → **the DUT is 93% idle when the link dies, and what collapses is the connection interval, not the CPU.** Its own trace settles it: the controller's ticker goes from 91 entries/s to **eight consecutive 626.4 ms holes, metronomic**, while *inside* the largest hole hundreds of SPI interrupts and idle switches fire — **interrupts on, kernel alive, radio simply not scheduled.** 626.4 ms is **the band's own configured connected-idle interval**, spec-legal and thin: at that interval the supervision timeout is eight connection events of margin. **The lever already exists in the firmware and fires downstream of the exchange that needs it** — the fast interval is requested only once a backlog exists, and the write that dies comes before any backlog. Confirmed by measuring rather than reasoning, and by fixing it: **one speed step took the study from dying at step 5 of 11 to 14 of 14.** **The sensor running was a correlate all along** — it is what coincides with the slow interval taking effect | bench |
| 96 | The traced DUT wants ~4700 rec/s more than the link can carry, so "the record must get smaller" is a requirement rather than an optimisation → **that number was measured on a run whose BLE link was in the failed state.** The first capture with the link actually holding runs at **1606 rec/s, about 17 KB/s against ~46 KB/s available, with 1.12% frame loss: roughly 2.5× headroom, not a 2× shortfall.** **A capacity requirement derived from a capture of a broken system would have bought a six-component wire-format change plus a version bump to fix a number a one-line study change removed** | outpost |
| 97 | The step-row projection follows the rule the rest of the parser already uses — anchor each frame's arrival against the last DUT stamp in that frame → **a gap record's stamp is not one of that frame's stamps, and using it reordered the study steps on the first real capture.** A gap is stamped when the *first dropped* record was lost, so its stamp sits outside its own frame's run — **487 ms ahead, on a capture whose largest row-to-row step is 20 ms** — poisoning 147 of 12,476 frames: one step vanished entirely and another started 0.4 s before the step before it had ended. **The parser already filtered gap records out — twice, for exactly this reason.** **A rule that exists in two of the three places it applies is not a rule anyone will find; it is a coincidence** | ui 10(j) |
| 98 | A tap that lost data says so via its close message, and end-of-study closing syncs scopes against one step past the last, so "no scope covers it" → **no scope covers it *unless it is whole-study*, which covers every step index by design.** So such a tap was never closed, never reported its drop count, and **its truncated flag stayed false however much was lost.** The same study run twice minutes apart: the scoped tap lost 16 and said so; the whole-study tap lost 31 and **claimed to be complete.** All three load-bearing taps were whole-study, **so all three flags were unfalsifiable while an investigation rested on them.** **The suite's own test pinned both halves of the contradiction nine lines apart** | bench 42 |
| 99 | A marker macro is safe to place anywhere, because the header no-ops when markers are compiled out and still checks the name — "the failure mode this prevents does not depend on a Kconfig", in that header's own comment → **the header could not be *included* at all without the module, so its no-op path was unreachable from any application.** The include directory sat below an early return in CMake, **and the cost landed exactly where a marker earns its keep**: a hot path compiled into both the tracing image and the shipping one. **The design was right and one line of CMake made it unreachable** | outpost 21 |
| 100 | A lane's visible spans are found by a lower bound plus **one** step back, "exactly one, because spans within a lane do not overlap" — in its own comment → **a lane's spans overlap whenever the capture lost a record, and the committed fixture already contained the shape.** A lost switch-out leaves a run open and every still-open span is drawn to the end, **so later, shorter runs of the same thread sit inside it.** The one-step walk-back halted on the first nested span and **the enclosing one vanished from every zoomed window past it** | ui 10(k) |
| 101 | The backlog fetch and the stream re-open are "kept in this order so a slow backlog fetch can never land lines into a console the user has since switched away from" → **ordering cannot cancel a request already in flight.** The fetch was un-awaited and captured no identity, so its answer landed in whichever console was mounted when it *resolved*. Reproduced against the live Core: **204 lines under one source's heading, 200 of them the other's**, in an order the timestamps contradict — **the exact interleaving the decision refuses a merged stream to avoid** | ui 13 |
| 102 | The live tail's diff "falls back to replaying the whole new window rather than silently dropping content; a few duplicate lines in a debug viewer is a smaller problem than missing ones" → **the implementation did the thing the sentence rules out**, scanning *backward* for the anchor's most recent occurrence, so **any line repeating verbatim later in the window swallowed everything between.** **Its own test asserted the loss as intended behaviour.** The window is a contiguous run of one append-only file, so the anchor is the whole suffix/prefix overlap | ui 13 |
| 103 | dev-bench is "EmbArch's own fixed test rig — there's exactly one, and its board, chip, flash format and base address are facts this suite already knows" — the stated ground for putting them in Rust rather than config → **the same physical bench has now been three different boards, agreeing about none of those four — plus a fifth nobody had noticed was a variable.** The artifact path differs too, because **one SDK defaults sysbuild on and the other has none: a property of which SDK the workspace pulls, so no rule over the other four predicts it**, and a change making only "board" configurable would have silently kept flashing the wrong path. All five are config now and **none is defaulted** — a default has to pick one of two boards | api 45 |
| 104 | Enrollment is idempotent: re-enrolling the same probe overwrites its old row "rather than accumulating stale duplicates that could disagree with each other" — in its own doc comment → **a role is the key everything actually addresses a board by, and nothing enforced its uniqueness.** Two rows claiming one role left the by-role lookup answering with the **unplugged** board, inheriting a dead link serial **that narrows hard and resolves detection to a port that cannot exist.** **The quoted sentence is what made it invisible: it names the duplicate class it prevents, which reads as though it had considered the space** | topo 20 |
| 105 | Several VCOM interfaces on one probe are resolved by taking the lowest index, with a warning — a rule carried since this logic lived in Core, and pinned by a test → **the rule had no hardware behind it, because no bench had ever had two VCOMs, and the first board that did falsifies it:** the console UART's pins are wired to the *higher* interface, and **the lower one accepts bytes and never answers.** **What made it expensive is that the guess was indistinguishable from an answer** — the warning went to a log and the endpoint reported full confidence, so the symptom was a bench that flashed, booted, ran, and timed out on a handshake, **which says nothing about a port having been chosen at all.** Two well-evidenced wrong hypotheses came first, and what settled it was writing a real handshake frame to each candidate by hand. **The serial was no help by construction:** link and probe are the same physical device here, so both declared serials narrow to the pair and stop | topo 20 |
| 106 | Turning the bench's log on and forwarding it to Core (row 59's fix) delivered what was asked for → **it delivered it *always on*, and "always" was never the ask.** The level was a detail, so it became a Kconfig line — **a choice made once, for every study, by whoever last edited the config** — and the one study that needed the BT host's account of a failure could only get it by rebuilding and reflashing. **When a feature's cost is per-use and its configuration is build-time, "on" and "always on" collapse into the same option, and nobody notices until someone asks for it once** | bench 39 |
| 107 | A log level set at runtime can raise verbosity above what the build was compiled with → **module registration at a level compiles every finer call out of existence, and runtime filtering can only reduce below it.** A study asking for debug got the bench's step-by-step account of *nothing*, silently — **the calls did not exist to be filtered.** **Both halves of a per-study level scheme have to be built for the loudest level anyone may ask for, and the Kconfig that looks like "the default" is really "the ceiling"** | bench 39 |
| 108 | Filtering a log record when the backend forwards it is equivalent to filtering it when it is created → **deferred logging puts up to a second between the two, and the level can change in the gap.** A study body running in ~50 ms finished and reverted to the idle level *before* its own records were examined, **so they were dropped under a level that was not in force when they were made.** **Any state a deferred consumer reads must be flushed, snapshotted, or carried with the item — reading it at consumption time is reading the future** | bench 39 |
| 109 | The outpost snippet should follow the existing pattern and take the shell off the traced UART, keeping BLE on so a study can still drive the DUT → **keeping BLE on is necessary and not sufficient, and the obvious way to "take the shell off" silently removes the stimulus.** The BLE-shell snippet does not bypass the serial shell backend, it **re-points** it — so disabling that backend disables the NUS shell too, **and with it the service every saved study stimulates through.** It also disables the traced UART outright to let the fast peripheral domain gate the clock, **so the tracer's own UART is switched off underneath it unless the outpost overlay is applied second.** The snippet is therefore an ordered composition, not a standalone | outpost |
