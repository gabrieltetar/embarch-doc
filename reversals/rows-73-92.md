| 79 | Bumping a module pin is a one-line change plus an update, and the thing to check is whether the new revision breaks anything → **every compatibility check passed, and the blocker was somewhere nobody had thought to look: the module checkout itself was not clean.** It carried 432 uncommitted lines across 10 files implementing the *opposite* design from HEAD, **and the update would have discarded them.** **Before an update that moves a pinned dependency, `git status` every module it will touch** — "does the new revision fit?" and "is there work here the move would destroy?" are different questions, and only the first is the one people ask | outpost |
| 80 | Layout 2's finding — that reading the cycle counter inside the context switch is the instrument charging its cost to the path it measures — means **the DUT must stop keeping time** → **the objection was to the lock, not to the clock, and only the lock had to go.** The kernel's cycle call takes a spinlock around a driver call that takes a *second* critical section around a 64-bit read in a retry loop, **all to hand back 32 bits sitting in the counter's low word.** Reading that word directly costs no locks and keeps per-record ordering, **which a host cannot reconstruct from frame arrival at all.** The version went **2 → 3, not back to 1**, although the wire is byte-for-byte what 1 was: **a version byte exists so a host can say "I decode up to N", and a number reused after an incompatible wire has worn a higher one cannot say that** | outpost |
| 81 | Snippet flags build that project with those snippets; "only meaningful for a discovery project" is a note about which projects *have* snippets → **for a project with an explicit build command the flags are accepted, silently discarded, and the build reports success — having produced an image without the snippet in it.** The generated config said the feature was unset while the tool said the build succeeded, **which it had: it built the wrong thing, correctly.** Fourth of this family in one day. **A flag that cannot be honoured must fail, not be ignored; "only meaningful for X" in a help string is documentation, and documentation is not a gate** | api |
| 82 | A direct route's declared serial identifies its bridge, so gating on vendor could only exclude the right answer → **the first real bridge has no USB serial number at all.** Windows falls back to a hub-location path and enumeration surfaces its first token. **The declaration resolves to exactly one port today, and a bogus serial fails loudly and correctly — but the identifier is a location, not an identity, and it will change when the adapter moves to a different hub port.** The reasoning assumed a serial that identifies a device; this one identifies a socket | topo 18 |
| 83 | The outpost's remaining unknowns are its wire constants, so the first real UART will be about whether the baud and batch size are right → **the first real UART said something else entirely: the DUT emits a burst at boot and then stops.** 355 bytes arrived after a flash-and-reset — the first outpost bytes ever on a real wire — then nothing across repeated resets, **while a header frame that should repeat every second does not.** The DUT is not dead and every host-side half works. **What real hardware had to say about this instrument was not about baud rates** | outpost |
| 84 | Row 83's own diagnosis: the outpost stalls after a boot burst, so the blocker is a DUT-side firmware bug → **the DUT never stopped.** It streams ~21 KB/s continuously at 91% of line rate, and **no serial port on the host receives a byte of it.** SWD register reads show the peripheral working as designed and a decode of the live record ring shows an ISR span matching the byte count to the microsecond. **What makes this stronger than the diagnosis it reinstates is a positive control**: the same all-port scan saw thousands of bytes from dev-bench on reset, so the method demonstrably detects traffic. **The 355 bytes remain unexplained, which is the honest weak point** — burst-then-silence is also what a stalling emitter looks like, which is why one unexplained burst overturned a correct diagnosis for a day | outpost |
| 85 | Row 84's conclusion: nothing on the host is connected to the pin, so closing this needs a rewire → **nothing was connected because that is not this board's debug pin. The DUT on the bench is a different board revision, and every build for three weeks had targeted another one.** The owner supplied the fact in a sentence — "my board is nff v7" — and it collapsed the whole investigation: **the board's own devicetree had written down the exact symptom being chased, in the tree, months earlier** ("transmitting … the byte simply lands on the wrong pad"). Rebuilt for the real board, the trace appeared instantly: **437,789 bytes in 20 s, 43,948 records, zero lost.** **Where the wrong board came from is the part worth keeping:** the config's board had been "corrected" weeks earlier by reading the repo's own stale build metadata — **a derivation from an artifact, presented as authoritative** — while the snippet's own header had shown the right target in a code block the whole time. **Three diagnoses, two wrong, and the correct one needed a fact no amount of reading could supply** | outpost, api |
| 86 | Row 80's account of what layout 3 bought — five ISR pairs with identical enter and exit cycles — read as a fixture observation, with the UI's frame-arrival axis left in place as still honest → **the observation was right and its scope was wrong: it was every span in every capture, and the host kept reading the coarse clock for a day.** The UI parsed six columns and **never read the two new clock columns**; its module doc still said records carry no timestamp. So every span was timed by its *frame's* arrival, and a span straddling two frames was charged the whole interval: **the outpost's own drain thread reported at 78.1% of measured extent against a true 1.6% — a 46× error, on the single number the next session was briefed to go and reduce** — plus 4286 of 4955 spans called below-resolution when none were. **A second, independent half was in Core:** the manifest was latched when the decode loop *reached* the header frame, so 488 rows rendered nameless inside a stream whose index said named. **A wire-format change is not done when the DUT emits it — it is done when every host that decodes it has been re-measured against it.** Row 80 is what happens when a new capability is verified to *exist* rather than to be *used* | ui 10, outpost |
| 87 | A thread created into a plain static struct "has no distinguishing symbol prefix, and identifying it would need DWARF type inspection" — an accepted limit → **accurate about the limit and wrong about its size; the inspection it named and declined takes about eighty lines.** Name matching resolved 5 of 20 thread objects, and **the fifteen it missed are most of what a quiet trace does** — including four that **are not that struct at all**, because a work queue starts with one, so its address *is* its thread's, and no naming convention could have found them. **"Declare it differently" was not available for any of them; they are the kernel's and the BLE stack's.** The fix joins two facts the build already recorded and resolves 20 of 20 | outpost 8 |
| 88 | Row 86's framing of what was left: the instrument's own 50.4% share of records is the thing to cut, "almost certainly the single biggest win", and fewer records means frames fill sooner → **removing half the records moved the link's duty cycle from 99% to 96% and improved resolution not at all.** Both halves fail for the same reason, and it is the drain loop's *shape*: it sends, blocks on the transmit, then drains exactly what arrived while blocked — **so frame size settles at whatever the record rate produces during one frame's own wire time, however few records there are.** Measured at 42.8 bytes per frame, **a fifth of the link carrying no records at all.** Waiting for the batch to fill took frames to 20.7 records and the duty cycle to 37% — **and it is only free because layout 3 restored the per-record clock**, since under layout 2 delaying a frame moved every event in it | outpost 19, 20 |
| 89 | The signal baud default and the overlay's rate are numbers to tune, and raising the link rate is the straightforward lever → **the link has a hard ceiling at 460800 and neither end chose it.** The bridge **refuses to open above 750000**, tested straight against the port; the SoC's UARTE **has no baud between 460800 and 921600**, its rate table being a fixed ladder. **The two constraints intersect at exactly one useful value.** Worth noting what that costs: the rate that would have needed no Core-side configuration at all is the one this bench cannot do, so the override now has to be set and kept in step with the DUT overlay by hand | outpost |
| 90 | A signal tap opens Core's own port and writes what arrives verbatim, so the capture starts when the port opens → **a TX-only DUT has been transmitting the whole time, so opening the port hands you whatever the OS buffered before the study existed.** The first six records of a real trace carried a cycle count **195 seconds ahead of the seventh.** **Why this went unnoticed for two days: against Core's own monotonic arrival clock a stale prefix is *invisible*** — it reads as a capture that started earlier, and every number derived from it is plausible. It became visible within an hour of the UI timing spans by the DUT's own counter, which restarts at reset: **a 1.2-second capture's window came out as 11 ms and two lanes claimed a 9159% share** | core 30, outpost 17 |
| 91 | Keeping the HCI disconnect reason in a step's failure text "earned itself immediately" — strictly more diagnostic information at no cost → **the extra information is what stopped the information arriving.** A longer reason pushed the result frame past a length only long frames hit, **and the frame reached Core short of what its own framing byte promised**, so Core refused it and dropped the link. Three studies that died of an *already-documented* fault reported no step failure at all — only a decode error, **which reads as if the link, not the DUT, were at fault.** **Neither side was wrong on its own**, which is why nothing caught it: what was missing is a test at a *length* nobody had reason to pick | bench |
| 92 | Row 91's own diagnosis: a truncation in transit whose identifying fact is that "the number that identifies it is 16", so find the 16-byte boundary → **there is no boundary, there is no 16, and the sender was not losing bytes — it was ceasing to exist mid-frame.** dev-bench **resets partway through transmitting**: uptime across the gap proves a reboot inside 150 ms. Every fact that looked like a transport fault follows — the prefix is byte-perfect because transmission got that far, one run's last byte arrived wrong because **the line went idle mid-byte and the remaining bits sampled as idle**, and nothing follows at all because the bench is rebooting. **The 16 was an artifact of the diagnostic that reported it** — a delimiter-inclusive length subtracted from a delimiter-exclusive claim — **so an off-by-one in a debug message became the name of a bug and the shape of the investigation into it.** Two things to carry: **the fix that found the cause was the *resilience* fix** — making an undecodable frame cost the frame instead of the link let a run keep reading long enough to observe the silence, **and tolerating a fault is what exposed it**; and this was the **third** well-evidenced wrong answer on one fault, **each refuted by a check on the *other* end rather than more reading of the same bytes** | bench, core 40 |
