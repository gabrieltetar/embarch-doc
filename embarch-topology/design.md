# embarch-topology: design

**Status:** implemented, merged, and live-validated end-to-end, 2026-08-24. [gabrieltetar/embarch-topology](https://github.com/gabrieltetar/embarch-topology) is a real, pushed repo (the user created it after this session's own `gh repo create` attempt was blocked by its permission classifier — an outward-facing action — and CI ran green on push) with a real shared crate (`software` always available, `hardware` feature-gated) and a thin `embarch-topology` CLI/UI binary (`features = ["bin"]`), both built/tested/`clippy`-clean. `embarch-core`, `embarch-api`, and `embarch-umbrella` have each merged their `topology-integration` branch to `main` and pushed — `embarch-core` is deployed and live on the real Windows Core (confirmed via `GET /enroll`/`GET /status` reachability post-`update`); `embarch-api`'s locally-run debug binary (the one Claude Code's MCP config actually spawns) is rebuilt against the merged dependency. Both real boards (DUT nRF54L15, dev-bench esp32c5) are enrolled against the redeployed Core, and a real end-to-end `build_and_flash` + `run_study` (BLE connect + full GATT discovery) has completed clean — closing `embarch-topology/milestone-1.md` item 5. Along the way, running that first real study surfaced and fixed a genuine bug (decision 17: dev-bench's link-port serial needed to be its own declared fact, distinct from its JTAG probe's serial), redeployed live. What's still open: `milestone-1.md`'s deliberate-mismatch/alert/SSE sub-check (skipped this session — no legitimate way to inject a stale identity record without either a physical board swap or writing the live enrollment file directly, both declined) and §5's UI/UX and MCP-surface items.

## 1. Purpose and scope

The rest of the suite has no single abstraction for "topology" — meaning two different things, both currently handled ad hoc, scattered across env vars, config files, and doctor checks in different repos:

- **Software topology**: where each process runs relative to the others — `embarch-api` and `embarch-core` on the same machine, WSL2-hosted API talking to native-Windows Core, Core moved to a headless Raspberry Pi on the LAN.
- **Hardware topology**: what's physically wired to what — which USB port carries a given board's debug probe vs. its serial link, which physical board plays which role (DUT vs. dev-bench), what that role's board identity currently is.

`embarch-topology` exists to become the one place both live, so `embarch-core`, `embarch-api`, and `embarch-umbrella` stop each carrying their own detection/resolution logic for either kind.

**The incident that motivated this** (2026-08-21, mid-`embarch-roadmap.md` Milestone 3): dev-bench's runtime serial link moved from the ESP32-C5's native USB-JTAG peripheral to a second, dedicated UART port (`embarch-core/design.md` decision 21's final update, `embarch-dev-bench/design.md` decision 26). The migration was implemented and validated once, but the Windows Core service still had a stale `EMBARCH_DEV_BENCH_SERIAL` value in its own registry Environment key — a leftover from before the port migration. Nobody cleared it. `run_study` failed with a 404 naming the excluded candidate; diagnosing it required manually enumerating Windows serial ports, reading `service.rs` source to understand `install`'s current behavior, and reasoning by hand about which of two recognized-VID serial ports was actually correct. `embarch-topology` exists to make that class of problem instantly diagnosable from one place — and, as of decision 2/3 below, structurally impossible in the first place, since the stale-override mechanism that caused it is being removed rather than merely detected.

`embarch-topology` is **not**:
- A standalone network service that Core, `embarch-api`, or `embarch-umbrella` query over HTTP/IPC. It ships primarily as a shared library (decision 2) that those three compile in and call directly, in-process — nothing about it can be "down" the way a service call can fail.
- A background daemon or watcher. Nothing needs to stay running for Core to get a live, current answer — calling linked code directly *is* the live mechanism (decisions 2, 7). Its own CLI/UI binary (decision 5) still only runs when explicitly invoked, for a human.
- A second, parallel implementation living alongside Core's own enforcement. `board_gate`/`Filter::resolve`'s detection logic doesn't stay in `embarch-core` for `embarch-topology` to double-check from outside — it moves *into* the shared crate, and Core's job becomes calling it, not maintaining a copy (decisions 2, 8).
- Scoped to multi-board or Raspberry-Pi-as-first-class modeling yet — both explicitly deferred (§3 decisions 10, 11) until either scenario is real.

## 2. Architecture overview

```
embarch-topology ships as two things built from one codebase:

  1. a shared Rust crate — every piece of topology logic lives here:
       - software-topology class detection (local/wsl-host/remote)
         and bind-address rules
       - hardware-topology detection (VID/port heuristics, live
         hardware_id reads over the debug port)
       - enrollment storage: which hardware_id plays which role — a
         human's declared intent, not something detection alone can
         determine, so this is the one thing that's genuinely persisted
       - live validation (decision 8), the durable alert log, and the
         event stream a currently-open UI can subscribe to (decision 12)

  2. a thin binary (CLI + local web UI, decision 5) that calls into
     that same crate, for a human to inspect or fix things directly —
     it runs only when explicitly launched, same as before

embarch-core, embarch-api, and embarch-umbrella all depend on the crate
and call its functions live, in-process, at their own moment of need —
no shell-out, no hand-off file, no env var:

  Core, mid-`flash`/`reset`/`run_study`:
      topology::resolve_dev_bench_port()   -> live, fresh, every call
      topology::validate(...)              -> mismatch -> structured
                                               error + durable alert +
                                               live push if UI is open

  embarch-api, resolving `base_url = "auto"`:
      topology::resolve_software_topology() -> live, every invocation

  embarch-umbrella's doctor, checks 2/3/5/12/13/14:
      topology::resolve_*() / topology::validate() -> pass/fail/warn

The only state that persists anywhere is a human's declared intent
(which board is enrolled as which role; a remote Core's host address) —
and that storage lives inside the crate itself. Consumers call functions;
they never parse a topology-owned file directly (schema TBD, see §5).
```

`embarch-topology`'s own binary/CLI name is provisionally `embarch-topology`, matching the repo/crate name — unlike `embarch-umbrella`'s `embarch` binary, there's no equivalent "most-typed command" pressure here to justify a shorter name, but this is a placeholder, not a real decision (§5).

## 3. Locked-in design decisions and rationale

1. **`embarch-topology` is a resolution/abstraction layer, not just a checker.** The rest of the suite should be able to say "give me dev-bench" or "what's my `base_url`" and get a resolved answer, rather than each independently re-implementing VID heuristics or a WSL2-gateway probe. This is a deliberate step further than "read-only diagnostic tool" — it's the thing that produces the answer, not just the thing that flags when the answer looks wrong.

2. **Architecture: a shared crate that `embarch-core`, `embarch-api`, and `embarch-umbrella` all link and call in-process — not a doctor-style standalone tool with no code shared.** All topology detection, resolution, enrollment, and validation logic lives in one crate; Core/api/umbrella depend on it and call its functions directly, live, whenever they need an answer. `embarch-topology`'s own CLI/UI binary (decision 5) is just a thin wrapper over the same crate, for a human to run standalone.

    **Reversed 2026-08-21** from this session's own earlier decision, which picked a doctor-style tool specifically to avoid a shared library, reasoning that the suite had deliberately kept mirrored copies of cross-repo logic instead of extracting crates (`embarch-umbrella/design.md` decision 20). That reasoning held right up until working through decision 9's mismatch-detection design surfaced the actual cost of *not* sharing code: Core still needed either a written-ahead file or a manual override to know the current answer, and a manual override left unmaintained is exactly what caused the motivating incident. A shared crate that Core calls live removes the need for either — Core always computes the fresh, correct answer itself, because there's only one implementation of "how do I find dev-bench" anywhere in the suite. This is **not** a reintroduction of the "standalone service Core queries live" option rejected earlier — that was rejected because a network/IPC dependency in the hardware-operation path is a new thing that can be down; a compiled-in library call carries no such risk, since it's just code running in Core's own process. There's already suite precedent for exactly this shape of sharing: `embarch-study-designer` is a shared crate across `embarch-core`, `embarch-dev-bench` firmware, and `embarch-api` today — this extends the same pattern from shared *data types* to shared *logic*.

3. **Resolution timing: live, in-process, on every call — no write-ahead file for anything auto-detectable.** Core/api/umbrella call the crate's functions at their own moment of need — per-request for anything that can change while a process is running (e.g. dev-bench's port, which could change on unplug/replug), once at process startup for anything that can't (e.g. a bind address, fixed for the life of the listening socket). There is no separate resolve-then-write step and therefore nothing that can go stale between a write and a read.

    **Reversed 2026-08-21**, same session, alongside decision 2 — this session's earlier framing had `embarch-topology` write resolved answers into files Core/api/umbrella read locally. That model still left a real gap: it solved "the file might be missing" but didn't remove the *incentive* for a manual override to exist in front of it, which is what decision 9 was built to detect and is now retired to prevent instead (see decision 9). The only state that still needs writing anywhere is a human's declared intent that can't be derived by detection at all — which hardware_id is enrolled as which role, and a remote Core's host address — and that lives inside the crate's own encapsulated storage, not as a file any consumer parses itself.

4. **Scope reach: both software and hardware topology, in one pass, not hardware-first.** `known_boards.toml`/`board_gate`/the dev-bench port `Filter` heuristic (`embarch-core/design.md` decisions 21, 22, §5) *and* the software-topology-class detection today mirrored between `embarch-api` and `embarch-umbrella` (`embarch-umbrella/design.md` decision 6, guarded by decision 20's CI diff job) both move into the shared crate (decision 2) as the sole implementation. The mirrored-copy CI diff job becomes obsolete once those copies are deleted outright — there's nothing left to mirror once everyone links the same crate (tracked in §5).

5. **UI: a local web page, served by `embarch-topology`'s own process, for the duration of one explicit run.** Not a native app, not a TUI, not always-on. The server exists only while `embarch-topology` is running; it isn't installed as a service and doesn't survive a reboot. It's a thin wrapper calling the same crate functions Core/api/umbrella call (decision 2) — a human sees exactly what Core would compute, not a separate opinion. Bind loopback-only by default, same reasoning as `embarch-core/design.md` decision 6's amendment (no TLS, no reason to expose past localhost).

6. **Doctor integration: `doctor`'s topology-relevant checks call the shared crate directly, in-process — not a shell-out to a separate `embarch-topology` binary.** Checks 2 (Core reachable/topology class), 3 (token/bind-vs-topology), 5 (probe visibility), 12 (dev-bench port detected), 13 (dev-bench firmware match), and 14 (bind address vs. detected topology) — see `embarch-umbrella/design.md` §5's table — become thin wrappers translating a crate call's result into pass/fail/warn.

    **Reversed 2026-08-21**, same session: originally `doctor` was going to shell out to `embarch-topology`'s CLI, mirroring the precedent `embarch-umbrella/design.md` decision 17's amendment set for check 8 (shelling out to `embarch-api list-targets --json`). That precedent fit when `embarch-topology` was a separate process with its own `--json` contract; once it's a linked crate (decision 2), calling it directly is simpler and consistent with how Core and `embarch-api` now consume it too — no process-spawn overhead, no JSON boundary to keep in sync.

7. **Declared facts can be unset — an ordinary, expected state — but there is no longer a general "topology hasn't been resolved yet" failure mode.** Because auto-detectable topology is computed live on every call (decision 3), there's no file that can be missing or stale for it. What *can* be unset is a human's declared intent — no board enrolled for a role yet, or (for a `remote` Core) no host address declared — and calling a function that needs one of those returns a specific, named error ("no board enrolled as `dev-bench`; enroll one" / "no remote host declared for Core; set one"), scoped to exactly the missing fact, not a blanket dependency on having run `embarch-topology` first for anything at all.

    **Reversed 2026-08-21**, same session: this session's earlier framing had `embarch-api`'s `base_url = "auto"` and `embarch-umbrella`'s `setup`/`doctor` hard-depend on a resolved-state file existing, failing outright if `embarch-topology` hadn't been run first — a real breaking change to today's zero-config auto-detection UX, flagged at the time as needing its own onboarding migration. That cost goes away under the live/in-process model: `local`/`wsl-host` detection needs no prior declaration at all, so `base_url = "auto"` keeps working out of the box exactly as it does today, just backed by the shared crate instead of duplicated code. Only genuinely-declared facts (enrollment, a remote host) can be missing, which is the same shape of "not configured yet" state `known_boards.toml` already has today.

8. **One implementation, multiple call sites — not two independent layers.** `embarch-topology`'s standalone UI/CLI (decision 5) and Core's/`embarch-api`'s/`embarch-umbrella`'s own live calls (decision 3) run the exact same crate function, not two separate implementations aimed at similar behavior. A human running `embarch-topology` sees precisely the validation Core enforces live, because it *is* that validation — there's no way for the two to disagree, since there's only one of them. Concretely: whatever port/probe an operation is about to use, the shared `validate()` function confirms the device is currently enumerated and still matches the identity recorded for its role before the operation proceeds, and returns a specific error naming what's stale if it doesn't.

    **Reversed 2026-08-21**, same session, from an earlier framing that described `embarch-topology`'s ahead-of-time check and Core's live re-check as two independent, separately-reasoned mechanisms that happened to agree. They're not independent once both are calls into the same crate (decision 2) — this decision now just names that explicitly.

    **Real gap this surfaces, not yet closed:** `embarch-core`'s current `board_gate::enforce_for_role` only does this live-identity-recheck for JTAG-capable roles enrolled via `POST /probes/enroll`. The dev-bench runtime *link* itself (today's `Filter::resolve`, `embarch-core/design.md` §5) has no equivalent live check — this exact gap is what the shared crate's `validate()` needs to close as part of absorbing that logic, not something to leave behind in `embarch-core` (tracked in §5).

9. **RETIRED — explicit-override detection.** This session originally planned a dedicated mismatch class for "an env var or registry override disagrees with what would otherwise resolve," since that's precisely what caused the motivating incident (`embarch-core/design.md` decision 11's env-var-beats-`core.toml` precedence). **Superseded 2026-08-21, same session**, by decisions 2/3: env vars and registry-based overrides for anything topology-shaped (`EMBARCH_DEV_BENCH_PORT`/`_PRODUCT`/`_SERIAL`/`_INTERFACE`, `--bind`, `core.toml`'s dev-bench/bind fields) are abandoned outright, not merely checked for disagreement. `EMBARCH_TOKEN` is unaffected — that's authentication, not topology, and stays exactly as it is. Removing the override mechanism is a stronger fix than detecting when it's gone stale: there's no longer anything that can silently win over reality, so there's nothing left in this category to detect.

10. **Hardware topology scope: one DUT + one dev-bench per machine, today's real shape — not multi-board.** Matches `known_boards.toml`'s actual current shape. Roles are modeled as an extensible table (not a hardcoded pair) so adding a second board later isn't a rewrite, but no UI or logic for concurrent multi-DUT or dual-dev-bench scenarios is built now — those don't exist yet, even though decision 22 already flagged the risk (an eventual nRF54L15DK dev-bench sharing a chip family with an nRF54L15DK DUT).

11. **Software topology scope: reuses `embarch-umbrella`'s existing three-class model (`local`/`wsl-host`/`remote`); a LAN Raspberry Pi is an ordinary `remote` for now, not a distinct class.** `embarch-core/design.md` §7's anticipated Pi move hasn't happened yet; giving it dedicated modeling ahead of that move would be building for a scenario that isn't real, mirroring the same reasoning as decision 10.

12. **Alert delivery is durable + live-when-open; opening/focusing the UI and retrying are the caller's job; all of this lives inside the shared crate.** When the shared `validate()` function (decision 8) catches a mismatch, it (a) durably records it to a local alert log the instant it happens — nothing is lost to bad timing between the check and someone looking — and (b) if `embarch-topology`'s UI happens to already be open, pushes it there instantly via a small event stream the crate exposes, so the durable record and the live view are two ends of one alert, not separate mechanisms. Whichever consumer called `validate()` (Core, most often) gets back a structured `topology-mismatch` error including a URL back into `embarch-topology`'s UI, rather than a generic error string, so the fix is one click away from wherever the failure surfaced — and returns that same structured error to *its* caller unchanged.

    **Opening/focusing the UI is deliberately not Core's job.** Core is typically a Windows service running in Session 0 (`embarch-umbrella`'s topology iii — the real primary deployment today) or, eventually, a headless Raspberry Pi with no desktop at all; neither can reliably make a window appear on an interactive desktop. Whatever's actually in the user's hands at the moment of failure — `embarch-api`'s CLI, or `embarch-topology` if it's already running — opens or focuses the UI from the structured error instead, since that tool runs in the user's own session with none of Core's platform restrictions.

    **Retry is just calling the operation again — no queue, no auto-resume.** Once the user fixes the config in the UI, they (or the agent acting on their behalf) re-invoke the original command. `flash`/`reset`/`run_study` are already safely re-invocable.

    **Revised 2026-08-21, same session:** the alert log, event stream, and structured-error shape were originally scoped as three new surfaces `embarch-core` would need to build itself. Under decision 2's shared-crate model they're crate-internal facilities instead — Core (and `embarch-api`/`embarch-umbrella`, wherever they call `validate()`) just gets the structured result back; it doesn't implement logging or eventing itself.

13. **Stays a design-only doc under `embarch-doc/`, no repo yet.** Matches how `embarch-umbrella` and `embarch-dev-bench` both started. Creating `gabrieltetar/embarch-topology` is a real next step once there's a concrete first implementation plan — noted here, not assumed or silently deferred. Worth flagging given decision 2: a shared crate needs *somewhere* for `embarch-core`/`embarch-api`/`embarch-umbrella` to depend on (a path or git dependency at minimum), which likely pulls "when does a real repo need to exist" earlier than a design-only doc's usual timeline — see §5.

14. **The web UI's one interactive surface is hardware enrollment; software topology stays read-only — a deliberate split, not just what happened to get built first, 2026-08-23.** Closes §5's "no enrollment form (enrolling is CLI-only)" open item, prompted by trying to actually use the UI against real hardware for the first time (plugging in both boards post-deploy, discovering enrollment hadn't moved to `embarch-topology`'s own storage — see decision 2's storage-location text — and needed redoing). The line isn't arbitrary: **hardware enrollment is the one place in this entire suite that structurally requires a human** — no software can derive which physical board a probe is wired to, only a person physically isolating it and saying so (decision 22's own reasoning in `embarch-core/design.md`, inherited here). Everything else this crate resolves — software topology class, dev-bench port detection, live identity re-validation — is already fully automatic (decision 3), so there is nothing for a human to *submit* about any of it, only something to *watch*. No software-topology equivalent was added, and none is planned unless a genuinely undeterminable fact shows up (§5 already names one candidate — a remote Core's declared host address — not yet even given storage, let alone a UI). This framing — hardware-enrollment-is-the-one-interactive-thing — holds; *where* that interaction lives is reversed immediately below.

    **Reversed same day, 2026-08-23:** this decision originally put the form in `embarch-topology`'s own standalone UI — `bin/ui.rs`'s index page gained `POST /enroll`, calling the exact same `hardware::enroll` function the CLI and Core's `POST /probes/enroll` already call. Correct code, wrong place: pointed out directly — real hardware I/O and the system-file write it produces should be done by `embarch-core`, which already does *exactly* that for `POST /probes/enroll`, under its own `hw_lock`. A second process (`embarch-topology.exe ui`) calling the identical underlying function doesn't share that lock, and makes a human start and stop a whole separate binary to reach something Core — already running, always, as an installed service — can serve directly. The enrollment form moved to `embarch-core`'s own new `GET /enroll` (`embarch-core/design.md` §3 decision 25) instead. This crate's own UI (`bin/ui.rs`) reverts to fully read-only — enrolled boards, currently-attached probes (`list_attached_probes`, kept — still useful as a live readout), recent alerts, a link to Core's `/enroll` — and no longer accepts any submission at all. `list_attached_probes()` itself is kept in the crate (not reverted) since it's genuinely useful, read-only, and now also informs a human *before* they go to Core's page. Net effect: enrollment now has exactly one route to it, not two independently-invokable ones that happened to agree today and could silently drift apart tomorrow — the same "one implementation, multiple call sites, not two independent layers" principle decision 8 already established for `validate()`, now honored for `enroll()` too.

15. **`hardware::enroll` gains an optional `probe_serial` parameter — enrolling two visibly-different boards no longer requires isolating them one at a time, 2026-08-23.** Prompted directly: a human enrolling both real boards (a J-Link DUT and dev-bench's own ESP JTAG, already both plugged in) shouldn't have to unplug either just because `enroll`'s original "exactly one probe attached" check couldn't otherwise tell them apart — when the probes are already distinguishable (different `identifier`/serial), that requirement is stricter than the actual ambiguity problem it exists to solve. `enroll(role, chip, probe_serial: Option<&str>)`: given, selects that specific attached probe by serial (matching `embarch-core`'s own `flash`/`reset` disambiguation shape, decision 9 there — extending an existing suite pattern, not inventing a new one); omitted, falls back to the original "exactly one attached" requirement unchanged, so every existing caller (the CLI's own `enroll --role --chip`, without `--probe-serial`) keeps working exactly as before. First real consumer: `embarch-core`'s `/enroll` page's drag-and-drop UI (`embarch-core/design.md` §3 decision 25's revision), which always sends `probe_serial` since it always knows exactly which card the human dropped.

    **What this does not, and cannot, close:** two boards sharing an identical probe type (decision 10's own flagged risk — an eventual nRF54L15DK dev-bench alongside an nRF54L15DK DUT) still can't be told apart by `identifier`/serial alone, which is all a human (or this parameter) has to go on without physically isolating them. `enroll`'s live hardware-ID readback still catches a wrong *chip name* for whichever probe got picked; it can't catch "right chip, wrong physical board" when both really are that chip. No UI can enroll around that — it still needs one-at-a-time isolation, same as before this decision.

16. **New `hardware::check_target_powered` — early diagnosis for an unpowered target, instead of `probe-rs`'s raw ARM/access-port error chain, 2026-08-23.** Found live, directly: the real nRF54L15 DUT enrolled this session turned out to be genuinely unpowered, and every attach attempt failed with a generic error a human has to already know how to read. Reads the probe's own sensed target-voltage pin (`Probe::get_target_voltage`) immediately before attach, in this crate's two attach sites (`enroll`, `validate_known`'s live re-check) — `embarch-core`'s own `flash`/`reset` carry the other half of the same fix (`embarch-core/design.md` §3 decision 26), calling this crate's exported wrapper. A reading under 1.0V fails fast naming the actual likely cause; not every probe type supports the reading (`Ok(None)`), and an ambiguous or plausible one just proceeds to attach normally — best-effort diagnosis, not a new hard gate. `cargo build`/`cargo test --features hardware`/`cargo clippy --features bin --all-targets -- -D warnings` clean.

17. **New `EnrolledBoard::link_port_serial` — a second declared fact for dev-bench, distinct from its JTAG probe's serial, 2026-08-24.** Found live, running the first real `run_study` against both real boards enrolled together for the first time: `resolve_dev_bench_port` reported dev-bench's detection as ambiguous between its real link (a Silabs CP210x bridge, `COM13`) and the DUT's own separate J-Link's VCOM interface (`COM5`) — both pass the SEGGER/Silabs-VID + product-string filter, and `Filter::resolve`'s only disambiguation signal (the enrolled dev-bench-role probe's *JTAG* serial) can never match either, because dev-bench's link moved to a dedicated UART bridge chip that's a different physical USB device from its JTAG probe (`embarch-core/design.md` decision 21's port migration) — the JTAG-probe-serial fallback assumed those two were the same device, which held until a second SEGGER-VID device (a DUT with its own probe) was enrolled onto the same bench at the same time, never previously exercised.

    Fix: `EnrolledBoard` gains `link_port_serial: Option<String>` — the link port's *own* USB serial, a directly declared fact (no `hardware_id` readback is possible over a plain UART, so this can't be inferred the way JTAG identity is), settable via new `hardware::set_dev_bench_link_port_serial` (amends an already-enrolled row; never creates one). `Filter::resolve` prefers it, hard (`serial_is_fallback: false`), over the old JTAG-probe-serial fallback whenever it's set; unset, behavior is unchanged (today's common case where the link and the JTAG probe really are the same device keeps working exactly as before). Exposed two ways, matching decision 8's "one implementation, multiple call sites": `embarch-topology set-dev-bench-link --serial <serial>` (CLI, writes the crate's own storage directly — usable when running the CLI has write access to `enrollment.toml`) and `embarch-core`'s new `POST /dev-bench/link` (goes through Core's already-elevated service process, same reasoning as decision 14's enrollment move — a plain-user CLI run on the live Windows deployment hit exactly the NTFS permission wall that motivated Core, not a second process, owning system-file writes). `cargo build`/`test --features hardware`/`clippy --features bin --all-targets -D warnings` clean in both crates; new unit test reproduces the exact real ambiguity (Silabs bridge + a different-role SEGGER probe) and confirms a declared `link_port_serial` resolves it. Verified against the real live deployment: declared dev-bench's actual bridge serial via the new endpoint, then a real `run_study` (BLE connect + full GATT discovery against the freshly-flashed DUT) completed both steps `Pass`.

## 4. Relationship to existing sub-projects

**Implemented 2026-08-21** — each bullet below now describes shipped code (built/tested/`clippy`-clean against the real crate dependency), not a plan, though none of it is deployed/merged yet (Status line, `milestone-1.md`).

- **`embarch-core`** lost its own copies of `board_gate`'s live-identity-recheck logic, `known_boards.toml`'s storage, `hardware_id.rs`, and the dev-bench `Filter` heuristic (`dev_bench.rs`) — deleted outright, replaced by `embarch-topology = { path = "../embarch-topology", features = ["hardware"] }` and calls into `embarch_topology::hardware` (decisions 2, 3, 8, and `embarch-core/design.md` §3 decisions 22, 23). Core keeps the hardware-I/O-specific plumbing (actually opening a `probe-rs`/`serialport` handle, `hardware.rs`'s `resolve_probe`/`open_probe`) and calls the crate for "which port/probe, and is it still valid." Real behavior change beyond the move: `EMBARCH_DEV_BENCH_PORT`/`_PRODUCT`/`_SERIAL`/`_INTERFACE` are gone, no replacement (decision 9).
- **`embarch-api`** lost its own software-topology-class detection code (`topology.rs`/`env.rs`/`probe.rs`) for `base_url = "auto"` (decision 4) — `embarch-topology = { path = "../embarch-topology" }` (no `hardware` feature; confirmed via `cargo tree` that probe-rs/serialport never appear), `core_client.rs` calls `embarch_topology::software::resolve_software_topology()` live, in-process, on every invocation (decision 3). Its existing declared-`base_url` fast path (skip probing outright) is unchanged — only the `"auto"` branch calls the crate.

## 5. Open questions / future work

Resolved during implementation, 2026-08-21 (kept here rather than deleted, per DOC-PROTOCOL.md §5's "record what you actually decided and why" — full detail in each item's own file/decision):

- ~~**The shared crate's public API shape.**~~ Resolved: `software::resolve_software_topology(port, host, declared_base_url)` (owns the WSL2/gateway/probe I/O itself, decision 2's reversal) plus the pure `candidates`/`classify_status`/`resolve`/`winner`/`detect_wsl2`/`parse_default_gateway` building blocks, all sync except `resolve_software_topology` itself; `hardware::{resolve_dev_bench_port, enroll, validate_serial, validate_role, list_enrolled, find_enrolled_by_role, recent_alerts}`, all sync (callers on an async runtime wrap in `spawn_blocking`, same as `embarch-core` already did). Errors are plain `anyhow::Result`, with `TopologyMismatch`/`DevBenchNotFound` as downcastable structured types for the two cases callers need to branch on — the same idiom `embarch-core`'s own `NotFound` already established, not a new pattern.
- ~~**Cross-repo dependency management.**~~ Resolved: a plain path dependency (`{ path = "../embarch-topology" }`), exactly `embarch-study-designer`'s existing precedent, with `features = ["hardware"]` added only by `embarch-core`. Release CI needed a real fix beyond just adding the dependency line: each consumer's `release.yml` only ever checked out itself, so a relative `../embarch-topology` path could never resolve — fixed by checking out every path-dependency repo as a named sibling directory and running the build from inside the consumer's own subdirectory. Found the same gap already existed for `../embarch-study-designer` (added 2026-08-19, never actually exercised by a green release run since) — fixed in the same pass. **Theoretical doubt resolved 2026-08-24, real-run confirmation still open**: whether `cross`'s Docker-based aarch64 build (`embarch-core`'s own release leg) can see sibling directories outside the crate root — researched against `cross-rs/cross`'s own history rather than assumed (no Docker available in this dev sandbox to run it for real): [`cross-rs/cross#684`](https://github.com/cross-rs/cross/pull/684) (merged, shipped `v0.2.2`+) auto-mounts any path dependency `cargo metadata` can see, no formal `[workspace]` required — exactly this repo's plain `path = "../..."` shape. `release.yml`'s own comment updated with the citation. What's left is the cheap, mechanical part: an actual tagged-release CI run to confirm it for real, not an open question about whether the mechanism exists.
- **`embarch-core` still needs to close the live pre-flight identity-check gap on the dev-bench runtime link — partially closed, not fully.** `hardware::validate_role` re-verifies the enrolled JTAG-capable probe's live identity on every call (what decision 8 asked for), and `embarch-core`'s dev-bench handshake already calls it before opening the link. What's still open, and looks structurally unclosable without a firmware protocol change: confirming that the *specific currently-detected UART port* (a separate physical USB device from the JTAG connection, since the port migration) is wired to the *same chip* the JTAG side just verified — nothing observable over USB proves that today. Closing it fully would need dev-bench's own `HelloAck` to carry a hardware ID read over the link itself, not something this crate can add unilaterally. See `hardware::validate`'s own doc comment.
- ~~**Crate-internal storage schema/location for enrollment and remote-host declarations.**~~ Resolved for enrollment: `<machine_data_dir>/topology/enrollment.toml`, reusing `known_boards.toml`'s old machine-wide root (`%ProgramData%\embarch` / `/var/lib/embarch`) under a new `topology` subdirectory this crate owns outright (alongside `alerts.jsonl` and the UI's `ui.addr` marker). **A remote Core's host address has no storage yet at all** — every consumer today declares it in its own config (`embarch-api`'s `[core].host`, `embarch-umbrella`'s `state.rs`), not through this crate; whether that should move into the crate's own storage too is still open, and nothing here forces it to.
- **Can a declared fact itself go stale?** Still open, unchanged by this pass — an enrolled `hardware_id` whose board was physically replaced only surfaces the next time `validate()` happens to run against it, same as before.
- **Call-site granularity isn't fully specified — still mostly true.** `resolve_dev_bench_port`/`validate_*` are fresh-every-call by construction (no cache in the crate). `software::recommended_bind_address(TopologyClass)` exists for the once-at-startup case decision 3 named, but nothing calls it yet — `embarch-umbrella`'s `setup` is the intended caller and hasn't been wired (`embarch-umbrella/design.md` §3 decision 22's own note on this).
- ~~**Removing the mirrored-copy CI diff job.**~~ Resolved: `embarch-umbrella/design.md` decision 20 updated in place — the CI diff job it proposed was never actually built, and is now permanently unnecessary for the topology-detection copy specifically (nothing left to diff, both consumers link the crate directly). Narrowed, not fully retired: `token.rs`/`config.rs`'s own unrelated mirrors of `embarch-api`-internal logic are untouched by this move and still raise the same question independently.
- **Web UI content — an MVP shipped, not a designed UX; enrollment moved out of it entirely, 2026-08-23.** Decision 14's reversal moved the one interactive surface this page ever had (the enroll form) to `embarch-core`'s own `GET /enroll` — this crate's UI is now fully read-only (enrolled boards, currently-attached probes, recent alerts). Still open, and now scoped to Core's page instead: no topology diagram, no click-to-fix flow beyond a plain link (a `TopologyMismatch`'s `fix_it_url` still lands on this crate's own read-only `/mismatch/{id}`, not something that pre-fills Core's enroll form). A per-alert "re-enroll the board this alert is about" action, linking straight into Core's `/enroll` with the role pre-filled, is the natural next step, not yet built.
- ~~**Binary/crate naming.**~~ Resolved by not changing it: `embarch-topology` for both the crate and the binary, confirmed rather than left as a placeholder — no naming pressure surfaced once actually building it (unlike `embarch-umbrella`'s `embarch`, nothing here is typed often enough to want a shorter form).
- **MCP/agent-invoked calls and decision 12's caller-opens-the-UI behavior — still open, and not yet even wired up to test against.** `embarch-api` has no MCP tool today that calls into `embarch-topology`'s `validate()`/alert surface at all (`enroll_probe` only ever called Core's `POST /probes/enroll`, unaffected either way) — so the "relay, don't auto-open" leaning has nothing exercising it yet. The CLI itself already behaves that way by construction (`embarch-topology validate` prints the mismatch and its `fix_it_url` to stderr, never opens a browser), which is *consistent* with the leaning but doesn't confirm it for the MCP case this question is actually about.
- ~~**First-rollout migration.**~~ Done, for the crate side: `embarch-core`/`embarch-api`/`embarch-umbrella` are all wired and passing `cargo build`/`test`/`clippy --all-targets -- -D warnings` against the real dependency, each on its own local `topology-integration` branch. **Not yet deployed** — none of the three branches are merged to `main`, pushed, or built against the live Windows Core; that live cutover (and the GitHub repo push blocked this same session, see the Status line) is the actual remaining rollout step, tracked in `milestone-1.md`.
