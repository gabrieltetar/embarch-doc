- 2026-08-25 — **§5's longest-standing structural hole is closed, and this crate turned out to be part of the fix after all.** New `hardware::compare_self_reported` + `SelfReportedIdentity`, called by `embarch-core`'s dev-bench handshake (`embarch-core/design.md` §3 decision 35) to relate a bench's self-reported chip ID to the one `hardware_id::read` gets over JTAG. §5 had twice recorded that "this crate again needs no change" — true of the wire protocol, false of the comparison, which is chip knowledge and belongs here by §3 decision 2. The `esp32c5` relation is derivable rather than guessed: Zephyr's `hwinfo_esp32.c` reads `EFUSE_RD_MAC_SYS0/SYS1` at the same addresses this crate declares, verified against the checked-out HAL headers. Unknown chips return `Undeclared`, which Core treats as "could not ask" and never as a pass. `validate.rs`'s doc comment, which called the gap unclosable, is corrected. `cargo test --all-features` 47 (up from 43), `clippy --all-targets --all-features -- -D warnings` clean. Not exercised against real silicon — no board attached.

- 2026-08-21 — **`software` split into its own default-on feature, separate from `hardware` — found while preparing to merge the three consumer branches, via `cargo tree`.** `reqwest` (needed only by `resolve_software_topology`) transitively pulls in `aws-lc-sys` (rustls's default crypto provider), a real C-toolchain-needing build dependency — harmless for `embarch-api`/`embarch-umbrella` (which already need `software` anyway) but a pure, avoidable regression for `embarch-core`, which never calls into `software` at all and is the one consumer whose real deployment target (a native Windows build) `embarch-dev-workflow.md` §4 already flags as sensitive to exactly this class of dependency. - 2026-08-21 — **Major architecture reversal**, same design-only session, prompted by a request to abandon env-var/registry overrides entirely and have Core call `embarch-topology`'s detection code directly rather than carry its own. Decisions 2, 3, 6, 7, 8, and 12 rewritten in place (each keeps its number and now describes current reality plus a same-session reversal note, matching `embarch-umbrella/design.md`'s convention for in-place decision revision); decision 9 retired outright rather than renumbered, since the override mechanism it was built to detect no longer exists. New shape: `embarch-topology` ships primarily as a shared Rust crate (precedent: `embarch-study-designer`'s existing role as a shared crate for data types, extended here to shared logic) that `embarch-core`, `embarch-api`, and `embarch-umbrella` all depend on and call live, in-process — confirmed via `AskUserQuestion` to extend to all three, not Core alone. This removes the write-ahead file and its staleness/missing-state failure mode for anything auto-detectable, and removes env-var/registry overrides for topology-shaped config outright (`EMBARCH_TOKEN` unaffected — not a topology concern). §1's "is not" list, §2's architecture diagram, and §4's per-sub-project relationships rewritten to match; §5 pruned of questions this resolved (schema-location uncertainty is now crate-internal and consumer-invisible; the onboarding-migration concern shrinks to a one-time rollout note) and gained new ones this raises (crate dependency management across sibling repos, call-site granularity, declared-fact staleness).
- 2026-08-21 — New decision 12 (alert delivery, UI-opening, retry): Core's live catch (decision 8) is now durably logged and, if `embarch-topology`'s UI is already open, pushed to it live via a small event stream; Core's failed-request response carries a structured `topology-mismatch` error with a fix-it URL. Opening/focusing the UI is explicitly the caller's job (`embarch-api` CLI or `embarch-topology` itself), not Core's — Core is typically a Session-0 Windows service or a headless Pi, neither of which can reliably show a window, the same wall decision 22 already hit. Retry is just re-invoking the operation; no queue or auto-resume. Prompted by a request to have Core "push a live alert to a UI on its own" on top of the ahead-of-time check — resolved via `AskUserQuestion` into durable-log-plus-live-push for delivery, and caller-opens/manual-retry for the UI-and-retry half.
