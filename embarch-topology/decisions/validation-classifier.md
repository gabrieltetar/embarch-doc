# embarch-topology decisions: The chip classifier behind the identity gate

**Status:** active, 2026-09-11.

Which register pair (or eFuse) a chip name resolves to for the self-reported-ID comparison, and the one classifier both `read` and `is_nordic_deviceid_chip` share. What the comparison itself asserts, and what it cannot, is [validation.md](validation.md) decision 21 — this file exists because a second question (coverage: which chips this arm even applies to) grew past that one's room.

Index: [../decisions.md](../decisions.md). Current truth: [../spec.md](../spec.md).

### 25 — `read` and `is_nordic_deviceid_chip` share one chip classifier; an unlisted nRF54L name no longer falls through to the classic address

Decision 21's arm rests on `read` and `is_nordic_deviceid_chip` agreeing on exactly which chips get the `FICR.INFO.DEVICEID` pair — that is the whole basis for deriving the self-report relation rather than guessing it. They were two separate matches instead: `read` listed four exact nRF54L names, then fell through to `c.starts_with("nRF5")` for everything else Nordic-shaped, and `is_nordic_deviceid_chip` duplicated the same four-name list. `"nRF54"` starts with `"nRF5"`, so any nRF54L or nRF54H spelling **not** one of those four exact strings — `nRF54L47`, `nRF54LM10`, a lowercase `nrf54l15_cpuapp` — matched the classic arm's `starts_with` guard first and never reached the newer pair, in both functions at once, silently, for the same input.

**The fix is one function, `classify_chip`, that both call.** It checks `nrf54l` (lowercased, so case and suffix don't matter) before the classic `nrf5`/`nrf9` prefix, so the newer family's names can no longer lose to the broader prefix that happens to contain them. `read` matches on its result to pick a register pair or bail with the named unrecognized-chip error; `is_nordic_deviceid_chip` reduces to "did this classify as either Nordic family" — the two cannot disagree because there is only one decision left to make.

**Why lowercase, when decision 21's four names were exact-case.** `embarch-core`'s `flash_backend.rs` already treats `chip.to_ascii_lowercase().starts_with("nrf54l")` as the test for "needs the vendor RRAM tool" — the flash path already accepts `nrf54l15_cpuapp` and unlisted parts like `nRF54L47` (`requires_vendor_tool`, and its own `an_unknown_nrf54l_part_is_still_refused` test). Hardware-id readback classifying a narrower set than the flash path already accepts was the actual defect; matching flash_backend's rule closes the gap on this side without proposing this crate depend on that one. **The two matchers are not unified across repos** — that would touch `embarch-core`, which this task does not own — so an `inbox/` drop records the option for whoever owns that boundary.

**nRF54H is refused outright, and that arm was corrected by the supervisor before this decision landed.** The worker's first version routed any `nrf54h` spelling to the `INFO.DEVICEID` pair alongside nRF54L, and this entry described it as if that were part of the same fix. It is not: decision 21's evidence for `0x00FF_C304`/`0x00FF_C308` is entirely nRF54L — three nRF54L15s read over JTAG, one HAL cross-check — and nothing in this repo or in `embarch-core` says anything about the Haltium family's FICR layout. So `classify_chip` checks `nrf54h` **first** and returns `None`, which is a named unrecognized-chip error. Checking it first is load-bearing rather than tidy: the classic arm's `nrf5` prefix would otherwise swallow it, which is exactly how the original defect worked. **The old code's behaviour was also a guess** — nRF54H fell through to the classic pair — so this is not a regression being avoided but a guess being retired, and it was available to retire because this task's own text authorised either the `INFO.DEVICEID` arm *or* the named error. When an nRF54H is enrolled, the way in is a register read on real silicon.

**What this does not change:** the register addresses themselves (still decision 21's, unverified past three nRF54L15s and the one confirmed `INFO.DEVICEID` pair), and the fallback-register exposure decision 21 already accepted — a chip whose device ID is truly inaccessible still comes back *mismatch*, not *undeclared*, on either classification.

**Amended 2026-09-10 (`tasks/suite/024`), on two counts.** First, this entry used to say that `embarch-core`'s `flash_backend.rs` "stops at `nrf54l` too", offered as corroboration for refusing nRF54H here. **That is no longer true and the sentence is removed rather than softened:** `embarch-core` decision 49 extended `requires_vendor_tool` to match `nrf54h` as well, because an nRF54H name was silently falling through to `false` and reaching probe-rs with no message at all. Both repos still refuse nRF54H — but they refuse it *in opposite directions*, and that is the point the deleted sentence obscured. `classify_chip` returning `None` means **"I cannot answer which register pair holds this chip's ID"**; `requires_vendor_tool` returning `true` means **"I can answer, and the answer is: keep probe-rs away from it."** One is an abstention, the other a positive refusal, and reading the second as agreement with the first is how a future change unifies them by mistake.

Second, and following from it: **the two matchers are not going to be unified, and this is where that is written down from this side.** The option was left open above and filed to `inbox/`, becoming `tasks/suite/024`; `embarch-core` decision 49 settled it on its own side by declining. The suite-level reason is the one just given — they answer different questions with different codomains. `classify_chip` is a three-way judgment over which register pair (or eFuse) holds a factory device ID, with `None` for "unrecognised"; `requires_vendor_tool` is a boolean over whether probe-rs's flat-NVM erase/write model is safe. There is no shared return type that serves both without one caller re-deriving its own answer from the other's, which is two matchers again with an indirection in front. **They agree on the nRF54L prefix by shared evidence, not by shared code, and that is the intended arrangement** — so a future reader finding the duplication should read this paragraph rather than file it as a fresh finding for a third time.

**One inconsistency left deliberately, so nobody has to rediscover it.** `esp32c5` is still matched case-**sensitively**, by exact string, before the lowercasing — so `ESP32C5` or `esp32-c5` reaches the named error rather than the Espressif arm. That is the safe direction and no other spelling of it has ever appeared in this suite, but it is now the one arm that does not follow the rule the paragraph above spends its length justifying, and it is unargued rather than argued.

**Amended 2026-09-11: an ST arm, and the first prefix that stops at a *family* rather than a vendor.** Enrolling a NUCLEO-G0B1RE hit `read`'s named error, so the gate refused every flash to it — the first time this classifier's *coverage*, not its correctness, was in the way. `classify_chip` gains `Stm32G0Uid` for `stm32g0`, read as the three words at `UID_BASE` (`0x1FFF_7590`/`4`/`8`). Evidence, unusually, both documented and observed: every `stm32g0*xx.h` in `hal_stm32` defines it, Zephyr's `hwinfo_stm32.c` reads three `LL_GetUID_Word*` from that base, and a real NUCLEO-G0B1RE enrolled off it.

**`stm32g0`, not `stm32`, is the arm's whole design.** `UID_BASE` moves between STM32 families (F4 `0x1FFF_7A10`, H7 `0x1FF1_E800`), so a vendor-wide prefix would read whatever sits at the G0 address on an unrelated part and return a plausible-looking string. Same shape as the nRF54H refusal above, inverted: there a family was carved *out* of a prefix that would have swallowed it; here a prefix is not widened to the vendor it could cover. The `STM32F407VG` test now guards that narrowness, with an H7 and an L4.

**96 bits needed a third word, so `read_two_words` became `read_words` over a slice** — one definition of what an ID string is. A two-word slice emits byte-identical output, so every `hardware_id` already in `enrollment.toml` still compares equal; without that, this would have silently invalidated both enrolled Nordic boards at their next gate check. Tested. `is_nordic_deviceid_chip` is untouched, so STM32 parts get `Undeclared`, already specified as not a match.
