### 21 — The self-reported-ID comparison gains a Nordic arm; the gate had never once run against Nordic silicon

Core's gate confirms the board answering on the runtime link is the same silicon its JTAG probe just verified. It shipped with **an exact-match shortcut good for any chip, exactly one declared relation beyond that, and a deliberate rule that every chip with neither returns undeclared** — *"not a pass: a comparison that could not be made is not a comparison that succeeded."* **That rule held. What it also meant is that the moment the bench stopped being that one chip, the gate stopped concluding anything**: the two sides' halves-swapped encoding meant the exact-match shortcut could not fire either, so it reported undeclared while showing two obviously-related IDs — **the same sixteen hex digits with their halves swapped.**

**The arm is derived, not fitted to that observation** — the standard the module sets is *both implementations' actual register reads, in view at once.* Zephyr's Nordic driver reads the pair in index order **and then emits it reversed on purpose**; the byte-emission and hex-encoding orders match on both sides, so **each half encodes identically and only their order differs. The observed pair confirms the derivation, it is not its source.**

One conditional branch covers both of Nordic's device-ID register layouts, so **one relation serves the classic parts and the nRF54L series alike.** That same code falls back to other registers for parts where the device ID is inaccessible, and **those produce something this projection does not describe** — such a chip comes back *mismatch* rather than *undeclared*, **the one way this arm can be wrong**, the same exposure the first arm already carries.

**Why a decision, not a bug fix:** decision 10 flagged the risk of a dev-bench sharing a chip family with the DUT, **and that is now the bench** — two boards of the same chip, two probes of the same vendor, two VCOMs each. **The gate that distinguishes them is the only thing standing between "the probe verified board A" and "board B answered on the link", and until this arm existed it was returning undeclared for both of them.**

**This arm turned out to confirm the register addresses it reads, which was not why it was built.** The nRF54L device-ID pair was the crate's one address taken partly on inference: the first word came from a real user's working read, and **the second was derived from the classic layout's two-word stride** and had never been checked against silicon. A match here settles it, because the two sides reach the registers by routes that share nothing: JTAG reads two hardcoded absolute addresses over the probe; the board's self-report goes through the vendor HAL's own device-ID accessor, which has never heard of those constants. On the dev bench they agree exactly, halves swapped as derived — **JTAG `6fcddc36cb781b71`, self-reported `cb781b716fcddc36`, relation *match*** [measured 2026-08-31, reproduced 2026-09-06 22:07:51Z and 22:15:45Z from Core's own handshake log]. The **second** word carries the weight: a wrong address there would still have produced a plausible, distinct-looking 64-bit value, and could not have produced the HAL's `DEVICEID[1]`.

**What it does not confirm, kept explicit because the temptation is to round it up.** This is one board. The DUT's readback rests on the same code arm and the same chip family, but nothing corroborates its 64 bits independently — its firmware speaks no handshake that self-reports, so the relation cannot run on that end at all. Three distinct nRF54L15s have now been read (`6fcddc36cb781b71`, `834f2559f10a6cdf`, `2f77b9c3f85b29e9`) and **all six words are distinct**, which rules out the second address landing on something family-constant, but that is corroboration and not the same proof. `nRF54L10`, `nRF54L05` and `nRF54LM20A` share the arm and no such silicon has been on this bench.

Which chips this arm's register pair actually covers — and how that coverage is decided — moved to [validation-classifier.md](validation-classifier.md) decision 25, once a second consumer (the flash path's vendor-tool refusal) needed the same answer.

### 38 — An ID read back as all zeros or all ones is a failed read, not a different board

On 2026-09-12 a NUCLEO-G0B1RE enrolled as `00250010343650172037334b` read `000000000000000000000000` three times within a minute, and the gate reported a **mismatch** (a different board) and refused flash and reset on a board that was the right one. On 2026-10-06 the same board, the same probe-rs (0.31.0) and the same `UID_BASE` reads gave the enrolled ID every time: running, connected under reset, and with the enrolled `STM32G0B1VE` chip name instead of the board's `RE`. Core's logs for that day had rotated out, so **the cause is unknown and recorded as such**: the read was transient.

What can be fixed is the classification. **No factory-burned ID has every word the same**, so `hardware_id::read` retries such a read once and then fails it by name ("the target did not return its ID"), which the gate reports as an unreadable board, not as a mismatch. A mismatch alert accuses the board; a failed read says the read failed, which is what happened.

**Widened the same day from all-zeros/all-ones to any repeated word.** An STM32G0 DUT asleep with its system bus unclocked (DHCSR `S_SLEEP` set, firmware in a deep low-power state) gave probe-rs `00000e80` in all three words and J-Link Commander zeros, for flash, SRAM and `UID_BASE` alike, and enrolment recorded `00000e8000000e8000000e80` as its ID. The debug port and the core's own debug registers answer in that state; the bus behind them does not.

**Rejected: retry until it reads.** One retry covers a transient; a loop would hold `hw_lock` against a board that genuinely cannot answer.

### 39 — Attach without rewriting a running target's clocks; read the ID halted when running reads are not good

Root cause of decision 38's readings, found 2026-10-06 on an STM32G0 DUT: the G0 reference manual's debug chapter says that in Sleep the bus matrix clock is off when no bus master is on, so with both DMA clocks disabled a debugger read of SRAM during Sleep "is not possible (returns 0x0)". Firmware that idles in WFI therefore answers every running debug read of the system bus (SRAM, flash, the UID, peripherals) with 0 or the previous word, acknowledged OK; the core's own debug registers still answer. Setting `DMA1EN` over the debug port made every running read correct and clearing it broke them again; a board whose firmware turns a DMA clock on (a NUCLEO-G0B1RE build) never shows it.

**That made probe-rs's ARMv6 STM32 sequence destructive.** It read-modify-writes the RCC register holding the DBGMCU clock enable and DBGMCU's control register at attach and at session end, core running or not; on a sleeping G0 the read returned `0x00000E80` and the write switched off the DUT's USB, PWR and I2C clocks until a reset. Every enroll and validate did it. **`hardware::attach::attach` swaps that sequence for one that does the same writes only on a halted core** and leaves a running core's RCC and DBGMCU alone; every other chip attaches as before. Given up: probe-rs no longer enables debug in Stop/Standby on a running board, which no caller here needs.

**The ID read then falls back to a halted read**: after decision 38's retry, `hardware_id::read` halts a running core for the three word reads and lets it run again. A halted debug read is always good, and the halt lasts microseconds. **An STM32G0's UID is always read halted**, not only as a fallback: the first live check read `0000c000 4d4d5003 00008000` — one word right, two stale — because the core woke between the reads, and no plausibility check can tell that from a different board. This is the gate's read, ahead of a flash or a reset or a human's validate; the live register reads planned for embarch-atlas never halt, and need the firmware to keep a DMA clock on instead.

**Rejected: turning a DMA clock on over the debug port before reading.** It is a read-modify-write of RCC on a running core, the very write this decision removes, and it changes the board's power state behind its firmware's back.
