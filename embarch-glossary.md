# embarch: glossary

**Status:** active, 2026-08-15. Added closing item 22 of that day's design-improvement review (`.claude/design-improvements-2026-08-15.md`, local working notes — not committed): DUT, study, target, project, board qualifier, topology class, and discovery kind are all load-bearing terms used across every design doc in this repo, and none of them had one place defining what they mean. This doc doesn't restate any sub-project's design — it links to the section that owns each term, per `DOC-PROTOCOL.md` §5's "link, don't restate" rule.

| Term | Meaning | Owning doc |
|---|---|---|
| **DUT** | Device Under Test — the physical firmware/hardware being flashed, reset, or bench-tested. Distinct from dev-bench, which plays the DUT's BLE *counterpart* during a study, not the DUT itself. | [embarch-core/decisions.md](embarch-core/decisions.md) §1 |
| **`.eap` / protocol manifest** | "EmbArch Protocol" — a small purpose-built text grammar, authored by an engineer in the *firmware* repo (`embarch/protocols/*.eap`), describing how to decode one DUT's notification bytes and how to drive its command handshake. Never inferred from source. Resolved into a submitted `Study` at build time (like `study-structs.toml`, not referenced by name or CRC), where it becomes `Study.protocols`, is sealed by `protocols_crc` — the study's **third** seal, checked independently of `steps_crc` and `streams_crc` so a mismatch names which third is corrupt — and crosses to dev-bench on `StudyStart`. | [embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decision 58, §4.9 |
| **`RunProtocol`** | The `Action` that hands the BLE link to a `.eap` state machine for the length of one step — named states, `on_enter` writes, frame-triggered transitions with guards, timeouts with retries, terminal states mapping to `Outcome`. Executed by **dev-bench**, not by Core: the loop closes against the DUT's own connection interval and Core still sends nothing mid-study. The interpreter is hand-written C (`eap_interp.c`), pinned against this crate's own reference one. | [embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decision 60, [embarch-dev-bench/decisions.md](embarch-dev-bench/decisions.md) §3 decision 41 |
| **guard-reachable** | The half of the `.eap` grammar that crosses the wire to dev-bench, because a running state machine can name it: `select_if` predicates, fixed-offset integer reads, byte-span lengths, write templates, the expression set. The rest (`repeat`, `bitpack`, `crc32`, `fixed`) is parsed from the same file and applied host-side at render time — no guard reads a bit-packed column, so putting a bit-unpacker in firmware would buy a capability nothing uses and make every grammar change cost a reflash. | [embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decision 59 |
| **Core** | `embarch-core`, the OS-level service owning the debug probe and serial console; the lowest layer in the suite. | [embarch-core/decisions.md](embarch-core/decisions.md) §1 |
| **project** | A named, configured build target in `embarch-api`'s config — one entry in `[[projects]]`, corresponding to one firmware repo/build (`discovery = "static"`) or a whole Zephyr/west repo's live-scanned surface (`discovery = "zephyr-west"`). | [embarch-api/decisions.md](embarch-api/decisions.md) §4 |
| **target** | One concrete, buildable (board, soc, cpucluster, variant, revision, app) combination within a `discovery = "zephyr-west"` project — what `list_targets` enumerates and `build`/`flash`'s four selection params narrow down to. Not the same as a *project*: one project can have many targets. | [embarch-api/decisions.md](embarch-api/decisions.md) §3 decision 12 |
| **discovery kind** | `static` (today's schema — a hand-authored `[[projects]]`/`[[projects.targets]]` entry) or `zephyr-west` (live filesystem+YAML scan, no stored build command/chip). A per-project config field, not a global mode. | [embarch-api/decisions.md](embarch-api/decisions.md) §3 decision 12 |
| **board qualifier** | Zephyr's own naming grammar for a buildable target: `<board>@<revision>/<soc>/<cpucluster>/<variant>` (revision and variant optional). What `west build -b` actually takes. | [embarch-zephyr.md](embarch-zephyr.md) §2 |
| **chip** | An opaque `probe-rs` target name (e.g. `nRF54L15`, `STM32F407VG`) — a different namespace from a Zephyr SoC name, with no mechanical mapping between them except `embarch-core`'s own `SOC_TO_CHIP` table. | [embarch-core/decisions.md](embarch-core/decisions.md) §3 decision 8 |
| **probe** | A physical debug probe (ST-Link, J-Link, CMSIS-DAP, FTDI, ESP USB-JTAG) `probe-rs` can attach to. Dev-bench's on-board J-Link counts as a second probe once dev-bench hardware exists. | [embarch-core/decisions.md](embarch-core/decisions.md) — see spec.md |
| **hw_lock** | Core's single mutex serializing all DUT probe/serial access across `/flash`, `/reset`, `/serial-log`. Deliberately separate from the dev-bench serial link's own one-study-at-a-time lock — different physical connections. | [embarch-core/decisions.md](embarch-core/decisions.md) §3 decision 4 |
| **Study** | A scripted sequence of BLE stimulus/interaction steps plus measurement, run against a DUT through dev-bench — the unit of work `POST /study` accepts. | [embarch-study-designer/design.md](embarch-study-designer/design.md) §1, §4.1 |
| **Step** | One action within a `Study` (`BleAdvertise`/`BleConnect`/`DataExchange`/the GATT-discovery and monitor-window actions), plus its own timeout, pre-action delay, and fail-continuation policy. It carried an optional power-sample window until 2026-08-25; a power capture is a **stream tap** now. | [embarch-study-designer/design.md](embarch-study-designer/design.md) §4.2 |
| **dev-bench** | `embarch-dev-bench`, the physical rig playing the DUT's BLE counterpart and sampling power during a `Study` — Zephyr-based C firmware, cross-vendor by design. | [embarch-dev-bench/decisions.md](embarch-dev-bench/decisions.md) §1 |
| **topology class** | `local` / `wsl-host` / `remote` — the three ways `embarch-api` and `embarch-core` can be arranged relative to each other, auto-detected by `embarch-umbrella`/`embarch-api`'s shared candidate-race logic. Only the class is ever persisted, never a resolved address. | [embarch-umbrella/design.md](embarch-umbrella/design.md) §3 decision 6, §4 |
| **outpost** | `embarch-outpost` — a Zephyr module an engineer compiles into the **DUT's own** debug firmware, emitting a thread/ISR/marker timeline out a TX-only UART. The only component in the suite that ships inside the thing under test, as against observing it from outside. **It carries no clock**: a record says what happened and in what order, and the time comes from the host (see **frame**). | [embarch-outpost/design.md](embarch-outpost/design.md) §1, §3 decision 4 |
| **frame** (outpost) | The unit of the outpost wire — a COBS-delimited batch of a few dozen records — and, since record layout 2, **the resolution of the whole instrument**. `embarch-core` stamps each frame with its own receipt time as it arrives; every record in a frame therefore shares one timestamp. Ordering inside a frame is real; duration inside one is **not measurable**, which is why an ISR span (enter and exit in the same frame, essentially always) is counted and never timed. A gap record is guaranteed to be the first record of its frame, which is what bounds dropped records in time: between the previous frame's arrival and its own. | [embarch-outpost/design.md](embarch-outpost/design.md) §3 decisions 4, 5, 17 |
| **signal link** | A named signal originating at the DUT (an outpost UART, a console UART, an SWO pin), with a declared **route**. A second class of declared hardware fact alongside board enrollment: enrollment says *which board is which*, a signal link says *what is wired to what*. | [embarch-topology/design.md](embarch-topology/design.md) §3 decision 18 |
| **dev-bench log level** | `Study.dev_bench_log_level` — how verbose dev-bench's own firmware is *for one study* (`Off`/`Error`/`Warn`/`Info`/`Debug`, default `Warn`). Applied when the study starts and reverted when it ends, so an idle bench stays quiet on a link the study protocol shares. Not covered by either CRC seal: a study re-run at a louder level is the same study. | [embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decision 51; [embarch-dev-bench/decisions.md](embarch-dev-bench/decisions.md) §3 decision 39 |
| **dev-bench debug log** | `dev-bench.log.<date>` in Core's log directory, beside `core.log` — every `LogLine` dev-bench sends, including its whole Zephyr `CONFIG_LOG` output, stamped by arrival and by the study it belongs to. Read it with `embarch-core dev-bench-logs`. Distinct from `core.log` (Core's account of what the *service* did) and from a study's `streams/dev-bench` tap (scoped to one study, so it cannot hold a handshake or a boot line). | [embarch-core/decisions.md](embarch-core/decisions.md) §3 decision 37; [embarch-dev-bench/decisions.md](embarch-dev-bench/decisions.md) §3 decision 38 |
| **dev-bench bypass** | A signal link whose route is `Direct` — it goes straight to a serial port on the Core machine, skipping dev-bench entirely. A first-class declared route, not a description of temporary wiring: the intended shape is via dev-bench, and the bench currently has neither the spare pins nor the pass-through firmware. | [embarch-topology/design.md](embarch-topology/design.md) §3 decision 18 |
| **wire schema version / host type version** | Two hand-bumped constants in `embarch-study-designer` (`DEV_BENCH_WIRE_SCHEMA_VERSION` **9**, `HOST_TYPE_SCHEMA_VERSION` **11**), one per hop they guard: the Core↔dev-bench serial `Hello`/`HelloAck` handshake, and the `embarch-api`↔Core `GET /status` check. The host one is a strict superset — `Study` crosses that hop whole, including `requires`/`gatt`, which dev-bench never sees, so it moves for host-only changes too and has now done so three times. One constant until 2026-08-25; both are mismatch **detectors**, never negotiators. | [embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decision 12 |
| **study seal** | Either of a `Study`'s two CRC-32s — `steps_crc` over `steps`, `streams_crc` over `streams` — each covering one contiguous span, each recomputed and overwritten by whoever submits, each checked independently at both hops so a mismatch says **which half** is corrupt. Two seals rather than one widened one because `steps_crc` sits between the two spans on the wire. | [embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decisions 17, 39 |
| **stream tap** | One declared capture in a `Study`: where bytes come from, how long the tap lives, how to render what arrives, what to call the output. That name is what `study_stream_data` fetches and what `list_study_streams` lists — including whether the capture was **truncated**, the one fact a short capture must not be readable without. The one generic inbound pipeline that replaces the separate power, sensor-waveform, and GATT-transcript channels. Nothing between the source and Core ever interprets a payload. Each tap gets its own file under a study's `streams/`, named after the tap. | [embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decision 39, §4.8, §5.2 |
| **raw before decode** | Core's rule for every stream tap: the bytes that arrived are written byte-for-byte *first*, and only then is the tap's declared rendering attempted. A decode that fails costs a rendering, not a capture — which is the difference between a bad afternoon and a lost one. | [embarch-core/decisions.md](embarch-core/decisions.md) §3 decision 30(b) |
| **version gate** | `POST /study`'s refusal to run a study against firmware that isn't the build the study declares — a `409` naming both strings, raised **before `StudyStart` is sent**, so no step runs. Still asymmetric, but no longer one-sided as of 2026-08-25: the bench self-reports over `HelloAck`, so Core observes it; the DUT reports nothing, so its requirement is checked **only when the caller says it just flashed one** (`?flashed_firmware_version`) and is recorded as `Declared` otherwise, rather than pretended to be verified. An `?allow_version_mismatch=1` proceeds and is **recorded** in the result, never silently honoured. | [embarch-core/decisions.md](embarch-core/decisions.md) §3 decision 31; [embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decision 40 |
| **manifest** (outpost) | The build artifact mapping an outpost trace's opaque IDs to names — marker IDs, thread addresses, ISR vector numbers, record layout. Emitted by the DUT's own build, read out of the linked ELF. Matched against the **build ID** the running firmware reports, *not* a CRC of the manifest (which the firmware cannot know — it is generated from the image it would have to be baked into; [embarch-decision-reversals.md](embarch-decision-reversals.md) row 37). A mismatch costs the **names**, never the capture: the trace still decodes, with an empty name column and a recorded reason, because a mislabelled trace reads perfectly and is entirely wrong. | [embarch-outpost/design.md](embarch-outpost/design.md) §3 decision 9 |
| **provenance** (study) | What a `StudyResult` actually ran against — the dev-bench and DUT firmware versions, **how each was established** (`ReportedByDevBench` / `ReportedByOutpost` / `FlashedThisRun` / `Declared`), and **which requirements were waved through rather than met** (`overrides`, since 2026-08-25). The source matters as much as the value: a `Declared` version is an assertion nobody checked, and `FlashedThisRun` is a claim about *the tree that was built*, not a readback — nothing in this suite can read a version off a DUT. | [embarch-study-designer/design.md](embarch-study-designer/design.md) §3 decision 40, §4.5 |
| **suite** | The whole `embarch-*` set of sub-projects together — Core, API, dev-bench, study-designer, umbrella, promptu, atlas — as opposed to any one of them. | [embarch.md](embarch.md) §1 |
