# embarch-ui decisions: Operator prompts

**Status:** active, 2026-10-28.

The operator-prompt modal and how the UI comes to follow a study it did not start. Index: [../decisions.md](../decisions.md).

## The modal
### 69 — A waiting host-study prompt opens a modal on any tab, fed by one stream; the UI follows studies it did not start by polling Core
`embarch-core` decision 105 lets a host study stop at a `Prompt` until a person answers; a study started from `embarch-api` is one this process never registered, and a prompt cannot wait for someone to open it from the studies list. **`LiveStudies::watch_running` asks Core for its studies every 3 s and `ensure`s a follow for each `pending`/`running` one** (idempotent, so a study started here is not followed twice; a failed read is skipped). Chosen over a Core-wide event stream because none exists, and over following only on demand because the prompt is the case that cannot wait. **Cost:** every running study gets a session and its rings, evicting older ones past `MAX_SESSIONS` (8). Each session holds `pending_prompt` (set by `PromptPending`, cleared by the `PromptResolved` it names, or by the follow ending, so a cancelled study leaves no modal), and the snapshot carries it, so a reload mid-prompt shows the modal. **One stream, `/api/prompts/events`**, merges every session's `prompt` frames: first frame `prompts` (all waiting now), then one `prompt` frame per change, and a lagged receiver is resent the whole pending set. The modal is on `index.html` outside every tab, so it opens wherever the operator is, with the prompt text at 2rem, a countdown, Confirm/Cancel, a Web Audio beep and a desktop notification (each best effort: a browser that has not had a click refuses audio). **The countdown's `remaining_ms` is worked out by the server** and counted down on `performance.now()`, so a phone with its own clock does not count to another instant; that the server and Core agree on the time is **assumed**, not measured (one machine in the usual setup). A resolve by another surface leaves the modal up with who answered; a resolve it answered itself closes it. `POST /api/live/prompt {study_id, prompt_id, answer}` relays `answer_prompt` as `answered_by: "ui"`; a `409` is returned as a `409` with Core's words and the modal says the prompt had already ended; any other failure keeps the buttons live. Measured: unit tests for snapshot, resolve, a late resolve of an older prompt, an overdue deadline, and the answer route against a stub Core (`ui` as `answered_by`, `409` passed on, a bad answer never sent). **Also measured (`tests/browser/drive_prompt.py`, headless Firefox against `stub_core.py`'s prompting host study, ui/101):** the modal opens on a non-Live-Study tab, shows step and text, its countdown moves, another surface's answer leaves it up naming who answered, a reload mid-prompt shows it again, Confirm posts `answered_by: "ui"` and closes it, a stub `409` shows the "already ended" text. The drive found no rendering bug. **Not measured:** a live Core prompt (the stub's frames follow `embarch-core` decision 105's documented shape, not a captured one), and the beep and desktop notification (headless refuses both).
