# embarch-ui decisions: What the Trace view transfers

**Status:** active, 2026-09-04.

How much of a capture reaches the browser, and when. What the chart *renders* is in [trace-view.md](trace-view.md); how a reader *moves around* it is in [trace-chart.md](trace-chart.md).

Index: [../decisions.md](../decisions.md). Current truth: [../spec.md](../spec.md).

### 18 — The binning moves to the server; the view asks for the window it is about to draw

**Decision 10 made the drawing independent of dataset size and left the transfer exactly where it was.** Aggregating sub-pixel spans into per-pixel occupancy runs bounded the element count by pixels × lanes — but it ran in the browser, so the whole capture still had to get there first. On a capture built to the reference's shape (225,627 rows, 112,804 spans, 26 lanes) the spans serialize to **12.6 MB of JSON, against 12.7 KB for everything else in the view** [measured 2026-09-04, host-side, `EMBARCH_VIEW_CSV` scratch test]. **The spans were not part of the payload; they were the payload.** So the tab's remaining cost was one blocking transfer, growing linearly with the study's length, to compute a picture whose size never grew at all.

**The same aggregation, on the other side of the wire.** `GET /api/trace/{study}/{tap}/bins?from&to&width` returns at most `width` runs per lane for the requested window; the view's own payload drops `lanes[].spans` entirely and keeps `span_count`. First paint is now **12.7 KB + 30.5 KB** rather than 12.6 MB, and every window after it is bounded by the grid rather than by the capture — 30 KB zoomed out, ~160 KB zoomed into 1%, where most runs are single spans carrying their own numbers. A window costs **1–6 ms end to end** including the browser's own fetch [measured 2026-09-04, release build, loopback, 1,170 bins].

**This is deliberately not the navigation work, and the separation is the point.** Decision 10's chart half was a *redraw* problem — a fixed-width SVG with a 34 µs run trapped in one pixel column. This is a *load-time* problem, and it survived that fix untouched. Conflating them is how a measured decision turns back into a guess: the aggregation would have been credited with a cost it never removed, and the transfer would have gone on being described as solved. They share an algorithm and nothing else.

**The binner is a transcription of the JavaScript, not a second design.** Same clamping order, same float scale, same four split flags, same "attributed to every column it covers, counted only on the column it starts in". The version that shipped in `app.js` is **kept, in the test module**, and `bins_match_the_browser_aggregation_they_replace` runs the two against each other over every committed capture at four grid widths and forty window shapes. The reference is deliberately the naive shape — it scans a lane rather than binary-searching `max_to_prefix` — so the production search is under test rather than restated by its own reference. **Two aggregations that agree on the reference capture and diverge somewhere nobody looked is the whole risk of moving one**, and the alternative to pinning it is finding out from a picture.

**One decoded capture is cached server-side, and loading the view is what refreshes it.** Binning a window is arithmetic over spans that are already decoded; re-fetching and re-decoding a 13 MB CSV per pan would move the cost rather than remove it. One entry, because the tab shows one trace at a time — and `GET /api/trace/{study}/{tap}` re-decodes unconditionally, so **the refresh is an action a reader takes** rather than a staleness rule nobody can see. A `/bins` request that misses decodes for itself, so a deep link into a window still works.

**Nothing is drawn from a window's bins that is not this window's.** A held set could be rescaled into position and would be approximately right — and a merged block's width would then be neither its own nor any span's, which is the one caveat decision 10's tooltips exist to state exactly. So a draw with no matching bins leaves the last correct picture up and returns; the reply schedules the redraw. Eighteen wheel notches and two fits produced **eight** requests [measured 2026-09-04, headless Firefox against the real binary], because the redraw was already coalesced onto an animation frame and an identical window is never asked for twice.

**Rendering it in a browser found the defect the Rust tests could not, again.** The window is clamped and drawn in floats, and zooming at the pointer computes its anchor from a pixel fraction — so **every wheel notch produced a fractional window**. That was invisible while aggregation happened in the same floats; against a `u64` query it is a `400` on the first notch. The window is rounded to whole units now, which is what the axis was already documented to be. **The same shape as decision 10's own duplicated-element-id finding, and the same lesson: this view is the most Rust-tested and least looked-at surface in the UI.**
