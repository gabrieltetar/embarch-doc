# embarch-ui decisions: Shape and stack

**Status:** active, 2026-09-02.

One consolidated process replacing three ad hoc UIs, with no build toolchain.

Index: [../decisions.md](../decisions.md). Current truth: [../spec.md](../spec.md).

### 1 — One consolidated process, not a shared library three separate binaries keep depending on

The same "one implementation, many call sites" shape `embarch-topology` decision 8 established for topology detection — except **here the consolidation is the UI surface itself**, not just the logic behind it. `embarch-topology`'s and `embarch-study-designer`'s standalone UI binaries (413 and 812 lines) are retired outright, and Core's enroll page's HTML moves out of Core, which keeps the enroll endpoint it already had. Settled on the repo owner's own framing: "1 UI for the whole project, just like the topology project centralized all topology from the suite."

### 2 — Zero-build, Rust-served HTML — pushed to a real design system rather than replaced with a framework

The alternative was weighed on its actual merits: an SPA framework plus a bundler, with the built bundle vendored into the Rust binary so the *end user* still runs one binary — buying a real component/chart/table ecosystem and a faster path to polish, against **a second toolchain at build time, new CI legs, new supply-chain surface, and an explicit break of the suite's "Rust, one toolchain" principle.** Decided against, with the corollary that matters: **stop treating plain unstyled HTML as the ceiling** and actually invest in hand-rolled CSS, type and component design. Confirmed against real mockups (decision 8) before committing further.

### 3 — VS Code integration is a thin launcher, not an embedded webview or a native VS Code UI

It manages the `embarch-ui` server process and opens it in the system browser. *Rejected: a VS Code Webview* — real CSP and localhost-connect plumbing, in exchange for never leaving the editor. *Rejected: a native TreeView built from VS Code's own toolkit* — **a second presentation layer hitting the same JSON API.** Neither matched the actual ask, which was **reach into the editor for convenience, not a second UI to keep in sync with the first.**

**It lives in a subdirectory of `embarch-ui`, not a sibling repo** — matching decision 1's own framing, and no marketplace packaging constraint forces a split: the packaging tools all work rooted at a subdirectory. A real TypeScript tree with start/stop commands, a status-bar toggle, and settings for binary path, host, port, config path and auto-start.

**Distribution is an internal `.vsix` only, never the public Marketplace**, matching the suite's single-engineer, not-yet-public posture: a listing would need a publisher account, which does not exist (the icon does, as of 2026-09-09 — decision 25). **The consequence of sideloading is that nothing reinstalls it**: a VS Code server update re-provisions its extensions directory and drops the extension silently, while the `embarchUi.*` settings survive in the client's own settings — so the symptom is the three commands quietly absent from the palette, with no error, which reads as a deleted command rather than a missing extension. `vscode-extension/reinstall.sh` is the recovery path and is idempotent. **It does not use `vsce`**, which needs an `npm` and a network this bench does not have: it borrows the `node` bundled inside the VS Code server to compile, and writes the `.vsix` with python's `zipfile` — the manifest is generated from `package.json`, pinning `ExtensionKind` to `workspace` so the extension runs remote-side, where the Linux binary it spawns actually is.

**Verified by packaging and installing it for real**, which found one gap: packaging **refused over a relative license field pointing outside the packaged subdirectory**, fixed by copying the license in and naming it plainly. There was no `node` on this bench at all, resolved at the time with a user-local portable Node; that Node is gone as of 2026-09-09 and the server's bundled one replaced it. The remote-CLI shim here does not support an Extension Development Host, so **a real install of the `.vsix` — exactly the chosen distribution path — stood in for one.** Live-confirmed by the repo owner afterwards in their own Windows VS Code over Remote-WSL against the real debug binary.

### 9 — Repo: [gabrieltetar/embarch-ui](https://github.com/gabrieltetar/embarch-ui), created empty

Matching how `embarch-umbrella`, `embarch-topology` and `embarch-dev-bench` each started: the path dependencies decision 5 requires **needed a real repo to exist before implementation could begin in earnest.**

### 28 — Start shows the window and tab already open, and pre-flights the address instead of inferring from a failed bind

Decision 3's launcher opened a browser tab on **every** `EmbArch UI: Start`: all three paths through `start()` called `openInBrowser()` unconditionally, so a repeat Start stacked duplicate tabs in the one browser window, and a server started somewhere else (a terminal, a second VS Code window) was recognised only *after* spawning a process that failed to bind the port. Both halves are fixed by asking first: a 400 ms loopback GET, true on any response, decides whether to spawn; a focus attempt decides whether to open a tab. The spawn-then-infer path stays as a backstop for the race where something binds the port in between.

**The tab is activated, not merely reported.** Chromium exposes its tab strip through Windows UI Automation, reachable from WSL through `powershell.exe` interop: `SelectionItemPattern.Select()` on the tab, then `SetForegroundWindow` on its window. Measured live: a round trip in **0.41–0.54 s** (1.7 s when the window had to be un-minimized first), the target tab's `IsSelected` going `False → True`, the foreground handle moving from a *different* browser window to the one holding the tab, and the tab census unchanged across a second Start. The Windows foreground lock never bit — a plain `SetForegroundWindow` from a WSL-spawned process, with no user gesture of its own, raised the window, so the `AttachThreadInput` fallback never had to fire.

**Four properties of the script are invariants, each one a defect found by measuring rather than by reasoning:**

- **The tab-class filter is case-*sensitive*, `-cmatch 'Tab$'`.** A plain `TabItem` descendant search returns far more than browser tabs: pages contribute their own tab widgets (GitHub's `tabnav-tab`, Harvest's `pds-tab`, chess.com's `tabs-tab`), and — because every Electron app shares Chromium's window class — so do VS Code's editor tabs, Slack's rail and Spotify's panel. All of them end in lowercase `tab`; the browser's own end in `BraveTab` or `Tab`. PowerShell's `-match` is case-insensitive by default and lets every one of them through, and a first attempt at this clicked an in-page widget instead of switching tabs. **The `c` is load-bearing.**
- **Every window is enumerated; `FindFirst` is wrong here.** The automation root orders its children by z-order, so the same query returned different handles on successive runs, and one browser process owned four windows on this bench. **Search first, raise second**: the window raised is the one whose strip actually held the tab, which is what makes a tab in the window behind reachable at all.
- **The restore is gated on `IsIconic`.** Calling `ShowWindow(SW_RESTORE)` unconditionally demotes a maximized window to its pre-maximize rectangle — hit for real on a VS Code window while measuring. Gated, a maximized window stays maximized (`IsZoomed` `True → True`) and a minimized one comes back **to** maximized.
- **The script is passed inline via `-Command`, and the extension ships no `.ps1`.** Execution policy here is `Restricted`, which fails `powershell.exe -File` outright with `UnauthorizedAccess` but does not govern `-Command`. `-ExecutionPolicy Bypass` is not the fix and is not used.

**No browser is named anywhere in it.** Windows are found by the Chromium window class `Chrome_WidgetWin_1`, which covers Brave, Chrome, Edge, Vivaldi and Opera without an allowlist to maintain — Chrome was verified working without a line of code or a setting mentioning it, and Edge is the one inference left (it shares Chrome's upstream view but was never opened here). Firefox is not Chromium and is not covered; it would be a second strategy, not a wider regex.

**The implementation is one strategy behind a registry, not the only way this can work.** `focus.ts` holds a `FocusStrategy` interface — `supports()`, `focus(title)` — and exactly one member, the WSL-plus-Chromium-on-Windows topology this bench is. A native-Linux (AT-SPI), native-Windows (the same UIA calls without the interop hop) or macOS (`tell application … to set active tab index`) path is **a new file and one line of the registry, not a refactor**. Until one exists those topologies return false from `supports()` and Start behaves exactly as it did before this decision: it opens a tab. That is also the failure mode for every other way this can go wrong — no browser window, no matching tab, a missing `powershell.exe`, a timeout, a thrown error. **The focus path is never allowed to be the reason nothing opens**, and it never reaches the notification area; the output channel gets one line naming the strategy that ran.

**`<title>EmbArch</title>` is a load-bearing interface between the served page and the launcher.** The match is exact, which is what keeps a decoy tab — a GitHub page, a file listing, this repo open in a browser — from being focused instead; a substring match on `embarch-ui` hit a decoy in testing, an exact match on `EmbArch` did not. So renaming the page's title silently breaks focus: the launcher keeps working and just opens a duplicate tab again, which is **the original bug returning with no error anywhere**. `assets/index.html` carries a comment saying so and the constant in `extension.ts` cites this decision. The short title also fits a tab (Brave's measured 175 px truncate at roughly 46 characters) and keeps a non-ASCII em dash off the command line.

**The UIA `Name` of a tab is not the document title.** Brave appends its own status annotations — `EmbArch - Memory usage - 34.6 MB` was what the tab read seconds after opening a 30 MB page, and an idle one reads `… - Audio playing - Memory usage - 449 MB`. A bare equality test would therefore fail intermittently, on nothing more than the tab having been idle. Those suffixes are stripped before the comparison, which is otherwise exact.

**Accepted side effect:** driving UI Automation puts Chromium into accessibility mode, which costs memory and CPU per tab. It answered in 16 ms on a nine-window desktop, so it is very likely already on for other reasons here — recorded rather than discovered later.

The probe also makes a third status-bar state knowable: `embarch-ui (external)`, an address that answers but whose server this window did not spawn, which used to show as `(stopped)`. Its click goes to `start()` — which now focuses the existing tab — not to `stop()`, which can only kill a child this extension started.

*Rejected: a notification saying it is already open* — cheap, and answers a different question than the one asked. An earlier draft of this change did exactly that, on the claim that tab activation was unreachable from outside the browser; the claim was disproved by measurement before anything was written. *Rejected: launching a Chromium `--app` window* — the window **is** the page, so focus becomes exact and titles stop mattering, at the cost of hardcoding a browser and dropping the tab strip and address bar the UI is otherwise used from. *Rejected: a browser extension using `chrome.tabs`* — the most reliable route, and the only one that matches on **URL** rather than title, at the cost of a second installable artifact plus a channel from the VS Code extension to it. *Rejected: an SSE-subscriber-count endpoint on the server* — real tab liveness rather than an inference from a window title, at a server change plus a keepalive staleness window, and it still cannot raise anything.
