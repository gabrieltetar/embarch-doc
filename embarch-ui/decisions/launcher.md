# embarch-ui decisions: The VS Code launcher

**Status:** active, 2026-09-02; 3 and 28 amended by 101 on 2026-11-05.

Index: [../decisions.md](../decisions.md). Current truth: [../spec.md](../spec.md).

### 3 — VS Code integration is a thin launcher, not an embedded webview or a native VS Code UI

It opens the server in the system browser and, since 101, drives the `embarch-ui.service` unit rather than managing a process of its own. *Rejected: a VS Code Webview* — real CSP and localhost-connect plumbing, in exchange for never leaving the editor. *Rejected: a native TreeView built from VS Code's own toolkit* — **a second presentation layer hitting the same JSON API.** Neither matched the actual ask, which was **reach into the editor for convenience, not a second UI to keep in sync with the first.**

**It lives in a subdirectory of `embarch-ui`, not a sibling repo** — matching decision 1's own framing, and no marketplace packaging constraint forces a split: the packaging tools all work rooted at a subdirectory. A real TypeScript tree with start/stop commands, a status-bar toggle, and settings for host and port; the binary path, config path and auto-start settings went with 101. **Since 2026-10-23 the launcher ships inside `embarch-chat`'s extension** (`embarch-chat` decision 29), commands and settings unchanged, and that repo's `./reinstall.sh` is its recovery path; that extension is a webview, which `embarch-chat` decision 6 sets against this decision for it alone. `vscode-extension/`, the old copy that the two paragraphs below describe, was deleted with 101.

**Distribution is an internal `.vsix` only, never the public Marketplace**, matching the suite's single-engineer, not-yet-public posture: a listing would need a publisher account, which does not exist (the icon does, as of 2026-09-09 — decision 25). **The consequence of sideloading is that nothing reinstalls it**: a VS Code server update re-provisions its extensions directory and drops the extension silently, while the `embarchUi.*` settings survive in the client's own settings — so the symptom is the three commands quietly absent from the palette, with no error, which reads as a deleted command rather than a missing extension. `vscode-extension/reinstall.sh` is the recovery path and is idempotent. **It does not use `vsce`**, which needs an `npm` and a network this bench does not have: it borrows the `node` bundled inside the VS Code server to compile, and writes the `.vsix` with python's `zipfile` — the manifest is generated from `package.json`, pinning `ExtensionKind` to `workspace` so the extension runs remote-side, where the Linux binary it spawns actually is.

**Verified by packaging and installing it for real**, which found one gap: packaging **refused over a relative license field pointing outside the packaged subdirectory**, fixed by copying the license in and naming it plainly. There was no `node` on this bench at all, resolved at the time with a user-local portable Node; that Node is gone as of 2026-09-09 and the server's bundled one replaced it. The remote-CLI shim here does not support an Extension Development Host, so **a real install of the `.vsix` — exactly the chosen distribution path — stood in for one.** Live-confirmed by the repo owner afterwards in their own Windows VS Code over Remote-WSL against the real debug binary.

### 28 — Start shows the window and tab already open, and pre-flights the address instead of inferring from a failed bind

Decision 3's launcher opened a tab on **every** `EmbArch UI: Start`, stacking duplicates, and saw a server started elsewhere only after a spawn failed to bind. Now a 400 ms loopback GET, true on any response, decides whether to spawn; a focus attempt, whether to open a tab. Spawn-then-infer stays as the backstop for a port race. **Since 101 nothing is spawned:** the probe tells an address answered by something other than the unit, and the focus half stands unchanged.

**The tab is activated, not reported**, via Windows UI Automation from WSL through `powershell.exe`: `SelectionItemPattern.Select()`, then `SetForegroundWindow`. Measured **0.41–0.54 s** a round trip (1.7 s un-minimizing); the `AttachThreadInput` fallback for the foreground lock has never fired.

**Four invariants, each a measured defect:**

- **`-cmatch 'Tab$'` — the `c` is load-bearing.** A `TabItem` search also finds page widgets and every Electron app sharing Chromium's window class (VS Code, Slack, Spotify), all ending in lowercase `tab`; the browser's end in `Tab` or `BraveTab`. `-match` ignores case; a first attempt clicked an in-page widget.
- **Enumerate every window, never `FindFirst`**: children come in z-order, so handles varied by run; one browser owned four windows. Search first, raise the window whose strip holds it.
- **Restore is gated on `IsIconic`**: an unconditional `SW_RESTORE` demotes a maximized window.
- **Inline `-Command`, no `.ps1` shipped**: `Restricted` execution policy fails `-File` with `UnauthorizedAccess` but does not govern `-Command`. `-ExecutionPolicy Bypass` is not used.

**No browser is named**: windows match `Chrome_WidgetWin_1`, covering Brave, Chrome, Edge, Vivaldi and Opera. Chrome verified; Edge inferred, never opened. Firefox would be a second strategy, not a wider regex.

**One strategy behind a registry.** `focus.ts`'s `FocusStrategy` (`supports()`, `focus(title)`) has one member, WSL plus Chromium on Windows; native Linux (AT-SPI), native Windows or macOS is a new file and one registry line. Unsupported, or on any failure — no window, no matching tab, no `powershell.exe`, a timeout, a throw — Start opens a tab as before. **Focus is never the reason nothing opens**; it never notifies; one output-channel line names the strategy.

**`<title>EmbArch</title>` is a load-bearing interface.** The match is exact, so no decoy tab is focused — a substring match on `embarch-ui` hit one in testing. Renaming it is **the original bug returning with no error**; `assets/index.html` says so; `extension.ts`'s constant cites this decision. Short, it fits a tab (Brave truncates near 46 characters) and keeps an em dash off the command line. **A tab's UIA `Name` is not the title**: Brave appends `- Memory usage - 34.6 MB`, `- Audio playing`, …, which break an equality test intermittently; they are stripped before the otherwise exact comparison.

**Accepted:** UIA puts Chromium in accessibility mode, costing memory and CPU per tab; at 16 ms on a nine-window desktop it is very likely already on here.

**A third status-bar state, `embarch-ui (external)`**: answering, not spawned by this window, formerly `(stopped)`. Its click goes to `start()`, which focuses, not `stop()`, which can only kill this extension's child. Since 101 it means answering but not as the unit, and a fourth state, `(not installed)`, joins it.

*Rejected: a notification saying it is already open* — answers a different question; an earlier draft did, claiming tab activation unreachable, which measurement disproved. *Rejected: a Chromium `--app` window* — exact focus, but hardcodes a browser and drops the tab strip and address bar. *Rejected: a `chrome.tabs` browser extension* — most reliable and matches on URL, at a second artifact plus a channel to it. *Rejected: an SSE-subscriber-count endpoint* — real liveness, at a server change plus a keepalive staleness window, and it still cannot raise anything.

### 101 — The UI runs as a systemd user service; the launcher drives the unit and spawns nothing

The UI was a child of whichever VS Code window started it: closing that window killed it for every window, a second window could start one on another port, no window could stop one it had not started, and with no window open the browser showed "reconnecting…". **Decided by the owner on 2026-11-05 over keeping it extension-owned and patching it**, on two precedents: Core is an installed, autostarting service rather than something a launcher starts (`embarch-umbrella` decision 3), and the desk is a user service because sessions were lost while the UI was closed (`embarch-desk` decision 27). Amends 3 and 28 above, and `embarch-chat` decision 29 by that sub-project's 102.

**`embarch-ui service install|uninstall|status` writes `embarch-ui.service`**, the desk's own install cut down: no named instances. **The unit runs the binary that installed it**, so installing from `target/debug` makes `cargo build && systemctl --user restart embarch-ui` the dev restart. It carries the installing shell's `PATH` (a build runs `west`, the Atlas tab `git` and `pdftoppm`) and `EMBARCH_UI_HOST`, `EMBARCH_UI_PORT`, `EMBARCH_UI_CONFIG` and `WSL_DISTRO_NAME` when they are set — **nothing else**, so a Claude session's `EMBARCH_DESK_PORT` no longer points the UI at a dev desk, as a hand restart from a session did on 2026-11-05. `WSL_DISTRO_NAME` because a user unit starts without it and the Atlas tab's editor links are built from it. **Measured before building it:** a transient user unit runs `cmd.exe`, so Core's token discovery works from the service; lingering is on, so the user manager outlives every window.

**One instance by construction.** systemd runs one unit, and **the binary binds its address before anything else starts**, so a second copy on the same address exits before its Core poll and `watch_running` follow a study and show its prompts beside the first's; the bind used to come after them. A copy started by hand on another port still runs alongside.

**The launcher spawns nothing.** It reads the unit's load and active state (`systemctl --user show`) and 28's probe, refreshes the status bar every 5 s, and drives the unit with `systemctl --user start|stop|restart`; **Restart is new**. Its states: running; stopped; `(external)`, answering but not as the unit, which nothing here stops; `(not installed)`, whose Start names the install command and **never falls back to spawning**. Every state's click goes to Start, which shows a running UI and starts a stopped one; Stop and Restart are palette commands, the unit being every window's. Closing a window stops nothing. The binary path, config path and auto-start settings are gone, the binary and its config being the unit's and an enabled unit starting with the user session; host and port stay for the probe and the URL.

*Rejected: keeping the UI extension-owned and patching it* — the owner's call. *Rejected: an `install.sh` writing the unit, as `embarch-private` has* — untested, and the quoting of a WSL `PATH` with spaces solved a second time. *Rejected: spawning the binary when no unit exists* — it keeps the window-owned instance this removes.
