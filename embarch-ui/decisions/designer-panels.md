# embarch-ui decisions: The Study Designer's panels

**Status:** active, 2026-09-19.

How the tab is laid out, and the one rule that keeps a panel from showing the study before last. What a study *says* — the version fields, security, the declared GATT, opening a project — is in [study-designer.md](study-designer.md); GATT capture and its pickers are in [gatt-capture.md](gatt-capture.md).

Index: [../decisions.md](../decisions.md). Current truth: [../spec.md](../spec.md).

### 41 — One apply-study path, build options behind a button, static analysis as a thing you ask for

Four changes from one bench session with the tab's author. The first is a defect and the other three are layout, but they share a cause: **a panel written to only on the path that happens to know about it.**

**Every field is assigned on every load, from the study or from a default.** Loading a saved study set the name, the requirements, the build spec, the log level, the taps and the rows; "New study" set the rows and the taps and *nothing else* — so starting a new study after opening a saved one left the previous study's version requirements, its build selection and its log level in the panel, attached to a file that stated none of them, and **the first save would have written every one of them back out.** There is one `sdApplyStudy` now, and **New study is a load**: the route already writes a valid, runnable, loadable `Study`, so the browser loads the file it just created rather than approximating it — which is what makes the two paths unable to drift apart. The invariant is the assignment, not the reset: *a field restored only when the study happens to carry it is the same bug waiting for the next property added to `Study`*.

**The two requirement fields, the Build card and the dev-bench log level moved into a "Build options…" dialog.** All three are properties of the saved study, all three are set once and then read, and together they took about a third of the page between the study toolbar and the step table. **A one-line summary stays on the page** — `dev-bench v9 · DUT any · no build · log level Warn` — because a modal hiding all three would make *what does this study require?* a question you must open a dialog to answer. The summary states what the **study** says, never what the picker shows: an untouched log-level select shows the server's default without the study asserting it, and reading the select would turn that into a claim the file does not make.

**Reading the firmware's source is an action with a result, not a side effect.** The static GATT extraction ran lazily the first time another panel needed a characteristic name, cached for the life of the open project, and logged its failures where nobody running this UI would see them — so *did reading the source find anything?* was answered by squinting at whether some other card's chips looked right. A **Static firmware analysis** submenu on the project panel now holds the extractor name, a **Run GATT extractor** button that discards the cache and re-runs (serving the cache would make it a button that does nothing after its first press, and editing firmware is exactly what changes the answer), the live **Discover GATT** beside it, and what was read: services, characteristics, their C identifiers and their declared properties. **"Nothing was read" and "an extractor ran and failed" stay different answers all the way to the browser** — collapsing them is how *static analysis found nothing* came to mean both "there is nothing" and "nobody looked". *(Decision 51 removed the third of those states — "nobody configured one" — by removing the thing you configured.)* The first press against the reference firmware surfaced a real extractor limitation (`unrecognized characteristic-properties token: WDS_CHRC_TX_PROP`) that had been failing silently — **fixed by [embarch-study-designer](../../embarch-study-designer/decisions/gatt-extract.md) decision 78**, which is what this panel existing is for.

**The four trailing cards became one panel, "Define the wire":** the stream taps, the detected-but-unregistered characteristics, the `.eap` protocol manifests, and the registered actions and payload layouts. Four unrelated subjects stacked below the step table, rather than the one question they all answer — *what goes over the link, and what do the bytes mean.*

**"New study" names nothing, so it is never refused for a name it invented.** Making New study a load exposed what it had always sent: the contents of the **Study name** box, which holds the name of the study that is *open*. Pressing it after reading a saved study answered `409 'alpha-study' already exists — open it, or pick another name` — a refusal about a decision nobody had made. A name now travels only when somebody typed one (the box differing from what it was last filled with is exactly that test); otherwise the route is asked for the first free `untitled-study`, `untitled-study-2`, … and cannot refuse. **The `409` itself is not weakened** — a deliberately typed name that collides still gets it, because that one is about somebody's existing work. **A uniquely-created study is named after the slug it landed on, not the base it was asked for**: two files both calling themselves `untitled-study` show the same name in the box, and a save from the second writes to the first one's slug — the overwrite the refusal exists to prevent, reached from the other side.

### 51 — There is one extractor, so there is no field: the panel keeps the button and loses the text box

Raised by the repo owner reading the panel: *"I don't understand what we need in that field — the static extraction is the main way to gatt discover and to get all the names of the GATTs. We should only have a run gatt extractor button, no text field."*

**A configuration option with exactly one legal value is not a choice, it is a spelling test.** Two text boxes — one in decision 41's submenu, one in the Open-project dialog — took the name of a `GattConfigExtractor` to run, and the build ships exactly one ([embarch-study-designer](../../embarch-study-designer/decisions/gatt-extract.md) decision 33). Everything the field could do was wrong: left blank it silently disabled the only source of characteristic and service *names*, and filled in wrong it answered `unrecognized static extractor`. **It had already cost one bug of its own** — the refusal text and the match arm disagreed about how the single value was spelled, so the only way to learn the right name was to read the Rust.

**Names are not a garnish, which is why the off state had to go.** A live `GattDiscover` returns ATT responses and **ATT carries no names**; the vendor table covers published UUIDs, and on a real DUT nearly every UUID is custom. So an unconfigured project renders every picker, tooltip and dialog group header as a hex UUID head — **the exact state decision 16 exists to have fixed.** A blank text box was one keystroke away from that at all times.

**What replaces it: nothing.** The extractor runs lazily against whatever repo is open, cached per project exactly as before, and **Run GATT extractor** still discards the cache and re-reads — **decision 41's whole point is untouched**, since it was about the extraction being an action with a visible result, not about naming it. The name is still *reported* by the panel, because *which extractor read this repo* is part of what was read; it is simply no longer *asked for*.

**The state that disappears is "no extractor configured", and it was a third answer the code carried everywhere.** `run_static_extraction` returned `Result<Option<_>, _>`, the response carried a `configured` flag beside its `error`, and `RecentProject` stored a per-repo extractor name so reopening a project restored it. All of that collapses: an extraction now succeeds with a table, or fails with a reason. **"Found nothing" is still reachable and still distinguishable** — a repo with no C source is [`NoSourceFilesFound`](../../embarch-study-designer/decisions/gatt-extract.md), an error naming what it looked for, which is the same refusal decision 57 chose over a plausible-looking empty table.

**A `static_extractor` key in an older config file or recents list is ignored, not refused.** Both deserialize non-strictly; rejecting the file would throw away the recents of everyone who had one, over a key that no longer decides anything.
