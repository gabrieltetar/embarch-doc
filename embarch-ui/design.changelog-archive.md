- 2026-08-26 — **Deployed, and the deploy found a real defect.** Rebuilt `target/debug/embarch-ui` (the path the VS Code launcher is configured with, and the assets are `include_str!`-embedded so a rebuild is the deploy) and drove the running instance with real clicks against the real firmware repo. That is what surfaced it: the target list rebuilt its `innerHTML` on every toggle, so the clicked checkbox was destroyed and keyboard focus fell to `<body>`. Split into a build pass and a `syncTargetDialog` patch pass; focus now stays on the control that was clicked, bulk buttons included. §3 decision 17 records it — the inline checkbox list it replaces had the same flaw and re-rendered the whole step table, so this was inherited, not introduced. The cell is one line now — `2 of 13`, two chips, `Choose…` — and the picking happens in the `.dialog` pattern four other places in this app already use, with per-service groups named by decision 56's amendment, per-group all/none, and a filter. `<select multiple>`, a floating popover (clipped by the table's own `overflow-x`), and an inline `<details>` were all rejected, with reasons recorded. `MAX_MONITOR_TARGETS` is now **served** as `max_monitor_targets` rather than restated in `app.js`, and the dialog shows and enforces it. Two silent losses fixed on the way: a saved study's `targets` and `security_level` were dropped when it was reopened, and a picked characteristic the current discovery no longer knows about was dropped without a word at submit.

- 2026-08-25 — **Decision 13 implemented: the Debug tab shows `embarch-api`'s logs.** A source switch (`embarch-core` / `embarch-api`) over two new routes mirroring Core's; a full console reset on switch rather than a merged stream, since the two files rotate independently and arrival order would contradict the timestamps. `logs.rs`'s poll/diff loop is shared, only the fetch differs — Core over HTTP, `embarch-api` from the file, at the one path `embarch_core_client::api_log` defines for both the writer and this reader.

  **Two pre-existing defects in this tab, found by building the second source and fixed here.** Core's logfile carries ANSI escapes and this tab rendered them as literal garbage — stripped at render, so the deployed Core reads correctly rather than only a future one. And every browser opening this tab got the log stream's last batch replayed on top of its own backlog fetch: a cloned `watch::Receiver` inherits the initial version when the original's `changed()` was never awaited, so the first `changed()` returns immediately. Fixed with `mark_unchanged` at subscribe — which is what `api_logs_events`'s comment already claimed.

  Live-validated: real `embarch-api` CLI invocations appeared over both the backlog route and the SSE stream, and after the fix the stream carried only lines from invocations made *after* subscribing. `cargo build`/`test` (6/6)/`clippy --all-targets -- -D warnings` clean.

- 2026-08-24 — **Decision 5 amended: `embarch-ui` never links `embarch-topology`'s `hardware` feature at all — every hardware-adjacent call, read or write, goes through `embarch-core` over HTTP.** Prompted directly, after the initial read-only-in-process/mutation-through-Core split had already been implemented: "Instead of having the UI access hardware, can the UI use the Core to access it?" Correct call — the original split only guarded against `hw_lock` races and missed a worse problem: an in-process read (`list_attached_probes`, `list_enrolled`, `recent_alerts`) queries whichever machine calls it, not Core's, silently wrong the moment Core runs on a different machine (the exact split-topology case `embarch-topology` exists for) — the same reasoning decision 7 already used for the Debug tab, just not generalized to every other read at the time. Now matches `embarch-api/design.md` §11's rule exactly: never link `probe-rs`/`serialport` directly, confirmed via `cargo tree -e normal`. `embarch-topology` is no longer a dependency of `embarch-ui` at all (only `embarch-study-designer` and `embarch-core-client` remain); `embarch-core-client` gained `list_enrolled`/`dev_bench_port` to cover the two Core endpoints that had no client wrapper yet (`embarch-api/design.md` §3 decision 38).
