## 1. Purpose and scope

The suite has accumulated three separate, inconsistent human-facing UI surfaces, each built ad hoc as its owning sub-project needed one: `embarch-topology`'s `ui` subcommand (read-only board/alert view, SSE-live), `embarch-study-designer`'s standalone `study-designer-ui` binary (Study builder, polling-based), and `embarch-core`'s own `GET /enroll` page (the one write-capable form among the three, added specifically because a second UI-owning process calling `hardware::enroll` directly would have bypassed Core's `hw_lock` — `embarch-topology/design.md` decision 14). Each is plain, unstyled HTML with no shared design, running on its own binary and port.

`embarch-ui` exists to be the one place a firmware engineer actually looks to exercise suite features by hand — day to day, not just when an agent needs a hardware read — replacing all three surfaces outright rather than adding a fourth alongside them.

`embarch-ui` is **not**:
- A build-toolchain project. Solution A holds: no npm/Node, no bundler — Rust-served HTML, with a real hand-rolled design system doing the work a framework would otherwise buy (§3 decision 2).
- Embedded inside VS Code as a webview. The VS Code extension is a thin launcher — start/stop the server, open the system browser — nothing renders inside the editor itself (§3 decision 3).
- A second owner of hardware mutation. Enrollment writes and study execution still go through `embarch-core`'s own process and its `hw_lock`, over HTTP — `embarch-ui` never calls a hardware-mutating function directly in-process, even though it links the crates that define those functions (§3 decision 5).
- A replacement for `embarch-api`'s MCP/CLI surface. Agents keep talking to `embarch-api`; `embarch-ui` is the human-facing counterpart, not a new agent transport.

## 2. Architecture overview

```
embarch-ui (one Rust binary, axum)
  |
  +-- links embarch-study-designer  (in-process fn calls: merged action list,
  |                                   custom-action registry, Study-building logic,
  |                                   the outpost trace decoder — pure data, no I/O)
  |
  +-- links embarch-core-client     (the one implementation of "reach embarch-core
  |                                   over HTTP+Bearer", shared with embarch-api)
  |
  +-- does NOT link embarch-topology, at all, deliberately (decision 5's amendment)
  |
  +-- HTTP + Bearer --> embarch-core (same channel embarch-api uses)
                           - every hardware-adjacent call, read or write:
                             POST /probes/enroll, POST/GET/DELETE /signals,
                             GET /serial-ports, GET /probes/enrolled, GET /alerts,
                             GET /dev-bench/port, GET /dev-bench/hello,
                             POST /study, GET /study/{id}, GET /study/{id}/streams,
                             GET /study/{id}/stream/{name}
                           - GET /logs/stream   (SSE, live tail)
                           - GET /logs/recent   (backfill from Core's own rotating logfile)

VS Code extension (thin, TypeScript)
  - spawns/stops the embarch-ui binary as a subprocess
  - opens the system browser at its bound address
  - renders nothing itself
```

Six sections behind one persistent sidebar shell: Dashboard, Topology, Study Designer, Enroll, Trace, Debug. A visual review pass (static mockups) is done as of 2026-08-24 — see §3 decision 8 for the settled design system; the Trace view is the one surface with no mockup behind it, and §3 decision 10 says what it was designed against instead.

**The `links embarch-topology` line above was stale from 2026-08-24 until 2026-08-26** and is corrected here rather than quietly: decision 5's own amendment reversed it the day it was written, and this crate's `Cargo.toml` has never listed that dependency. The correction matters because the reason is load-bearing — a board read done in-process would enumerate whichever machine `embarch-ui` runs on, not Core's.

## 3. Locked-in design decisions and rationale

1. **Scope: one consolidated process, not a shared library three separate binaries keep depending on.** Following the same "one implementation, multiple call sites" shape `embarch-topology` already established for topology detection (`embarch-topology/design.md` decision 8) — except here the consolidation is the *UI surface itself*, not just the logic behind it. `embarch-topology`'s `bin/ui.rs` (413 lines) and `embarch-study-designer`'s `tools/study_designer_ui.rs` (812 lines) both get retired outright; `embarch-core`'s `GET /enroll` page's HTML also moves out of Core (Core keeps the underlying `POST /probes/enroll` endpoint it already had). Settled directly on the user's own framing: "1 UI for the whole project, just like the topology project centralized all topology from the suite."

2. **Frontend tech: Solution A (zero-build, Rust-served HTML), pushed to a real design system rather than replaced with a framework.** The alternative — a real SPA framework (React/Svelte) + a Vite build step, with the built bundle vendored into the Rust binary so the *end user* still only ever runs one binary — was weighed on its actual merits: a real component/chart/table ecosystem and a faster path to visual polish, against a second toolchain (Node/npm) at build time, new CI legs, new supply-chain surface, and an explicit break of the suite's stated "Rust, one toolchain" principle. Decided against it: stay zero-build, but stop treating "plain unstyled HTML" as the ceiling and actually invest in hand-rolled CSS, type, and component design. Confirmed against real mockups (decision 8) before committing further.

3. **VS Code integration: a thin launcher, not an embedded webview or a native VS Code UI.** Manages starting/stopping the `embarch-ui` server process and opens it in the system browser. Two alternatives were considered and rejected: hosting the same HTML inside a VS Code Webview panel (real CSP/localhost-connect plumbing, in exchange for never leaving the editor), and a native TreeView/Custom Editor built from VS Code's own UI toolkit (a second, separate presentation layer hitting the same JSON API). Neither matched the actual ask, which was reach into the editor for convenience — not a second UI to build and keep in sync with the first.

    **Repo layout, resolved 2026-08-24 (milestone 1 §4.8): a subdirectory of `embarch-ui` (`vscode-extension/`), not a sibling repo.** Matches this decision's own "one consolidated thing" framing (decision 1) and `embarch-ui`'s own `bin`-adjacent-tooling precedent — no VS Code marketplace packaging constraint was found that forces a split (`vsce package`/`npm`/`tsc` all work fine rooted at a subdirectory). Scaffolded as a real TypeScript source tree (`package.json`, `tsconfig.json`, `src/extension.ts`): commands to start/stop the `embarch-ui` subprocess and open the system browser, a status-bar toggle, and settings for the binary path/host/port/config path/auto-start.

    **Build/package verification, closed later the same day.** This session's sandbox had no `node`/`npm` at all (the same gap decision 8's changelog noted for the mockup canvas step) — resolved by downloading a portable Node build to a user-local directory (`~/.local/node`, no root needed), not a system package. `npm install && npm run compile` (TypeScript `strict`, `noUnusedLocals`/`noUnusedParameters`) is clean, and `npx @vscode/vsce package` produces a real, valid `.vsix` — the same tool/output the chosen distribution path (below) uses. Real gap found and fixed doing this: `vsce` refused to package over a broken relative `SEE LICENSE IN ../LICENSE` field (a file outside the packaged subdirectory) — fixed by copying `LICENSE` into `vscode-extension/` and switching the field to a plain `"MIT"`. The packaged `.vsix` was then installed for real into this session's own VS Code (`code --install-extension`, confirmed via `--list-extensions`) — `--extensionDevelopmentPath` isn't supported by the remote-CLI shim this environment exposes, so a real install (exactly the internal-`.vsix` distribution path below) stood in for a disposable Extension Development Host. **Live-confirmed working by the user afterward**, in their actual Windows VS Code (Remote-WSL, attached to this same WSL2 instance): start/stop/open-in-browser all function correctly against the real debug binary once `embarchUi.binaryPath` was pointed at it.

    **Distribution, resolved 2026-08-24 via `AskUserQuestion`: internal `.vsix` only, never the public Marketplace.** Matches the suite's current single-engineer, not-yet-public posture — `embarch-ui`'s own repo isn't pushed yet, and a Marketplace listing would need a publisher account/PAT and a real icon, neither of which exist. Install via `code --install-extension <path-to-vsix>` (exactly how this session's own verification pass installed it) or a shared file; `npx @vscode/vsce package` (no publish flag) is the one command that ever produces the artifact — `vsce publish` is never run.

4. **Shell: one app, not linked-but-separate pages.** A persistent left sidebar plus a top status bar, **six** sections behind it: Dashboard, Topology, Study Designer, Enroll, Trace, and Debug (the last two new — present in none of the three existing surfaces). Client-side navigation between sections, one shared header/status chrome throughout, so it reads as one product rather than a pile of tools that happen to share a port.

    **Trace is the sixth, added 2026-08-26** (decision 10's second half). It got its own section rather than living inside the Study Designer's run card for one reason: a trace belongs to a *completed* study, which is not necessarily the one this tab currently has in its table — a run from an hour ago, or one `embarch-api run-study` submitted from a terminal, is exactly as valid a thing to open. A per-run panel could only ever show the run you just did. The Study Designer's run card links into it instead, handing over the `study_id`, so the common case costs no typing.

    Client-side navigation is by URL fragment, and the fragment carries parameters where a section needs them: `#topology` (already `embarch-topology`'s `fix_it_url` destination, that crate's §3 decision 19) and `#trace?study=<id>&tap=<name>`. Parameters in the fragment rather than the query string, because the fragment already selects the section — so an address is one mechanism rather than two — and because a fragment never reaches the server, so linking somebody to a trace costs no round trip and puts no study id in a log.

5. **Backend wiring: every hardware-adjacent call, read or write, goes over HTTP+Bearer to `embarch-core` — `embarch-ui` never links `embarch-topology`'s `hardware` feature at all.** `embarch-ui` depends on `embarch-study-designer` as a library crate and calls it in-process, but only for pure/offline authoring logic that touches nothing but the firmware repo being edited: the merged action list, the custom-action registry, and Study-building logic (turning table rows into a `Study` value). Every capability that involves a physical board or Core's own storage — probe/board enumeration, alert history, dev-bench port detection, enrolling a board, running a `Study` — goes through `embarch-core-client` (decision 5's own amendment below) over HTTP+Bearer, the same channel `embarch-api` already uses, never through an in-process call into `embarch-topology`.

    **Originally split along a mutation/read-only line instead — reversed 2026-08-24, same day, prompted directly: "Instead of having the UI access hardware, can the UI use the Core to access it?"** The original framing put only *mutating* operations (enrolling, running a `Study`) behind Core, reasoning that read-only calls (`list_attached_probes`, `list_enrolled`, `recent_alerts`) were safe in-process since they don't race Core's `hw_lock`. That reasoning missed a second, worse failure mode the `hw_lock` framing never covered: those "read-only" calls still touch either live USB enumeration or a local file on whichever machine calls them — correct only when `embarch-ui` happens to run on the same machine as `embarch-core`, and silently wrong (missing probes, an empty/nonexistent `enrollment.toml`) the instant Core runs on a different machine, which is a real, already-supported topology class and the whole reason `embarch-topology` exists in the first place. This is the exact reasoning decision 7 below already used to keep the Debug tab from reading Core's logfile directly — it turns out to apply to every other hardware-adjacent read too, not just logs. The fix generalizes the rule `embarch-api` already follows and never violated: `embarch-api/design.md` §11 states plainly that it "never links against [probe-rs or serialport] directly; every hardware operation goes through Core's HTTP API" — `embarch-ui` now follows the identical rule, confirmed via `cargo tree -e normal` showing neither `probe-rs` nor `serialport` anywhere in its dependency graph.

    This still preserves the exact invariant `embarch-topology/design.md` decision 14 established when Core's own `/enroll` page was built for the mutation-safety reason: a second process calling a hardware-mutating function directly, without sharing Core's `hw_lock`, is a real class of bug that decision's own reversal exists to prevent. `embarch-ui`'s Enroll tab submits to Core's existing `POST /probes/enroll`; its Study Designer tab's "Run study" action submits a built `Study` to Core's existing dispatch path — both unchanged from the original framing, just no longer the only things routed through Core.

    **How `embarch-ui` reaches that HTTP path at all — resolved 2026-08-24, via `AskUserQuestion` rather than picked silently:** a shared library, not a duplicated client. `embarch-api`'s `core_client.rs` (plus the `CoreConfig`/token-resolution chain it depends on) is extracted into a new crate, `embarch-core-client`, that both `embarch-api` and `embarch-ui` depend on — following the same "one implementation, multiple call sites" shape `embarch-topology/design.md` decisions 2/8/14 already established, rather than growing `embarch-ui` its own independent client and reintroducing the exact mirrored-copy risk that precedent exists to eliminate. `embarch-core-client` gained two new methods the same pass, closing a real gap found doing this: `GET /probes/enrolled` and `GET /dev-bench/port` had no client wrapper in either `embarch-api` or the new shared crate until `embarch-ui`'s Dashboard/Topology tabs needed one (`embarch-api/design.md` §3 decision 38). Full execution plan: milestone 1 §4.1/§4.2.

6. **Real-time: standardize on SSE everywhere, not the mixed SSE/polling split the two source UIs have today.** `embarch-topology`'s UI already pushes alerts live over a `tokio::broadcast`-backed `/events` SSE endpoint; `embarch-study-designer`'s UI instead polls a JSON status endpoint once a second. `embarch-ui` adopts SSE as the one mechanism across every section — Dashboard's active-study/alert cards, Topology's board/alert list, Study Designer's run log, and Debug's live log tail all update by push, not by client-side interval polling.

7. **Debug tab: a genuinely new suite-wide capability, not a repackaging of something that already existed.** Neither source UI streamed logs. `embarch-core` gains `GET /logs/stream` (SSE, live tail) and `GET /logs/recent` (returns the tail of Core's own logfile, so the Debug tab has backlog on first open rather than starting blank) — mirroring the alert/SSE pattern Core already has for topology mismatches. `embarch-ui` never reads Core's logfile directly: Core can run on a different machine than `embarch-ui` (a real, already-supported topology class — the whole reason `embarch-topology` exists), so direct filesystem access would work today on a single-machine dev setup and break silently the moment someone runs a split topology. Both endpoints go over the same HTTP+Bearer channel as everything else — the UI is handed the data, never the file. Retention: a simple size-capped rotating logfile (`tracing-appender`-style), not a time-based policy — bounded disk use, no separate cleanup pass needed. `embarch-api`'s own logs are explicitly not addressed by this decision (§5).

8. **Visual design system, settled against real mockups (2026-08-24).** Dark-first developer-console aesthetic, togglable to a light palette: IBM Plex Sans for UI text, IBM Plex Mono for data/parameters/log lines; an oklch-based token system (one cyan accent, green/amber/red semantic status colors, consistent chroma/lightness held across hues); a real component set — stat cards, status badges, data tables, pill toggles, chip inputs, and a terminal-styled console/log panel — replacing the two source UIs' single inline `style=` attribute and bare `<style>` block respectively. Zero-build throughout (decision 2): tokens and components are hand-authored CSS, no bundler.

    **Light-palette caveat resolved 2026-08-24:** the mockups' own theme-toggle script already authors a complete light-mode oklch token set alongside the dark one (found reading the saved `.dc.html` files directly), so "not yet exercised standalone" no longer applies — both palettes are lifted verbatim into `embarch-ui`'s own stylesheet (milestone 1 §4.3), not re-derived.

9. **Repo: created 2026-08-24.** [gabrieltetar/embarch-ui](https://github.com/gabrieltetar/embarch-ui), empty, matching how `embarch-umbrella`, `embarch-topology`, and `embarch-dev-bench` each started — `embarch-ui`'s dependency on `embarch-study-designer` and `embarch-api`'s `crates/embarch-core-client` as path dependencies (decision 5) needed a real repo to exist before implementation could begin in earnest, the same reasoning `embarch-topology/design.md` decision 13 already recorded for itself. See milestone 1 for the execution plan now that it exists.

10. **Topology tab gains the one declaration a human makes about wiring: a DUT signal's route — and a Trace view renders an outpost capture post-hoc, 2026-08-25.** Both from the new [embarch-outpost](../embarch-outpost/design.md) sub-project.

    **Routing belongs in the Topology tab, next to the diagram it changes.** Each declared signal ([embarch-topology/design.md](../embarch-topology/design.md) §3 decision 18) gets a row: its name, its origin role, and a route selector — `direct`, which then asks for a serial-port pick from Core's own enumeration, or `via dev-bench`, which then asks for pins. The diagram redraws from the same data, so a signal on a `direct` route is **drawn going around the dev-bench node** rather than through it: the picture matches the wiring, including when the wiring is deliberately unusual. Backed by a new Core endpoint, the same shape as `POST /dev-bench/link` (`embarch-core/design.md` §3 decision 27) and for the identical reason — Core owns writes to that storage, decision 5's rule that every hardware-adjacent call goes over HTTP applies unchanged. **Confirmed and made concrete 2026-08-25** (`embarch-topology/design.md` §3 decision 18's amendment, settling that doc's own §5): the endpoints are `POST /signals` and `GET /signals` — the read one added because `list_signals` has never had an HTTP caller and this tab has to list declared signals before it can offer to change one — and there is deliberately **no** `embarch-topology` CLI mirror, so this tab is the only human surface there is. One consequence for this tab specifically: a signal that is declared but wrong shows up here or nowhere, since a `SignalMismatch` is not written to the alert log this tab already renders (closed as not-needed-yet there, since nothing can currently raise one).

    **Not the Enroll tab, and not the Study Designer.** Enroll answers "which physical board is which," a question about identity; routing answers "what is wired to what," a question about the bench — related but not the same declaration, and the Topology tab is already where the second one is *shown*. The Study Designer was rejected outright: a study names a signal, never a carrier ([embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 39), so putting routing there would bind bench wiring into saved studies and re-author every one of them the day a cable moves.

    **The Trace view is post-hoc, deliberately.** Outpost capture is study-scoped with no live feed ([embarch-outpost/design.md](../embarch-outpost/design.md) §3 decision 10), so this renders a completed study's recorded timeline — the one place in this UI that is not live, and it is the honest shape for the data rather than an omission. Two things it must not do, both being the visual form of a lie the rest of the suite works hard to avoid: **a dropped-record gap is drawn as a gap**, labelled with what was lost, never bridged into a continuous timeline; and **a trace whose manifest CRC did not match is not rendered at all**, only reported, since a mislabelled trace reads perfectly and is entirely wrong. What the timeline actually looks like is deferred to the first real capture (§5), the same posture every other tab here took.

    **Built 2026-08-26 (Milestone 7 Phase D), and five things this decision did not say turned out to be load-bearing.**

    **(a) Two of the endpoints this needs did not exist, and one of them existed for nothing.** `POST`/`GET /signals` had shipped in Phase B, but `embarch-core-client` — which every call from here goes through — had no wrapper for either, so Phase D touches `embarch-api`'s workspace as well. Beyond that, two new Core routes: `GET /serial-ports`, because "a serial-port pick from Core's own enumeration" had no enumeration to pick from (`/dev-bench/port` answers a different question and VID-gates to do it, which would hide exactly the bridge a `Direct` route names); and `DELETE /signals/{name}`, because this decision's own "this tab is the only human surface there is" plus `declare_signal`'s idempotency meant the one place that can state a wire could not retract one.

    **(b) "Not rendered at all" was too strong, and Phase C is why.** This decision said a trace whose manifest did not match "is not rendered at all, only reported." Core's implementation settled something better: the rows *are* written, unnamed, with the reason in `streams/index.json` — because a timeline of numeric thread pointers is a real answer, and it is honestly distinguishable from a named one (`embarch-core/design.md` §3 decision 30(c)). So the requirement is not "render nothing", it is **never render it as a named trace**: the view leads with a banner saying the trace has no names, carries Core's reason verbatim, and every lane below is the raw pointer or vector number it actually is. Recorded as [embarch-decision-reversals.md](../embarch-decision-reversals.md) row 45. Note "manifest CRC" in the sentence above is also stale — the check is a build ID, since `embarch-outpost/design.md` §3 decision 9's rework.

    **(c) Nothing over HTTP could tell a refused trace from a named one**, which made (b) unbuildable as stated. `GET /study/{id}` returns `StreamRef { name, bytes_written, truncated }` with no room for the reason, and `GET /study/{id}/stream/{name}` serves the rendered CSV either way — so `streams/index.json`'s `note`, the field Phase C added precisely to record *why* a trace has no names, had no HTTP caller at all. Settled with a third new route, `GET /study/{id}/streams`, rather than a field on `StreamRef`: that type lives in `embarch-study-designer` and rides inside `StudyResult`, so growing it is a host schema bump for a fact that is Core-side bookkeeping and means nothing to dev-bench.

    **(d) A gap band is not an empty interval** — the finding that changed the drawing. A gap says *records were lost in here*, not *nothing happened here*: the records at both ends of a band survived. So the band is drawn as an overlay over what survived, with every span it touches flagged as continuity-not-established, rather than as a hole punched through real data. Erasing real records to make the picture tidier would be its own version of the lie this half exists to avoid.

    **A band is a bound on the host's clock and a measurement on the DUT's** ([embarch-outpost/design.md](../embarch-outpost/design.md) §3 decisions 4, 5, 17). On the host's, a gap record is guaranteed to be the *first record of its frame*, so the losses fall between the previous frame's arrival and that frame's; the band is that interval, deliberately drawn *wider* than one frame when a header frame arrived in between, because a rendered trace carries only frames that held records and cannot see the header's arrival. Too wide is still a bound; too narrow would be a claim. On the DUT's clock, restored by layout 3, the firmware states the interval outright — `cycles` is when the first record was dropped and `b` is the cycles to the last — so the band is arithmetic, `unbounded_start` is never set, and it is typically far tighter than the frame bound. Layout 1's opposite problem is back and handled: a gap's own stamp precedes the rows printed after it, because the FIFO ring is still draining records reserved before the overflow, so the band's end comes from `b` and never from "the next row".

    **(e) What the timeline looks like was deferred to the first real capture; it was designed against the closest thing that exists.** The committed `native_sim` capture (`embarch-core/tests/fixtures/outpost-native-sim.bin`, 848 records, 41 frames, 4 gaps) produced by the real firmware encoder — not a DUT, and stated as such. Three of its seven thread pointers resolve to no name, and every ISR record reports `IRQ_UNKNOWN` because that ELF has no `_sw_isr_table` at all; both are the *common* case on a real image (`embarch-outpost/design.md` §3 decision 8), so "unnamed" is a first-class state here rather than an error path, drawn italic and dotted with the number as the label. One thing the fixture changed directly: markers began as full-height rules and 132 of them across 760 ms swamped every span on the chart, so they became a bright tick in their own strip plus a very faint rule.

    **(f) The load repartition, built 2026-08-26 (Milestone 7 Phase E), and the one thing it refuses to do.** "Understand the load repartition in the DUT firmware" is what a results UI is *for*; the timeline came first only because a gap is visible on a timeline and invisible in a total. Per subject — each thread, each ISR vector, CPU idle — it reports entries, measured spans, total time, and share of the capture window, as arithmetic over the spans `parse` already builds. It is not a second decode, which is the property that matters: every caveat it reports is one a `Span` already carried.

    **A repartition computed across an interval where records were dropped is not a measurement**, so classes of span whose drawn width is an *extent* rather than a duration are excluded from a total and *counted separately* rather than folded in or dropped. Three of them are properties of the *records*: crossing a gap, no closing record, no opening record. **The fourth is a property of the clock** — `below_resolution`, added under layout 2 as `same_frame` and renamed 2026-08-27 when layout 3 made the distinction load-bearing. On the host's frame clock it means both ends arrived in one frame; on the DUT's per-record clock it is never set, because both ends stamped themselves. `entries` counts every span regardless, because "this subject ran N times" survives all four doubts. The gap-covered fraction of the window is rendered **above** the table, not as a footnote, because it is the number deciding whether the rest is a measurement at all.

    **(g) The axis is a three-tier choice over the two clocks the wire carries, and picking the wrong tier was worth a 46× error — reworked 2026-08-27.**

    Written 2026-08-26 for layout 2, when the DUT had no clock and Core's per-frame receipt stamp was the only time a trace had. Layout 3 restored a per-record microsecond stamp ([embarch-outpost/design.md](../embarch-outpost/design.md) §3 decisions 4, 17) and **this view did not follow for a day**: it went on timing every span by its frames' arrivals, so a span whose ends fell in adjacent frames was charged the whole frame interval. On the reference reference-dut capture that reported the outpost's own drain thread at **78% of the measured extent** where the DUT's own clock says **1.6%** — 3.9 ms charged for 85 µs of work — and reported **4286 of 4955 spans** as below the resolution when **none** of them were. Nothing was wrong with the wire; the coarser of two available clocks was being read. [embarch-decision-reversals.md](../embarch-decision-reversals.md) row 86.

    So `unit` has three tiers, chosen **once per view** and named in `axis_clock`:

    | `unit` | `axis_clock` | requires | what it is for |
    |---|---|---|---|
    | `us` | `dut-cycles` | every row has a `us` | **measuring** — both ends of a span stamp themselves |
    | `ms` | `host-arrival` | every row's frame is stamped | **placing** — the clock every other stream in the study is on |
    | `frame` | `frame-index` | neither | order, with no duration claimed |

    Five rules this view enforces, each of them a lie it would otherwise tell:

    - **A tier is chosen for a whole view, never per span.** Measuring the long spans on one clock and the short ones on the other is a mixed axis arrived at one span at a time, and unauditable. One row missing the stamp its tier needs drops the entire view to the next tier down.
    - **Both clocks are reported even though one draws the axis.** `resolution_ms` stays populated on the DUT clock, labelled as the **placement** resolution: it is how finely this trace can be laid against a power capture, which is the one job the DUT's counter cannot do. `dual_clock` says a capture has both.
    - **Records in one frame are drawn at one instant *on the host's clock*.** Spreading them across the interval would look better and be fabricated. On the DUT's clock they have their own instants and are drawn at them, which is not interpolation — it is the stamp the firmware wrote.
    - **What is below the resolution is a property of the clock, not of the wire.** On the host's clock a span inside one frame has zero extent and is excluded while still being counted — most ISR spans are exactly that, so **on that clock this view reports ISR entries and refuses to report ISR time** (389 of the committed `native_sim` capture's spans). On the DUT's clock it reports both: 24.8 ms across 4955 measured ISR spans on the reference capture, 0.6% of the window, `uarte_nrfx_isr_async` at 9.9 µs a call.
    - **A backwards axis position is reported, not smoothed.** On the host's clock it means the wall clock stepped mid-capture (an NTP correction); on the DUT's it means Core's unwrap lost a wrap. Either way the axis note says so.

    **A gap band is a measurement on the DUT's clock and a bound on the host's**, and the difference is not small. A gap record stamps the cycle of the *first* dropped record and carries the cycles to the last in `b` (`outpost.c`'s emit site), so the DUT clock draws the interval the firmware actually measured. The host clock can only reach back to the previous record-carrying frame. Two consequences: the DUT-clock band never sets `unbounded_start`, and a gap's own stamp legitimately runs **ahead** of the records printed after it — the ring is FIFO, so records reserved before the overflow are still draining behind the record reporting it — which is why the band's end comes from `b` rather than from "the next row".

    `named` and `timed` are now read as two separate booleans from `GET /study/{id}/streams`. They have to be: `embarch-api`'s old `rendered && note.is_none()` rule called an untimed-but-named trace unnamed, and a trace can be either without the other.

Thread lanes alone are the mutually-exclusive set; the idle-record lane is a **corroborating** figure that is never added. The two are also allowed to *disagree* — and they do, on the committed capture, because some idle-record spans have no closing record — and the disagreement is surfaced rather than averaged away.     **(i) The chart could be read and not navigated, and the fix rests on a measurement that contradicts the obvious framing — 2026-08-27.** Everything above draws a capture; nothing above lets a reader *look* at part of one. The reference reference-dut capture is 147.5 s and 112,801 spans across 26 lanes drawn into a fixed-width SVG, which puts a 34 µs ISR run inside one pixel column with no way to open it. Wheel over the plot zooms at the pointer, drag pans, double-click or a Fit button returns to the whole capture, and the window is clamped to `t_from..t_to` so a reader cannot end up staring at empty axis wondering whether the trace stopped.

    **It stays SVG, and "112,801 rects is too many to re-render" is the wrong way to frame it.** Once sub-pixel spans are aggregated into per-pixel occupancy runs per lane, **the element count is bounded by pixels × lanes, not by the dataset** — measured in the browser against the real view at a 990 px plot, the worst case across every zoom level is ~2,500 rects, aggregating in 3.6 ms and redrawing in 27 ms. A canvas rewrite would have cost CSS-variable theming (colors would come from `getComputedStyle`), hand-written hit-testing, and amendment (h)'s browser harness's ability to inspect what was drawn — to solve an element count aggregation had already bounded. Per lane the visible window is a binary search, because `parse` builds a lane's spans in record order off a clock it has already vetted.

    **Aggregation is exact, and that is checked rather than asserted.** A merged run is split wherever `crosses_gap`, `below_resolution` or an open edge changes, so a block can never fold an unvouched-for span into a clean-looking bar — which is the quiet lie this whole decision exists to prevent, arriving through the back door of a performance optimisation. Splitting on all four costs nothing on real data (1,937 rects either way at full zoom), so the honest version is also the cheap one. Audited in the browser against the raw spans at five zoom levels: identical occupied columns, identical flags per column, identical span counts. A block that merged more than one run says so and **refuses to report a duration**; a block that is exactly one run still says everything that span said.

    **(j) The study-action row: which step was running, projected onto the axis and told which clock it is on — 2026-08-27.** A timeline with no answer to "what was the study doing here" is a picture; with one it is a diagnosis. A pinned row above the lanes carries one band per step, labelled, coloured by the outcome Core recorded — `Pass`, `Fail` and `TimedOut` are all present in a single real capture — and **shaded to separate the delay the study declared from the execution**. That split is not cosmetic: dev-bench sleeps `delay_before_ms` as part of dispatching a step, so it genuinely falls inside the step's window, and without the split `close-nus-window` reads as a 5-second step when it ran for 23 ms.

    **The stamps had to be recorded, because `events.json` step entries carried no time at all.** `embarch-core` now writes both edges of each step's window plus its declared delay, and serves them from `GET /study/{id}/steps` (`embarch-core/design.md` §3 decision 30's amendment). Core's own arrival stamps, deliberately — putting a timestamp in `StepResult` would be a dev-bench wire bump, a schema version, a hand-written C encoder change, and a third clock in a picture that already has two. `gatt.csv` already carries `step_index` and `core_rx_utc_ms` and was the tempting UI-only version; it covers only steps inside the transcript's declared scope that produced GATT traffic — on the reference capture, steps 2–10, **missing the two-minute drain**, which is the stretch anyone actually wants to look at.

    **Three axis cases, each named rather than guessed**, and they are (g)'s three tiers again:

    - `us` / `dut-cycles` — the axis is the DUT's counter and the stamps are the host's, so each band is **projected** through the frames carrying both clocks and the row carries `resolution_ms` as its accuracy. Good to about 12 ms on a real capture, invisible against seconds-long steps — **and said out loud anyway**, in the axis note's own idiom and in the row's gutter label, because the lanes beneath are microsecond-exact and a row that looked aligned to them would be claiming a precision it does not have.
    - `ms` / `host-arrival` — the axis already *is* Core's receipt clock, in the same absolute UTC the stamps are in. No projection, no caveat, exact alignment.
    - `frame` / `frame-index` — no time base, so a step **cannot be placed**, and none is: no bands, and the reason said instead. Both of the first two cases were produced by real runs on 2026-08-27; the same study run twice, ten minutes apart, landed on a different tier each time.

    **Three ways this goes quietly wrong if built the obvious way.** The projection is built from the rows the view kept and drops a stale pre-reset prefix — the DUT's counter restarts at reset and a capture can open with bytes that were already inside the USB-UART bridge, which Core's port flush cannot reach; the prefix ends at the single largest *backward* step between frame anchors, filtered at 10 ms so the benign kind is left alone (a hook stamps before it reserves its ring slot, so a preempting interrupt is stamped before the thread it preempted — 93 µs at worst across a 225,606-row capture, against seconds for a restart). An anchor is a frame's arrival against the **last** DUT stamp in it, since a frame is sent once the last record it batched is in. And a step that overruns the capture is **clipped, not moved**: a tap's scope is a step range and is routinely narrower than the study, so a band whose edge is the capture's edge says so, and a step entirely outside the window is left out rather than squashed against `t_from`. Which of those two a step is has to be decided by **overlap**, not by whether either edge could be placed — see (k), where deciding it the other way cost the row the one band that mattered most.

    **A gap record must not anchor that projection, and finding out cost the first real capture's step row.** A gap record is stamped when the first *dropped* record was lost rather than when the drain thread reported it, so its stamp sits outside the run its own frame carries — 487 ms ahead of every other record in the same frame, on a capture whose largest row-to-row step is 20 ms. Left in, 147 of 12,476 frames were poisoned: `batchmgr-start-ppg` vanished from the row entirely and `open-bds-data-window` came out starting 0.4 s *before* the step before it had ended. `parse` already excluded gap records from both of its backstep measurements for exactly this reason; the projection was the third place that rule belonged and the only one that had not got it. [embarch-decision-reversals.md](../embarch-decision-reversals.md) row 97.

    **(k) A bug-fix pass over the whole tab, 2026-08-31 — and the three findings worth keeping are all the same shape: a comment that named the right invariant sitting over code that did not implement it.** Ten defects fixed, each verified by running the thing rather than by reading it again; the mechanical ones are in the Changelog. Four bear on this decision.

    **A lane's spans overlap, and the fixture already proved it.** The chart found a lane's visible spans by a lower bound on `from` plus one step back, over an explicit comment asserting that a lane's spans never overlap. They do, exactly when the capture lost a record: a dropped `thread_switch_out` leaves its run open, and (d)'s own rule draws every still-open span out to `t_to`, so later runs of the same thread sit *inside* it — two of `0x08058240`'s 65 spans in the committed `native_sim` capture. The step-back halted on the first nested span and the enclosing one disappeared from every zoomed window past it, which is (i)'s aggregation-must-be-exact property failing on the read side rather than the merge side. The search is now over the lane's running maximum of `to`, non-decreasing by construction and so still one binary search. [embarch-decision-reversals.md](../embarch-decision-reversals.md) row 100.

    **A thread is never inside itself — a new invariant, and the other half of the same finding.** The idle lane already closed an open run when a second entry arrived, on the stated grounds that the record which should have closed it was among the losses. Nothing applied that rule to threads, so two switch-ins with no switch-out between them left both runs open and drew the first across every later run of itself. One CPU runs one thread, so this is a scheduler invariant rather than a claim about any firmware, and it is now enforced. **Deliberately not extended to ISRs:** `isr-unidentified` is a *bucket* for every vector the manifest could not name ((e)'s common case), so two of its spans overlapping is a higher-priority vector nesting inside a lower one — real, and a stack is the right shape for it. Both cases have tests; the fix changed no total, because the affected spans were already excluded as open-ended.

    **The step row's own clipping rule, corrected in (j) above.** Bands were decided by whether each edge could be projected, which drops a step *enclosing* the capture — neither edge is inside the window — and that is the ordinary shape of a tap opened and closed inside one long step. The single step running for the whole trace was the one step the row never drew. Deciding by overlap in host milliseconds first, then clipping the unplaceable edge to its own side, covers both cases.

    **A delay that ended before the capture opened is not a delay.** (j)'s split shaded the band from `from` to the projected end of `delay_before_ms`, and read an unplaceable delay end as "past the capture's far edge" in *both* directions. Before the near edge is the common case, not the rare one — the delay runs first, so a tap opening partway into a step opens *after* it — and those bands were drawn as though the whole visible span were a sleep, which is precisely the misreading the split exists to prevent, arriving from the other end.

    **The routing half's one defect was in the markup, and it made the migration path unreachable.** Decision 10's "re-declaring the same name *is* the migration path" is what the signal table's "Move route" button exists to start. Every one of those buttons rendered its `data-signal-edit` attribute empty — a stray quote closed it before the name reached it — so the handler looked up a signal named `""`, found none, and opened the dialog on a blank *read-only* name field. The only human surface there is for retracting or moving a wire had no working way in, and no Rust test could see it. Found and fixed by rendering the row in headless Firefox and reading the attribute back, the same instrument amendment (h) established.

11. **Study Designer gains the two version fields; the run dialog gains the reflash selector; results show provenance — 2026-08-25.** The human surface for [embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 40.

    **The two `requires` fields are prefilled from live bench state, not left blank.** dev-bench's currently-reported version comes from Core's `GET /dev-bench/hello`; the DUT's comes from the configured project's own `git describe`. Prefilling is what makes a mandatory field a help rather than a tax — the common case is "the builds currently in front of me," and typing a hash by hand to express that would guarantee people paste `any` to get past it, defeating the decision.

    **`any` is a visible, deliberate choice in the UI** — a checkbox reading "any build," not an empty field that happens to validate. Same reasoning as above, from the other direction: the decision's value comes from the operator having actually considered it.

    **Reflash lives in the run dialog, never in the saved study**, matching decision 10's split for signal routes: the study is the experiment, the run dialog is this particular run. A mismatch is shown *before* the run starts, next to the reflash selector, with both strings — so the choice is made against the actual discrepancy rather than in the abstract.

    **A result renders how each version was established, not just what it was.** `Declared` gets visibly weaker treatment than `ReportedByDevBench`/`FlashedThisRun` — an unverified assertion that looks identical to a verified reading is the exact defect decision 40 exists to close, and a UI is the easiest place to accidentally reintroduce it.

    **Built 2026-08-26 (Milestone 7 Phase D) — every half except reflash, which is scoped out with its reason recorded.**

    **The reflash selector is not built, and that was a decision rather than an omission.** `run_study --reflash none|dev-bench|dut|both` is an **`embarch-api`** feature: it sequences check → build → flash → submit, and `embarch-api` owns the project config and the build machinery. `embarch-ui` posts studies straight to Core and builds nothing; Core's `POST /study` accepts only `allow_version_mismatch` and `flashed_firmware_version`, and neither flashes anything — the second is the caller *reporting* what it already flashed, which is what makes `VersionSource::FlashedThisRun` honest. So the three options were: duplicate `embarch-api`'s orchestration here (a second implementation of something one crate already owns — the exact shape decision 1 and `embarch-topology` were built against), give `embarch-ui` a dependency on `embarch-api` (a direction the suite does not currently have anywhere), or land the rest and leave this named. **Settled with the user, 2026-08-26: the third.** The run dialog says so out loud rather than leaving a gap a reader has to notice, and points at `embarch-api run-study --reflash`. Carried into §5 as an open question; nothing about the rest of this decision depended on it.

    **What did land.** `requires` prefilled from live bench state on first paint, re-readable on demand: dev-bench from `GET /dev-bench/hello`, the DUT from the configured project's own `git describe`. `any` is a checkbox that visibly takes the field over — the input keeps showing the literal and goes disabled rather than being cleared, so the checkbox *is* the statement instead of a way of not making one. A blank field is refused rather than quietly upgraded to `any`, because `Requirements::validate` treats blank as the not-thought-about case and silently promoting it to a deliberate answer would erase the distinction the whole decision rests on. A mismatch is shown before the run with both strings, next to the override — and **unreadable is rendered as unreadable, which is not a mismatch**: a bench that is not plugged in has no version to disagree with, and presenting that as a discrepancy would be a claim about a gap nobody established. `Declared` renders dashed, muted and italic — three separate signals, because one a reader can miss is the same as none — and `verified` is decided server-side by `VersionSource::is_verified`, never re-derived in JavaScript, since deciding for itself which variants count is the easiest way for a UI to reintroduce the defect decision 40 closes.

    **One thing had to move for the DUT half to exist at all.** `DEFAULT_VERSION_COMMAND`, `derive_version` and the never-move-the-tree rule that guards them lived in `embarch-api`'s `reflash.rs`, and `embarch-ui` cannot depend on `embarch-api`. They now live in `embarch-core-client::version` and `reflash.rs` re-exports them (`embarch-api/design.md` §3 decision 40). The alternative was a second copy of that argv and that rule in a crate that would never see its tests.

    **Tap authoring landed with this, because a Trace view with no way to author an outpost tap is a view of nothing.** `embarch-ui`'s own `seal_crc` had said so since it was written — this tab authored no taps, so `streams_crc` always resealed to the empty-list value. The Study Designer now has a Streams card that authors a `StreamTap { source: Signal { name }, encoding: OutpostTrace, scope: WholeStudy }`, and `streams_crc` seals a real non-zero value. Neither `OutpostTrace` nor `WholeStudy` is offered as a choice: an outpost capture is study-scoped with no live feed by design and its encoding is the one thing a trace tap can be, so a menu whose other entries are all wrong would be worse than no menu. The ordering this implies — routes before taps — is **verified rather than assumed**: a study whose tap names an undeclared signal is rejected by Core's `POST /study` pre-flight with a `400`, and the same study with a declared signal gets past it.

    **`BleSecurity` is an ordinary step in the step table**, authored like any other, with `level` as a four-option select (`L1`/`L2`/`L3`/`L4`) carrying one line of what each means in practice rather than the bare Zephyr constant — "encrypted, authenticated (LESC)" is what an engineer picks by; `BT_SECURITY_L4` is what it compiles to. **Not** a hidden toggle on the connect step and **not** something the UI inserts on the author's behalf: a study that needs an authenticated link should show a step that says so, because the whole argument for a separate `Action` (decision 44) is that a failed elevation must be legible as itself.

13. **The Debug tab reads `embarch-api`'s logs from a rolling per-machine logfile, not from an endpoint, 2026-08-25.** Decision 7's `/logs/recent` + `/logs/stream` pattern works for Core because Core is a long-running service with a logfile to mediate. `embarch-api` is the opposite shape: spawned per Claude Code session as an MCP server, or run once as a CLI and gone. There is nothing to poll, and by the time anyone wants to see what a one-shot did, the process that could have answered has exited.

    `embarch-api` appends every invocation — both modes — to one rolling file under the machine data dir, pid- and mode-tagged so interleaved sessions stay separable ([embarch-api/design.md](../embarch-api/design.md) §3 decision 43). This tab tails it with the same reader already pointed at Core's file. The property that decides it: the record outlives the process, which no endpoint-based design can offer here.

    **Implemented 2026-08-25.** The Debug tab gained a source switch — `embarch-core` / `embarch-api` — backed by `/api/api-logs/recent` and `/api/api-logs/events`, mirroring the two Core routes exactly. Switching is a **full console reset, not a merge**: the two files rotate independently, so interleaving them by arrival order would put lines in an order their own timestamps contradict. `logs.rs`'s poll/diff loop is shared; only the fetch differs (Core over HTTP, `embarch-api` from the file, via the `embarch_core_client::api_log` path `embarch-api` itself writes through).

    **This is a real exception to decision 7's "never read a logfile, always go over HTTP," and it does not reopen that argument.** Decision 7's reasoning is that *Core* can run on a different machine than `embarch-ui` — a supported topology this suite exists to handle. `embarch-api` cannot: it is spawned by the MCP client sitting in front of the engineer, on the machine this UI is opened on. Reading its file locally is correct for precisely the reason reading Core's was not.

    **Two defects fixed in the same pass, both pre-existing and both visible in this tab.** Core's logfile carries ANSI escape sequences (its writer tees one colored stream to stderr and file), and this tab was rendering them as literal garbage around every level and target — now stripped at render, so the *deployed* Core is readable, not just a future one. And every browser opening this tab was shown the log stream's most recent batch on top of its own backlog fetch, as duplicate lines: a `watch::Receiver` cloned from one whose `changed()` was never awaited inherits the initial version, so the first `changed()` returns immediately. `mark_unchanged` at subscribe time is what `api_logs_events`'s own comment had always claimed the code did.

    **Two more, 2026-08-31, and both had a comment over them claiming the code already handled it.** The live tail's diff anchored on the previous window's last line and searched the new window *backward* for its most recent occurrence, so any log line repeating verbatim later in the window swallowed every line in between — under a comment stating the opposite preference outright ("a few duplicate lines in a debug viewer is a smaller problem than missing ones"), and with a test asserting the loss as intended. The window is a contiguous run of one append-only file, so the anchor is now the longest suffix/prefix overlap rather than one line that may appear twice ([embarch-decision-reversals.md](../embarch-decision-reversals.md) row 102). And **the "full console reset, not a merge" property above was not actually held**: the backlog fetch was un-awaited and carried no identity, so switching source while `/recent` was in flight landed the old source's 200 lines in the new source's console, under the new source's heading — reproduced against the live Core with only Core's `/recent` delayed, and exactly the timestamp-contradicting interleaving this decision refuses a merged stream in order to avoid. A generation token, bumped on every switch, now invalidates a stale answer (row 101).

    **Not: `embarch-api` shipping its lines to Core.** One place to read from, reusing mediation that already exists — but it breaks the invariant that Core has no idea `embarch-api` or any MCP client exist, which holds up far more than logging. **Also not: nothing at all**, on the argument that an MCP client surfaces its server's stderr and a CLI prints to the terminal in front of you. Both true; neither survives wanting to know what an agent's `embarch-api` did twenty minutes ago in a session that is now closed.

    **The invariant that makes this more than a text box: `firmware_repo_path` is read by three different things** — the saved-studies directory (`embarch-study-designer/design.md` §3 decision 38), the custom-action registry (decision 34 there), and the static GATT extractor (decision 33 there). A switch has to move all three together or the tab shows one repo's studies beside another repo's registry. So the open project lives in one `Mutex<Option<StudyDesignerConfig>>` and switching is a single assignment, and both per-project caches — the last live `GattDiscover` and the static extraction — are dropped with it. The static-extraction cache stopped being a `OnceLock` for exactly this reason: a `OnceLock` that has been set cannot be un-set, so the first project's extraction would have been served for every project after it. It becomes `Mutex<Option<Option<_>>>`, where `None` is "not computed for this project" and `Some(None)` is "computed, and there is nothing" — two different facts a `OnceLock` could not tell apart once the project became switchable.

    **A repo with no `embarch/` directory is a first-time state, not a fault** — `api_studies_list` already tolerates a missing studies directory and the first save creates it — so the survey reports "is this a source repo" and "does it have studies yet" as separate answers, and the acceptance rule only looks at the first. **A bare `embarch/` subdirectory is not evidence of anything, and a live run is how that was learned:** the first acceptance rule counted it, and on this bench that accepted `$HOME`, because the suite's own parent folder is `~/embarch`. A directory *called* `embarch` says nothing about its contents; something `embarch init` or this tab actually wrote inside it (`study-actions.toml`, `studies/`, `embarch.toml`) does. The rule is now `.git` **or** a firmware/Cargo marker **or** a real `embarch/` config, and a refusal names all of them rather than saying "invalid".

    **Recent projects persist in the per-user data directory, not in the config file.** `EMBARCH_UI_CONFIG` is a file an engineer writes and this process only reads; writing a UI convenience into it would mean rewriting a human's own file, comments and all. They go to `<per-user data dir>/embarch/ui/recent-projects.json` — the directory `embarch-api`'s own logfile already established (`embarch-api/design.md` §3 decision 43's 2026-08-25 correction), now shared through `embarch-core-client::user_dirs` rather than resolved twice. `EMBARCH_UI_STATE` overrides it. An unreadable or absent file is an empty list, logged, never an error: a convenience list that can refuse to start the tab would be worse than no list.

    **"Create study" writes a study that is valid the moment it exists**, through the same `build_authored` a save uses rather than a shape only this route can produce: `requires` written as an explicit `REQUIREMENT_ANY` on both fields (mandatory with no serde default — `embarch-study-designer/design.md` §3 decision 40's "it has to be *said*"), both CRCs sealed, and both `_embarch_ui_rows`/`_embarch_ui_taps` sidecars present so it is `editable` and loadable from the moment it is created rather than only after its first save. A name whose slug already exists is a `409`, never a silent overwrite. It lives at `POST /api/study-designer/new-study` and deliberately **not** at `/studies/new`, because `study_slug` accepts `"new"` as a perfectly good slug and that path would be ambiguous with a real study named `new` on the sibling `{slug}` route.

15. **The Study Designer authors GATT capture: a per-characteristic tap, a decoder picked from the firmware repo, and a transcript nobody has to remember — 2026-08-26.** The UI half of [embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decisions 52/53/54/55, raised by the repo owner authoring a real study here and finding `GattMonitorAll` was the only monitor available.

    Three surfaces. A **selective monitor row** renders a checkbox per notify/indicate-capable characteristic — never a free-text UUID list, since the whole point is picking from what discovery actually found, and the service UUID comes from the same entry the checkbox was rendered from so a row's two UUIDs cannot disagree. A **GATT notify tap** gives one characteristic its own file, with a decoder dropdown populated from the firmware repo's `embarch/study-structs.toml`; "raw bytes" stays selectable and is the honest default. And **taps became a tagged union** (`TapInput::Outpost`/`GattNotify`) rather than one struct with optional fields — "no signal" and "no characteristic" are different authoring mistakes with different fixes, and an untagged shape makes them the same one.

    **The transcript tap is auto-declared, not a checkbox, and that is the decision worth arguing.** Any study with a monitor step gets an uncapped `GattTranscript` tap at `streams/gatt.csv` whether or not the author asked. Before this pass, this tab authored *no* GATT tap at all — so a monitor step's capture existed only as `StepResult.gatt_activity`'s first 32 records, and that field is now retired. A checkbox would make "monitor everything and record none of it" reachable by leaving a box unticked, which is not a configuration anyone wants and is precisely the silently-empty capture this suite keeps rediscovering. An author who declares their own `GattTranscript` tap keeps it; the auto tap is skipped rather than duplicated.

    **A tap whose characteristic no step subscribes to is refused here, before submit.** It would otherwise capture nothing, pass, and look fine. This tab is the only place that holds both the resolved steps and the taps, so it is the only place that can catch it — Core sees a tap list that is internally valid, and dev-bench sees a tap it will faithfully route zero notifications to. Checked against the *resolved* `Action`s rather than the raw rows, because whether something is subscribed is a property of what a row became.

    Validated in the headless-Firefox harness ([embarch-dev-workflow.md](../embarch-dev-workflow.md)-adjacent technique, recorded in that session's notes): the step row renders its checkboxes and its "n characteristics subscribed" line, both tap kinds render side by side in one table, and `sdCollectRows` resolves a checked UUID back to the `{service, characteristic}` pair the server parses.


16. **Every characteristic picker shows a name; the UUID moves to the tooltip — 2026-08-26.** The human half of [embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 56, raised by the repo owner authoring a study here immediately after decision 15 shipped the pickers: "the option show up as numbers." They did — `00000002`, `00000003`, `00000004` — and on this DUT the choice was between eighteen characteristics differing in one hex digit.

    **One name map for the whole response, not a `name` field on the subscribable list.** `GET /api/study-designer/actions` gains `characteristic_names`, keyed by hyphenated characteristic UUID. Four places in the browser render a characteristic — a selective-monitor checkbox, a GATT tap's dropdown, a new tap's default file name, an unregistered-characteristic chip — and **three of them read from `actions`, not from `subscribable`**. A field on one list would have named the options in one picker and left the same characteristic a bare UUID in the next, which is a worse state than uniformly showing UUIDs. It covers every characteristic any source found rather than only the notify-capable ones: a name is a name regardless of what a study can do with it.

    **The UUID never stops being the identity.** It is what a checkbox's `value` carries, what `sdCollectRows` sends, and what `charTitle` puts in every tooltip alongside the label's provenance — "the vendor publishes this name" reads differently from "your own source spells it this way", and an engineer has to be able to tell them apart. A characteristic nothing names falls back to the UUID head, unchanged.

    **A tap's default file name is the characteristic's name.** `+ GATT notify tap` named the new tap `00000002`; it now names it `sds_hrm_rrm`, sliced to `MAX_STREAM_NAME_LEN` so an over-long identifier is trimmed here, where it was chosen, rather than refused by `build_study` at submit.

    **One CSS fix that is a real bug, not a polish pass.** `.sd-param > span` uppercases a parameter's *caption*, and a selective-monitor checkbox borrows `.sd-param` for its layout — so the name rendered as `SDS_HRM_RRM`. Invisible while that span held hex digits; wrong the moment it holds a C identifier, because an identifier's case is part of it and the firmware source does not spell it that way. New `.sd-param-value` opts the value spans out.

    Validated in the headless-Firefox harness against the **real** `reference-dut-fw` checkout, with a running `embarch-ui` serving its real `characteristic_names` (15 names, all from firmware source): the checkbox list reads `sds_hrm_rrm` / `sds_spo2` / `sds_skin_temp` / … , the tap dropdown reads `sds_hrm_rrm · notify`, and the unregistered pool reads `sds_hrm_rrm 00000002 · notify · source`. A refinement of that harness worth keeping: **strip the app's own `DOMContentLoaded` initializer** out of the evaluated IIFE body before rendering — it fires *after* an inline harness script and re-renders every panel from fetches that fail under `file://`, silently clobbering the state the harness just set up.

17. **The selective-monitor target list becomes a dialog, grouped by named service — 2026-08-26.** Raised by the repo owner one decision after 16, looking at the same row: "instead of having all options with check box can we have a drop down menu with checkbox? Or something better." Decision 15 rendered **one inline checkbox per notify/indicate-capable characteristic** into the step table's Parameters cell — eleven on this DUT, thirteen once [embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 57's repo-wide scan found the `bds` service — which made one row taller than the rest of the table put together and could only grow.

    **A dialog, not a dropdown and not an inline disclosure.** Three shapes were on the table and the app's own history picked between them:

    - **Rejected outright: `<select multiple>`.** No visible checkboxes, ctrl-click discovery, and it renders as a text field on a bench where every other multi-select in this app is explicit. A native control that looks like a text box is not "something better".
    - **Rejected: a floating popover in the cell.** The step table lives inside an `overflow-x: auto` wrapper (`style.css`), so an absolutely-positioned panel in a cell is clipped by the table's own scroll container; escaping it means `position: fixed` plus scroll-tracking plus outside-click handling, which is a lot of machinery for a zero-build vanilla app (decision 2) to carry.
    - **Rejected: an inline `<details>` disclosure.** It was the obvious first answer and it loses on two counts. There is **no `<details>` anywhere in this app**, so it is a new pattern to be consistent about — while `.dialog`/`.dialog-backdrop` is a pattern **four** existing places already use (run-check, register-action, signal, probe-assign). And expanding inline still makes the row tall, just on demand; a dialog keeps it one line always. It also collides with how this table works: the step table re-renders `innerHTML` on every change, so a `<details>` would snap shut on each checkbox click unless its open state were tracked in the row model — machinery a dialog doesn't need because its state lives outside the table.

    **What the cell holds instead: one line.** `2 of 13`, the first two picked characteristics as `.probe-card` chips, `+N more` beyond that, and a `Choose…` button. Nothing new was drawn for it — `.probe-card` is the Enroll tab's chip and `.dialog` is the existing modal.

    **Grouped by service, with per-group all/none.** This is what made the service-naming work worth doing in the same pass ([embarch-study-designer/design.md](../embarch-study-designer/design.md) §3 decision 56's 2026-08-26 amendment): the group headings read `bds_service` / `sds_service` / `dms_service` rather than `00000020` / `00000001` / `00000010`. Groups keep discovery's own order rather than sorting — that order is the DUT's, and a picker that reorders it stops matching what `Discover GATT` printed. A filter input matches the label, the origin identifier, the characteristic UUID and the service alike.

    **Decision 15's two invariants are untouched, and that is the point of the shape.** Options come from `sdSubscribable` and nowhere else — there is still deliberately no free-text UUID box, because a step naming a characteristic nothing has seen is a run that fails on the bench. A picked characteristic's *service* UUID is still read back out of the same discovery entry the option was rendered from at submit time, so a row's two UUIDs cannot disagree. And an empty selection is still refused rather than promoted to "everything": the cell says so, the dialog says so, and `sdCollectRows` still throws.

    **The cap becomes visible, having been enforced only server-side.** `limits::MAX_MONITOR_TARGETS` is now **served** on `GET /api/study-designer/actions` as `max_monitor_targets` rather than restated in `app.js` — a browser-side copy of a limit is a number that drifts silently the day the limit moves. The dialog shows `n of N · max 16`, disables unchecked boxes at the cap (rendered, not hidden — hiding one would look like discovery had lost it), disables the per-group `all` at the cap rather than offering a control that would add nothing, and says what to do instead: a study wanting more than this wants `GattMonitorAll`.

    **Two silent losses found and fixed while in here, neither of them cosmetic.**

    - **A saved study's selective-monitor targets did not survive being reopened.** `sdLoadStudy` read a `built_in` row's `which`/`role`/`target_name` and stopped — so `targets` came back empty and `security_level` reset to the default, both without a word, even though `TableRow` round-trips them perfectly well. Reopening a saved study silently discarded the selection it was saved with.
    - **A picked characteristic the current discovery no longer knows about was dropped in silence.** `sdCollectRows` resolves each UUID back to a discovery entry and `.filter(Boolean)`s away whatever doesn't resolve — the correct behavior (there is no service UUID to pair it with) done invisibly. It is now surfaced in the cell and in the dialog, naming the UUIDs and saying they will be dropped.

    **The list is patched on a toggle, not rebuilt — found by deploying it, not by review.** The first implementation re-rendered `.sd-targets-list`'s `innerHTML` on every checkbox change, which destroys the node that was just clicked: `document.activeElement` falls back to `<body>`, so a keyboard user pressing Space on a checkbox is returned to the top of the tab order. Measured against the deployed binary (`focusedAfter: BODY` before, `INPUT/checkbox` after the fix), and the same for a bulk `all`/`none` button, which now keeps focus too. Scroll position happened to survive because the rebuilt content had identical height — luck, not design, and not something to rely on. So `renderTargetDialog` builds the list (on open, and on a filter change) and a new `syncTargetDialog` patches checked/disabled/counter/note in place. Worth recording because the inline checkbox list this replaces had the same flaw and worse — it re-rendered the entire step table on every tick — so this is a defect that was inherited invisibly rather than introduced.

    Validated in the headless-Firefox harness against a running `embarch-ui` serving the **real** `reference-dut-fw` checkout (13 subscribable characteristics across the three named services): the collapsed cell reads `2 of 13 · bds_status · bds_data · Choose…` at the same height as a `BleConnect` row; the open dialog shows three named groups with correct all/none states; filtering to `bds` leaves 2 rows; at the cap (exercised by lowering the served cap to 3, since this DUT has fewer characteristics than the real limit) 10 rows go disabled, both `all` buttons go disabled, and a bulk `all` click stops at 3 rather than overshooting; an emptied selection still throws `pick at least one characteristic…`; and a target UUID discovery does not know about is reported in the cell and drops to 1 collected target rather than 2.

    **Then re-validated against the deployed binary itself**, driving the real page with real clicks rather than a harness (`assets/` is `include_str!`-embedded, so the deployed artifact is the only thing that can be checked): opening the project from its recents list, adding a step, switching it to `GattMonitorSelected`, opening the dialog, ticking two boxes in sequence, clicking a group's `none`, and committing. Two sequential clicks landing at all is itself the check that the patch-in-place fix works — against the rebuild-on-toggle version the second click hit a detached node and the count went to 1 instead of 2.

## 4. Relationship to existing sub-projects

- **`embarch-topology`** — `bin/ui.rs` **retired outright, 2026-08-24** (milestone 1 §4.9), now that `embarch-ui`'s Topology tab covers what it did, but **`embarch-ui` is not a dependent of this crate at all**: the Topology tab's board list, attached-probe enumeration, alert history, and diagram data all come from `embarch-core`'s existing HTTP endpoints (`GET /status`, `GET /probes/enrolled`, `GET /alerts`, `GET /dev-bench/port`) via `embarch-core-client`, not from an in-process call into `embarch_topology::hardware` — the same "never link probe-rs/serialport" rule `embarch-api` already follows. Its existing SSE alert-broadcast mechanism was the direct model for decision 6's suite-wide SSE convergence, just not a shared code path. A real, orphaned gap this retirement surfaced (tracked in `embarch-topology/design.md` §5): `hardware::alert::push_live`/`fix_it_url`'s marker-file live-push mechanism had no UI to reach any more, since `embarch-ui` gets alert data by polling Core's `GET /alerts` instead of running a loopback receiver. **Closed 2026-08-25 by that doc's §3 decision 19** — the mechanism was deleted rather than given a destination, and `fix_it_url` is now a fixed link at this UI's Topology tab. **That cost this repo one change**, which is the only way `embarch-ui` is touched by any of it: `assets/app.js`'s `initNav` picked its tab from `localStorage` alone, so an inbound link could not name a tab at all; it now reads a `#<tab>` fragment first (with a `hashchange` listener, so following the same link twice in an open tab still switches). Nothing else here moved, and this repo still does not depend on `embarch-topology`.
- **`embarch-study-designer`** — `tools/study_designer_ui.rs` **retired outright, 2026-08-24** (milestone 1 §4.9); `embarch-ui` depends on the crate directly (`study-ui` + `gatt-extract` features) for the Study Designer tab's merged action list, custom-action registry, and Study-building logic — genuinely pure/offline logic scoped to the firmware repo being edited, unaffected by decision 5's amendment. Unlike the retired `study-designer-ui` binary (which shelled out to `embarch-api`'s CLI for `run-study`/`study-status`), `embarch-ui` talks to `embarch-core` directly over HTTP+Bearer for actually running a Study, via the shared `embarch-core-client` crate (decision 5).
- **`embarch-core`** — gained `GET /logs/stream` and `GET /logs/recent` (decision 7); its `GET /enroll` HTML page **retired outright, 2026-08-24** (milestone 1 §4.9) in favor of `embarch-ui`'s Enroll tab, which submits to Core's existing `POST /probes/enroll` (unchanged) — Core keeps every endpoint it has today, lost only the page that rendered a form around one of them, and `build_router` no longer has a public/protected split at all (every route requires the bearer token now). `embarch-core-client` (physically part of `embarch-api`'s repo, `crates/embarch-core-client/`) gained `list_enrolled`/`dev_bench_port` wrappers for two Core endpoints (`GET /probes/enrolled`, `GET /dev-bench/port`) that had no client wrapper anywhere until `embarch-ui` needed one (`embarch-api/design.md` §3 decision 38).
- **`embarch-api`** — unaffected as the agent-facing surface; not a dependency of `embarch-ui` and not depended on by it. `embarch-ui` does depend on a crate that physically lives inside `embarch-api`'s repo (`crates/embarch-core-client/`, decision 5), but that crate is independent of `embarch-api`'s own binary/MCP/CLI code — both simply depend on it.

## 5. Open questions / future work

- **The reflash selector in the run dialog (decision 11) is deliberately not built, and where it should live is genuinely undecided.** `run_study --reflash` is `embarch-api` orchestration — it sequences check → build → flash → submit and owns the project config and build machinery — while `embarch-ui` posts studies straight to Core and builds nothing. The three shapes are: duplicate the orchestration here (a second implementation of something one crate already owns), give `embarch-ui` a dependency on `embarch-api` (a dependency direction the suite has nowhere else), or leave reflash a terminal-only affordance. **Settled for Phase D as the third, and the run dialog says so** — but "the UI cannot reflash" is a real limitation rather than a design goal, so this stays open. Whichever answer wins, `allow_version_mismatch` and the before-the-run mismatch display are already built and unaffected.
- **The Trace view has rendered a simulator's capture and never a DUT's — still true after Phase E, for a physical reason.** Decision 10 deferred the timeline's look to the first real capture; the committed `native_sim` capture is what it was actually designed against (see that decision's own note (e)). Every wire constant in `embarch-outpost/design.md` §5.3 is still an unmeasured default with the instrumentation's own overhead deliberately uncharacterised, so a working view is not validation of the numbers underneath it. **Phase E did not close this**: no trace was read off the DUT, and why is not established — the first diagnosis (an unwired trace pin) was withdrawn 2026-08-27 ([embarch-outpost/design.md](../embarch-outpost/design.md) §3 decision 16's amendment). Either way there was nothing for Core to read and nothing new for this view to render. The load summary below was therefore built against the same simulator capture, which is a real limitation of it and not a formality.

  **This bullet has now been wrong twice in two days, in opposite directions, and the second correction is the one to keep.** It first noted that a `native_sim` run reports zero cycles for every ISR span, "so the ISR half of a load repartition has never been exercised against a counter that advances." On 2026-08-26 that was rewritten to say there is no counter any more, so an ISR span is **permanently** below this instrument's resolution and the view reports ISR entries and refuses to report ISR time. **Layout 3 put the counter back the same day**, and on the first real DUT capture (2026-08-27) the ISR half is measured: 4955 ISR spans, all of them timed, 24.8 ms total = 0.6% of the window, `uarte_nrfx_isr_async` at 9.9 µs across 1540 calls, `rtc0_nrf5_isr` at 33.6 µs, the radio vector at 18.2 µs. The "refuses to report ISR time" posture is true only of the host-arrival tier now (decision 10's amendment (g)).

  **What remains genuinely unmeasured is narrower and it is about the other clock.** How coarse and how jittery a real frame's arrival is — the *placement* resolution — is now observed at 4.0 ms median on the reference capture, but nothing has compared a trace's placement against a second stream in the same study to see whether the two actually line up. That is the check `dual_clock` exists to enable and it has not been run.

- ~~**A per-thread load summary is not built.**~~ **Built 2026-08-26** (decision 10's amendment (f)): per subject — thread, ISR vector, cpu idle — entries, measured spans, total extent and share of the capture window, computed over the spans `parse` already produces rather than by a second decode. **Four** classes of span are excluded from a total and counted separately, because their drawn width is an extent and not a duration: crossing a gap, no closing record, no opening record, and below the axis clock's resolution (amendment (g)). The gap-covered fraction of the window is rendered *above* the table, since it is what decides whether the rest of it is a measurement. **First run against a real DUT capture, 2026-08-27:** the fourth class emptied out — 0 of 4955 spans on the DUT's clock, against 4286 on the host's — and the summary's `unaccounted_extent` fell from 10.6% of the window to 0.1%.
- **A `SignalMismatch` still has nowhere durable to land, so a declared-but-wrong signal shows up in the Topology tab or nowhere.** `embarch-topology/design.md` §3 decision 18's amendment closed this as not-needed-yet under a two-part trigger — a signal being declarable, and a physically real `Route::Direct` existing. **Half of it fired on 2026-08-26**: signals are now declarable through this tab, which is the only surface for it. The other half has not; there is still no wire and no bridge. The consequence is stated in decision 10 and carried by the row's own carrier cell, which says "not enumerated on Core right now" against a declared serial nothing answers to — this tab does not lean on the alert list for it.
- **The Trace view caps at 250,000 rows per view and says so** (`rows_dropped_by_cap`, rendered as part of the Records stat rather than swallowed). It used to say "no real capture has come close" and "still no real volume to judge against"; **both stopped being true on 2026-08-27**, when the reference reference-dut capture came in at **225,606 rows — 90% of the cap** — with `rows_dropped_by_cap: 0` only because the study was two and a half minutes long. A five-minute one overflows it.

  **The cost that real volume exposed is not the cap, though — it is the transfer.** That view serializes to a **13 MB JSON** the browser waits for and then holds 112,801 spans from. Decision 10(i)'s aggregation made the *drawing* independent of dataset size, which leaves load time as the only remaining term and makes the windowed fetch this bullet has always pointed at a concrete, sized piece of work rather than a hedge: a `?from&to&width` endpoint on `/api/trace/{id}/{name}` binning server-side in Rust, which is the same aggregation the browser now does and the right side of the wire to do it on. Deliberately **not** folded into the navigation work, because it is a load-time problem and that was a redraw problem, and conflating them is how a measured decision turns back into a guess.
