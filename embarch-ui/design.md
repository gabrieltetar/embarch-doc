## 1. Purpose and scope

The suite has accumulated three separate, inconsistent human-facing UI surfaces, each built ad hoc as its owning sub-project needed one: `embarch-topology`'s `ui` subcommand (read-only board/alert view, SSE-live), `embarch-study-designer`'s standalone `study-designer-ui` binary (Study builder, polling-based), and `embarch-core`'s own `GET /enroll` page (the one write-capable form among the three, added specifically because a second UI-owning process calling `hardware::enroll` directly would have bypassed Core's `hw_lock` — `embarch-topology/design.md` decision 14). Each is plain, unstyled HTML with no shared design, running on its own binary and port.

`embarch-ui` exists to be the one place a firmware engineer actually looks to exercise suite features by hand — day to day, not just when an agent needs a hardware read — replacing all three surfaces outright rather than adding a fourth alongside them.

`embarch-ui` is **not**:
- A build-toolchain project. Solution A holds: no npm/Node, no bundler — Rust-served HTML, with a real hand-rolled design system doing the work a framework would otherwise buy (§3 decision 2).
- Embedded inside VS Code as a webview. The VS Code extension is a thin launcher — start/stop the server, open the system browser — nothing renders inside the editor itself (§3 decision 3).
- A second owner of hardware mutation. Enrollment writes and study execution still go through `embarch-core`'s own process and its `hw_lock`, over HTTP — `embarch-ui` never calls a hardware-mutating function directly in-process, even though it links the crates that define those functions (§3 decision 5).
- A replacement for `embarch-api`'s MCP/CLI surface. Agents keep talking to `embarch-api`; `embarch-ui` is the human-facing counterpart, not a new agent transport.

## 2. Architecture overview

```
embarch-ui (one Rust binary, axum)
  |
  +-- links embarch-topology        (in-process fn calls: board/probe enumeration,
  |                                   alert history, topology-diagram data — read-only)
  |
  +-- links embarch-study-designer  (in-process fn calls: merged action list,
  |                                   custom-action registry, Study-building logic — pure data)
  |
  +-- HTTP + Bearer --> embarch-core (same channel embarch-api uses)
                           - hardware-mutating ops: POST /probes/enroll, run_study dispatch
                           - GET /logs/stream   (SSE, live tail)
                           - GET /logs/recent   (backfill from Core's own rotating logfile)

VS Code extension (thin, TypeScript)
  - spawns/stops the embarch-ui binary as a subprocess
  - opens the system browser at its bound address
  - renders nothing itself
```

Five sections behind one persistent sidebar shell: Dashboard, Topology, Study Designer, Enroll, Debug. A visual review pass (static mockups) is done as of 2026-08-24 — see §3 decision 8 for the settled design system.

## 3. Locked-in design decisions and rationale

1. **Scope: one consolidated process, not a shared library three separate binaries keep depending on.** Following the same "one implementation, multiple call sites" shape `embarch-topology` already established for topology detection (`embarch-topology/design.md` decision 8) — except here the consolidation is the *UI surface itself*, not just the logic behind it. `embarch-topology`'s `bin/ui.rs` (413 lines) and `embarch-study-designer`'s `tools/study_designer_ui.rs` (812 lines) both get retired outright; `embarch-core`'s `GET /enroll` page's HTML also moves out of Core (Core keeps the underlying `POST /probes/enroll` endpoint it already had). Settled directly on the user's own framing: "1 UI for the whole project, just like the topology project centralized all topology from the suite."

2. **Frontend tech: Solution A (zero-build, Rust-served HTML), pushed to a real design system rather than replaced with a framework.** The alternative — a real SPA framework (React/Svelte) + a Vite build step, with the built bundle vendored into the Rust binary so the *end user* still only ever runs one binary — was weighed on its actual merits: a real component/chart/table ecosystem and a faster path to visual polish, against a second toolchain (Node/npm) at build time, new CI legs, new supply-chain surface, and an explicit break of the suite's stated "Rust, one toolchain" principle. Decided against it: stay zero-build, but stop treating "plain unstyled HTML" as the ceiling and actually invest in hand-rolled CSS, type, and component design. Confirmed against real mockups (decision 8) before committing further.

3. **VS Code integration: a thin launcher, not an embedded webview or a native VS Code UI.** Manages starting/stopping the `embarch-ui` server process and opens it in the system browser. Two alternatives were considered and rejected: hosting the same HTML inside a VS Code Webview panel (real CSP/localhost-connect plumbing, in exchange for never leaving the editor), and a native TreeView/Custom Editor built from VS Code's own UI toolkit (a second, separate presentation layer hitting the same JSON API). Neither matched the actual ask, which was reach into the editor for convenience — not a second UI to build and keep in sync with the first.

    **Repo layout, resolved 2026-08-24 (`milestone-1.md` §4.8): a subdirectory of `embarch-ui` (`vscode-extension/`), not a sibling repo.** Matches this decision's own "one consolidated thing" framing (decision 1) and `embarch-ui`'s own `bin`-adjacent-tooling precedent — no VS Code marketplace packaging constraint was found that forces a split (`vsce package`/`npm`/`tsc` all work fine rooted at a subdirectory). Scaffolded as a real TypeScript source tree (`package.json`, `tsconfig.json`, `src/extension.ts`): commands to start/stop the `embarch-ui` subprocess and open the system browser, a status-bar toggle, and settings for the binary path/host/port/config path/auto-start.

    **Build/package verification, closed later the same day.** This session's sandbox had no `node`/`npm` at all (the same gap decision 8's changelog noted for the mockup canvas step) — resolved by downloading a portable Node build to a user-local directory (`~/.local/node`, no root needed), not a system package. `npm install && npm run compile` (TypeScript `strict`, `noUnusedLocals`/`noUnusedParameters`) is clean, and `npx @vscode/vsce package` produces a real, valid `.vsix` — the same tool/output the chosen distribution path (below) uses. Real gap found and fixed doing this: `vsce` refused to package over a broken relative `SEE LICENSE IN ../LICENSE` field (a file outside the packaged subdirectory) — fixed by copying `LICENSE` into `vscode-extension/` and switching the field to a plain `"MIT"`. The packaged `.vsix` was then installed for real into this session's own VS Code (`code --install-extension`, confirmed via `--list-extensions`) — `--extensionDevelopmentPath` isn't supported by the remote-CLI shim this environment exposes, so a real install (exactly the internal-`.vsix` distribution path below) stood in for a disposable Extension Development Host. **Live-confirmed working by the user afterward**, in their actual Windows VS Code (Remote-WSL, attached to this same WSL2 instance): start/stop/open-in-browser all function correctly against the real debug binary once `embarchUi.binaryPath` was pointed at it.

    **Distribution, resolved 2026-08-24 via `AskUserQuestion`: internal `.vsix` only, never the public Marketplace.** Matches the suite's current single-engineer, not-yet-public posture — `embarch-ui`'s own repo isn't pushed yet, and a Marketplace listing would need a publisher account/PAT and a real icon, neither of which exist. Install via `code --install-extension <path-to-vsix>` (exactly how this session's own verification pass installed it) or a shared file; `npx @vscode/vsce package` (no publish flag) is the one command that ever produces the artifact — `vsce publish` is never run.

4. **Shell: one app, not linked-but-separate pages.** A persistent left sidebar plus a top status bar, five sections behind it: Dashboard, Topology, Study Designer, Enroll, and Debug (new — present in none of the three existing surfaces). Client-side navigation between sections, one shared header/status chrome throughout, so it reads as one product rather than a pile of tools that happen to share a port.

5. **Backend wiring: every hardware-adjacent call, read or write, goes over HTTP+Bearer to `embarch-core` — `embarch-ui` never links `embarch-topology`'s `hardware` feature at all.** `embarch-ui` depends on `embarch-study-designer` as a library crate and calls it in-process, but only for pure/offline authoring logic that touches nothing but the firmware repo being edited: the merged action list, the custom-action registry, and Study-building logic (turning table rows into a `Study` value). Every capability that involves a physical board or Core's own storage — probe/board enumeration, alert history, dev-bench port detection, enrolling a board, running a `Study` — goes through `embarch-core-client` (decision 5's own amendment below) over HTTP+Bearer, the same channel `embarch-api` already uses, never through an in-process call into `embarch-topology`.

    **Originally split along a mutation/read-only line instead — reversed 2026-08-24, same day, prompted directly: "Instead of having the UI access hardware, can the UI use the Core to access it?"** The original framing put only *mutating* operations (enrolling, running a `Study`) behind Core, reasoning that read-only calls (`list_attached_probes`, `list_enrolled`, `recent_alerts`) were safe in-process since they don't race Core's `hw_lock`. That reasoning missed a second, worse failure mode the `hw_lock` framing never covered: those "read-only" calls still touch either live USB enumeration or a local file on whichever machine calls them — correct only when `embarch-ui` happens to run on the same machine as `embarch-core`, and silently wrong (missing probes, an empty/nonexistent `enrollment.toml`) the instant Core runs on a different machine, which is a real, already-supported topology class and the whole reason `embarch-topology` exists in the first place. This is the exact reasoning decision 7 below already used to keep the Debug tab from reading Core's logfile directly — it turns out to apply to every other hardware-adjacent read too, not just logs. The fix generalizes the rule `embarch-api` already follows and never violated: `embarch-api/design.md` §11 states plainly that it "never links against [probe-rs or serialport] directly; every hardware operation goes through Core's HTTP API" — `embarch-ui` now follows the identical rule, confirmed via `cargo tree -e normal` showing neither `probe-rs` nor `serialport` anywhere in its dependency graph.

    This still preserves the exact invariant `embarch-topology/design.md` decision 14 established when Core's own `/enroll` page was built for the mutation-safety reason: a second process calling a hardware-mutating function directly, without sharing Core's `hw_lock`, is a real class of bug that decision's own reversal exists to prevent. `embarch-ui`'s Enroll tab submits to Core's existing `POST /probes/enroll`; its Study Designer tab's "Run study" action submits a built `Study` to Core's existing dispatch path — both unchanged from the original framing, just no longer the only things routed through Core.

    **How `embarch-ui` reaches that HTTP path at all — resolved 2026-08-24, via `AskUserQuestion` rather than picked silently:** a shared library, not a duplicated client. `embarch-api`'s `core_client.rs` (plus the `CoreConfig`/token-resolution chain it depends on) is extracted into a new crate, `embarch-core-client`, that both `embarch-api` and `embarch-ui` depend on — following the same "one implementation, multiple call sites" shape `embarch-topology/design.md` decisions 2/8/14 already established, rather than growing `embarch-ui` its own independent client and reintroducing the exact mirrored-copy risk that precedent exists to eliminate. `embarch-core-client` gained two new methods the same pass, closing a real gap found doing this: `GET /probes/enrolled` and `GET /dev-bench/port` had no client wrapper in either `embarch-api` or the new shared crate until `embarch-ui`'s Dashboard/Topology tabs needed one (`embarch-api/design.md` §3 decision 38). Full execution plan: [milestone-1.md](milestone-1.md) §4.1/§4.2.

6. **Real-time: standardize on SSE everywhere, not the mixed SSE/polling split the two source UIs have today.** `embarch-topology`'s UI already pushes alerts live over a `tokio::broadcast`-backed `/events` SSE endpoint; `embarch-study-designer`'s UI instead polls a JSON status endpoint once a second. `embarch-ui` adopts SSE as the one mechanism across every section — Dashboard's active-study/alert cards, Topology's board/alert list, Study Designer's run log, and Debug's live log tail all update by push, not by client-side interval polling.

7. **Debug tab: a genuinely new suite-wide capability, not a repackaging of something that already existed.** Neither source UI streamed logs. `embarch-core` gains `GET /logs/stream` (SSE, live tail) and `GET /logs/recent` (returns the tail of Core's own logfile, so the Debug tab has backlog on first open rather than starting blank) — mirroring the alert/SSE pattern Core already has for topology mismatches. `embarch-ui` never reads Core's logfile directly: Core can run on a different machine than `embarch-ui` (a real, already-supported topology class — the whole reason `embarch-topology` exists), so direct filesystem access would work today on a single-machine dev setup and break silently the moment someone runs a split topology. Both endpoints go over the same HTTP+Bearer channel as everything else — the UI is handed the data, never the file. Retention: a simple size-capped rotating logfile (`tracing-appender`-style), not a time-based policy — bounded disk use, no separate cleanup pass needed. `embarch-api`'s own logs are explicitly not addressed by this decision (§5).

8. **Visual design system, settled against real mockups (2026-08-24).** Dark-first developer-console aesthetic, togglable to a light palette: IBM Plex Sans for UI text, IBM Plex Mono for data/parameters/log lines; an oklch-based token system (one cyan accent, green/amber/red semantic status colors, consistent chroma/lightness held across hues); a real component set — stat cards, status badges, data tables, pill toggles, chip inputs, and a terminal-styled console/log panel — replacing the two source UIs' single inline `style=` attribute and bare `<style>` block respectively. Zero-build throughout (decision 2): tokens and components are hand-authored CSS, no bundler.

    **Light-palette caveat resolved 2026-08-24:** the mockups' own theme-toggle script already authors a complete light-mode oklch token set alongside the dark one (found reading the saved `.dc.html` files directly), so "not yet exercised standalone" no longer applies — both palettes are lifted verbatim into `embarch-ui`'s own stylesheet (`milestone-1.md` §4.3), not re-derived.

9. **Repo: created 2026-08-24.** [gabrieltetar/embarch-ui](https://github.com/gabrieltetar/embarch-ui), empty, matching how `embarch-umbrella`, `embarch-topology`, and `embarch-dev-bench` each started — `embarch-ui`'s dependency on `embarch-study-designer` and `embarch-api`'s `crates/embarch-core-client` as path dependencies (decision 5) needed a real repo to exist before implementation could begin in earnest, the same reasoning `embarch-topology/design.md` decision 13 already recorded for itself. See [milestone-1.md](milestone-1.md) for the execution plan now that it exists.

## 4. Relationship to existing sub-projects

- **`embarch-topology`** — `bin/ui.rs` **retired outright, 2026-08-24** (`milestone-1.md` §4.9), now that `embarch-ui`'s Topology tab covers what it did, but **`embarch-ui` is not a dependent of this crate at all**: the Topology tab's board list, attached-probe enumeration, alert history, and diagram data all come from `embarch-core`'s existing HTTP endpoints (`GET /status`, `GET /probes/enrolled`, `GET /alerts`, `GET /dev-bench/port`) via `embarch-core-client`, not from an in-process call into `embarch_topology::hardware` — the same "never link probe-rs/serialport" rule `embarch-api` already follows. Its existing SSE alert-broadcast mechanism was the direct model for decision 6's suite-wide SSE convergence, just not a shared code path. A real, orphaned gap this retirement surfaced (not fixed here, tracked in `embarch-topology/design.md` §5): `hardware::alert::push_live`/`fix_it_url`'s marker-file live-push mechanism has no UI to reach any more, since `embarch-ui` gets alert data by polling Core's `GET /alerts` instead of running a loopback receiver.
- **`embarch-study-designer`** — `tools/study_designer_ui.rs` **retired outright, 2026-08-24** (`milestone-1.md` §4.9); `embarch-ui` depends on the crate directly (`study-ui` + `gatt-extract` features) for the Study Designer tab's merged action list, custom-action registry, and Study-building logic — genuinely pure/offline logic scoped to the firmware repo being edited, unaffected by decision 5's amendment. Unlike the retired `study-designer-ui` binary (which shelled out to `embarch-api`'s CLI for `run-study`/`study-status`), `embarch-ui` talks to `embarch-core` directly over HTTP+Bearer for actually running a Study, via the shared `embarch-core-client` crate (decision 5).
- **`embarch-core`** — gained `GET /logs/stream` and `GET /logs/recent` (decision 7); its `GET /enroll` HTML page **retired outright, 2026-08-24** (`milestone-1.md` §4.9) in favor of `embarch-ui`'s Enroll tab, which submits to Core's existing `POST /probes/enroll` (unchanged) — Core keeps every endpoint it has today, lost only the page that rendered a form around one of them, and `build_router` no longer has a public/protected split at all (every route requires the bearer token now). `embarch-core-client` (physically part of `embarch-api`'s repo, `crates/embarch-core-client/`) gained `list_enrolled`/`dev_bench_port` wrappers for two Core endpoints (`GET /probes/enrolled`, `GET /dev-bench/port`) that had no client wrapper anywhere until `embarch-ui` needed one (`embarch-api/design.md` §3 decision 38).
- **`embarch-api`** — unaffected as the agent-facing surface; not a dependency of `embarch-ui` and not depended on by it. `embarch-ui` does depend on a crate that physically lives inside `embarch-api`'s repo (`crates/embarch-core-client/`, decision 5), but that crate is independent of `embarch-api`'s own binary/MCP/CLI code — both simply depend on it.

Correct call — the original split only guarded against `hw_lock` races and missed a worse problem: an in-process read (`list_attached_probes`, `list_enrolled`, `recent_alerts`) queries whichever machine calls it, not Core's, silently wrong the moment Core runs on a different machine (the exact split-topology case `embarch-topology` exists for) — the same reasoning decision 7 already used for the Debug tab, just not generalized to every other read at the time. Now matches `embarch-api/design.md` §11's rule exactly: never link `probe-rs`/`serialport` directly, confirmed via `cargo tree -e normal`. `embarch-topology` is no longer a dependency of `embarch-ui` at all (only `embarch-study-designer` and `embarch-core-client` remain); `embarch-core-client` gained `list_enrolled`/`dev_bench_port` to cover the two Core endpoints that had no client wrapper yet (`embarch-api/design.md` §3 decision 38).
