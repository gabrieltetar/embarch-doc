**Status:** CLOSED, 2026-08-24. Repo created ([gabrieltetar/embarch-ui](https://github.com/gabrieltetar/embarch-ui)) — §4.1–4.7 done and live-validated (all five tabs real against the deployed Core), §4.8 done (VS Code launcher extension built/packaged/installed for real, distribution decided as internal-`.vsix`-only, and live-confirmed working by the user in their actual Windows VS Code), §4.9 done (the three surfaces this project replaces are deleted). This doc is the execution plan turning [design.md](design.md)'s decisions into ordered, concrete steps — see that doc for the architecture/rationale, not restated here.

## 1. Goal, restated

`embarch-ui` replaces three separate, ad hoc, plain-HTML UI surfaces — `embarch-topology`'s `ui` subcommand, `embarch-study-designer`'s `study-designer-ui` binary, `embarch-core`'s `GET /enroll` page — with one consolidated, visually real product: a persistent sidebar + top status bar shell around five tabs (Dashboard, Topology, Study Designer, Enroll, Debug), zero-build (Rust-served HTML, hand-rolled CSS, no npm/Node), SSE everywhere instead of the mixed SSE/polling split the two source UIs have today. In-process crate calls into `embarch-study-designer` alone cover pure/offline authoring work (Study-building, the registry); every hardware-adjacent capability — enumeration and alert history included, not just enrollment and running a `Study` — goes over HTTP+Bearer to `embarch-core`, the same "never link `probe-rs`/`serialport` directly" rule `embarch-api` already follows (design.md §3 decision 5's amendment). This milestone takes the project from an empty repo through all five tabs live, plus a thin VS Code launcher, and ends by retiring the three surfaces it replaces.

## 2. Decisions resolved before drafting this plan (design.md §5, no longer open)

Per design.md's own instruction not to guess on anything §5 marked open, three things were resolved via `AskUserQuestion` before this doc was written, rather than picked silently:

- **How `embarch-ui` reaches `embarch-core`'s HTTP+Bearer API:** a shared library, not a duplicated client. `embarch-api`'s `core_client.rs` (plus the `CoreConfig`/`token_discovery.rs` auth-resolution chain it depends on) is extracted into a new crate, `embarch-core-client`, that both `embarch-api` and `embarch-ui` depend on — following the suite's now-twice-established "one implementation, multiple call sites" precedent (`embarch-topology/design.md` §3 decisions 2/8/14) rather than reintroducing the exact mirrored-copy risk that precedent exists to eliminate. This is step 4.1 below and is a real architecture change to `embarch-api` itself, not just an `embarch-ui`-side implementation detail — `embarch-api/design.md` gets updated in the same pass it ships (§5 below).
- **Repo creation:** done. [gabrieltetar/embarch-ui](https://github.com/gabrieltetar/embarch-ui), empty, matching how `embarch-topology`/`embarch-umbrella`/`embarch-dev-bench` each started.
- **Mockup artboard location:** found at the path the user supplied (a local scratchpad directory, five `.dc.html` files plus `canvas.json`). Pulled directly rather than re-derived: an oklch dark-first token set with a **light-mode counterpart already authored** in the mockups' own theme-toggle script (`Main.dc.html`'s `<script data-dc-script>` block) — design.md §3 decision 8's "not yet exercised standalone" caveat is resolved by this alone, no new design-tool session needed. Component classes (`.card`, `.btn`/`.btn-primary`, `.badge-*`, `.data-table`, `.console`, sidebar/topbar/footer layout) are lifted verbatim into `embarch-ui`'s own stylesheet in step 4.3, not re-implemented from a text description.

**A fourth correction landed mid-implementation, not before drafting**: design.md §3 decision 5 originally split backend wiring along a mutation/read-only line — read-only calls (`list_attached_probes`, `list_enrolled`, `recent_alerts`) in-process via `embarch-topology`, only mutations through Core. Prompted directly while executing §4.2 ("Instead of having the UI access hardware, can the UI use the Core to access it?"), that split turned out to be wrong for a reason bigger than the `hw_lock` race it was designed around: an in-process read queries whichever machine calls it, not Core's, silently wrong the moment Core runs on a different machine (a real, already-supported topology class). §3 and §4 below are written to the corrected architecture — every hardware-adjacent call, read or write, goes through `embarch-core-client`; `embarch-ui` never depends on `embarch-topology` at all. Full account: design.md §3 decision 5's own changelog entry.

## 3. Scope for this milestone

- New repo `embarch-ui` — Rust workspace, `axum` server binary as the main member.
- New shared crate `embarch-core-client`, extracted from `embarch-api`'s repo (§2 above) — `embarch-ui` depends on it as a cross-repo path dependency, same shape as its existing `embarch-study-designer` path dep.
- Depends on `embarch-study-designer` (`features = ["study-ui", "gatt-extract"]`) in-process, for pure/offline authoring calls only (design.md decision 5) — never a hardware call in-process, and **not** a dependent of `embarch-topology` at all (§2's fourth correction): every hardware-adjacent call, read or write, goes through `embarch-core-client`.
- Zero-build frontend throughout: IBM Plex Sans/Mono via Google Fonts, the oklch token set + component CSS lifted from the reviewed mockups, no bundler anywhere.
- `embarch-core` grows `GET /logs/stream` (SSE) + `GET /logs/recent`, backed by a new size-capped rotating logfile (design.md decision 7) — needed for the Debug tab.
- `embarch-core`'s `GET /enroll` HTML page is retired (the endpoint's HTML is removed; `POST /probes/enroll` itself is unchanged and kept).
- `embarch-topology`'s `bin/ui.rs` and `embarch-study-designer`'s `tools/study_designer_ui.rs` are retired outright once `embarch-ui` covers what each did.
- VS Code extension: thin launcher (start/stop the `embarch-ui` binary, open the system browser), TypeScript, no webview, no native VS Code UI.
- **Out of scope for this milestone:** `embarch-api`'s own log treatment (design.md §5, unresolved — a different shape than Core's, since `embarch-api` is usually spawned per-session rather than long-running); multi-board/remote-Core UI modeling beyond what `embarch-topology`/`embarch-core` already resolved; VS Code marketplace publication (the extension gets built and runs locally; distribution format is asked about, not decided, before anything is published).

### 4.4 Dashboard + Topology tabs — via `embarch-core-client`, no in-process hardware access — done, 2026-08-24

**Dashboard:** board/probe enumeration, alert history, and dev-bench port status, calling `embarch-core-client`'s `status`/`list_enrolled`/`alerts`/`dev_bench_port` over HTTP+Bearer (§2's fourth correction) — no in-process `embarch_topology::hardware` call anywhere, since `embarch-ui` doesn't depend on that crate at all. **Topology:** the topology diagram (embarch-ui's own rendering, built from the same Core-fetched data — not a port of `embarch-topology`'s `bin/ui.rs` SVG-generation code, which operates on in-process types this crate deliberately no longer has), plus the same board/alert list. Both push updates over SSE rather than polling.

**Implementation shape**: a single background task (`src/snapshot.rs`'s `poll`, called from `main.rs`'s `poll_loop`) polls all four `embarch-core-client` calls concurrently (`tokio::join!`) on a 5-second interval and publishes one `Snapshot` onto a `tokio::sync::watch` channel — shared across every connected browser tab, so opening a second tab doesn't double the load on Core. `/events`' SSE handler sends the current snapshot immediately on connect, then again on every subsequent publish; `GET /api/snapshot` is a plain one-shot read of the same channel, for curl/debugging. Client-side (`assets/app.js`) renders both tabs entirely from the `"snapshot"` SSE event — no client-side polling anywhere, satisfying decision 6 literally, not just in spirit. `embarch-core-client`'s `ProbeInfo`/`StatusResponse`/`EnrolledBoardResponse`/`AlertResponse`/`DevBenchPortResponse` gained `Serialize`+`Clone` (behavior-neutral for every existing deserialize-only caller) so `embarch-ui` re-serializes what it deserializes from Core instead of hand-duplicating the same field lists.

**Definition of done — met:** matches `Main.dc.html`/`Topology.dc.html`'s layout (fixed dev-bench/dut role boxes + serial/BLE connectors, colored by enrolled/attached state, mirroring the mockup's diagram shape); confirmed by inspection that no hardware-touching crate (`probe-rs`, `serialport`, `embarch-topology`) appears anywhere in `embarch-ui`'s own dependency graph. **Live-validated against the real, already-deployed Windows Core** — not a mock: `base_url = "auto"` correctly resolved it at `http://172.22.128.1:4884` (`wsl-host` topology class), and `/api/snapshot`/`/events` returned the two real enrolled boards (`dut`/nRF54L15, `dev-bench`/esp32c5) and their real currently-attached probes exactly as `embarch-topology/milestone-1.md`'s own real-hardware validation recorded them. `dev_bench_port` came back empty this run (the link wasn't enumerable at the moment of testing) — rendered as an honest "not attached" state, not an error.

### 4.5 Enroll tab — submits to Core, never calls `hardware::enroll` in-process — done, 2026-08-24

Ports the drag-and-drop *interaction model* `embarch-core`'s current `GET /enroll` page already has (attached probes as draggable cards, drop onto a role zone, a chip-input dialog, click-to-select as a touch-friendly fallback) — submitting to Core's existing `POST /probes/enroll` over HTTP+Bearer via `embarch-core-client` (4.1), through a new `POST /api/enroll` on `embarch-ui`'s own server, never a direct in-process call to `embarch_topology::hardware::enroll`, which would reintroduce the exact `hw_lock`-bypass bug `embarch-topology/design.md` decision 14 already fixed once.

**A real UX improvement over the page it replaces, not just a port**: Core's own `GET /enroll` page is static markup with no server behind it, so it has no choice but to ask a human to paste in Core's bearer token by hand, kept in that origin's `localStorage`. `embarch-ui` already holds a live `CoreClient` server-side (the same one the Dashboard/Topology poll uses) — the browser talking to `embarch-ui` never sees Core's token at all. A successful enroll also wakes the same background poll loop immediately (a `tokio::sync::Notify`, not waiting out the rest of the 5s interval), so the Dashboard/Topology tabs and this tab's own enrolled-boards table reflect it on the very next SSE push.

**Real gap found and fixed along the way**: `embarch-core-client`'s `enroll_probe` never actually threaded `probe_serial` through at all, despite Core's real handler accepting it since `embarch-topology/design.md` §3 decision 15 — the exact field this tab's whole drag-and-drop model depends on (which specific dropped probe to enroll). Fixed at the client layer and threaded through `embarch-api`'s own `enroll-probe` CLI/MCP surface too, not just patched locally for this one caller (`embarch-api/design.md`'s own changelog has the full account).

**Definition of done — met:** the tab renders and drag-and-drop/click-to-select/dialog interactions are wired; **live-validated safely against the real deployed Core**, not skipped — a request with a `probe_serial` matching no currently-attached probe correctly round-tripped a `502` naming the real cause ("no attached probe with serial '...' — is it still plugged in?"), confirming the full `embarch-ui → embarch-core-client → Core → embarch_topology::hardware::enroll` path end to end **without** ever attaching to a real probe or writing to the real enrollment file. **Deliberately not tested with a real, currently-enrolled board's actual serial** — doing so would overwrite that board's real enrollment record (chip/role), a hard-to-reverse action against the user's actual working setup that this session did not ask to perform; a genuine enroll-a-real-board pass is left for the user to run themselves, or to explicitly ask for. `embarch-core/design.md` §4's endpoint table still describes the HTML page as live — retiring it is step 4.9, once every other tab is confirmed working, not this step.

### 4.6 Study Designer tab — in-process build/merge, HTTP-to-Core for execution — done, 2026-08-24

Ports `study_designer_ui.rs`'s registry-management/merged-action-list/table-builder logic (`embarch-study-designer/milestone-11.md` §3.1–3.3) onto `embarch-ui`'s shell: `embarch_study_designer::{registry, merged_actions, study_builder}` called in-process for authoring (unchanged — pure/offline logic, no hardware touched), but the built `Study` is submitted to `embarch-core`'s existing `POST /study` through `embarch-core-client` — **not** the `embarch-api` CLI-subprocess shim `study-designer-ui` uses today.

**Repo scoping, resolved via `AskUserQuestion` before this step started (never guessed):** `study-designer-ui` sidesteps "which firmware repo" by being launched from inside one; `embarch-ui` is one long-running suite-wide service with nothing in its config naming a repo at all — a real, previously-unnoticed gap. Resolved: a `[study_designer]` table in `embarch-ui`'s own config (`firmware_repo_path`, optional `static_extractor`), matching how `embarch-api`'s `[dev_bench].source_path` already works. Absent, the whole tab answers `404` with a clear "not configured" message rather than guessing.

**Real-time mechanism, a deliberate, documented deviation from decision 6's literal wording — not silent:** the design text says "watched via `GET /study/{id}/events` (SSE)." `embarch-core-client` never actually gained a wrapper for that endpoint (design.md itself already noted "no embarch-api/CLI consumer built yet"), and consuming a foreign SSE stream through `reqwest` is real, untested complexity for marginal benefit here. Implemented instead: `embarch-ui`'s own backend polls `GET /study/{study_id}` server-side (1s interval, via a `tokio::sync::watch` channel — the identical pattern the Dashboard/Topology poller already uses) and republishes over its own `GET /api/study-designer/events` SSE stream. Decision 6's actual property — **the browser never polls** — holds exactly as before; only *which* process does the polling underneath differs from the plan's literal text. `discover` (§3.6's one-click live discovery) uses the same `poll_until_terminal` helper synchronously instead of a background task, since it has its own 30s bound and returns the merged action list directly, matching `study-designer-ui`'s own precedent.

**A real, proactively-found stack-overflow bug, not a hypothetical one:** `main` was moved off a plain `#[tokio::main]` onto a dedicated big-stack thread *before* wiring this tab, reasoning from `embarch-api/design.md` decision 36's precedent that the same oversized `StudyResult` deserialization risk would apply here too on every `get_study_status` poll. That reasoning was correct, but the first attempt at the fix was incomplete — it only enlarged the thread that calls `block_on`, not `Builder::new_multi_thread()`'s own worker threads, which is where a `tokio::spawn`ed axum request handler actually runs. **This reproduced as a real crash**, live, the first time `discover` was tested against the real deployed Core (`thread 'tokio-rt-worker' has overflowed its stack, fatal runtime error: stack overflow, aborting`) — confirming decision 36's own account that `Builder::thread_stack_size` alone (this time on the *runtime*, not the calling thread) is the load-bearing half for a multi-thread runtime. Fixed by adding `.thread_stack_size(512 * 1024 * 1024)` to the runtime builder, matching `embarch-api/main.rs`'s exact shape byte-for-byte, not just its rationale. Re-tested clean afterward — the exact same `discover` call, and a real one-step `run`, both correctly relayed a genuine hardware-state error (dev-bench's link port not currently resolvable on this real machine) with no crash.

**Definition of done — met:** registry read/write round-trips verified against the real `reference-dut-fw` repo (a test action registered via `POST /api/study-designer/registry`, confirmed on disk and correctly deduplicated from `Unregistered` to `Registered` in the merged list, then cleaned up — `embarch/study-actions.toml` removed, repo left exactly as found); static extraction (`reference-dut`) against that same real repo returned 15 real, previously-unregistered characteristics; `discover` and a real one-step `run` were both submitted against the real deployed Core — both correctly surfaced Core's own real "dev-bench link port not currently resolvable" error (an honest environmental fact on this machine right now, not a code bug) with **no real BLE/hardware operation ever attempted** and no crash. `cargo build`/`cargo clippy --all-targets -D warnings` clean.

### 4.7 Debug tab — `embarch-core` grows `/logs/*` — done, 2026-08-24

**Real correction found before writing any code, not after:** design.md decision 7 said Core would gain "a size-capped rotating logfile (`tracing-appender`-style)." Reading `main.rs` first found Core already had one — a real, tested, daily-rolling `tracing-appender` file (7-file retention) backing the existing `embarch-core logs` CLI subcommand, added by an earlier decision this design pass simply hadn't noticed. Reused outright rather than building a redundant second mechanism: the existing selection logic (`latest_log_file`/`tail_lines`, previously private to `main.rs`) moved into a new shared `src/logs.rs` module so the CLI subcommand and the two new HTTP handlers call the identical implementation — matching this suite's own "one implementation, multiple call sites" precedent. `embarch-core/design.md` updated to describe reality, not the original size-capped plan.

**Two new endpoints, both under normal bearer auth** (unlike `GET /enroll`, these carry real backlog content): `GET /logs/recent?tail=<n>` (default 200) returns `{"lines": [...]}` — plain lines exactly as `tracing_subscriber`'s own formatter wrote them, no server-side level/component structuring (design.md §5's open question, resolved this way rather than reformatting Core's actual log output into JSON, which would touch a foundational, already-deployed piece of a live service for a debug-tooling feature). `GET /logs/stream` is SSE, polling the current log file every 750ms (`logs::FollowState`, new) and pushing newly-appended lines as one JSON-array event per tick — deliberately not a custom broadcasting `tracing` layer wired into `init_tracing`, for the same "don't touch foundational, already-deployed setup" reason; mirrors `serial::read_log`'s own existing poll-loop shape in this same crate. `FollowState` never replays a file's backlog on first use or on rotation (`/logs/recent` is the backlog path) — verified by three new unit tests (first-tick silence, new-lines-after-first-tick, rotation starts fresh from the new file's end), plus the two moved `latest_log_file` tests and the `tail_lines` tests, all now living in `logs.rs`.

`embarch-ui`'s side: `embarch-core-client` gained `logs_recent(tail)`. A new `src/logs.rs` module runs its own background poll of `GET /logs/recent` (2s interval, `POLL_TAIL = 500`) and republishes only the *new* lines since the last poll onto a `watch` channel — `diff_new_lines` anchors on the previous poll's last line (found by scanning backward, in case it repeats earlier in the window) and takes everything after it; falls back to replaying the whole window if the anchor aged out entirely (more than `POLL_TAIL` lines appended in one interval) rather than silently dropping content. 6 unit tests cover the anchor logic (no change, simple append, window sliding forward, anchor aging out, empty-previous, a repeated anchor line). `GET /api/logs/recent` proxies Core's endpoint once for the Debug tab's first paint; `GET /api/logs/events` (SSE) — deliberately **not** replaying its channel's last value on connect, unlike `/events`'s `Snapshot` stream, since replaying the last *new-lines batch* on every fresh subscribe would duplicate or desync backlog vs. live. Frontend (`assets/index.html`/`app.js`/`style.css`, CSS lifted from `Debug.dc.html`): a terminal-styled console, client-side level detection (`\bERROR\b`/`\bWARN\b`/`\bINFO\b` word-boundary match — tolerant of however `tracing_subscriber` did or didn't wrap the level in ANSI codes, not a fixed-column parse), clickable Info/Warn/Error filter chips, a live search box, and a working Pause button — all real, wired functionality, not decorative. The mockup's multi-component filter/raw-toggle were deliberately omitted rather than faked: this tab only ever has one real log source (`embarch-core`'s own), and `embarch-api`'s logs are explicitly out of scope (design.md §5).

**A real, proactively-found stack-overflow bug in `embarch-core` itself, not `embarch-ui`'s Study Designer tab this time:** unrelated to this step directly, but confirmed while working in `main.rs` — Core's own `build_runtime()` already carries the identical `thread_stack_size(64 MiB)` fix (its own decision, predating this session) for the exact same `heapless`-oversized-type risk this session's own `embarch-ui`/`embarch-api` fixes address. No new fix needed here; noted because it confirms the pattern generalizes across every process in this suite that ever deserializes a `Study`/`StudyResult`, not just the two this session touched directly.

**Definition of done — fully met, including the real happy path.** `embarch-core/design.md` §4 gains the two new endpoint rows; `cargo build`/`cargo test` (55 passed, up from 53)/`cargo clippy --all-targets -- -D warnings` clean in `embarch-core`, and clean in `embarch-api`/`embarch-ui` too. Live-tested in this sandbox first for graceful degradation (no writable `/var/lib/embarch` here — a local foreground `run` still started, both routes correctly required the bearer token, `/logs/recent` returned a clean real `500` rather than crashing, `/logs/stream` opened and retried without ever bringing the server down).

**Then genuinely deployed and validated for real, the same day, once the user explicitly asked for that specific deployment.** Built a real native Windows release binary via `cargo.exe` reached through WSL2 process interop (a staged sibling checkout at `C:\Users\tmp12\embarch-deploy-2026-08-24\`, not the user's own existing dev checkouts) — 55/55 tests passing on that real Windows build too, not just Linux. Self-updated the live `com.embarch.core` service via its own documented `update` procedure (`embarch-core/design.md` decision 28's exact invocation: run from the *installed* exe, pointing at the new build) — the one step needing the user's own interactive UAC click, which they gave; the service came back `Running` on the new binary. ### 4.8 VS Code extension — thin launcher — done, 2026-08-24

New TypeScript extension at `embarch-ui/vscode-extension/` (repo layout resolved: a subdirectory of `embarch-ui`, not a sibling repo — design.md §3 decision 3's own amendment; no marketplace-packaging convention was found that forces a split): start/stop the `embarch-ui` binary as a subprocess, open the system browser at its bound address, nothing rendered inside the editor. `package.json` (commands `embarchUi.start`/`.stop`/`.openInBrowser`, settings for `binaryPath`/`host`/`port`/`configPath`/`autoStart`), `tsconfig.json`, and `src/extension.ts` (spawns the process, watches its stdout/stderr for the real `"listening on"` log line before opening the browser rather than a fixed sleep, a status-bar toggle, kills its own child on `deactivate`). A subprocess this extension didn't start (e.g. run from a terminal) is left alone by `stop`/`deactivate` — only `openInBrowser` is meant for that case.
